# Recap

A stable reading of where one session stands, taken without disturbing it. The operator returns after hours away, or asks whether a session is safe to park, and needs the state without steering the session into new work. Plans run for days and the operator does not carry their details. A session's own working understanding also drifts from the plan it serves, and part (e) below is where that drift gets computed.

A recap fails in two directions. One is the recap that starts working: it notices a stale doc, fixes it, and now reports on a session it has itself changed. The other is the recap that reports nothing anyone can act on, marking every line inferred so the operator learns only that the session is uncertain. Both are miscalibrated. The reading has to be precise enough to decide on and cheap enough to take at any moment.

Paths here spelled `skills/` or `hooks/` are under the kit plugin root; `docs/plans/` is under the project.

## When this fires

The operator invokes it. A session recapping itself unprompted is the doctrine's ordinary close-with-the-state discipline and needs no skill.

## Restate before you read

**First, in the session's own words and before touching any file: the goal as this session currently understands it, and what it is working on right now.** Hold both in the turn; they enter the report at (a) and (e), and nothing goes to disk. Then the freshness pass. Then the report.

The order cannot be reversed, and the reason is mechanical rather than stylistic. A restatement composed after the plan doc is re-read is a paraphrase of that doc, and a paraphrase agrees with its source by construction, so it can no longer disagree with it and detects nothing. Only a restatement taken while the record is still unread carries the session's actual working understanding, which is the one thing the drift diff measures. Re-reading first yields a clean drift line every time, including every time there is drift. A session that already read the record this session, with no compaction between, still takes the restatement first; part (e) says what its diff is then worth.

## The freshness pass

Re-read, never re-verify. Five sources:

- **The plan doc from disk**, its latest Chapter read whole: `Completed:` and `Next:` are the record side of the restatement, `Gate:` is what part (b) reports, and `Review Findings:` feeds part (d). Loaded context is not the doc: a compaction keeps a summary and drops the contents, and a peer or the operator can have advanced the doc since it was last read.
- **Git against origin.** What is committed, what is pushed, what is still dirty, and what the branch tip on origin carries. Read that tip with `git ls-remote`, which asks the remote and writes nothing, neither a tracked file nor a ref, so it passes the bound below. A local remote-tracking ref read instead is stale by an unknown amount and silently so, which is the false reading a recap exists to prevent; where the remote is unreachable, the tip is an inferred claim naming `git ls-remote` as what would confirm it.
- **The leash**, read with `node <plugin-root>/hooks/kit-goal.js status` from the project directory (`<plugin-root>` is `CLAUDE_PLUGIN_ROOT` where the harness supplies it, else this skill's base directory's grandparent; the status call answers the directory it is run from, so run it from the tree root). Both halves of the binding matter, because the Stop hook keys on both: which plans a goal is armed for, with the current plan's queue position, and the binding, which `status` prints in one of three forms: bound to a named session id, carrying a last-active phrase only where the recorded transcript path resolves and its modification time can be read; unbound with an arming session recorded; and unbound with none recorded. Both unbound forms can be claimed at a stop and they differ in which route claims, so the kit-goal skill's claim signals are what to read there rather than the form itself. Do not place the binding on the printed id: it appears in the first form alone, so a session holding the leash by the arming route would be reported unbound and freely claimable while its very next stop binds and blocks. Place it on `sessionHoldsLeash` in `hooks/kit-goal-lib.js`, the kit's own composed answer over the bound-id and recorded-arming-id routes, resolving the absent state and then the damaged one before the id, so that a project with nothing armed reads none armed and a goal that exists but cannot be read reads unknown rather than either landing as a placement, and gating the id on shape before the call so that an unusable id reads unplaceable, all three being where a bare false would otherwise land. Spell `<plugin-root>` with forward slashes in this one position: here it sits inside a single-quoted JavaScript string rather than in a shell argument, and JavaScript drops any backslash that does not open an escape sequence, so a Windows-spelled root collapses into a path that does not exist, the require throws, and the catch reports unknown for a goal the instrument could have read. The invocation: `node -e "try{const g=require('<plugin-root>/hooks/kit-goal-lib.js'),s=process.env.CLAUDE_CODE_SESSION_ID,c=process.cwd(),st=g.readGoal(c);console.log(!st&&g.goalStateAbsent(c)?'none armed':!st||typeof st.plan!=='string'||!st.plan?'unknown':!g.isSessionIdShaped(s)?'unplaceable':g.sessionHoldsLeash(st,s)?'this session':'not this session')}catch{console.log('unknown')}"`, run from the project directory, which reads the goal state and writes nothing, so it passes the bound below. Report the placement rather than the value: this session's own leash, not this session's, unplaceable, unknown, or none armed. The negative is reported as not this session's rather than as another session's, because that predicate leaves out the third route the claim points act on, an unbound goal claimed by a session whose own arming text names the plan, which it omits deliberately as too expensive to read on every call and which `hooks/kit-goal-lib.js` states as its own cost; a goal armed outside any session records no arming id, so the session that will claim on that typed text reads here as not this session's. That placement is inferred rather than confirmed and is reported as inferred, and the residual is worth stating exactly, because the obvious discriminator is not one: the environment value is read on shape alone, and a dispatched subagent's shell carries the id of the session that dispatched it, so a subagent placing this leash places its dispatcher's rather than its own. `CLAUDE_CODE_CHILD_SESSION=1` does not separate those cases, being set in a main session's own tool shell exactly as it is in a dispatched agent's, so gating the instrument on it would report the ordinary main-session reading as unplaceable and buy nothing. What would confirm the placement is an identifier the harness gives a dispatched agent for itself, which nothing here supplies, so a reading taken anywhere but a session's own shell is unverified rather than merely uncertain. Only the placement word enters the report, never the id, and the catch narrows what the reader has to strip by hand rather than removing the need for the rule: a failed require prints an absolute path and a stack trace, which is the disclosure the bars below keep off an external channel, and the wrapper resolves that class to unknown. What it does not reach is a root spelling malformed enough to break the parse, an unpaired quote or a backslash opening an escape sequence, where the `try` never comes into existence and node prints the stack trace anyway, so the bar on forwarding the command's own error text holds whatever the wrapper catches; where any part of the reading leaves this session, the store's readership question is the coordinator skill's precondition to establish rather than this bullet's to answer at the field. The reading decides how the report is delivered below, and it is half of what bounds a park. None armed, unplaceable and unknown are three readings this instrument reports and no one of them is another: none armed is no goal state in the project at all, which is the ordinary state of most projects and carries no leash to bound anything; unplaceable is this session's own id being unset or unshaped while a goal is armed; and unknown is a goal state that exists and cannot be read, whether unparseable or carrying a `plan` that is not a non-empty string, or the command failing to run at all. The split is the point rather than a nicety, because the delivery below binds on it: unplaceable and unknown take the leashed shape, which is the safe reading in those states because ending the turn is not, while none armed carries no delivery constraint at all and a recap in such a project is an ordinary report. Read them from the kit's own answers rather than by inference, `goalStateAbsent` being what separates an absent state from a damaged one, which `readGoal` alone cannot: it returns null for both.
- **Any background run's own marker.** The reading comes from the marker the run wrote (an exit-code file, a completion line appended to the log), because a completion notification reports the wrapper's exit and not the run's. An absent marker does not read as in flight, since a run that died before writing one looks identical. The doctrine's background-task bullet owns what settles it, and settles it on two components rather than one: a background run's death is "settled by the process list plus the completion notification". Both are reads that change no state, so both sit inside the bound, and a reading taken on the process list alone is half the test. One case makes no marker by design, and calling it death would be the false line this instrument exists to prevent: under the doctrine's worktree-isolated fallback the run is a bare backgrounded redirect whose result is read from its own summary output once the completion notification arrives. Report each run on both components, and name the no-marker-by-design case as itself rather than folding it into either verdict. That bullet also owns why a log that stopped growing is buffering rather than death.
- **The roster**, one `ListAgents` read, where a peer session is load-bearing to what the report will say. Where none is, skip it.

The bound is hard, and it is one test rather than a list: during a recap the session takes no action that changes state anywhere, and none that spends the machine's one heavy-process slot. Suites, review dispatches, probes to dispatched agents, messages to peers, staging, commits, memory writes, kaizen appends, and plan-doc edits all fail the test as instances of the class, not its boundary; the reads this pass names all pass it, and so does delivering the report itself, which is the recap's output rather than an act taken during the reading. A fact that would need a run to confirm is an inferred claim naming the run that would confirm it. A recap that spawns a suite spends the machine's one heavy-process slot to answer a question the operator asked precisely so they would not have to spend anything.

## The report

Five parts, in this order. Scale the prose to the session: a two-hour session with one open section gets a few lines per part, a three-week plan gets more.

**(a) The goal and the current focus, each beside its record.** The goal as the record states it, quoted verbatim: the plan doc's `## Goal`, which is the planning session's statement of what exists when the work is done (`skills/brainstorming/SKILL.md` owns that shape; the requester's own framing, where the plan carries it, sits in `## Dispatch Authorization`), or the dispatch brief where the session is executing one. Beside it, the pre-read restatement from working memory. The current focus the same way: what the session said it is working on, beside the latest Chapter's `Completed:` and `Next:`, or, where no Chapter exists yet, beside the plan's first section or the brief's stated scope. Both pairs verbatim, side by side, never merged into one summary.

**(b) Where things actually stand.** Every load-bearing claim marked confirmed, inferred, or reported per the doctrine, with its evidence named: the file and line, the command, or the artifact read for a confirmed claim; what would confirm it for an inferred one; the peer session whose evidence it is for a reported one. A green suite is reported as a suite result, with the lane it ran and the baseline it is a delta against, never as proof of behavior that suite does not exercise.

**(c) What the session is waiting on, split by what holds it.** A person, named by role and what they hold: the operator's yes on a destructive step, a reviewer's round still in flight, an expert seat's unanswered ask. Or something technical, named with the last diagnosis. This split is the report's own axis over the session's open waits rather than the completion contract's blocker vocabulary: the closed blocker set and the `BLOCKED:`/`WAITING:` stop shapes are executing-work's (`skills/executing-work/SKILL.md`, its completion contract), and some waits reported here gate nothing there, an expert ask being sent and worked past, a reviewer round in flight being awaited rather than declared.

**(d) Next steps in order, each marked as the session's or the operator's**, stated so the operator can act from a phone. Where the question is whether the session is safe to park, name every in-flight dispatch against the windows finishing-work's unavailability rule owns (`skills/finishing-work/SKILL.md`, from the bold lead **Unavailability is the gate failing to run at full strength**): executing-work's `WAITING:` stop shape owns the park preconditions, under which a dispatch whose first-turn reading is still pending holds the park, in-turn and unrefused, until that reading is taken and resolved, and one past its window owes that rule's readings, probe included, before any park. The recap reports each dispatch's window state and names what a park would still owe; the readings that change anything, the probe among them, run when the operator acts on the report, never during it. And name the leash, because the kit wakes a parked session on no timer, save a parked coordinator seat, which its own armed reconciliation timer wakes into restating that it is parked and taking no new work: a session at a `WAITING:` stop over dispatched background work, which is a stop and not a park, is re-invoked by that work's completion notification, one parked on a request wakes only when someone resumes or cancels it, and the armed goal wakes nothing in either case, instead keeping a stop that never woke visible, the park and the dispatch stop alike, surfaced at session start and to the doctor, with re-arming as the recovery.

**(e) The drift diff.** The restatement from (a) against the record from (a), both halves: goal against the record's goal, focus against the Chapter. Usually "none", and one word is the whole line. When it is not none, it is the most valuable line in the report: name what the session believed, name what the record says, and stop there. The focus half is where drift usually shows, a session working section 3 whose latest Chapter closed section 3 an hour ago. Where the record was freshly read this session with no compaction between, say so beside the line: a "none" there is expected and proves little, while a diff that shows anyway is real.

## Delivering the report

**A recap never ends the turn in a project with a leash armed.** The lead is stated over the project rather than over this session's hold on the leash, because the rule binds on all four of the armed readings below and a lead naming only the holder would read as not addressing a session that places the leash elsewhere. With a goal armed in the project and the current plan not `Complete`, this session being bound to it or claiming it by the recorded-arming route the hook also enforces on, the Stop hook allows a deliberate stop on a last assistant message whose very first characters are `BLOCKED:` or `WAITING:`, records a mid-queue `BLOCKED:` and blocks it with an advance reason rather than releasing, and refuses either prefix whose stated reason is capacity; `hooks/kit-goal-stop.js` owns those clauses, stated in its header comment, which also names the indeterminate reads it allows on by design. A report opening with the goal is none of these, so the turn bounces and the session is fed straight back into the work the operator asked it to hold still about. So read the leash before composing. Four of the five readings the instrument above reports take the same delivery, which is why the branch is stated once, and they are placements rather than a mix of placements and printed forms: the leash is this session's, it is not this session's, this session's own id leaves it unplaceable, or the state leaves it unknown. The fifth is outside this rule and not a weaker case of it: none armed is a project with no goal state at all, the ordinary state of most projects, where there is no leash for a recap to be held by and this paragraph does not bind. The readings differ in what the report says about the leash and not in what it licenses. The hook allows a stop on a foreign binding and on a genuinely non-claiming unbound goal, `hooks/kit-goal-stop.js` stating both in its header: a session merely mentioning the plan is never leashed, and of the routes that claim an unbound binding, a session matching none of them is allowed. That is narrower than the instrument's own negative, and the gap is the arming route: a session that would claim an unbound goal by its own transcript text reads here as not this session's while the hook enforces on it, so a placement of not this session's is never evidence that a stop would in fact be allowed. So on those readings the delivery is this bullet's own rule rather than the hook's: a recap is a report inside work the operator asked for and is not a stop that work has reached, so it delivers without ending the turn whatever the hook would tolerate. What the placement buys is the report's accuracy about whose leash is armed, never a licence to end the turn on it. In all four of those, deliver without ending the turn, over the relay reply or in the message before the work continues, and then continue whatever work the session was already doing, the armed plan where the leash is this session's and that same work where it is not, since the recap licenses no stop and the operator's follow-up arrives as its own steering. On none armed, the session ends its turn or not on whatever its own work calls for, exactly as it would with this bullet absent. One case the continue clause cannot serve is a session that has no work of its own, a bystander invoked only to produce a recap in a project some other session leashes, and it is not stranded by the rule: continuing what the session was already doing is satisfied vacuously where that is nothing, so it delivers the recap and ends the turn on a true statement that it holds no work here, which is a report of its own state rather than the manufactured stop the paragraph below bars. Where that session is one the hook would in fact block, the arming-route reading above, the turn ends under a `BLOCKED:` naming that it was invoked with no work under a leash it may claim, which is the honest reading rather than a workaround. Where the session is stopping anyway on a true `BLOCKED:` or `WAITING:`, the recap rides under that lead, after the blocker paragraph. What none of this licenses is manufacturing a stop to get a recap out: per executing-work's completion contract, "A progress update is not a stop and must not be written as one". Clearing the goal so a recap can stop is never the route either, since it abandons the continuity the leash exists to hold.

Two bars ride on any part of the reading that leaves this session on an external channel: a board line, a peer message, an outcome note, and the relay reply among them. The coordinator's ledger rules own both (`skills/coordinator/SKILL.md`, under the bold lead **What rides, and the two things that stop it riding**), and they are bars "on what a line carries rather than on which surface it lands on", so being addressed to the operator exempts nothing: the relay is an external service whatever the allowlist on its far end. Every path is spelled repo-relative or home-relative and never absolute, because an absolute worktree path embeds the OS username on the default layout, which is the exact disclosure a relay-delivered part (b) evidence reference would otherwise carry. And the operator's own words ride as a pointer to the artifact or the channel that carries them, never quoted and never paraphrased: the owner's bar "covers a paraphrase of those words exactly as it covers a quotation". That reaches part (a)'s own quoting: the record's `## Goal` is the planning session's prose and rides verbatim, while anything the plan or the leash carries of the operator's own authorization words rides as a pointer to where it sits.

## The read-only bar

**Every standing rule that would make the recap write is suspended for its duration.** The doctrine's act-on-found-work rule is the loudest of them, and it is not the boundary: the rule that a memory contradicted by evidence is corrected in the same turn, and the standing authorization to append a kaizen note, are two more, and a freshness pass is exactly the pass that surfaces both. The class is any rule that mandates a write, whether or not it is named here. Those rules are right everywhere else and wrong during a recap: a recap that fixes what it notices is reporting on a session it has already changed, and the operator asked for this reading in order to decide whether the session should continue at all. Acting first destroys the reading the invocation was for.

Anything found rides in the report as a next step under (d), named and unactioned: the stale plan doc, the uncommitted file, the review finding nobody answered, the contradicted memory, the branch three commits behind. The operator's follow-up is where one of those becomes work. Rationalizations to refuse, as instances rather than the boundary of the class: "it is one line", "it was the next step anyway", "fixing it is what makes the report accurate".

## Neighbours

- **The coordinator's status round** is the machine-wide instrument, pulled by that seat under conditions its own runbook owns (`skills/coordinator/SKILL.md`, the operator-interface function). A recap is the opposite shape: operator-invoked, one session, deep, bounded by the five parts and the read-only bar. Neither substitutes for the other, and a coordinator that starts running recaps has left its seat.
- **Parking** is the act this reading informs, and performing it is not this skill's job: /recap answers whether a session is safe to park, and never parks it. A recap ends at the reading, and the operator decides what to do with it.
