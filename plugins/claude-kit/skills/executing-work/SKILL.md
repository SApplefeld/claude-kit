# Executing Work

Once the spec is approved, execute it under the completion contract below: no per-step check-ins, no "should you continue?", no gating individual edits.

Interrupt me only for a member of the blocker set below. Everything else is yours to resolve and record.

## The completion contract

The spec is the goal. Once execution starts, run every remaining unblocked section to completion in this session. A section boundary is not a stopping point. A long-running gate is not a stopping point. Context pressure is not a stopping point.

For an externally-driven worker (the External-engine stand-down), the directed section is the whole goal. Finishing that one section and stopping is completion under this contract, never an early stop. The engine verifies the section and spawns the next worker itself.

**Do not end your turn** to:

- report progress between sections ("§3 done, say the word and start §4"). Close the section and start the next.
- wait on a build, test suite, or Live gate ("holding for the gate, ~2 min"). Wait on it in-turn. Background it and poll a readiness signal (`until` on a marker or exit code), then continue when it returns.
- manage context ("pausing here rather than open §7 at the tail of a long run"). The Chapter plus the SessionStart resume hook make a fresh session lossless. Starting one is my call, never your reason to halt.
- await a dispatched subagent on a bare turn-end. That wait does end the turn, and it ends it on a `WAITING:` lead.
  - A background dispatch (`run_in_background: true`, the Agent-tool default) is awaited by ending the turn on `WAITING:` once it is the only remaining work in the turn. That holds whatever its class: a single implementer, a fan-out member, a reviewer pair, or an agent resumed over SendMessage, which always resumes in the background. It holds whether or not the dispatch carries a model override. Under an armed leash a turn-end without that lead is a stop the hook blocks.
  - Only remaining work means every next step reads the dispatch's result. Work the session can do now without that result is done first, and a turn that has such work does not end on `WAITING:`. With several tasks pending the same test applies to the set. A returned result not yet read is work the session can do now, so the turn reads every returned task before it ends. Where others are still pending after that and nothing else is available, it ends again on a `WAITING:` line naming only the ids still pending.
  - The `WAITING:` line names each pending task by its id and the wake the session expects: the completion notification and, where one was armed, the timer. That line is the dispatch registry the post-wake turn reads. Where the session has a means to arm a timer, arm it before that turn end. Finishing-work's cadence paragraph owns which window it is armed for and how the means is named.
  - The synchronous shape is the one in-turn option: dispatch that agent synchronously (`run_in_background: false`), so its whole run is one in-turn call. Step 1's leash bullet, the one opening "Under an armed completion leash", owns the choice between it and the `WAITING:` turn end.
  - Never infer completion from transcript-file quiescence: a mid-run pause reads as done, and completion is read from task status or nowhere. Only the wedge hallmark, which finishing-work's unavailability rule owns, makes a stall out of silence, and that rule owns the wakes at which it is evaluated. Where the wedge hallmark calls for a growth reading, take it the way finishing-work's rule specifies, at the artifact it names.
  - Never clear the leash to escape a block, since that abandons the very continuity it exists to hold.

Rationalization table (the excuse, and why it is wrong):

| The excuse | Why it is wrong |
|---|---|
| "This is a clean boundary to pause at." | Clean boundaries are for resuming, not for stopping with work left. Continue. |
| "Holding for the gate." | A wait is not a stop. Poll the gate in-turn and continue. |
| "It is the tail of a long run, safer to stop." | The Chapter plus resume hook protect you. Context is my call, not a stop condition. |
| "Let me confirm before continuing." | The approved spec is the confirmation. Continue unless a true blocker hits. |
| "I'll hold the turn open until the agent finishes so I can watch it." | An open turn holds inbound messages and gains nothing the wake does not give. End the turn on the `WAITING:` lead the dispatch row above states, and do not clear the leash to get out of a block. |
| "I don't have enough context left to review the next round properly." | Compaction gives you a fresh window and the plan doc carries the state. The choice is not stop-versus-ship-unreviewed; it is compact-and-review versus abandon. Continue. |

The table is instances, not the boundary. Any reason to stop with unblocked work remaining that is not in the blocker set below is wrong the same way, whether or not a row names it.

Red flags that you are about to stop wrongly: "say the word and continue", "holding for", "paused here", "at the tail of", "ready to continue when you are". If you are about to write one of these with unblocked work remaining, do not. Keep going.

**Stop only for a true blocker, and make it loud.** The blocker set:

- an external dependency only I can satisfy (a GUI action like a Docker memory bump, a cloud resource that must be provisioned, a credential or secret you cannot reach),
- a contradiction inside the spec, or a material decision the spec does not cover,
- an act the doctrine's stop-for-a-yes rule gates and no proceed-ahead covers,
- a systematic-debugging dead end.

The set is closed. Capacity is never on it. Native compaction gives a fresh window with the leash intact, and the plan doc plus its Chapters carry the state, so a stop reasoned from context is a stop dressed as a blocker. The `WAITING:` shape's two occasions below are not on the set either: a turn whose only remaining work is dispatched background subagents, and a park at a safe boundary taken on a request. Each ends a turn with the leash armed rather than work stranded. So neither is the stop this set governs, and neither is a route to one.

**Before any BLOCKED at all, the expert ask goes out, and it goes ahead of the consult.** Where the repo has a live expert seat on the roster, the blocker goes to it before you declare. The peer-sessions skill owns that route, the seats it runs between, and the bounds on both ends. This paragraph is where the moment lives. The ask goes first because it is the cheaper instrument, and the one that resolves from sources that already exist. It never gates: send it, keep working whatever is still workable, and declare at exactly the point you would have with no ask in flight.

What an answer discharges is narrower than it looks, because the two instruments ask different questions. The ask is about whether the answer already exists somewhere. So it prevents a declaration only where it hands you something you verify on your own surface: an existing source that answers the question with its provenance traced, or a diagnosis you can reproduce. A peer's say-so is a claim to check rather than the thing that settles it. The consult is about whether your framing is wrong. So it still runs on whatever decision survives the ask, and the ask never stands in for it. Neither discharges a blocker that exists because only I may say yes. Where no expert seat is live there is no ask at all, and you go straight to the consult path below.

On declaring, also notify this machine's live coordinator seat where one is up, and the expert too where the ask went unanswered. The coordinator routes the escalation rather than resolving it. The ask and the notice carry the same public-board cap the first-line paragraph below puts on the declaration's first line. They carry it as a standard rather than as a reading of where either lands, stated against a public board so that moving the board somewhere quieter never reads as relaxing it. Reach is what puts each leg in scope, never what warrants the cap on it: the ask goes to an address nothing corroborates, any session being able to answer to an expert's name, and the notice is what the coordinator briefs from. `docs/security-model.md` carries the readership analysis behind the standard. The coordinator skill owns the precondition it names, which bounds what that seat may land rather than what a sender may send. An ask that prevents a declaration is an agreement reached over messaging, so the record rule binds it exactly as it binds any other. The resolved ask lands in the plan doc in the same turn, or a post-compaction session re-hits the blocker with nothing to show it was answered.

**Before any BLOCKED that turns on a decision, the consult runs too, after the ask and before the declaration.** Two shapes in the set above are not decisions to rule on and go straight up: an external dependency only I can satisfy, and an act the stop-for-a-yes rule gates and no proceed-ahead covers. For the rest, a spec gap is mine to answer only where the answer turns on preference, cost, or risk appetite. Where it turns on facts about the system it is rulable. A mixed question is ruled first, so that what reaches me is the small real fork. The BLOCKED that survives carries the ruling in its decision brief. The consult skill owns the mechanics. Step 4's review-round backstop makes the one substitution this paragraph admits: a design stop's own ruling stands in for this consult on the conditions that paragraph states and on no others.

When you stop, the message's very first characters are `BLOCKED: <exactly what you need from me>`, so I see it in seconds rather than discovering a silent halt hours later. The body under the prefix is a decision brief in the doctrine's client-briefing register. A BLOCKED lands on my phone hours later with no session context, so it must be decidable from the brief alone. The bare prefix opens the message: no close-out summary above it, no bold or heading wrapping it. Put any shipped-work recap after the BLOCKED paragraph. The Stop hook releases only on that exact leading prefix. It deliberately ignores a `BLOCKED:` sitting mid-message, since quoting the convention must never release the leash. A release whose BLOCKED line gives capacity as its reason (context, compaction, a fresh session) is refused the same way, since capacity is not in the set. A progress update is not a stop and must not be written as one.

**The first line carries only what you would put on a public board, because it travels further than the rest of the message.** The rest of the declaration is addressed to me alone. The first line is not. On a mid-queue advance the Stop hook records it into the blocked plan's outcome note, which this machine's coordinator seat reads onto an operator brief and onto that seat's board. So compose that one line for a public board and keep it inside 120 printable-ASCII characters. What runs past is dropped mid-clause and reads downstream as though it were whole. The cap is a standard rather than a reading of where the board sits, stated against a public board so that moving the board somewhere quieter never reads as relaxing it. `docs/security-model.md` carries the readership analysis behind it. The coordinator skill owns the precondition it names, which bounds what that seat may land rather than what a sender may send.

Spell any path in that first line repo-relative rather than absolute. The cap holds whatever the queue position. What varies is the recording: the last plan of a queue records no note at all, while the coordinator notice carries that same line either way. The peer-sessions skill states the same cap over the messages this route adds. It is restated here because this is the paragraph a leashed run actually reads, while a worker mid-run may never load that one.

Waiting is the third stop shape, and it has two occasions. One is a turn whose only remaining work is background subagents already dispatched. Do not hold the turn open with a foreground wait, and do not dress the pause as a blocker. End the turn with `WAITING:` as the very first characters, naming the dispatch that is pending. The completion contract's dispatch row states the only-remaining-work test and what that line names. The first-turn reading is taken at the first wake at or after the first-turn window closes, per finishing-work's cadence paragraph. Where a dispatch is what the turn ended on, evaluate the hallmark at the first re-block after the wake, before doing anything else with that dispatch.

The other is a park: a stop at the next safe boundary taken on a request rather than on the run's own judgment of its own work. The operator-declared update window is the occasion that ordinarily produces one. The request is the predicate because it is the one the receiving session can evaluate. The window's operator-initiated condition sits with the coordinator that declares it, the party that can establish it, and never with the receiver. A stop request from the operator, direct or relayed by the coordinator, is honored at the next safe boundary under the ordinary rules: the interim board entry where a section is mid-flight, the commit the plan's recorded commit model directs, and the compaction checkpoint opened.

A leashed session leads its stop message with `WAITING:` so the Stop hook does not bounce it. Every later turn it ends while parked re-leads the same way, since the leash stays armed and a turn without the lead is pushed back into the work. That line names the park and its ground and nothing else. Capacity, context, compaction and a fresh session are among the things it never gives as the reason, because the hook screens that one line and refuses the capacity formulations it names. Once every dispatch is finished or explicitly stopped, so that nothing is left in flight, a relayed request is answered with one line naming the parked state. That reply is the last act before the turn ends on that lead. The ground is the window where the operator declared it to this session directly, the operator's own instruction where they gave one, and otherwise the request itself, named as the request it was rather than borrowing either of the other two.

Where an in-flight dispatch's growth window or its first-turn window has already closed by parking time, run the hallmark check through to its probe before writing this line. Where the first-turn reading's pair of counts reads synthetic-only, run it through the TaskStop that route begins with instead. Finishing-work's unavailability rule defines both readings and owns their windows. The first-turn window is readable from the dispatch record you hold at the moment you park. The growth window is too, in its elapsed-since-dispatch fallback form, since its own opening, the last observed growth, is a session observation the record does not carry.

Where a dispatch is young enough that its first-turn reading is still pending, do not park yet. That is a hold rather than a refusal. The window closes minutes after dispatch, at the point finishing-work's rule sets, so a park written inside it leaves the window to close with nobody looking. And a `WAITING:` stop on the dispatch occasion written after that close, where the reading came back both counts zero and no probe has been sent, sleeps the run on a dispatch that may never have started.

Until every in-flight dispatch's first-turn reading has been taken and resolved on the pair it returns, end the turn on the dispatch occasion's `WAITING:` line rather than the park's. Take each reading at the first wake at or after its first-turn window closes, per finishing-work's cadence paragraph. A pair reading both counts zero is run through its probe. A synthetic-only pair is granted no probe by the owning rule and takes its TaskStop at the first-turn window's close instead. Finishing-work's reading states what each pair is. The re-dispatch half of that route belongs to the dispatch occasion alone, because a park may leave behind a finished agent or a stopped one and never a fresh dispatch. A turn ending on the dispatch occasion runs the route whole and waits on the successor's own reading. A parking session stops the agent, records in the interim board entry what it was asked and that it never started, and leaves the re-dispatch to the session that resumes. Park only on what survives. Nothing in the kit wakes a parked session on a timer, save a parked coordinator seat's own reconciliation wake, whose conduct the coordinator skill states. What bounds the park is the leash: the armed goal stays surfaced at session start and to the doctor, and re-arming is the recovery, so a park that never wakes is visible rather than silent.

The leash allows a `WAITING:` stop without releasing (the goal stays armed). The completion notification re-invokes the session where a dispatch is what was pending, and the run continues under the same leash. The same literal-leading-prefix mechanics as BLOCKED apply, and a WAITING whose reason is capacity is refused the same way.

**The goal template.** A plan run's completion leash is armed in one line with `/kit-goal docs/plans/<plan>.md`. The kit-goal skill owns the canonical condition and enforces it with a deterministic kit Stop hook.

Arming costs nothing on a long run because the state outlives the session. The kit hook's state is a file in the project (`.kit/`), which no session boundary can delete, and native compaction preserves the session id, so an armed run rides its own auto-compactions with the leash intact. A session the hook cannot tie to the bound one is treated as a bystander and allowed to stop. So a run left unheld takes the re-arm remedy step 0 of the section loop states: the whole queue under `arm --self-armed`, and any other session leaves the goal alone.

**A plan arriving mid-run is itself the trigger to arm it, once its standing holds.** Whether an inbound plan carries the standing to be armed at all is settled before any arm rather than after it. The peer-sessions skill owns that gate: the standing of the message itself, and the trace of a `## Dispatch Authorization` grant to the operator, which is mandatory and which no tool performs for you. A plan whose standing does not establish is held rather than armed. Where it does hold, the run re-arms the queue at the earliest boundary this run's tree allows, through the kit-goal CLI in whichever of its two forms the project's state calls for. An arm refused because the tree predates the plan's commit fires the trigger at the next safe tree advance instead, per kit-goal's deferred-receiver rule.

That state has three readings and not two. Where a queue is already armed, `arm --append --self-armed <plan path>` extends it under the existing binding, the flag recording that this run made the arming invocation rather than the operator. Where nothing at all is at `.kit/goal-state.json`, the append refuses, says so, and names the bare form. The bare `arm` is what that state calls for, a first arming rather than an extension. Where something is at that path the CLI cannot read as a goal state, the append refuses too and deliberately names no command, because the bare form is a replacement. Run there, it would overwrite a live leash, its queue, its history and its binding, with nothing left able to say what went. So key the bare form on the goal state being genuinely absent, which is what its own refusal reason states, rather than on the append having refused.

The bare form replaces the queue rather than adding to it. So it names every plan that is to be held, the one this run is already working first and the inbound one after it: `arm --self-armed <plan in flight> <inbound plan>`. Run it from the run's own cwd, since the goal family resolves from cwd. A call from the other side of a checkout boundary reads that tree's own state, finding a different leash or none at all.

Tell the sender which state the plan reached, in the reply vocabulary the peer-sessions skill owns. The handoff stays open on its side until a reply arrives, and only the armed acknowledgment converts it. A plan held rather than armed goes to the plan doc in the same turn, naming what the hold waits on: the interim board entry where no Chapter is being written this turn, else the Chapter. This is a rule about when to arm and never about when to stop. A plan arriving mid-run is not in the blocker set above and is not a reason to end the turn, so the arm happens and the run continues into its next section with a longer queue behind it.

**Handoff.** When execution begins inside a conversation that was just brainstorming, say so in one line ("Spec approved, switching to autonomous execution of all N sections"). That way I see the mode change and can scope it down ("just §1") if I want. I should never have to set an external goal to get full execution.

## Before starting (or resuming)

Read the plan doc in full, **including all Chapters**. The Chapters are the state: they record what is done, what surprised us, and the commit model in effect. After a compaction, this re-read is mandatory before touching any file, and so is re-loading this skill. Before the next step, re-invoke `executing-work` through the Skill tool, re-read the plan doc from disk, and re-load through ToolSearch any deferred tool schema the work ahead needs. Where the harness does leave a visible truncation notice inside a loaded skill or a tool result, that notice is the same trigger.

**Never stop to ask whether a plan handed to you was approved.** On an armed run the kit-goal skill's arming-is-approval rule already answered it. A plan handed on the operator's own channel, or by a chain handoff as the peer-sessions skill defines one, is approved as written whether or not a leash is armed. The absence of a leash is never the absence of approval. That same rule states what a chain handoff may reach, and a plan past those bounds holds for the operator's word as that rule says. Where the plan's `Status:` header reads anything other than `In Progress` or `Complete`, set it to `In Progress` as part of starting. A header already reading `In Progress` is left exactly as it is. `Complete` is the one value the normalization does not touch, because flipping it would be the run silently overwriting the record of a close-out rather than repairing a header. A plan a run is starting whose header says the work is finished is a contradiction between the doc and the fact of the run, and it takes the contradiction path in the blocker set above rather than a quiet flip.

The curating-docs skill's machine contract owns the `Status:` lifecycle and the values the kit's tooling reads. The header sits inside the approval-scoped fingerprint region the `## Assumptions` rule below describes. So where the value did change, the first Chapter this run appends records the normalization, naming what the header read and the `In Progress` it now reads, which is what marks it deliberate rather than drift. Where nothing changed there is nothing to record. A worker under an external engine (the stand-down below) leaves the header to its engine.

**Then run the intake gap check on the plan doc.** List what each section does not state that its implementer would need. The listing runs here. The routing runs after the memory recall below, since memory is one of the sources a gap routes to, and every gap is routed before its section is dispatched. On an armed run, a material gap (the spec-does-not-cover decision the blocker set already names) is the `BLOCKED:` the leash already handles. It is named there because the `goal-blocked` event is the surface that reaches me while I am away. On an attended run it is a decision ask instead.

A non-material gap is one answerable from an existing source (route (a): doctrine, memory, the plan doc, the code's conventions; cite it) or covered by a low-blast reversible default (route (b): pick it and declare it). It is recorded on that section's Chapter `Assumptions:` line, in brainstorming's declared-assumption line format dated today with `, section N` in the parenthetical, and the dispatch brief carries the resolved answer rather than the gap. It goes to the Chapter and never to the plan doc's `## Assumptions` section. That section sits above `## Chapters`, inside the approval-scoped fingerprint the external engine reads. So a mid-run append there reads as approval drift. The section freezes at approval and holds the design-time entries alone.

**Then run `memq recall`, once, before the first section.** It returns the whole memory store as one bounded digest. The memory-system skill owns what the digest contains and how to act on it. The plan doc carries the effort's own state. The digest carries what earlier efforts learned the hard way, which a plan written days ago cannot cite because nobody had recorded it yet. Read it against the sections ahead and carry forward what bears on them. On a resume, run it again rather than trusting a recollection of an earlier pass. A boundary taking the memory-system skill's hand walk runs it again too, since that walk enumerates from the digest. When a recalled record changes what you build, stamp it in that turn with `memq touch <name> --applied`.

Run it from the project root, a worktree of it, or any directory inside the project. Which store `memq` resolves from a working directory is the memory-system skill's resolver rule (`skills/memory-system/SKILL.md` under the kit plugin root): the session's own filing, a worktree's main checkout through the `.git` handshake, an external engine's pin, and the boundaries at which the resolution stops. The harness files a session started inside a linked worktree under that worktree. Two tells ride here because this is the step that reads the digest, and each means `memq` resolved a different, empty store. A worktree whose handshake fails resolves such a store, and it announces itself with a `git worktree repair` note on stderr. A digest whose coverage lines all read zero on a project you know has memories is the other tell. The resolver rule names the other directories that resolve such a store.

**External-engine stand-down.** Two things make the engine the supervisor and this session its worker. One is a driving directive stating that an external engine owns continuation by spawning a fresh worker per section (Spine's Dispatch pump is one). The other is the environment carrying `KIT_EXTERNAL_ENGINE`, the marker such an engine sets at spawn. Run the section loop for the directed section only. The marker is a directive to you, not a mechanism: treat it exactly as you would the driving directive's own words. The **worker runs this skill** - it orchestrates, dispatches implementers, and writes Chapters exactly as any session would. It does not absorb implementation inline just because it is headless.

**Workspace and siblings.** If concurrency put you in a worktree on a feature branch, that is your workspace. Integration and any teardown happen in finishing-work. Expect sibling sessions to touch the same repo, so own a disjoint set of files, and never stage another session's uncommitted work or carry it in a commit of yours.

## Section loop

For each Section of Work, in order (sections run concurrently only where the disjoint-files rule in "Delegating to subagents" permits):

0. **Close the previous boundary.** If the run is leashed, clear any compaction checkpoint the last boundary left open, since work is about to resume and this is no longer a boundary:

   ```
   node <plugin-root>/hooks/kit-compact-checkpoint.js clear
   ```

   Resolve `<plugin-root>` the same way the Dispatch Brief template's style-skill bullet does (step 1 below carries that rule). It is a no-op when nothing is open, so it costs one call on the first section. It refuses at exit 1 over a record that is another session's boundary, and over a state it cannot read (a goal state that is present but unreadable, or something other than a regular file at the checkpoint path), naming the remedy in each case. The case a run meets is a resumption under a new session id against a goal still bound to its dead predecessor. That resumed run re-arms the goal with its whole queue (`arm --self-armed`, the invocation being the run's own), which rebinds it, while any other session leaves the goal alone. One further exit-1 reading carries its remedy on the CLI's own line: a caller id the shell cannot resolve over a record that is somebody's boundary, which is why the verb runs from the session's own shell.

1. **Confirm the approach, then implement.** Before writing a section whose mechanism the spec assumed without reading the code, do a quick in-session read of the files it touches and confirm the planned approach holds. Where you open a file to find one mechanism in it, take that file through the doctrine's rule on hunting in a large file, and read whole any file that is itself the mechanism. Confirming a mechanism often spans call sites and error paths, so where you do outline, expect to read more than one of the ranges it names. This is a lightweight read, not a fan-out. If the real shape differs materially, adjust and note it in the Chapter, and raise it to me only if it changes design intent. Then implement per the section's model tier, which is a dispatch instruction rather than a hint: a section carrying a `Model:` tier goes to that tier's implementer. The doctrine's standing dispatch request covers it, including where a session-prompt line makes dispatch conditional on my having requested it.

   **At each section open, whatever the section's locus, grep the plan doc for its `Standing Brief Amendments` block and hold every entry as binding on this section's work.** Step 4 writes to that block mid-run, so a full-doc read taken at an earlier section is stale by construction. The grep is what establishes the current text, and a grep that finds nothing is the read. On the dispatch path the entries then ride into the brief. An inline section has no brief for them to fold into, so the grep is the only delivery that path gets. The same open writes the section's own add-decision line, for the section as a whole, to the scratch file step 4 names; that step owns the line's five parts and the one thing this one does not do, which is fire a stop.

   - **A section that writes under `docs/` goes to the main thread regardless of the tier it carries.** An implementer may still draft the prose and return it in its final message for the main thread to place, but the `docs/` write itself is always the main thread's. This is a routing override, not a tier change: record `Locus: inline` under the section's `Model:` line so the override is visible up front, and leave the `Model:` value the bare tier it earned.
   - **Tier `haiku` / `sonnet` / `opus` / `fable`:** dispatch the matching `implementer-haiku` / `implementer-sonnet` / `implementer-opus` / `implementer-fable` agent with a complete brief built from the Dispatch Brief template:

     - Rich references: the section's References: line when the spec has one,
       plus any mockup, rubric, or reference implementation its acceptance
       leans on, by path
     - Tests: the section's Tests: line verbatim when the spec has one (a floor
       over the named contracts, extended with what implementation reveals and

     - Pin tests + new expected values, when the section changes a counted

     - Standing Brief Amendments: every entry from the plan doc's block, when one exists

       `git checkout -- <file>` at all, its own files included, since that
       restores the file to HEAD rather than to the state before the
       agent's own edits, which your own contract leaves unstaged. Two

A delta in a declared file no live dispatch covers is an incident like any other: a fold widens a section's `Files in scope:` mid-run, and a guard-escaping write into a declared file would otherwise wear the sibling's name.

Those are the writes steps 4 through 8 and the interim-board ritual direct mid-round: a sibling section's Chapter append and staging, a plan doc update, an interim board entry, a `docs/backlog.md` entry, a route write under step 4, and every other write those steps name. "This session made it" is established by reading the delta's content and recognizing it as what you wrote, never by recognizing the path. An agent-authored write to the plan doc produces a porcelain line identical to your own append. The plan doc is the recovery spine a post-compaction session re-reads and executes, so content you do not recognize in a file you also write to takes the incident path.

   Any other delta is an incident: restore the tree, record the delta and the agent that produced it in the Chapter, treat that agent's findings as suspect pending a re-review against the restored tree, and jot a kaizen note. A delta means either a write-shaped command got past the guard or an allowance the guard grants is wider than the invariant. For a genuinely trivial, self-contained section (a rename, a comment, a one-line change with no logic), the per-section reviews are optional as a pair, since finishing-work still covers it.

   **The Document Review Brief.** The document pair's dispatches fill this template. Add no field to the blind-reader's dispatch beyond what its input contract names.

   **Reviewer effort.** The model rule above sets each reviewer's model. This sets its effort and route, for every reviewer dispatch in the round, the advisory lenses included. Three questions generate the rows: is the round the first, is the reviewer Fable, and how far outside the diff must the lens read?

   | The reviewer's dispatch | Model | Effort | Route |
   |---|---|---|---|
   | Round 1's code pair and document pair over a section whose writer tier is opus or fable | fable | `low` (frontmatter default) | Agent tool |
   | Round 1's security-reviewer over a section whose writer tier is opus or fable | fable | `medium` (frontmatter default) | Agent tool |
   | Round 1's performance-reviewer over a section whose writer tier is opus or fable | fable | `medium` (frontmatter default) | Agent tool |

   The route question decides first among the last two. A Fable reviewer carries its agent's frontmatter effort, so its round rides the Agent tool. The lens question sets that effort: `low` for the blind, adversarial and prose lenses, `medium` for the security and performance lenses, and `high` for the scope adjudicator, which is its charter's own pin and never a compensation notch. A reviewer below Fable earns its findings on effort, so it runs at `high` in every lens. A frontmatter effort is one value per agent whatever model runs it, so only the per-call route lifts Sonnet and Opus without lifting Fable. The finishing pass reads the whole changeset for cohesion, so `high`. That row and the compensation row are finishing-work's to specify.

   The compensation row exists for a Fable gate that could not run here and nothing else, a below-Fable reviewer ruled out taking the re-aim row, so no dispatch reaches it except through the unavailability rule. Unavailability is confirmed and recorded per finishing-work's unavailability rule, which owns its triggers. Every per-section row keys on the model rule's writer tier, the re-aim row on the tier ruled out, and the scope adjudicator's row on neither. That seat is not a per-section reviewer, and its tier is its charter's rather than one tier above whoever wrote the section. The rule never produces Fable at `max`, and a below-Fable reviewer's `high` never climbs there.

   **Dispatching a reviewer above its frontmatter default.** On v2.1.205 the Agent tool takes a model override but has no effort parameter. So any dispatch whose row names an effort other than the frontmatter default goes through `Workflow`'s `agent()` instead. Every such call fills this template:

   ```
   Reviewer Dispatch (all REQUIRED):
   - agentType: the agent's scoped name (claude-kit:adversarial-reviewer,
     claude-kit:blind-reviewer, claude-kit:blind-reader, claude-kit:prose-reviewer,
     claude-kit:security-reviewer, claude-kit:performance-reviewer,

   - model: named explicitly, never left to inherit. A call carrying an effort but no

     a weak model at maximum effort: the downgrade this rule exists to prevent
   - effort: named explicitly, never left to inherit. An unnamed effort resolves

   ```

   A sighted dispatch on this route carries the `Amendments in effect:` line as well, and a dispatch carrying the plan's what carries the `Trace target:` line beside it, both per the rules above. Those lines sit beside the template rather than in it, as dispatch content owned by the sighted-only rule and the trace-target rule.

   The doctrine's standing-dispatch bullet carries the operator's request for this route, so it needs no per-session ask. This skill states the mechanics, never the authorization. The round stays one round: mixed Agent-tool and Workflow dispatches go out together under the single tree-state capture, and a Workflow round is awaited by the `WAITING:` turn end exactly as an Agent-tool dispatch is, its completion being a wake. Every input contract above still binds on this route. A script assembling several dispatches builds the blind ones, it does not filter them. Each blind prompt is authored as its own literal, composed of the blind boilerplate plus its contract inputs (the base ref or changed-file list; the document paths and `Reader:` line) and nothing else, sharing no brief-building constant, helper, or template variable with any sighted dispatch. The property test judges the assembled string each agent will actually receive, never the ingredient list.

   Where the Workflow route is unavailable in a session, the dispatch, and any re-aim of it, takes the Agent tool at its row's own model override and the agent's frontmatter effort. The model is the row's own: sonnet or opus below Fable, fable for the finishing reviews, opus for compensation per finishing-work's bare fallback. The Chapter then records the review as run at reduced effort against its row's effort rather than silently.

   **The compensation notch belongs to gate-shaped work and never to plan-following work**, which is the rule step 1 states and this is its ground. Compensation belongs to the gate with no backstop. That is what makes it a reviewer's instrument and never an implementer's, and what extends it to the consultant and the scope adjudicator alike: a shallow ruling gets adopted and steers the section with nothing downstream re-asking the question. A below-Fable reviewer's `high`, first-aim or re-aimed, is the rule's own level rather than this notch.

4. **Address findings.** These routes are the correctness tier's, the adversarial and blind lenses'. An advisory lens's Critical or Major takes the advisory disposition paragraph below and none of them. A Critical from a correctness lens is fixed before the section closes. A Major is read for its provenance first, per the paragraph below, which decides what it enters. Then it is fixed, bucketed, or recorded in the Chapter with the justification for not fixing it. A Minor is read at adjudication and upgraded on a stated consequence. Otherwise it is recorded in the section's Minor list and fixed in one pass at section close. Claim findings take the split the terminal condition below states, and the accumulating ones join this list. A Minor outside the section's scope takes the out-of-scope route below.

   The Minor list is a file the orchestrator keeps at `.kit/scratch/<plan-slug>/minors-section-<n>.md`. It is created at the section's first Minor with the file tool rather than composed on a command line. It carries one line per Minor as the lens printed it, with the round number prefixed. `.kit/` is gitignored scratch, so the close pass reads that file and nothing deletes it.

   The close pass runs after the terminal condition below is met and before the close gate, and no review round follows it. A Minor whose fix would meet the fix-delta bar below, its two triggers and its judgment clause alike, is left with the reason rather than fixed, so the pass never owes a round. The pass's delta takes step 5's below-bar author re-read, recorded in the Chapter as an author re-read rather than a round, so main never carries a close-pass delta nobody read.

   **An advisory lens's Critical or Major is weighed and dispositioned, never routed.** This paragraph is the advisory tier's whole route, so a finding from the performance-reviewer or the security-reviewer is read here and under no other paragraph of this step. Every Critical and Major an advisory lens returns gets one line in the section's advisory list, `.kit/scratch/<plan-slug>/advisory-section-<n>.md`, kept as the Minor list above is. The line carries the finding as printed and one of three dispositions with its reason: fix now, defer (the backlog entry it went to), or refuse (why it does not apply to this project's stated requirements and deployment). A fix-now fix joins the fix round the correctness findings open. Where none is open, a fix whose delta would meet the fix-delta bar below opens a fix round of its own before the terminal condition is read, never the Minor close pass, which forbids owing a round, and a fix below the bar joins the close pass. A fix-now lean on any advisory Critical or Major takes one relevance ruling from the scope adjudicator before the fix is written: does this finding apply to this project's stated requirements and deployment. A refuse or a defer of a Major, or of an uncited Critical, needs no ruling. The ruling is that charter's relevance shape, the seat dispatched as the held-finding paragraph below dispatches the `scope-adjudicator`, on the fixed brief its charter states for this shape. That brief carries the finding verbatim, the plan's `## Goal` and `## Intent` record, and one item more by lens. For a security finding it is the finding's `threat:` field and the project's `## Threat model` section from `docs/security-model.md`, or the line `threat model: absent`. For a performance finding it is the requirement the finding names, quoted from the plan or stated as assumed, and the acceptance bullet it quotes where it quotes one. Nothing else rides. The ruling returns `CONFIRM`, `REFUSE` or `ASK`. The orchestrator adopts it rather than re-deriving it, and checks on its own surface that its `GROUNDS` names a positive ground rather than a bare absence, as the design-stop paragraph below checks a bucket's. On this shape that positive ground may be a quoted sentence of the project's `## Threat model` section. Where the model is absent it may be the deployment sentence the Intent record and the Goal state. A residual `ASK` satisfies the check too, by naming the sentences it read and what none of them settled. That is the bucket the charter designates where no sentence can be quoted for either other bucket. The one blocking case is a security Critical carrying a `threat:` citation, `threat: absent` read as one. It takes the ruling whatever the orchestrator's lean, since the citation is a claim the lens makes about this project. Where the ruling confirms a cited security Critical, the finding takes a correctness Critical's route: fixed before the section closes or raised to me, and never frozen by the round backstop below. Where the ruling refuses, the finding is dispositioned refuse on the judge's ground. A security Critical carrying no citation is read as an advisory Major. An `ASK` on a Major or an uncited Critical dispositions the finding defer, with the judge's recommendation as the backlog entry's reason. An `ASK` on a cited Critical takes the blocking case's raise branch, as an item under the plan's `## Operator Verification` rather than a BLOCKED hold. The honesty duty has one narrower route. A security-lens finding that a security document or a security-boundary comment states something the code does not do takes fix now, or a Chapter line naming the sentence and why the finding does not hold, and never defer, since a false sentence left standing is a defect under the doctrine's nothing-untrue-ships rule. The claim-class region below binds the two correctness lenses alone, the charters that carry its copies, so a security-lens finding on any surface, a published contract included, is advisory by lens. A fix-now advisory fix takes the add-decision line and the design stop below like any correctness Major, because the two rulings ask different questions. The relevance ruling asks whether the finding applies to this project. The design stop asks whether the mechanism the fix adds traces to a clause, and a relevance ruling that confirms a finding says nothing about whether a guard no clause names is the right fix for it. Where that stop rules on a confirmed cited Critical's fix, a refuse on a negative-half ground or an ask takes the blocking case's raise branch rather than justified-not-fixed, since that case is the one advisory finding a section never closes unfixed and unraised. An advisory finding never opens a round on its own, never enters the provenance read below, and never fires the design stop or the round backstop on its own. A fix round its fix's delta owes under the fix-delta bar counts toward the backstop as every fix round does, because opening it was the orchestrator's act. Where a correctness lens and an advisory lens report one defect, the advisory copy is dispositioned as covered by the correctness finding. An advisory finding of Minor weight joins the Minor list as any Minor does. The Chapter's `Metrics:` line carries the tally, `advisory: <v> findings, <w> fixed, <d> deferred, <e> refused`, beside the provenance tokens, which count correctness findings only.

   A behavior finding states a failure scenario: an input or a state where the code does the wrong thing on a reachable path, or a test exercises the wrong thing. Its fix changes what runs or what a test exercises. A claim finding states none, no input the sentence names failing today. Its fix changes a sentence and nothing that runs: a comment, a header, a docstring, a test's because-string or title, a test instrument's stated reach.

   One exception holds a claim finding to a behavior finding's bar. It is a claim on a published contract surface: a README, a skill, a charter, a document under `docs/`. It is owed in two cases. One is a sentence in the section's own delta contradicting an acceptance bullet, a Goal sentence or an Intent clause of the `Trace target:`, which the finding's `trace:` quotes, the orchestrator making that trace for the blind lens as the provenance paragraph has it do. The other is a pointer that delta left aimed at nothing, wherever it sits. Every other claim there rates as a claim finding. A claim finding whose trace names no such clause rates Minor whatever severity it arrived with, and the adjudication downgrade is recorded on the Chapter's Minors line as an upgrade is.

   **A Major enters a fix round on its provenance, never on its severity alone.** Provenance is read at adjudication, before any fix exists. It is read from the finding's trace and the diff, never from the repair that follows. It takes one of three values, and their precedence makes them exclusive. A finding tracing to no acceptance bullet, no Goal sentence and no Intent clause is new-requirement, wherever its lines sit. A finding tracing to one and sitting in lines a fix round of this section wrote is fix-introduced. Every other traced finding is spec-traceable. One subject is exempt from the first value whatever its trace. A Major reporting that the delta built something the plan's `## Out of Scope` list keeps out, something the Intent record says done does not need to do, or an alternative that record refused, or that it contradicts a decision the plan records, is spec-traceable rather than new-requirement. It asks for a removal the plan already ordered rather than for a mechanism nobody asked for.

   Reading the fix-introduced value needs a per-round record the base ref does not carry, since under two of the three commit models nothing this section wrote is committed at the moment the read happens. So capture the section's delta when each review round returns, before its adjudication and so before any fix round it owes, with `git diff <base> -- <the section's Files in scope> ':(exclude)docs/plans/**' ':(exclude)docs/archive/**' ':(exclude)kaizen/**' > .kit/scratch/<plan-slug>/<section>/fix-round-<n>.diff`. That command lists tracked paths only. So each path in the section's Files in scope that is absent from the index is appended to the same capture with `git diff --no-index -- /dev/null <path> >> <capture>`, one call per such path. `git ls-files --error-unmatch <path>` failing is what establishes the absence. The call runs from the repository root with the path spelled repo-relative and carrying no `..` segment, since `--no-index` reads any path it is handed, outside the worktree included. A path under one of the three excluded roots is skipped rather than appended, because `--no-index` honors no exclusion pathspec and the append would otherwise carry exactly what the exclusions keep out. The call exits 1 whether it captured the file or could not read it, a new file being itself a difference, so its exit code is no reading. The reading is that the capture grew, and an append that grew it by nothing names a path the section did not create as spelled. Intent-to-add is refused as the alternative: `git add -N <path>` puts the path in the index, which the staged-list read reads and which the subagents-neither-stage rule keeps empty until the scope check.

   Capture n is taken at review round n's return, so one file on its own is the delta as that round found it rather than the lines any fix wrote. The fix-introduced value is read as the difference between consecutive captures: round n's fix lines are what capture n+1 holds and capture n does not. A judge's brief on a single held finding names the latest capture alone, read whole for the finding's lines. Keep the project's `.gitignore` covering `.kit/`, per the Delegating section's rule, or the capture is a tracked file carrying the fix narrative into the next commit.

   The trace is supplied by whichever party holds the spec. The adversarial, security and performance lenses are dispatched with the spec path and carry a `trace:` field on the output line of every Critical and Major. The blind lens is dispatched without the spec by design and cites nothing, so the orchestrator traces its Criticals and Majors at adjudication, and the Chapter records that trace as orchestrator-made. A `trace: unsupplied`, which a sighted lens returns only where it was dispatched with no spec path at all, is read as no trace supplied rather than as a trace of none. That finding is traced by the orchestrator and recorded as orchestrator-made exactly as the blind lens's is, since a lens that never held the spec has asserted nothing about the plan. The document pair sits outside the read altogether: the reader and prose lenses return comprehension and prose findings, so no trace is asked of them and none is made for them.

   A trace is a reviewer's assertion rather than a fact, and the check runs in both directions, since each has its own failure. Before reading provenance off a cited bullet, Goal sentence or Intent clause, confirm that it exists in the `Trace target:` and covers the finding's subject. An existence check alone passes any real bullet quoted at an unasked mechanism. Before holding anything on a `trace: none`, re-trace it against that same target. A lens that missed the bullet would otherwise cost a hold, a judge and a ruling on work the plan did ask for. Either re-trace is the orchestrator's and is recorded as orchestrator-made, like the blind lens's.

   A Critical from a correctness lens governs ahead of all of this. It keeps the route the out-of-scope route below already gives it: fixed before the section closes or raised to me. Provenance is read on it for the Metrics line alone, so it is never held and never bucketed. Below that bar, a spec-traceable or fix-introduced Major takes the add-decision below and then the fix round. A new-requirement Major never enters one. It is held, and the section continues on every other finding, the hold being on the disputed finding alone.

   The held finding goes to a judge. The judge is the repo's live Expert seat where the `ListAgents` roster the peer-sessions skill owns shows one, reached through the completion contract's expert-ask paragraph above. Otherwise it is the `scope-adjudicator`, dispatched through the Agent tool with the fable model override at that charter's own frontmatter effort, and through `Workflow` only as the compensation route above directs, where its fable tier could not be run. It is dispatched on the fixed brief the charter states, whose contents and whose forbidden inputs are the charter's to state rather than this paragraph's. That brief carries no `Amendments in effect:` line, whatever the sighted-only rule says of a reviewer. The block's own contents are operator decisions and adopted judge rulings, and the charter refuses the rulings as inputs. So an amendment that moved the acceptance bullets reaches the judge by refreshing the what its brief quotes rather than through that line, the plan's what being its Goal, its `## Intent` record, its acceptance bullets and its `## Out of Scope` list.

   Three things differ from the ask that expert paragraph otherwise describes. A bucket is a ruling the asker adopts and records rather than a source it verifies, the question being scope rather than fact, which is why the asker does not re-derive the scope call. What it does check on its own surface is the ruling's `GROUNDS`. That check reads a positive ground rather than an absence, since a refusal grounded on nothing but the missing bullet quotes back the very fact that put the finding in front of the judge and would pass every time it was made. So a refuse names the Goal reading, the Intent clause or the `## Out of Scope` entry that keeps the finding out, and the check confirms that entry exists and reaches this finding. For that purpose the check reads the plan's `## Out of Scope` list beside the `Trace target:`, since a refusal's ground routinely sits in the list rather than among the bullets. An accept-and-declare names the Goal sentence or the Intent clause it serves and the bound it stays inside, and the check confirms that sentence or clause exists and that the declared work adds no mechanism the trace target does not already carry. Wherever a bullet is quoted, the check confirms that it exists in the target and covers the finding's subject.

   Say plainly which bound this widens rather than claiming the expert paragraph's hold here unchanged, because that paragraph's own address is one nothing corroborates. There an answer supplies a lead the asker verifies and may never suppress an escalation. Here a refuse does suppress one, on the operator's recorded decision that a scope call is a ruling to adopt rather than a fact to re-derive. The `GROUNDS` check is the whole of what that decision rests on. So a ruling whose `GROUNDS` will not check out on this surface is a lead rather than a ruling, and the finding falls to the adjudicator as an unanswered ask does.

   A `NEEDS_CONTEXT` return from the adjudicator is a defect in the brief rather than a ruling. Correct what the charter names missing or forbidden, and re-dispatch once before the close gate, as the first dispatch runs. Where the second return is `NEEDS_CONTEXT` too, the finding takes the ask bucket's route to me with both returns in the brief. Its first line is fixed, `BLOCKED: section <n> holds a new-requirement Major; the judge returned NEEDS_CONTEXT twice`, since the bucket literal names a recommendation the judge never made. The Chapter records the ruling with the seat that gave it.

   That expert paragraph states no answer window, so this one does. An ask unanswered by the time the section's other work is ready for the close gate falls to the adjudicator, dispatched then and before that gate runs, and no section closes with a finding still held. A seat's answer arriving after that dispatch is late, and the adjudicator's ruling is the one in force, recorded with the late answer beside it. Record a held finding on the Chapter's `Review Findings:` field with what it waits on, since a hold that lives only in context dies at the next compaction.

   The judge returns one of three buckets, a set closed at three: refuse, accept-and-declare, and ask. A finding meeting neither of the first two tests is an ask.

   Refuse is for a finding off the goal path as the Goal, the `## Intent` record and the acceptance bullets draw it, or inside what the plan's `## Out of Scope` list keeps out, what the Intent record says done does not need to do, or an alternative that record refused. It is recorded in the plan doc's `Standing Brief Amendments` block as the ground rather than the verdict. The ground is the Goal reading, the Intent clause or the `## Out of Scope` entry, written as a rule the next round judges against and never as a finding named and rated refused. That block rides verbatim on every sighted `Amendments in effect:` line, and a line naming a finding and its disposition is exactly the pre-judging step 3 bars. A refusal moves no bullet, so it never refreshes the what a judge's brief quotes.

   Accept-and-declare is for a finding that serves the Goal, is bounded and adds no new mechanism. It re-enters the finding as spec-traceable, so it takes a fix round and the close gate like any other. Its record has one home, the same `Standing Brief Amendments` block, written there at adoption as that block's own trigger below requires. The declaration changes what every later dispatch is built from, and step 3 rebuilds the `Trace target:` from that block rather than from a session's memory of a ruling. It is written as one appended acceptance bullet stating the declared behaviour and nothing else, carrying no lens, round, seat, bucket or ruling provenance. That same block is quoted into a later judge's own trace target, and a bullet carrying its ruling's history hands that judge the prior ruling its charter refuses as an input. The Chapter's approval-drift line and the line in the next board recap are that adoption's record rather than a second home.

   Ask is for a new mechanism, a changed recorded decision, a reopened accepted risk or section-sized work. It goes to me on the BLOCKED path with the judge's recommendation folded into the brief's own recommendation. That declaration's first line is fixed rather than composed: `BLOCKED: section <n> holds a new-requirement Major; the judge recommends an ask`. Where the review-round backstop below fires on the same adjudication, its line leads instead and carries this ask in its body, on that paragraph's own precedence rule. The finding, the judge's recommendation and the evidence ride in the body, under the public-board cap that path already carries. An ask is the one bucket that disposes of nothing. Refuse and accept-and-declare settle the finding where they land. An ask holds the section at this step until the answer arrives: the section does not close, steps 5 through 8 do not run, and what the answer closes is the section rather than the round.

   **Every Major entering a fix round gets one line before anything is built, and so does every section at its open.** That line is the add-decision. The orchestrator writes it to `.kit/scratch/<plan-slug>/add-decisions-section-<n>.md`, kept as the Minor list above is, the Chapter not existing until step 6. It names five things: what the fix changes; the Goal sentence, Intent clause or acceptance bullet it serves; whether it adds a mechanism; its size as a number where one exists, lines, branches or states for code and bytes for prose; and what not building it costs. A mechanism is a unit of behavior that runs and that no such clause names. A fallback, a retry, a special case and a guard are members and not the boundary, while a renamed identifier, a moved line or a changed message is not one, since nothing new runs.

   The line step 1 writes at a section's open fires no stop: a section whose line names a mechanism no clause names is an intake gap, routed under the intake gap check. A line an implementer's report carries mid-work is appended beside it when the orchestrator adjudicates that report, and on an inline section the orchestrator writes both and takes the stop itself on a mid-work line naming a mechanism no clause names. A Critical from a correctness lens takes no line at all, since it cannot fire this stop and is fixed before the close.

   **A fix whose add-decision adds a mechanism no clause names is a design stop, not a fix round.** The trigger is that line rather than severity, provenance or a round count. The stop fires at the adjudication that wrote the line, before the fix round opens and before anything is built.

   The question it puts is whether the mechanism the fix proposes to add should exist, and if it should, what its design is. It is on the consult skill's trigger floor: a question on the premise, answered on fresh context before the repair is written. The seat it convenes is the judge the paragraph above names rather than the `consultant`, because that judge must never receive the querent's lean. The second half of the question is answered in the bucket rather than in prose, the judge ruling on scope and not on design.

   The brief is the `scope-adjudicator` charter's fixed one. For this shape it carries the add-decision line's first four parts, the finding verbatim, and the latest capture as the state of the tree. Where an implementer's report raised the stop rather than a review finding, that report's add-decision line stands in for the finding and the capture is taken at that adjudication and named `add-decision.diff` rather than for a round. It never carries the line's cost clause, nor the account of a round. The one re-dispatch, the double-`NEEDS_CONTEXT` exit and the `GROUNDS` check are the paragraph above's, inherited whole. A refuse passes that check on this shape by naming the bullet, Goal sentence or Intent clause the finding traced to, or the one the add-decision line names it would serve where no finding exists, and the form it asks for. The check confirms not that the clause exists, which the trace or that line already settled and which would pass every time, but that the mechanism proposed departs from the form that clause asks for, which is the whole of what separates a refuse here from a declare on the same clause. An `## Out of Scope` ground passes as the paragraph above states it. The inherited exit carries one change: its BLOCKED takes this shape's own fixed first line, `BLOCKED: section <n> hit a design stop; the judge returned NEEDS_CONTEXT twice`, since on that exit the judge recommended nothing and neither paragraph's recommendation literal is true there.

   The section continues on every finding the proposed mechanism does not touch, as the hold above works.

   The answer window is the paragraph above's, inherited whole. Where the stop leaves no other finding in flight the window is zero and the adjudicator is dispatched at once.

The case a run meets is the same resumption under a new session id that step 0 names, with the same re-arm remedy and the same bound: the resumed run re-arms with `--self-armed`, and any other session leaves the goal alone. It writes the calling session's id from its own environment, so it runs from the session's shell rather than an operator's. What the checkpoint admits and how long it lives are stated by the CLI's own open message and the gate hook's header.

Compaction is the harness's own: native auto-compaction may fire mid-run on a long session, and the plan doc plus its Chapters are the recovery spine.

**On a gated run, compaction lands at chapter and interim boundaries by design.** With a kit goal armed and this session holding the leash, the kit's PreCompact gate defers auto-compaction mid-chapter. It stands aside once step 8 or the interim ritual below has opened a checkpoint, so the compaction falls where nothing is half-finished. A deferral you notice mid-section is the gate working, never a fault and never something to act on: do not clear the goal, do not touch the checkpoint other than through the interim ritual below, and do not treat it as context pressure. A safety valve allows the compaction regardless once consumption nears the model's limit, so sustained deferral cannot wedge a run on the roughly 1,000,000-token window its ceiling assumes. That assumption is the one part of this that does not fail safe. On a model with a smaller window the valve would sit above the hard limit and never fire, and nothing detects that. So the standing instruction to ignore a deferral holds on a full-window model, and a run that is actually climbing toward its limit with compaction still being deferred is the one case worth surfacing to me rather than ignoring.

**A closure drought earns an interim boundary.** Two consecutive review-round adjudications with no section closing is the floor that names a drought. A run that can see one forming may write the entry early, since the count is the floor, not a gate on judgment. The deferral nudge is the second trigger: `compact-deferral-nudge.js` says so at the return of a long tool call, naming how many offers it is holding and for how long. Either trigger earns the entry. Treat the nudge as the more reliable of the two. At either trigger, append an interim board entry to the plan doc below `## Chapters`, honor the commit model for the doc, then open the checkpoint with the same CLI call step 8 names. The checkpoint's own expiry is what bounds an interim boundary no compaction consumes, since step 0's clear runs only when a section starts. The entry supplements step 8 and never replaces it: it is not a Chapter and carries no `Completed:` line. Its heading is `### Interim board N - YYYY-MM-DD`, N counting the plan's interim entries the way Chapters count theirs, a shape the Chapter-heading row of curating-docs' machine contract never matches. The entry carries, in order: each in-flight section's stage, the live dispatches and what each was asked, the current gate baseline, the rulings adopted since the last boundary, and the next action per section. That baseline carries the moment the moment-pin bullet of `skills/testing-discipline/SKILL.md` under the kit plugin root requires. Under Review-Only the entry is written and staged like everything else and the checkpoint still opens.

Then continue to the next section. Do not stop here.

## The consult

The consult is a single read-only fresh-context agent convened to rule on a question the session could not settle. It is the `consultant` at every shape but the design stop, whose judge step 4 names. The consult skill (`consult/SKILL.md`) owns its triggers and its mechanics: when to convene it, what the brief carries, the model rule, and how a ruling is adjudicated. A second opinion arrives through fresh eyes, or through a warm peer holding context this session lacks: the consult for a question whose framing may be wrong, the expert ask for an answer that may already exist, the reviewers for a diff.

## Delegating to subagents

The orchestrator stays the designer: it writes dispatch prompts, judges findings, reads implementer diffs, and writes Chapters. Keep a task in the main session only when it is design-entangled, tiny, or session-state-dependent. Design-entangled means its shape is still being discovered in contact with the code. Tiny means the prompt would cost more than the work. Session-state-dependent means an in-flight debugging chain.

A subagent loads the skill catalog (one-line descriptions) and, where the machine's CLAUDE.md carries the kit doctrine import, the global doctrine. It loads neither the skill bodies, the conversation, your in-flight directives, nor the kit's memory context. The SessionStart memory blocks never reach a subagent. The harness injects its auto-memory index only where that feature is enabled. The memory-system skill's recognition nudge hands a dispatch at most a pointer at its boundary, where an `agent:` trigger names its type. So assume no memory arrived and carry any memory that bears on the section in the brief. Forward every standing directive verbatim (the style contract, the exact constraint).

**Write the dispatch prompt from the actual current code,** assuming a skilled engineer with zero context for this codebase. The Dispatch Brief template in step 1 names the fields.

**Hand bulky inputs over as files,** not pasted inline: the spec, or a diff captured with `git diff > .kit/scratch/<name>.diff`. Keep the project's `.gitignore` covering `.kit/`. The blind-reviewer is the standing exception: it takes the base ref or changed-file list per step 3's contract, never a captured diff.

**A subagent's report comes back in its final message, not as a committed file.** The implementer's status protocol and the reviewers' findings lists are terse by design, so have each return its report inline and distill the durable outcome into the Chapter. A large review can still use the summary-plus-file pattern: return the verdict, the Critical/Major/Minor counts, and the top finding inline, and write the full findings to a file the orchestrator reads only when adjudicating. A report file goes to `.kit/` per the doctrine's curated-`docs/` rule. The same discipline applies to read-only scouts, whose return contract is below. Parallelize only when tasks touch non-overlapping files; lock shared contracts first and assign disjoint files.

**Stagger concurrent sections; lockstep is the anti-pattern.** Advance them offset: one being briefed, one implementing, one in review. Run steps 4 through 8 for a section the moment a round's step 4 ends with nothing blocking its close, which is a fixes-then-re-review cycle clearing at its final round's adjudication, and never batched with siblings. A step 8 close reached while siblings are in flight appends an interim board entry beside its Chapter, carrying the closure-drought rule's content list.

**A brief grants nothing a mechanical guard denies.** Where a PreToolUse guard keys on agent type, widening the agent's file scope in the brief text is inert: the write is blocked whatever the brief says. Route around the guard at dispatch time instead. Send an agent type the guard admits, keep the guarded write in the main thread, or tell the agent up front to return the text in its report for the main thread to place. The `docs/` routing override in step 1 is this rule's standing instance.

**A brief forbids nothing the guard does not govern.** The mirror of the rule above: the readonly-agent-guard binds only the types its own classifier names. So a scout dispatched as Explore or general-purpose, or a Workflow `agent()` call naming no `agentType`, carries Bash the guard never reads, and its brief's read-only instruction is a request, not a control. Every read-only-intent dispatch under an ungoverned type therefore takes its own tree-state bracket: `git status --porcelain` before dispatch and again at return, any delta taking step 3's round-bracket incident path. The named types are instances, not the boundary: the governed set is the guard's own classifier, so a type you cannot place as governed gets the bracket.

**Band the scout by question shape, and state its return contract.** A closed fact-check (does X contain Y, confirm a value, verify a checklist item) rides the harness default. Open discovery (map a surface, find every call site) gets an explicit sonnet override. Top-model recon is pure burn either way, and a "simple check" that comes back with more than a couple of leads was mis-banded: re-run it as discovery. Every scout dispatch states its return contract in the prompt. Each lead comes back as a file:line reference with a one-sentence fact and why the site matters, never pasted file contents, and bulky evidence goes to the gitignored `.kit/` scratch path, read on demand.

**Serialize what the environment cannot share.** Implementation stays single-agent-per-worktree when it touches shared state, and the long integration suites run through one controller, per the doctrine's sequencing bullet.

## Chapter format

Append to the `## Chapters` section of the plan doc:

```markdown
### Chapter N - YYYY-MM-DD
Completed: <N. section title, the bare section number leading; one section per Chapter>
Implemented By: <main session | implementer-haiku | implementer-sonnet | implementer-opus | implementer-fable, plus any escalation>
Metrics: <review rounds <n>, closed <clean | claim-exit | major-closed>; provenance <s> spec-traceable, <f> fix-introduced, <r> new-requirement, rulings (<a> refused, <b> declared, <c> asked); advisory: <v> findings, <w> fixed, <d> deferred, <e> refused; NEEDS_CONTEXT count; escalations; consults <n>>
Recap: <omitted from a section Chapter, carried on the finishing Chapter alone; the plain-language recap whose parts and order finishing-work's step 6 owns>
Decisions / Surprises: <the section's add-decision lines, carried verbatim and line by line from `.kit/scratch/<plan-slug>/add-decisions-section-<n>.md`, the section's own open first, or on the finishing Chapter from the interim board entry `finishing-work` writes them to; then anything resolved or discovered; "none" is acceptable for that second part; in the kit's own repository, one line for the probe pair reading writing-skills' RED and GREEN step calls for, or the state that step names instead, or that no scenario turned on so no pair ran, or that the change named no shape file, none of which is recorded as clean, with its moment-pin where a pair ran>
Assumptions: <the declared-assumption entries recorded during this section; "none" is acceptable>
Review Findings: <held: <finding> awaiting <seat>; design stop: <mechanism>, ruling <bucket> by <seat>; `review: <pair or lens>[ (<n> readers)] at <model>, <route>[ (<chain>)]`, per dispatch where a pair split, or `review: <pair or lens> ungated (<chain>)`, `blind: no code diff` beside it where the blind lens was skipped; then Critical/Major addressed, a Major whose trace the orchestrator made rather than a lens named as orchestrator-made; Majors justified; Minors: <n> fixed in the close pass, <m> upgraded on a stated consequence, <k> left with the reason; on the finishing Chapter alone, `goal read: <b> built-but-unasked (<a> refused, <d> declared, <c> asked), <u> asked-but-unbuilt`>
Stamps: <adjudicated N, stamped M; "none surfaced" is acceptable where the stretch was accounted for; a window that owed a hand walk says so, why, and what the walk found>
Gate: <the lane or lanes that ran: the targeted lane at every section close; the contention lane beside it where the section's delta touched machine-shared state; the whole gate where step 7's push lands on an install-surface trunk; and the contention lane again beside that whole gate, which is a second trigger rather than the same one; their counts as tests/pass/fail and the exit code read from the run itself, the code itself rather than a statement that it was read; the delta against the baseline recorded on that same lane, or that no baseline exists on it; the section's test delta: tests added, tests retired, and tests edited to stay green on the section's own change, with one line per added or edited test naming the requirement it pins; the count of added tests that spawn a process, directly or through a shared helper, a generated site counted once with its instance count beside it; the run's wall clock and its contention reading in the form testing-discipline's clock-and-box bullets state, as a delta against the baseline recorded on that same lane; a retired test's retire class, and for a retired guard, grant, refusal-path or designed-copy test its surviving cover or the `docs/security-model.md` sentence amended to record that none stands; any contention the run carried; and, in the kit's own repository and on a final Chapter alone, the probe set's reading where finishing-work's step 6 calls for one: for each invocation of each leg that step calls for, the summary line the runner prints to stdout, whose fields the runner's own README owns, quoted verbatim except that a path it printed in full, there or in a quoted refusal reason, is respelled repo-relative or left out on the Delta line's rule, with the process exit code beside it where the two differ, the warning lines of the run's report.md beside it where any printed, the mismatched moments by name with each row's status, and its moment-pin as the Delta line below carries its own; a reading that reports and never blocks>
Next: <next section, or "finishing-work">
Commit Model: <Review-Only | Branch-and-PR | Commit-and-Push>
Delta: <the moment-pin for the reading below, in the form this format's own paragraph requires of every measured figure a Chapter records, since the verb's output carries no machine and no contention of its own; then the reading `node <plugin-root>/scripts/kit-size.js report --repo <the project's root>` prints, quoted in a fenced block below this line exactly as it prints it, whatever rows, totals or non-output line it holds>
```

Chapters exist so that a compacted or fresh session can recover full working state from the plan doc alone. Write them for that reader.

The Metrics line doubles as the data feed for the kit's open experiments (the tier-band question and the consult-adoption watch in `docs/backlog.md`), so record it even when every count is zero. Its `closed` is read off the last round that carried findings: `major-closed` where that round carried an owed Major, `claim-exit` where it carried a claim finding and no such Major, and `clean` otherwise, a section with no round included. Its `consults <n>` counts consultant dispatches alone. A judge's ruling on a new-requirement Major or a design stop, the Expert seat's and the scope adjudicator's alike, is counted under the provenance tokens instead, so the backlog's consult-adoption series keeps measuring the one thing it has always measured.

The provenance tokens count every Critical and Major from a correctness lens that survived adjudication, a correctness Critical included, since it is read for this line even though it is never held. They count correctness findings only. An advisory lens's Criticals and Majors are counted on the `advisory` tally beside them, which step 4's advisory disposition paragraph defines, and nowhere else on the line. The `rulings` parenthetical counts every bucketed ruling rather than only the new-requirement findings it sits beside, a design stop's ruling bucketing a proposed fix and having nowhere else on the line to go. A relevance ruling is the one bucketed ruling counted nowhere on this line: its buckets are `CONFIRM`, `REFUSE` and `ASK` rather than the three this parenthetical names, a `CONFIRM` maps to none of them, and the advisory tally carries no slot for one. A finishing goal read's buckets are counted on its own `goal read:` field and never here. A double-`NEEDS_CONTEXT` exit counts under `<c>` on either paragraph's route, the finding having reached me for an answer whether or not a judge recommended it. A stop counts once, as the single ruling it is, and the Major whose fix it held, where a finding raised it, still counts under its own provenance value. So `<a> + <b> + <c>` runs short of `<r>` by the correctness Criticals that read as new-requirement and were fixed on their own route, and long by one per design stop, neither direction of the difference being a defect. The `Review Findings:` field is what names a design stop and the ruling it took, so a reader reconciling that arithmetic has a field to read it off rather than a subtraction to guess at. A declared finding counts once, under `<b>`, never again under `<s>` when its fix round comes.

The Assumptions line is the home the intake gap check under Before starting gives an execution-time assumption.

The Gate line's test delta is a record. Nothing on that line is a review finding at the section, since the Chapter is written after review. The modelled price of a spawning test is its wall clock against every future section. It is stated in the Chapter body under testing-discipline's price paragraph and never on the Gate line. At the finishing pass the verifier reads the plan's Gate lines against the whole changeset. A test the changeset adds that no Gate line names with the requirement it pins is a finding there, once per plan.

The Delta line resolves `<plugin-root>` the same way the Dispatch Brief template's style-skill bullet does. It names the repository outright because the reading's default root is derived from where the script itself sits, which under a marketplace install is inside the plugin payload rather than inside the project. It quotes the verb and states no condition of its own. Which rows that output holds, which it omits, whether this project is one the reading measures at all, and what each of its three non-output lines means are the verb's own answers. They are stated at `scripts/kit-size.js` rather than copied here, where a copy could only go stale against the tool. One rule the field imposes on all three: any path they carry is spelled relative to the project's root or left out. The BLOCKED first line already follows that rule. The rule exists because an absolute checkout path carries the operator's user name into a tracked document.

The Delta output sits after every line the Chapter heading's machine contract reads rather than between them. The fence is no barrier to that parser, which reads a Chapter body line by line. What keeps the reading harmless is that no line the verb prints can open with `Completed:` or `Next:`: a row opens with a path under a measured root and every other line with a label of the verb's own. The verb also strips a leading markdown heading marker from any path it prints, which would otherwise end the parser's Chapters block. The Gate line's probe legs sit between the contract lines instead, so the rule on their writer is the whole protection. That rule holds over every line an author adds to any Chapter field, the finishing Chapter's assumptions block among them: no such line, quoted or free, opens with `Completed:`, `Next:` or `#`, and a recorded text that would is respelled there with the respelling noted. The runner's summary line opens `probe-corpus:` and the report's warning lines `- WARNING:`, which is what lets both be quoted verbatim.

What the reading compares is the worktree against HEAD, so what it covers depends on where HEAD stands when it is taken. Under a commit model where HEAD does not move during the plan it reports the accumulated delta of every section since. Under one whose section commit lands before the Chapter is written it covers the delta since that commit rather than the section whole. On a shared checkout it carries any other session's uncommitted edits under the measured roots too, which is why the row list is worth reading rather than only the totals.

A Chapter is a journal-layer artifact, so every measured figure it records carries its moment in the form the moment-pin bullet of `skills/testing-discipline/SKILL.md` under the kit plugin root states. That is what lets a later reader tell a live number from one the machine expired. The deep evidence behind a figure keeps the home that bullet gives it, so the Chapter cites the analysis rather than restating it.

The Chapter heading and its `Completed:`/`Next:` lines are a machine contract read by external tooling, not just kit convention. See `curating-docs/SKILL.md`'s machine contract section for the frozen shape and which values register a section complete.

## When all sections are complete

Invoke the finishing-work skill; the effort is not done without it. This holds under Review-Only, which defers only the commit: finishing-work still flips the plan to Complete, archives it and stages it with the code.
