# Executing Work

Once the spec is approved, execute it under the completion contract below: no per-step check-ins, no "should you continue?", no gating individual edits.

Interrupt me only for a member of the blocker set below. Everything else is yours to resolve and record.

## The completion contract

The spec is the goal. Once execution starts, run every remaining unblocked section to completion in this session. A section boundary is not a stopping point. A long-running gate is not a stopping point. Context pressure is not a stopping point. The only reason to stop mid-spec is a true blocker, and when you hit one you make it impossible to miss.

For an externally-driven worker (the External-engine stand-down), the directed section is the whole goal: finishing that one section and stopping is completion under this contract, never an early stop, because the engine verifies the section and spawns the next worker itself.

**Do not end your turn** to:

- report progress between sections ("§3 done, say the word and start §4"). Close the section and start the next.
- wait on a build, test suite, or Live gate ("holding for the gate, ~2 min"). Wait on it in-turn: background it and poll a readiness signal (`until` on a marker or exit code), then continue when it returns.
- manage context ("pausing here rather than open §7 at the tail of a long run"). The Chapter plus the SessionStart resume hook make a fresh session lossless; starting one is my call, never your reason to halt.
- await a dispatched subagent ("holding while the implementer builds §3.1b"). A background agent (`run_in_background: true`, the Agent-tool default) ends your turn to await its completion notification, and under an armed leash that bare turn-end is a stop the hook blocks. A wait is not a stop here either: keep the turn alive. The in-turn loop below is the only shape a wedge reading can be taken in. Step 1's quiet-agent bullet owns the choice between that loop and the synchronous call. The loop yields to the `WAITING:` occasion, the one turn-end the hook does allow, once the dispatch is the only remaining work and its first-turn reading is resolved. Dispatch a single critical-path implementer synchronously (`run_in_background: false`) so its whole run is one in-turn call, unless the dispatch carries a model override, which is refused the synchronous shape whatever its length and waits on the in-turn `TaskOutput` loop below instead. For any other live agent (a parallel fan-out member, or an agent continued via SendMessage, which always resumes in the background), wait in-turn on real task status: `TaskOutput(task_id, block: true)` blocks until the run completes, resumed runs included. It returns at its own `timeout` first, which is thirty seconds where the parameter is omitted and ten minutes at the highest value it takes. Loop the call until status reads completed, capping each call's `timeout` per the `WAITING:` stop shape's hold mechanism below while finishing-work's unavailability rule has any window pending on an in-flight dispatch, so no window elapses whole inside a call. A call that times out mid-run returns a raw truncated slice of the agent's JSONL transcript inline (thinking blocks and tool payloads, not the report); only a call whose status reads completed yields the final message, so treat a timeout's payload as the expected cost of an overrun and call again, never as the result and never, on its own, as a stall. Only the wedge hallmark, which finishing-work's unavailability rule owns, makes a stall out of silence, and that rule owns the cadence on which this loop evaluates it. Never infer completion from transcript-file quiescence either: a mid-run pause reads as done, and completion is read from task status or nowhere. Where the wedge hallmark calls for a growth reading, take it the way finishing-work's rule specifies, at the artifact it names. Never end the turn on a completion notification while a leash is armed, the `WAITING:` occasion above being the one turn-end that is not that bare stop, and never clear the leash to escape the block: that abandons the very continuity it exists to hold.

Rationalization table (the excuse, and why it is wrong):

| The excuse | Why it is wrong |
|---|---|
| "This is a clean boundary to pause at." | Clean boundaries are for resuming, not for stopping with work left. Continue. |
| "Holding for the gate." | A wait is not a stop. Poll the gate in-turn and continue. |
| "It is the tail of a long run, safer to stop." | The Chapter plus resume hook protect you. Context is my call, not a stop condition. |
| "Let me confirm before continuing." | The approved spec is the confirmation. Continue unless a true blocker hits. |
| "I'll end the turn to await the dispatched agent's notification." | Awaiting is a wait, and a wait is not a stop. Take the in-turn shape the dispatch row above names; do not end the turn, and do not clear the leash to get out of the block. |
| "I don't have enough context left to review the next round properly." | Compaction gives you a fresh window and the plan doc carries the state. The choice is not stop-versus-ship-unreviewed; it is compact-and-review versus abandon. Continue. |

The table is instances, not the boundary: any reason to stop with unblocked work remaining that is not in the blocker set below is wrong the same way, whether or not a row names it.

Red flags that you are about to stop wrongly: "say the word and continue", "holding for", "paused here", "at the tail of", "ready to continue when you are", "holding while the agent builds", "awaiting the notification". If you are about to write one of these with unblocked work remaining, do not. Keep going.

**Stop only for a true blocker, and make it loud.** The blocker set:

- an external dependency only I can satisfy (a GUI action like a Docker memory bump, a cloud resource that must be provisioned, a credential or secret you cannot reach),
- a contradiction inside the spec, or a material decision the spec does not cover,
- a destructive or irreversible action that needs my yes,
- a systematic-debugging dead end.

The set is closed. Capacity is never on it: native compaction gives a fresh window with the leash intact, and the plan doc plus its Chapters carry the state, so a stop reasoned from context is a stop dressed as a blocker. The `WAITING:` shape's two occasions below, a turn whose only remaining work is dispatched background subagents and a park at a safe boundary taken on a request per the park skill, are not on the set. Each ends a turn with the leash armed rather than work stranded, so neither is the stop this set governs and neither is a route to one.

**Before any BLOCKED at all, the expert ask goes out, and it goes ahead of the consult.** Where the repo has a live expert seat on the roster, the blocker goes to it before you declare; the peer-sessions skill owns that route, the seats it runs between, and the bounds on both ends, and this paragraph is where the moment lives. It goes first because it is the cheaper instrument and the one that resolves from sources that already exist, and it never gates: send it, keep working whatever is still workable, and declare at exactly the point you would have with no ask in flight. What an answer discharges is narrower than it looks, and the two instruments are asking different questions. The ask is about whether the answer already exists somewhere, so it prevents a declaration only where it hands you something you verify on your own surface, an existing source that answers the question with its provenance traced, or a diagnosis you can reproduce; a peer's say-so is a claim to check rather than the thing that settles it. The consult is about whether your framing is wrong, so it still runs on whatever decision survives the ask, and the ask never stands in for it. Neither discharges a blocker that exists because only I may say yes. Where no expert seat is live there is no ask at all, and you go straight to the consult path below. On declaring, also notify this machine's live coordinator seat where one is up, which routes the escalation rather than resolving it, and the expert too where the ask went unanswered. The ask and the notice carry the same public-board cap the first-line paragraph below puts on the declaration's first line, and they carry it as a standard rather than as a reading of where either lands, stated against a public board so that moving the board somewhere quieter never reads as relaxing it. Reach is what puts each leg in scope, never what warrants the cap on it: the ask goes to an address nothing corroborates, any session being able to answer to an expert's name, and the notice is what the coordinator briefs from. `docs/security-model.md` carries the readership analysis behind the standard, and the coordinator skill owns the precondition it names, which bounds what that seat may land rather than what a sender may send. And an ask that prevents a declaration is an agreement reached over messaging, so the record rule binds it exactly as it binds any other: the resolved ask lands in the plan doc in the same turn, or a post-compaction session re-hits the blocker with nothing to show it was answered.

**Before any BLOCKED that turns on a decision, the consult runs too, after the ask and before the declaration.** Two shapes in the set above are not decisions to rule on and go straight up: an external dependency only I can satisfy, and a destructive action waiting on my yes. For the rest, a spec gap is mine to answer only where the answer turns on preference, cost, or risk appetite; where it turns on facts about the system it is rulable, and a mixed question is ruled first so that what reaches me is the small real fork. The BLOCKED that survives carries the ruling in its decision brief; the consult skill owns the mechanics. Step 4's review-round backstop makes the one substitution this paragraph admits, a design stop's own ruling standing in for this consult on the conditions that paragraph states and on no others.

When you stop, the message's very first characters are `BLOCKED: <exactly what you need from me>`, so I see it in seconds rather than discovering a silent halt hours later. The body under the prefix is a decision brief in the doctrine's client-briefing register: a BLOCKED lands on my phone hours later with no session context, so it must be decidable from the brief alone. The bare prefix opens the message: no close-out summary above it, no bold or heading wrapping it; put any shipped-work recap after the BLOCKED paragraph. The Stop hook releases only on that exact leading prefix and deliberately ignores a `BLOCKED:` sitting mid-message (quoting the convention must never release the leash). A release whose BLOCKED line gives capacity as its reason (context, compaction, a fresh session) is refused the same way: capacity is not in the set, so that stop bounces too. A progress update is not a stop and must not be written as one.

**The first line carries only what you would put on a public board, because it travels further than the rest of the message.** The rest of the declaration is addressed to me alone. The first line is not: on a mid-queue advance the Stop hook records it into the blocked plan's outcome note, which this machine's coordinator seat reads onto an operator brief and onto that seat's board. So compose that one line for a public board and keep it inside 120 printable-ASCII characters, since what runs past is dropped mid-clause and reads downstream as though it were whole. The cap is a standard rather than a reading of where the board sits, stated against a public board so that moving the board somewhere quieter never reads as relaxing it; `docs/security-model.md` carries the readership analysis behind it, and the coordinator skill owns the precondition it names, which bounds what that seat may land rather than what a sender may send. Spell any path in it repo-relative rather than absolute. The cap holds whatever the queue position, and the recording is what varies: the last plan of a queue records no note at all, while the coordinator notice carries that same line either way. The peer-sessions skill states the same cap over the messages this route adds, and it is restated here because this is the paragraph a leashed run actually reads while a worker mid-run may never load that one.

Waiting is the third stop shape, and it has two occasions. One is a turn whose only remaining work is background subagents already dispatched: do not hold the turn open with a foreground wait, and do not dress the pause as a blocker; end the turn with `WAITING:` as the very first characters, naming the dispatch that is pending. The completion contract's dispatch row states when the in-turn loop yields to this occasion. Where a dispatch is what the turn ended on, evaluate the hallmark at the first re-block after the wake, before doing anything else with that dispatch.

The other is a park at a safe boundary per the park skill, taken on a request rather than on the run's own judgment of its own work, the operator-declared update window being the occasion that ordinarily produces one. The request is the predicate because it is the one the receiving session can evaluate; the window's operator-initiated condition sits with the coordinator that declares it, the party that can establish it, and never with the receiver. There the park skill's drain runs first, every live dispatch finished or explicitly stopped by its steps, and only once nothing is left in flight does the turn end on the same `WAITING:` lead, naming the park and its ground as the park skill's ground rule states it. Where an in-flight dispatch's growth window or its first-turn window has already closed by parking time (finishing-work's unavailability rule defines both readings and owns their windows), run the hallmark check through to its probe, or, where the pair reads synthetic-only, through the TaskStop that route begins with, before writing this line: the first-turn window is readable from the dispatch record you hold at the moment you park, and the growth window is too in its elapsed-since-dispatch fallback form, its own opening, the last observed growth, being a session observation the record does not carry. Where a dispatch is young enough that its first-turn reading is still pending, do not park yet, which is a hold rather than a refusal: that window closes minutes after dispatch, at the point finishing-work's rule sets, so a park written inside it leaves the window to close with nobody looking, and a `WAITING:` stop on the dispatch occasion written between that close and the growth window's, where the reading came back both counts zero, sleeps the run on a dispatch that may never have started. Hold the turn in-turn per the completion contract until every in-flight dispatch's first-turn reading has been taken and resolved on the pair it returns: a pair reading both counts zero is run through its probe, while a synthetic-only pair is granted no probe by the owning rule and takes its TaskStop at the first-turn window's close instead, finishing-work's reading stating what each pair is. The re-dispatch half of that route belongs to the dispatch occasion alone, because a park may leave behind a finished agent or a stopped one and never a fresh dispatch: a turn ending on the dispatch occasion runs the route whole and waits on the successor's own reading, while a parking session stops the agent, records in the interim board entry what it was asked and that it never started, and leaves the re-dispatch to the session that resumes; park only on what survives. Nothing in the kit wakes a parked session on a timer, save a parked coordinator seat's own reconciliation wake, whose conduct the park skill states. What bounds the park is the leash: the armed goal stays surfaced at session start and to the doctor, and re-arming is the recovery, so a park that never wakes is visible rather than silent.

The hold carries its mechanism, because the only in-turn hold the contract names is a blocking `TaskOutput`, which returns at its own `timeout` rather than at the run's end, and a window running inside that call is observed only at that return. While any of the unavailability rule's windows is pending on an in-flight dispatch, a first-turn reading, a growth window, or a running probe window, cap the block by passing `TaskOutput`'s `timeout` parameter, which on v2.1.205 is a millisecond count taking 30000 where it is omitted and 600000 as its maximum, so the ten-minute figure is the ceiling on what you may pass and never what a bare call gives you: set it to the lesser of the time remaining until the earliest pending window closes and that 600000 maximum, rather than to a window's full length. The cap is not this pre-park hold's alone: it rides every blocking `TaskOutput` the completion contract loops while such a window is pending, since the awaiting loop is where most windows are actually observed and a loop passing the maximum to spend fewer calls observes a window as much as ten minutes late. The window's figure stays finishing-work's and is not copied here, since no test pins the two files' figures to each other. The leash allows a `WAITING:` stop without releasing (the goal stays armed), the completion notification re-invokes the session where a dispatch is what was pending, and the run continues under the same leash. The same literal-leading-prefix mechanics as BLOCKED apply, and a WAITING whose reason is capacity is refused the same way.

**The goal template.** A plan run's completion leash is armed in one line with `/kit-goal docs/plans/<plan>.md`. The kit-goal skill owns the canonical condition and enforces it with a deterministic kit Stop hook.

Arming costs nothing on a long run because the state outlives the session. The kit hook's state is a file in the project (`.kit/`), which no session boundary can delete, and native compaction preserves the session id, so an armed run rides its own auto-compactions with the leash intact. A session the hook cannot tie to the bound one is treated as a bystander and allowed to stop, so a run left unheld takes the re-arm remedy step 0 of the section loop states: the whole queue under `arm --self-armed`, and any other session leaves the goal alone.

**A plan arriving mid-run is itself the trigger to arm it, once its standing holds.** Whether an inbound plan carries the standing to be armed at all is settled before any arm rather than after it, and the peer-sessions skill owns that gate: the standing of the message itself, and the trace of a `## Dispatch Authorization` grant to the operator, which is mandatory and which no tool performs for you. A plan whose standing does not establish is held rather than armed. Where it does hold, the run re-arms the queue at the earliest boundary this run's tree allows, through the kit-goal CLI in whichever of its two forms the project's state calls for, and an arm refused because the tree predates the plan's commit fires the trigger at the next safe tree advance instead, per kit-goal's deferred-receiver rule. That state has three readings and not two. Where a queue is already armed, `arm --append --self-armed <plan path>` extends it under the existing binding, the flag recording that this run made the arming invocation rather than the operator. Where nothing at all is at `.kit/goal-state.json`, the append refuses, says so, and names the bare form, and the bare `arm` is what that state calls for, a first arming rather than an extension. Where something is at that path the CLI cannot read as a goal state, the append refuses too and deliberately names no command, because the bare form is a replacement: run there, it would overwrite a live leash, its queue, its history and its binding, with nothing left able to say what went. So key the bare form on the goal state being genuinely absent, which is what its own refusal reason states, rather than on the append having refused. The bare form replaces the queue rather than adding to it, so it names every plan that is to be held, the one this run is already working first and the inbound one after it: `arm --self-armed <plan in flight> <inbound plan>`. Run it from the run's own cwd, since the goal family resolves from cwd and a call from the other side of a checkout boundary reads that tree's own state, finding a different leash or none at all. Tell the sender which state the plan reached, in the reply vocabulary the peer-sessions skill owns, since the handoff stays open on its side until a reply arrives and only the armed acknowledgment converts it. A plan held rather than armed goes to the plan doc in the same turn, naming what the hold waits on: the interim board entry where no Chapter is being written this turn, else the Chapter. This is a rule about when to arm and never about when to stop: a plan arriving mid-run is not in the blocker set above and is not a reason to end the turn, so the arm happens and the run continues into its next section with a longer queue behind it.

**Handoff.** When execution begins inside a conversation that was just brainstorming, say so in one line ("Spec approved, switching to autonomous execution of all N sections") so I see the mode change and can scope it down ("just §1") if I want. I should never have to set an external goal to get full execution.

## Before starting (or resuming)

Read the plan doc in full, **including all Chapters**. The Chapters are the state: they record what is done, what surprised us, and the commit model in effect. After a compaction, this re-read is mandatory before touching any file, and so is re-loading this skill. Re-invoke `executing-work` through the Skill tool before the next step, re-read the plan doc from disk, and re-load through ToolSearch any deferred tool schema the work ahead needs. Where the harness does leave a visible truncation notice inside a loaded skill or a tool result, that notice is the same trigger.

**On an armed run, never stop to ask whether the plan was approved: the kit-goal skill's arming-is-approval rule already answered it.** Where the plan's `Status:` header reads anything other than `In Progress` or `Complete`, set it to `In Progress` as part of starting; a header already reading `In Progress` is left exactly as it is. `Complete` is the one value the normalization does not touch, because flipping it would be the run silently overwriting the record of a close-out rather than repairing a header: a plan a run is starting whose header says the work is finished is a contradiction between the doc and the fact of the run, and it takes the contradiction path in the blocker set above rather than a quiet flip. The curating-docs skill's machine contract owns the `Status:` lifecycle and the values the kit's tooling reads. The header sits inside the approval-scoped fingerprint region the `## Assumptions` rule below describes, so where the value did change, the first Chapter this run appends records the normalization, naming what the header read and the `In Progress` it now reads, which is what marks it deliberate rather than drift; where nothing changed there is nothing to record. A worker under an external engine (the stand-down below) leaves the header to its engine.

**Then run the intake gap check on the plan doc.** List what each section does not state that its implementer would need. The listing runs here; the routing runs after the memory recall below, since memory is one of the sources a gap routes to, and every gap is routed before its section is dispatched. On an armed run, a material gap (the spec-does-not-cover decision the blocker set already names) is the `BLOCKED:` the leash already handles, named there because the `goal-blocked` event is the surface that reaches me while I am away; on an attended run it is a decision ask instead. A non-material gap, answerable from an existing source (route (a): doctrine, memory, the plan doc, the code's conventions; cite it) or covered by a low-blast reversible default (route (b): pick it and declare it), is recorded on that section's Chapter `Assumptions:` line, in brainstorming's declared-assumption line format dated today with `, section N` in the parenthetical, and the dispatch brief carries the resolved answer rather than the gap. It goes to the Chapter and never to the plan doc's `## Assumptions` section, which sits above `## Chapters` and so inside the approval-scoped fingerprint the external engine reads: a mid-run append there reads as approval drift. That section freezes at approval and holds the design-time entries alone.

**Then run `memq recall`, once, before the first section.** It returns the whole memory store as one bounded digest; the memory-system skill owns what the digest contains and how to act on it. The plan doc carries the effort's own state, and the digest carries what earlier efforts learned the hard way, which a plan written days ago cannot cite because nobody had recorded it yet. Read it against the sections ahead and carry forward what bears on them. On a resume, run it again rather than trusting a recollection of an earlier pass, and a boundary taking the memory-system skill's hand walk runs it again too, since that walk enumerates from the digest. When a recalled record changes what you build, stamp it in that turn with `memq touch <name> --applied`.

Run it from the project root, a worktree of it, or any directory inside the project. `memq` resolves the store from the session before the shell: unless an external engine pinned it, a working directory inside the project the harness filed this session under resolves that project's store, subdirectories included, and a git worktree resolves its main checkout's store (memq follows the worktree's `.git` pointer through a two-way handshake), from the worktree's own subdirectories too in a session the harness filed under the worktree, which is where it files a session started there. What resolves a different, empty store is a working directory outside the filed project, a nested independent checkout inside it (the resolver's climb stops at the nearest enclosing repository root, so a repository boundary is a store boundary), a subdirectory of a linked worktree in a session filed under the main checkout rather than the worktree (the worktree's own boundary is the ceiling there, and the plain path derivation stands), a subdirectory in a session no transcript answers for, a bare-repo worktree, or a worktree whose handshake fails (which announces itself with a `git worktree repair` note on stderr); the tell is a digest whose coverage lines all read zero on a project you know has memories.

**External-engine stand-down.** When the driving directive states that an external engine owns continuation by spawning a fresh worker per section (Spine's Dispatch pump is one), or the environment carries `KIT_EXTERNAL_ENGINE` (the marker such an engine sets at spawn), the engine is the supervisor and this session is its worker. Run the section loop for the directed section only. The marker is a directive to you, not a mechanism: treat it exactly as you would the driving directive's own words. The **worker runs this skill** - it orchestrates, dispatches implementers, and writes Chapters exactly as any session would; it does not absorb implementation inline just because it is headless.

**Workspace and siblings.** If concurrency put you in a worktree on a feature branch, that is your workspace; integration and any teardown happen in finishing-work. Expect sibling sessions to touch the same repo, so own a disjoint set of files, and never stage another session's uncommitted work or carry it in a commit of yours.

## Section loop

For each Section of Work, in order (sections run concurrently only where the disjoint-files rule in "Delegating to subagents" permits):

0. **Close the previous boundary.** If the run is leashed, clear any compaction checkpoint the last boundary left open, since work is about to resume and this is no longer a boundary:

   ```
   node <plugin-root>/hooks/kit-compact-checkpoint.js clear
   ```

   Resolve `<plugin-root>` the same way the Dispatch Brief template's style-skill bullet does (step 1 below carries that rule). It is a no-op when nothing is open, so it costs one call on the first section. It refuses at exit 1 over a record that is another session's boundary, and over a state it cannot read (a goal state that is present but unreadable, or something other than a regular file at the checkpoint path), naming the remedy in each case: the case a run meets is a resumption under a new session id against a goal still bound to its dead predecessor, and that resumed run re-arms the goal with its whole queue (`arm --self-armed`, the invocation being the run's own), which rebinds it, while any other session leaves the goal alone. One further exit-1 reading carries its remedy on the CLI's own line: a caller id the shell cannot resolve over a record that is somebody's boundary, which is why the verb runs from the session's own shell.

1. **Confirm the approach, then implement.** Before writing a section whose mechanism the spec assumed without reading the code, do a quick in-session read of the files it touches and confirm the planned approach holds, taking any file you are opening to find one mechanism in through the doctrine's rule on hunting in a large file, and reading whole any file that is itself the mechanism. Confirming a mechanism often spans call sites and error paths, so where you do outline, expect to read more than one of the ranges it names. This is a lightweight read, not a fan-out; if the real shape differs materially, adjust and note it in the Chapter (raise it to me only if it changes design intent). Then implement per the section's model tier, which is a dispatch instruction rather than a hint: a section carrying a `Model:` tier goes to that tier's implementer, and the doctrine's standing dispatch request covers it, including where a session-prompt line makes dispatch conditional on my having requested it.

   **At each section open, whatever the section's locus, grep the plan doc for its `Standing Brief Amendments` block and hold every entry as binding on this section's work.** Step 4 writes to that block mid-run, so a full-doc read taken at an earlier section is stale by construction and the grep is what establishes the current text; a grep that finds nothing is the read. On the dispatch path the entries then ride into the brief; an inline section has no brief for them to fold into, so the grep is the only delivery that path gets.

   - **A section that writes under `docs/` goes to the main thread regardless of the tier it carries.** An implementer may still draft the prose and return it in its final message for the main thread to place, but the `docs/` write itself is always the main thread's. (This is a routing override, not a tier change: record `Locus: inline` under the section's `Model:` line so the override is visible up front, and leave the `Model:` value the bare tier it earned.)
   - **Tier `haiku` / `sonnet` / `opus` / `fable`:** dispatch the matching `implementer-haiku` / `implementer-sonnet` / `implementer-opus` / `implementer-fable` agent with a complete brief built from the Dispatch Brief template:

The `docs/` routing override in step 1 is this rule's standing instance.

**A brief forbids nothing the guard does not govern.** The mirror of the rule above: the readonly-agent-guard binds only the types its own classifier names, so a scout dispatched as Explore or general-purpose, or a Workflow `agent()` call naming no `agentType`, carries Bash the guard never reads, and its brief's read-only instruction is a request, not a control. Every read-only-intent dispatch under an ungoverned type therefore takes its own tree-state bracket: `git status --porcelain` before dispatch and again at return, any delta taking step 3's round-bracket incident path. The named types are instances, not the boundary: the governed set is the guard's own classifier, so a type you cannot place as governed gets the bracket.

**Band the scout by question shape, and state its return contract.** A closed fact-check (does X contain Y, confirm a value, verify a checklist item) rides the harness default; open discovery (map a surface, find every call site) gets an explicit sonnet override. Top-model recon is pure burn either way, and a "simple check" that comes back with more than a couple of leads was mis-banded: re-run it as discovery. Every scout dispatch states its return contract in the prompt: each lead comes back as a file:line reference with a one-sentence fact and why the site matters, never pasted file contents, and bulky evidence goes to the gitignored `.kit/` scratch path, read on demand.

**Serialize what the environment cannot share.** Implementation stays single-agent-per-worktree when it touches shared state, and the long integration suites run through one controller, per the doctrine's sequencing bullet.

## Chapter format

Append to the `## Chapters` section of the plan doc:

```markdown
### Chapter N - YYYY-MM-DD
Completed: <N. section title, the bare section number leading; one section per Chapter>
Implemented By: <main session | implementer-haiku | implementer-sonnet | implementer-opus | implementer-fable, plus any escalation>
Metrics: <review rounds <n>, closed <clean | claim-exit | major-closed>; provenance <s> spec-traceable, <f> fix-introduced, <r> new-requirement, rulings (<a> refused, <b> declared, <c> asked); NEEDS_CONTEXT count; escalations; consults <n>>
Recap: <omitted from a section Chapter, carried on the finishing Chapter alone; the plain-language recap whose parts and order finishing-work's step 6 owns>
Decisions / Surprises: <anything resolved or discovered; "none" is acceptable; in the kit's own repository, one line for the probe pair reading writing-skills' RED and GREEN step calls for, or the state that step names instead, or that no scenario turned on so no pair ran, or that the change named no shape file, none of which is recorded as clean, with its moment-pin where a pair ran>
Assumptions: <the declared-assumption entries recorded during this section; "none" is acceptable>
Review Findings: <held: <finding> awaiting <seat>; design stop: <mechanism>, ruling <bucket> by <seat>; `review: <pair or lens>[ (<n> readers)] at <model>, <route>[ (<chain>)]`, per dispatch where a pair split, or `review: <pair or lens> ungated (<chain>)`, `blind: no code diff` beside it where the blind lens was skipped; then Critical/Major addressed, a Major whose trace the orchestrator made rather than a lens named as orchestrator-made; Majors justified; Minors: <n> fixed in the close pass, <m> upgraded on a stated consequence, <k> left with the reason; on the finishing Chapter alone, `goal read: <b> built-but-unasked (<a> refused, <d> declared, <c> asked), <u> asked-but-unbuilt`>
Stamps: <adjudicated N, stamped M; "none surfaced" is acceptable where the stretch was accounted for; a window that owed a hand walk says so, why, and what the walk found>
Gate: <the lane or lanes that ran: the targeted lane at every section close; the contention lane beside it where the section's delta touched machine-shared state; the whole gate where step 7's push lands on an install-surface trunk; and the contention lane again beside that whole gate, which is a second trigger rather than the same one; their counts as tests/pass/fail and the exit code read from the run itself, the code itself rather than a statement that it was read; the delta against the baseline recorded on that same lane, or that no baseline exists on it; any contention the run carried; and, in the kit's own repository and on a final Chapter alone, the probe set's reading where finishing-work's step 6 calls for one: for each invocation of each leg that step calls for, the summary line the runner prints to stdout, whose fields the runner's own README owns, quoted verbatim except that a path it printed in full, there or in a quoted refusal reason, is respelled repo-relative or left out on the Delta line's rule, with the process exit code beside it where the two differ, the warning lines of the run's report.md beside it where any printed, the mismatched moments by name with each row's status, and its moment-pin as the Delta line below carries its own; or the state that step names instead, or that the changeset named no shape file so no run was called for, none of which is recorded as clean, a before leg the after leg gave no moments for being none of them, a `(partial)` line marked as the leg its re-run replaced, and the exit code marked unreadable where the doctrine's fallback path left none; a reading that reports and never blocks>
Next: <next section, or "finishing-work">
Commit Model: <Review-Only | Branch-and-PR | Commit-and-Push>
Delta: <the moment-pin for the reading below, in the form this format's own paragraph requires of every measured figure a Chapter records, since the verb's output carries no machine and no contention of its own; then the reading `node <plugin-root>/scripts/kit-size.js report --repo <the project's root>` prints, quoted in a fenced block below this line exactly as it prints it, whatever rows, totals or non-output line it holds>
```

Chapters exist so that a compacted or fresh session can recover full working state from the plan doc alone. Write them for that reader. The Metrics line doubles as the data feed for the kit's open experiments (the tier-band question and the consult-adoption watch in `docs/backlog.md`), so record it even when every count is zero. Its `closed` is read off the last round that carried findings: `major-closed` where that round carried an owed Major, `claim-exit` where it carried a claim finding and no such Major, and `clean` otherwise, a section with no round included. Its `consults <n>` counts consultant dispatches alone, while a judge's ruling on a new-requirement Major or a design stop, the Expert seat's and the scope adjudicator's alike, is counted under the provenance tokens instead, so the backlog's consult-adoption series keeps measuring the one thing it has always measured. The provenance tokens count every Critical and Major that survived adjudication, the carve-out's Criticals and security findings included, since those are read for this line even though they are never held. The `rulings` parenthetical counts every bucketed ruling rather than only the new-requirement findings it sits beside, a design stop's ruling bucketing fix-introduced Majors and having nowhere else on the line to go. A finishing goal read's buckets are counted on its own `goal read:` field and never here. A double-`NEEDS_CONTEXT` exit counts under `<c>` on either paragraph's route, the finding having reached me for an answer whether or not a judge recommended it. A stop counts once, as the single ruling it is, however many Majors its held unit carried, and those Majors still count individually under `<f>` where they belong, so `<a> + <b> + <c>` runs short of `<r>` by the carve-out findings that read as new-requirement and were fixed on their own route, and long by one per design stop, neither direction of the difference being a defect. The `Review Findings:` field is what names a design stop and the ruling it took, so a reader reconciling that arithmetic has a field to read it off rather than a subtraction to guess at. A declared finding counts once, under `<b>`, never again under `<s>` when its fix round comes. The Assumptions line is the home the intake gap check under Before starting gives an execution-time assumption. The Delta line resolves `<plugin-root>` the same way the Dispatch Brief template's style-skill bullet does. It names the repository outright because the reading's default root is derived from where the script itself sits, which under a marketplace install is inside the plugin payload rather than inside the project. It quotes the verb and states no condition of its own. Which rows that output holds, which it omits, whether this project is one the reading measures at all, and what each of its three non-output lines means are the verb's own answers, stated at `scripts/kit-size.js` rather than copied here, where a copy could only go stale against the tool. One rule the field imposes on all three: any path they carry is spelled relative to the project's root or left out, on the same rule the BLOCKED first line already follows, because an absolute checkout path carries the operator's user name into a tracked document. The Delta output sits after every line the Chapter heading's machine contract reads rather than between them. The fence is no barrier to that parser, which reads a Chapter body line by line. What keeps the reading harmless is that no line the verb prints can open with `Completed:` or `Next:`: a row opens with a path under a measured root and every other line with a label of the verb's own. The verb also strips a leading markdown heading marker from any path it prints, which would otherwise end the parser's Chapters block. The Gate line's probe legs sit between the contract lines instead, so the rule on their writer is the whole protection, and it holds over every line an author adds to any Chapter field, the finishing Chapter's assumptions block among them: no such line, quoted or free, opens with `Completed:`, `Next:` or `#`, and a recorded text that would is respelled there with the respelling noted. The runner's summary line opens `probe-corpus:` and the report's warning lines `- WARNING:`, which is what lets both be quoted verbatim. What the reading compares is the worktree against HEAD, so what it covers depends on where HEAD stands when it is taken. Under a commit model where HEAD does not move during the plan it reports the accumulated delta of every section since. Under one whose section commit lands before the Chapter is written it covers the delta since that commit rather than the section whole. On a shared checkout it carries any other session's uncommitted edits under the measured roots too, which is why the row list is worth reading rather than only the totals. A Chapter is a journal-layer artifact, so every measured figure it records carries its moment in the form the moment-pin bullet of `skills/testing-discipline/SKILL.md` under the kit plugin root states, which is what lets a later reader tell a live number from one the machine expired, and the deep evidence behind a figure keeps the home that bullet gives it, so the Chapter cites the analysis rather than restating it.

The Chapter heading and its `Completed:`/`Next:` lines are a machine contract read by external tooling, not just kit convention; see `curating-docs/SKILL.md`'s machine contract section for the frozen shape and which values register a section complete.

## When all sections are complete

Invoke the finishing-work skill; the effort is not done without it. This holds under Review-Only, which defers only the commit: finishing-work still flips the plan to Complete, archives it and stages it with the code.
