# Finishing Work

An effort is not done when the last section compiles. It is done when behavior is verified, security is reviewed, documentation matches reality, and the plan doc is closed. Run these steps in order; steps 2 and 3 may be dispatched in parallel after step 1 passes, and step 4 follows them, since the curator writes under `docs/` while the reviewers are reading the changeset.

When per-section reviews already cleared parts of the changeset, tell the finishing reviewers what those passes covered and what has changed since, so they spend their budget on cross-section cohesion and on deltas rather than re-deep-reviewing unchanged, already-cleared code. Eliminate true duplication, not coverage. For a small effort that had no meaningful per-section reviews (a few files, one short pass), a single combined adversarial and security pass is enough; do not manufacture separate passes for a handful of files.

In a session running below fable, dispatch the security review (step 2) and the final adversarial review (step 3) with the explicit `fable` model override by default: the fresh-eyes strong-model verdict over the whole changeset is the oversight that makes plan-covered implementation safe. Only the literal `Fable Spend: none (cost hold)` holds these two reviews at the session model. Any other value, including one that restricts the implementation surface (some sections only, or escalation ceilings only), leaves the finishing-review fable default fully in force.

**Bracket steps 1 through 3 with the tree-state check.** Capture `git status --porcelain` before dispatching each of those rounds and compare when the round returns, before acting on any finding. A delta is the same incident executing-work's review rule names, with the same consequences: restore the tree, record the delta and the agent that produced it in the final Chapter, treat that agent's findings as suspect pending a re-review against the restored tree, and jot a kaizen note, since a delta means either a write-shaped command got past the guard or an allowance the guard grants is wider than the invariant. The check backstops every write that leaves a tracked-file delta; a write to a gitignored path or outside the git root, a mutate-read-restore inside one round, and an outward `gh` mutation leave no delta and rest on the guard alone. Step 4 is deliberately outside the bracket: the docs-curator's edits under `docs/` are its deliverable, so running it alongside a bracketed round turns its own output into a phantom incident.

## Steps

1. **QA verification.** Dispatch the `qa-verifier` agent with the spec path: full build, full test suite, and every acceptance criterion checked with evidence. Any FAIL: fix and re-run before proceeding. Do not rationalize a failing criterion as "close enough".

2. **Security review.** Dispatch the `security-reviewer` agent over the whole changeset (not just the last section). Critical findings block completion. Major findings: fix or present to me with the tradeoff. One waiver exists, on a file-type predicate, not a judgment call: when every file in the changeset is prose (markdown or plain text - no code, script, hook, config, query, or schema file anywhere in it), the dispatch may be skipped, with the skip and the changed-file evidence recorded in the final Chapter. A single non-prose file, even a one-line edit, voids the waiver: run the review, scoped to the non-prose files when the rest is prose.

3. **Final adversarial review.** Dispatch the `adversarial-reviewer` agent over the entire changeset against the spec, with the fable model override: the finishing gate always runs the top model whatever tiers wrote the sections (under a recorded `Fable Spend: none (cost hold)`, the session model). When the changeset touches C# or T-SQL, also pass the csharp-style and/or sql-style absolute paths (resolved by the same ladder as executing-work's Dispatch Brief template), so the house-style pass over the whole changeset has something to read. Per-section reviews catch local issues; this pass catches cross-section cohesion problems, leftover debris (dead code, stale TODOs, orphaned files), and spec items that fell through the cracks.

4. **Documentation curation.** Dispatch the `docs-curator` agent with the spec path and the absolute path to the scott-writing-style skill (same resolution ladder). It updates the project's docs/ from the as-built code and returns a Drift Report with each item tagged `Class: mistake | deviation`, plus the `CLAIMS SWEPT` block its charter requires. That sweep is scoped by claim rather than by changed file, so its edits and findings will reach docs the changeset never opened: a falsified count, enumeration, justification, or path is in scope wherever it lives, and treating that reach as scope creep is how the misses get shipped. A `mistake` (the code may be wrong, not just the docs) is a true blocker: stop, put it to me, and resolve it (a code, spec, or doc fix) before the PR. A `deviation` is the docs now reflecting a deliberate as-built choice: record it in the final Chapter and surface it in the PR description for awareness, with no stop. **Never silently reconcile a `mistake`; never halt the run for a `deviation`.** This fast-path means a clean or deviation-only effort flows straight through a long run, and only a likely-mistake stops it.

5. **Close and archive the plan doc.** Set `Status: Complete` and append a final Chapter summarizing the effort, the review outcomes, and the drift adjudications. Then invoke the `curating-docs` skill to finish the lifecycle: `git mv` the plan from `docs/plans/` into `docs/archive/` (history preserved, Chapters intact), act on any cross-reference gaps the docs-curator flagged, prune `docs/backlog.md` of items this effort completed into the quarter's archive snapshot, and refresh the `docs/README.md` index. A plan is not closed until it has left `docs/plans/`.

   **Finalizing the doc is not committing it.** This step runs in full under every commit model: flip to Complete, append the final Chapter, archive, and (Review-Only) stage it with the code. The Review-Only deferral is about the commit, which is mine, never about leaving the doc open. The resting state you hand me is a closed, staged plan, so my one review-commit lands the code and a Complete, archived doc together.

   | The excuse | Why it is wrong |
   |---|---|
   | "Review-Only means leave the doc open." | Review-Only defers the commit, not the truth. Flip the plan to Complete and stage it; I commit. |
   | "The plan is not done until it is accepted, so leave it In Progress." | If the work is delivered and the gates passed, the plan is Complete now. A change I request reopens it as a new round. |
   | "Flip it to Complete after the commit." | After the commit you are out of the loop and nothing flips it. That is exactly how a finished plan sits stale. Finalize before you hand off. |

6. **Apply the commit model.** For Branch-and-PR and Commit-and-Push, the docs work from steps 4 and 5 (the curator's edits, the archival `git mv`, the backlog prune, the index refresh) is committed *before* any push or PR, in the same commit series as the code. The docs ship in the same PR as the code, never as a follow-up: where neither author can release their own PR, a separate docs PR is a governance dead-end, so the docs must ride in the one authored PR. Do not open the PR, or do the Commit-and-Push final push, while the plan still sits in `docs/plans/` or `git status` shows uncommitted `docs/` changes. Red flags that you are about to strand the docs: "open the PR, clean docs after", "docs can be a follow-up PR", "the code is committed, tidy docs next". The predicate gates the PR (plan archived, `docs/` clean), not your read of whether the docs feel done. This applies to every durable record, not just docs: the Chapters, decision records, and the register are committed before the merge is requested, and the merge request is the effort's last action. A PR branch is frozen the moment it is up for merge: do not push to it again. Anything decided after that (a post-review decision, a late close-out note) goes in a separate doc PR opened last against the current integration branch, never back to the up or merged branch. Pushed is not merged.
   - **Review-Only:** present a consolidated walkthrough, every changed file, what changed and why, organized by section, with a diff summary (the staged changes are the review surface). Then stop; I review before anything is committed.
   - **Branch-and-PR:** with the docs commit already on the branch, verify the branch builds and tests green, update from origin and surface any sibling-session conflicts for resolution, push the branch, and open the pull request via host detection (GitHub `gh pr create`, Azure DevOps Git `az repos pr create`, or, when no CLI or auth is present, push and surface the "create a pull request" URL the host prints). The PR carries the title, a by-section summary, the test evidence, the archival summary, and the deviation drift items. Then present the options: merge, keep the branch for iteration, or discard. Never merge without my explicit choice; on my merge, offer the teardown below. After any merge (mine in-session, or detected on a later session), run the strand-check before trusting the records landed: `git fetch`, then `git log origin/<integration>..origin/<branch>`. Any commits there are post-merge work stranded off the trunk; recover them via a new doc PR against the integration branch, never by reopening the merged branch.
   - **Commit-and-Push:** the docs commit lands with the section commits. If the session ran directly in the main checkout, the commits already landed, so confirm everything, code and docs, is pushed. If concurrency put the session in a worktree on a feature branch: update from origin (surfacing conflicts rather than failing), merge to main, push, then **tear down: remove this session's worktree and delete its branch local and remote**. Teardown touches only the branch and worktree this session created, is reversible (the commits are already in main), and is named in the close-out.

7. **Bank the learnings.** Anything durable discovered during the effort (build quirks, conventions, gotchas, environmental facts) belongs in auto memory, not the plan doc. Save it now, while it is fresh. Settle the memory ledger in both directions: any recalled memory this effort caught being wrong should already be fixed under the same-turn rule - if one slipped through, fix it now. Then, when the effort wrote or corrected any memory and a `consolidate-memory` skill is present in the session's skill catalog, offer a pass in one line; when the skill is absent, fold the same hygiene (merge duplicates, fix stale facts, prune the index) into the memory edits you already made and say nothing. The predicate gates the offer, same as the kaizen check.

   **Run the decay pass when it is due.** When `memory/decay-stamp` in the project's memory directory is older than 14 days, or does not exist yet, run the pass; when it is fresher, skip it and say nothing. The predicate gates the pass, not your read of whether the store feels stale. The pass has three moves, in order. First, `memq decay-scan`: it only reports, so every summarize-or-archive call is yours, made where Scott can see it. Second, your judgment: summarize each summarize candidate in place, keeping its index description (that edit is yours, and it is the only hand edit in the pass), and decide which archive candidates are done. Third, `memq decay-prune --rollup`, naming each archive call as `--archive <name>` (`--archive-type <name>` for a type-tier candidate): the command mutates only what its flags name. The archive flags move those memories to the tier's `archive/`, carrying each index line to the archive's own index so a retired memory keeps its description, and prune the line from the tier's; `--rollup` rolls journal entries older than 30 days into per-key rollup entries that preserve each key's pass/fail tally and tags, folds each memory's `applied` stamps into one per-file record carrying its distinct-day count and its first and last application (the evidence the reinforcement tally reads), and prunes `read` stamps to the newest per file. A pinned memory, or one whose pin state cannot be read, is refused by name rather than archived, so remove the `pinned:` line first if retiring it is genuinely the call; the memory-system skill owns the pin. The full pass carries `--rollup`; without it nothing is rolled up or pruned from the sidecars. Under the store lock it leaves a `.bak` beside every file it rewrote and prints what it removed. Never hand-edit `outcomes.jsonl` or `usage.jsonl`; the command is the only mutation path, and a hand edit races the stamp hook that appends on every memory read, including yours. Fold in tag hygiene against the registry, then run `memq decay-done` to touch the stamp; without the touch, the next close-out re-runs a pass you already finished.

   **Then recap what the store recorded.** After the memory writes and any decay pass, run `memq recent --since <the session's span>` and carry its digest into the close-out status, labeled by surface. That is what makes the close-out's memory claim checkable: the digest names the journal entries, the applied stamps, and the memory files added or updated across every tier, so a session that banked nothing says so in its own counts. Report the digest; never paraphrase it into a claim it does not make.

8. **Kaizen check.** First make sure any kit friction from this effort (captured along the way, or a Chapter Surprise that traced to the kit) is in the kaizen inbox. Then offer a kaizen pass in one line only if the inbox has pending items; on a clean effort the inbox is empty and you say nothing. The predicate, not your read of the session, gates the offer.
