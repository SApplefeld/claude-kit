# Kaizen inbox: SCOTT-CLAUDE

- **The read that clears a shared file before staging it has to be the read that can see a hunk you did not write** (2026-08-29, worker seat, from a live collision between two seats on one checkout, and refined by the other seat at its own surface). The doctrine's scope-and-safety bullet says to re-read any shared file, the plan doc being the named case, immediately before `git add`, and to hold the add while the file carries content you did not author. Both seats followed it and the sweep happened anyway, because the rule names the moment without naming the instrument, and the instrument most readers reach for cannot answer the question. Reading the file's content tells you what the file now says; it does not tell you which of those bytes are yours, and in a 46-item backlog nobody can hold the authored set in their head to diff against. The read that discriminates is `git diff HEAD -- <file>`, which shows the uncommitted hunks and therefore shows a peer's, and it has to run before the add rather than before the commit. That ordering matters because the two existing protections cover different objects and neither covers this one: the staged-list read (`git diff --cached --name-only`, read as its own step) catches a foreign FILE in your index, and the pre-add re-read as commonly performed catches nothing at all, so a foreign HUNK inside a file you legitimately own and legitimately staged rides through both. The general shape worth carrying past git: A RULE THAT NAMES THE MOMENT TO CHECK BUT NOT THE INSTRUMENT THAT ANSWERS IS SATISFIED BY THE CHEAPEST READING THAT FITS THE WORDS, and where a cheaper reading exists it is the one that gets performed, forever, by careful people. The coordination half is the same defect wearing a protocol instead of a command. A freeze notice announcing a commit is delivered after the add has already captured the peer's worktree, because `git add <path>` takes worktree content rather than staged content, so the notice arrives about a capture that has happened and cannot be declined; a notice that could be answered has to precede the add and wait one round for a reply. Neither half lost content here, which is what makes this a note rather than an incident: the retirement hunk was correct and survived, and what actually split was a curating-docs move whose two halves, the item removed from the backlog and the dated record in the archive saying why, landed in different commits, leaving origin briefly showing two items vanished with no stated reason. Directions worth weighing rather than a settled fix. Name the instrument in the doctrine bullet, one clause, so the pre-add read is spelled `git diff HEAD -- <file>` rather than left to the reader, which is cheap and is the change that would have prevented this. Or fold the pre-add diff into whatever staging discipline the seat-infrastructure claim work settles on, since that effort is already building claim files for shared surfaces and the worktree is one. Or, at the protocol layer, make the freeze notice a pre-add notice with an acknowledgment round, which costs a round trip per shared-file commit and is the only one of the three that protects a seat which never reads this note.

- **A procedure step that names a lookup path, but not the record tier that can override that path, is followed literally and reports the override as an absence** (2026-08-29, coordinator seat, from one seat concluding a sibling seat had no ledger while an operator-tier record pinned its actual location, and from the same seat rediscovering a shell-quoting bug that two operator-tier records already documented, both inside one session). The kit's answer to "where does X live" is layered: a skill states the default path, and the operator tier records the machine-specific decisions that override it, CLI-authored and deliberately outranking a prose default. THAT LAYERING ONLY WORKS IF THE STEP THAT PERFORMS THE LOOKUP KNOWS THE UPPER LAYER EXISTS, and today several do not: the step says read the file at this path, the reader does exactly that, finds nothing, and takes the documented not-found branch, which for a coordinator's cold start is report-and-hold. What makes this worse than an ordinary miss is that THE FAILURE IS INDISTINGUISHABLE FROM SUCCESS AT THE POINT OF OBSERVATION. A settled, operator-decided, recorded arrangement looks, to a filesystem query, exactly like the thing not existing, so the reader is not careless and gains no signal that would prompt a second look. What protects a reader today is a habit imported from a different skill, the memory skill's run-recall-at-effort-start, which is real but is neither named at the lookup step nor guaranteed to have run in the branch that matters, since a cold start reaching for a ledger has often not yet done anything else. THE GENERAL SHAPE, which is the note rather than the incident: WHERE A SYSTEM LETS ONE LAYER OVERRIDE ANOTHER, EVERY STEP THAT READS THE LOWER LAYER MUST NAME THE UPPER ONE, because a reader who does not know an override layer exists cannot distinguish "absent" from "relocated," and will report the second as the first with full confidence. Directions worth weighing rather than a settled fix. The cheapest is one clause at each path-naming step pointing at the tier before the not-found branch is taken, which is small and touches several skills. A stronger version inverts the default so a location-shaped lookup queries the tier first and the path second, which costs a tier read on every lookup and removes the trap entirely. A third is to make the not-found branch itself the guard, so any step about to report an absence has to state which tiers it queried, which generalizes past locations to every absence claim the kit makes and is the only one that would also have caught the rediscovered-bug half of this note.

- **An instrument that silently truncates its render breaks every derivation built on reading it whole, and the break arrives exactly when the data grows past the render** (2026-08-29, expert seat, from the coordinator's status round: its ready-but-unarmed count, derived by subtracting the goal CLI's visible queue rows from a plans-directory grep, worked at a queue of five and failed at nine with no signal, because the CLI collapses the render at five rows plus a bare "and N more" that carries the count but hides the names the subtraction needs). The general shape: a consumer cannot tell a complete render from a truncated one unless the truncation names what it hides or the instrument offers a whole read, so a derivation built on the render is correct until the day it is silently wrong, which is the worst failure schedule there is. Directions worth weighing rather than a settled fix. Render every queue row, since a nine-entry queue costs nine lines and the collapse saves little. Or give `status` a complete machine-readable form a seat can consume, making the human render a view rather than the only surface. Or keep the collapse but make it name the hidden paths, so the count and the names both survive it.

- **A machinery-owned installed surface that accepts a hand edit and silently reverts it converts a durable-looking fix into a timed illusion** (2026-08-29, expert seat, from the live doctrine copy in the harness home: edited at the operator's ruling, confirmed changed on disk, and back to the prior text within hours with an on-the-minute mtime that points at a scheduled pass, the reverting machinery inferred rather than identified). Nothing at the surface names an owner, warns a writer, or points at the real source of truth, so an expert making an operator-ruled change has no signal that the durable path is the repo commit plus the fleet update and that the local edit is on a timer. The general shape: where machinery regenerates a file, a hand edit is not rejected but expropriated, and the writer learns it only if they happen to re-read; ownership must be visible at the surface or the overwrite must be loud. Directions worth weighing rather than a settled fix. Have the regenerating pass detect a locally-modified managed file and report the overwrite rather than performing it silently. Or state ownership in the installed copy itself, one header line naming the generating machinery and the source of truth. Or carry a doctrine clause naming installed copies as machinery-owned surfaces whose durable path is the repo.

- **A failing check's remediation text that states the class hazard rather than the measured instance converts a mismatch into a false emergency** (2026-08-29, expert seat, from the doctor's memory-sync FAIL on this box: the store's dotfiles had drifted from the doctor-derived allowlist, and the remediation text warned that an add in the store root can stage credentials, settings and transcripts, which is the mismatch class's worst case rather than this mismatch's measured exposure; independent verification with two-direction controls found the drift real and the exposure none, so the true state was a standing condition, not an emergency). The general shape: a diagnostic that cannot measure its own blast radius should say what it verified and what it did not, because worst-case prose attached to a mechanical mismatch reads as a measurement to the seat receiving it, and the cost lands either as a false emergency or as a cried-wolf discount on the next real one. Directions worth weighing rather than a settled fix. Have the check measure before it warns, a dry-run add enumerating what would actually stage, which the manual verification showed is cheap. Or split the message into the mechanical fact (dotfiles differ from canonical) and the unverified hazard, marked as class risk rather than this instance's state. Or have FAIL remediation name the verification a receiving seat should run before treating the state as an emergency.

- **Every staging safeguard is per-file and a push is per-branch, so a seat can pass every check it holds and still publish work it never staged** (2026-08-29, coordinator seat, from a false alarm on a four-seat shared checkout that turned out to contain no incident at all, which is why it is a note about the rule rather than a report of damage). The doctrine's scope-and-safety discipline is thorough on the index and silent on the ref. It says to stage exactly your target, to read `git diff --cached --name-only` as its own step before committing, to hold the add while a shared file carries a hunk you did not author, and to never chain the add and the commit so the staged list goes unread. Every one of those instruments answers a question about FILES IN YOUR INDEX. None of them answers what a `git push` will carry, because a push moves a branch ref and takes every commit beneath the tip, whoever authored them and whatever they touched. So the fully compliant sequence is available and looks clean at every step: stage one file you wrote, read a staged list containing exactly that file, commit it, push, and publish every unpushed commit on the branch below yours. The seat has satisfied the whole rule set and has no signal that anything else moved. WHAT MAKES IT WORTH A NOTE RATHER THAN A SHRUG IS THE ASYMMETRY OF THE FAILURE: the index checks exist because a bad `git add` is recoverable and embarrassing, while an unintended push is the one git act on this list that is genuinely outward-facing and effectively irreversible on a shared trunk, since the only undo is a revert commit that is itself public. The cheaper checks guard the reversible act and the expensive act is unguarded. The instrument the discipline lacks is one line and costs nothing: read `git log origin/<branch>..HEAD` before pushing and confirm every commit it names is yours to publish. The general shape worth carrying past git: WHERE A SAFEGUARD AND THE ACT IT GUARDS OPERATE AT DIFFERENT GRANULARITIES, THE SAFEGUARD PROVES SOMETHING TRUE AND IRRELEVANT, and it will keep passing for exactly as long as nobody checks whether it was ever measuring the act. A second, sharper reason the gap survives: on a shared checkout every seat commits under one git identity, so authorship cannot discriminate after the fact either, and a seat trying to establish who published what has to reason from commit times and ref movement rather than from any field git records. Directions worth weighing rather than a settled fix. Name the instrument in the scope-and-safety bullet, one clause, so the pre-push read is spelled out the way the pre-add read now is, which is the cheapest change and the one that would have prevented the alarm. Or state the granularity principle directly, so a reader generalizes it to the next per-branch act rather than learning one more git command. Or, at the protocol layer for shared checkouts specifically, treat a push as a shared-surface act needing the same freeze-notice discipline as a shared file, which is the only one of the three that protects a seat that never reads this note.
