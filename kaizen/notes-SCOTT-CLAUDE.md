# Kaizen inbox: SCOTT-CLAUDE

- **The read that clears a shared file before staging it has to be the read that can see a hunk you did not write** (2026-08-29, worker seat, from a live collision between two seats on one checkout, and refined by the other seat at its own surface). The doctrine's scope-and-safety bullet says to re-read any shared file, the plan doc being the named case, immediately before `git add`, and to hold the add while the file carries content you did not author. Both seats followed it and the sweep happened anyway, because the rule names the moment without naming the instrument, and the instrument most readers reach for cannot answer the question. Reading the file's content tells you what the file now says; it does not tell you which of those bytes are yours, and in a 46-item backlog nobody can hold the authored set in their head to diff against. The read that discriminates is `git diff HEAD -- <file>`, which shows the uncommitted hunks and therefore shows a peer's, and it has to run before the add rather than before the commit. That ordering matters because the two existing protections cover different objects and neither covers this one: the staged-list read (`git diff --cached --name-only`, read as its own step) catches a foreign FILE in your index, and the pre-add re-read as commonly performed catches nothing at all, so a foreign HUNK inside a file you legitimately own and legitimately staged rides through both. The general shape worth carrying past git: A RULE THAT NAMES THE MOMENT TO CHECK BUT NOT THE INSTRUMENT THAT ANSWERS IS SATISFIED BY THE CHEAPEST READING THAT FITS THE WORDS, and where a cheaper reading exists it is the one that gets performed, forever, by careful people. The coordination half is the same defect wearing a protocol instead of a command. A freeze notice announcing a commit is delivered after the add has already captured the peer's worktree, because `git add <path>` takes worktree content rather than staged content, so the notice arrives about a capture that has happened and cannot be declined; a notice that could be answered has to precede the add and wait one round for a reply. Neither half lost content here, which is what makes this a note rather than an incident: the retirement hunk was correct and survived, and what actually split was a curating-docs move whose two halves, the item removed from the backlog and the dated record in the archive saying why, landed in different commits, leaving origin briefly showing two items vanished with no stated reason. Directions worth weighing rather than a settled fix. Name the instrument in the doctrine bullet, one clause, so the pre-add read is spelled `git diff HEAD -- <file>` rather than left to the reader, which is cheap and is the change that would have prevented this. Or fold the pre-add diff into whatever staging discipline the seat-infrastructure claim work settles on, since that effort is already building claim files for shared surfaces and the worktree is one. Or, at the protocol layer, make the freeze notice a pre-add notice with an acknowledgment round, which costs a round trip per shared-file commit and is the only one of the three that protects a seat which never reads this note.

- **A fleet-wide maintenance act whose precondition is an unobservable global state has no window anyone can declare, so it waits on the operator noticing one rather than on the fleet producing one** (2026-08-29, coordinator seat, captured by the kit expert seat from the operator's own account of the friction and routed here under the standing kaizen function). The concrete case is the mass plugin update: its timing depends on catching every session on several machines idle at once, which no seat can observe and the operator can only sample by looking. THE MECHANISM THE NOTE POINTS AT ALREADY HALF-EXISTS, which is what makes it promote-shaped rather than a wish: the registry gives a live all-idle reading per machine, and a maintenance-window flag on the coordinator board would let every seat drain at its next banked boundary, so the operator DECLARES a window and the fleet quiesces itself rather than being hunted quiet. It rides on the seat-infrastructure registry and board machinery already shipped, so the durable form is a successor plan rather than a clause. WHY IT IS FILED RATHER THAN DECLINED, against the standing test: this is not a rule the kit states and fails to site, it is a capability the kit lacks, and the doctrine has nothing to say about it. WHAT MAKES IT URGENT ENOUGH TO CARRY RATHER THAN PARK: the same pass that captured it measured what a stale install actually costs, and it is no longer cosmetic. The installed SessionStart hook reports a backlog count off a bounded 64 KB head read of a 271,201-byte file with no truncation notice, so it prints 48 active where the file holds 191, and derives its oldest-dated figure off the same fragment so the age reads 17 days younger than the truth. That defect is FIXED in the tree and was retired as a backlog item the same day; it is live on every session because the installed build has not advanced. A PEER SEAT REASONED FROM THAT NUMBER FOR A REAL MEASUREMENT. So the general shape is that the update window and the correctness of every unattended reading are the same problem: where the install lags the checkout, a shipped fix is not a delivered fix, and the thing standing between them is a window nobody can currently declare.
