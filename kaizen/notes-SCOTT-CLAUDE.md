- 2026-08-21 | SCOTT-CLAUDE | claude-kit | A shared-tier memory is final at creation: `memq add-operator` and `add-type` can write a record and `--update` can replace its index description, but nothing repairs a body and nothing deletes. The only removal is `decay-prune --archive-operator`, which retires rather than removes, so a record created by mistake survives forever in the archive with its mistake intact, and the memory-system skill bars the hand edit that would fix it. Hit while banking this effort's learnings: a one-line probe record written to isolate a CLI failure could only be retired, not removed. The general shape is that the tier's write path and its correction path are asymmetric, which pushes a session toward composing shared-tier text under pressure not to get it wrong, exactly when it is least able to check. Candidate fixes worth weighing at the pass: a body-repair flag under the same lock the writes already take, a delete path gated the way `--confirm-shared` gates retirement, or an explicit statement in the skill that a shared-tier write is one-way so the composition bar is understood before the keystroke rather than after.

The workaround that worked was invoking `memq-shim.js` through a programmatic argv from node, bypassing the shell entirely, which is not a thing a session should have to discover mid-close-out. The general shape is that this CLI's argument surface has at least three shell-layer traps and its own diagnostics cover one of them; the pass should decide whether the fix is a hint per trap, a body-from-file flag that sidesteps the whole class, or a documented rule that shared-tier bodies are composed as single-line text.
