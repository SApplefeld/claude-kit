# The shared memory store serves one persona's own records: a segment-scoped judged search, an unindexed write, a description fallback, and a project-tier forget

Status: In Progress
Commit Model: Branch-and-PR
Created: 2026-09-25

## Dispatch Authorization

The operator asked the ARCHITECT on its channel on 2026-09-25 to convene a design council on moving the persona plugin's memory onto the kit's shared memory store, and on the council's converged design and the operator's five value rulings the same day asked for this plan as the kit half of that port, queued to the kit's expert seat ahead of the persona plugin's half. This plan has no merge precondition. It runs on a branch and lands through a pull request, since the kit's main refuses direct pushes. The persona plugin's companion plan, `agent_persona_persona-memory-port_spec_v1.md` in the `agent_persona` repository, starts only after this plan's host changes are installed, because its prompt-time read calls the verb this plan adds.

## Goal

When this ships, a caller standing in one project's memory directory can ask the shared memory store for a Jev-judged ranking of that project's own records against a situation, and get back only lines for records the caller's own segment published, optionally narrowed to one tag, never a private record another project on the same machine published. A caller that spawns memq can write one project-tier record with a description, tags and an author, into the store memq itself resolves for the working directory, with no index line, so the record never reaches a session's opening text. A memory file that carries a `description:` frontmatter line and no `MEMORY.md` index line ranks, publishes and is judged on that description rather than on an empty string. And a project-tier record can be removed outright with one locked command that takes every local copy and index line with it and tells the caller what the host will do with the row. The four together are what the persona plugin's port needs from the kit: a read that returns the persona's memories and not the fleet's, a write that lands in the right store and stays out of session start without losing its description, and a removal the operator can order by name.

## Intent

The frame, in the operator's words on 2026-09-25: "port the whole thing to the SQL memory store instead of doing the forget", so the persona plugin stops "recreating the wheel by evolving it piecemeal twice", since the shared store already has embeddings, judged ranking, decay and applied validation and the persona store has none of that. On tags: "I've been advocating for Tags and Filters since the beginning ... If this gives us an in for Tags, I'm all for it."

What done needs to do. Give the host's search a way to cut its candidate population to one segment, and optionally to one tag, before the thirty candidates are chosen, since a cut applied after the thirty are chosen starves the judge. Give memq a verb that runs the judged block under that cut and prints only its lines, for a caller that spawns it. Give memq an unindexed project-tier write, so a spawning caller lands a record in the store memq resolves rather than in a path it guessed. Let a record's own frontmatter supply its description when the index holds no line for it. Give the project tier the removal verb the shared tiers already have. State each of those on the documents that describe the store. What done does not need to do: change how `memq recall` and `memq find` rank today, add a second scope mode that no caller asks for yet, add a project-tier add verb, or change the persona plugin, which is the companion plan's.

Alternatives refused:
- A kit MCP server in place of a spawn. Refused: memq's host transport is a sqlcmd spawn per query whoever calls it, so a server saves only the Node start and costs a life-cycled component.
- Writing persona distillates as indexed records, each with a `MEMORY.md` line, through a new locked project-tier add verb. Refused by the operator's ruling of 2026-09-25: the index is exactly what the session-start hook emits, so an indexed distillate reaches every session's opening text, which he does not want; the description fallback gives an unindexed record the same ranking without that.
- Serving `find --tag` from the host now that the host is known to hold tags. Refused here: `find`'s tag branch is a local channel by design and its callers expect the local ranking; this plan only corrects the comment and note that give the wrong reason for it.
- A client-side filter over the thirty rows the procedure returns. Refused: on one persona's store here, twelve measured runs of the judged block returned none of that persona's records among the thirty, so a post-filter answers empty.
- A tag as a ranking signal. Refused: a tag says nothing about how close a record is to the situation; it decides which records compete and the embedding ranks inside that population.
- A `shared-plus-own` scope mode beside the own-segment cut, for kit recall to take later. Refused here: no caller asks for it in this plan, and the doctrine writes no mechanism a requirement does not name; it is parked in the backlog behind the measurement that would justify it.
- The persona plugin mapping its launch directory to a store path itself and writing the file with the engine's file API. Refused: memq resolves a project's segment through a pin, a worktree's main checkout or a transcript filing (`scripts/memq.js` lines 1761 to 1771), legs a plugin cannot reproduce, so a plugin-side path would file records into a directory memq never reads.

Rulings by the operator on 2026-09-25, from the council's five value calls. Three bind this plan: distillates are unindexed with a description fallback (V2); forget is built here (V3); own-segment scope, with a tag filter beside it for a persona sharing a repository store (V5). Two bind the companion plan only: the awaited bounded spawn per prompt (V1) and the applied-stamp ask (V4).

Provenance: the operator's channel messages on 2026-09-25, the design council record under the ARCHITECT's `.kit/sql-store-council/` scratch, and the ARCHITECT's read of the kit tree at `032ef32c`.

## Approach

**The cut lives in the procedure, at the fill of `#Visible`, and it never widens what the caller may see.** `mem.usp_Search` (`plugins/claude-kit/db/Procedures/100-usp_Search.sql`) fills `#Visible` from `mem.udf_VisibleRecords(@SandboxId)` at lines 177 to 202, and every one of its four candidate lists joins `#Visible` before ranks are assigned. Two new parameters narrow that fill. `@p_Segment NVARCHAR(400) = NULL` names a segment: where it is non-null, a row survives only where its tier is `project` and its segment equals `@p_Segment`. `@p_Tag NVARCHAR(200) = NULL` names a tag: where it is non-null, a row survives only where its `Tags` JSON array holds that value. Both are `AND` predicates inside the visible set, so the sandbox gate in `030-udf_VisibleRecords.sql` lines 48 to 51 is untouched and no row outside it can appear, and a call naming neither fills `#Visible` exactly as today. The segment predicate reads the tier as well as the segment because only project stores hold private rows, and it keeps a persona's promoted records too: `usp_PromoteRecord` flips a row's `Visibility` to `shared` and leaves its `Tier`, `Segment` and store alone (`120-usp_PromoteRecord.sql` lines 108 to 112). Both `Tier` and `Segment` are columns `#Visible` already carries from the function's own select (`030-udf_VisibleRecords.sql` lines 33 to 34).

**Tags are already on the host as a JSON array string.** `mem.Record.[Tags]` is `NVARCHAR(MAX)` (`db/Schema/060-Record.sql` line 37), `usp_UpsertRecords` reads it from the batch's `$.tags` as JSON (`040-usp_UpsertRecords.sql` line 169), and the publisher sends every record's frontmatter tags (`scripts/memory-database.js` line 2559). `udf_VisibleRecords` does not project the column, so the fill joins `mem.Record` on `RecordId` for the tag predicate: `ISJSON(R.[Tags]) = 1 AND EXISTS (SELECT 1 FROM OPENJSON(R.[Tags]) J WHERE J.[value] = @p_Tag)`. The `ISJSON` guard makes a null or malformed `Tags` string a row the tag drops rather than an error the call raises, and the equality runs under the database's collation as the name columns do. The function's own column list stays as it is. The comment at `scripts/memq.js` lines 7210 to 7213 and the note at line 7230 say the host holds no tags. They are wrong and this plan rewrites both to give the true reason `find --tag` stays local.

**The host takes schema version 6, and a client naming the new parameters gates on it by name.** The installer's `$script:SchemaVersion` (`db/Install-MemoryDatabase.ps1` line 123) moves from 5 to 6. The version script writes one constant `[Notes]` string for whichever version it inserts (`db/Version/010-RecordSchemaVersion.sql`, the `INSERT` at its tail), so that string gains a clause naming the segment and tag cut, and nothing else in the script changes. `scripts/memory-database.js` gains `SCOPED_SEARCH_SCHEMA_VERSION = 6` beside `SEARCH_SCHEMA_VERSION` (line 1020) and `NEAREST_ARCHIVED_SCHEMA_VERSION` (line 1033), and a search that asks for a segment or a tag against a lower host stands down by name, in the sentence shape the archived nearest scan uses at lines 1298 to 1308. The query log's digest at line 171 of the procedure hashes the query text, or the vector's text, and nothing else. Its input gains the segment and the tag by bare concatenation, each as an empty string where null and with no separator, so two calls that differ only in scope differ in the log and a call naming neither hashes byte-for-byte to what it hashes today.

**One new verb prints the judged block's lines and nothing else.** `memq judged --situation "<text>" [--tag <t>] [--limit <n>]` runs `fleetJudgedBlock` (`scripts/memq.js` line 7109) with the working project's segment, read through `memoryDatabase.tierIdentity(memDir).segment` exactly as the unjudged path reads it at lines 7053 to 7054, and under the tag where one is given. The working project is the one every project verb resolves today, a store pin included, and the verb takes no segment flag. Its stdout is the block's lines in `fleetMemoryLine` form (line 7008) and no framing, since the caller frames them. Its stderr carries the block's reason or note where there is one. It exits 0 with no lines when the host stood down, the judge fell back to nothing, or nothing cleared the floors, on the rule `recall` states at lines 9845 to 9847 that finding nothing is an answer and only argument errors exit non-zero. It records what it judged under `CLAUDE_CODE_SESSION_ID` through the same `appendShown` path `recall` uses, so a shown record can be stamped applied later; where that variable is absent or not of the harness's shape, `appendShown` omits the record with the reason `no session id` (`scripts/jev-judge.js` line 657) and the verb prints that reason on stderr beside its lines, which is why the persona plugin passes the id in the spawn's env. `--limit` is clamped to the fleet block's own ceiling, the bound `recall` applies to `FLEET_RECALL_SHOWN`, and an over-limit value is clamped rather than refused. Without a Jev configuration it prints nothing and says on stderr that the judged block needs the judge, rather than falling to the unjudged block, because a caller asking for a judged ranking must not receive an unjudged one under the same name; a reader telling that case from an empty answer reads stderr. The verb adds no clock of its own: the block's 2,000 ms budget and the judge's 1,500 ms edge inside it (`scripts/jev-judge.js` line 76) bound the work, and a caller that needs a harder stop bounds the process from outside, which is what the persona plugin does at 2,500 ms. The verb joins `GRANTED_VERBS` in `hooks/memq-grant.js` (line 329), since it writes nothing but the shown record and is the same class as `recall`.
