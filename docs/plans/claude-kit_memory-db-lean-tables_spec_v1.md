# The memory database stops logging reads and keeps usage as one flat row per memory, so neither table grows with every read

Status: Ready
Commit Model: Branch-and-PR
Created: 2026-10-03

## Dispatch Authorization

The ARCHITECT persona wrote this plan on 2026-10-03 on the operator's rulings of that day on the ARCHITECT's channel, quoted under `## Intent`. It has one precondition on dispatch: plan 1 of the memory-in-SQL work, `claude-kit_memory-in-sql_spec_v1.md`, has merged to `main`, since this plan edits procedures and a schema version that plan creates. It does not wait on plan 2, `claude-kit_retire-file-store_spec_v1.md`, and may run before or after it. The coordinator persona queues it for the worker that ran plan 1.

## Goal

When this is done, a read of the memory database writes no log row, and the usage of a memory is one row holding three facts: when it was last shown to a session, when it was last marked applied, and on how many distinct days it was marked applied. The table `mem.QueryLog` is gone, with the four inserts that fed it and every sentence that describes it. The table `mem.Usage`, which holds one row per stamp and nothing ever trims, is replaced by `mem.RecordUsage`, which holds at most one row per memory, so its size follows the number of memories and not the number of reads. Search ranking, the curator's unapplied report and the index listing read the same three values they read today, exact wherever a reader's cap can see the count. A stamp delivered twice changes nothing the second time, as today, with no stamp identifier stored. The installer carries a version 7 database to version 8 in place: it folds every existing usage row into the flat rows before it drops the old table, so no memory loses its last-read time, its last-applied time or its applied-day count.

## Intent

The frame, in the operator's words of 2026-10-03 on the ARCHITECT's channel. On the read log: "Let's stop the logging. I don't really feel the need to have logging on a local SQL database system that's meant to act as a memory interface to all my sessions. It's just in my local desktop ecosystem. I think the logging is unnecessary for that environment." On usage: "more interesting than that, I think, would be just to have flat rows", with columns per memory for "the last time it was read", "how many times it was marked applied" and "the last applied date", "basic things that would essentially serve the same purpose as the aggregate metrics that you would get from a usage per row type table." Earlier that day, on the same subject, recorded in the operator tier as `operator-wants-no-unbounded-audit-logs`: unbounded audit growth "will be a big concern pretty quickly".

What done needs to do. Remove the read log whole: the table, the four inserts, the tests that assert a row and the sentences that promise one. Replace the per-stamp usage table with one flat row per memory that serves the three values the kit reads. Carry the host's existing usage across the change with those three values intact. Keep every procedure's parameters and return keys, so a machine on an older kit keeps working against the upgraded host.

What done does not need to do. It does not keep who read a memory, which session read it, or any stamp older than the newest: no reader uses them. It does not count applied marks, only the distinct days carrying one, for the reason under Alternatives refused. It does not trim `mem.RecordStamp`, `mem.Outcome`, `mem.PublishRun` or `mem.IndexOrphan`. It does not change the client's queue, the local usage files or any `memq` verb's output. It does not run the installer against the shared host, which is the operator's act.

Alternatives refused. Keeping the read log with a 30-day purge: refused by the operator, who sees no use for a read log on a local desktop system. Keeping `mem.Usage` and trimming it on a rolling window: set aside by the operator for flat rows, and it would need a scheduled purge the kit has no runner for. Usage columns on `mem.Record` itself: refused here, since every read stamp would then rewrite a wide row whose `UpdatedDt` means the record changed. A raw count of applied marks: refused here, since ranking and decay read distinct applied days, and a raw count cannot tell a resent stamp from a new one without storing stamp identifiers, which is the growth this plan removes. A day count raised only by a stamp newer than the last: refused here, since three machines deliver on their own schedules and every applied day one of them delivers late would be lost. Trimming the write-stamp ledger `mem.RecordStamp` in this plan: refused here and stated under `## Out of Scope`, since it grows by one row per memory write and a trim needs a client guard against replaying an old queued write.

Rulings after the spec shipped: none yet.

## Approach

**What is there.** Four procedures write one `mem.QueryLog` row per call: `usp_ListRecords` (`db/Procedures/045-usp_ListRecords.sql:140`), `usp_Search` (`100-usp_Search.sql:457`), `usp_Nearest` (`110-usp_Nearest.sql:132`) and `usp_JevCalibration` (`170-usp_JevCalibration.sql:130`). No kit code reads the table. Its one reader is the operator, by hand, under the `kit_review` login. `mem.Usage` takes one row per read or applied stamp through `usp_AppendUsage` (`060-usp_AppendUsage.sql:228`), and three procedures read it, each through aggregates grouped by record and none through `SandboxId`, `SessionId` or `StampId`: `usp_Search` counts distinct applied days for the ranking boost (`100-usp_Search.sql:410-416`), `usp_CurationUnapplied` takes the newest read and the newest applied stamp (`130-usp_CurationUnapplied.sql:66-70`), and `usp_ListIndex` takes all three (`200-usp_ListIndex.sql:129-136`). No procedure deletes a row from either table, and `DENY DELETE ON SCHEMA::mem` holds for every role. All paths in this plan are under `plugins/grimoire/` unless they open with `docs/` or `test/`.

**The read log leaves.** The four procedures lose their insert, the digest computed only to feed it, and the header sentences that describe it. The table is dropped where it exists, and a fresh install never creates it. The `kit_review` login and the `mem_review` role stay, since the operator still reads records through them. Every document sentence that says a read is logged is removed or rewritten to say that no read is logged, and the security model's statement of what `kit_review` reads loses the log. The tests whose subject is a log row retire with the table, and two pins replace them: no procedure script names the table, and an installed database holds no such object.

**The flat usage row.** `mem.RecordUsage` has `RecordId BIGINT` as its primary key and a foreign key to `mem.Record`, `LastReadDt DATETIMEOFFSET NULL`, `LastAppliedDt DATETIMEOFFSET NULL`, `AppliedDays INT NOT NULL DEFAULT 0`, `AppliedDates NVARCHAR(400) NULL`, and the audit columns `CreatedDt` and `UpdatedDt` as `mem.Usage` carries them, with the fold setting `UpdatedDt`. `AppliedDates` is a JSON array of the newest sixteen distinct calendar dates the memory was marked applied, as `yyyy-mm-dd` text. Sixteen is a constant in the procedure, chosen above both caps a reader applies to the count: `usp_Search`'s `@p_AppliedDaysCap` default of 10, and the thirteen days at which `memq`'s decay extension reaches its ceiling (`EXTEND_CAP_DAYS` 365 over `EXTEND_PER_APPLIED_DAY` 30, `scripts/memq.js:579-580`). A memory with no stamp has no row, and a reader takes NULL, NULL and 0 for it, as the three readers do today through their outer joins.

**The fold.** `usp_AppendUsage` keeps its parameter, its stamp validation, its resolution of a stamp to a record and its `rejected` count exactly as they are. Where it inserted one row per stamp, it now folds the batch into one row per record:
- `LastReadDt` becomes the later of its current value and the batch's newest `read` stamp for that record.
- Each distinct calendar date among the batch's `applied` stamps for that record is a new day where `AppliedDates` does not hold it, unless `AppliedDates` already holds sixteen dates and this one is earlier than all of them. `AppliedDays` rises by the number of new days, and `AppliedDates` becomes the newest sixteen of its dates and the new ones. The date of a stamp is `CAST(StampedDt AS DATE)`, as `usp_Search` reads it today.
- `LastAppliedDt` becomes the later of its current value and the batch's newest `applied` stamp.

This rule is what makes a resend harmless with no stamp identifier stored, and it does not depend on the order stamps arrive in. A resent stamp's date is already in the list, or is older than a full list, so it raises no count, and its time is never later than what the row holds. A stamp one machine delivers days after another machine's newer stamp is still counted, since its date is not in the list. The `stampId` an element carries is accepted and ignored. The row is read under `UPDLOCK` and `HOLDLOCK` before it is written, so two deliveries for one record queue. The return keeps its three keys: `appended` is the number of stamps that resolved to a record, whether or not they changed its row, so a resent batch returns the same `appended` as its first delivery. `rejected` is as today, and `skipped` is 0. The client reads `rejected` alone (`scripts/memory-database.js:2321`).

**The limit the fold accepts.** An applied day is not counted where the memory already holds sixteen applied dates and the late day is earlier than all of them. The count is then sixteen or more, which is above every cap a reader applies, so no ranking and no decay decision changes. Only the number `memq recall` prints can read low, and only past sixteen.

**The three readers.** Each replaces its aggregate over `mem.Usage` with a join to `mem.RecordUsage` and returns the same keys with the same meaning: `usp_Search`'s applied-day count, `usp_CurationUnapplied`'s `lastApplied` and `lastRead`, `usp_ListIndex`'s `lastRead`, `lastApplied` and `appliedDays`.

**Schema version 8 and the upgrade.** The installer's version constant moves from 7 to 8 (`db/Install-MemoryDatabase.ps1:141`) with a version 8 paragraph in its history comment and version 8's notes in `db/Version/010-RecordSchemaVersion.sql`. The installer applies every script in ordinal order by directory, `Schema` before `Procedures`, and each script is idempotent. On a database that holds `mem.Usage`, one schema script creates `mem.RecordUsage` where absent, then in one transaction seeds it from `mem.Usage` and drops `mem.Usage`: `LastReadDt` is the newest `read` stamp, `LastAppliedDt` the newest `applied` stamp, `AppliedDays` the count of distinct applied dates and `AppliedDates` the newest sixteen of them, per record. One transaction means an interrupted upgrade leaves either the old table whole or the new rows complete, never both half done. On a database with no `mem.Usage` the script creates the table and seeds nothing. `Schema/080-Usage.sql` no longer creates `mem.Usage`. The drop of `mem.QueryLog` is a second schema script of the same shape with no seed. Between the schema step and the procedure step a procedure still names a dropped table, and a call landing in those seconds fails. `## Operator Verification` has the operator run the install while no session is mid-work, and a usage delivery that fails there stays in its machine's queue for the next drain. Both sections reach a host together: the version 8 notes name both changes from section 1 on, and no database but the local test instance is installed from a tree that holds section 1 without section 2. No client constant is added: every procedure keeps its signature and its return keys, so a kit below this one and a kit at this one both work against a version 7 host and a version 8 host.

**What still speaks the old contract.** A machine on an older kit sends `usp_AppendUsage` the same JSON and reads `rejected`: unchanged. It calls `usp_Search`, `usp_Nearest` and `usp_ListRecords` with the same parameters and reads the same result: unchanged. The operator's hand queries against `mem.QueryLog` or `mem.Usage` under `kit_review` stop working, which is the point of the change and is named under `## Operator Verification`. The local usage file on each machine and the local queue are untouched.

**The coverage sweep.** One read-only scout ran on 2026-10-03 over the tree at f4ae1e9e, its return held in the authoring session and restated here, outside `docs/archive/`, for every surface naming `QueryLog`, `mem.Usage`, `usp_AppendUsage` or `RecordStamp`, the installer's version and script ordering, the role grants, and the client's version gates. It found the surfaces the two sections list, and these that need no edit: `db/Security/020-Logins.sql` and the installer's login lists, which name `kit_review` and not the log; `db/Security/010-Roles.sql`'s grants and denies, which name no table; `scripts/memq.js` and the hooks, which reach `usp_AppendUsage` only through the queue; `docs/backlog.md:555`, which is a different log; and the plan 1 document, which is history once it archives.

## Out of Scope

- `mem.RecordStamp`, the write-stamp ledger plan 1 adds. It takes one row per memory write, not per read, so it grows with the store's own writes. Trimming it needs a rule for a queued write older than the trim window, which lives in the client's drain. It is a follow-up if the table's size is ever measured as a concern.
- `mem.Outcome`, `mem.PublishRun` and `mem.IndexOrphan`, which are insert-only and are the kit's data or its publish history, not read logs.
- Who read a memory and from which session. The flat row holds neither, and the per-machine usage file holds them until plan 2 retires it.
- The client's queue, `memq touch`, the read-stamp hook and every `memq` verb's output.
- Carrying usage from a losing row to a winning row when two rows merge under plan 1's twin merge, adoption or promotion. Usage stays keyed to the row that earned it, as today.
- Running the installer against the shared host.
