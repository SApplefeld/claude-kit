## Context

Decided 2026-08-16 with Scott, after an overnight incident on the ASR VM: two sessions hit the five-hour session limit mid-run ("Agent terminated early due to an API error: You've hit your session limit · resets 6:20am"), the console showed a stop-and-wait/use-credits modal invisible to the Discord relay, and the run stranded roughly eight hours until the operator reached the console.

Harness facts this design stands on (doc-researched 2026-08-16 via the claude-code-guide agent against current hooks.md/errors.md/settings.md; Section 1 live-verifies the ones marked probe):

- **`StopFailure` is a real hook event**: it fires when a turn ends due to an API error. It cannot block (exit code 2 is ignored), so it is an observer, which is exactly why the kit-goal Stop-hook leash never held these sessions: an API-error turn end routes to StopFailure, not Stop, and the leash lives on Stop. (Payload shape beyond the common fields is undocumented; probe.)
- **The session-limit modal cannot be suppressed, pre-answered, or dismissed by any setting, flag, env var, or hook.** Hooks cannot answer UI prompts. Auto-resume at limit reset does not exist natively. The modal is a hard blocker in unattended operation; this plan routes around it rather than fighting it.
- **`CLAUDE_CODE_RETRY_WATCHDOG=1` exempts any 429 from the retry budget, the session limit included.** The gate is `status === 429` with no session-limit exclusion, and the delay comes from the response's own `anthropic-ratelimit-unified-reset` header, capped at six hours, falling back to exponential backoff capped at five minutes. Section 1 proved this against a fake API serving identical 429s: without the variable the run exhausted retries and died in 187 seconds with `error: "rate_limit"`; with it the run was still retrying past ten minutes on a doubling backoff. **This corrects the plan's own starting premise** that the watchdog covers transient errors but not the session-limit class. It is the mechanism this plan now leans on rather than a neighbouring concern, and the watcher sets it on the child it launches. Whether it changes the interactive modal behavior at the five-hour limit remains unknown and rides in Operator Verification, now as a decision rather than an observation.
- **The StopFailure payload on this install** (Section 1 read the schema out of the shipped binary and confirmed it against captured payloads): the common hook fields plus `error`, a closed enum of `authentication_failed`, `oauth_org_not_allowed`, `billing_error`, `rate_limit`, `overloaded`, `invalid_request`, `model_not_found`, `server_error`, `unknown`, `max_output_tokens`; `error_details`, an optional raw API error string; and `last_assistant_message`, the optional user-facing error text. **No structured rate-limit state reaches the hook.** The reference repo's `rate_limit_state`, `five_hour_resets_at`, and `cached_at` do not exist in this build, so the watcher gets no machine-readable reset timestamp and its timing rule cannot depend on one. The logger stays shape-agnostic anyway, since the enum and the optional fields are undocumented and can change.

Kit facts:

- `.kit/goal-state.json` records the armed plan and the leash-bound session id (`kit-goal-lib.js` owns it). The kit-goal leash binds one session; re-arming is the documented recovery when a bound session dies, and the claim signal is the `/kit-goal` invocation's command arguments in the transcript, never CLI stdout (per `skills/kit-goal/SKILL.md`).
- The plan doc plus Chapters is the handoff state; a resumed session re-grounds from it via the existing SessionStart recovery. Nothing in this plan invents a parallel notebook.

## Goal

When an unattended, kit-goal-armed run dies on a retryable API failure (the session limit above all), the failure is recorded durably the moment it happens, and a watcher on the machine resumes the run after the limit resets, re-arms the leash, and continues the plan, so an overnight limit hit costs the reset wait instead of stranding until the operator reaches a console. Failures the kit cannot retry (auth, billing, invalid request) are recorded and left alone. Every piece fails toward "do nothing and leave the record", never toward acting on bad data.

## Approach

**Split policy from observation: a dumb logger hook, a deciding watcher.** The `StopFailure` hook cannot know whether resuming is safe, and its payload shape is not fully documented, so the hook records and nothing else. The watcher, running outside any session, owns every decision: retryability, timing, scoping, and the resume itself.

**The logger.** A new hook `plugins/claude-kit/hooks/stop-failure-log.js`, wired in `hooks.json` under `StopFailure`: it reads stdin, appends one JSON line (full payload plus an ISO timestamp) to `.kit/stop-failure-events.jsonl`, and atomically writes the same record to `.kit/stop-failure-latest.json` (tmp-plus-rename, the `kit-compact-lib.js` pattern). Fail-open on every path: any error exits 0 silently; no payload content ever reaches stderr (untrusted data, same posture as the compact gate). The hook does not classify, does not read the goal state, and does not act.

**The watcher.** `plugins/claude-kit/scripts/stop-failure-watcher.ps1` (PowerShell, per house default), designed to run as a Windows scheduled task and equally runnable by hand. Each pass:

1. Read `.kit/stop-failure-latest.json`. Absent or unparseable: exit quietly.
2. Scope guard: `.kit/goal-state.json` must hold an armed plan whose `boundSession` matches the marker's `session_id` (opaque case-insensitive compare, the `sameSessionId` convention). No match: exit, leaving the record. This is the deliberate v1 scope: only leashed unattended runs auto-resume. An interactive session that dies on an API error is the operator's to resume, and this guard is also the main fork-risk mitigation, since the stranded-console case is precisely the armed-run case.
3. Retryability: the marker's error classification must be in the configured retryable set (default `rate_limit`, `overloaded`; `server_error` off by default since the retry watchdog owns transient retries in-session). Not retryable, or unclassifiable: exit, leaving the record.
4. Due-ness, not wake-time arithmetic. The watcher computes no reset instant and reads no reset field, because none exists in the payload and the resumed client can read the true one for itself. A pass acts when `now >= marker.timestamp + SettleDelaySeconds` (default 120, so a still-settling failure is not raced) and `now >= lastLaunch + RetrySpacingSeconds` (default 1,200). Not yet due: exit; the next scheduled pass re-checks. The waiting itself belongs to the resumed child, per step 6.
5. Incident budget, not an attempt count. A sibling `.kit/stop-failure-attempts.json` holds `{ sessionId, firstSeen, launches, lastLaunch }`, **keyed by the marker's `session_id`**, which is the stable incident key: `--resume` preserves the session id, so a resumed run that re-dies of the same limit writes a fresh but indistinguishable marker, and a per-marker counter would reset on every death and never bind. Stop when `launches >= 6` or `now > firstSeen + 8h`, appending an exhausted note to the events log and leaving the incident alone thereafter. Clear the record when a child exits 0 or ran longer than 30 minutes, that runtime being the evidence it got past the limit.
6. Resume: validate the session id against a strict grammar (hex, dashes, bounded length; refuse anything else outright, since the marker is user-writable and this value reaches a command line) and run `claude -p --resume <session_id> "<resume prompt>"` from the project directory. The resume prompt is fixed text shipped in the repo, never composed from marker content. It **opens with the literal `/kit-goal <plan path>`** (the plan path read from the goal state and validated through `normalizePlanArg`), then states that the session was resumed by the stop-failure watcher after a retryable failure and is to continue executing per the plan doc. Section 1 confirmed the two harness behaviors this rests on: `--resume` continues the same session id and transcript, and a slash command in a `-p` prompt genuinely executes and writes the user-typed command markup the leash claims on, so the arming both re-binds the leash to the resumed session and holds it past a single turn.

   **The child does the waiting, and the watcher sets it up to.** The watcher puts `CLAUDE_CODE_RETRY_WATCHDOG=1` explicitly in the child's environment rather than inheriting and hoping. With it set, a 429 (which a session limit is) no longer counts against the retry budget, and the client sleeps to the reset instant it reads off the response's own `anthropic-ratelimit-unified-reset` header, capped at six hours, falling back to exponential backoff capped at five minutes when the header is absent or stale. That is why step 4 computes nothing: the exact reset time reaches the child for free and reaches the hook not at all. The child is bounded at 25,200 seconds (seven hours, above the six-hour native cap plus margin); on timeout its process tree is killed, recorded, and counted as a launch, so a weekly-limit incident cannot park a `claude` for days.
7. Record: write `.kit/stop-failure-resumed.json` **before the child starts**, carrying `{ launchedAt, pid, oldSessionId, state: "in-flight" }`, and update it with the exit code when the child ends. The sentinel exists to keep an operator from forking the run, so it must exist for the whole window in which a fork is possible: written at wake time it would be absent during exactly the hours an operator is most likely to reach the console and continue the dead session by hand. A pass that finds an in-flight sentinel whose pid is still alive exits without acting, which is what keeps two scheduled passes from launching two children. Append to the events log. Clear the latest-marker only when the resume invocation exited 0; on a nonzero exit, leave the marker so the next due pass retries within the incident budget.

**The doctor owns installation.** A new `plugins/claude-kit/doctor/install-stop-failure-watcher.ps1` (one installer per repair, the house convention) registers the scheduled task behind an explicit `-Fix` consent, and the doctor's check mode reports the task's presence and the watcher script's reachability (INFO when absent; installing is opt-in, since only unattended machines want it). The task interval is the watcher's fallback granularity; default 15 minutes. The registration pins `MultipleInstances = IgnoreNew` and `ExecutionTimeLimit = PT8H` explicitly rather than taking Task Scheduler's defaults, because the parked-child design depends on both: a second pass must not start beside a running one, and the task must be allowed to outlive a long wait.

**The fork risk, mitigated and then named.** The dangerous sequence: the watcher resumes headlessly while the dead session's console still shows the modal, and the operator later answers the modal, producing two continuations sharing one worktree. Mitigations in order: the scope guard (only armed runs resume, and re-arming rebinds the leash to the resumed session, so the old console session is no longer leashed even if continued); the `.kit/stop-failure-resumed.json` sentinel; and the operational rule, which ships in the watcher's header comment and the security model: **before answering a stale limit modal on a console, check `.kit/stop-failure-resumed.json`; if the incident was resumed, exit that console session instead of continuing it.** The residual (an operator continuing anyway) is accepted and documented; nothing mechanical can stop a human at a console.

**What Section 1 must settle before the watcher is finalized.** Whether `claude -p --resume <id>` continues the same session id or forks a new one (affects how re-arming binds and how a repeat failure of the resumed run is tracked); whether a `/kit-goal` slash command inside a `-p` prompt executes as a command (if not, the resume prompt instructs the session to run the arm CLI and the leash claim rides on the next real `/kit-goal`, or the prompt is adjusted to whatever the probe shows works); and the real StopFailure payload of this install. The Approach is amendable on those results, delta flagged in the Chapter.

## Operator Verification

- The end-to-end that no session can force: on the next genuine session-limit hit on an armed run, the events log holds the real payload, the watcher resumes after the reset, the resumed session re-arms and the plan progresses. ### Chapter 1: Section 1, the probe (2026-08-16)

**Every part of Section 1 confirmed, and two of them overturned a premise the plan was built on.** Probe artifacts are under the session scratchpad at `scratchpad/probe/` (a `--settings` file registering dump-to-file hooks, per the `probe-scripts-scratchpad-and-controls` pattern), run from a scratch cwd so the repo's own armed leash could not be disturbed. Every probe carried a known-answer control.

**(a) StopFailure fires, and Stop does not.** Control: a successful cheap turn fired `SessionStart` and `Stop`. Forcing an API error with `--model claude-not-a-real-model-99` fired `SessionStart` and `StopFailure` and **no `Stop`**. That is the plan's central premise confirmed by direct observation rather than by inference: the kit-goal leash lives on `Stop`, so an API-error death slips it silently. Kill-or-confirm criterion: confirmed, on Claude Code 2.1.233, node v24.19.0.

**(b) The payload, read from the schema rather than guessed from samples.** Two live captures plus the schema extracted verbatim from the shipped `claude.exe` bundle, which is the stronger evidence because it enumerates fields no forced error happens to populate:

```
{ hook_event_name: "StopFailure", error: <enum>, error_details?: string, last_assistant_message?: string }
```

on top of the common fields. `error` is a **closed 10-value enum**: `authentication_failed`, `oauth_org_not_allowed`, `billing_error`, `rate_limit`, `overloaded`, `invalid_request`, `model_not_found`, `server_error`, `unknown`, `max_output_tokens`. `error_details` is documented in the bundle as the raw API error message, preserving detail the user-facing text discards.

**The reference repo's `rate_limit_state` does not exist on this install.** Zero occurrences of `rate_limit_state`, `five_hour_resets_at`, `cached_at`-shaped rate-limit fields, or their camelCase variants, against controls where every real payload field hits (`last_assistant_message` 9, `model_not_found` 20, `hook_event_name` 14, `rate_limit` 111, `resets_at` 11). The binary does carry `resets_at`, but inside the `/usage` display subsystem that reads `anthropic-ratelimit-unified-*` response headers; that data is never plumbed into a hook payload. **No machine-readable reset timestamp reaches the watcher**, which kills the first clause of the Approach's watcher step 4 and is the one finding that changed a design rather than confirming it. Ruling and amendment in Chapter 2.

Two observed classifications: the invalid model gave `model_not_found`; a dead `ANTHROPIC_BASE_URL` gave `server_error` after 181 seconds of internal retrying. That second one **retroactively justifies holding `server_error` out of the default retryable set**: a persistent network fault classifies as `server_error`, and resuming on it would burn the attempt cap against a fault no resume can fix. Field presence also varies between captures (`effort` rode on one payload and not the other), so the shape-agnostic logger is load-bearing, not defensive habit.

**(c) Resume semantics, and a refuted finding.** `claude -p --resume <id> "<prompt>"` **continues the same session id**, writes to the same transcript file, and fires `SessionStart` with `source: "resume"` (cache-read of the prior turn's 38,489 tokens confirms it genuinely continued rather than replaying). Since the leash binds on session id, a resumed run is still the bound session.

The slash-command half **refuted the finding this plan's `## Related` section was built on**. `claude-kit_interactive-compact-deferral_spec_v1.md` Chapter 1 recorded that a slash command in `claude -p` does not execute. It does. Fresh session and `--resume` alike, the command expands, runs, and writes ordinary user-typed `<command-name>` markup: a probe of `/kit-goal status` loaded the kit-goal skill, ran the CLI, and reported "No kit goal armed."

The old probe's own evidence line contains its refutation. It quoted the transcript reading `C:/Program Files/Git/goal clear` and treated that as the harness receiving prose. It is Git Bash's MSYS path conversion rewriting a leading-slash argument before `claude` ever sees it. The probe never sent a slash command; its silence measured the shell. I reproduced the contamination exactly (my own first Bash-tool attempt produced `C:/Program Files/Git/kit-goal status`), then got real markup from PowerShell. **A probe that concludes from an absence must first prove the stimulus arrived.** The archived deferral plan's bullet is corrected in place, the operator memory rewritten, and the trap logged to `kit.probes.headless-slash-commands`.

**(d) A plugin-registered StopFailure fires**, tested directly rather than assumed equivalent to `--settings`: a scratch plugin loaded via `--plugin-dir` with `Stop` and `StopFailure` blocks fired `Stop` on the control and `StopFailure` on the forced error. No equivalence assumption is carried into Section 2.

**Bonus, and the single most valuable result: the whole recovery mechanism works headlessly, end to end.** Probing whether the leash survives into `-p`, I ran `claude -p "/kit-goal docs/plans/probe_spec_v1.md"` against a throwaway plan in a scratch project. So the resume prompt does not merely restart a session, it restarts a *supervised* one, and Section 3's prompt should open with the literal `/kit-goal <plan path>` rather than instructing the arm CLI in prose.

### Chapter 2: Section 2, the logger, and the timing ruling (2026-08-16)

**Section 2 shipped, and a consult rewrote Section 3's timing rule before it was built.** Two threads ran in parallel: the logger went to an opus-tier implementer while a fresh-context consultant ruled on the timing gap Chapter 1 opened.

**The logger.** `plugins/claude-kit/hooks/stop-failure-log.js`, wired under `StopFailure` in `hooks.json`, with 18 tests in `test/stop-failure-log.test.js`. Behavior is exactly the Approach's: the parsed payload re-serialized plus `recordedAt` (applied last, so a payload carrying that field cannot displace the real timestamp), appended to `.kit/stop-failure-events.jsonl` and atomically replacing `.kit/stop-failure-latest.json` via pid-suffixed tmp plus rename. The two writes are independent, so one failing does not skip the other. Nothing reaches stdout or stderr at all, which is how the sanitize-before-output convention is met for a hook whose payload strings come from an API error message. Exit 0 unconditionally.

Gate re-run by me rather than taken on report: `./build.ps1` (69 files, manifest restamped), then `node --test "test/*.test.js"` giving **809 tests, 807 pass, 2 fail**, against the 791/789/2 baseline. Delta is exactly +18, and the two failures are the same standing `memq-shim` exceptions. The implementer earned its green with a red/green probe (removing the cap check and the unlink-on-failed-rename turned exactly two tests red), restoring from pre-probe file copies rather than `git checkout`.

Three test additions worth naming because they close holes the brief did not ask for: a valid JSON **array** payload is treated as a length-only note, since a spread of one would have put raw content back into the record under numeric keys, which is the content leak by another route; an unknown future field is recorded verbatim, which pins the shape-agnosticism the whole split rests on and had no test; and a wiring test asserts the `hooks.json` block, since the hook is inert unwired and nothing else would catch a rewiring.

**The timing ruling, which overturned my framing.** I asked the consultant to choose between an escalating fixed backoff and best-effort parsing of the reset time out of the error text. It rejected both and the premise under them: **the watcher should compute no wake time at all.** The reset instant does reach a process that can act on it, just not the hook. With `CLAUDE_CODE_RETRY_WATCHDOG=1`, the client reads `anthropic-ratelimit-unified-reset` off the 429 itself and sleeps to that instant, capped at six hours, and a 429 stops counting against the retry budget. So the watcher launches promptly with the variable set on the child, and the child parks until the limit lifts. No parsing, no ladder, no guessing.

I verified the three load-bearing reads myself in the shipped binary rather than taking them: `h8b` reading the header, `xbp(e){return Lye(e)||e instanceof xs&&e.status===429}` (no session-limit exclusion), and `uYe(){return q.CLAUDE_CODE_RETRY_WATCHDOG}`. Anthropic's own remote runner sets the variable, which is a decent endorsement for unattended use.

**Then I tested the ruling's one medium-confidence claim instead of shipping on it,** since it was the mechanism the redesign rests on. A local fake API served identical 429s carrying a reset header, in both directions:

- **RED**, no watchdog: 11 message attempts over **187 seconds**, then `retry_exhausted` and a real `StopFailure` with `error: "rate_limit"`. That capture is itself the first genuine rate-limit payload this effort has, and it confirms the consultant's reading that the rate-limit branch carries no `error_details`.
- **GREEN**, watchdog set, same server and same 429s: still retrying at t+310s on a doubling backoff and alive past ten minutes, never exhausting.

The discriminator is clean because only the environment variable differed. Two honest limits: the GREEN run was killed by my own shell timeout rather than reaching the eventual 200, so what is confirmed is "does not exhaust", not "completes"; and because my fake reset instant had already passed by the second attempt, GREEN exercised the backoff fallback rather than the sleep-to-reset path. The header-read path is confirmed from the binary and **inferred** at runtime.

This also **corrects the plan's own Context bullet**, which said the watchdog covers transient errors but not the session-limit class. It covers any 429.

**A second defect the consult found, which I had not seen.** The attempt cap as specified could never bind. It was keyed per marker, and since `--resume` preserves the session id, a resumed run that re-dies of the same limit writes a fresh, indistinguishable marker that resets the counter. The failure mode was not the one I described (exhausting three attempts in an hour) but an unbounded relaunch loop. Fixed by keying the incident on `session_id` and bounding it with a wall-clock budget as well as a launch backstop.

**And a third, in the sentinel's timing.** The fork-risk sentinel was to be written when the resume fired. Under the old wake-time design that meant it stayed absent for the hours an operator is most likely to reach a console and continue the dead session by hand, so the one artifact meant to prevent a fork was missing during the whole window a fork was possible. It now goes down before the child starts, carrying `state: "in-flight"` and a pid, and doubles as the duplicate guard between scheduled passes.

**Approach amendments applied inline:** the `CLAUDE_CODE_RETRY_WATCHDOG` Context bullet (inverted), watcher steps 4 (due-ness only), 5 (incident budget keyed on session id), 6 (the watchdog set on the child, plus a seven-hour child lifetime bound), and 7 (sentinel before launch, in-flight duplicate guard); the installer paragraph (pinning `MultipleInstances` and `ExecutionTimeLimit` rather than inheriting Task Scheduler defaults); and Section 3's knob list and test list, the latter gaining three regression tests that pin exactly the defects above.

**Carried to Section 4 for the security reviewer:** the logger takes its output directory from the payload's own `cwd`, so "nothing is written outside `.kit/`" holds for a payload naming the project and not for one naming anything else. The trust boundary is the harness that writes the hook's stdin, and the sibling gate has the identical shape, so this is a note for review rather than a defect found. Also noted by the consultant and unverified by me: re-arming sets `boundSession: null` before rebinding, so a run dying inside that window fails the step-2 scope guard and is left for the operator.

**An operator decision, not a blocker,** carried to the close-out: setting `CLAUDE_CODE_RETRY_WATCHDOG=1` machine-wide on the ASR VM interacts with this plan, because an interactive session at the limit would then stall alive rather than die, no `StopFailure` fires, and this watcher never engages. The ruling works either way, since the watcher sets the variable on its own child regardless.

### Chapter 3: Section 3, the watcher, the installer, and the docs (2026-08-16)

**Shipped.** The code half went to a fable-tier implementer; the docs half stayed in the main thread per the routing rule, and was re-grounded against the as-built code rather than against the brief, which caught two places where my draft described an interface that did not end up being built.

**The watcher** (`plugins/claude-kit/scripts/stop-failure-watcher.ps1`) runs the Approach's amended steps as nine ordered guards, each failing to exit-0-without-acting. The security posture went further than the spec asked: rather than validating the session id and then interpolating it, **nothing reaches a command line at all.** The validated id and the fixed prompt travel to a constant wrapper through environment variables and the child receives per-element argv, so the class of defect where a hostile value escapes its quoting has no surface to occur on. That is the better answer, because a correct escape is a property you have to keep being right about and an absent command line is not.
