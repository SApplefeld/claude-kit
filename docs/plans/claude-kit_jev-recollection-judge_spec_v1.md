# Jev recollection judge: a calibrated judge over the fleet memory block, and the outcome keying that measures it

Status: In Progress
Commit Model: Branch-and-PR
Created: 2026-09-20

## Goal

The fleet memory block that session start and `memq recall` show is a recollection rather than a nearest-neighbour list. The memory database plan delivers that block as the ten records nearest by vector, unjudged, because the host judge cannot answer inside the block's two-second budget. This plan puts a fast calibrated judge (TypeSafe's Jev, a model that returns a probability per typed question and generates no text) between the vector shortlist and the block, asks it one question per candidate (would reading this record now change what the agent does next), and shows the records that clear a measured floor. The judge sees the composed situation text and each record's name, description and status, and nothing else; bodies never leave the LAN. Where the judge is unreachable or slow, or configured with no key, the block is the vector list it is today with one stand-down line, pinned both ways; where no config exists the judge never runs and no line prints. Every pointer the block shows carries a recognition id, and a `memq get` of that record inside the session writes an outcome row keyed to it, so the floor is set from this fleet's own hit rate rather than from a feel. When this is done, the two floors are the numbers section 1's battery produced on this fleet's store, `memq jev-calibration` is the query over the fleet's own hit rate that confirms or raises them, and a session that starts with a fleet block sees the records that bear on its recent work rather than the records whose vectors sit closest.

## Approach

**The judge and its wire.** Jev answers typed questions about a block of state with calibrated probabilities and generates no text. One request is `POST <endpoint>/v1/systemone` with `Authorization: Bearer <key>` and a JSON body `{ state, model, questions }`: `state` is the situation text, `model` is the name the config file gives, and `questions` is a map from an id of the caller's choosing to `{ type, instructions, criteria }`. The one type this plan uses is `noul`, a probability of yes, whose `criteria` are two sentences describing what true and false mean. The response carries `answers` keyed by the same ids, each a number in `[0, 1]`, and `usage.input_tokens`. Errors are `401`, `422`, `429` and `529`. Every question in one request is evaluated against the state in one pass and none sees another, so thirty candidates cost one round trip. The handoff doc under Related carries the vendor's documentation links and the full measured method.

**Measure before wiring.** Section 1 runs the brief's recognition harness against the live store's top-30 for a hand-labeled situation set with at least ten negatives, and records the boundary in its Chapter. The brief's 0.55 and 0.7 came from three negatives and a three-point separation, which directs the experiment and settles nothing. The operator reads the Chapter and sets the two floors before section 2 starts.

**The judge sits between the shortlist and the block.** The block's stage 1 is `usp_Search`, the procedure section 1 measures against, with the fetch limit raised from ten to thirty so the judge has headroom; ten is a display cap. Where the memory database plan delivers the block calling `usp_Nearest` instead, section 2 moves it to `usp_Search`, since `usp_Nearest` is live-only and the floors section 1 rules hold over a candidate set with the status mix `usp_Search` returns. The situation is what the block already composes: the project segment name and the three most recent action keys from the project's outcome journal. The composer skips journal rows that carry a recognition id, since those are this plan's own `read` and `unread` rows and a judge scoring them would be scoring its own output rather than the session's work. One `noul` question per candidate, all sharing the situation as state, carrying the record's title, its index-line description and its status inside the question. Status is what `usp_Search` returns and nothing more: `archived` where the procedure sets its archived key on the row, else `live`. The memory database plan's return-shape sentence for the procedure lists no such key, and the built procedure carries one (the project memory below records it); where the delivered procedure carries none, section 2 adds the archived key to its projection, the one change to `usp_Search` the Out of Scope list excepts. The procedure carries no superseded marker and this plan adds none, so superseded-ness is not read. The project memory `nearest-and-search-disagree-about-retired-rows` records that `usp_Search` serves archived rows with that key while `usp_Nearest` filters them in SQL and projects none, which is the second reason stage 1 is `usp_Search`. Status rides in the question because `usp_Search` ranks an archived record below a live one of the same distance (the memory database plan's section 4 states the multipliers); a fetch of thirty ordered that way can drop a live record from what the judge sees, and the judge weighing status itself is what keeps stage 1's ordering from deciding. Selection: the top-scoring candidate where its score is at or above the first floor, plus every further candidate at or above the second floor, ordered by judge score, capped at the block's line limit (five at session start, ten in `recall`). Where the top candidate is below the first floor the block prints one line saying no fleet record bears on the session's recent work and nothing else; that is a judged result, not a fallback. The two floors are named constants in the client module, set from section 1's Chapter.

**The fallback is the block as it is today.** The judge runs only where `~/.claude/kit-jev.json` exists, on the same terms the kit gives `kit-endpoint.json` and `kit-memory-db.json`; the key comes from `TYPESAFE_API_KEY` in the environment and is written to no file. A failed call, a `429` or `529` after one retry (200 ms later, and skipped where the retry could not return before the edge), or 1,500 ms elapsed of the block's 2,000 with no answer, falls back to the distance-ordered list with one stand-down line naming the judge as unavailable. The config file carries two fields, `endpoint` and `model`; the key is never in it. Silent fallback is the expensive failure and both directions are pinned with a fake client, on the same terms as the plan's fake database client.

**Every judged candidate is measurable.** The block appends what it judged to `jev-shown.json` under the project's `.kit/` scratch directory, resolved through `kit-compact-lib.js`'s `kitScratchDir` and never through `<cwd>/.kit` directly, since that resolver redirects a store-governed working directory and three readers picking differently would leave `get` reading a file the block never wrote. One entry per judged candidate, under the writing session's id. A hook process (the block at session start, the session-end hook) takes that id from the hook payload's `session_id`; a shell process (`memq recall`, `memq get`) takes it from `CLAUDE_CODE_SESSION_ID`, which the operator-tier record `claude-code-session-id-in-shell-env` and `docs/harness-assumptions.md` name as set in tool shells, equal to the transcript basename, and say nothing about in hook processes. That the payload's id and the shell's name one session is a belief `docs/harness-assumptions.md` gains in section 2, falsified by one session whose `memq get` finds no entry under its id after the block wrote one, and section 2's Chapter records the run that checked it. Each entry carries the record name, a recognition id, the judge's score, the candidate's stage-1 rank (its position in the thirty as `usp_Search` orders them, fused), whether the block showed it, the time, and a `marked` field that is null at the write. Where the shell carries no session id (an operator's `memq recall` from a terminal) the block judges and renders but writes no entry, since no hook would ever remove it. Entries append rather than replace, since the block runs at every session start (compaction included, per the hook's `startup|resume|compact` matcher), at every `memq recall`, and from every session sharing one checkout. A `memq get <name>` in that project reads the file, and where the name is listed unmarked under the caller's own session id it marks every unmarked entry of that name under that id (one name sits under one session several times, since the block appends at each start and each `recall`) and writes one outcome row keyed to the newest of them with its score, rank, shown flag and `read`, so a duplicate never becomes a false `unread` at session end; a peer session's entry for the same name is never marked, and a `get` from a shell with no session id writes nothing. A session-end hook reads the file, writes `unread` for every shown entry of its own session id still unmarked, removes its own session's entries, and deletes the file when none remain, so a miss is a row rather than an absence and a peer session's entries are never touched. That hook rides the harness's `SessionEnd` event, which `hooks.json` wires nowhere today; section 3 adds the entry. The kit's `Stop` entry is the wrong seam, since Stop fires at the end of every response turn rather than once per session, and an `unread` written there would mark every pointer after one turn. `read` and `unread` are the `pass` and `fail` results of one action key, `kit.jev.pointer`, with the record name as the summary, so the journal gains one key and no near-duplicate. Both writes take the route every `memq log` outcome takes under the memory database plan: the local `outcomes.jsonl` line is written as today, and the database write goes through `usp_AppendOutcomes` with the local spool on failure. So the local journal does hold rows carrying a recognition id, which is why the composer's skip rule above is real and not a no-op, and `memq recent` prints those rows as a group of their own, which section 3 builds, rather than interleaved with the session's `memq log` entries. The row carries four fields the journal has today in neither the file nor `mem.Outcome`: recognition id, score, vector rank and shown flag; section 3 adds them as nullable columns and widens the entry shape's pin. The bands are fixed: ten of width 0.1 over `[0, 1]`, a score landing in the band whose lower edge it is at or above. A query over the shown rows by band gives the hit rate per band, which is what a calibrated floor is. That query has one structural limit and the plan states it rather than hiding it: only shown pointers earn a `read` or `unread` row, and a pointer is shown only at or above a floor, so the live rows can confirm a floor or raise it and never lower it. Lowering a floor is a re-run of section 1's battery against the live store, which is why the harness stays in the tree. The stage-1 rank on every row is what makes the second comparison possible: over the same logged candidates, how often the record a session opened sat inside `usp_Search`'s top ten against how often it sat inside the judged block, with no live surface touched. Sections 2 and 3 land in one pull request, since section 2 alone appends to the shown file and only section 3's hook removes entries.

**Egress is named where the kit names it.** `docs/security-model.md` states what leaves the LAN (the composed situation text, and each candidate's title, description and status), to whom, and under what retention terms the vendor states, as a property of the surface in the present tense. The threat-model section, where the reviewer re-ranking plan has written it by then, lists the vendor as a party in consideration for the names and descriptions it holds and out of consideration for bodies, which it never receives.
