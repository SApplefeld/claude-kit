# Jev coverage check: a shared TypeSafe client, and a reading of which spec sections leave the most unstated

Status: In Progress
Commit Model: Branch-and-PR
Created: 2026-09-21

## Goal

A design session can ask TypeSafe's Jev model which sections of a new spec leave the most unstated, before the blind reader and the plan reviewer are spent on it. The answer is a ranking of the spec's sections, thinnest first, each with its weakest topics, and it is advice the author may act on or ignore. The kit gains one shared client for TypeSafe that keeps the API key out of every artifact and reports a call that could not be made as not checked, never as clean. The memory judge plan and the later code checks reuse that client instead of each writing their own. The curated docs state what this channel sends off the LAN.

## Intent

The operator's frame. He ran six rounds of experiments with a session on 2026-09-20 to learn whether Jev, a fast model that returns probabilities and no text, can help check the kit's work. The record is that Jev answers a precise question cheaply and repeatably and cannot invent the question. He agreed a shape that day: the tools are generic and the questions stay specific, the checks advise and never gate, and the work splits into two plans. This is the first plan, the client and the spec coverage check. The second plan is the code checks: a promise check and a fix-round regression check around review, and an implementer's self-check on prepared questions.

What done needs to do. Give a design session a ranking of its spec's sections by how much of a fixed topic list each one states, in a few seconds, at the spec self-review. Build the one TypeSafe client every Jev use in the kit shares. Keep the API key out of every log, result and error text. Say not checked, with the reason, whenever the call could not be made. State the egress in the security model.

What done does not need to do. It does not block, fail or gate a spec on any score. It does not print a finding, a pass, a fail or a threshold. It does not write or suggest spec text. It does not check code, which is the second plan's. It does not decide per project whether to send: the operator ruled that every project on a configured machine may send. It does not screen files for credentials, since it sends one plan document the author named and gathers nothing from a tree. That screen is the second plan's.

Alternatives refused. Waiting for the memory judge plan to build the client: refused by the operator on 2026-09-21, since that plan is parked behind the memory database work and the client depends on none of it. Each plan writing its own client: refused by the operator the same day, as two key-handling surfaces to keep safe instead of one. A per-project allow list in the machine config: recommended by the design session and refused by the operator on 2026-09-21, who ruled that every project may send information to TypeSafe. A threshold that marks a section as thin: refused on the experiments, where no single threshold held across question types. Reporting each low topic as a gap: refused on the experiments, where the per-topic forecast ran near a coin flip and only the per-section reading was strong. Extending the existing endpoint library with a bearer key: refused by the design session, since that library serves four callers on a stated contract that it redacts nothing and no test of it looks for a leaked secret.

Rulings made after the spec shipped: none at the write.

## Approach

**Two modules and one data file.** `jev-client.js` is the transport and nothing else. `kit-jev-check.js` is the command a skill runs, and `spec` is its first verb, so the second plan adds verbs to it and adds no second command. `jev-coverage-topics.json` holds the questions, because the experiments showed the questions are where the value sits and they will be tuned without touching code.

**The line between the client and its callers.** The client owns the wire shape, the config read, the key read, the closed set of failure reasons and the guarantee about the key. A caller owns its own time limit, its retry count and any score it treats as meaningful. The memory judge needs an answer inside 1,500 milliseconds over thirty short questions. The coverage check can wait twenty seconds a section. One client serves both only if neither policy lives in it.

**The wire.** `POST <endpoint>/v1/systemone`, `Authorization: Bearer <key>`, a JSON body of `{ state, model, questions }`. `questions` is a map of question id to `{ type, instructions, criteria }`. A `noul` is the vendor's yes-or-no question type: its `criteria` is `{ true: <description>, false: <description> }` and its answer is the probability of yes. The response carries `answers` keyed by question id and `usage.input_tokens`, and a `noul` answer is a number from 0 to 1 at `answers[id].noul`. The vendor's errors are 401, 422, 429 and 529. This shape is reported from the handoff brief under Related and from the experiment scripts that ran against it, and section 1 confirms it against the vendor's published documentation, reached through the API contract link in that handoff brief's section 2, before it is pinned.

**Config and key.** `~/.claude/kit-jev.json` holds two fields, `endpoint` and `model`, and never the key. That is the file and the shape the memory judge plan already names, unchanged, so one hand-authored file serves every Jev use on the machine. The key is read from `TYPESAFE_API_KEY` at the moment of the call and is held in no module-level variable. The file's presence is the machine's only switch. The footing is the one `memq find`'s judged channel already stands on: the operator hand-authors the config file and sets the key on a machine, and that act is his yes for every send the machine then makes. No session asks again per run. The operator's ruling of 2026-09-21 under Intent, that every project may send, is what places this channel on that footing, and the security model states it so a reader of that document sees the switch and what it covers.

**Failure reads as not checked.** The client never throws and never returns an empty answer set as a success. It returns either the answers or one reason from a closed set. The pattern is the one `plugins/claude-kit/scripts/kit-endpoint-lib.js` already uses for the local model endpoint: a described refusal for each way the config can be unusable, named reasons for each way the call can fail, and no use of a runtime error's own message, since that message can spell the request URL and its headers back out.

**The key travels only over TLS.** The client refuses an `endpoint` that is not `https`, with one exception: a loopback host, which is what the tests' stand-in server and a local Jev-shaped server are. Loopback is `localhost`, `127.0.0.0/8` and `::1`, and nothing else. A private-range address is another machine on the network and is refused in cleartext, and an IPv4 octet written with a leading zero is refused, since the dialer reads it as octal. `kit-endpoint-lib.js` exports `hostIsLocal`, which admits the private ranges for its own purpose and is therefore not this test. A typo in the config file therefore cannot send the key in cleartext across the network.

**What one request carries.** The coverage tool sends one request per section. The request body admits three things, and the set is closed at these three: the text of that one section, from its `### N.` heading line to the line before the next heading, as the whole of `state`, which is exactly `{ spec: <text> }`; the model name from the config; and one question per topic, keyed `c_<topic id>`, carrying the type, the instructions built from the topic's text and the two fixed criteria. A topic's `family` value is used for the local means and is never sent. A section ends at the next line outside a code fence that opens with `## ` or `### `, so a `####` heading stays inside its section, a fenced `### N.` line starts nothing, and the document's header lines and the `## Sections of Work` heading sit outside every section. The request therefore never carries the plan's file path, the repository's name, the plan's other sections or its title, any memory record, or any environment value.

**The reading.** Each topic is asked as "Does the specification in `spec` explicitly state <topic>?", a `noul` with the two criteria the experiment used. A section's score is the mean over all 28 topics, and the two family means are printed beside it. Sections print thinnest first, each with its three lowest topics. Nothing is compared to a threshold. The author reads the thinnest sections again with those topics in mind and decides whether the text owes anything. A low score is a pointer to re-read, never a finding.

**Where it runs.** In the brainstorming skill's spec self-review, after the author's inline pass and before the blind read. It costs a few seconds and no dispatch, so a thin section is cheapest to fix there, before two fable reviews read it.

**The sweep.** One Explore scout at sonnet read trunk `32017b73` through `git grep origin/main` and the installed plugin copy, under a tree-state bracket that compared identical before and after. It searched for statements of what leaves the machine, for the three recap line keys `blind read:`, `gating litmus:` and `plan review:`, for `kit-[a-z]+\.json` and the environment overrides account, for enumerations of `plugins/claude-kit/scripts/`, for every Jev and TypeSafe name, and for any hook rule on outbound calls. The surfaces it found, with where this plan places them:

## Sections of Work

### 1. The shared TypeSafe client

Model: fable

Write `plugins/claude-kit/scripts/jev-client.js`, a zero-dependency CommonJS module with no command-line entry. It is the first module in the kit that carries a secret, which sets the tier.

Acceptance:

- Before the wire shape is pinned, the implementer reads the vendor's published API documentation for `/v1/systemone` and confirms the request body, the `noul` answer field, the `usage.input_tokens` field and the four error statuses. A difference from the Approach is followed in the code and recorded in the Chapter as drift. Where the documentation cannot be reached, the Approach's shape is built and the Chapter records the confirmation as not made.
- The module exports one config read and one call. The config read returns the endpoint and model, or a described refusal whose reason is one of `absent`, `unreadable`, `malformed`, `invalid`, the same four `kit-endpoint-lib.js` returns. `invalid` covers a missing or empty field, an endpoint that does not parse as a URL, and an endpoint that is neither `https` nor on a loopback host.
- The call takes the state, the questions, a required time limit in milliseconds and an optional retry policy, which is a list of delays in milliseconds whose length is the retry count. It performs the config read itself and takes the endpoint and the model from it, so a caller passes neither. The config path is `~/.claude/kit-jev.json` under `os.homedir()`, and no parameter, flag or environment variable relocates it, since a relocatable config is a way for a repository's own environment to name the host the key is sent to. Tests redirect the home directory. The config read is decided first and the key second, so a machine with neither reads `not configured`. The time limit is one deadline over the whole call, retries and their delays included. A retry that could not start before the deadline is skipped and the reason is `busy`. A deadline that passes with a request in flight is `timeout`. The request follows no redirect, so a 3xx is `refused`. It returns the answers with the input token count, or a refusal carrying one reason. The reasons are a closed list of eight: `not configured`, `config unusable`, `no key`, `timeout`, `unreachable`, `refused`, `busy`, `unusable answer`. The config read's `absent` is `not configured`, and its other three reasons are `config unusable`. Every outcome of a sent request has exactly one reason. A failure to connect, resolve the host or complete TLS is `unreachable`. The time limit passing is `timeout`. A 429 or 529 is retried under the caller's policy and is `busy` when the policy is spent, and no other outcome is retried. Every other status outside the 200s, the 401 and 422 included, is `refused`. A missing time limit is a programming error and the one case that throws.
- The call never throws on any network, parse or config failure, and never resolves a failure as an empty answer set. A response is read field by field: a body that is not JSON, an `answers` that is not an object, or a question id that was asked and is absent from `answers` is `unusable answer`. So is a `noul` question whose answer carries no number from 0 to 1 at `answers[id].noul`, which keeps a caller from averaging a value that is not a score. The response body is read to a cap of 256 KiB and a longer one is `unusable answer`.
- The key is read from `TYPESAFE_API_KEY` inside the call and stored in no module-level variable. An unset or empty variable is `no key`, decided before any socket opens. No returned object, thrown error or written line contains the key or any part of it, and no refusal text is built from a runtime error's own message.
- The memory judge's needs are met without the judge's policy: a caller can pass a 1,500 millisecond limit and one retry at 200 milliseconds, and the module holds no score floor, no fetch limit and no default time limit.
- `kit-endpoint-lib.js` is unchanged. The implementer may import a helper it already exports.

Files in scope: `plugins/claude-kit/scripts/jev-client.js` (new), `test/jev-client.test.js` (new), `test/size-budget.json`.

Tests: lock the key's absence from every artifact a call can produce, with a planted recognizable key as the control, across the success path and every refusal path, a malformed endpoint included, since that is the path where a runtime error spells the request back out. Lock that each of the eight reasons is reachable and that a failure never resolves as answers. Lock the cleartext refusal both ways: a plain `http` endpoint on a public name and one on a private-range address each open no socket, and a loopback one does. Lock that a redirect is not followed. Lock the single deadline: a call whose retry delay would pass it makes no second request. Lock that a retry happens only on 429 and 529 and only as many times as the caller asked. Tests run against a local stand-in server and make no call off the machine.

References: `plugins/claude-kit/scripts/kit-endpoint-lib.js` for the refusal and reason shapes and the rule against a runtime error's message; `docs/plans/claude-kit_jev-recollection_handoff_v1.md` for the reported wire contract.

### 2. The coverage tool

Model: opus

Write `plugins/claude-kit/scripts/kit-jev-check.js` with one verb, `spec <path>`, and the topic file it reads.

Acceptance:

- `plugins/claude-kit/scripts/jev-coverage-topics.json` holds 28 topics, each with an id, a family of `code` or `prose`, and its text. The shipped file holds exactly the 14 code topics and 14 prose topics of the experiment script, verbatim from the block under References, and a test pins each of the 28 by its id, its family and its text, so tuning the list is a deliberate edit to the file and its pin together. At run time the tool asks every well-formed topic the file holds and does not count them. A topic file that is unreadable, empty, or carries an entry missing one of the three fields is a usage refusal that sends nothing.
- `node <plugin-root>/scripts/kit-jev-check.js spec <path>` reads the file at the path, which must end in `.md` and carry a `## Sections of Work` heading with at least one `### N.` section under it, on the header shapes the curating-docs skill's machine contract states. Anything else is a usage refusal that sends nothing.
- It sends one request per section, in order, through section 1's client, with a 20 second time limit and two retries at 1 and 4 seconds. Each request's body is exactly what the Approach's closed set admits. A section whose text passes 60,000 characters is not sent, and the run is not checked with the tool's own reason `section too long`, the one reason the line can carry that is not the client's.
- The run is all or nothing. Where every section answered, it prints a header naming the model and the total input tokens, then one block per section, thinnest first: the section's number and title, its mean over all 28 topics, its code mean, its prose mean, and its three lowest topics with their values. Every mean and value prints to two decimal places. Ties keep document order. It ends with the one line the brainstorming skill records, `jev coverage: <n> sections, thinnest <N> at <mean>`, and one fixed sentence saying a low score is a pointer to re-read and never a finding. It prints no threshold, no pass and no fail.
- Section lengths and the topic file are checked before the first request. The run stops at the first refusal, sends nothing further, and prints that refusal's reason. The tool's closing line has three forms and no others: the checked form above, the not-checked form and the not-configured form. Where any request was refused, it prints no ranking and no partial result. It prints `jev coverage: not checked (<reason>)` with the client's reason, and for a machine with no config file, `jev coverage: not configured`.
- The exit status is 0 for a checked run, 2 for not checked or not configured, and 1 for a usage refusal. The tool writes no file and keeps no state, so a re-run is a fresh reading.

Files in scope: `plugins/claude-kit/scripts/kit-jev-check.js` (new), `plugins/claude-kit/scripts/jev-coverage-topics.json` (new), `test/kit-jev-check.test.js` (new), `test/size-budget.json`.

Tests: lock the request body against the plan file it was built from, proving that the section's own text rides and that the path, the title and a neighbouring section's text do not, with a marker string planted in each as the control. Lock all-or-nothing: a run whose second of three sections is refused prints no ranking. Lock the three exit statuses and the two not-checked lines. Lock the ordering on a stand-in server that returns fixed scores. Lock the shipped topic file against the 28 ids, families and texts under References, carried in the test as its own literals, so a paraphrased question fails.

References: the topic texts, verbatim from the experiment script. Code family: `dep_throws` "what must happen when something this code calls (a helper, a host function, a callback) throws or rejects"; `invalid_input` "what must happen when this code is given invalid, malformed or unexpected input"; `error_vs_no` "how an error from a dependency is told apart from a legitimate negative or empty answer"; `partial_failure` "what state must be left behind when an operation fails partway through"; `memory_vs_disk` "how in-memory state must relate to what was actually written or sent, when the write or send fails"; `size_limits` "a limit on the size or length of values that come from outside (files, responses, user text)"; `outside_shape` "that values received from outside must be checked field by field before use"; `secrets` "how secrets or credentials must be kept out of logs, results and error text"; `concurrency` "what must happen when two operations run at the same time"; `timeouts` "a time limit or deadline, and what happens when it passes"; `who_calls` "which code must call each exported helper or guard, so that none is left unused"; `closed_sets` "every closed list of allowed values, and what happens to a value outside the list"; `test_failure_paths` "that failure paths, and not only the happy path, must have tests"; `rollback` "how to turn the feature off or return to the old behaviour". Prose family: `p_terms` "a definition of each new term it introduces, precise enough to decide a borderline case"; `p_boundary` "at least one worked borderline example showing which side of a new rule a near-miss case falls on"; `p_owner` "which single document owns each new rule, and that every other mention points at it or copies it whole"; `p_copies` "how two copies of the same text are kept identical (a pin, a build step or a test)"; `p_old_text` "which existing sentences elsewhere contradict the new rule and must be changed or removed"; `p_executable` "for each new instruction, how the person following it can observe the condition that triggers it"; `p_conflict` "how the new rule ranks against an existing rule it could collide with"; `p_existing_items` "what happens to existing items (tests, documents, records) that do not meet the new rule"; `p_acceptance_observable` "acceptance points that a third party could check as true or false without judgment"; `p_pointers` "that every file, section or name the new text refers to exists, and how that is checked"; `p_comment_truth` "that comments and headers touched by the change must describe what the code actually does"; `p_scope_files` "the exact list of files each section may change"; `p_total_rule` "for each new rule with several outcomes, that every possible case gets exactly one outcome, with none left unassigned and none given two"; `p_test_instrument` "for each test or check the change adds or edits, what it must select and what it must not select, and the control that proves it". The question wording is "Does the specification in `spec` explicitly state <text>?" with criteria true "Yes, the text states this explicitly." and false "No, the text is silent on this or only implies it."
