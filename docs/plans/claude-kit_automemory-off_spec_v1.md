## Goal

The kit memory store works at full strength whatever state Claude Code's auto-memory feature is in. Today the kit delegates two read-side jobs to the harness: injecting the project `MEMORY.md` index into session context at start, and (by consequence) letting `memq recall` print project-tier records as bare names because "the descriptions are already in context." Both jobs go dark silently when auto-memory is off, and no session is ever told where the kit's memory files belong. When this plan is done the kit carries both jobs itself, unconditionally: the SessionStart memory hook emits the project index and the write destination under the same sanitization discipline it already applies to the type-tier index, and `memq recall` always carries project-tier descriptions. The operator can then run memory purely through the kit's deliberate write bar, decay lifecycle, and reinforcement stamps, with no surface that depends on a harness setting.

## Approach

**The kit does its own job unconditionally; it does not detect the harness.** This is the decision the whole design turns on, and it replaces an earlier one. The plan originally specified a predicate that read the harness's auto-memory state so the kit could emit the index only when the harness was not already injecting it. That predicate was built and abandoned; Chapter 1 has the full account. The short version: the harness decides auto-memory through a private, undocumented, minified function that consults five environment signals and merges five settings tiers, several of which no out-of-process reader can observe. Two review rounds each matched one more layer and each found another underneath, and what the chase produced was a mirror of private code that can drift on any Claude Code release with no signal.

The cost of not detecting is that when auto-memory is on, the session sees the project index twice, once from the harness and once from the kit. It is the same index of the same directory, so the duplication is redundant rather than contradictory, and it costs on the order of a few hundred tokens. The two copies are not textually identical: the harness injects the file verbatim while the kit's copy is reduced to bounded printable ASCII and capped, so a line carrying non-ASCII or running past the line cap reads differently in the two. That is a rendering difference over identical records, and the kit's copy is the reduced one by design, because store content crossing into trusted context is fenced here whether or not the harness fences its own. That is a much smaller price than a permanent coupling to harness internals, and it buys a property the detection design never had: the kit behaves identically no matter what the harness is doing, so nothing here can be silently broken by an upstream change.

**The hook emits per a stated matrix.** `memory-session.js` already runs four independent blocks (decay nudge, type index, run-scoped destination, pinned destination) plus a stand-down state. The new project-index block slots into that structure, ungated:

| Session state | What the new block emits |
|---|---|
| Stand-down (unusable pin, or unusable run id) | Nothing. The stand-down is the whole of what the hook says; a session told to write no memory needs no index or destination. |
| Run-scoped (usable run id) | Nothing. The run block already names the pending destination and prohibits `MEMORY.md` edits; a directed worker reads the store through `memq recall`/`get`, which S2 makes description-complete. Emitting an index plus ordinary-write guidance would dilute the run block's prohibitions. |
| Pinned (usable pin, no run) | Index only. The pin block already names the destination and says `MEMORY.md` is the ordinary index; the new block adds the pinned directory's index lines, which the harness never injects for a pinned store in any auto-memory state. |
| Ordinary session | The full block: the project index lines, the memory directory named verbatim as the write destination, and the standing instruction (file-per-fact memory files written with the Write tool, an index line added to `MEMORY.md` per file, in the kit's established format). |

The destination and the convention instruction are the part that earns its place regardless of the harness: they are what holds a session to the kit's write bar, and nothing in the harness ever states them.

**The emission takes the type-index treatment, verbatim precedent.** The project index is store content crossing the data-to-model boundary, so every emitted line passes `memq.sanitize` (bounded printable ASCII), the line count is capped with a counted remainder, the block names its lines as data rather than instructions, and the file read is a fixed-size prefix (`INDEX_READ_CAP`) so a grown index cannot make session start pay for its size. New cap `PROJECT_INDEX_MAX_LINES = 60` (the type index caps at 30; the project index is the session's primary tier and the operator's current index runs about 20 lines, so 60 gives headroom). Line cap reuses `INDEX_LINE_CAP = 200`. The destination path takes the pinned-destination treatment exactly: emitted verbatim on its own indented line framed as data, or not at all when `emittable()` fails, in which case the block states that the directory cannot be named faithfully and directs the session to reach the store through `memq`, whose commands resolve it without needing the path in context. An absent or empty `MEMORY.md` still emits the block in the ordinary-session case, with the emptiness stated as fact ("no index yet"): a fresh project store is when the destination matters most.

**`recall` always carries project-tier descriptions.** `cmdRecall` today carries them only under a store pin, because without one "the descriptions are already in session context" via the harness injection. That premise is exactly the harness dependence this plan removes, so the condition goes away rather than gaining a third branch: project lines always carry their descriptions, and the coverage line drops the "already in session context" claim. Budget, cut order, and every other recall behavior are unchanged; the added characters compete for the same budget like every other line, under the same announced-truncation discipline.

**Rollout sequencing (operator-facing, drives nothing in the sections).** The plugin cache is a snapshot: a repo edit reaches no live session until the kit is rebuilt, released, and updated on each machine. Because nothing here is gated on a harness setting, the order no longer matters. The operator can turn auto-memory off whenever they like; before the kit update lands they run today's degraded-but-not-broken state, and after it lands the kit carries both jobs itself.

## Out of Scope

- **Detecting the harness's auto-memory state.** Deliberately abandoned; see the Approach and Chapter 1. Not a limitation to be closed later, a design choice: the kit is independent of the setting rather than reactive to it.
- **The two-writers problem, which is the real cost of auto-memory being on.** Confirmed against the harness bundle: when auto-memory is enabled, Claude Code runs its own extraction agent (a separate model call, `querySource: "extract_memories"`, up to 5 turns) that reads the conversation and writes memory files into the same directory the kit curates, on its own bar, with none of the kit's frontmatter, index, decay, or applied-stamp discipline. It skips a run in which the conversation already wrote to memory files, so a session using the kit's bar suppresses it for that run, but a read-only session is still extracted from. Turning auto-memory off resolves it outright, which is what the operator is doing. Recorded here and in memory (`auto-memory-writes-its-own`) so a future effort can pick it up; no work in this plan.
- **The `autoMemoryDirectory` setting.** If the operator ever points auto-memory at a custom path, memq's cwd-derived resolution and this plan's emissions both target the derived directory, not the custom one. That divergence exists today for every memq surface and is not widened here.
- **`find`, `get`, `recent`, decay, tags, the type tier, the journal.** None of them lean on the injection; nothing changes.
- **Three pre-existing conditions the S1 review surfaced, each recorded rather than fixed here.** A stand-down block currently coexists with the decay nudge and the type index, so a session can be told to write no memory files and, in the same context, to record one with `memq add-type`; the `storePinUnusable` branch already emits alone and is the shape a fix would take. The hook re-emits every block on a `resume` SessionStart, accumulating copies in a transcript that already carries the earlier ones. And `fs.openSync` follows symlinks, so a symlink at a tier's index would stream another readable file's first prefix into context, reduced and capped; exploiting it needs write access to a directory inside the user's home, and an `lstat` regular-file check would close it at the cost of refusing a legitimately symlinked store. All three predate this plan and none is widened by it beyond the third now sitting on a more frequent path.

## Standing Brief Amendments

Folded into every dispatch brief from here on.

- **Every claim about harness behavior is verified against the installed bundle, never against documentation.** Claude Code ships as a single large executable at `~/.local/share/claude/versions/<version>` (a file, not a directory), and it is greppable: `grep -ao '<pattern>' <version>` over the minified source is the authority on what the harness actually does. The documentation is a summary and is demonstrably incomplete, which is how the abandoned detector's first round shipped an environment-variable rule that matched the docs and not the code. Two independent reviewers converged on the same finding class, "the code claims a fidelity to the harness it does not have", so this is the generator rather than one defect: any section asserting what the harness does states the bundle evidence for it, or states that it is inferred and unverified. Grep patterns must avoid `\{n,m\}` interval syntax, which collides with brace matching in the shell available here; a bare `.` run or a bounded character class works.

- **Do not reintroduce a harness-state check.** The Approach's first decision is load-bearing and was reached the expensive way. A section that finds itself wanting to know whether auto-memory is on has misread the design: the answer is to do the kit's job unconditionally and accept the redundancy. Escalate rather than adding a predicate.
