# Reviewer re-ranking: two review tiers, a threat-model-bound security lens and a performance lens

Status: In Progress
Commit Model: Branch-and-PR
Created: 2026-09-20

## Goal

The kit's review loop runs four code lenses in two tiers. The correctness tier is the adversarial reviewer and the blind reviewer, and its findings drive the fix round, the provenance read, the design stop and the round backstop exactly as today. The advisory tier is a new performance reviewer and the security reviewer. An advisory finding never carries an automatic route: it is weighed by the orchestrator against the project's own stated requirements and recorded with a written disposition (fix now, defer, or refuse, each with its reason), it never opens a review round on its own, and it never counts toward the design stop or the round backstop. The security lens reads a per-project threat model before it reviews, and only a Critical that cites an entry in that model, confirmed by the scope adjudicator, blocks a close. The security lens keeps one duty at full weight: a security document or a security-boundary comment that states something the code does not do is reported with the contradicting code cited. When this is done, a section on a shell or hook surface closes on the same terms as any other section, and the fourteen review-round backstop declarations logged to the memq outcome journal under the key `kit.review.cap` (one entry per declaration, read with `memq get kit.review.cap`) stop being generated by a lens whose every Major was fixed before anyone weighed it.

## Intent

The frame, in the operator's words on 2026-09-19: "I think security is important, I set too high of a bar and too much emphasis on it. We need to be advised of risks relative to the uses of the code base we're working on, and they need to be weighed not just blindly assumed to be of critical or major importance. I honestly think the majority of its findings have slowed us more than they've helped us, though it certainly has been essential at several points." And: "Security documents are not critical. They help shape and document the code base, they feed forward to other models looking at it, but they aren't really consumed by anyone in the sense that they are essential. That said, it's a best practice for them to be accurate, and real, so I support maintaining them." Where security is critical is outside this codebase: customer-facing APIs, Azure architecture, SQL designs, permission modeling. So the bar is per project, and the kit's own is the low-stakes end.

What done needs to do. Rank the four code lenses adversarial, blind, performance, security. Make performance and security advisory: their findings are weighed and dispositioned, never auto-routed. Add a performance lens broad enough to catch deadlocks, cross-process waits, loop shape and timing, API timing and process-spawn cost, not only query shape. Bind the security lens to a written threat model per project. Keep a security Critical that is real for this project and its deployment blocking, confirmed by an adjudicator rather than assumed.

What done does not need to do. It does not remove the security lens, cheapen its model, or stop it running at finishing. It does not make the adversarial or blind lens advisory. It does not build a single adjudicator seat that runs all four lenses and rules on every finding; the operator chose two tiers over that shape. It does not change how the prose reviewer or the blind reader work. It does not write threat models for other projects; each project writes its own under the shape this plan defines, and the kit's charter says what the lens does where one is absent.

Alternatives refused. One adjudicator over all four lenses, deciding each finding's value: refused, because it puts a judge dispatch on every finding, where the two-tier shape spends the judge only where the orchestrator leans to fix. Widening the design stop so a kit-required guard counts as a named mechanism: refused under the operator's 2026-09-19 ruling; the stop stays and the fast lane that let security fixes bypass it goes. Keeping the security lens's fix-before-close route for a Critical with no threat-model citation: refused, since an unciteable Critical is exactly the class the operator named as overengineering.

Rulings made after the spec shipped: 2026-09-20, a project with no threat model keeps its security Criticals behind the relevance ruling, read as cited, with its Majors advisory (widens what is asked for: the blocking route survives on a project that has written no model).

## Approach

**Tier is keyed on the lens, never on the finding.** Today's carve-outs key on the finding ("a security finding of Critical or Major weight whichever lens raised it"), which is what lets a security-shaped finding from any lens bypass the design stop, the round backstop and the out-of-scope route. Under this plan a finding's route is its lens's. An adversarial finding about an injection is a correctness finding, rated on that charter's own ladder (wrong behavior against the spec) and routed on its provenance like any other. A security-lens finding about the same line is advisory. The two lenses may report one defect twice; the orchestrator dispositions the advisory copy as covered by the correctness one. This is the single rule every deletion below follows.

**Advisory disposition.** Every Critical and Major an advisory lens returns gets one line in the section's advisory list, `.kit/scratch/<plan-slug>/advisory-section-<n>.md`, kept as the Minor list is. The line carries the finding as printed and one of three dispositions with its reason: fix now, defer (the backlog entry it went to), or refuse (why it does not apply to this project). A fix-now fix joins the same fix round the correctness findings open. Where none is open, a fix whose delta would meet the fix-delta bar opens a fix round of its own before the terminal condition is read, never the Minor close pass, which forbids owing a round; a fix below the bar joins the close pass. A fix-now lean on an advisory Critical or Major takes one relevance ruling from the scope adjudicator before the fix is written: does this finding apply to this project's stated requirements and deployment. That is the operator's ask that a fix not be taken on the lens's word alone. A refuse or a defer of a Major, or of an uncited Critical, needs no judge. A cited security Critical takes the ruling whatever the orchestrator's lean, since the citation is a claim the lens makes about this project and the judge is what confirms or refuses it (the next paragraph). The ruling is the scope adjudicator's relevance shape, a third question shape section 3 adds to its charter beside the single-finding and design-stop shapes, because the charter's existing mandate rules on the goal path from the plan's text alone and a threat model is in none of its inputs. The relevance brief carries the finding verbatim, the plan's `## Goal` and `## Intent` record, and one thing more by lens: for a security finding its `threat:` field and the project's `## Threat model` section or the line `threat model: absent`; for a performance finding the requirement the finding names (quoted from the plan or stated as assumed, per the performance charter) and the acceptance bullet it quotes where it quotes one. Nothing else rides. It returns one of three buckets: `CONFIRM` (for security, the cited entry, or with the model absent the deployment the Intent record and the Goal state, admits the attacker class and the asset the finding needs; for performance, the Goal, the Intent record or the quoted acceptance bullet states the requirement the finding measures against; in both, the admitting sentence quoted), `REFUSE` (it does not, with the excluding sentence quoted), or `ASK` (the sentences pull both ways, or none can be quoted for either other bucket, `ASK` being this shape's residual since no bucket on this shape rests on an absence). The orchestrator adopts the ruling rather than re-deriving it, and checks on its own surface that the ruling's `GROUNDS` names a positive ground rather than a bare absence, as the design-stop paragraph checks a bucket's. A fix-now advisory fix takes the add-decision line and the design stop like any correctness Major, because the two judges ask different questions: the relevance ruling asks whether the finding applies to this project, and the design stop asks whether the mechanism the fix adds traces to a Goal clause. A relevance ruling that confirms a finding says nothing about whether a guard no clause names is the right fix for it, and letting the first ruling stand in for the second is the bypass the fast lane was. A fix round its delta owes counts toward the round backstop as every fix round does, because opening it was the orchestrator's act rather than the finding's, which is what "never opens a round on its own" bounds. The honesty duty has one narrower route: a security-lens finding that a security document or security-boundary comment states something the code does not do takes fix now, or a Chapter line naming the sentence and why the finding does not hold, and never defer, since a false sentence left standing is what the doctrine's nothing-untrue-ships rule names as a defect. The Chapter's `Metrics:` line carries the advisory tally, `advisory: <n> findings, <f> fixed, <d> deferred, <r> refused`, beside the provenance tokens it already carries, which count correctness findings only. An advisory finding of Minor weight joins the Minor list as today. Every section that edits a file `test/size-budget.json` budgets re-syncs that file's row in the same section.

**What the deletions are.** The security fast lane is five sentences and their copies: the provenance carve-out (executing-work step 4, "The carve-out governs ahead of all of this"), the design-stop exemption ("A Critical, and any security finding, takes no line at all"), the round backstop's second frozen class ("Two classes never freeze"), the out-of-scope route's second carve-out ("neither does a security Major"), and the fix-delta bar's third trigger (the security surface list). Each is replaced by its correctness-only reading: a Critical from a correctness lens is still fixed before close or raised, still takes no add-decision line, still never freezes, still never takes the out-of-scope route. The claim-class region's first exception (a claim on a security boundary held to a behavior finding's bar) is deleted, because a false security claim is now the security lens's honesty duty and rates as an advisory finding; the second exception (a published contract surface) stands. That region binds the two correctness lenses only, the charters that carry its copies; a security-lens finding on any surface, a published contract included, is advisory by lens. The security-reviewer charter's "Your Criticals and Majors are fixed before the section closes or raised to the operator" goes with them.

**The one blocking case.** The security lens may rate a finding Critical only by citing an entry in the project's threat model: the attacker class, the asset and the deployment the model names, in the finding's own line as `threat: <entry>`. A Critical carrying no citation is read as an advisory Major. Every cited Critical takes the relevance ruling above, on whatever lean the orchestrator holds, and where the adjudicator confirms the citation it is fixed before the section closes or raised to the operator, the one route this plan keeps from the old fast lane. Where the adjudicator refuses, the finding is dispositioned refuse on the judge's ground. So the orchestrator alone can never wave off a cited Critical: the judge sees every one. The judge's third bucket, ask, holds nothing here: on a Major or an uncited Critical it dispositions the finding defer with the judge's recommendation as the backlog entry's reason, and on a cited Critical it takes the blocking case's raise branch, an item under the plan's `## Operator Verification` rather than a BLOCKED hold.

**The threat model.** A `## Threat model` section in the project's `docs/security-model.md`, in a fixed shape the security-reviewer charter states: the deployment (where the code runs and who can reach it), the assets (what is protected and from whom), the attacker classes in consideration, and the attacker classes out of consideration with the reason. The kit's own, written by this plan: the operator's own machines, a Windows desktop and the virtual machines on its home network, under the several-principal deployment `## Principals` states, since the payload is shared with other team members and one person operates it under three accounts; the assets are the operator's working trees, memory store and credentials on disk; in consideration is an untrusted input reaching a hook, a guard or a permission grant through a tool call, a fetched page or a peer message; out of consideration is any party who already holds the machine account, this kit checkout or the operator's accounts, since that party holds the code and has no use for an inference attack on what the code protects; a repository a session merely opens stays in consideration, since the security model prices a cloned repository as a configuration channel. Where a project's `docs/security-model.md` carries no such section, the lens runs its full checklist and opens its report with `threat model: absent`. Its Majors are advisory as everywhere. Its Criticals carry `threat: absent` in the field, and that value alone is read as a citation, so every one takes the relevance ruling, where the judge reads relevance against the plan's Goal and the deployment its Intent record states in place of the missing model, and a confirmed one blocks exactly as a cited one does. The finishing pass carries "write the threat model" to the operator under `## Operator Verification`'s route. So a project that has written no model keeps its blocking Criticals behind the judge rather than losing them, and writing the model is what narrows the lens to the attacker classes the project actually faces. The operator decided this on 2026-09-20. The non-convergence rule the operator tier of the memory store holds (record `non-converging-review-rounds-mean-no-standard-exists`, read with `memq get <slug> --operator`; a lens with no written standard invents a new case each round) is why the model is a precondition for a Critical rather than a nicety.

**The performance lens.** A new `performance-reviewer` agent, read-only, advisory. Its charter is broad on purpose: throughput and latency on the path the change touches, process spawn count and cost, per-call work on a hot path (a hook that runs on every tool call, a loop over the tree, a query in a loop), locks and deadlocks, waits across processes and their bounds, loop shape and termination, timing assumptions against an API or a clock, resource lifetime, and whether the shape scales to the requirements the plan states as future. It is bound to a written bar by the same rule as the security lens: each Critical or Major names the requirement it measures against, quoted from the plan's Goal, an acceptance bullet, or a project doc, or states the requirement it assumes in one sentence. That assumed requirement is exactly what the orchestrator weighs. A finding with no measurement, count or complexity as evidence, or that names no requirement, rates Minor. It runs per section on a trigger list stated in executing-work beside the security trigger (the section's delta spawns a process, runs on a per-tool-call path, walks the tree, holds a lock, waits on another process, or queries a store), and always at finishing.

**Dispatch and effort.** The advisory lenses ride round 1's roster where their triggers hold, and a re-raised round, which runs at round 1's roster, carries them on the same triggers; a decayed one-lens round never does, as the security lens joins none today. Both carry frontmatter effort `medium` and the model rule's tier; the effort table gains the performance row beside the security row. Where any lens in a round goes through Workflow, every lens in that round goes in one `agent()` wave, so the orchestrator reads the round together. At finishing both advisory lenses run over the whole changeset; the all-prose waiver applies to both. The `Disclosure:` sweep stays with the security lens, and a `Disclosure:` hit is the one Critical that blocks without a threat-model citation and without the judge, its list being the plan's own statement of what must not appear.

## Standing Brief Amendments

Every sighted reviewer dispatch carries these entries verbatim on its `Amendments in effect:` line.

- The preamble's combined-pass allowance in `finishing-work/SKILL.md` states three things and no more: which two lenses fold into one adversarial dispatch, what a folded pass prints and how those printed lines route, and the compensation row naming the performance reviewer. It states nothing about which surface licenses the fold, nothing about the adversarial charter's delegation of the advisory deep passes, and nothing a folded dispatch's brief must say. Section 2's acceptance bullet 4 is that form. Where the adversarial charter and a folded brief conflict over an advisory lens's deep pass, the charter is the surface that changes, and section 3 is where it changes.
- An edit to a sentence stating a rule is not complete until every sibling surface stating that same rule has been enumerated and re-read. The siblings are the other question shapes the same charter defines, the output fields that report the rule's result, the tests that list the rule's cases, and the ledger keys and reasons carrying the rule's passages. Enumerate them from the file's own structure before the edit rather than from the lines a finding cited, because a finding cites where the rule broke rather than everywhere it is stated. A scoping clause added to one shape's rule is the highest-risk form, since it retracts the rule on every shape it does not name. The mirror case is owed the same enumeration and is easier to miss, because nothing was edited to trigger a re-read: a sentence newly written to restate a rule that already exists elsewhere is enumerated against that rule's owning surface before it ships, and a restatement written onto several surfaces at once is checked once per surface, since each can drop a different qualifier the owner carries.
