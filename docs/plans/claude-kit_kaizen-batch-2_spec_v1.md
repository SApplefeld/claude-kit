### 2. The plan doc's live copy
Model: fable

The doc half of the asymmetry. The goal state gains an optional `executionTree` field: an absolute path recorded when the checkpoint CLI, invoked with a cwd that resolves (per section 1) to the project root, observes that its literal cwd differs from that root. The checkpoint CLI is this section's sole writer of the field, deliberately: chapter boundaries are where a worktree run already calls it, and one boundary-timed writer beats several racing ones; other goal-family CLIs only read it. Plan-doc readers that render or report section progress, today the statusline's Sections segment, prefer `<executionTree>/<plan path>` when the field is set, that tree exists, and it holds the plan path; otherwise they fall back to the project root's copy exactly as today. The field is display-trust only: nothing gate-deciding or leash-deciding reads it, and the code states that where the field is written. Lifetime: the field dies with the state file where a clear deletes the file, and any code path that rewrites state to change the current plan (the Stop hook's queue advance, or an arm that replaces the goal in `kit-goal.js`) drops it explicitly, so a stale tree path cannot outlive the plan it described.
Tests: red-first both directions; the risk is the widget lying about which doc it counted and a stale path silently redirecting a reader. At minimum: with `executionTree` set to a fixture worktree holding a further-along copy of the plan doc, the statusline counts that copy's sections (red on today's code); with the field naming a missing tree or a tree lacking the plan path, the reader falls back to the project root's copy; clearing or advancing the goal drops the field; no gate or Stop-hook decision changes with the field present (guard direction).
Acceptance: statusline over a fixture reproducing the AI-OS shape (main checkout with a stale doc copy, worktree branch with the live one, `executionTree` recorded) renders the live counts; suite matches baseline plus new tests; build stamp refreshed.
Files in scope: `plugins/claude-kit/hooks/kit-goal-lib.js`, `plugins/claude-kit/hooks/kit-compact-checkpoint.js`, `plugins/claude-kit/hooks/kit-goal-stop.js` (drop-on-advance), `plugins/claude-kit/hooks/kit-goal.js` (drop-on-replace, and only if its clear path rewrites rather than deletes the state file), `plugins/claude-kit/scripts/kit-goal-statusline.js`, matching tests.

### 3. Queue position that survives a missed advance
Model: opus

Root-cause first: find the writer that should have advanced `queueIndex` past a completed plan and why it did not fire for the live defect state described in the Approach (the disrupted b448e80 close-out is the candidate trigger, but confirm from the code what the advance path actually is before changing it). Then make position reporting self-healing rather than trusting the stored index: the session-start advisory and `kit-goal.js status` treat a queue entry as complete when its plan doc's Status reads Complete or the doc has moved to `docs/archive/` with no copy left in `docs/plans/`, and report position as the first entry that is neither; an entry absent from both `docs/plans/` and `docs/archive/` is reported as unresolvable, never silently skipped. ### 4. The prose lessons land on their owning surfaces
Model: fable

Five amendments, each on the surface that owns the behavior, per the writing-skills skill, with reviewers briefed to read each amended file whole:

- **(a) The channel-guard case joins the doctrine's single-source clause.** `home/claude-kit-doctrine.md`, the "Make the test earn its green" bullet's single-source sentence gains the guard case: a sanitising or clamping guard is a property of the output channel, not of the producer that first needed it, so the moment a channel gains a second producer the guard moves to the shared boundary as an exported helper, because an unexported fix is one the next author reimplements by not implementing it. The doctrine has a byte-identical twin: `test/doctrine-parity.test.js` holds `home/claude-kit-doctrine.md` identical to the `operating-instructions` skill body, so this amendment lands in both hand-edited copies, exactly as the first kaizen batch's six amendments did.
- **(b) The second-producer tell joins two reviewer charters.** `plugins/claude-kit/agents/adversarial-reviewer.md` and `plugins/claude-kit/agents/security-reviewer.md` gain the cheap check: does this change create a new path to a surface some other file already guards, and is that guard reachable from here?
- **(c) The anchor-growth guard joins the handoff protocol.** `plugins/claude-kit/skills/peer-sessions/SKILL.md`'s anchor paragraph gains the guard: sender-names-the-anchor never grows into sender-names-the-line-ranges, because a line coordinate is computed on a tree the receiver does not have; the receiver re-derives positions from its own tree at each boundary, and that check staying one fetch cheap is what keeps it run.
- **(d) The merge-side counted-claim rules.** `plugins/claude-kit/skills/finishing-work/SKILL.md` gains the timing rule: a counted claim about a concurrently-worked document is re-read after the last merge, never before it, because integration is itself a writer, so a close-out that verifies counts and then integrates has verified nothing. `plugins/claude-kit/agents/docs-curator.md`'s counted-claim sweep gains the superlative pass: every only-sentence ("X is the only Y") on a swept surface is re-checked, because any merge adding a second member falsifies it silently.
- **(e) Gate numbers ride with their tree state.** `plugins/claude-kit/skills/executing-work/SKILL.md`'s gate-delta reporting rule gains: a reported gate number is a fact about the tree it was measured on, so it rides with that tree's state (clean worktree at sha X, or main checkout with N foreign dirty files), which is what lets a downstream reader reconcile two honest counts that disagree.

Heading pins: `test/doctrine-parity.test.js` pins specific headings in `peer-sessions/SKILL.md` and, since the coordinator effort, in `coordinator/SKILL.md` (fourteen tests at last report, and the set grows). None of the amendments above rewords a heading; keep it that way, check the pin set before any heading-adjacent edit, and expect it to have grown again by execution time.

Acceptance: each amendment lands in its file's voice without duplicating an existing rule; `test/doctrine-parity.test.js` and `test/output-style-parity.test.js` pass because the hand-edited copies agree, never by editing either test: amendment (a) lands byte-identical in `home/claude-kit-doctrine.md` and `plugins/claude-kit/skills/operating-instructions/SKILL.md`, and it sits outside the register core the output-style test pins, so that test passes untouched; `node --test test/*.test.js` matches baseline.
