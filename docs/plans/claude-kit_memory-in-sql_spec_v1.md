## Goal

When this is done, the shared SQL Server database is where every memory record lives, and `memq` is the only way a session reads or writes one. A session saves a memory with one command that takes the name, the description, the tags and the body, refuses an existing name unless told to replace it, and lands the record in the database, or in a durable local queue when the host does not answer, which drains in order the next time it does. `memq get`, `find`, `recall`, `recent`, the session-start memory blocks and the recognition nudge read from the database, or from a small read-only snapshot this machine last took of it, with a visible line saying which. No hook ever waits on the database: session start reads the snapshot and refreshes it in the background, and the nudge reads the snapshot alone. A project's memories are keyed by what the project is, its git remote, with the folder path as the fallback, so the same repository on any machine reads and writes the same project memories, and a checkout can declare a space label that orders what it sees. Each machine's existing files are copied into the new shape by one publish that runs once, after which nothing writes a memory file and nothing but that publish reads one, with one carve-out: a record written inside an engine run keeps landing in the run's pending file directory, which the engine adjudicates by file. The markdown tiers, the git sync, the local index and the embedder stay on disk untouched for plan 2 to remove.

## Intent

The frame, in the operator's words of 2026-10-02. On what goes where: "SQL memory is the tool all the way down, excepting the local queue and small cache." On the outage case: "I'd be willing to lose memory retrieval during an outage, that's basically Fail Fast and Fail Loud, you'd notice quickly. However, what would be worse is being unable to save a memory during an outage." On the write door: "Consistency is key, and I like one tool being responsible for ALL our memory processes, it makes it easy if we want to hook into it or augment it in the future." On the project key: "Project memories SHOULD follow the project." On the client branches of the ASR-CLAUDE master repository, each with its own worktree and persona: memories "could conflate slightly", much overlaps and fixes are copied between clients, "so it's not a bad thing, just something that would be nice if there was slightly more guidance about that extra level of separation." On the git sync's other tenant: the coordinator board "is a scratch pad for active, current work ... I think we can stop syncing it entirely." On the local index: "I agree. Remove it. Let's move all memory into SQL." On future machines: a standalone VM gets "a local SQL Developer Instance on it so they can use the same pattern", so the database address and the embedding address stay two settings and a box with no embedding endpoint still works.

What done needs to do. The database holds the record. One command writes, with a replace flag guarding an existing name. A durable queue holds a write the host cannot take, and it drains in order. Reads come from the database, or from a snapshot with a visible line. Hooks never wait on the database. Project memories key on the git remote. A space label is carried and orders reads. The migration is one publish per machine, and the old files are not deleted. The documents that tell a session to write a memory file tell it the command instead.

What done does not need to do. It does not delete a memory file, the git repository under the kit's home, the local index or the embedder, or remove the doctor steps that check them, which is plan 2. It does not move the coordinator directory anywhere; it stays local and unsynced from plan 2 on. It does not move the run-scoped pending tier, whose promotion is the external engine's verdict applied by file. It does not change the persona plugin's own code. It does not add an approximate vector index or change the search ranking. It does not keep the old files and the database in step after the migration: the files are history from that run on.

Alternatives refused. No files at all, with retrieval lost in an outage: refused by the operator, since a save that cannot land is the worse failure, so the queue is the load-bearing part and the snapshot the bonus. Files as the working copy with the database as the carrier: refused, since two machines could still edit one record apart and the conflict handling would be rebuilt in SQL. A drop folder a hook ships to the database: refused, since Claude Code rewrites such files under the kit and two doors stay open. Project memories private to the writing machine: refused, since "picked up and run anywhere" means the project tier travels. Moving the coordinator directory into SQL: refused as a different domain, and then mooted by the operator's ruling that it stops syncing. Keeping the local index as the outage fallback: refused by the operator, since an outage should read as an outage.

Rulings after the spec shipped. Decided 2026-10-03 by the operator on the relay: the two new read procedures, `usp_GetRecord` and `usp_ListIndex`, write no `mem.QueryLog` row, since auditing every read is "a LOT of auditing growth" and the log has no retention, so it grows without bound. Decided 2026-10-03, ARCHITECT ruling on DEV-PLUGIN's ask: `usp_PutRecord` with `@p_Body` NULL on a name no live row holds writes nothing, touches no deleted row, records no stamp and returns `refused` with a null description, whatever `@p_Replace` reads, since a record is never born without a body and `memq anchor` and `memq triggers` edit an existing record; the null description is the client's signal for "no record of that name". Decided 2026-10-03, ARCHITECT ruling on DEV-PLUGIN's ask: `usp_Health`'s `sharedRecords` and `sharedEmbeddings` exclude fleet project stores and are disjoint from `fleetRecords` and `fleetEmbeddings`, since the doctor's shared count meant the shared tiers before this plan. Decided 2026-10-03, ARCHITECT ruling on DEV-PLUGIN's ask: the publish keys every project folder `path:<folder name>` and never recovers a directory, and `mem.usp_AdoptProjectStore` re-keys a `path:` store into the `remote:` key a session's working directory computes, since 26 of the 40 folders holding memory files on SCOTT-CLAUDE have no session log to recover a directory from and a key file would exist only for the current directory at the one publish that matters; the declared limits are that an unopened project stays under its `path:` key, the first refresh in a project reads the old snapshot until it finishes, and two repositories sharing one folder path share one `path:` key. **The record's shape in the database, schema version 7.** `mem.Store` gains `ProjectKey NVARCHAR(400) NULL`. A project store from this version on is fleet-wide: `SandboxId NULL`, `Tier 'project'`, `ProjectKey` set, `Segment NULL`, unique on `(Tier, ProjectKey)`. The old per-sandbox project stores stay as rows until section 2 moves their records and then carry no live record. `mem.Record` gains `Space NVARCHAR(100) NULL`, `Triggers NVARCHAR(MAX) NULL` and `Anchors NVARCHAR(MAX) NULL` as JSON arrays, `IsPinned BIT NOT NULL DEFAULT 0`, `CreatedOn DATE NULL` for the frontmatter's `created`, `Origin VARCHAR(10) NOT NULL DEFAULT 'file'` reading `file` for a published row and `memq` for a row `usp_PutRecord` wrote, and `WrittenBySandboxId INT NULL`; `Author` takes the `--author` value a verb carries and stays NULL otherwise. From this version `Body` holds the record's prose alone, the fields living in columns; `memq get` strips a leading frontmatter block from a version 6 row's `Body` no machine has republished yet, so a row is never served with its fields twice. `Visibility` keeps its column for the version 6 rows; `usp_PutRecord` writes `shared`, and `mem.udf_VisibleRecords` returns every undeleted row to every mapped sandbox and still no row to an unmapped one. Promotion, `usp_PromoteRecord`, moves a project record into the operator store rather than flipping its visibility, and stays curator-only. `usp_Search` gains `@p_ProjectKey` and keeps `@p_Segment` as an accepted parameter a version 6 client may still send, which maps to the old store so an un-updated machine's fleet block keeps answering; a search from a project scope ranks that project's rows and the shared tiers' rows, never another project's. `usp_UpsertRecords` likewise keeps taking a version 6 client's rows into the old per-sandbox stores. The new procedures, each in the `sql-style` skill's shape and granted to `mem_publisher`: `usp_PutRecord` takes tier, project key, space, name, description, body, tags, triggers, anchors, pinned, supersedes, author, `@p_Replace BIT` and `@p_StampId`. A stamp already applied wins over every other reading and returns `stored` with nothing written, so a queued replay never refuses. Otherwise, where the name exists in that store and `@p_Replace` is 0 it writes nothing and returns `refused` with the existing description; where it exists and the flag is 1 it overwrites, deleting the row's embeddings only where `@p_Body` is non-NULL, taking a NULL field as "keep" and a non-NULL one as the new value, so a verb that sends only anchors changes only anchors and `memq put --replace` sends every field, an empty array for none, and so clears; where it is absent it inserts. `usp_GetRecord` returns one row with its body by tier, project key and name. `usp_ListIndex` returns, for one project key and the two shared tiers, every live record's name, description, tags, triggers, anchors, pinned flag, space, supersedes, created, origin and the three usage aggregates recall prints today from `mem.Usage`: last read, last applied, distinct applied days. `usp_ArchiveRecord` sets `IsArchived` by tier, project key and name, and with `@p_Delete` sets `DeletedDt`. The client gains one constant, `RECORD_SCHEMA_VERSION = 7`, gating the four and the drain of the new row kinds; the drain of `usage` and `outcome` rows keeps its gate at 2. The installer upgrades a version 6 host in place, keeping every row, and `usp_Health` reports 7.

**The project key.** For a working directory inside a git checkout, the key is `remote:` followed by the origin remote's host and path, lower-cased, with the scheme, credentials, a trailing `.git` and a trailing slash removed, so `https://github.com/SApplefeld/claude-kit.git` and `git@github.com:SApplefeld/claude-kit` both read `remote:github.com/sapplefeld/claude-kit`. The URL is read from the main checkout's `.git/config` text, reached through `worktreeMainRoot` (`memq.js:1027`), with no git spawn. A checkout with no origin remote, and a folder that is no checkout, take `path:` followed by today's `sanitizeProjectPath` segment (`memq.js:829`), so a persona's own folder keeps its own memories. The key is computed where `projectSegment` is computed today and rides beside it, and the local `.kit/` files that today key on the segment keep doing so. A pinned store (`pinnedProjectSegment`) pins the key the same way. The snapshot's directory for a key is the first sixteen hex characters of the key's SHA-1; the shared tiers take the tier name alone.

**The space.** A checkout declares a space in `.kit/memory-space`, read from the nearest ancestor of the working directory that holds a `.git` entry, which in a linked worktree is the worktree itself and not the main checkout, so each client worktree declares its own. The file holds one label matching `^[a-z0-9][a-z0-9-]{0,39}$`, and `.kit/` is already gitignored. The environment variable `KIT_MEMORY_SPACE` wins over the file, for a persona declared at launch. A record written under a space carries it. A read under a space lists the project's own-space records first, then the project's unspaced records, then records from other spaces each marked `[space: <label>]`, and never hides any. A read under no space lists the project's records unmarked, which is today's behavior.

**The write door.** `memq put` writes a project record, `memq add-operator` an operator record and `memq add-type` a type record, as today, and each gains `--replace`. Each writes the record through `usp_PutRecord` within the client's existing budget, the four-second probe and the ten-second call, and where the host does not answer writes a `record` row to the queue and reports `queued` rather than `stored`; a save never fails for want of the host. Under the down marker below, a write queues at once with no probe. A write verb that reaches the host drains the queue before sending its own row, so a row queued in an outage never lands after a write made once the host returned. `memq forget` and the decay pass's archive step write through `usp_ArchiveRecord`, `memq anchor` and `memq triggers` through `usp_PutRecord` with the flag and only their own field, `memq touch` and the read stamp through `usp_AppendUsage` and `memq log` through `usp_AppendOutcomes`, each with the queue behind it. The queue keeps its one table and gains the kinds `record` and `archive`; the drain sends rows in `created_at, id` order. A transport failure stops the drain and leaves every row. ## Sections of Work

### 1. The database holds the record: schema version 7 and the four procedures

Model: opus

`mem.Store` and `mem.Record` take the columns above, the visibility function returns every undeleted row to a mapped sandbox, `usp_Search` takes `@p_ProjectKey` beside `@p_Segment`, `usp_PromoteRecord` moves a record into the operator store, and `usp_PutRecord`, `usp_GetRecord`, `usp_ListIndex` and `usp_ArchiveRecord` are written and granted to `mem_publisher`. The installer upgrades a version 6 database in place.

Acceptance:
- `Install-MemoryDatabase.ps1` run against the local instance holding a version 6 database, produced by the installer at e4712827, leaves it at version 7 with every pre-existing `mem.Record` and `mem.Embedding` row present, read by count before and after in the Chapter; run again, it changes nothing and exits 0.
- `usp_PutRecord` on an absent name inserts with `Origin` `memq` and returns `stored`; on an absent name with `@p_Body` NULL writes nothing, leaves any deleted row of that file key as it stands, and returns `refused` with a null description; on a present name with `@p_Replace = 0` writes nothing and returns `refused` with the existing description; with `@p_Replace = 1` and only `@p_Anchors` non-NULL changes anchors alone and leaves the `mem.Embedding` rows in place; with every field non-NULL overwrites them all and leaves no `mem.Embedding` row; a second call with the same `@p_StampId`, whatever its other arguments, writes nothing and returns `stored`.
- `usp_GetRecord` returns the body and every column for one name under one key, and no row for that name under another key.
- `usp_ListIndex` for one key returns that project's rows and the operator and type rows, none from another project key, and the three usage aggregates read from `mem.Usage`'s `read` and `applied` stamps.
- `udf_VisibleRecords` returns a project row of another sandbox's old store to a mapped sandbox and nothing to a NULL sandbox.
- `usp_Search` with `@p_ProjectKey` ranks only that key's rows and the shared tiers, pinned by a seeded pair of projects, and a call in the version 6 shape with `@p_Segment` still answers.
