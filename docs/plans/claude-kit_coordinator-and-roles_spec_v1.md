Any session holding this plan may arm and run it; the executor choice is deliberately open and the peer message delivering this plan carries a pointer, not the authority.

## Goal

Codify session roles as the mesh's coordination vocabulary and stand up the machine-coordinator seat as a skill. When this is done: the peer-sessions skill teaches roles as stewardship seams (an open set starting at coordinator, expert, worker, admin) with declaration, handshake, per-role etiquette defaults, and collision routing; a new `coordinator` skill carries the machine-wide seat's runbook (operator interface, cross-repo dependencies, machine-resource arbitration) on the standing-watch chassis with a committed ledger that survives session death; and the parked coordination-spine backlog item is consumed with this spec as its answer. The design source is `claude-kit_session-roles_notes_v1.md`, the banked four-pass dialogue; this spec turns its settled conclusions into shipped text and invents nothing beyond them.

## Approach

Execution shape: prose-only (no code sections, no new tests; the suite gate proves no collateral damage). The writing-skills skill governs every section; project memory `skill-amendments-collide-with-neighbours` applies; it lives in the machine-level memory store rather than this repo, and its operative lesson is restated here whole: skill amendments break in the seam with unchanged neighbouring text, so reviewers are briefed to read the amended file whole rather than the diff. The settled design (from the notes doc, restated here so sections build from this spec alone):

- **A role is a stewardship claim on a function-times-resource pair, for coordination, never a privilege.** Authority stays on the dispatch-authority rail; a role changes only mandate shape and etiquette defaults. Any session can name itself anything, so a claim confers nothing except legibility.
- **The starter seats and their exclusivity, an open set:** the **coordinator** stewards the seam between repos and toward the operator, one per machine, exclusive; the **expert** stewards a repo's knowledge and plan authorship (writes specs, sequences within-repo work, receives friction, answers warm consults), one seat per repo, exclusivity economic rather than safety-critical; the **worker** stewards mutation of one checkout, exclusive per tree, leashed, defers non-plan messages to boundaries and hands work requests up; the **admin** stewards machine state, one per machine, open mandate by the operator's sandbox-perimeter decision, restated here in full so sections need no other source: the installation runs sandboxed with disarmed access and a separate GitHub identity, so blast radius is bounded at that boundary by construction, and the operator ruled (2026-08-25) that the perimeter is the restriction, an open-ended admin on the strongest available model being deliberately unrestricted inside it because interior allowlisting would buy little safety and cost real capability, with two design lines that are not restrictions: every action reported to the operator thread, and support-not-work (fixes processes, permissions, services, workspaces; never produces or bypasses work product, because process integrity is inside-the-perimeter value the perimeter cannot protect).
- **Declaration in layers:** the session name advertises (`PROJECT: Role`, the token the shipped skill already uses at its Naming section, quoted exactly; ListAgents as the directory); the first-contact handshake confirms (the peer-sessions who-you-are line gains the role and scope claim); the coordinator's ledger is the durable registry. A claim on an exclusive seam that collides with a standing claim routes to the coordinator, or to the operator where the coordinator seat is empty or party to the collision; never assumed resolved by silence.
- **The coordinator's three functions and only those:** (1) operator interface: one voice toward the operator, status aggregation as a periodic status round (message each live session for a bounded status line, consolidate, relay; avoid the word fleet in the skill text, which this repo's memq machinery already uses for engine-spawned workers), escalation routing, decision asks batched with recommendations; (2) cross-repo dependency and portfolio sequencing: merge gates spanning plans, retrospective triggers, handoff brokering between repos; (3) machine-resource arbitration: the one-heavy-process budget, suite-slot contention, the shared-surface claims nobody stewards today. Oversight within a repo is explicitly not a coordinator function; the expert owns it.
- **The coordinator runs on the standing-watch chassis, with the overrides it states.** The chassis contributes the loop shape (`/loop`, a harness command rather than a repo artifact, or self-paced wakes), the runbook discipline, and the reconciliation posture: each pass re-derives the board from durable state (roster, plan docs and their Status headers, `~/.claude/kit-events.jsonl`, the kaizen inbox in the kit repo, its own ledger), messages as interrupts only, nothing load-bearing in loop context. The override, which the skill states explicitly with this reason rather than importing by pointer: standing-watch's ledger is gitignored under `.kit/` and rewritten in place because a watch's state dies with the watch by design, while the coordinator's ledger is the seat's survival and handoff mechanism and is therefore committed. It dispatches nothing directly: it writes specs and backlog entries, asks the operator to arm over a warranted channel, and hands artifact-authorized plans per dispatch-authority. The warranted channels are a closed list the skill names: the operator's keyboard in the session, the account-allowlisted relay thread, and an artifact-borne authorization per dispatch-authority; extensions are operator decisions recorded in the operator memory tier, never in the skill file, which is public, machine-agnostic and replaced at the next plugin update.
- **The ledger** is the seat's committed board in its home repo (`docs/coordinator-board.md` where the seat lives), classified as a living document in exactly `docs/backlog.md`'s class (the curated-library discipline routes transient artifacts to `.kit/`, but a living board is curated state, and the backlog is the shipped precedent for a frequently-updated committed doc under `docs/`; the docs-write-guard binds subagents, not the main session holding the seat): the roster with role claims, active efforts per repo with plan paths and anchors, pending handoffs with their protocol state (armed, `received-verified-holding-for-authority`, `received-authorized-deferred`), and, under active efforts, a pointer to any plan that carries its own authorization, naming the plan and nothing else; machine-resource claims (who holds the heavy-process slot, a suite slot, a shared surface); and open operator escalations with what each waits on. The board holds coordination state and never authority: nothing in it warrants an action, and a session needing an authorization goes to the artifact that carries it, because a board the seat itself writes cannot satisfy a trace back to the operator however it is worded. Nothing on the board is publishable without the operator's clearance, which rides the confirmation the seat already owes before its first write and names the board's categories, the sensitive values knowable at that moment (this machine's hostname, the repos live on it, and that plan filenames will appear), and the readership those reach; visibility sets what that ask names and never whether it happens, a private home repo narrowing readership to that repo's principals rather than bounding it. Afterward an entry rides when the clearance covers its subjects and its form is the pointer form, with two things stopping it: a repo or machine reaching the board for the first time, and a commitment the clearance does not cover or that will not take pointer form, sensitivity being the test there and fit only its common case, either riding as a contentless stub meanwhile. Before that clearance exists the seat has no board rather than a quieter one, since the confirmation precedes the first write, so it declines the commitments it could not record instead of improvising a store for them. Updated each pass; a successor session takes the seat by reading the ledger and announcing the takeover on the roster, which is the seat-handoff answer. This design is the coordination-spine backlog item's answer, generalized: any session holding cross-session commitments records them durably in its repo; the coordinator's ledger is the machine-wide instance.
