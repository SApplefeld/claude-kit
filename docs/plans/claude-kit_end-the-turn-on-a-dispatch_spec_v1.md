## Goal

When this plan is done, a session whose only remaining work is a background dispatch ends its turn on a `WAITING:` lead that names what it awaits, and the rule text that today tells it to hold the turn open in a `TaskOutput` loop says the opposite. The wedge reading that loop existed to take is taken at the wake instead: at the completion notification, at a timer wake where the session can arm one, and at the first re-block after either. The stop hook is unchanged, since it already allows this turn end without clearing the leash. Inbound messages, operator redirections and peer messages reach a waiting session because it is idle rather than inside a wait call, and a dispatch that never comes back is still caught: one window later than today where the session could arm a timer, and at the next session start where it could not. A dispatch carrying a model override follows the same rule as any other. The synchronous shape survives as the one in-turn option, for a short single dispatch where turn continuity is worth the wedge-blindness it costs.

## Approach

The problem is upstream of the hook. `plugins/claude-kit/hooks/kit-goal-stop.js` clause b2 allows a stop whose last assistant message leads with `WAITING:`, keeps the goal armed, emits no event, and re-enters enforcement at the first stop after the wake; `test/kit-goal-stop.test.js` pins that at seven sites (lines 315, 1761, 1782, 1796, 1813, 2314, 2635 at authoring). What keeps sessions in-turn for hours is executing-work's completion contract, which reads a background dispatch's turn end as a stop the hook blocks and tells the session to keep the turn alive with a blocking `TaskOutput` loop, yielding to `WAITING:` only once the dispatch is the only remaining work and its first-turn reading is resolved, and which tells a fan-out member or a SendMessage-resumed agent to be awaited in-turn for its whole run. Finishing-work's cadence paragraph then assumes that loop: it evaluates the wedge hallmark in the gaps between `TaskOutput` calls and sets the call's `timeout` so no window elapses whole inside one.

The design inverts the default and keeps the guard. Ending the turn is the ordinary wait shape. The harness re-invokes the session when a background Agent or Bash task completes, which `docs/harness-assumptions.md` already records as an assumption the charters rest on, and when a Workflow run completes, which the Workflow tool's own description states (the tool returns at once with a task id and a task notification arrives at completion) and which this plan's own authoring observed at its plan review; section 4 records that third case beside the first two. Two sentences outside executing-work's four wait passages tell a session to await a Workflow round in-turn, `executing-work/SKILL.md:400` ("a Workflow round is awaited in-turn per the completion contract's `TaskOutput` pattern") and `finishing-work/SKILL.md:32` ("Await the round in-turn as executing-work's completion contract awaits any Workflow round"), and sections 2 and 3 take them, since a review round through Workflow is the commonest dispatch a run makes and a rule that ended the turn on an Agent-tool dispatch and held it on a Workflow one would leave the executor holding two rules for one moment. What the in-turn loop bought was a cadence on which to take the wedge reading, and that cadence moves to the wake: the completion notification, a timer wake, and the first re-block after either are the three moments the hallmark is evaluated. The first-turn reading, which today gates the yield to `WAITING:`, is taken at the first wake at or after the first-turn window closes. The timer is named by class, not by tool, because the kit's rule stays harness-neutral: where a session has a means of waking itself on a timer, it arms one for the dispatch class's growth window before ending the turn; where it has none, the completion notification is the wake and a wedged dispatch surfaces at session start and to the doctor exactly as the hook's header already describes for a `WAITING:` that nothing re-invokes. The coordinator seat's four-hour reconciliation wake, stated at `plugins/claude-kit/skills/coordinator/SKILL.md:10` at authoring, is the precedent for a kit session arming its own timer. Windows themselves do not change; finishing-work still owns them.

Options weighed and declined, recorded so they are not re-litigated. Breaking the in-turn wait into shorter calls so messages land between them changes the granularity of the hold and not its shape: peer messages already land between tool calls, while the relay channel and the nudge pile-up key on the turn ending, the pile-up being the harness's own "the user hasn't heard from you in a while" prompts, which accumulate inside a long turn and each spend a model round to answer. Dropping the wait and trusting the harness alone is right about completion and wrong about the wedge, since a wedged agent never completes and nothing wakes the session. Moving liveness out of the session into a controller is where the operator's agent_persona work is heading and is deliberately left out; this plan makes the kit's rule compatible with that model by making the wake the reading point, and states nothing about who supplies the wake.
