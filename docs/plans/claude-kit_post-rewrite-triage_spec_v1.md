## Approach

The rewrite changes what the corpus says and where it says it, and every artifact written against the old corpus is now a claim about a document that may no longer exist in that form. Three kinds of rot follow, and the verdict set is built from them. A citation rots when it names a line, a heading, or a quoted sentence the rewrite moved or reworded, and the item is otherwise sound: that is `re-anchor`. A premise rots when the item asks for a rule the rewrite now states, or fixes friction the rewrite removed, or depends on a mechanism the rewrite retired: that is `retire`, and the verdict names the rewritten text that covers it. An item whose subject the rewrite never touched is judged on its own merits under its surface's ordinary bar, and is `keep` where it survives that. For a kaizen note that bar is the kaizen skill's pass, which asks whether the note names concrete kit friction that is still present and, where it does, whether the fix is applied now, promoted to a spec, routed to another surface or parked. For a backlog item it is the curating-docs skill's prune pass, which asks of an item past 90 days whether it is still actionable and answers promote, retire or keep. For a memory record it is the memory-system skill's four remedies, which route a record by what went wrong with it: delete for one that was never true, repair for one whose fact holds and whose body says it badly, supersede for one that was right and is stale now, and archive for one that merely aged out.

The judgment is a model reading each item whole, never a script scoring it. A script may list and count, and section 1 has one do exactly that, so that every later section's verdict count reconciles against a baseline the run measured rather than a figure it remembered. The inventory carries no self-check beyond the reconciliation its acceptance states. The doctrine asks a check that reports an absence to prove it can detect a presence, and that bar is for a silence someone acts on; the inventory's silences are acted on by nobody, because every item it lists is read whole by a judge and an item it missed is caught at the reconciliation, so proving them would be effort spent on a list a stronger reader re-reads anyway.

Each judge reads the kit's own routing first rather than the whole corpus. `plugins/claude-kit/skills/operating-instructions/references/ownership-map.md` names the owning document for every moment the kit governs, so a judge takes the item, names the moment or rule it turns on, finds the owner in the map, and reads that owner in the rewritten tree. Where the item quotes a sentence, the judge searches the rewritten corpus for that sentence's subject rather than its wording, since the rewrite changed wording by design. Where the item names a mechanism, the judge reads the mechanism's skill. The rationale ledgers under `plugins/claude-kit/skills/*/references/rationale-ledger.md` carry the why of every surviving claim and are read where a verdict turns on why a rule survived.

Verdicts are files, one per item, under `.kit/scratch/post-rewrite-triage/<surface>/`, each carrying the item's identifier, the verdict, the one-line reason, the document and heading checked, and for `re-anchor` every citation as old form and new form. The files are the run's record until the Chapter and the surface edits land; they are scratch and never enter the tree.

Order. Sections 2, 3 and 4 each have two halves, a judging half and an edit half. The judging halves are independent across the three surfaces, so judges may overlap across sections where the box has capacity under the dispatch shape, subject to the cap of three. The batched ask goes out when all three judging halves have returned. The edit halves land in section order after the operator's answer, so the Chapters read in the order the surfaces were judged and one commit's reconciliation is not confused with another's. A section's Chapter closes when its edit half lands, so section 2 closes first after the answer and no section closes before it. Section 5 runs last because it reconciles the whole.

## Sections of Work

### 1. The inventory

Model: opus
Locus: inline

A listing, not a judgment. The run records, before any judge is dispatched, the baseline each later section reconciles against, under three predicates. The pending kaizen notes: every non-empty line under each `kaizen/notes-*.md` that opens with neither `#` nor whitespace, counted per file, which admits both note forms `kaizen/README.md` names, the pipe-delimited short line opening with a date and the long form opening with `- `; a heading is out, and an indented continuation line belongs to the note line above it and is cleared or kept with it, so the session-start count, which counts every non-empty non-`#` line indented or not, never meets an orphaned continuation. The active backlog items: every bullet opening `- **` at column one under the `## Active` heading of `docs/backlog.md` and before the next `##` heading; a continuation line, an indented bullet and a bullet under any other heading are out. The kit memory records: every `.md` file that is a direct child of the kit's project memory tier except its index `MEMORY.md`, plus every operator-tier record whose body or triggers name a path under `plugins/claude-kit/`, a path under this repo's `docs/plans/`, `docs/archive/` or `docs/backlog.md`, or the doctrine file `claude-kit-doctrine.md`; a file in a subfolder, a non-`.md` file and the index's backup are out. The project memory tier is the directory the kit resolves for the checkout the run executes in, which for the kit worker's checkout at `D:\claude-kit` is `~/.claude/projects/D--claude-kit/memory/`, and the run names the directory it read in the inventory. The operator-tier candidates are listed by a read of the tier's record files on disk rather than by a semantic query: `grep -l -E 'plugins/claude-kit/|claude-kit-doctrine\.md|docs/(plans|archive|backlog)' ~/.claude/memory-operator/*.md`, excluding the index and its backup, each hit then read whole to confirm the path is this repo's rather than a same-named path elsewhere. Reading the tier's files is a read; every write to that tier still goes through the `memq` CLI per the memory-system skill. The listing is written to `.kit/scratch/post-rewrite-triage/inventory.md`, a directory the run creates under `.kit/`, which the kit's own writers keep ignored, with the commit it was taken at, the three counts, and the item identifiers under each. The whole gate runs once here and its counts are the baseline every later section's lane reports against. The whole gate is `node --test test/*.test.js` from the repo root, run in the background with its exit code written to `.kit/scratch/post-rewrite-triage/gate.exit` and read from that marker, as the testing-discipline skill states. The inventory names every failing test the baseline carries, and green everywhere in this plan means that failure set and no other.

Acceptance: the three counts in the inventory match a fresh listing by the same predicates at the same commit; the project memory index line count reconciles with the file count or the difference is named; the gate's counts and exit code are read from the run's own marker and every failing test is named.

Files in scope: none tracked. Scratch under `.kit/` only.

### 2. The kaizen inbox

Model: opus
Locus: inline

One judge per machine note file for which the inventory lists at least one pending line, reading every pending line against the rewritten corpus and the kaizen skill's own pass bar, as that skill reads at the run's HEAD and located by content rather than by step number. The pass's dispositions stand as that skill states them, at authoring apply now, promote, route elsewhere and park, and this section adds the one the rewrite creates: `covered`, where the rewritten corpus already states what the note asked for or removed the friction it named, with the covering document and heading in the verdict. A note that is `covered` is cleared from the inbox exactly as an applied note is, by its own line text and never by truncating the file, and its brief is not written. A note that is not covered takes the pass's ordinary disposition, and the pass's brief-writing mechanics, the ones that write an apply-now item's brief under `kaizen/briefs/` before the change is applied, apply to it with one bound: the run writes the brief for an apply-now item and stops there, since this plan edits no rule text; the brief waits under `kaizen/briefs/` for the first ordinary kaizen pass after this plan closes, which applies it. A note that deserves a spec takes the `promote` disposition, and this run writes no spec for it: the verdict carries a one-paragraph sketch, the ask carries the sketch, and on the operator's yes the line is cleared and the sketch goes to the coordinator persona as a message through the persona plugin's `agentic_say` tool, which relays it to the architect persona as a design ask; the record id that tool returns is what the Chapter names. The run routes and parks the rest, and reconciles the staged diff's removed lines against the verdicts before the clearing commit. An apply-now line is cleared once its brief is written and the operator has answered the ask, in which it rides as its own group, and the brief carries the note's text so nothing is lost between the two.

This section also carries the one batched decision ask. Every removal verdict from sections 2, 3 and 4 goes to the operator in one ask, in the client-briefing register, grouped by surface, one item per removal, each with the recommendation and what the alternatives cost, and with the `re-anchor` edits listed so he can approve them as a class. The ask goes out when all three surfaces' judges have returned, and nothing leaves any surface before his answer.

The kit's own capture rule stays open through the run: a note appended while a judge is reading is not in the inventory, survives the clear by construction, and is the next pass's.

Acceptance: every pending line in the inventory has exactly one verdict file; every `covered` verdict names its covering text and that text exists; the decision ask went out carrying every removal verdict from sections 2 to 4 grouped by surface, and the answer is recorded under `## Chapters` with the date; no line was cleared before the answer, and every cleared line is matched to a verdict in the Chapter and no line without one was removed; the inbox files after the clear contain only lines the inventory did not carry or the verdicts left in place; briefs written are under `kaizen/briefs/` in the skill's format; every `promote` sketch the operator accepted is recorded in the Chapter with the coordinator record that carried it to the architect.

### 3. The backlog

Model: opus
Locus: inline

The `## Active` block read in three regions by three judges, since a count past two hundred items is past one reading. The regions are cut by item count at the inventory commit: the bullets in file order split into three consecutive runs as near equal as the count allows, each region a line range from its first bullet's first line to the line before the next region's first bullet, so a multi-line item belongs whole to the region its opening `- **` line falls in, and each judge's brief carries its range. Each item is judged whole against the rewritten corpus and the curating-docs skill's prune pass, which is where the rule lives that an item past 90 days gets a promote, retire or keep call. Verdicts: `keep`, which for an item past 90 days writes the adjudication date ahead of its parked date with the reason, as the prune pass does, and gives an undated item its parked date; `re-anchor`, where the item cites moved or reworded text; `retire`, where the rewritten corpus covers it, a closed plan delivered it, or its signal can no longer fire, naming which; `promote`, where it is a plan waiting to be written, whose verdict carries a one-paragraph sketch that rides in the ask, and on the operator's yes the sketch goes to the coordinator persona through `agentic_say` for relay to the architect persona, as section 2 states, this run writing no spec. Retired items move to a dated snapshot `docs/archive/backlog-retired-YYYY-MM-DD.md` naming the corpus rewrite as the effort that removed what they were about, which the backlog's Snapshots heading routes them to and lists, created where absent. Promoted items move to the quarter's `docs/archive/backlog-YYYY-QN.md`, created from the curating-docs template where the quarter's file does not exist yet, each snapshot line naming the coordinator record that carried its sketch. Nothing is struck in place, and nothing moves before the operator's answer to section 2's ask.

Acceptance: every active item in the inventory has exactly one verdict file; every `retire` names its reason of the three; the items remaining under `## Active` after the edit are exactly the `keep` and `re-anchor` verdicts plus any item appended after the inventory, every `keep` past 90 days carrying its adjudication date; the retired snapshot carries every retired item and is listed under the backlog's Snapshots heading; the quarter's snapshot carries every promoted item with its record; no item moved before the answer.

Files in scope: `docs/backlog.md`, `docs/archive/backlog-retired-YYYY-MM-DD.md` for the run's date, `docs/archive/backlog-YYYY-QN.md` for the quarter the edit lands in.

### 4. Kit memory

Model: opus
Locus: inline

One judge over the project tier and one over the operator-tier candidates the inventory listed, each record read whole against the rewritten corpus. The memory-system skill's four remedies bind the verdicts, routed by what went wrong with the record. `keep`, where the fact and the body both hold. `repair`, where the fact holds and the body names a moved location or a reworded rule, so the body is replaced whole and the record keeps its name. `supersede`, where the record was right and the rewrite has overtaken it, so a new record carries the current answer and points back at the old one; a judge that finds a retired rule with nothing to replace it writes the superseding record to say the rule is retired and where the current rule lives, which is an answer. `delete`, reserved for a record that was never true. Archive, the fourth remedy, is the decay pass's and is not a verdict here. Edits to the project tier are hand moves, since that tier has no CLI verbs: a repair edits the record's body, a supersession writes the new file and its `MEMORY.md` line and leaves the old record in place for the decay pass to archive, since the remedy demotes the old record rather than removing it, and a deletion unlinks the file, its `MEMORY.md` line and any `.bak` copy beside it. An index line with no record, or a kept record with no index line, is repaired in the same edit and named in the Chapter, since the tier's index and its files do not reconcile today. Edits to the operator tier go through the `memq` CLI only, never the Write tool, in the forms the memory-system skill states: a repair is `memq add-operator <name> "<description>" --update --body-file <path> --confirm-shared`, where `<name>` is the record's filename stem and `<description>` is its index line; a supersession is the same verb for the new record with `--supersedes <old name>`; and a deletion is `memq delete-operator <name> --confirm-shared`. The store is a git repository, so a deleted record is recoverable from its history, and that is the reversal a `delete` verdict names.

Acceptance: every record in the inventory has exactly one verdict file; every `delete` names why the record was never true, every `supersede` names the record that replaces it, and no record was changed before the operator's answer to section 2's ask; the project memory index after the edits names exactly the records that exist; `memq recall` exits 0 after the operator-tier edits, and the operator tier's own `MEMORY.md` names exactly the records that exist; the Chapter lists every repaired, superseded and deleted record by name.

Files in scope: the kit's project memory tier and its `MEMORY.md` index; the operator tier through the CLI only.
