## Goal

The project memory tier has two gaps that the same week's reading surfaced. A memory about a file cannot say whether that file has changed since the memory was written, so a record that was true of `WorkerSpawner.cs` in July answers `recall` in September with nothing marking it unverified; and a project-tier record is authored with the Write tool under no validation at all, so a hand-written `supersedes:` naming a record that does not exist, a `tags:` list in the YAML form memq silently reads as no tags, or an indented `pinned:` that pins nothing, all land without a word. When this plan is done:

- A project memory can carry `anchors: <path>@<sha>, <path>@<sha>`: repo-relative paths at the git blob SHA of their content when the memory was written or last re-anchored. `memq anchor <name> <path>...` writes the line, computing the hashes so no 40-hex value is ever typed by hand.
- `memq decay-scan` reports a `DRIFT` block naming every live project memory whose anchored file has changed or gone, as a nomination beside summarize and archive, never as a retirement. `memq get <name>` prints each anchor's state. `memq recall` marks a drifted record's digest line with a `[drift]` token, so the effort-start read shows it. The SessionStart hook says how many project memories anchor changed files, as one integer, when there are any.
- A PreToolUse guard validates the frontmatter of a project-tier memory at the Write (and at an Edit that touches the block), refusing with the fix named: a `supersedes:` naming no live same-tier record, an `anchors:` entry that does not parse or escapes the project, list-form `tags:`, an indented top-level key, a malformed `pinned:` or `created:` date. The same guard refuses the Write tool on the two shared tiers, which the memory-system skill already says are CLI-authored only.
- The memory-system skill documents both, and the kit's architecture and security docs follow through the finishing pass.

## Approach

The design decisions, settled 2026-08-23 in the reviewing session, each with its reason:

- **An anchor is a whole file at its git blob SHA.** The hash is the one git itself computes over the file's own bytes (`git hash-object --no-filters <path>` reproduces it), so a reader can verify an anchor by hand, it works on uncommitted content, and it needs no git process at check time. The flag is load-bearing rather than decorative: this checkout runs `core.autocrlf=true` with no `.gitattributes`, so a bare `git hash-object` applies the clean filter and returns the LF-normalized hash, which for any CRLF file in the tree is not the hash an anchor records. Whole file rather than a line range because a memory is about a file's contract, and any edit to the file is a reason to re-read it; whitespace-only drift is accepted as the price of a hash a human can check.
- **Drift nominates; it never retires.** A changed file does not make the memory wrong, it makes it unverified, and the store's posture since decay shipped is that the scan reports and the operator decides. The remedies on a DRIFT line are re-read, then `memq anchor` again (still true), a fresh record with `supersedes:` (overtaken), or a hand correction (wrong); a DRIFT line alone never deletes. Prior art read this week (memspec) inferred relations between records lexically and had to drain the result; a hash the operator set is the only inference here.
- **Project tier only in v1.** An anchor needs a project root to resolve against and a tree to hash; the type and operator tiers have neither. Shared-tier anchors would need a repo reference per entry, which is the cross-tier question the supersedes round deferred for the same reason.
- **The writer is a CLI verb that touches one line.** The project tier is Write-tool authored, and stays so for bodies; but a 40-hex value typed by hand is exactly the error the field cannot survive, so `memq anchor` computes and writes the `anchors:` line and nothing else. `decay-prune`'s archive move is the precedent for the CLI touching a project-tier file. The rewrite moves the file's mtime, which `lastAliveMs` counts as a sign of life; that is correct (anchoring is a verification act) and is stated in the skill.
- **The fleet grant withholds `anchor`.** Anchoring rewrites a record in the shared priors, an authoring act on state a fleet worker's writes are otherwise quarantined from; the grant's verb allowlist does not gain it, and a test pins the withholding as the existing withheld shapes are pinned.
- **Four read surfaces in v1, and not `find`** (decided 2026-08-23, Scott). `decay-scan` (the pass where nominations are adjudicated), `get` (the moment of use), `recall` (the effort-start read, where a drifted record's digest line carries a `[drift]` token in the slot the `superseded by` label uses), and the SessionStart count line (discovery, integer-only under the hook's provenance bound). Cost is not the reason `find` waits: hashing the anchored paths a project store carries is milliseconds. `find` spans every project store on the machine, and a hit from another project has no root to check against, so its label would read "not checked" on most lines, noise rather than signal; cross-project checking is a v2 question of its own. The `[drift]` token sits in the same tool-written span as the `superseded by` label and inherits the forgeability residual the backlog records for that label; the positional fix that item names covers both when it lands. `memq recent` and `memq unstamped` carry no label either, ruled 2026-08-25 from Section 3's fourth review round, which named them as sibling surfaces the section never enumerated. Both display events rather than a record's state (what was added or updated, what was read and not stamped), and neither carries any checked or not-checked vocabulary a reader could generalize from, which is what made `recall`'s archive line a real defect and does not hold of these. The ruling is recorded here rather than left to the finding, because Standing Amendment 1 asks for the ruling and not merely for the absence.
- **Decay is orthogonal.** A drifted anchor moves no idle clock and no threshold; drift is its own class, and a pinned record still reports drift, since the pin exempts a record from retirement, not from being unverified.
- **The guard imports memq's readers rather than re-parsing.** Two parsers of one grammar drift; memq already guards `main()` behind `require.main === module` and exports a symbol table, so the frontmatter readers join the exports and the hook requires them. A cross-component pin is then structural rather than a test.
- **The guard denies only what is certain and fails open on everything else,** on the kit's guard posture (`docs-write-guard.js`, `readonly-agent-guard.js`): a missing target file, an unparseable payload, an unresolvable root, all allow. A dangling `supersedes:` is certain (the file is absent); a top-level list-form `tags:` is certain (memq reads it as none); a memq field (`pinned:`, `supersedes:`, `anchors:`, `tags:`, `created:`) indented under any key other than the harness's `metadata:` map is certain, because once `claude-kit_memq-reads-the-harness-shape_spec_v1.md` lands memq reads a field at the top level and under `metadata:` and nowhere else. Every file in this project's store carries the harness's shape (`name: ""` over a `metadata:` map), because the harness rewrites every Write into its memory directory that way, moving the author's top-level keys under the map; so the guard validates a Write's payload as the author wrote it, top-level fields included, and for an Edit or MultiEdit validates the on-disk result through memq's exported readers, which read both placements, judging a record by what it says rather than where the harness put it. The shared-tier refusal applies to every writer, the main session included, because the rule it enforces is "never the Write tool", not "not by subagents" (decided 2026-08-23, Scott: the consistent choice; the main session is the likeliest hand-writer, every legitimate move has a CLI verb the refusal names, and a hand-edit hatch, if one is ever wanted, is an explicit override rather than an exemption by role).
- **`supersedes:` is checked in exact casing.** The backlog records that a variant-case pointer passes the CLI's typo guard on Windows and goes inert on a case-sensitive checkout, and asks for canonicalization at write time. The guard is a write-time check, so it refuses a target that exists only under a different casing and names the exact filename, which is the same fix at the hand-written door.
- **Declined (decided 2026-08-23, Scott), with the reason recorded so it is not re-derived.** A `verified:` witness date: the file's mtime and its applied stamps already carry "still true" evidence into the idle clock, and `memq anchor` re-run is the anchored record's re-verification, so a third witness would duplicate two. A stored supersede reason: the successor's own body is the reason, and a field beside it would be a second place to say the same thing. Both are one-line additions if a real need appears.

## Standing Brief Amendments

Entries here bind every section opened after they were written, dispatched or inline. Each was added because a review round found the same defect class at a second site, which means the brief rather than the implementer is generating it.

- **A not-checked answer never shares a value with a checked-and-clean answer (added 2026-08-25, from Section 1's two review rounds).** Every reader on this surface has three outcomes, not two: it checked and found something, it checked and there was nothing to find, and it could not check at all. The third must be a value no caller can mistake for the second, at *every* entry point rather than at the one the review happened to name. Section 1 shipped this defect twice at different doors: first an unusable root answering with the same empty list as a record carrying no anchors, then an unreadable record file and a field misplaced under the wrong key doing the same through the frontmatter sentinels. The consequence is the same each time and it is the worst one this feature has: the surface whose entire job is to say "unverified" reports "verified" instead, and nothing anywhere says otherwise. So when writing or reviewing any reader here, enumerate its failure inputs (an absent file, an unreadable file, a refused parse, an unresolvable root, a sentinel from a shared reader, a pinned or run-scoped store, a frontmatter block that opened and never closed, a block longer than the reader's line bound, a list truncated at a cap) and name the answer each one gives, before writing the happy path.

  The enumeration is a deliverable, not a habit (strengthened 2026-08-25, after the class recurred a third time). Section 1 fixed this defect at the door its second review named and left it standing at the exported entry point one level below, which is the narrow reading this amendment already forbade in prose and did not prevent. So a section touching a reader on this surface returns, in its report, a table with one row per exported reader and one column per failure input above, each cell naming the value that reader answers with. A cell whose value is the same one the reader gives for checked-and-clean is the defect, visible in the table before any reviewer reads the code. An input that cannot reach a given reader is written as such rather than left blank, because a blank is unreadable as either "cannot happen" or "not considered".

  The enumeration covers two doors it did not used to reach (strengthened 2026-08-25, after the class recurred twice more in Section 3's third review round, at both of them). The first is the error boundary above a reader rather than the reader itself: the session-start hook enumerated every failure its drift pass could answer with, rendered each in words, and then wrapped the whole function in a catch returning the value that means checked-and-clean, so any throw from a helper it called was silence again. A table of readers cannot show that, because the boundary is not a reader. The second is a sibling surface the section never edited: `recall` grew a not-checked clause on its type, operator and pending coverage lines and not on its archive line, which displays the same records and is checked by nothing, so a reader who had just learned that an unlabeled line means checked-and-clean was taught to misread it. A table of what the section changed cannot show that either, because the section changed nothing there. So the deliverable carries two further row groups beside its per-reader rows: one row per error boundary wrapping any reader on the surface, naming the value it answers with on a throw and which throws reach it; and one row per sibling surface that displays the same subject and which this section did not change, naming what that surface says about whether the subject was checked. The second group is the expensive one to enumerate and the one that has now cost a review round, because its members are found by asking what else shows this thing rather than by reading the diff.

  The enumeration covers the channel an answer travels on, not only its wording (strengthened 2026-08-26, after the class recurred in Section 4's second review round at the outermost boundary of all). Section 4's guard produced a correct not-checked answer, worded distinctly from every other answer it gives, and wrote it to stderr on an exit-0 path, which is the one channel the harness does not deliver to the model. A table of readers cannot show that, because every cell in it was right: the defect was not in what the answer said but in whether the consumer could hear it, and a not-checked answer nobody receives is a clean answer. So a surface whose answers reach a consumer through a channel returns, in its report, the channel each of its three answers travels on and the evidence that a consumer on that channel receives it; where two of the three arrive on channels the consumer cannot tell apart, that is the defect whatever the wording says. The evidence is the repo's own precedent for that consumer, or a live observation, and never the test suite, because a test that reads a spawned child's stderr directly observes a channel the real consumer never reads and so reports green either way.

  The enumeration covers the unit an answer is measured in and the field the operation is decided from (strengthened 2026-08-26, after the class recurred in Section 4's third review round at two doors at once). Section 4's guard bounded a record at 65536 characters and answered checked-and-clean below that bound, while every memq reader the guard speaks for bounds the same record at 65536 bytes, so a frontmatter block closing past the byte bound and inside the character bound was validated by the guard and read as never closing by the store: the guard's own denied defect, arriving on its clean channel, and reachable with ordinary non-ASCII text rather than only with a built payload. And the same guard inferred which operation it was judging from the payload's shape rather than reading the tool name the payload carries, so a payload whose shape and name disagree was checked as the operation it was not. Both are one failure: every cell of the answer was right about a subject that was not the one in front of it. So a surface answering about a bounded or shaped subject returns, in its report, the unit each of its bounds is measured in beside the unit the consumer measures that same subject in, and the field it decides the operation from beside the field the harness decides it from; where either pair differs, that is the defect whatever the answer says. This is the axis the four strengthenings above cannot reach, because each of them asks whether the answer is right and this one asks what the answer is about.

- **A symbol a later section must reuse is exported by the section that defines it (added 2026-08-25, from Section 1's two review rounds).** The Approach rejects two parsers of one grammar by name, and an unexported grammar is how the second one gets written: the later section cannot call what it cannot import, so it re-spells the rule and the two drift. Section 1 hit this twice, once on the frontmatter placement sentinels that Section 4's guard has to tell apart, and once on the path grammar Section 2's writer has to refuse through. When a section defines a rule a sibling section's brief also describes in prose, that rule is a shared symbol: export it, and have the sibling call it rather than restate it.

- **A comment states a property the code has, and a claim about callers is checked against the tree (added 2026-08-25, from Section 1's two review rounds).** Three separate comments in Section 1 asserted properties the code did not hold: that a containment check caught link escapes when it was purely lexical, that a helper mirrored a derivation it did not mirror under a store pin, and that four callers read through a function no caller referenced yet. A comment is read as settled fact by the next session and by every reviewer, so an overclaim costs more than silence. State what the code does now; where a property arrives in a later section, say that rather than asserting it in the present tense.

  The check is a deliverable, not a habit (strengthened 2026-08-25, after the class produced three more instances in Section 2's second review round: a comment denying that `frontmatterValue` can return a value it had just been given, a lock comment stating a two-lock discipline exactly one caller in the file follows, and an invisible-class comment claiming one expression does a job two expressions actually do). Prose telling an implementer to be accurate is what already failed here twice. So a section returns, in its report, one line per comment it added or edited that makes a checkable claim, and a claim is checkable when it says what a function can return, what its callers do, what another expression covers, or how many of something there are. Each line names the claim, the command that checked it (the grep of the call sites, the measured return value), and the result. A claim the section cannot check is rewritten until it can be, or deleted; it is never shipped unchecked, because a comment is read as settled fact by the next session and by every reviewer, and the three instances above each cost a review round to find what one grep would have caught at writing time.

## Sections of Work

### 1. The `anchors:` field: grammar, readers, blob hash, states, exports

Model: opus

The field: `anchors: <path>@<sha>, <path>@<sha>` on one line at the top level of the frontmatter block that opens on the file's first line, the same line discipline as `tags:`. A path is forward-slashed and relative to the project's main root (`worktreeMainRoot`), with no leading slash or drive letter and no `.` or `..` segment; a sha is 40 lowercase hex. Three bars sit beyond that grammar, each a deliberate v1 deviation carried on the Chapter's Assumptions line with its cost: whitespace, an invisible-character class (C0/C1, zero-width, bidi controls, BOM, and the double quote), and any segment whose stem is a win32 reserved device name, refused on every platform so one record cannot read differently per machine. Visible non-ASCII is admitted, so a repository with non-English filenames keeps the feature; nothing normalizes Unicode, which is a stated limit for Section 5 to carry.

In `memq.js`:

- `parseAnchors(value)` reads a line's text into `{items, entries, bad, truncated}`, naming every refused entry rather than stopping at the first, and capping at `ANCHOR_ENTRIES_MAX` entries with `truncated: true`.
- `frontmatterAnchors(raw)` is the single composition every reader goes through (block check, `frontmatterValue`, `parseAnchors`); `readFrontmatterAnchors(file)` is its file-reading wrapper.
- `blobSha(absPath)` computes sha1 over `blob <len>` plus a NUL byte plus the file's bytes from one descriptor: open, fstat, size-gate at `ANCHOR_READ_CAP`, read, re-fstat, and null on a short read or a size change, mirroring the descriptor discipline `--body-file` and `readGitPointer` already use in this file.
- `anchorStatesFrom(parsed, root)` and `anchorStates(file, root)` return one `{path, entry, recorded, current, state}` per entry, `state` one of `fresh`, `changed`, `missing`, `unreadable`, plus one further row bearing `truncated: true` when the line carried more than the parse read. Neither throws on any input.
- `isAnchorPath(value)` is the exported grammar Section 2's writer refuses through; `anchorRoot(cwd)` is the one root derivation, answering `null` under a store pin.
- `anchorEntryState` judges a record-named path and never resolves it: lexical containment, then a per-segment `lstatSync` walk refusing a symbolic link or junction where it is found. So an anchor whose path runs through a link inside the project reads `unreadable` rather than `fresh`, which is the cost of closing the win32 hazard where a planted link to a UNC target turns resolution into an outbound authenticating connection.

`null` is the not-checked answer at every one of those doors and never shares a value with checked-and-clean, per Standing Brief Amendment 1; the section returned the measured table the amendment requires.

Exports gained: every reader above, plus the pre-existing `frontmatterBlock`, `frontmatterValue`, `frontmatterField`, `readFrontmatterTags`, `readFrontmatterCreated`, `pinState`, `supersedesName`, `frontmatterTags`, and the three caps `ANCHOR_READ_CAP`, `ANCHOR_PATH_CAP`, `ANCHOR_ENTRIES_MAX`, so Sections 2 and 4 call the grammar rather than re-spell it.

Tests, red first, in `test/memq.test.js`: the grammar (top-level reads, indented does not, list form reads as none, every malformed entry is named); `blobSha` of the bytes `hello
` equals `ce013625030ba8dba906f756967f9e9ca394464a`, with its short-read and grew-while-read branches proved in a spawned child through the suite's existing fs-layer fault-injection pattern; `anchorStates` for fresh, changed, missing, an escaping path, and a link inside the root judged against an in-root control; each reader's not-checked answer for a non-string, a sentinel, an unterminated block, and an unusable root; the exports are present.

Files in scope: `plugins/claude-kit/scripts/memq.js`, `test/memq.test.js`.

### 2. `memq anchor <name> <path>...`, and the grant that withholds it

Model: opus

The verb resolves `<name>` in the project memory directory of the cwd's project (the same resolution `get` uses, the run-scoped pending tier taking precedence over the project tier when a run id is honored), refuses `--type` and `--operator` with the v1 reason, and refuses when no project root resolves from cwd. A pending tier that cannot be examined is a refusal and never a fallback: only `ENOENT` means the project tier, since a stat failing for any other reason says nothing about which tier holds the record, and reading it as absence would rewrite the shared project-tier record of the same name and report success. Each path is resolved against the main root and refused, naming it, when it is outside the root, missing, a directory, absolute, or carries a `..` segment; one refusal writes nothing. It computes the blob SHAs, merges them into the existing `anchors:` line per path (a fresh SHA replaces the old one, existing order kept, new paths appended), creates a frontmatter block (`---`, the line, `---`) at the top when the file has none, and otherwise rewrites only that line; the write is temp-and-rename under both of the project directory's locks (`acquireLock`), decay first and then store, which is the order the file already establishes, so a concurrent decay pass cannot archive the record out from under the rewrite; and the body's bytes are unchanged. It prints the resulting line. Removing an entry is a hand edit in v1; no `--drop`.

The grant: `memq-grant.js`'s verb allowlist does not gain `anchor`; a test in the grant's test file pins the withholding in the deny direction, the way the withheld flag shapes are pinned.

Tests, red first: merge semantics (replace, keep order, append); the body byte-identical before and after (buffer compare); each refusal with its message; block creation on a file without one; both locks held during the write, in that order; the grant withholding; a pending tier that cannot be examined refused with both records left byte-identical.

Files in scope: `plugins/claude-kit/scripts/memq.js`, `plugins/claude-kit/hooks/memq-grant.js` (comment naming the withheld verb, where the allowlist's comment enumerates them), `test/memq.test.js`, `test/memq-grant.test.js`.

### 3. Four read surfaces: the DRIFT block, the `get` line, the `recall` label, the session count

Model: opus

`memq decay-scan` gains a `DRIFT` block after its existing blocks, in the scan's own output style. Its heading names the tier it covers, `memq: anchor drift (project tier): ...`, because the block reads that tier alone and a heading that did not say so would read as a verdict over the whole store. A live project-tier record with at least one `changed` or `missing` anchor gets `memq: drift  <name>  changed: <path>[, <path>]  missing: <path>[, <path>]`, pinned records included. The records the pass could not settle are listed beside the drifted ones rather than dropped, each named for what stopped the check: a frontmatter block it could not read, an anchored file it could not examine, and a line cut at `ANCHOR_ENTRIES_MAX`. The heading counts each class separately, and the scan's no-candidates wording (`memq: no anchor drift (project tier)`) is reserved for a pass that checked everything and found nothing. Two whole-tier failures are the block's own not-checked answers and share a value with neither: a tier that is there and cannot be examined gives `memq: anchor drift (project tier): not checked (this tier could not be examined)`, examined rather than listed because a listing that failed and a walk that threw both arrive at that one answer and only the first is a listing, and a working directory no root derives from gives `... not checked (a store pin is in effect, so no root is derived from this working directory)`. No `decay-prune` flag acts on the block. Only anchored paths are hashed, and the tier is listed once and that listing handed to every walk that reads it.

`memq get <name>` prints, after the body, one line per anchor: `anchors: <path> fresh`, `... changed (recorded <sha7>, now <sha7>)`, `... missing`, or `... unreadable`. It prints instead a single not-checked line whenever the record cannot be checked at all, naming which cause it was, and the causes are spelled once each in `ANCHOR_CAUSE` so this surface and the scan cannot give two accounts of one fact: `this record's frontmatter could not be read` when the parse answers null, and `this project's root could not be examined` when the root does not resolve. `ANCHOR_CAUSE` carries a third, `this record's file could not be examined`, which this surface cannot reach and does not claim to: `get` has already read the record to print its body, so a record whose own file cannot be examined never arrives here at all. That cause belongs to the drift pass, which learns of a record from a tier listing rather than from a read, and it is spelled here so both surfaces say it the same way. The pin sentence (`anchors: not checked (a store pin is in effect, so no root is derived from this working directory)`) is its own answer, given when `anchorRoot` answers null before any record is read. A hit on the type or operator tier is never checked whatever it declares, and says so: `anchors: not checked (this record is on a shared tier, whose anchors do not resolve against this project's root)`, with silence where such a record declares no anchor. Those tiers have no root; they are written by other projects and synced across machines, so resolving one of their paths against this session's working directory would state a verdict about a repository the record was never about, which is the same reason `find` carries no label. That sentence is fixed text carrying nothing from the record, which is what keeps a path from a tier every project on the machine can write out of column zero, where these lines sit outside the provenance fence a shared body prints under. A line the parse cut at `ANCHOR_ENTRIES_MAX` adds `anchors: the rest of the line is unread past <n> entries, so those anchors were not checked` after the rows it did read.

`memq recall` appends a `[drift]` token to the digest line of every live project-tier record with at least one `changed` or `missing` anchor, in the slot the `superseded by` label occupies (a record can carry both), and `[drift?]` to one the pass could not verify, so an unlabeled line is never read as a checked one. The check hashes only anchored paths, runs once per invocation, and is skipped with no token where the pass could not run at all; the project tier's coverage line then carries the answer the tokens cannot, naming the cause. That line answers for one more class the tokens structurally cannot reach: a record the tier holds and the digest's own listing could not stat has no digest line to carry a token, and a reader counting the lines reads a tier one record smaller than it is. So the coverage line counts those separately with their cause (`, plus <N> this digest could not list, anchors not checked (<causes>)`), and a tier holding no record at all earns no not-checked clause, since there is nothing there for the claim to be about. An honored store pin is what produces that: a pin names the project directory the store reads, which says nothing about the working directory, so resolving those records' anchors against cwd would report every anchored file in the store as deleted. Checking a pinned store's anchors needs a per-record repo reference, which is the same cross-tier question v1 defers. A run-scoped store (`KIT_RUN_ID`) is not that case and carries the token normally: a run id adds a pending tier and leaves the project tier where cwd puts it, so the root a project-tier record resolves against is the right one. `find` carries no label in v1.

`hooks/memory-session.js` emits, after the project index block, one line built from up to three sentences, because three states must not share a value: the drifted sentence (`<N> project memories anchor files that have changed since they were written; memq decay-scan lists them.`), the could-not-settle sentence for records the pass reached and could not settle (`<M> project memories could not be checked against the files they anchor; memq decay-scan says why.`), and the bounded sentence for records this hook's own budget stopped short of (`This session-start check stopped short of <B> project memories, because it stops after <records> records, <anchors> anchors or <bytes> bytes read.`). The third names this hook's own bound rather than pointing at the scan, because the scan is operator-invoked and carries no budget, so it could not answer for them; and it carries its own subject rather than reading as `<B> more`, so no reading of it depends on which sentence it follows. A record the budget stopped part way through belongs to that third sentence and not the second: nothing about the record defeated the check, this check ran out. A record carrying an unreadable entry as well is genuinely unsettled and stays with the second. A whole pass that could not run gets its own fixed sentence (`This project's memories could not be checked against the files they anchor, because its memory directory could not be examined; memq decay-scan says why.`), since a tier that is there and cannot be examined would otherwise read as a clean tier. The counts are the only store-derived values on any of them (the hook's provenance bound). Silence is reserved for exactly three inputs and each is a true nothing-to-say: an honored store pin, where no root resolves and the records were never this session's to check; every count zero, which is the clean answer; and a memq whose export table has moved, which the nudge tests for before it calls anything, because a version-skewed memq cannot be spoken for. A throw is not on that list: anything thrown below the nudge answers with its own fixed sentence (`This project's memories could not be checked against the files they anchor, because the check itself failed.`), because an error boundary that returns the clean answer is Standing Amendment 1's defect one level above the readers. A run-scoped store is not the pin case, for the reason the `recall` paragraph above states. The pass is bounded in three dimensions, `DRIFT_RECORDS_CAP` records examined, `DRIFT_ENTRIES_CAP` anchors walked and `DRIFT_BYTES_CAP` bytes hashed, because this hook runs on every session start and a hook that runs long loses its whole stdout, the project index and the write destination with it. The reading half is bounded too, and by the same expression every other reader of a record's fields takes: `listMemories` reads a capped head of each record (`FRONTMATTER_READ_CAP`) rather than the whole file, so a record costs a bounded read whatever its length and the two frontmatter doors cannot disagree about one record. That is a `listMemories` contract change and this section owns it (widened 2026-08-25, from the fourth review round, and so approval drift, recorded in Chapter 3): every field the listing takes from that text is a frontmatter field, and `frontmatterBlock` already refuses to look past `FRONTMATTER_MAX_LINES`, so the cap costs nothing a reader was entitled to. Its named residual is a record whose frontmatter head exceeds the cap, which now loses its `tags` and `supersedes` at that door as well as its anchors, in the not-checked direction rather than the falsely-clean one.

`tierAnchorDrift(dir, memories, root, limits)` is the one pass behind the block and the hook, exported so neither re-spells it, per Standing Amendment 2. Its `limits` are `{records, bytes, entries}` and a cap that is not a finite count at or above zero bounds nothing rather than bounding everything, because a `NaN` compared against silently examines no record at all, which is the checked-and-clean answer for a pass that never ran. It establishes the tier directory itself rather than inferring it from the caller's listing, and reconciles the two: a record name present in its own `readdirSync` and absent from the caller's listing is one the listing could not stat, and it is reported rather than dropped. The read budget is consulted between entries as well as between records, since one record can hold many anchors, and an entry a mid-record stop skipped makes its record `unverified` rather than checked. Bytes are metered from the read loop's own total inside `blobSha`, charged whether or not a hash came out of it, because a bound that counted only successful reads would not bound the work. ### 4. The frontmatter guard

Model: opus

New `hooks/memory-frontmatter-guard.js`, PreToolUse on `Write|Edit|MultiEdit`, registered in `hooks.json` beside `docs-write-guard.js`. Scope: the target's directory is a memory tier directory, resolved through memq's exported root helpers (the project tier under `projectsRootPath()` or an engine store's `projects/<pin>/memory/`, the shared tiers under `typesRootPath()/<type>/` and `operatorDirPath()`), honoring the same `KIT_MEMORY_ROOT` override memq honors so a test can point it at a temporary store; the filename satisfies `isMemoryFilename`. `MEMORY.md`, `decay-stamp`, sidecars, and `archive/` are out of scope and allow.

Shared tier: deny every Write, Edit, and MultiEdit, for every writer including the main session, with one stderr line naming `memq add-type ... --update` or `memq add-operator ... --update`.

Project tier: compute the resulting content (Write: `content`; Edit: the file on disk with `old_string` replaced by `new_string`, honoring `replace_all`; MultiEdit: the edits applied in order). If the result has no frontmatter block, or the block's text equals the block on disk, allow without validation. Otherwise validate through memq's exported readers and refuse, exit 2 with one stderr line naming the rule and the fix, on any of: a `supersedes:` naming no `<name>.md` in the same directory in exact casing (a target that exists only under another casing is refused naming the exact filename; a target found only under `archive/` is refused naming the live-successor rule; the file's own name is refused); an `anchors:` entry `parseAnchors` rejects, or, where a project root resolves from the payload cwd, a path that escapes it; a `tags:` line with no inline value followed by `- ` lines, at the top level or under `metadata:`; a memq field (`pinned:`, `supersedes:`, `anchors:`, `tags:`, `created:`) indented under any key other than `metadata:`; a `pinned:` or `created:` value that is not `YYYY-MM-DD`, in either placement. It also refuses a payload whose frontmatter block opens on the first line and never closes inside the reader's line bound (`frontmatterUnclosed`), which is certain in the guard's sense: every memq field reader answers such a record as though it declared no fields, so a `pinned:` inside one pins nothing and a `supersedes:` inside one points nowhere. It refuses on the same reasoning a record whose first non-blank line is a `---` fence that is not line 0 (folded 2026-08-25, from Section 4's first review round, and so approval drift, recorded in Chapter 4). `frontmatterBlock` opens a block only when the file's very first line is the fence, so a single blank line above it makes every field inside read as absent, exactly as an unclosed fence does: the `pinned:` pins nothing and the `supersedes:` points nowhere, with nothing anywhere saying so. Chapter 1 already recorded this as this section's to refuse ("Section 4's guard refuses such a record at the Write") while the deny list did not name it, so the fold resolves a contradiction inside the spec rather than adding a rule to it. The rule keys on the first non-blank line specifically, so a `---` sitting in a body that never opened a fence at the top is not refused. Both are the write-door half of the defect Section 6 closes at the read doors, and they are here rather than there because the guard is the only surface that sees the record before it exists. Everything else allows, and any parse error, unreadable file, unresolvable root, or unknown payload allows.

Two deliberate widenings of this section, both approval drift recorded in Chapter 4. The placement rule is asked of six memq fields rather than the five the deny list names, adding `machine:`, because memq reads that field too and a rule that covered five of the six would leave one field silently unpinned by placement; the comment claiming the list is every field memq reads is then true. And the refusal line on a shared tier names, unconditionally, that `--update` carries a record's existing frontmatter across and so neither adds nor removes a `pinned:` line, because the verb the refusal names cannot perform that one operation and a refusal naming a remedy that is a no-op is an untrue line in this section's own deliverable (ruled 2026-08-26 from Section 4's second review round, consult attached in Chapter 4). The guard itself gains no exemption for that write: a content-scoped one would permit the delta in both directions, letting any writer silently remove a pin, which is a quieter form of what `memq-grant` withholds from an unattended worker.

Canary: two probe blocks in `hooks/hook-canary.js` rather than the one the deny direction alone needs (widened 2026-08-26, and so approval drift, recorded in Chapter 4), because this guard matches every Write, Edit and MultiEdit, so one stuck at deny blocks every file write in every session and only an allow probe catches that. One in the deny direction (a Write payload for a fixture project-tier path carrying a dangling `supersedes:`), on the shape of the existing probes; the probe-count figures the canary's comment and `docs/security-model.md` carry move with it (the doc through the curator). Two of the canary's pre-existing probes changed behavior in the same file while this section was open, and both are declared here rather than shipped quiet (2026-08-26, and so approval drift, recorded in Chapter 4): the leash probe's child environment is now built by the same allowlist every other probe's is, so an ambient run id or events-path override cannot make the probed leash answer for the machine's own session state, and the grant probes' throwaway store root is now the per-run random one rather than a fixed name, which closes the hole where a planted directory at a known path could decide a probe. Both are the anti-planting reasoning the new probes already carry, applied to the probes beside them.

Tests, red first, in a new `test/memory-frontmatter-guard.test.js` on `docs-write-guard.test.js`'s harness (spawned child, exit code, stderr), with a temporary store: each deny rule with its reason text; a clean record allows with empty stderr; an Edit that leaves the block unchanged allows; out-of-scope files allow; the shared-tier deny for the main session and for a subagent; a malformed payload allows.

### 7. The drift pass stands down on a network working directory, and says so

Model: sonnet

Appended 2026-08-25 from Section 3's third review round, and so approval drift, recorded in Chapter 3. `driftNudge` resolves its root from the session's working directory and then runs synchronous `lstat`, `open` and `read` calls beneath it, once per path segment of every anchor it examines. On a working directory that names a network share, each of those is a network round trip, and a synchronous open on an unreachable share hangs for the SMB timeout rather than failing fast. This hook runs at session start with no timeout entry in `hooks.json`, and a hook that runs long loses its whole stdout, taking the project index, the sync-health warning and the write destination with it. So the cost of the drift pass hanging is not the drift line; it is every other block this hook emits.

`hooks/compact-deferral-nudge.js` already refuses a network working directory for exactly this reason and exports its predicate so the suite can pin it, which makes this a single-source question rather than a new judgment: the predicate moves to one home both hooks import, and neither re-spells it, per Standing Amendment 2. The drift pass then stands down where it answers true. Standing Amendment 1 governs what the stand-down says: a pass that did not run is not a clean store, so it answers in words, with a fixed sentence naming the working directory as the reason and carrying no store-derived value, joining the silences the hook already reserves rather than borrowing the clean answer. Whether the shared home is the existing exporter or a small module both require is the implementer's call, provided exactly one expression decides the question.

Tests, red first: the drift line absent and the stand-down sentence present for a UNC working directory, against a local-path control that produces the normal line, so the test proves the predicate speaks rather than that the pass happens to be quiet; the stand-down sentence carrying no text from the store; the rest of the hook's blocks still emitted alongside it; and a source-inspection pin that the predicate is spelled once, on the pattern the suite already uses for single-construction rules.

The stand-down covers four callers rather than one (widened 2026-08-25, from Section 3's fourth review round and again from Section 4's first, and so approval drift, recorded in Chapters 3 and 4). `memq recall` and `memq decay-scan` run the same per-segment `lstat` walk against the same working directory, so a network share hangs them exactly as it hangs the hook; `recall` is the heavier case, because the effort-start read is the one a session takes before it has done anything else. The two differ from the hook in what a hang costs, not in whether it happens: they are operator-invoked and foreground, so a hang is visible and interruptible where the hook's is silent and takes the whole stdout with it. They therefore stand down on the same predicate and say so in the same words, and the answer joins each surface's existing not-checked vocabulary rather than minting a third.

The fourth caller is the frontmatter guard Section 4 builds, and it is the one that costs the most. `memory-frontmatter-guard.js` derives an anchor root from the payload's working directory to judge whether an `anchors:` entry escapes the project, which runs the same synchronous walk; and it sits in a PreToolUse hook in front of every Write, Edit and MultiEdit that lands on a memory path, so where the other three cost a lost stdout block or an interruptible wait, this one stalls the operator's own tool call until the harness's hook timeout ends it. Section 4 already gates the derivation on there being an entry to check, which removes the cost from every record declaring no anchors; the stand-down here is what covers the records that declare one. That guard walks the working directory at a second site as well, `placeTarget`'s `fs.realpathSync.native` on the payload's own directory, which Section 4 closes for a UNC or device-namespace root at the moment it ships because it sits in front of every write; the predicate this section single-sources is what that site takes once this section lands, so the two spellings collapse to one.

Two further memq.js corrections ride here, both surfaced by Section 4's second review round and neither foldable into Section 4, whose file list carries no `scripts/` file (folded 2026-08-26, and so approval drift, recorded in Chapter 4). `tierDirFor` answers whether a directory is a tier and not which one, so Section 4's guard re-spells the three tier shapes to name the tier in its refusal, which is the second spelling Standing Amendment 2 forbids and drifts fail-open: were memq's shapes to move, `tierDirFor` would still place the file while the guard's own reading answered null, and a shared-tier write would be allowed in silence. memq gains the exported answer and the guard calls it. And the prune refusal on a pinned record (`delete its pinned: frontmatter field to retire it`) names an edit that Section 4's guard now refuses to the session's own write tools; the sentence stays true of the operator's editor and of a shell, so it gains the clause saying which rather than being withdrawn.
