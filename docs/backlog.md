Adjacent candidate from the 2026-08-19 kaizen note on ungoverned scouts: consider governing the harness's `Explore` type as strict too; its tool list already excludes Edit and Write, so Bash is its only mutation channel and strict-governing it should break no legitimate use, while `general-purpose` can never join (it legitimately mutates), which is why executing-work brackets read-only-intent dispatches under ungoverned types rather than leaning on the guard for them. If Explore joins the roster, the parity test's read-only predicate must special-case a type that lives in the harness rather than in `agents/`.

- **Decide whether the read-only guard should deny outbound-network commands (2026-08-18, from the document-review-battery security review).** The guard's strict class denies write-shaped commands and says nothing about `curl`, `wget`, `Invoke-WebRequest`, `Invoke-RestMethod`, or `nslookup`, and the tree-state capture that backstops a review round sees only worktree deltas, which a network call never leaves. So the sole control against a read-only reviewer being talked into exfiltrating by a document it was told to review is the charter sentence telling it not to. Both new document agents state that prohibition with its rationale, which is the strongest form the kit's model currently offers, and the exposure predates them; what the effort changed is that two agents now exist whose entire job is reading documents that may come from outside. The candidate is naming the outbound-network commands in the strict-class denylist, which is cheap and mechanical. The argument against is that a read-only reviewer sometimes has a legitimate reason to fetch (a version, a published doc), so the denial would need an escape and the escape is where this gets expensive. Judge it the next time a reviewer agent is given a document from a source the operator does not control.

- **Decide whether the disclosure sweep needs a section-time trigger (2026-08-18, from the document-review-battery adversarial review).** The disclosure sweep runs at finishing, because that is where the audience predicate lives. Under Commit-and-Push, a section closes by committing and pushing, so an outward-facing document carrying a leak is already on the remote before the sweep that would catch it ever runs. The executing-work security-reviewer trigger list (input handling, auth, SQL construction, secrets or configuration, an external boundary) does not name a section whose spec carries a `Disclosure:` list, so nothing pulls the sweep earlier. This matches what the spec designed rather than drifting from it, which is why it was recorded rather than fixed at close-out; the proof runs are the counter-evidence, since they exercised the sweep at what was effectively section scope and it fit naturally there. The fix, if taken, is one entry on that trigger list. Judge it on the first real effort that ships an outward-facing document under Commit-and-Push.

- **Judge the boundary cadence on a real parallelized run (2026-08-19, the operator verification carried out of the boundary cadence effort).** The effort shipped the stagger rule, the interim boundary, and first-green branch commits, and every gate it could run in-session passed, but its acceptance is behavioural and only the operator can observe it: on the next real parallelized run, compactions should land at a declared boundary, a section close or an interim board entry, rather than at the safety valve, and no finished section should sit uncommitted on a feature branch for hours. This is not a check any session can close for itself: it needs a multi-hour parallelized run under a live PreCompact gate on the operator's own machine.

- **Give the finishing pass a compaction boundary of its own (2026-08-19, from the boundary cadence finishing review).** The section loop now yields a boundary at every section close and, during a closure drought, at an interim board entry, so a long parallelized run no longer starves the PreCompact gate. The finishing pass has neither. No section closes during finishing by definition, so step 8 never fires there, and the drought rule is scoped to the section loop, so a finishing pass running QA, a security review, an adversarial review, a fix round, and a docs curation produces no boundary at all and compacts wherever context happens to fill. The exposure is smaller than the section loop's was, since a finishing pass is bounded by a fixed step list rather than open-ended, which is why this is parked rather than folded in. It needs its own design: the section loop's trigger is a count of review-round adjudications with no close, and finishing has no closes to count, so the analogous trigger has to be named rather than borrowed. Parked rather than appended to the boundary-cadence plan because it needs its own brief and acceptance, and appending a section during that plan's own finishing pass would reopen a plan that had already passed QA and both finishing gates.


- **Silent store auto-sync: the fail-safe hardening deferred at ship (2026-08-19, from the worktree-store-and-autosync Section 2 close-out, `docs/plans/claude-kit_worktree-store-and-autosync_spec_v1.md`).** The auto-sync shipped after five review rounds, security-clean of any Critical or security-Major (the inbound screen converged to a completeness-proven mode+path allowlist). The operator authorized shipping now with these residuals parked (Option A, 2026-08-19); every one is fail-safe (it wedges the sync loudly or misses a nudge, never leaks or silently corrupts) and most need a party who can push to the private remote. Judge each on real multi-machine use; none is urgent. (1) **Intermediate-commit history wedge:** the inbound screen reads the upstream TIP tree, so an add-then-remove of a disallowed path across incoming commits presents a clean tip, the rebase latches the intermediate commit into local history, and the post-rebase probe then wedges a loud `leaks` gate (push blocked, no leak). The complete fix screens the incoming range, which is fragile across merge commits; the tip screen covers the common case. (2) **Hostile managed-file intake:** the screen admits an incoming `.gitignore`/`.gitattributes` without a content check, so a peer's non-canonical one materializes over the live allowlist, the drift gate blocks the push, and `doctor -Fix` refuses to rewrite a Foreign managed file, so the loud line's own remedy cannot clear it (the operator fixes the file by hand). Fix: screen the two managed files' content (canonical or marker) on intake. (3) **Overridden-root silence on win32:** a pending store at a non-default `KIT_MEMORY_ROOT` gets neither the spawn (by design) nor any text (the state-file and marker paths never run there), so its drift is silent, where off-Windows and the base hook nudge. Fix: emit the text fallback for a pending owned non-default-root store; the cost that parked it is that the transient-streak and backstop tests use non-default stores as proxies and would need reworking onto default-store fixtures. (4) **Outbound probes' own blindness:** `install-memory-sync.ps1`'s tracked/history leak probes read paths only (no mode axis) and dedupe objects, the exact two gaps the inbound screen just closed, so a mode-120000 entry or a rename in local history could publish; same-user reachable, low value, and in the shared installer the section otherwise left alone. (5) **PATH steering of the bare `git`:** the detached sync invokes `git` by name, so a repo-carried PATH could choose the binary the unattended credential-using run executes, the same env-steering class as the `USERPROFILE` anchor the section did close; the fix is an absolute git path across the sync's invocations.

- **Type-check the session-id comparison the leash and the compaction gate both rest on (2026-08-21, from the boundary-ritual-reinforcement Section 2 security review).** `sameSessionId` in `plugins/claude-kit/hooks/kit-compact-lib.js` coerces both sides with `String()` before comparing, so a non-string `session_id` can compare equal: a payload carrying the bound id inside an array fired the chapter-boundary nudge in the reviewer's probe. The nudge's own consequence is one spurious reminder, which is why it was not fixed inside that section, but the same comparator decides the PreCompact gate's verdict and the Stop hook's leash binding, where a type-confused match is worth considerably more. Not reachable from a real harness payload, which always sends a string, so this is hardening against a shared primitive rather than a live defect. The fix is one line, requiring `typeof` string on both sides, and its cost is that every caller must be checked for a non-string it currently gets away with.

- **The integrity manifest reports on the files it knows, and is silent about a hook it does not (2026-08-21, from the boundary-ritual-reinforcement Section 2 security review).** `integrityProbe` in `plugins/claude-kit/hooks/hook-canary.js` iterates the build manifest's own keys, so a `.js` file present in the installed plugin cache but absent from the manifest is uncovered silently rather than reported. The manifest is currently complete, and the build regenerates it, so nothing is wrong today; what is missing is the reverse check that would notice a hook file the manifest does not name. This matters more now that a PostToolUse hook writes into the model's context on every edit, which raises the value of a tamper against the cache from one injection per session to one per edit.

- **The checkpoint command does not ask who is calling it (2026-08-21, from the boundary-ritual-reinforcement Section 2 security review).** `kit-compact-checkpoint.js open` writes a checkpoint using the armed goal's `boundSession` with no check on the invoking agent, and `readonly-agent-guard.js` permits writes under `.kit/` for every governed read-only class. The chapter-boundary nudge stands subagents down on the payload's agent keys, which is the only guard that can do it (a subagent's payload carries the parent session's own id, so the bound-session check passes for one), but that stand-down rests on the harness continuing to emit those keys, a field this kit established by probe rather than from documentation. If a future harness drops or renames them, a nudged read-only reviewer could open the compaction checkpoint on the parent's behalf mid-chapter, defeating the control the nudge exists to reinforce. The fix is a refusal in the checkpoint CLI itself when the environment or payload marks a subagent, which is defence in depth rather than a replacement for the guard.

- **Judge the chapter-boundary nudge on a real leashed run (2026-08-21, operator-only, from the boundary-ritual-reinforcement close-out).** The whole effort is a feedback loop for a failure only a live multi-hour run produces: a leashed session that never loads the executing-work skill, closes Chapters from the doctrine alone, and so never opens a compaction checkpoint. Everything shipped is verified in test and by direct hook invocation, and none of that can answer the question the effort exists for, which is whether the reminder actually changes what a session does. Each machine runs the installed plugin copy rather than this clone, so the check waits on the fix reaching SCOTT-CLAUDE and NEO-CLAUDE. What to look for on the next real unattended plan run: compactions landing right after Chapter commits rather than mid-section, and, in the scrollback, the gate's boundary note NOT still firing after a Chapter has closed. Two outcomes reopen work rather than closing this. A run where the nudge fires and the session still skips the checkpoint means the reminder is reaching the model and losing to something else, which is a wording or a placement question rather than a mechanism one. A run where the nudge never fires at a real Chapter append means one of the seven guards is standing the hook down wrongly on live payloads, and guard 3's agent-key stand-down is the first suspect, since it rests on payload fields established by a probe against one harness version.
