# Backlog

The living handoff and next-steps doc for the kit. It carries active items only. When an item is done, it moves out to a dated snapshot in `archive/` (`backlog-YYYY-QN.md`) rather than being struck through in place, so this file stays lean and readable.

Per-plan history does not live here. A plan's Chapters are its own append-only record and travel with the plan into `archive/` when it closes. This file is for cross-effort next-steps that do not belong to any single open plan.

- **Flake: the memq stale-lock race test, roughly 1 run in 4 (2026-08-01).** `two concurrent acquirers of one stale lock admit exactly one winner` in `test/memq.test.js` failed 2 of 8 full-suite runs in one session and passed every isolated run and every immediate re-run, including under changesets of pure markdown that have no mechanism to reach a lock. It races two real child processes against one stale lock, so it is load-sensitive, and a full-suite run is where its timing assumption is thinnest. Its assertion text is still uncaptured, because it does not reproduce on the runs made to capture it; a run that writes the suite's output to a file rather than a pipe would hold it. The rate is high enough to erode the gate's signal, since a green now means "green or one known flake" and that is exactly the ambiguity a baseline exists to remove. The fix is to make the test wait on a real readiness signal rather than a timing window.
- **`memq recent`'s added-versus-updated split does not mean what it reads as (2026-08-01, found by running the shipped command against the real store).** The label is correct against its stated rule and its tests, and still misleads: the Edit and Write tools rewrite a memory file rather than patching it in place, which resets `birthtimeMs` to the moment of the edit, so a memory that has existed for a week and was edited today reports `added`. Measured on this store: `subagent-wait-mechanics.md` and `plugin-cache-snapshot-inert-hooks.md`, both days old and both edited in that close-out, carry a birthtime equal to their mtime to the millisecond. The platform gate is doing its job (Windows keeps a real creation time); what the birthtime tracks is the writing tool's behavior, not the record's history, so on this toolchain `added` effectively means "written by a tool that recreates the file" and fires for nearly every memory write. No test caught it because fixtures construct files directly. Three ways out, cheapest first: drop the split and label every memory file `updated`, which is true either way and costs the platform gate; key `added` on the memory's own `created:` frontmatter date falling inside the window (`readFrontmatterCreated` already exists and `lastAliveMs` already reads it), which is author-asserted and absent on some records; or keep the split and say plainly in `memory-system` that `added` means first written by this toolchain. The middle option is the recommended one, since the frontmatter date is the only signal that describes the record rather than the tool.
- **Fence `memq recall`'s journal lines under a store pin (2026-08-01, from the memq-session-recap finishing reviews).** `cmdRecall` prints journal lines at column zero whatever the pin state, so under a pin each carries the latest summary another of the instance's workers wrote for that key, in the tool's own voice. `memq recent` fences its journal lines for exactly this reason, and the security model's keyed-on-the-pin rule reaches both. Deliberately deferred rather than missed: `recall`'s surface is narrower (one line per key against `recent`'s one per entry inside a window), and closing it changes a shipped command's output and its expected-output tests, which is a separate call from adding a new command. The counterweight is frequency, and it argues for doing it: `recall` runs at every effort start while `recent` runs at close-out. The fix is one `projectIndent` on the journal line at `plugins/claude-kit/scripts/memq.js:2702`, plus the recall tests' expected output and the exception paragraph in `docs/security-model.md`.

- **Explore channels for unattended interactive runs (research preview).** A channel is an MCP server that injects external events into the interactive session as model input (code.claude.com/docs/en/channels-reference). Two uses for long runs, both keeping the work on subscription billing: a local webhook or scheduler nudging an overnight run's next turn, and permission relay (v2.1.81+) answering tool-approval prompts from a phone. - **Push-time stranded-branch guard (candidate, 2026-07-17).** When a repo auto-deletes merged head branches, a late push to a just-merged branch silently recreates it off the integration line (the stranded-commit trap), signaled only by `git push` printing `[new branch]` for a branch that should already exist. The kit already ships merge-strand-guard and branch-hygiene, and the manual strand-check caught a live instance on the neo project, so this is defense-in-depth, not a gap. A mechanical guard would flag an unexpected `[new branch]` on push. Build only if the trap recurs despite the existing guards; the strand-check working is why it is parked, not prioritized.
