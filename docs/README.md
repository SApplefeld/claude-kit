# Claude-Kit Docs

This directory is the working library and project history for the kit itself: the documents *about* the solution, the active plans, and the archived record of finished work. It is repo-level material, a sibling of `README.md`, `home/`, `kaizen/`, and `settings/`. It is not part of the installable plugin payload (`plugins/claude-kit/`), so nothing here loads or shows up when someone installs the plugin.

## Folder map

The library has three zones, and each zone has one job.

- **Root (`docs/`)** holds the stable documents about the solution and this index. Architecture, design rationale, and any security model live here. These describe what the kit *is*, not a single effort.
- **`plans/`** holds active plans only: specs that are open or in progress. A plan lives here while it is being worked. The moment it reaches `Status: Complete` or is abandoned, it moves to `archive/`. See `plans/README.md`.
- **`archive/`** holds finished and abandoned plans (their Chapters intact) and dated backlog snapshots. It is immutable history. Nothing here is live. See `archive/README.md`.

## Documents about the solution

- **`architecture.md`** is the system overview: what ships in the plugin payload, which parts are prose and which are code, the boundary between the always-on doctrine and the on-demand skills, the three surfaces the communication register rides (the source skill, the home doctrine mirror every subagent inherits, and the `Kit` output style that binds the main thread late in a session) with the parity test holding them byte-identical, the hook wiring and which hooks stand down under the external-engine marker, the canary's three probe classes and the build stamp its integrity check reads, the memory store's shape (its five read surfaces, the run-scoped pending tier's writes, the data-to-model boundary, the evidence-based retention gradient, and its two digests, `recall` over what the store holds and `recent` over what it recorded inside a window), the goal release event stream and its consumer contract, and the external surfaces the kit touches.
- **`security-model.md`** states what the kit's local state assumes and what it does not claim: the single principal and the absence of any boundary between projects, the memory store's per-tier provenance with each path's guard tabulated, the five gated environment overrides plus the deliberately ungated external-engine marker and what the gates buy, the ungated `HOME`/`USERPROFILE` residual under all of them, the residual command-injection exposure on the cmd.exe wrapper, the five PreToolUse hooks (four that deny and one that grants, each with the invariant it enforces, the accepted risk it carries, its compensating controls, and the gap it cannot see), what the build's hook manifest does and does not cover (the output style is payload it never hashes, and it is system-prompt content in every session), what retention does and does not bound (archiving is demotion rather than deletion, the 425-day ceiling on an extended memory, the `pinned:` exemption), and why fail-open hooks mean silence is not evidence of health. Written as preconditions that can be re-tested rather than assurances that cannot.
- **`fleet-integration.md`** is the contract between the kit and the external engine that spawns sessions with it: the nine environment variables, two of them gate signals, that must never be omitted, the five hooks that change behavior under the marker and the two controls that go dark with the canary, the run-scoped memory tier and the promotion the engine owns, the memq grant and the spawn-environment coupling that can turn it off, and the three surfaces the engine reads back. It assembles what `architecture.md` and `security-model.md` describe mechanism by mechanism rather than restating either.

## Living documents

- **`backlog.md`** is the single living handoff and next-steps doc. It carries only active items. Completed items are pruned out to a dated snapshot in `archive/` so the doc never grows without bound.

## How the library is maintained

The `curating-docs` skill owns the mechanics: it archives a plan when it completes, prunes the backlog, cross-references related plans, and refreshes this index. `finishing-work` calls it at close-out, `brainstorming` calls it when a new plan is written, and it can be invoked directly to tidy or retrofit an existing tree.

## Active plans

- **`plans/claude-kit_synced-semantic-memory_spec_v1.md`** replicates the memory tiers across the operator's machines through a private git remote over `~/.claude`, born with an exclude-all allowlist that admits only `projects/*/memory/**` and `memory-types/**` and is re-verified by the doctor on every run, and adds a per-machine semantic layer: an optional in-process embedder and a derived, never-synced index sidecar make `memq find` a hybrid lexical-plus-semantic search with usage-boosted ranking, archive demotion, machine labeling, and provenance fencing, degrading loudly to lexical-only wherever the embedder is absent. Execution is gated on the auto-memory independence plan reaching Complete.
- **`plans/claude-kit_automemory-off_spec_v1.md`** makes the kit memory store independent of Claude Code's auto-memory feature, so memory runs purely through the kit's deliberate bar whatever that setting is: the SessionStart hook emits the project index and the write destination unconditionally under the type-index sanitization discipline, `recall` always carries project-tier descriptions, and a prose sweep drops the injection premise from the docs and the memory skill. The kit deliberately does not detect the harness's auto-memory state; it does its own job and accepts a redundant index when auto-memory is on.
