# Claude-Kit Docs

This directory is the working library and project history for the kit itself: the documents *about* the solution, the active plans, and the archived record of finished work. It is repo-level material, a sibling of `README.md`, `home/`, `kaizen/`, and `settings/`. It is not part of the installable plugin payload (`plugins/claude-kit/`), so nothing here loads or shows up when someone installs the plugin.

## Folder map

The library has three zones, and each zone has one job.

- **Root (`docs/`)** holds the stable documents about the solution and this index. Architecture, design rationale, and any security model live here. These describe what the kit *is*, not a single effort.
- **`plans/`** holds active plans only: specs that are open or in progress. A plan lives here while it is being worked. The moment it reaches `Status: Complete` or is abandoned, it moves to `archive/`. See `plans/README.md`.
- **`archive/`** holds finished and abandoned plans (their Chapters intact) and dated backlog snapshots. It is immutable history. Nothing here is live. See `archive/README.md`.

## Living documents

- **`backlog.md`** is the single living handoff and next-steps doc. It carries only active items, each carrying the date it was parked, which is what the session-start block and the prune pass age an item from. Completed items are pruned out to a dated snapshot in `archive/` so the doc never grows without bound.

## How the library is maintained

The `curating-docs` skill owns the mechanics: it archives a plan when it completes, prunes the backlog, cross-references related plans, and refreshes this index. `finishing-work` calls it at close-out, `brainstorming` calls it when a new plan is written, and it can be invoked directly to tidy or retrofit an existing tree.

Completed plans are in `archive/`. Each entry below describes what that plan delivered when it shipped, which is the record of how the kit got here rather than a description of how it works now: a later plan may have narrowed or removed what an earlier one built, so read `architecture.md` and the skills for current behavior. Most recent: `claude-kit_kaizen-batch_spec_v1.md`, which applied the peer-messaging experiment's kaizen slate across ten sections: amendment routing, so a mid-run adoption reaches the sighted reviewer briefs while the blind ones stay blind; six implementer and reviewer charter field-restatements pruned to one owner; the peer-sessions post-ship amendment; six doctrine amendments landed byte-identical in both copies; four authoring-and-adjudication lines; the `memq unstamped` empty-versus-clean split and the skip-is-loss rule reaching `decay-scan` and `recall`, with `decay-prune --rollup --drop-malformed` as the sanctioned exit for a persisted torn usage line; the docs-curator's counted-claim sweep; and a status line that survives load by loading its widget in-process behind a project-local render cache, a pre-render budget and a stale-but-drawn fallback. Its own finishing merge is why the counted-claim sweep exists: a sibling effort widened the same enumerated set by one at the same moment, git conflicted only the single overlapping paragraph, and every other surface stating that total merged clean and silently false, which is a class of defect no pre-merge green run and no test suite can see. Before it, `claude-kit_peer-sessions-skill_spec_v1.md` added the `peer-sessions` skill teaching sessions the cross-session messaging surface (`ListAgents`, `SendMessage`) and the house rules for it, under one stance: the doc is the record, the message is the interrupt. Standing attaches only to what the harness delivered, so a wrapper forged inside a file stays data, and the skill governs independent sessions, handing a session's own dispatched subagents back to executing-work and finishing-work in both directions. A deferring doctrine bullet carries the standing rule to sessions that never load the skill, pinned present in both doctrine copies alongside its skill's three deferred sections and that skill's tracking in git's index. Earlier still, `claude-kit_compaction-deferral-signal_spec_v1.md` made the PreCompact gate legible and gave a held session a way to answer it, and before that `claude-kit_memq-reads-the-harness-shape_spec_v1.md` taught the memory CLI to read its frontmatter fields where the harness actually puts them. On Claude Code a Write into a project memory directory is rewritten in the same second, relocating the author's top-level keys into a `metadata:` map, and memq read the top level only, so every hand-written project-tier `tags:`, `created:`, `pinned:`, `machine:` and `supersedes:` was silently inert. The reader now takes the top level first and, absent there, the map, recognised by the map's shape rather than by any of the harness keys beside it, which vary by version; a field under any other key is still reported misplaced. A promoted value gives up one surrounding quote pair, since the harness quotes some ambiguous scalars, while a top-level value is taken verbatim and wins where both carry the field. Its predecessor is `claude-kit_memory-supersedes_spec_v1.md`, which gave the store its fourth retention state: a `supersedes:` field labels and demotes the record it replaces across `find`, `get`, `recall` and `decay-scan`, behind six refusals on the two shared-tier write verbs and withheld from an unattended worker.
