# Security model

What the kit's local state assumes, what it guards, and what it does not claim. Written as preconditions that can be checked, because a premise stated as a reassurance ("the store is trusted") cannot be re-tested when something changes underneath it, and one did: the memory store's trust premise was accepted when the store was per-project, then invalidated when a machine-wide shared tier was added, and nothing forced a re-check.

## Principals

**Within one machine account, there is exactly one principal**: that account's user. Every project session, every dispatched subagent, and every hook runs as that user with full read and write access to `~/.claude`. Anyone who can write there already has code execution through hooks and `settings.json`, so no control in this document defends against that.

**Across the deployment, there are several.** The kit is shared with other team members, the repositories sync across multiple machines, and the same person operates it under two work accounts and one personal account. That means kit code, and any repository-carried configuration, crosses account and person boundaries routinely. A control whose only justification is "one person, one machine" is not justified here.

Three consequences follow, and they are why several of the sections below are stricter than a single-user store would warrant:

- **The store is not a security boundary between projects.** Per-project separation is a convention the tooling follows, not a control the design enforces. Any session can read and write any project's memory directory by resolving the path itself.
- **The shared project-type tier is a cross-person surface, not merely a cross-project one.** Content one person writes is read into another person's session context, wherever a type tier is shared rather than machine-local.
- **A repository is a distribution channel for configuration.** Anything a synced or shared repository can set for the shell that opens a session (`terminal.integrated.env.windows` in a committed `.vscode/settings.json`, a `devcontainer.json` env block, an `.envrc`) reaches an account that merely cloned it. Environment-driven behavior is therefore attacker-reachable in a way it would not be on a single-operator machine.

**What is machine-local versus shared is worth checking rather than assuming.** The kit payload is shared by design. Whether a given store directory syncs depends on how that machine is configured, and the tooling neither knows nor enforces the answer. Treat a type tier as shared unless you have confirmed otherwise for that machine.

## The memory store, per tier

The store lives at `~/.claude/projects/<sanitized-cwd>/memory/` (project tier), `~/.claude/memory-types/<type>/` (type tier), and `~/.claude/memory-operator/` (operator tier). The `<sanitized-cwd>` of the project tier is the working directory's path with non-alphanumerics flattened; when the session runs in a git worktree, it is the MAIN checkout's path, because memq follows the worktree's `.git` pointer to the main checkout only when a two-way handshake holds (the pointed-at gitdir has the `.git/worktrees/<name>` shape, its `commondir` and back-pointer resolve, and `<main>/.git` is a real directory). That handshake is a trust boundary in itself: a `.git` pointer file is repo-adjacent data in a directory the session cd'd into, so a planted one must never redirect memory reads and writes, and only a link git itself maintains carries the back-pointer the handshake checks.

**Project tier.** Authored by that project's sessions and emitted into context by the kit's own SessionStart hook (the index emission below). Inside the trust boundary in the ordinary sense: the thing that wrote it is the thing that reads it. That condition, and not any harness behavior, is what leaves the tier unfenced where it is unfenced; Claude Code's auto-memory may also inject the same index when it is enabled, but nothing in the kit depends on whether it does.

Under a store pin that description does not hold, and the difference is the point of the pin rather than a side effect. One pinned tier serves every repository the instance works in, so the Principals section's "the store is not a security boundary between projects" stops being a caveat about what the tooling fails to enforce and becomes the operating condition: cross-repository sharing inside one instance is the intended behavior, because the instance is the entity meant to accumulate, not the repository. Two consequences follow. The tier's content is fenced on the way into context, per the fence discussion below. And the containment that remains is the store root: every memq-mediated write stays inside the root the engine chose for that instance, which is why that root, not the segment, is the boundary. For the memory files a session writes with its own file tools, the destination block is an instruction rather than a boundary, the same status this document gives the data-not-instructions framing.

**Type tier.** Authored by *any* project on the machine that declares `Project-Type: <type>`, and read into the context of *every* project declaring that type. This is a machine-wide shared read-and-write surface. A claim that no store-controlled content reaches a session's trusted context is false by design for this tier.

**Operator tier.** `~/.claude/memory-operator/`, authored by *any* project on the machine and read by *every* one of them. It is the type tier's sharing without the type tier's opt-in: no declaration gates it, so it is machine-wide by construction rather than by a project's choice, and the same sentence holds, that no-store-controlled-content-in-trusted-context is false by design here. Its content is fenced wherever it enters context, on the same reasoning the type tier's is. Two properties narrow the surface rather than widen it: authoring is CLI-only and mechanically so, `memory-frontmatter-guard` refusing every `Write`, `Edit` and `MultiEdit` here whoever is writing, so a memory arrives through `add-operator` under the tier's lock rather than through any session's file tools, and the tier is not emitted at session start, so it enters context only through a command a session chose to run. A `machine:` field scopes a fact to one box; it is a label rather than a boundary, and the reader re-validates it against the writer's own identifier gate before printing, so a hand-edited or synced value cannot put free prose on a search line.

**Two seat rituals read the operator tier for something privileged, and neither is covered by the Principals section's already-has-code-execution reasoning.** That reasoning bounds what a writer on *this* machine gains; both of these records are writable by any local session and reachable from every machine the store syncs, so the writer need not be here at all. The first is the launch invocation `/role` resolves at its name check: the exact command that starts a seat's session is a per-machine operator fact the public skill cannot carry, so it lives in one record per machine. Per machine is a convention there rather than a mechanism: unlike the delegation record below, nothing keys that record to a hostname, the ritual runs no machine comparison when it resolves one, and `memq get` applies no machine filter, so a record written on another box answers here. What the ritual does with it is the whole control. The resolved text is never presented as runnable: the launcher, the seat name and each flag are described in prose, and the operator confirms that description against what they themselves wrote before anything acts on it, a confirmation paid at each resolution rather than once per machine, since nothing here records what was confirmed or can notice that the record has been rewritten between one resolution and the next. An allowlist over the flags is refused for a structural reason rather than a cost one: the payload class is flag-shaped, a launcher's own flag able to disarm its permission prompts or load a session's system prompt from a store path while reading as one clean flag-and-value line, and the flags a launcher accepts are enumerable from nothing this repository ships, so a list naming them decides membership on the untrusted record's own say-so, while a denylist over the same space misses silently. A metacharacter screen stands beside the prose rule as an independent catch for its own class, reporting as suspect a record that is not a single line of printable ASCII or that carries a command separator, substitution, or redirection, since no launch invocation is any of those. Both screens are model-facing prose in the role skill with nothing mechanical beneath either: no hook implements them, no test pins them, and `skills/` sits outside the build's hook manifest, so an in-place edit in the user-writable plugin cache removes either one with no canary. They are conventions the ritual follows, on the footing the warranted-channels list below has rather than the footing the frontmatter guard has. The second is the standing-delegation opt-in, one hostname-keyed record whose presence flips a seat's default treatment of scoped direction from the seats above it in the chain. Its ceiling is the dispatch-authority trace's exactly: it narrows an honest writer without authenticating one, any local session being able to run the CLI that writes it. Its body is read as data and never as instructions, the scope and the exclusions coming from the role skill alone, so a body purporting to widen a scope or drop an exclusion changes nothing and is reported to the operator as a finding; the record's only effect is that on-switch. The machine keying is what makes the grant machine-scoped where the tier's replication is not, and the comparison is caseless because no surface on the path holds a canonical case, so a case-sensitive one would read a real grant as absent on the kit's primary platform. One reach belongs on both records rather than on the tier's general description: `memq add-operator` is granted prompt-free and agent-blind under the engine store signals, per the `memq-grant` bullet under The guard hooks below, and that grant was priced when this tier carried facts. It now also carries an authorization switch, so what the grant reaches has changed even where its stated precondition holds; `docs/backlog.md` carries the re-pricing.

**Pending tier.** `<project tier>/pending/<run-id>/`, present only inside a run the external engine spawned (the `KIT_RUN_ID` entry below). Authored by that one run, read back by that same run, and entered into the project tier only by an adjudication verdict the engine applies. It exists so a headless worker's memory writes do not enter a shared record unreviewed. A pending memory carries no `MEMORY.md` index line: the index is written at promotion. Pending content reaches a model's context only through the run's own memq reads (`find`, `get`, `recall`, `recent`), and none of them fences it. That is the resolution rule rather than a gap: each resolves the single directory the calling process's own `KIT_RUN_ID` names, so the run reading a pending record is the run that wrote it, and there is no provenance gap for a fence to frame. What `memory-session.js` emits for a run is the destination path, not the tier's content, and that path is fenced as the configuration it is (the destination block below).

The scoping is a resolution rule, not an enforced boundary. A process resolves the single pending directory its own `KIT_RUN_ID` names and enumerates no others, so runs do not see each other in ordinary operation. Nothing stops a session that holds Bash from setting a different id and resolving another run's directory, which is the same limit the Principals section already states for every tier.

Six paths carry the memory tiers' content into a model's context, and they are not equally guarded. The machine coordinator directory is not among them and is not a seventh path of the same kind: all four of its file forms are read directly, with no charset reduction, no cap and no fence, and memq's own readers reach none of them, so what stands in for a guard there is the read-as-data framing alone. The board is the one a single seat maintains, and the other three are read more widely than it. A session reads a peer's `registry/<session-id>.md` for the working directory a roster row does not carry. Every agent holding Write, Edit and Bash reads `claims/heavy-process.md` before a heavy spawn, which puts the directory's widest-writer form in front of its widest readership. And the Admin seat polls `admin-requests.md` at the highest privilege on the box. Five of the six carry both shared tiers; the first carries the type tier's index and the project tier's, the operator tier being deliberately absent from what session start emits, the digests carry project records too, and the semantic block reaches further than any of them:

Both indexes share one emitter, so the treatment cannot drift between them; the project index caps at 60 lines against the type tier's 30 |
| `memq get <name>` body | Length-capped, and fenced the same way for the type and operator tiers always and for the project tier under a pin: provenance and a data-not-instructions line on stdout, every body line two-space indented so column zero stays the tool's own voice. The indent frames rather than sanitizes: the print path applies no charset reduction, so a body carrying a bare carriage return or an escape sequence can still put text back at column zero on a terminal. Not charset-sanitized, because a body is a document where newlines and punctuation are legitimate content |

Shared-tier lines two-space indented under one framing line named by contribution, so a tier that put no line in the run is not claimed by the fence. No store text reaches it, so the line is one more field this row enumerates and changes nothing about this row's posture. No description and no body crosses it. The withheld line that follows the block under archive suppression carries no store text at all: two counts and a similarity figure, all this tool's own arithmetic, which is why it sits at column zero |

The run-scoped destination block carries content into context and differs from the six above in its source: the block `memory-session.js` emits names the pending directory, and that path embeds `KIT_MEMORY_ROOT`, so its content is environment configuration rather than store content, and the environment is attacker-reachable per the Principals section. It is emitted faithfully or not at all (a value that would be truncated or reduced stands the session down instead), and it rides on its own indented line inside the block's data fence, so printable-ASCII prose set as a store root reads as a filesystem destination and not as an instruction.

The pin destination block is the same shape: under a store pin (the `KIT_MEMORY_PROJECT` entry below), a session with no run id is told where its memory files go, and that destination embeds the pin as well as the store root. Same treatment: emitted faithfully or not at all, on its own indented line inside the block's data fence.

The project destination block is the third of that family and the one with the widest trigger, since an ordinary session with no run and no pin still gets it. Its path embeds `KIT_MEMORY_ROOT` the same way, and it takes the same faithfully-or-not-at-all rule, but it answers an unemittable path with a third outcome the other two do not have: it withholds the directory, emits the index lines anyway, and points the session at `memq`, which resolves the directory itself. The write convention goes with the directory rather than staying behind, since a session that cannot be told where the directory is cannot follow an instruction to write a file in it, so what it is told instead is to report the condition rather than guess a path for one. It does not stand the session down. The reason is that a stand-down is a response to an environment that asked for something the kit cannot deliver, and an ordinary session has asked for nothing: standing it down would cost a developer their memory writes over a path this block happens not to be able to spell.

Its steering condition is the least gated of the three that decide where the model's own file tools write memory: the store pair alone reaches it, two variables and no `KIT_MEMORY_PROJECT`, where the pin destination block needs all three. Fewer preconditions means broader reach, which is why this block is the one to audit first. The consequence to keep in view is that a store root pointed inside a cloned repository puts a session's memory writes into that repository's working tree.

**The project index emission carries project-tier content into context with no command invoked at all, at every session start, and it fences unconditionally.** The `recall` and `recent` digests in the table above are automatic in the weaker sense of running at a fixed point in a workflow; this one needs nothing invoked. Under a pin, the justifying condition below (the project that wrote it is the project reading it) is false by design, so the writer is another of the instance's workers. The emitter does not key on that: it reduces, caps, indents, and frames the project index in every state, which is stricter than the rule below requires. That is deliberate and should not be "corrected" toward the looser rule, because the block's own trigger is the widest in the hook and a per-state fence would be one more branch to get wrong.

Those nine hops (the table's six rows, plus the run-scoped, pin, and project destination blocks) carry the fence, and the fence rather than the charset is the control on a body. Two further surfaces carry store content at column zero and deliberately do not fence it, both under the same reasoning and both over the project tier alone (find's withheld line, every coverage line, and `unstamped`'s closing verdict also sit at column zero, but they carry counts and figures this tool computed, at most alongside a charset-closed identifier such as the declared type name or the regex-bounded `--since` label, rather than store prose, so no fence question arises for them): `memq find`'s lexical channel, one bounded, charset-closed, quote-stripped line per hit, labelled by tier and never a body, over the caller's own tiers; and `memq unstamped`'s project-tier lines, the same shape over the records this project's own sessions opened. Both are guarded by construction rather than by framing, because a single sanitized line cannot forge a block, and that narrower guard is the claim to check rather than assuming the fence covers it. Both take the fence the moment the reach widens: each command indents its type-tier and operator-tier lines under the full framing line, and `unstamped` also fences its project lines under a store pin, since a pin makes that tier another worker's writing. The narrower guard is tied to the narrower reach, which is why `find`'s semantic channel, spanning every store on the machine, sits in the table above under the full fence rather than sharing this exception. The exposure it leaves is real and worth naming: under a pin, a description another of the instance's workers wrote arrives in the tool's own voice, as it already does for the type tier. The exposure that distinguishes them is frequency rather than guard: the index emission and both digests are automatic, `recall` at every effort start and `recent` at every close-out, and the close-out's after-query runs `find` there too, while a `get` is a deliberate fetch of a named record. Frequency moves how often the exposure is met rather than how wide it is: the narrower guard above is tied to reach, so it holds identically whether the channel runs once or at every close-out.

**The anchor surfaces take a grammar in place of the charset reduction, and that substitution is deliberate rather than an omission.** An anchor path reaching a display line, on `memq get`'s per-anchor lines, on `decay-scan`'s `DRIFT` block, and on the CLI's own anchor refusal lines, does not go through `sanitize` the way a record name or a description does. It goes through `isAnchorPath` at the write door instead, which is a stricter gate on everything except the one axis the sanitizer covers: no whitespace, no C0 or C1 control, no bidi or zero-width character from a named enumeration, no double quote, no backslash or colon, at most 256 characters, and a refusal line strips both unshowable classes and names each reduction it made. What it admits and the sanitizer would not is visible non-ASCII, and that is the point: `sanitize` strips every non-ASCII character, so quoting a refused `src/Übersicht.cs` back through it would name a different file, and a repository with non-English filenames would lose the feature outright. The residual is homoglyph confusion rather than injection, and it is narrower than the enumeration is complete: the invisible class is a hand-written list, so a visible-width-zero character such as U+3164 HANGUL FILLER is admitted. The drift block's record names still take `sanitize`, and a shared-tier record's anchors are answered with fixed text carrying nothing from the record at all, which is what keeps a path from a tier every project on the machine can write out of column zero.

The sync trigger (`memory-session.js`) is a further path into context and needs no fence, because it carries no store-derived text at all. The hook's own checks are read-only git subcommands and never a fetch, so a session start costs no in-hook network round trip and the "behind" figure it may report is what this machine last knew rather than what the remote holds now; the fetch, rebase, and push happen in a detached background runner (`doctor/sync-store.ps1`) the hook spawns off the session's critical path. Every value in an emitted line is an integer parsed out of a fixed count, a boolean read from whether `git status --porcelain` printed anything, or a fixed literal from the hook's own source (a state-file reason code is a lookup key mapped to a fixed literal with a fallback, never emitted text); no path, branch name, remote URL, or state-file string reaches the line, which is stricter than sanitizing and is what makes the fence unnecessary rather than merely absent. Only three states speak at all: a recorded standing-down gate, a failure streak past a week, and a broken sync chain (a spawn that recorded no outcome past a stale window); a healthy sync is silent.

Several conditions gate it, and they gate the spawn more tightly than the line. The store root must hold its own `.git`, checked by a stat before any git call runs, because git discovers repositories upward: without that check a store root merely sitting inside an unrelated checkout would be described as the memory store. Every `GIT_*` variable is stripped from the child environment (not only `GIT_DIR`/`GIT_WORK_TREE`), because a repo-carried `GIT_COMMON_DIR` would otherwise redirect even a `--local` config read at an attacker-supplied config. The background spawn, which commits, fetches, screens, rebases, and pushes, runs only when the store is the kit's OWN repository, established by the local git config key `claudekit.memorysync` rather than the marker-bearing `.gitignore` that also proves ownership elsewhere: a committed file rides into a clone and could be planted, but a `--local` config value is never cloned, so this gate is not forgeable by shipping a repo at the store root. The spawn also runs only at the default `<home>/.claude` root (an environment-overridden root is synced by the operator's own hand, since `os.homedir()` follows the attacker-reachable `USERPROFILE`, so ownership rather than the path is the security gate) and only on Windows, where the PowerShell runner exists. The runner screens the inbound direction as tightly as the doctor's probes screen the outbound: every entry of the incoming upstream tree is checked by its mode and its path against the allowlist before the rebase touches the working tree, so a rename, a duplicate-content push, or a symlink at an allowlisted path cannot materialize a disallowed file (`settings.json`, a credential) in the store root, where nothing un-writes it. The trigger is silent under a store pin the kit cannot honor and under a run-scoped session (a fleet of run-scoped workers each spawning a sync would be contention with no owner), whose own block already claims the whole of what this hook says about where the store stands; it rides beside every other state, a localized pin stand-down included, exactly as the decay nudge does.

The embedder-absence nudge is the same shape and needs no fence for the same reason: it reports whether the local embedding stack is installed, and every word of it is a literal in the hook's own source or the install remedy the doctor and `memq find` share, so nothing store-written or machine-derived rides it. It is gated identically, silent under a stand-down and inside a run.

The anchor-drift line the same hook emits is a third member of that class. Every word of it is a literal in the hook's own source and every value on it is an integer the hook computed, at most three of them: how many project memories anchor a changed or missing file, how many the pass reached and could not settle, and how many its own read budget stopped short of. No record name and no anchor path rides it, which is why the line points at `memq decay-scan` for the detail rather than carrying it. Silence there is reserved for three inputs and each is a true nothing-to-say: an honored store pin, every count at zero, and a memq whose export table has moved, which the hook tests for before it calls anything. A throw is not on that list and answers in its own fixed sentence, because an error boundary that returned the clean answer would be the same defect the three-count split exists to prevent.

**The sync repository's allowlist is the boundary the whole replication design rests on, and it is not self-enforcing.** The store root holds `.credentials.json`, `settings.json`, `history.jsonl`, and every session transcript, so a git repository there is one careless add away from publishing them. The gitignore excludes everything and re-includes only the memory tiers and the machine coordinator directory, admitting only the file forms those tiers write; one leaf set covers both roots, and over the coordinator directory it is wider than that directory's own contract rather than derived from it. The contract names four files, all `.md`, while the shared leaf set also re-includes `*.jsonl` and the path predicate admits `coordinator/` followed by anything, so a `.jsonl` written anywhere under that root by any tool is admitted and replicated to every machine that pulls. But ignore rules alone do not close it: a `.gitignore` planted inside a directory git traverses outranks the root file and can re-include what the root excluded. So the guarantee is the rules plus four direct probes the doctor re-derives on every run, reading the four surfaces a path can reach by, the ignore rules, the worktree, the index, and the object history. Each answers a question the others cannot: a tracked file ignores the ignore rules entirely, and a blob in history survives being untracked. Any drift in the allowlist is a FAIL rather than a warning, and a probe that cannot answer is also a FAIL, because an unproven negative is not a clean one. The commit path refuses rather than repairs: it will not add or commit unless both managed files verify canonical, and it restores the index it found rather than leaving a disallowed path staged.

**The doctor's sync report is a trusted output channel carrying store-derived strings, and one line in it is a command an operator pastes.** Branch names, the upstream ref, the configured `push.default`, and the origin URL are all read out of the store's own git state and printed to the terminal an operator reads before deciding what to do about a broken sync, so each goes through `Get-SanitizedLine` first: bytes outside printable ASCII stripped, length capped at 200, and any truncation marked in the line rather than silent. That bounds what reaches the eye and says nothing about what is safe to run. The one line the report composes as a runnable command, the `git branch -m <local> <upstream>` rename remedy on a name-pair finding, therefore takes a gate of its own rather than resting on the sanitizer: the merge ref must sit under `refs/heads/`, both names must match `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, and both must survive sanitization unaltered. Git permits `;`, `&&`, `|`, `$()` and quotes in a branch name, every one of them printable ASCII, so a store branch named `main;calc` would otherwise render a remedy that runs `calc` when pasted. A leading `-` is barred for a different reason: it carries no shell meaning, but git reads it as an option, so a branch named `-f` would compose a forced rename that clobbers an existing ref. Where any clause fails, the finding is still reported in prose with no runnable command. On the read side the doctor's git invocations pass an argv array with no shell, so a hostile branch name reaches no second command and no config key. One disclosure is outside all of that: the report prints the origin URL as configured, so a remote in the `https://<user>:<token>@host/path` form puts the token on screen and into whatever the operator pastes into a chat or an issue. `docs/backlog.md` carries the redaction item.

**Project-tier output is unfenced only while the project that wrote it is the project reading it.** That is the whole justification, so it holds exactly as far as the condition does. Under a store pin the condition is false by design: one tier serves every repository the instance works in, so a memory written while working one repo is read back by a session working another, and the writer is a spawned worker rather than the attended session reading it. That is the same sentence this document uses to justify fencing the pending tier, so pinned project-tier bodies and pinned digest records carry the fence too. The decision is keyed on whether a pin is in effect, never on the tier's name, because the name is precisely what stops being a reliable signal.

One record type is outside that rule today: `recall`'s journal lines print at column zero under a pin, each carrying the latest summary another of the instance's workers wrote for that key. `recent`'s journal lines are fenced, and the two differ because the surfaces differ in size, one line per key against one line per entry inside a window. The residual is real and narrower rather than absent, and it runs more often, since `recall` fires at every effort start. `docs/backlog.md` carries the item.

A second, narrower residual sits on `recent`'s framing line. The line is decided from the type-derived records the digest built, not from the ones that survive the budget cut, so a pinned digest whose every type line was cut still names the type tier in its provenance line. The direction is over-claiming provenance rather than under-fencing content: no line loses its indent, and every fenced line still rides under a fence.

## Storage properties

Plaintext. The three memory tiers and the machine coordinator directory are versioned: `~/.claude` is a git repository once the sync repo exists, and that repository replicates to whatever remote is configured for it, nothing in the kit reading that remote's visibility or refusing a public one, which The coordinator board section below states at length and which this sentence deliberately does not narrow back to a private one. The coordinator directory is versioned without the merge attribute the tiers carry: `Get-MemorySyncAttributesText` names `merge=union` for the three tiers' `.jsonl` files and for nothing under that root, while two of its four file forms are multi-writer across machines by their own contract, so an ordinary concurrent append there takes a content conflict rather than a union merge, at the blast radius the conflict paragraph above describes. The single-generation `.bak` written before a rewrite is the only local recovery for an overwritten memory, and the next rewrite of that file overwrites it; that is unrelated to, and much weaker than, what git itself now retains. Two paths back up a memory record itself, being the two that overwrite one. The shared-tier body repair (`add-type`/`add-operator` with `--update`, a body flag, and `--confirm-shared`) is the first. The second is `memq anchor`, which rewrites one project-tier record's `anchors:` line and leaves a `<name>.md.bak` beside it holding the record as it stood before the rewrite. That backup is worth knowing about for what it is not: no listing surfaces it, and a successful anchor names it nowhere, the clause that reports a backup riding the verb's failure line only. It holds the pre-rewrite text of a record whose body the verb never touched, so what it exposes is the same body already live one file over rather than anything new, and `*.bak` sits in the sync's never-sync patterns, so it stays on the machine that made it. The other locked rewrites leave a backup of what they rewrite rather than of a record: `decay-prune`, the create path, the `--update` repair of a description or a body, and both delete verbs each take one beside every index, journal, or sidecar file they rewrite, and `decay-prune` moves a record rather than overwriting it, so it has no record backup to leave. Those `.bak` files never leave the machine: `*.bak` sits in the sync's never-sync transient patterns, so the recovery is local only. A record removed by `delete-type` or `delete-operator` leaves no local recovery the verb can name, deliberately, and that holds for the index and sidecar backups as well as for the record: any confirmed run reaching its end, including one that finds no record left to remove, removes the backup beside each of those three paths, whoever wrote it, which also spends whatever single generation any other record in that tier had there, a spend the command's own output does not report, on the reasoning that a copy of a body the operator just destroyed is the archive the verb exists not to leave, and an index line for a record authored without a body flag carries that whole body. Three things leave a backup- or temp-shaped copy of the removed record and nothing else does, the git history above and the vector index and transcripts the Not-claimed section covers lying outside the verb's reach entirely: a delete that stopped before its closing sweep, where the backups are the recovery for a rewrite that did not land; a completed delete whose sweep could not remove one, which is named on stderr and deliberately does not fail the command, so a zero exit is not on its own evidence that the residue is gone; and a `<file>.tmp.<pid>` a hard-killed rewrite stranded at one of those paths, which the sweep does not name and which the Not-claimed section below describes.

Removal replicates asymmetrically, because the sync's merge policy differs by
file. A record file and the `MEMORY.md` index lines are ordinary tracked
content, so a delete propagates as a deletion and a rewrite exactly as an add
propagates as a creation. The usage sidecars do not:
`memory-types/**/*.jsonl` and `memory-operator/**/*.jsonl` carry
`merge=union` in the store's `.gitattributes`, which is what keeps two
machines' concurrent appends from colliding, and union merge has no way to
express a removal. A delete's removal of a record's usage stamps therefore
holds on the machine that ran it and is undone for any stamp another machine
still carries, which returns at the next merge touching both sides. What
returns is a name and a timestamp in an applied-stamp line, never a body, and
the record those lines counted is gone from every tier; what it means is that
the stamp removal is local hygiene rather than a replicated guarantee. That
matters because the stamps are not inert. A record created later under a
removed record's name inherits any applied history that came back, and an
applied history extends decay thresholds by 30 idle days per distinct applied
day up to the 365-day cap, so a fresh record can outlive the retention policy
written to retire it. The recycled name is reachable rather than theoretical:
the create path's duplicate check reads the live file only.

A delete meeting a record another machine has since modified is a git
modify/delete conflict, and the store's sync handles it by standing down
rather than by choosing a side. The background runner's rebase fails, the
run aborts it so the worktree is left exactly as it was found, and it records
`transient` with reason `pull-conflict`
(`plugins/claude-kit/doctor/sync-store.ps1`). Nothing is lost and nothing is
silently resolved, which is the sane behavior; what is worth knowing is the
blast radius. The stall is the whole store's, not the conflicting record's, so
until someone resolves it by hand that machine stops syncing every tier, every
project, and the journal along with them, behind a soft nag rather than an
error.

A credential, connection string, or token written into a memory file, a journal entry, or any file of the machine coordinator directory is committed, and on a store with a remote pushed, with no further deliberate act: on Windows the background sync runner does both at the next session start, and the doctor's `-Fix` does both on demand. From there it persists like any other tracked content: a later edit or local delete leaves the earlier blob reachable in history, and once pushed it reaches the remote object history too, recoverable by anyone who can read that repository until the history is rewritten everywhere that cloned it and the credential rotated. The sync boundary is path-shaped rather than content-shaped: the allowlist probes prove a path sits inside a memory tier or the coordinator directory and takes one of the admitted forms, and nothing on the commit, push, or check path reads a byte of content looking for a secret. The only control preventing the write in the first place is the instruction in the `memory-system` skill telling the model not to record one, and that instruction reaches the memory tiers alone, because it is an instruction to that skill's writers and the coordinator directory's writers are seats, a Stop hook, claim-writing subagents, and inbox appenders, none of which load it to write a board line, a registry entry, a claim, or an inbox request. Nothing states the equivalent for that directory. Its own content rules are per file form rather than one rule over the directory, and none of them is about secrets. The board bars The coordinator board section below states, no absolute path and none of the operator's words, reach the board alone and bound two named disclosures rather than content in general. A registry entry takes its own bar from the role skill's contract, and that one is conditional: an absolute `Workdir:` is permitted where the operator has answered who reads the store's remote, the default state being unanswered. The claim file and the Admin inbox carry no content bars at all. So a credential in a board line, a registry `Status:` line, a claim, or an inbox request is refused by nothing and syncs like any other admitted content. Sync does not weaken the memory-system instruction where it reaches, but it changes what a lapse costs: what stayed on one machine now reaches every machine that pulls. There is no redaction, no scanning, and no mechanical guard, on write or on sync.

## Environment overrides, and why they differ

Variables that redirect where the tooling looks are gated, and so is the one below that redirects nothing and steers a control's timing instead; all of them are deliberately gated differently:

- **`KIT_MEMORY_ROOT`** relocates the store root, and is honored only when `KIT_MEMORY_ROOT_ALLOW_DATA` is also set. It selects *which data reaches the model*, and, since the `memq-grant` hook below conditions on the same pair, it also selects whether one fixed Bash command shape bypasses the host's permission prompt. That second consequence is newer than the gate's original data-only rationale, and it is why the pair is now load-bearing for execution and not only for content. A third consequence is the background sync's: the auto-sync spawn is gated both to the default `<home>/.claude` root and to a store the config key marks owned, so relocating the root with this variable does not arm the automatic commit-and-push against the relocated directory. That is deliberate, and it is why the gate is ownership rather than the path: `os.homedir()` follows `USERPROFILE`, which is attacker-reachable, so a path check alone would move with the attacker while the un-clonable config key does not. Set without its signal, it is ignored, the real store is used, and a note goes to stderr.
- **`KIT_PLUGINS_ROOT`** relocates the plugin payload the `memq` shim executes, and is honored only when `KIT_PLUGINS_ROOT_ALLOW_CODE` is also set. It selects *which program runs*.
- **`KIT_RUN_ID`** routes a run's memory writes into the pending tier and scopes its reads to that tier plus the main one. It is honored only alongside the `KIT_MEMORY_ROOT` pair above, and carries no separate signal of its own because it selects a subdirectory *within* an already-gated store: the store's gate is the one that decides whether the redirection happens at all. Set without those signals, the memory routing is ignored, the session behaves as an ordinary attended session, and a note goes to stderr. One deliberate exception to that word: a goal-release event still carries the id in its `run` field, since the field is correlation metadata on an outbound record rather than a routing decision, and it is validated by the same grammar. The value becomes a directory name, so it is validated against a conservative token grammar that also refuses the Windows directory-name shapes that alias onto a different directory than they spell (dots-only names, trailing dots, reserved device stems) and is folded the way the platform's filesystem folds it. A value that fails the grammar is refused rather than fallen back on, because a silent fallback would place an unadjudicated write in the shared record.

- **`KIT_MEMORY_PROJECT`** replaces the `projects/<segment>` directory name, which is otherwise derived from the working directory, and is honored only alongside the `KIT_MEMORY_ROOT` pair. Like `KIT_RUN_ID` it carries no signal of its own, because it selects a directory *inside* an already-gated store. It exists because an engine instance spawns workers with three different working directories (a plan worker runs in the repository it is working on), so without it one instance's store fragments into a tier per cwd and a memory promoted out of a plan run lands where no later run and no reviewer reads. Set without the store pair it is ignored, the cwd derivation stands, and a note goes to stderr; set with the pair and unusable as a directory name it is refused loudly rather than falling back, since a silent fallback would scatter the instance's memories back across per-cwd directories invisibly. It answers the same grammar `KIT_RUN_ID` does, from one shared predicate.
- **`KIT_EMBEDDER_ROOT`** relocates where the optional embedding stack is loaded from, and is honored only when `KIT_EMBEDDER_ROOT_ALLOW_CODE` is also set. It selects *which program runs*, the same class as `KIT_PLUGINS_ROOT` and deliberately not the data class: the install location is spelled from the home directory rather than from the store root, so a store redirect gated as data can never move where code loads from. The stack is located by a direct file check rather than by module resolution, because resolution walks upward through parent `node_modules` and would make "installed" depend on where the process happened to start. Set without its signal, it is ignored, the real location is used, and a note goes to stderr.
- **`KIT_EVENTS_PATH`** redirects the goal-event sink `emitGoalEvent` appends to, and is honored only when `KIT_EVENTS_PATH_ALLOW` is also set. Unlike the others it selects *where data is written* rather than what reaches the model, which is true of the variable and not of the stream: the coordinator seat's BLOCKED funnel reads `~/.claude/kit-events.jsonl` and briefs the operator from what it finds, so that file is content reaching a session as much as an outbound feed an external watcher reads, and the funnel treats each entry as a claim to corroborate for exactly that reason. The gate is unaffected by the correction, because the variable steers the writer's sink while the seat reads the fixed path, so a redirected writer cannot plant what the seat reads. What a redirected writer can do is silence, and the consequence is stated here because it is stated nowhere else: a repo whose environment carries the pair sends its own sessions' goal events to a file the funnel does not look at, so the dead-worker backstop is off for that repo's sessions, which the funnel's standing honesty about an absent event never proving an absent blocker already covers and which nobody reading either surface alone would derive. Set without its signal, it is ignored, the real `~/.claude/kit-events.jsonl` is used, and a note goes to stderr. The intended users of both signals are the repo test suite and the hook canary's own goal probe, which point the stream at a throwaway file. What the signalled override grants is worth naming exactly, because "sink" understates it: the named path is appended to, and past 1 MB renamed to `<path>.old`, replacing any previous file of that name. Pointed at a regular file the user can write, a goal release therefore appends to it and can move it aside. A symlink or junction at the sink is refused (the regular-file check is an `lstat`, and a hardlink is a regular file that passes, deliberately), and the rest sits inside the accepted framing above, that the gates remove accidents rather than contain a deliberate actor.
- **`KIT_MERGED_PR_GUARD_NO_DEADLINE`** turns off the deadline on the merged-PR push guard's `git` and host-CLI queries, and is honored only when `KIT_MERGED_PR_GUARD_NO_DEADLINE_ALLOW` is also set to `1`. It is the one variable in this list that redirects nothing: it steers a control's timing, and it takes the same gate because here the timing is the control. Every way that guard's queries can fail ends in an allowed push, so a deadline short enough to time them all out would be an off switch for a deny guard, silent and indistinguishable on every surface from a healthy allow. What closes that is the switch's shape rather than its gate: it is a boolean carrying one direction, and that direction is toward waiting longer. Honored, each query runs under `execSync`'s `timeout: 0`, which is how Node spells no deadline; unhonored, each runs under its own production budget, which is per-query and never shared (3 seconds for each git read, 8 for the host query, so a four-query invocation's worst case is 17 seconds). Removing a deadline can only remove `ETIMEDOUT`, and `ETIMEDOUT` is one of the paths that ends in an allowed push, so no setting of this pair can stand the guard down and the honored setting can only make it more likely to block. The gate is uniformity with the rest of this list rather than this guard's safety, and it earns its place by letting a reviewer check one property across every kit override instead of re-deriving a per-variable argument; the same uniformity decides what a value other than `1` means, which is nothing at all, so `NO_DEADLINE=0` reads as no request rather than as a refused one. What the honored setting costs is an unbounded wait, and what bounds it is the caller rather than this hook: the only intended caller is the repository's test suite, which spawns the hook under its own `spawnSync` timeout and so holds the ceiling itself. The switch exists for that suite, which spawns the hook and a faked host CLI on a box under parallel load and so pays spawn costs a developer's machine never does, where a query that overran was read as a missing block. Set without its signal it is ignored, the production budgets stand, and a note goes to stderr, written once per process and only on the allow path, so it never rides alongside the reason a denial feeds back to the model; an invocation that consults no query at all (a non-push command, or a push whose own refspec names develop, main, or master) writes no note, because nothing read the switch; the configured-default exemption and a bare `git push` each reach a git read before deciding, so those write the note like any other consulting invocation.

**What the gates buy, stated plainly, because the uniform rule invites over-reading.** An actor who can set one variable from a committed file can set two in the same file, so against the repository-as-distribution-channel threat above, a second signal is not a mitigation. What it does buy is real but narrower: one auditable rule that holds across every override, so a reviewer checks a property rather than re-deriving a per-variable argument, and the elimination of the accidental case, where a variable set for an unrelated reason or inherited from a parent process silently steers a session. Read the gates as removing accidents and making deliberate redirection legible, not as containment.

**The ungated residual under all of them.** Every default path above ends in `os.homedir()`, which reads `USERPROFILE` on Windows and `HOME` on POSIX. One of those, set from the same committed file, relocates the store, the plugins root, and the event sink together, with no second signal anywhere. The Principals section places an actor with write access to `~/.claude` outside every control here; this is the adjacent case it does not state, an actor who redirects what the kit believes `~/.claude` is. It is a broader compromise than any single override (the harness's own settings and transcripts move with it), which is why no gate here addresses it, but a claim that every path-redirecting variable is gated is only true one level down from this one.

**`KIT_EXTERNAL_ENGINE`** redirects no path and carries no gate, and it is one of three deliberately ungated behavior-steering variables here (`CLAUDE_CODE_SESSION_ID` and `KIT_GOAL_STOP_RETRY_MS` follow below), because an external engine must be able to declare itself on a spawn it already fully controls. Set to `1` it stands these hooks down: `session-start.js` drops its drive-to-completion push, `branch-reaper-nudge.js` and `kit-version-nudge.js` go silent, `hook-canary.js` returns before its first probe, `chapter-boundary-nudge.js` emits no reminder, `compact-deferral-nudge.js` neither emits nor stamps (and writes nothing either, its guard returning before the interval stamp rather than after it, which matters because that hook takes its stamp first and emits only if the stamp landed), and `kit-compact-gate.js` allows every auto-compaction (the compaction-gate section below carries why that is a scope decision rather than a lost control). `stop-docs-hygiene.js` also downgrades its block to advisory. Two consequences belong here rather than in the architecture doc, because they are the loss of controls this document credits elsewhere: the canary's integrity check (the SHA-256 manifest comparison) and its `memq-grant` both-direction probes do not run under the marker, so in a fleet worker neither the tamper detection nor the grant's health check is active, and the Stop-scan backstop for scratch reaching `docs/` becomes advisory. Setting the marker is therefore enough to turn off the detection this document describes, without any second signal. That is accepted rather than mitigated: the actor who can set it on a session is the actor who spawned that session, and the controls it disables all report to an attended operator who is not present in a spawn. What it means for the reader is narrower than it sounds and worth stating exactly: the manifest check protects an attended machine against a hook edited in place, and it has never protected a fleet worker, whose payload integrity is the deploy's concern.

**`CLAUDE_CODE_SESSION_ID`** is the second deliberately ungated behavior-steering variable, and the only one here the kit does not own: the harness sets it in every tool shell it spawns, naming the session the shell serves. Two readers steer two different things with it. The `/kit-goal` CLI's `arm` steers the leash binding: an arm run inside a session binds that session at arm time instead of arming unbound and waiting for a claim point. The compaction checkpoint CLI's release verbs steer which session a release marker names, and they gate the value more weakly than `arm` does, on character set and leading character alone with no corroboration against a real transcript. The weaker gate is tolerable because the worst a wrong value reaches is a compaction's timing, where a wrong leash bind holds a real run. It is not inert, though, and the two wrong-value cases differ. A marker naming a session that offers no compaction releases nothing and ages out. A marker naming a live session releases that session's next deferred compaction, which is the cross-session reach the release-marker paragraphs below state. The variable is undocumented upstream and is not what a dispatched subagent's shell can be trusted to carry, so a marker written from one may name a session other than the writer's, and whether that is inert or effective turns on whether the named session is live. No second signal gates it, because the pairing rule above exists to remove accidents, and the accident case here is handled by corroboration instead: the id binds only when it is UUID-shaped and a transcript file with that basename exists under the harness's transcript store, checked before anything is written, so a stale export, an inherited value, or a repo-committed terminal env carrying a UUID that names no real session on this machine arms unbound and falls back to the claim points, exactly as an arm with no variable at all. What the corroboration cannot refuse is a value naming a real transcript on this machine that is nonetheless not the arming session; that binds a leash no session enforces, is visible in the arm output's binding report and in `/kit-goal status`, and re-arming recovers it, the same bounded, recoverable blast the claim predicate's accepted risk below states. Two smaller residuals ride with the mechanism: the transcript scan can store another project's transcript path in this repo's `.kit/goal-state.json` when the id's first match lies elsewhere (the path is never surfaced, per the goal-state section below), and the scan composes its candidate paths from `os.homedir()`, which the ungated-residual paragraph above already places outside these controls. The variable is undocumented upstream and can change or vanish without notice; either direction degrades to the unbound arm and the claim points, never to a wrong bind.

**`KIT_GOAL_STOP_RETRY_MS`** is the third and the narrowest. It replaces the completion leash's re-read schedule in `kit-goal-stop.js`, the short delays that stop the hook concluding from a single read while the harness is still appending the turn's final assistant entry. It carries no gate because the code reading it bounds both ends of what it can do: each delay is clamped to 5 seconds and the schedule to 5 delays, so no value pins a synchronous hook to its timeout, and the hook's top-level call is wrapped so that any error allows the stop. What a hostile or accidental value buys is therefore the opposite of a disabled control in the sense the guards above use: disabling the retries makes a leash release slightly more likely, never less, and the leash is guidance enforcement rather than a security boundary. It is listed here because a claim that every behavior-steering variable is gated is only true of the ones that can cost something.

Two further variables, **`KIT_SPAWN_VECTOR`** and **`KIT_RUN_SECTION`**, redirect nothing. They are recorded as provenance in a pending memory's frontmatter, reduced to bounded printable ASCII at the write boundary so a value cannot forge an additional frontmatter field or break the document's structure.

No gate may be loosened to match another, and the reason the store root carries one at all is worth keeping: it was originally ungated on the reasoning that it redirects data rather than code. The project-type tier voided that. The SessionStart hook reads the store, so a redirected root supplies content a session sees before the user types, which makes it a behavior-shaping input and not merely a data path.

The precondition the old gate rested on was **the launching environment is trusted**. In a deployment where repositories sync across machines, accounts, and people, that precondition does not hold: a committed `.vscode/settings.json` (`terminal.integrated.env.windows`), a `devcontainer.json` env block, or an `.envrc` sets environment for whoever opens the repository. The gate exists because cloning a repository must not be enough to steer what a session reads.

## The `memq.cmd` residual

On Windows, `memq` resolves to a different wrapper per shell: PowerShell resolves `memq.ps1` (arguments splat directly onto node), Git Bash resolves the extensionless `memq` (`"$@"`), and only a caller inside `cmd.exe` reaches `memq.cmd`.

`memq.cmd` forwards arguments as `%*`, which `cmd.exe` substitutes into the command line before parsing it. An argument carrying an odd number of double quotes therefore ends the quoted region, and a following `&` starts a second command. This is confirmed by probe, not theoretical.

What covers it: the `memq.ps1` and sh wrappers keep the two common shells off that parser entirely, `memq` strips double quotes from free-text fields at the write boundary, and the skill instructs the model to compose summaries itself rather than pasting raw tool output into an argument.

The limit of that coverage: the write-boundary strip protects stored *summaries and descriptions*, not memory *bodies*, which are length-capped only.

For bodies specifically, `--body-file` takes the text off the command line altogether: the argument is a path, and the content reaches memq through a file read rather than through any shell's parser. What that removes is the composing hop, and that much is a property of `--body` alone, so a body of any composition should take the file channel. It does not remove the residual this section closes on: a body reaches the store unstripped whichever channel wrote it, so what `get` hands back can still carry the command break onto a later command line. What the file channel adds in its place is an encoding surface the argv channel does not have, since a file holds bytes no command line could carry. On the file's content it answers that surface and only that surface, the channel's path-text, file-shape and size guards being a separate matter: a UTF-16 file, a file that is not valid UTF-8, and a file holding a NUL byte are each refused by name, a UTF-8 byte order mark is stripped, line endings are normalized, and the result meets the same cap gate `--body` takes. Body *content* stays ungated on both channels, which is the standing position stated above rather than anything this channel changes: the fence `get` puts around another writer's body is the control there, not the charset.

This one is rated higher than a single-operator store would warrant. With a shared kit and a shared type tier, a body one person wrote can reach another person's command line, so the exposure is no longer bounded by one operator's own paste.

## Locks are availability, not integrity

The lockfile serializes rewrites of shared files. Two properties to know:

- A lock path can be wedged by a directory, or by a file whose contents are valid JSON but not a lock record, either of which the stale-break correctly refuses to remove. There is no in-tool recovery; the fix is deleting the file by hand.
- Whether a locked rewrite copies bytes that appeared past its read is stated by each call rather than defaulted, and the helper refuses a call that states nothing. The files with a lawful lock-free appender take the copy: the outcome journal, the usage sidecars in every tier, whose read-stamp hook appends without the lock by design, and the project tier's own index, whose lock-free writers the next two bullets name. Growth alone does not establish an append, because the whole store syncs and a pull replaces a file while holding no lock this module takes. So the head check is not the copying caller's to opt into: every rewrite reads the file back first and fails, with nothing written, unless the bytes the pass read are still that file's head, in preference to republishing a stale copy of every line the pass did not touch. What the per-call statement decides is the narrower question of whether bytes found past that head are carried forward or dropped. A window remains between that copy and the rename in which one concurrent append can be lost, which is one usage stamp and matches the tolerance the sidecar's readers already carry for torn appends. A caller that is removing a record also states what the carried tail may not bring back, so a usage stamp for the deleted name cannot ride back in past the rewrite that dropped it.
- The two index files are decided per tier, not per name. In the shared tiers nothing appends to them lawfully and a sync pull replaces them whole, so a rewrite there takes itself as written; the project tier's own index does have lock-free writers and keeps the copy. What the shared-tier choice gives up is stated rather than implied, and a pull landing inside that window is no longer last-writer-wins. One that replaces the file whole loses instead: the head check fails the rewrite with nothing written. One that only appends, which is the shape another machine adding a memory produces, leaves the bytes the pass read as the file's head, so the rewrite proceeds and drops what was appended, that being exactly what this choice declines to carry.
- The shared tiers' usage sidecars have both properties, and so does the project tier's sidecar. They keep the copy, because the read-stamp appender is the common case and the rebase collision is the rare one. The project tier's own index keeps the copy for a different appender: `merge=union` covers the store's `*.jsonl` files only, so `MEMORY.md` gets no union merge, and what makes it append-friendly is that a session's Write tool adds an index line beside a memory it just wrote, and a reinstatement restores one by hand, both lock-free by design. The residual is stamps a prune had just removed coming back, which is the same reinstatement the union merge produces anyway. A rebase result that no longer carries the read bytes as its head is not spliced at all: the rewrite fails with nothing written, and the same command run again rebuilds from the file as it stands.

## Hooks fail open, and what that costs

Every kit hook swallows errors and exits 0 silently, by design: a hook bug must never trap a session. The monitoring consequence follows directly and is easy to miss.

**Absence of a nudge, a stamp, or a warning is not evidence of health.** A hook that cannot run, cannot resolve its dependencies, or cannot write produces exactly the same observable output as one with nothing to say. The hook canary exists because of this, and it probes cache consistency rather than correctness.

## The guard hooks

Six PreToolUse hooks mechanically enforce the agent access model: five guards that deny, and one grant that allows a single fixed command shape. Each is the teeth under a skill's routing wording, and none is a security boundary: by the Principals section, every agent runs as the one machine principal, so the guards defend the work against well-intentioned-but-wrong agent behavior (a reviewer "fixing" the code under review, an implementer writing reports into the curated docs tree, a push stranding records off a merged branch, a memory record landing in a shape the store cannot read), not against an attacker.

- **`readonly-agent-guard`** holds the state under review immutable, by agent class. Strict agents (adversarial-reviewer, blind-reviewer, security-reviewer, council-member, design-facilitator, consultant, blind-reader, prose-reviewer) get a read-only repo tree: writes, file mutations, git and GitHub state changes, package installs, and formatters are denied. The gate-runner (qa-verifier) builds and runs suites, so it may write and delete freely inside a fixed list of build-output directory names (bin, obj, TestResults, node_modules, .vs). Outside those directories it may still bring into existence a file that does not already exist, by `touch`, by `New-Item`, or by a copy to a fresh path (test scaffolding needs that), but not by any content-writing spelling: a redirect, `Set-Content`, `Add-Content` and `Out-File` are denied at a fresh path exactly as at an existing one. It may not modify the content of, overwrite, delete, move, or rename anything existing, though `chmod` on an existing path is allowed it and the exec bit is tracked state; a stray created file leaves a tracked-tree delta the review bracket sees, or an untracked entry `git status` shows. Every other agent type and the main session are untouched, and `.kit/` (gitignored) is scratch both classes may write. Command text is judged against a quote-masked copy in which every command substitution bash would perform, at the top level, inside double quotes, and standing in an arithmetic operand alike, is blanked whole to a sentinel and its interior collected and scanned as a command of its own, with nested executor payloads descended recursively within a depth bound, and containment against the git root above the payload cwd. A substitution or an executor payload that the depth bound leaves unexpanded is unresolved rather than absent, and denies. git's own command-line alias surface denies on the same rule and is bounded at the config key rather than at the value: `git -c alias.<name>=<value>` and both `--config-env` spellings of an `alias.` key put the real verb inside a config value, which is data to the shell and a command to git, so the quote mask is right about it and cannot be what bounds it, and the subcommand is simply unresolvable from the command line. The rest of that class is residual rather than covered, and is named because the bound that works for an alias does not reach it: `core.pager` carrying a bang, `core.sshCommand`, `core.fsmonitor`, `credential.helper`, `diff.external`, `uploadpack.packObjectsHook`, and an `include.path` naming a file that sets any of them each run a command from a config value too, and every one of them allows, because keying on those names would deny the everyday review spelling `git -c core.pager=cat log` and bounding them needs a value-shape rule this instrument does not have. Coverage extends to a second dispatch route on one condition. On v2.1.205, established by probe rather than inferred, an agent dispatched through `Workflow`'s `agent()` with `agentType` naming a governed kit agent carries that identity into the PreToolUse payload, so its policy class resolves and the guard governs it exactly as under an Agent-tool dispatch; the named agent's frontmatter `tools:` list applies alongside its prompt, so the named agent holds no write tool on either route. Both halves are load-bearing, because the read-only property rests on two controls at once: `hooks.json` matches this guard on `Bash` and `PowerShell` only, so a strict agent's inability to write is held jointly by the guard denying write-shaped shell and by the `tools:` list withholding Write and Edit. A dispatch that omits `agentType` presents as `workflow-subagent`, resolves to no policy class, and loses both controls together rather than only the guard; what default toolset such an agent receives is unprobed and must not be assumed read-only. That condition is why the doctrine's Workflow grant and both skills' dispatch templates require the field.

  One command shape is exempt from that command-position scanning, and its residual is stated rather than closed. Where the entire command is a single simple command whose whole content is one `cat` or `tee` writing one quoted-delimiter heredoc into the class's own writable set, or to a destination outside the git root entirely, the body is data and is masked rather than scanned, so a reviewer writing a report about `git push` or `rm -rf` is not blocked by its own subject matter. Anything outside that one shape leaves the body's command positions scanned. Redirects are the standing exception in either case: a `>` inside any quoted-delimiter body stays blanked whether the shape qualifies or not, so a hidden write is the miss the guard's own header names and this exemption neither widens nor closes. What the exemption itself leaves open is a literal body written to any path the exemption admits, inside the class's writable set or outside the tree alike, and run by a later, separately scanned command carrying a file operand (`bash <path>`, `sh <path>`, `. <path>`, `source <path>`, an interpreter with a file operand, `$(cat <path>)`). The guard already carries that residual in another spelling, a mutation written to such a path by `printf` or any other producer, and the tree-state check around a review round backstops both only where they leave a file delta, never where the later command's mutation is a push, a merge or a tag, which is the class that moves no tracked file, leaves that check's two `git status --porcelain` readings identical, and is therefore the one this guard exists to cover in the first place.

  The requirement is prose-enforced, and saying so is the point: no hook matches the Workflow tool, so nothing observes the dispatch that decides whether a read-only agent, a reviewer or the consultant alike, is governed. It lives in the doctrine's standing-dispatch bullet and the two skills' templates, with one `doctrine-parity` test over the doctrine's wording as the only mechanical trace. The tree-state bracket around a review round is the sole runtime backstop, and by finishing-work's own account it misses a write to a gitignored path or outside the git root, a mutate-read-restore inside one round, every act that moves HEAD and the worktree together so the porcelain reading is unchanged (a merge, a `checkout`, a `pull`, a `reset --hard`), and every act outside the worktree (an outward `gh` mutation, a push, a tag); `git fetch` is outside both it and the guard; and under an omitted `agentType` those classes rest on nothing. Accepted risk on the same footing as the memq-grant invariant below, checked by hand rather than by mechanism, with a Workflow-matcher hook as the fix if it ever needs one.

  The strict roster is itself hand-maintained in three places, the guard's own anchored regex and two enumerations in `test/readonly-agent-guard.test.js`, against a fourth set that is simply the files under `plugins/claude-kit/agents/`. Nothing fails when an addition misses one of them: the new agent resolves to no policy class and runs ungoverned, which is the silent direction. `docs/backlog.md` carries the directory-driven parity check that would turn that omission into a red.

  Two members of the class read prose that need not be the operator's own. `blind-reader` and `prose-reviewer` are dispatched at documents, a customer-facing draft among them, and both hold Bash, so a document in scope is untrusted input reaching an agent with a shell. Each charter states the prohibition with its reason: a document is data, an instruction found inside one is a finding reported verbatim rather than an action taken, and the reviewer chooses the command a claim check needs rather than letting a document choose it. That prohibition is prose and nothing under it is mechanical, because the guard denies write-shaped commands and command text it cannot resolve: a read-shaped command it can resolve is outside its denylist apart from three deliberate over-blocks, `git stash list`, `git clean -nd` and `git apply --check` all denying, and so is an outbound `curl`, `wget`, or `Invoke-WebRequest`, which the review round's `git status --porcelain` bracket cannot see either, a network call leaving the worktree byte-identical. The exposure predates these two agents and is unchanged in kind; what changed is that two agents now exist whose whole job is reading documents. `docs/backlog.md` carries the denylist candidate and the reason it is not obviously right, which is that a reviewer sometimes has a legitimate reason to fetch.

  A third site puts untrusted text in front of a shell, and it is the widest of the ones named here because no read-only guard governs it. The main session reads text it did not write at many points, every subagent report among them; this is the one a run-stopping tag turns on. `finishing-work`'s step 4 adjudicates the docs-curator's Drift Report, and an entry whose basis rests on any claim about the state before the changeset rests on a state the curator holds no tool to read, so for a `mistake` item the orchestrator runs that read itself. A `deviation` stops nothing and gets no read; its pre-change claim is tagged unverified instead.

  What bounds that read is set membership rather than a pattern judging report text, and the distinction is worth stating precisely because the weaker reading is the tempting one. The curator's `Paths:` token is not interpolated as text: it selects, by whole-token equality, an entry of a changeset listing the orchestrator produces itself (`git diff --name-only --no-renames <base-ref>` unioned with `git ls-files --others --exclude-standard`), and the selected entry is what the read is composed from, passed as a single argument after `--` where the git form takes one. A token equal to no entry selects nothing, and selecting nothing stops the run with its reason stated rather than skipping quietly. Selection is one control of two. The second is a load-bearing token gate that the selected entry passes before it reaches any command: a repo-relative path of ASCII letters, digits, `.`, `_`, `-` and `/`, carrying no leading `/`, no leading `-`, and no `.` or `..` segment, whose rejection is a stated-reason stop rather than a pass-through. The gate may reject a real listing entry, and that direction is deliberate, since an oddly-named honest file costs a stop while the alternative costs a shell. The same pair covers every other curator token a command or a file write consumes rather than the `Paths:` list alone: the `LIBRARY HYGIENE` block's `docs/plans/<file>` paths, selected against the orchestrator's own listing of that directory because a stale plan sits in no changeset of this effort, and the cross-reference block's plan names, which reach an `Edit` rather than a shell. The gate carries more of the weight on the hygiene route, since step 5's archival `git mv` ends in a shell command holding that name as an operand and `docs/plans/` sits under the `docs/` the curator writes ungoverned.

  The honest residual is that equality makes a selected entry byte-identical to the token that selected it, so what the control actually establishes is provenance and membership, not that the text is the repository's rather than the report's. The curator's writes under `docs/` are ungoverned, so a file it creates joins the untracked half of that listing and its own name becomes selectable; and `git show <base-ref>:<path>` takes no `--` to put the path behind. Two exits follow from that, and each has a control of its own. What keeps such an entry from retiring the run-stopping tag is not the selection but the two rules beside it, that a refutation must be responsive to the claim and retires only the pre-change premise. What keeps it from reaching a shell as command text is the token gate above, and quoting alone would not have: a filename may legally contain a single quote, so a name of the form `docs/x'$(echo PWNED)'.md` is whitespace-free, joins the untracked half of the listing, selects itself by equality, and closes the surrounding single quotes when it is composed. The report's prose is held as data by skill wording alone, with no hook beneath it, exactly as the document-reading agents above are. And the `file:line` citations take no screen whatever, being opened with the file-reading tool: that removes the command-injection surface and nothing else, since the read is deliberately unbounded, so a citation may name any file the session can open and whatever it holds enters that session's context as untrusted text.

  One channel at this site is genuinely an interpolation surface and is bounded rather than absent. Curator prose reaches a pull request body, so step 6 passes that body with the host CLI's file form (`gh pr create --body-file <path>`) and summarizes instead where a host has none, and the title is the orchestrator's own words because it rides the command line either way. Whether the pre-change read meets a permission prompt is a property of the operator's settings rather than of anything the kit installs.

Thirteen deny paths sit behind that, and the list is closed by the guard's own set rather than by this sentence: two on the block itself (a block that opens on line 1 and does not close inside memq's line bound, and a fence that is the record's first non-blank line without being line 1), one on placement (any of the six fields memq reads indented under a key other than `metadata:`), one on `tags:` (a key with no inline value followed by `- ` items), two on dates (a `created:` memq cannot parse, and a `pinned:` or `created:` outside the `YYYY-MM-DD` calendar form), two on `anchors:` (an entry the grammar rejects, and a path that escapes the project root), and five on `supersedes:` (a name outside the record-name grammar, the record's own name, a target held only under a variant casing or extension case, a target held only under `archive/`, and a name the tier holds no record of). A command that chains its own `git commit` ahead of the PR create is allowed, and a checkout parked on the default branch or a detached HEAD never denies.
- **`merged-pr-push-guard`** blocks a push to a branch whose PR the host reports MERGED, the stranded-commit trap. Its shell calls are fixed literals with the one variable (the branch) allowlisted before interpolation; that discipline is load-bearing against command injection. It finds the push at a real command position rather than anywhere in the command string, cutting on the separator set `readonly-agent-guard` uses plus the literal backtick that hook masks and this one does not, and admitting the `NAME=value` assignment prefixes every POSIX shell treats as command position, so a push behind a newline, a bare `&`, a subshell, or `GIT_SSH_COMMAND=... git push` is guarded and a following command's operands stay out of the branch it judges. Both error directions are residue rather than coverage. A separator inside a quoted string still opens a command position, which over-detects into a needless query and at worst a needless block. In the other direction, a push the shell reaches through a layer the parser does not model (a quoted string executed later, a backslash-newline continuation between `git` and `push`, an interposed runner such as `xargs`, an alias or shell function) is not seen at all, and neither is any command-position push after the first inside one compound command. `test/merged-pr-push-guard.test.js` asserts the caught shapes and each of those misses by name, so the residue is a recorded decision. The guard's git and host queries run with every `GIT_*` variable stripped from the child environment, the wholesale strip `memory-session.js` takes for the same reason: a repo-carried `GIT_DIR` or `GIT_CONFIG_GLOBAL` redirects every read the block decision rests on. `HOME` and `XDG_CONFIG_HOME` reach the same global config and are not stripped, since git needs `HOME` for legitimate config; `docs/backlog.md` carries that residual, whose worst outcome is a spurious block or the fail-open default rather than any grant.

- **`memq-grant`** is the inverse of the five guards: it never denies, and it emits an allow decision for exactly one command shape so a fleet worker on the engine's write-gated spawn vector keeps the memq CLI for recall and outcome logging. The invariant: a grant is emitted only when the fleet-store signals are present (`KIT_MEMORY_ROOT` with `KIT_MEMORY_ROOT_ALLOW_DATA=1`, checked through memq's own exported `storeSignalsPresent()` so the hook and the CLI share one definition), the command is one `node` invocation whose first argument is an absolute spelling resolving by normalized path equality to this plugin's own `scripts/memq.js` (anchored to the hook's on-disk location, never an environment variable, never a pattern; relative spellings are refused because the Bash tool's shell keeps a working directory nothing pins to the payload cwd, and on Windows a spelling without a drive-letter root is refused because this process and Git-Bash resolve it to different files), the interpreter is positively identified rather than accepted by name (the hook walks its own inherited PATH and grants only when the first `node` candidate realpath-equals its own `process.execPath`, so a PATH-planted node or wrapper refuses; that is the hook's PATH rather than provably the child's, since the shell the Bash tool runs can rewrite PATH, and that residual is a divergence between the two rather than an unchecked interpreter; PATH is not the only channel, though, because that shell persists across calls, so a shell function or alias named `node` defined by an earlier approved call preempts the PATH lookup with nothing this process can observe, and against that one the pin is not weakened but absent, leaving the grant's own store bound as what limits it; the module-preload variables `NODE_OPTIONS`, `NODE_PATH`, and `NODE_REPL_EXTERNAL_MODULE` refuse the grant outright whenever set, since node honors them in the granted child), and the command line is free of shell metacharacters, with the executors banned across the whole line including quoted spans (a `$` and a backtick compose text inside double quotes too), with every C0 control byte and DEL banned line-wide, tab alone excepted, because bash strips a NUL from a command line outright and what a shell and this tokenizer each do with the rest is unspecified rather than agreed, and with word separators restricted to space and tab and the divergent spellings (a backslash outside quotes, a backslash before a quote, an unquoted comment tail, and an unterminated quote anywhere in the line) refused because the hook must never judge different words than the shell builds. The expansion characters are banned too, and where they are banned is the whole of their rule: bash rewrites a brace, a glob, or a leading tilde into a different list of words after a hook has tokenized the line and before the child sees them, so a screen reading one word list while the child receives another is no screen at all. Bash performs none of those expansions inside quotes, so the ban is scoped to unquoted spans: `{ } * ? [ ]` unquoted refuse the grant, and quoted they are ordinary free text, which is what a summary naming a test glob or a description carrying a bracketed note is made of. The tilde takes that span rule with a position rule on top, because only a leading tilde expands: an unquoted tilde opening a word refuses the grant, while a tilde anywhere else in a word is a literal to bash and grants. That last clause is a correctness requirement rather than a concession: refusing every mid-word tilde would withhold the grant over words the shell rewrites into nothing the screens care about, an argument carrying one, a description mentioning one, and a Windows 8.3 short path, which carries its tilde mid-word. One mid-word shape is not literal, and the hook admits it knowingly rather than by oversight: bash expands a tilde after the `=` of an assignment-shaped word and after each `:` within one, so a word of that shape does carry a substitution. What makes it admissible is that the expansion keeps everything before the tilde, so such a word can become neither one of the screened tokens, which are matched whole, nor the script path, which is matched by path equality; what it can become is a longer argument of memq's own, which memq validates. A screen that ever matched a word's interior rather than the whole of it would have to revisit that. That last is not a spelling the grant covers, though, and for an unrelated reason: the script path is judged by resolved-path equality with no realpath step anywhere, so an 8.3 spelling of it is refused at the path check like any other spelling that is not the resolved one. What makes the leading tilde a control rather than a curiosity is that it substitutes caller-controlled content: with `HOME` set to a verb name, a word the hook reads as a bare tilde reaches the child as that verb, which is how a screened shape would otherwise arrive wearing an unscreened spelling. The invariant screens the command's own words as well as its shape, because a shape check alone would hand a worker every verb the CLI has. The subcommand is judged against a list of granted verbs rather than a list of refused ones, and that polarity is the point: a verb memq gains later is withheld until this list learns it, where a refusal list would grant it on arrival and reopen whatever it does. The granted set is `log`, `get`, `recall`, `recent`, `unstamped`, `touch`, `add-type`, `add-operator`, `decay-scan`, `decay-prune` and `decay-done`, which is memq's own dispatch less four. Two of the four are the delete verbs, whose destruction leaves no local recovery the verb can name, the residues being enumerated under Storage properties above. The third is `find`, whose semantic channel requires and runs an embedder package in process from a directory that resolves under the home directory, which is not a thing a hook can screen on, since `HOME` is always set and refusing on it would refuse every command; a test pins the coupling that makes `find` the only such verb, asserting that memq holds exactly one dynamic require past its built-ins, that it is the embedder module, and that it is reached from `find` and nowhere else. The fourth is `anchor`, which rewrites a record in the shared priors, an authoring act on state a worker's writes are otherwise quarantined from; it is withheld at this grant alone, `cmdAnchor` carrying no store-signals refusal of its own, so the allowlist is the whole of what withholds it. Five flag shapes are withheld anywhere in the line, each matched as a whole word or carrying an attached value: `--body-file`, which names a file the CLI reads and admits into a record; `--update` together with `--body`, which is the shared-tier body repair; `--supersedes`, which points a new record at a live one and thereby demotes it in the search ranking and labels it wherever the store is read; `--rollup`, which replaces each expired journal group with one synthetic tally line and discards the prose of every entry in it; and `--drop-malformed`, which rides `--rollup` and removes outright the unparseable usage lines every other read path and every other rewrite preserves. `--supersedes` is the one of the five withheld on which records it can reach rather than on how much it does to one, and it is worth stating apart because its reasoning does not follow the others'. It destroys nothing and the target stays live, fetchable, and unmodified on disk. What is not bounded is its reach: `decay-prune`'s archive flags are refused against a pinned name outright (`archiveTargetsValid`), and a pointer is bounded by no pin at all, while `decay-scan` is granted and prints the pinned count with the first ten names, so a worker with nobody in the loop could enumerate the operator's own exemptions and demote them in one further command. Both of those locks bound the CLI verb and not the field, and a third one now bounds part of the field: `supersedes:` is a plain frontmatter line, so a worker holding file tools writes one into a record without meeting either CLI lock, but `memory-frontmatter-guard` meets it at the write door. On the two shared tiers that guard refuses the write outright whoever is writing, so the reach through file tools there is closed rather than residual. On the project tier it refuses a pointer naming no live same-tier record and allows a pointer naming one, so what survives is a hand-written pointer at a real target, which is the instruction-rather-than-boundary residual the delete paragraph below records, and every read surface honors it. The guard is a hook rather than a boundary and fails open, and its matcher names the three file-writing tools, so a shell redirection into the store meets none of this. On Claude Code that reach includes a project-tier record written with the Write tool, whose frontmatter the harness relocates under a `metadata:` map that memq reads at both placements. The refusals bite in the availability direction as well as the security one, and `docs/fleet-integration.md` carries that half: an engine setting any of the three preload variables ambiently on its spawns silently turns the grant off for every worker, and no worker gets `find` at all. What a withheld grant costs on this vector is the capability and not a prompt, which is the whole reason the hook exists: the Bash tool refuses `node <script>` there and no operator is present to approve a fall-through, so a shape this screen withholds is a shape a fleet worker cannot run. Every withholding here is chosen against that cost rather than against an approval that never arrives.

A further invariant this hook introduces, load-bearing for anything added later: a grant must stay disjoint from every deny guard's command shape. Today it is, and no mechanism checks it, so a new guard or a widened grant is checked against this rule by hand. On anything else it emits nothing and the call falls through to the engine's normal permission flow; its safe failure is silence, the opposite direction from the guards' fail-open-by-allowing. Accepted risks: arguments after the script path are granted along with it apart from what the screen above withholds, which is the five flag shapes plus every word in the verb position that the allowlist does not name, because node hands everything past the script to the script, so the rest are memq's argv and memq's own argument validation is the control there; and the grant is agent-blind, so a strict read-only agent inside a fleet worker gets prompt-free memq writes (`readonly-agent-guard` does not deny memq, which writes the external store rather than the reviewed tree, and its agent classifier cannot be shared without restructuring that hook, while a second copy of the class list is exactly the drift the gated-override rule exists to prevent). The compensating controls, each with the bound it actually has: the grant surface ships in the build manifest like every hook (`hooks.json` rewiring included), so widening it is a stamped edit, and the canary probes the grant in both directions at session start, because a grant hook gone inert never announces itself in use: the allowed invocation must grant, and five withholding probes on Windows, four elsewhere, must each stay silent (a metacharacter-carrying near-miss, a `--body-file` value, a `--rollup`, `find` in the verb position, and the Git-Bash `/d/` spelling of the script path). The probes cover three of the nine withheld shapes, so six have no probe of their own. Five of those six share `--body-file`'s posture, the two delete verbs, a body-carrying `--update`, `--supersedes` and `--drop-malformed`: a second lock stands behind each, so a hook regression on any of them degrades to that lock rather than to nothing, though `--drop-malformed`'s is the CLI's coupling of the flag to a shape this hook also withholds rather than a refusal of its own. Those five are the same accepted risk covering more shapes rather than a new one. The sixth does not share that posture and is the one the probe set closes first: the verb `anchor` is refused nowhere but here, the verb being the operator's own, so a regression on its screen degrades to nothing and no probe would say so; what stands in its place is `test/memq-grant.test.js`, which pins the withholding in the deny direction and runs in the repo suite rather than at session start, and closing that is what the probe set would buy if it grew. Both of those are attended-session controls only. The canary stands down under `KIT_EXTERNAL_ENGINE`, which the engine sets on every worker it spawns, so in the deployment this grant exists for, neither the manifest check nor the grant probe runs. State it plainly rather than counting it twice: the detection covers the machine where a person would act on it, and does not cover the fleet worker.

The quarantine is not a control here, and an earlier reading of it as one was wrong. The grant conditions on the store pair alone, while the run-scoped pending tier additionally requires a valid `KIT_RUN_ID`, so under the store pair without a run id a granted memq writes the project tier directly. Even inside a genuine run the tier bounds less than the word suggests: `log` appends to the project-tier journal and adds a `run` field rather than rerouting, `add-type` writes the shared type tier, and the grant's verb allowlist admits `decay-prune`, which archives memories and rewrites an index. The honest bound is the store: everything a granted invocation does lands inside the redirected store the engine owns, which is why the reach is that store rather than the machine, and it is the store boundary rather than the pending tier that does the containing. That bound is itself a property of the child's environment and not of the hook, so it carries the same caveat the refusal below does rather than standing flatly. The hook reads its own environment and memq reads the child's, and where those diverge the redirection is what is lost: memq falls back to the operator's real `~/.claude`, so a granted invocation reaches the machine's own store rather than the engine's. The two failures are one failure, since the same divergence that unbinds the store also silences the CLI-side refusals, which is why those verbs are additionally screened at the hook, where the argv cannot be forged by the environment the child controls. That bound is a property of memq's own argument surface rather than of the hook, so it holds only while no memq argument names a path outside the store. `--body-file` is refused outright whenever the store signals are present, for exactly that reason: it reads a caller-named path, and a granted worker invokes `scripts/memq.js` through node directly rather than through a wrapper, so it never meets the `cmd.exe` truncation the flag exists to route around and loses nothing to the refusal. Any argument added later that reads or writes a caller-named path has to take the same refusal, or the sentence above stops being true.

A second class of memq argument takes the same refusal, on a different reason. The store bound answers where a granted invocation can reach; it says nothing about how much of the store it can destroy. The risk this grant accepts was written on a reading of `decay-prune` that its archival half supports and its other half does not: an archived record keeps its description in the archive's own index and still answers `get` by name, so nothing an `--archive` flag touches is gone, but `--rollup` on the same verb replaces each expired journal group with one synthetic tally line and discards the prose of every entry in it, and folds each memory's raw applied stamps into one rolled record while pruning its read stamps to the newest, in the project tier and in either shared tier the same call works. It leaves that text in a single-generation `.bak` no sync carries. The shared tiers now carry a whole-body repair and two delete verbs on top of that. That is not a bound on reach but a bound on blast radius, and it exists because the grant is agent-blind and prompt-free: a fleet worker, or a read-only agent holding Bash inside one, would otherwise irreversibly remove a record every project reading that store reads, with no operator in the loop, no archive copy, and, under an environment-overridden root, no automatic git sync to recover from. The `--confirm-shared` gate does not narrow that, because it is a token on the same command line the grant already covers: it is a typo guard, not consent. What the refusal costs a fleet worker is nothing it had before those verbs existed, and the ungated description-only `--update` still answers there. Two properties of that refusal are worth stating rather than leaving an auditor to find. It is CLI payload rather than a wired hook, so it sits inside the manifest gap recorded below: `scripts/` is unstamped, and an in-place edit disabling the refusal is not attested and not reported by the canary. And the hook evaluates `storeSignalsPresent()` in its own process while memq evaluates it in the child, so the CLI half of the refusal binds while those two environments agree, the same structural assumption the interpreter pin already rests on. That assumption is why the refusal is not CLI-only. `grantable()` screens the argv it already holds: the verb position must name one of the granted verbs, and the grant is withheld for `--body-file` anywhere, for an `--update` carrying `--body`, for `--supersedes` anywhere, for `--rollup` anywhere, and for `--drop-malformed` anywhere. Nine shapes are withheld in all: the four verbs `delete-type`, `delete-operator`, `find` and `anchor`, and the five flag shapes `--body-file`, `--update` carrying `--body`, `--supersedes`, `--rollup`, and `--drop-malformed`. Six of the nine have a second lock in the CLI, so a hook regression on those degrades to that lock rather than to nothing: both delete verbs refuse under the store signals, and so do both body-writing shapes and the supersedes pointer, while `--drop-malformed` is an argument error unless `--rollup` accompanies it, so its second lock is that coupling to a shape withheld here rather than a refusal of its own. Three have no second lock and rest on the hook alone. One is `find`, which is why the pin on memq's single dynamic require is load-bearing rather than tidy: it is the only mechanical statement that `find` is still the sole verb selecting code. Another is `anchor`, which rewrites a project-tier record's `anchors:` line at a name the command line gives it, so a worker could re-anchor a memory onto whatever the tree holds now and every drift surface would then report that memory verified when nobody read it; `cmdAnchor` carries no store-signals refusal, the verb being the operator's own, so this screen is the only thing withholding it. The last is `--rollup`, withheld here and nowhere else, because the CLI cannot refuse it on the store signals without taking the archival half of the same verb with it, and archival is the half a fleet worker's decay pass is for. That is the half that survives a divergence, and it survives it only because the expansion refusals above hold: the screen is a content test on words, so it is worth exactly as much as the guarantee that the words the hook reads are the words the child receives. A caller-controlled expansion breaks that guarantee rather than bypassing the screen, which is why an unquoted brace, glob, or leading tilde refuses the grant outright instead of being screened. Withholding is silence rather than a deny, so the call falls through to the ordinary permission flow and the hook stays a pure grant hook. Silence is not leniency here: on the vector this grant exists for, that flow is the Bash refusal the grant was written to route around, so a withheld shape is one a worker cannot run. The flag screen matches a whole word or a word carrying an attached value, so `--body-file=x` is withheld exactly as `--body-file x` is. Today's parser answers `unknown option` to every `--flag=value` spelling, so the attached-value half screens shapes this CLI would reject anyway; it is written that way because the alternative is a screen whose completeness depends on a parser rejection two files away, which is the coupling this surface keeps paying for. The verb screen reads the subcommand strictly as the first argument past the script path, the same position the CLI's own dispatch reads, so no leading global flag can shift a screened verb out of it. A parser that later admits a flag ahead of the subcommand needs the screen widened with it. The gap it cannot see: it judges command text and its own environment, not what runs, so it cannot see what the granted memq process does with its arguments, nor an interpreter swap that happens after the decision, and an engine vector that already allows the command gains and loses nothing from it.

**Every guard fails open on its own malfunction; one of them denies on command text it cannot resolve. The grant fails the other way: silence.** A guard that cannot decide allows the call; a grant that cannot decide emits nothing, which leaves the call to the host's normal permission flow. The two directions are both the safe one for their own hook, and reading either as the general rule inverts the other. A parse error, an unidentifiable agent, an unresolvable path, a missing CLI, or a host timeout allows. One branch runs the other way, and it is named here so the rule above is not read past it: `readonly-agent-guard` denies command text it cannot resolve, a substitution or an executor payload nested past its depth bound and a name with a substitution spliced into it among them. A second branch runs that way too: a destructive cmdlet whose every path operand fails resolution denies where an enumerating cmdlet feeds it, though the same unresolvable operand standing alone allows. Both are deliberate, on the reasoning that a parser fails closed on exactly the ambiguity a bypass exploits, an allow-list's lapse failing open and silently where an ambiguity check's failure announces itself. The accepted risks that follow, per guard:

- The gate-runner's build-directory list is a policy assumption the guard does not check: a repo that tracks real content under one of those names gets no protection there.
- Agent identity comes from the hook payload's subagent-type field; a call the guard cannot positively attribute to a governed agent is allowed.
- A literal payload written to any path the heredoc exemption admits, inside the class's writable set or outside the git root entirely, and executed by a later, separately scanned command carrying a file operand is unseen, whether a heredoc body or a `printf` wrote it, and the tree-state check sees it only when it leaves a file delta.
- Several parsing shapes reach a mutation the guard names elsewhere and allow it anyway. They are lexer limits rather than policy choices, and the list is open rather than closed: each was found by driving strings at the hook, which is a method that finds what it was pointed at. A command substitution standing as a whole token, in a verb or a subcommand slot, is stepped over rather than read, so `git $(echo push)`, `gh pr $(echo merge) 1`, `git ls-files | xargs $(true) rm` and `find /tmp -exec $(true) rm <path> ;` all allow, where the spliced spelling `git $(true)push` denies on the unresolvable token; bash drops the empty unquoted word and runs the denied spelling, and the bulk-idiom member is the highest-consequence of these, reaching a delete of the tracked worktree. The mirror case is a substitution spliced before a flag's dash rather than after it (`sed $(true)-i s/a/b/ <path>`), which evades every flag reader while `sed -$(true)i` denies. A heredoc introduction in comment position still opens a body range, so a redirect or a continued command on the lines beneath a `# <<'A'` is blanked as body text where the shell opens no body at all. An operand standing past a redirect in a simple command is dropped with the segment the operand scan reads, so `rm >/dev/null README.md` allows, while the descriptor-prefix spelling denies on the prefix itself read as an operand. And the PowerShell pipeline branch scans a destructive-cmdlet list carrying `Remove-Item`, `Move-Item`, `Rename-Item` and their `ri`/`rd`/`del`/`erase`/`mi`/`move`/`ren`/`rni` aliases, so `Get-ChildItem src -Recurse | rm` allows where `| Remove-Item` denies. All of them sit inside this section's accepted heuristic risk and are named rather than closed.
- `docs-write-guard` covers the Write/Edit tools exactly and shell writes heuristically; an exotic write (python, `sed -i`, `Copy-Item`, a variable-assembled path) is out of its reach and is caught, if at all, by the Stop-scan backstop. When the payload carries a cwd, its `docs/` match is contained against the git root above that cwd, so a path outside the session's project tree (a session scratchpad, a fixture repo) is out of scope; without a cwd, or for a target unresolvable before the shell runs (a variable, a home-relative path), the shape-only match stands and over-reaches in the false-deny direction.
- `pr-docs-guard` carries a residual false-deny: a payload cwd resolving to a different checkout that is both dirty and parked on a non-default branch still denies.
- `memory-frontmatter-guard` matches Write, Edit and MultiEdit only, so a shell redirection into the store never meets it. Its store-root containment is lexical first, with the directory's real path tried as a second candidate only for a target whose lexical path already sits under the store root and is not UNC- or device-rooted, which resolves a short name or a link inside the store while asking nothing of any other write on the machine. What that leaves out is a spelling of the root itself that the filesystem accepts and a lexical compare does not: a short name of the store root, a mapped or `subst` drive letter, a UNC spelling by a non-admin share name, and an admin-share host spelling outside the five `isLocalHost` compares against, a fully qualified name and a DNS alias among them. Each of those places nothing and allows the write in silence, on the tier where silence is never the right answer. Resolving them would mean an outbound SMB connection made before the user's permission prompt, which is why the check stops where it does. One further residual rides the store root's own location: `memoryRoot()` is `os.homedir()` plus `.claude` absent an honored override, so a profile redirected onto a mapped network drive puts the store root itself on a network-backed volume, where the resolver runs and the shared network predicate does not fire, that predicate answering only the UNC and `//server` forms. And a record's own field values reach the deny line the harness hands the model as its reason for blocking: capped, reduced to printable ASCII, with CR and LF folded so no second line can be forged, but not delimited from the guard's own prose, so store text and hook text meet in one sentence.
- The guards' case tables under `test/` are the lists their authors wrote rather than a proof of coverage, and one of them reads as exhaustive without being so: `docs-write-guard`'s redirect heuristic carries named misses no case in that file exercises, which `docs/backlog.md` enumerates. `merged-pr-push-guard`'s push detector carries named misses too, and its own case table asserts each of them, so there the misses are recorded decisions a change has to re-adjudicate rather than gaps a reader has to find. They sit inside the heuristic-with-a-Stop-scan-backstop risk this section already accepts rather than adding a new one.

**Compensating controls, and the gap each cannot see:**

- Every strict agent's frontmatter grants no Write or Edit tools, the code reviewers, the two document lenses, the council and facilitator seats, and the consultant alike (each holds `Read, Grep, Glob, Bash` and nothing more), so the guard only has to police shell commands. Gap: nothing frontmatter can do about what Bash reaches.
- The executing-work skill brackets every review round with a `git status --porcelain` capture and comparison, so a write that slips past the guard surfaces as a tree delta and is treated as an incident. Gap: the comparison is two `git status --porcelain` readings rather than a byte comparison of the worktree, so it misses every act that moves HEAD and the worktree together while leaving that reading unchanged (a merge, a `checkout`, a `pull`, a `reset --hard`, so a `reset --hard` discarding committed work is invisible here) as well as every act outside the worktree (a `gh` or `az` host-state mutation, a push, a tag); `git fetch` is outside both this comparison and the guard.
- The Stop-scan backstop (`stop-docs-hygiene`) catches scratch that reached `docs/` by any route, including the exotic writes the write-guard cannot parse.
- The build stamps a SHA-256 manifest of every shipped hook file (`hooks.json` included, since rewiring is an equal disarm path to editing a guard) into `.claude-plugin/build-info.json`, and the canary verifies the executing plugin cache against it at session start, warning loudly on drift. This exists because the guards execute from the user-writable plugin cache: a governed agent holding Bash can overwrite a guard there, outside any git root where no tree comparison looks, disarming all five with no signal, and that write is confirmed reachable. The manifest converts a permanent silent disarm into a bounded loud one. Its limits: it is detection, not prevention, and it speaks at the next session start, not in the moment; the canary that performs the comparison stands down entirely under `KIT_EXTERNAL_ENGINE`, so the detection covers attended sessions and not the engine's spawned workers, whose payload integrity is the deploy's concern rather than this check's; and the manifest lives in the same writable cache as the payload it attests, so deleting the stamp file alone silences the check (the canary treats an absent manifest as an older build), and rewriting stamp and payload together defeats it outright. The actor who does either deliberately holds write access the Principals section already places outside every control in this document; the threat the detection is sized for is a model misstep or a rationalized edit, and one naive overwrite is exactly what it catches. Coverage is the shipped hook files; the cache's other executed payload (`scripts/`, `doctor/`) is outside the manifest today, and so is its model-facing prose, `skills/` and `output-styles/kit.md`, which steers behavior when read rather than when executed. The style is the one member of that prose needing no load to take effect: the harness reads it into the system prompt of every main-thread session the plugin is enabled for, so a cache edit to it reaches the model in every session rather than when something invokes it. `test/output-style-parity.test.js` is not that control, since it attests the repo copy against the repo's doctrine and never reads the installed cache.

## The goal state file

`.kit/goal-state.json` is the leash's whole state, and eleven surfaces read it, ten of them belonging to the project that owns the leash: the Stop hook that enforces, the compaction gate, the checkpoint CLI, the chapter-boundary nudge, the compaction-deferral nudge, the SessionStart notice, the `/kit-goal` CLI's own status report, the status-line widget, the doctor, and the status-line launcher. The last of those reads it for one derived answer only: the status-line launcher, deciding whether its render cache is still fresh, needs the armed plan path and the tree the plan doc should be counted from, and takes both through this library's own reader, so the kind, cap and re-validation rules the rest of this paragraph describes cover it exactly as they cover the nine. What it does with the answer is a modification time; it never opens the plan doc itself. It is written only by `kit-goal-lib.js`, and its plan paths are normalized at write time to repo-relative paths that cannot traverse out of the project. Write-time normalization alone would leave a hand edit unchecked, so every read re-validates: the stored current plan and every queue entry must round-trip the same normalizer, and a value that does not round-trip is by definition not one this library wrote. A current plan that fails reads as no armed goal at all, which turns the leash off and leaves the doctor as the surface that flags the file; a queue entry that fails collapses the queue to the current plan rather than being dropped, because dropping one entry would silently renumber the positions `queueIndex` counts. The position walk the bullet below describes re-applies that same round-trip to each entry itself rather than resting on `readGoal` having done it, because it derives a second path per entry that `readGoal` never saw; containment there is a guard the walk holds itself to, not a convention it inherits from its caller. The property that buys is that no reader can hand an unvalidated path to an `openSync`, which matters because a path naming a FIFO would block one, and the readers include a Stop hook where a block wedges the stop. Re-validation is one of two legs, and it covers only paths that came from the state file. Two readers take paths that were never in the state file at all: the SessionStart plan inventory, whose paths come from a `readdir` of `docs/plans/`, and `stop-docs-hygiene.js`, which scans that same directory for a completed-but-unarchived plan and walks `docs/` for leaked scratch, testing each candidate for the plan-header contract. For both the property rests on the kind rule alone, which is why the kind rule below is stated over every reader of a plan doc rather than over every stored path. The Stop hook is the sharper of the two for the same reason the leash is: a blocking open there wedges the stop at every turn end in that checkout, so a FIFO planted under `docs/` at any name either walk reports would hold the session rather than costing one skipped file. Re-validation answers where the path may point; a second rule answers what may be at the end of it, and both are needed, since a path that round-trips the normalizer perfectly can still name a FIFO. So every node-side reader of a plan doc, the armed plan’s own, the unarmed ones the SessionStart inventory scans, and the Stop hook’s own two directory-derived reads alike, goes through one shared kind-and-size rule that lstats first and reads only a regular file, and every node-side reader of the state file itself is preceded by the same lstat, kind and cap check. The qualifier is load-bearing and names a real exception: the doctor, the ninth reader in the list above, is PowerShell and reads both files with a bare `Get-Content -Raw`, with no lstat, no kind check and no size cap. That is deliberate for what the doctor is, the surface that exists to report a state file the hooks refuse, and it is why this document credits it as the reporting control rather than as a hardened reader. It has two consequences worth stating plainly rather than leaving to be discovered. A plan doc symlinked outside the repo reads as unusable to every hook while the doctor follows the link and reports the goal active, which is the two-readers-disagree shape in a place the shared rule does not reach. And an oversized file at either path is read whole on an attended doctor run where every hook refuses it, which is a backlogged item rather than a closed one. The rule resolves exactly one link, and only where the target is inside the project and round-trips the normalizer, because a plan doc reached through a symlink is genuinely readable and refusing the whole non-regular class outright is not a safe default here: it fails closed on a leash, where a plan the reader calls absent while the goal stays armed holds every stop until the harness's block cap fires. That is one rule at one site rather than a spelling per reader, deliberately: the failure this design has actually produced is not a missing check but two checks that answer the same question differently, where one reader calls a path absent and its sibling follows the link, and the branch between them falls through to silence. The check is a round-trip rather than an acceptance test, which makes it stricter than the write path in one direction worth knowing: normalization is platform-dependent, so a state file carried from another operating system can read as malformed on arrival. It fails safe, and it is consistent with the file being machine-local in the first place. Staying machine-local is the other half of its posture, and it is a property of the consuming repository rather than one the kit can impose: the kit's own `.gitignore` covers `.kit/`, but nothing stops a project from tracking the file, and a tracked goal state puts one clone's plan paths into history where every collaborator's session start reads them back. So the doctor checks the property instead of assuming it, and it checks the whole `.kit` directory rather than any one filename, because the gate's state and its journal sit beside the goal state under the same posture and a probe keyed on a single path reports PASS on a repository tracking either of them. It reports paths under the directory tracked, the directory neither tracked nor ignored, or the directory ignored, each with the git command that fixes it, names every tracked path it found rather than truncating the list, and reports a git it cannot run rather than skipping silently, so an absent check never reads as a passing one. The two readings are taken over the same directory and the tracked one runs first, since git stops reporting a path as ignored once it is tracked, and a repository can ignore `.kit/` while still tracking a file inside it through `git add -f`. The check inspects the directory the doctor was launched from rather than the kit's own checkout, which is the whole point: the kit's checkout already ignores `.kit/`, so a check scoped to it would be a permanent pass over the one repository where the exposure cannot occur. Detection is all it is. Nothing prevents the exposure, and nothing runs unless somebody runs the doctor; the preventive fix, a nested ignore file written whenever `.kit/` is created, is backlogged. An arming adds `queue`, `queueIndex`, `history`, and `authorizations` to it whatever the queue's length, a single-plan arm included, a leash that has bound or blocked adds `boundTranscript`, `blockedAdvanceKey`, and `blockedAdvancePlan`, and a leash whose chapter boundary was opened in a linked worktree adds `executionTree`; `queue`, `queueIndex`, and `history` carry the same provenance and the same guards as the fields beside them, being plan paths and an index the same writer produced, `blockedAdvanceKey` is a capped printable-ASCII token the hook derives from a transcript entry and compares only against itself, and `blockedAdvancePlan` is a plan path of the same provenance as the queue's, used only in equality compares against `plan` and the preceding queue entry and never opened. `authorizations` is the exception to that provenance among the fields, and the paragraph below states what it costs; the reported queue position, its own bullet further down, has the same provenance without being a field, and the two claims stay separate rather than either widening to cover the other.

The eleventh is the only foreign one, and it is the newest: the machine-coordinator seat reads a blocked project's state from outside that project, through the CLI rather than by opening the file, which is what keeps the bound transcript's and the execution tree's absolute paths out of a seat composing a brief for an external channel. What makes that a control rather than a hope is a property of the command's output rather than anything the skill can enforce, so it is pinned in `test/kit-goal-lib.test.js`: `status` prints the recorded blocker note and neither path, and the pin's absence checks are required to go red against output carrying each path before they are trusted passing against the shipped command. One field survives that filter, the recorded authorization, which carries the operator's own quoted words, so the bar keeping those words off a board line and out of a brief is what bounds this reader and is stated where the seat reads it.

**The state file belongs to the main checkout, and a git worktree resolves to it through a two-way handshake.** One repository has one leash, so a session working a worktree of it reads and writes the same `.kit/goal-state.json` the main checkout does rather than minting a second one beside its own tree. That makes the location depend on an on-disk pointer, which is a trust input the fixed path did not have, and the handshake is its control. Only `<cwd>/.git` is consulted and never a walk up the tree, so a pointer planted in a parent directory is not reachable. It is read only as a regular file, its `gitdir:` line is matched at the start of the file rather than anywhere in it, and the path it names is judged on its text alone before any filesystem call touches it: a UNC or device-namespace path is refused outright, because opening `\\host\share` is an outbound authentication as the logged-in account, and a path past the length cap is refused for the same reason, ahead of the same call. The claimed main checkout must then vouch back, all three legs or none: its own `.git` is a directory, `<gitdir>/commondir` is a file, and `<gitdir>/gitdir` names this `.git` in return. Any leg failing answers no worktree at all and the reading directory stands, so the resolution fails toward the unresolved behaviour rather than toward a guess, and a bare-repo worktree, having no main checkout to reach, keeps its own state. The reach this buys is worth stating plainly, since it is wider than a read: resolution moves the writes too, so a bind, a queue advance, and the clear’s unlink land outside the payload cwd’s git root. What bounds that is the handshake itself, since the only directory reachable is one that named this `.git` back. The rule is the same one `memq` applies to the memory store, reimplemented here rather than imported because a hook may not carry that script’s weight, and the two are pinned against each other over shared fixtures so they cannot answer differently. The doctor is the exception it was already, and for a second reason now: it resolves the state path from its own launch directory with no handshake, so in a worktree it inspects a file no hook reads. That is the two-readers-disagree shape this section names elsewhere, it is a reporting surface rather than a control, and it is recorded rather than closed.

**`authorizations` is the only field whose value comes from a document rather than from this writer, and it is asserted, never authenticated.** It maps each queued plan path to the first sentence of that plan's `## Dispatch Authorization` section, or to none where the plan carries no such section, and the CLI derives it from the artifact at arm time rather than accepting it from a caller, so there is no flag with which to assert an authorization a plan does not itself state. What that buys is a trail and not a check: the sentence is the plan's own claim about who authorized arming it, the file's content is taken at its word, and nothing consults the field to decide whether an arm may proceed. On a single-principal machine it narrows an honest writer without authenticating one, exactly as the guard hooks above do, and git history is what makes the claim traceable. The value is quoted plan-doc content on its way into a file whose readers print it, so it is screened as untrusted input at both ends: stripped to printable ASCII and capped at write, and re-screened identically on every read, because the field is written back verbatim by every advance and bind and a hand edit that never went through the writer must not survive one round trip into the file the readers trust. A value with nothing printable left in it records as none, since an empty quote would assert a section that said nothing. The scan that produces it reads a bounded head of the plan doc through the same kind-and-size rule as every other read of a plan path, so a plan doc that is a FIFO or a directory yields none rather than blocking, and a section the window does not reach records as none rather than as a partial sentence. That covers two shapes: a heading below the window entirely, which the scan never sees, and a section whose body ran to the window's edge with no following heading and no sentence terminator, where the end of the body is unseen rather than short. A body the window did reach the end of is recorded whatever its punctuation, since the heading that bounds it is evidence the scan saw the section end. A sentence longer than the cap is the one partial the field does carry, and it carries a truncation marker so it cannot read as whole; the marker is written inside the cap rather than past it, which is what keeps the screen idempotent against the re-screen every read applies.

**The SessionStart hook reads the harness transcript store, listing only.** Its shared-checkout advisory enumerates `~/.claude/projects/<flattened-cwd>/` for sibling `.jsonl` files and takes their modification times, to say that another session may be live in the same working tree. It opens no transcript, so no other session's content crosses into this one, and the line it emits carries a count and an age and nothing else: no path, no session id, no filename. Every path fails open, including an unreadable directory and a layout that does not match, because a session start that breaks over a detector is worse than a detector that stays quiet. Recency is the whole signal, so the line is a hint rather than a verdict, and a checkout whose path flattens to the same directory as another is the residual it cannot tell apart.

- **`boundTranscript` is one of the two fields naming a path outside the project, and it is never surfaced and never executed.** `executionTree`, the bullet below, is the other, and the two differ in what is done with the path: this one is stated and stat'ed, that one is followed. It has two provenances: an arm-time record from the `/kit-goal` CLI's existence-checked scan for `<sessionId>.jsonl` under the harness's transcript store (candidate paths composed from `os.homedir()`), and a claim-time record from the hook payload's `transcript_path`. Either way it is sanitized as a length-capped string with control characters refused and a network-shaped path (two leading separators, the UNC and `//server` forms) refused outright, and its only use is an `fs.stat` whose result reaches the model as a number and a unit ("last active about 20 minutes ago"), never as the path. So a hand-edited state file can point the stat at an arbitrary local path and learn nothing from it that reaches a session beyond an age in minutes. The FIFO-hang concern that governs transcript reads elsewhere does not arise, because the path is stated rather than opened, but the stat has a hang of its own and the network refusal is most of what answers it: the call is synchronous and runs at every session start, so a path naming an unreachable share would hold the hook for the SMB timeout. That refusal covers the UNC and `//server` forms only. A path on a mapped network drive letter is indistinguishable from a local disk without a syscall and passes it, so a state file naming one can still hold the stat for the SMB timeout. The harness itself never hands a hook such a transcript path, but the arm-time scan composes its candidates from `os.homedir()`, so a home resolved onto a mapped network drive makes the kit compose one with no hand edit; the residual is reachable from that configuration as well as from a hand edit, and it stays stated rather than closed because the only closure available is a syscall in the path the guard exists to keep cheap.
- **`executionTree` is the second field naming a path outside the project, and unlike `boundTranscript` it is followed.** It names the linked worktree a chapter boundary was last opened from, so a progress-rendering surface can count the copy of the plan doc that lives on the executing branch rather than the checkout's possibly stale one. Its provenance is a single writer: the compaction checkpoint CLI's `open`, which records `path.resolve(cwd)` when and only when the worktree resolution above answers a main checkout other than that cwd. No other surface writes it, and the goal-family CLIs, the hooks, and the harness never accept it as input. It is display trust only, by design and by statement at both ends: nothing that decides a hold, a release, an advance, or a gate outcome reads it, so the worst a false value buys is a section count taken from the wrong copy of a document.

  Four guards run before anything under the recorded path is opened, and their order is the control. The lexical screen comes first, sharing one predicate with `boundTranscript` so the two cannot drift: a non-empty string within the 2048-unit pointer-path cap, no control characters, and no doubled leading separator, which refuses the UNC, `//server` and `\\?\` device forms alike. Absoluteness is required on top, and on Windows that means a drive-qualified root rather than `path.isAbsolute`, which also admits a rooted drive-relative path that would resolve against whichever drive the reading process happened to be on. Then the tree must prove it is what it claims: the same two-way `.git` handshake that resolves goal state must close from the tree and land on the same main checkout this session's own state resolves to, so a hand-edited value naming an arbitrary directory, or a worktree of a different repository, falls back rather than being followed. Then the tree must hold the plan path as a readable regular file under the same kind-and-size rule every other reader of that path applies, and within the reader's own read cap, so an oversized copy falls back to the checkout's readable one rather than dropping the segment. Every failure answers the caller's own cwd, which is the resolution a display reader applies with no tree recorded at all.

  Two properties of the follow are worth stating because they differ from the goal-state resolution they reuse. The probe runs silently: the operator note a failed handshake earns when goal state is being resolved would be false here, since this probe decides nothing about where state is read, and a status line would repaint it at every refresh. And the mapped-network-drive residual `boundTranscript` carries applies identically: a path on a mapped drive letter is indistinguishable from a local disk without a syscall, so it passes the lexical screen and can still hold the handshake's stats for the SMB timeout. Here it does not even take a hand edit to reach, since the writer records the directory it is running in and a worktree may legitimately sit on such a drive; what bounds it is that the session choosing that directory is the operator's own.

  Lifetime is explicit at every path that could strand it, because a stale tree path outliving the plan it described is the field's whole failure mode. A clear unlinks the state file, so nothing survives it. An arm builds its state from nothing and never carries a previous goal's tree. An advance deletes the field, since where the finished plan's boundaries were opened is no claim about the plan the leash moves to. A boundary opened from the resolved checkout itself drops any standing record for the same reason. And the write takes a compare-and-swap on the plan path and the arming timestamp across its read-to-write window, the guard the advance takes over the same window, so an advance or a re-arm landing between the two reads is refused rather than re-attaching the finished plan's tree to the state that replaced it.
- **The reported queue position is derived from the plan docs, not read from `queueIndex`.** Three surfaces report where a run stands in an armed queue: the SessionStart advisory, the `/kit-goal` CLI’s status report, and the status-line widget. All three walk the queue and ask the plan docs themselves, reading each entry’s `Status:` header under the frozen machine contract and, where nothing stands at the plans path, the header of a same-named copy filed under `docs/archive/`. The stored index moves only at a clean stop of the bound session, so a run that died at its close-out leaves it naming a plan that is finished and archived, which is the state this derivation exists to report truthfully.

  What that adds to the trust surface is a new input, and it is repository content rather than state-file content: what sits in `docs/plans/` and `docs/archive/`, in up to two trees, now influences the number a session is told. Four bounds hold it. The walk runs forward only from the clamped stored index and never backward, so it can move the reported position past a finished plan and never behind a live one. It is capped at sixteen entries, so a hostile or corrupt queue cannot turn a session-start notice into an unbounded scan. It never writes back, so a misreading costs a wrong number on one render rather than a mutated leash. And an entry counts finished only where every tree with a say agrees, a worktree and its main checkout both, since the two can legitimately hold different copies of the same doc; a disagreement reports the entry pending, which under-reports progress rather than moving the reported position past live work.

  The paths it opens are each entry’s own doc and one derived sibling under `docs/archive/`, and the derived one is the reason containment is restated here rather than assumed. A stored entry that passes a bare `docs/plans/` prefix test can still carry traversal in its tail, so the archive path is round-tripped through the same normalizer every stored plan path answers to before anything stats or opens it, and a path that does not round-trip yields nothing rather than a target outside the project. An entry that does not round-trip at all is reported unresolvable, named as such, and keeps its position rather than being skipped, because skipping it would renumber every entry behind it. The archived copy is held to the same header bar as a doc still in `docs/plans/`: presence alone is not evidence, since nothing ties a file under `docs/archive/` to this queue entry beyond a matching name, and a plan deleted rather than filed, with a same-named doc from an earlier effort already in the archive, would otherwise read finished in every tree.

  It decides nothing, and that is the whole of why two readings of one queue can coexist safely. The leash still acts on the stored index: every hold, release and advance reads `queueIndex` and nothing reads the derived position, which is a reported number and a sentence, on the same display-trust footing as `executionTree` above. The doctor is again the deliberate exception, and sharper here than elsewhere: it renders the raw stored index, so on exactly the defect state this derivation exists for, the doctor and the hooks report different numbers by design. That is the reporting control doing its job, since a doctor that silently corrected the state file it exists to show would stop being one, and it is stated here so an auditor reading two numbers knows which surface is claiming what.
- **A hand edit is the threat model here, not a remote one.** Nothing outside the machine writes this file, and anything able to write it could equally have written `plan` or `boundSession`, which are the fields with real leverage. The readers are defensive anyway rather than trusting: `readGoal` normalizes every read to a consistent shape, so a queue disagreeing with `plan` or a non-array `history` is repaired rather than propagated, and the doctor discards a queue that disagrees with `plan` in favour of reading the file as a single-plan arming.
- **Advancing is the same write as arming, and it inherits the same atomicity.** The advance is one temp-file-plus-rename rewrite, so a state file is never observed half-advanced. What it does not have is a lock, and the session binding is deliberately not credited as one in its place: the binding serializes the Stop hook's own writes, while the `/kit-goal` CLI is a writer it does not exclude, so a re-arm or a clear can land between the snapshot a stop decided from and the advance's own re-read. A compare-and-swap is what closes that. The advance carries both the plan the stop decided from and the timestamp that state was armed at, and refuses when the re-read state no longer matches either. The timestamp is not redundant: a re-arm that puts the same plan back at the head is the ordinary crash-recovery spelling, and on the plan alone it would pass the compare and let a stop advance a queue that had just been freshly armed. A refused advance holds the stop rather than releasing it, so the failure direction is a retry at the next stop rather than a queue position spent against state the caller never saw. `arm --append` is the fourth writer and guards itself on the same reasoning in its own terms: an append is typed into whatever shell is at hand while the leashed session runs, and validating one opens a plan doc per path, so it re-reads the state immediately before the write and refuses unless the arming timestamp, the current plan, the queue position, the queue length and the history length all still match what it decided from. The timestamp alone would not carry it, because an advance preserves the timestamp by design. What it writes is the re-read with the append applied, never its own snapshot, so a bind or a blocked advance landing mid-validation is kept rather than reverted, and a bystander cannot come to claim a leash whose binding an older snapshot put back to null. `bindSession` takes the same rebase for the same reason, setting only the two binding fields it owns onto a fresh read. Neither closes the window between that re-read and the rename, which stays last-writer-wins. The compaction gate is a third write trigger, reaching the same library to claim a binding at an auto-compaction offer, and the binding cannot serialize it either, because it fires precisely in the unbound state where there is no binding yet. That write carries no compare-and-swap: it is last-writer-wins, so a clear or a re-arm landing between its read and its write can be resurrected by it, recoverable by clearing again.

## The compaction gate

`kit-compact-gate.js` is a PreCompact hook, and it is not a guard: it governs no agent and protects no state from anyone. It schedules. Native auto-compaction lands wherever context happens to fill, which on a leashed plan run is mid-section; the gate defers it until the run declares a boundary, a section's close or, during a drought between closes, an interim board entry. The only lever the harness offers is a veto, and a denied auto attempt is re-offered once per assistant turn indefinitely, which is what makes vetoing a schedule rather than a cancellation.

**The invariant:** the gate denies in exactly two states and allows every other, and both denials are bounded by the same ceiling. Two preconditions gate both: the trigger is `auto` and `KIT_EXTERNAL_ENGINE` is unset. Past those, it denies **boundary-gated** when a kit goal is armed for the project, the compacting session is the one bound to that goal's leash, no boundary checkpoint is open that matches the armed plan, matches the bound session, and is still fresh, consumption read from the session transcript is legibly below a named ceiling, and no live operator-consent marker names the bound session. Those three checkpoint legs are one predicate in the shared library, which the gate's verdict and the CLI's status report both answer from, so what the report says gates nothing is what the gate treats as absent. It denies **interactive** when no goal is armed for the project, an armed one is bound to a different session, or an armed one is unbound and this session's transcript makes no claim on it, the transcript shows no native `/goal` or `/loop` driving it, consumption is legibly below that same ceiling, and neither a live role-boundary marker nor a live operator-consent marker names the compacting session. An armed goal no session has claimed yet is resolved by the same claim proof the leash itself uses: where the compacting session's transcript shows the user typing the arming command, the gate claims the binding and takes the boundary-gated path, and where it does not, the session is a bystander and takes the interactive path. That second claim point exists because the leash's other one is a stop, and a run holding the completion contract does not stop while work remains, so a stop-only claim leaves a well-behaved run unbound and therefore ungated for its whole length. One armed state still allows outright: an armed goal beside a payload carrying no usable session id, which is an anomaly rather than evidence of a bystander, and from which no binding could be written in any case, so it is resolved toward allowing. Any other state, any read error, any ambiguity allows. Each denial writes its own stderr string carrying no input-derived data, distinct per kind so a reader can tell which deferral fired; the boundary note's one composed value is the hook's own install directory, which it names so the remedy command it offers the operator resolves outside this repo's own checkout. Manual `/compact` is never gated, checked in code as well as by the `hooks.json` matcher so a rewiring cannot silently widen it. Deny is exit code 2; the JSON deny form is inert for this event on the versions probed, so nothing is built on it.

**The scope of the interactive state, stated plainly because it is this section's widest claim.** The deny reaches every session the harness offers an auto-compaction to, not only the sessions that opted in by arming a kit goal, and the ceiling assumption below rides along with it onto that default population. What bounds the exposure is that the gate can only veto an offer the harness already made, never raise one, and that the same ceiling ends every deferral. The reach also makes the transcript reader a per-session code path rather than a per-plan-run one, which is why its input handling is treated as untrusted parsing rather than as a convenience read.

**Accepted risk: the automation detection reads attacker-influenceable transcript content.** The transcript holds file content, tool output, and agent reports, so the literal command markup the detector keys on can be planted by anything the session reads, including this repository's own documentation. Detection is therefore structural rather than substring-based: an entry must parse as JSON on a line of its own, carry the right entry type, and hold the markup in the user-typed position, and tool results, meta entries, compaction summaries, and sidechain rows are excluded. Content quoted into a transcript rides inside a JSON-escaped field and so cannot produce the standalone line the test requires, which is the property the whole defense rests on. The residual is bounded rather than absent, and it runs in both directions: the detector reads retirement evidence too (a completed goal, a `clear` argument, a loop's terminating stop), so a plant can push a session either way. What bounds it is that both destinations are treatments the gate already applies to real sessions, and both answer to the same ceiling: a plant can move a session between compacting at the native trigger and deferring to the ceiling, and can do nothing else. It cannot extend a deferral past the ceiling, and it cannot reach any file or process. The parsing itself is the sharper edge: the reader caps its read, parses line by line rather than with a whole-file pattern, and its span scanning is linear, because a backtracking pattern over untrusted transcript text is a denial-of-service reachable from every session's compaction path.

**Accepted risk: the claim predicate is an authorization decision taken from the same transcript.** The automation detection above only steers a deferral; the claim decides which session holds a leash and writes `boundSession` into the goal state, so an entry that satisfies it moves real state. It is not a second reader written for the gate. It is the predicate the Stop hook has always claimed a binding with, single-sourced in `kit-compact-lib.js` and called by both hooks, so the gate adds no evidence shape the leash did not already trust. The exclusions are the anti-steal set: the entry must be user-type and neither a sidechain, an `isMeta` harness injection, nor a compaction summary; local-command stdout is stripped before the tag scan; and the path match is directory-qualified, so a same-basename file elsewhere is not the plan. Two invocation shapes then count, and only those two. In the markup shape the plan path must sit in a `<command-args>` span belonging to a `<command-name>` that is exactly `/kit-goal` or ends `:kit-goal`, so another command taking a path argument cannot claim. The typed-lead shape covers the arming the harness does not parse into markup (a multi-line `/kit-goal` with one plan path per line): the message's first non-whitespace characters must be the `/kit-goal` token (optionally plugin-namespaced), and the plan path must sit inside the argument block, the text from the token to the first line that is empty or opens with a backtick or `<`, so quoted, fenced, or injected material after the argument list can never supply the path, and a message that leads with prose, or that mentions the path only behind one of those boundaries, never claims. One residual survives the block boundary: a contiguous prose line inside the block (a lead-token arming of one plan whose very next line, with no blank line, fence, or tag between, mentions another armed plan) can still claim, since the block cannot tell a path line from a prose line; the blast is the same bounded, recoverable one this paragraph already accepts, and arm-time binding shrinks the unbound population it can act on. Array content carrying any `tool_use` or `tool_result` block discards the whole entry rather than being filtered block by block, one step stricter than the sibling readers in the same file, because a claim is a decision and an entry mixing genuine user text with tool output is where planted markup would ride beside a real turn. What a claim would buy an actor who forged one is bounded and recoverable: the claiming session becomes the boundary-gated one and the real run becomes a bystander to its own plan, which re-arming undoes. The write carries no compare-and-swap, the residual recorded under the goal state file above.

**Accepted risk: the checkpoint file is user-writable and steers compaction timing.** `.kit/compact-checkpoint.json` is an ordinary file in a writable tree, so anyone who can write the tree can open or remove one. The worst case is bounded and small: a compaction landing earlier or later in a session than intended. It cannot deny a compaction that the gate would otherwise allow (the file only ever opens the gate), it cannot cause data loss (the harness's own summarizer runs unmodified either way, and the kit summarizes nothing), and it cannot reach outside the project (the filename is a composed by the shared `.kit/` resolver from the payload cwd and never caller-chosen, on the two-branch derivation the residual paragraph below states, and the delete refuses a planted symlink outright, its kind check answering nothing-cleared rather than following the link or removing it). The plan and session fields are compared for equality and never joined to a path. An actor who can write this file already holds the tree write access the Principals section places outside every control in this document.

**Accepted risk: the release markers are self-declared, and the consent marker's authority is asserted rather than authenticated.** `.kit/compact-role-boundary.json` and `.kit/compact-consent.json` are two more ordinary files in the same writable tree, each releasing a deferral for the session it names. Which tree that is comes from one shared resolver rather than from a fixed suffix: ordinarily the project directory's own `.kit/`, and for a project directory lying inside the memory store an unsynced per-machine path outside the store, so a store-resident seat's markers are not replicated to every machine. One resolver serves every writer and the gate's reader alike, which is what keeps a marker's writer and its reader agreeing on where it lives; the residual paragraph below states what the resolver does and does not screen. The role-boundary marker is deliberately model-writable, and the asymmetry against the gate's own verdict legs is the design rather than an oversight. It now has a second writer that is not a model deciding to write: the `seat-stop.js` Stop hook opens it for a registered session whose registry entry shows a status push this turn over a clean tree. That widens who writes the marker rather than what a marker can do, and it widens it in the direction this paragraph already accepts, since the entry the hook reads is one the seat itself writes and the hook's own conditions are a freshness stamp and a `git status --porcelain` read. The clean-tree conjunct fails open on a non-git or failing `git`, which is the deliberate direction: the marker's worst case is a compaction landing at a declared boundary, so a seat whose `git` is unreachable banks unconditionally rather than never banking at all. The precise form of it matters, because the loose form is false. Model-writable inputs do steer this gate, and two of them steer it toward a deny: the goal state selects the boundary-gated path, so a state naming the compacting session reaches that path's deny before the automation clause is consulted at all, and removing a live checkpoint turns that same path's allow into a deny. The narrow claim is the one this design rests on, and it is about the release inputs alone: a marker releases a deferral or is inert, and neither marker reaches a deny on either leg. What bounds all of them together is the ceiling force-landing, which no plant and no deletion can defer a session past, and that bound is why the paragraphs above can call the transcript attacker-influenceable and still call the gate sound. Timing is the whole of what any of them costs: the gate exists to prevent a mid-work landing rather than compaction itself, the ceiling is already the worst case this design tolerates, and a leashed worker's checkpoint already extends exactly this trust on the other path. The consent marker is the one carrying the operator's authority, and nothing authenticates it: on a single-principal machine an asserted identity narrows an honest writer without authenticating one, the same shape the goal state's `authorizations` field takes, though without that field's trail, since a marker records a session, a write timestamp and a consumed flag and never who instructed it or over which channel. What bounds it is prose. A session may write it only on the operator's explicit instruction to release that session's deferred compaction, over one of the warranted channels the coordinator skill's closed list names, and never on the session's own judgment; the role skills carry that rule. Code bounds the rest. Each marker is single-shot in intent, retired by the allow that spends it and by any other allow the session it names lands, with that retirement best-effort on every path, so a delete that fails releases again on every later offer inside the marker's own age bound, with no cap on the count: the same read-then-delete residual the checkpoint carries, in the same direction, an extra release rather than a run held to the ceiling. Each carries an age bound past which it reads as absent, and both are the deferral episode's own four-hour idle bound, derived rather than restated, so retuning that episode constant retunes both windows with it. The boundary marker's bound is the one that moved, from a figure of its own to this derivation, and the direction is a widening: a marker now stays live for four hours rather than thirty minutes. What makes that safe is not the length but where it is written, since it is opened only at a moment a seat's runbook defines as banked and a seat's stated invariant is that its context holds nothing the disk does not, so a compaction anywhere inside the window costs a re-read and never state. Each is compared for equality against the payload's session id, never joined to a path, and read only through the same lstat-and-kind-and-size screen the checkpoint takes, so a planted symlink is refused rather than followed. Marker content reaches a model-read channel at one place only, the checkpoint CLI's `status`, which prints the recorded session and write timestamp through the same sanitizer and length cap every other file-derived value in that report passes. And neither marker reaches a clause that denies for an integrity reason: both release scheduling denials only, the verdicts whose meaning is not at this moment, so consent converts a not-yet into a now and never a never into a yes.

**Accepted risk: neither release marker is scoped to its writer.** This is the widest claim in the release design, and it is deliberate rather than a gap. `consent --session <id>` names any session, by design, since the operator releasing a session usually is not that session; the boundary marker takes its id from `CLAUDE_CODE_SESSION_ID`, which the writing shell sets; and both verbs write into the caller's own current directory while the gate reads at the compacting session's project directory, except that `consent --project <path>` now resolves against a named directory instead of the cwd. So the party that writes a marker and the session it releases need not be the same, nor need the directory be the writer's own, and the target id is not secret, `.kit/goal-state.json` carrying `boundSession`. The `--project` flag is the one place in this section where a caller's value reaches a marker's path, which is exactly the shape the residual paragraph below says the rest of the section avoids, so it carries a corroboration the other paths do not need: the command refuses loudly unless the named session has a transcript under the named project, which ties the pair the marker asserts to evidence on disk rather than accepting both from the command line. That check is a corroboration and not an authentication, on the same reading this document gives every other asserted identity here: it narrows an honest operator's mistake, the silent miss where a marker was written where nobody would read it, and it does not stop a writer who can already reach the tree. Two things bound how far the narrowing reaches, and both are worth stating because the mistake class the flag exists for is exactly where they bite. The corroboration is collision-blind: it resolves a project to its transcript directory through the harness's own flattening, which maps every non-alphanumeric character to a single separator, so paths differing only in punctuation flatten to one name and a near-miss path of that shape passes the check while the marker lands where nobody reads it. That is the silent miss surviving inside its own mitigation, for the narrow class of typo that stays inside the flattening's equivalence class. And the check proves only that the named session ran under that project at some point, never that it is there now. Neither weakens the harm bound, which is a compaction's timing on every path here, but a reader should not take the refusal for a guarantee that the pair is right. The flag does not widen the harm class either, since every path in this section still costs a compaction's timing and no marker reaches a deny. A writer with access to another session's project directory can therefore land a compaction mid-chapter on that session's leashed run, which is the one placement the gate exists to prevent. Two writer classes reach it, and they are not alike. Anyone who can write the tree already holds the access the Principals section places outside every control in this document, so that class adds nothing new. The strict read-only agent class does: the guard holds those agents to `.kit/` among write-shaped commands and screens no `node <script>` invocation at all, so a governed reviewer, consultant or council member holding Bash can run the checkpoint CLI and plant a marker in the project it is reading. That is a genuine widening of what a read-only agent reaches, and it is accepted rather than closed because the harm class does not change with the writer: every path here costs a compaction's timing and nothing else, no marker can produce a deny, and an agent that plants one is an agent already off its charter. The tree-state bracket around a review round is not the instrument that catches it: `.kit/` is gitignored and a `git status --porcelain` comparison omits ignored paths, so the plant leaves no delta, which is the blind spot this document already names for that bracket. What does record it is the gate's own journal, where the release lands as an `operator-consent` or `role-boundary` allow, and the checkpoint CLI's `status`, which prints a live marker and the session it names.

**Accepted risk: the gate's own records are user-writable, and one of them steers the checkpoint's freshness leg.** The gate writes two more ordinary files in the same writable tree: `.kit/compact-gate.json`, the current state, and `.kit/compact-gate.jsonl`, an append-only journal carrying two record classes, one per gate decision (keyed `verdict`) and one per nudge stamp (keyed `event`). The journal is diagnostic and nothing branches on it. Four code sites read the state (the PreCompact gate, the checkpoint CLI, the Stop hook's queue advance, and the nudge), and its content steers three things, each degrading to the status quo when it is forged. A planted episode can make a checkpoint take the 24-hour leg instead of the ten-minute one, which is the same bounded, small worst case the checkpoint paragraph states, a compaction landing later in a session than intended; it cannot deny a compaction the gate would otherwise allow, and the predate condition means a forged episode still cannot vouch for a checkpoint opened before it. A planted or removed nudge stamp changes whether a sentence is shown to the model. And the third is worth naming rather than leaving implicit, because it is a channel from a user-writable file into a model's context: the episode's denial count and start time are what the nudge renders into that sentence. Both pass the same clamp, to a non-negative integer no larger than 1e9, so a forged file yields two odd-looking numbers and never free text; the reminder around them is a fixed literal. Neither file is ever joined to a caller-chosen path. Both are lstat-and-kind screened before any read, the state additionally under a byte cap, while the journal's 2 MB figure is a trim threshold rather than a read cap, since it is never read whole. The reporting CLI advises removing a file only where the refusal was an oversize, never where it was a transient read failure, since removing it there would discard a live episode over a scanner's lock. Two properties are worth naming because they are weaker than a reader might assume: the read-modify-write is unlocked, so concurrent gate processes can undercount, and an armed goal resolving for the directory is the one condition under which the recorder creates `.kit/` rather than refusing, so a project that has never armed a goal records nothing at all. That creation is the leashed worktree run’s case, which has no local `.kit/` of its own: only an absent directory reaches it, and any other failure to read one stays a refusal. The creation is recursive rather than single-level, because the resolver's store-backed branch names a directory several levels below a per-machine root that need not exist yet. What bounds it is the armed-goal condition rather than the depth: a goal resolves only for a directory that already exists, so the recursion creates the scratch path for a project that is already there and never conjures a project. A failing creation, a racing creator included, degrades to the same refusal an unreadable directory takes.

**Accepted risk: the status line's render cache is user-writable and its contents reach the operator's terminal.** `.kit/statusline-cache.json` holds the last status-line segment drawn for a project, with the modification times of the two files a cacheable line is rendered from, so a refresh that finds both unchanged reprints it instead of re-reading and re-parsing the armed plan doc. Not every render reaches it. The Plans segment takes its position from a walk over the queue’s plan docs, and that walk reads as many files as the queue and the trees give it: a second checkout’s copy of an entry in a worktree session, a plan’s archived copy, and every entry past the stored one all sit outside the pair the key stats. So the walk reports the paths it actually read, and a line is stored only where that report is exactly the one keyed plan doc. Every other render is refused entry to the cache and so is never served, which trades a re-render per refresh for a number that cannot freeze. What makes the refusal hold is that it is decided on what the walk read rather than on a list of the states that send it further, so an input class added to the walk later cannot quietly widen what the key fails to cover. The file is an ordinary file in a writable tree, and a project that does not ignore `.kit/` can carry one in its history, so a checkout plus one status-line refresh is the whole reachability chain. It is the only `.kit/` file printed to a terminal as a whole stored line rather than reaching one as a comparison or a clamped number, which is what earns it a paragraph. The goal state's content reaches a terminal too, but only as the armed plan's base name inside a segment the widget composes and sanitizes at construction. The read screens it as the others do, lstat and kind before any open and an 8 KB cap, and rebuilds every field by type rather than trusting the parse, so an unexpected shape costs a re-render and nothing more. The line itself is the channel, and it is closed at the print rather than at the parse: a line that came off disk is printed only through the same terminal sanitizer the widget applies to every segment it composes, which strips C0 and C1 controls (a raw 0x9B is CSI and 0x9D is OSC), bidi overrides, zero-width characters, the line and paragraph separators, and lone surrogates, under a length cap. A freshly rendered line is printed as the widget produced it, which is already sanitized segment by segment at construction. The stored plan path is a stat target and never opened, and it must round-trip the same normalizer every other reader of a stored plan path applies, so it cannot name a target outside the project. The write is one of the two `.kit/` writes in this section that screen their own directory, the gate-record writers being the other: it lstats `.kit` and requires a real directory, lstats the target and refuses anything that is not a regular file, and lands through an exclusive-create temp plus rename, so a symlink, junction, or FIFO planted at either is refused rather than followed. A hardlink at the cache path is admitted, matching the goal state's posture. The file is disposable: deleting it costs one re-render, and the first refresh after a disarm that renders inside its budget drops it, the disarm itself removing only the goal state.

**Residual, documented rather than closed: most of these checks screen the file, not the directory holding it.** Every `.kit/` path in this section is composed by one shared resolver from the payload's cwd, and every read lstats its target and refuses a kind it does not expect. The resolver is a fixed suffix on that cwd in the ordinary case and, for a cwd inside the memory store, a fixed suffix on an unsynced per-machine root keyed by the cwd's store-relative path; either way the caller supplies no part of it. One path is the exception and is the reason this sentence no longer says "never from a caller's value": `consent --project <path>` takes the directory from the command line, and the corroboration its own paragraph above describes, refusing unless the named session has a transcript under the named project, is what stands in place of the composition guarantee there. The `.kit` component itself is screened on two write paths and on none of the read paths. The gate-record writers check it: `gateStateTarget` lstats `.kit` and requires a real directory, so a symlinked `.kit` is refused rather than followed for both the gate state and the journal. The status-line cache's writer checks it the same way, for the reason its own paragraph gives. Every read, and the checkpoint and release-marker files' own writes, do not: a `.kit` that is a symlink, or that sits under a symlinked ancestor, redirects them to wherever it points, with the file at the far end still passing its own kind check because it genuinely is a regular file. The reachable consequence is bounded by what those files do, which the checkpoint, release-marker and gate-records paragraphs state: a redirected checkpoint, release-marker, or gate-state read shifts a compaction's timing. It is left as a residual rather than fixed because closing it means resolving and re-validating a directory component on every hook invocation on the pre-verdict path, and because planting that link requires the tree write access the Principals section already places outside every control here.

The compaction-deferral nudge writes as well as emits, which makes it the first hook whose emission is gated on its own write landing. It is not the first PostToolUse writer: `memory-usage-stamp.js` appends a read stamp to the memory store's usage file and emits nothing at all, and `format-on-edit.js` spawns a formatter that rewrites the edited file. What is new here is the coupling. This hook writes both of the gate's files, the interval stamp on the episode in the state and one journal line recording that the stamp was taken, and it takes the stamp *before* it emits, returning silently when the stamp does not land. So the write is the rate limit rather than a side effect of the reminder, which is also why the external-engine stand-down keeps it from writing: that guard returns before any of this runs, not because the write rides on the emission. Neither path is caller-chosen, both being fixed suffixes on the payload cwd, and the stamp is the narrowest write available for what it must do, a compare-and-set against a re-read of the state that fails closed to no stamp. The compare-and-set is load-bearing rather than tidy. Without it a stamp landing across a valve or an illegible allow would restore an episode that allow had just cleared, and a restored episode hands a stale checkpoint the long freshness leg instead of the short one, which admits exactly the mid-chapter compaction the gate exists to prevent. So the hook that only reports a hold could otherwise extend one.

The gate's decision writer is the one path where that same restoration is still reachable, and it is a residual rather than a closed hole. `recordGateDecision` does its read-modify-write without the fingerprint verify the stamp uses, so a bystander session's `deny-interactive` carries the deferral episode through from a read of its own; where that read predates the bound session's valve or illegible allow, writing it back restores the episode the allow had just cleared, and a pending checkpoint the allow left standing is vouched for a second time. It needs two gate processes in one project inside the same few milliseconds, and its cost is the ceiling every other failure direction here already accepts: one compaction landing mid-chapter, which is the state before the gate existed. It is carried rather than fixed because giving a lock-free writer a retry loop is a larger change than the exposure buys.

**Compensating controls, and the gap each cannot see:**

- **The safety valve is the control the rest rests on.** Sustained denial on a run that declares no boundary, neither a section close nor an interim board entry, would otherwise climb to the model's hard context limit, where a session dies outright on an over-length prompt, which is a strictly worse outcome than the mistimed compaction the gate exists to prevent. At or above the ceiling the gate allows regardless of any checkpoint, and the interactive denial answers to the same constant. Its gap: the ceiling is an absolute token count assuming the roughly 1,000,000-token window these sessions carry, because the PreCompact payload carries no `model` field to derive the real one. On a window falling between the trigger and the ceiling the valve would sit above the hard limit and never fire. That is the single direction of this design that is not fail-open, and it is an assumption pinned in the code rather than a property the hook can verify. One shared ceiling is a deliberate choice rather than an oversight, and through the interactive state it governs every session rather than only opted-in runs; what keeps the exposure bounded is that reaching the deny at all requires the harness to have offered a compaction, which a window too small to reach the trigger never does.
- **The doctor's auto-compaction-window check** reads the ceiling out of the hook file rather than restating it, warns when the configured `autoCompactWindow` would leave too small a band between the trigger and the ceiling, the state in which the valve allows everything and the gate defers nothing, and reports a configured value that merely differs from the recommendation, which is the only way a machine already carrying a value learns of a new one. Its one write that touches an operator's own choice, replacing a differing value, is withheld from the unattended `-Yes` consent and takes an interactive answer; supplying an absent value is not, because that case converges while replacement does not. Its gaps, stated plainly because this control is easy to credit with more than it does: it is an attended check that speaks only when someone runs it; it reads the configured window, which is not the running model's real context window, so **the not-fail-open direction above is not covered by this check or by anything else**, and a model whose window is smaller than the ceiling is caught by nothing; and if it cannot read the ceiling constant out of the hook source it reports the skip rather than the comparison.
- **The checkpoint expires.** A boundary is often reached below the trigger, where no compaction is pending, so a checkpoint with no staleness bound would sit open and admit the next offer, which arrives mid-section. The gate treats a stale checkpoint as absent, and it measures staleness on two legs rather than one, because a checkpoint opened below the trigger and one opened while an offer is already being held are not the same object. The first takes a short window of ten minutes, which is what retires the leftover. The second takes an outer bound of 24 hours, and it is not available on the record's own say-so: the CLI stores a `pendingOffer` flag at the open, and the gate honors the long leg only when it can corroborate that flag against its own recorded state, requiring an episode still open, owned by this binding, and dated before the checkpoint it vouches for. An absent or uncorroborated flag falls back to the ten-minute leg, which is the fail-safe direction, and the future-skew check applies to both. The predate requirement is the security-relevant half: without it the flag would mint its own licence, since the very denial that refused a stale checkpoint opens the episode that would corroborate that same checkpoint one turn later. The 24 hours is a sanity cap against a hand-made or clock-skewed record rather than an operating figure; the operating ceiling is the episode's own life, which ends four hours after its newest denial. The executing-work ritual independently clears the checkpoint when the next section starts. That second guard covers a section close alone: no section starts during a closure drought, so a checkpoint opened at an interim board entry rests on the expiry by itself. This is a correctness control rather than a security one, listed here because its absence makes every claim in this section describe a feature that is not doing anything. Two gaps ride with it. The short leg's bound is wall-clock, so a chapter that crosses the trigger within ten minutes of the previous boundary can still spend a stale checkpoint, costing one mistimed compaction. And the long leg has a residue no discriminator closes: an allow that lands without clearing the episode leaves a hold standing with no offer behind it, which a manual `/compact` produces (the gate's matcher is auto-only, so it never sees one) and so does the `no-session` allow (which carries no id, so the ownership test cannot clear). Inside the episode's idle window a boundary opened in that shadow takes the long leg with nothing waiting for it, costing one mistimed compaction, which is the pre-gate status quo. What would close it, whether a compaction landed by some other route, is not observable to a hook the harness never invokes on that path.
- **Session binding retires an orphaned checkpoint.** The checkpoint records the goal's bound session alongside the plan, and the gate requires both to match, so a checkpoint left behind by a crashed run cannot open the gate for the session that resumes the plan. Its gap: it assumes a single writer, since the gate's read-then-delete is not atomic; a concurrent writer landing between the two would burn a boundary. A second legitimate writer of that file exists, the queue advance, which rewrites an open checkpoint to the plan it moved to so a plan's own close-out boundary is not retired by the advance that follows it. It writes from the bound session's Stop event, the same session and a different event from the gate's read, so the single-writer assumption holds across both. A checkpoint opened while the goal was still unbound records a null session and therefore matches nothing once the gate claims the binding, which costs one more chapter of deferral rather than opening the gate early.
- **The build's SHA-256 manifest covers these files like every other shipped hook**, so editing the gate or rewiring it out of `hooks.json` is a stamped edit the canary reports. Its gap is the manifest's own, stated in full under the guard hooks above: detection rather than prevention, at the next session start, and stood down entirely under `KIT_EXTERNAL_ENGINE`.

**Not a control:** the gate stands down under `KIT_EXTERNAL_ENGINE` because an engine's workers are fresh per section and have no mid-chapter context to protect. That is a scope decision, not a security property, and it removes nothing an attacker would otherwise face.

**The chapter-boundary nudge rides beside the gate and shares its posture.** `chapter-boundary-nudge.js` is a PostToolUse hook closing the gate's one-way signal: the gate's deny note reaches the user and never the model, so a leashed run that skips the chapter-close checkpoint would be denied every offer with no word to the party able to write one. When a Chapter heading is added to the armed plan's own doc, matched by path so a sibling plan under `docs/plans/` never fires it, the hook emits the boundary steps into the model's context. Its model-visible output is a single fixed string carrying no payload, transcript, or repo data, the same injection posture as the gate's deny notes and the checkpoint CLI's sanitized output, and the string states the hold as bounded by the safety valve rather than as permanent, so the one surface that speaks to the model does not contradict the ceiling documented above. It fires only for the session bound to the armed goal, and it stands down for a subagent's tool call on the payload's agent keys rather than on the session id, because a subagent's payload carries the parent session's own id and the bound-session check alone would pass one. It never exits 2, and never exits non-zero at all: the kit library requires are deferred behind the guards so a damaged installed cache degrades to silence, every guard and every internal error fails toward a silent exit 0, and a payload cwd naming a network share (the UNC and `//server` forms) is refused before any filesystem touch, so its worst failure is a missed reminder rather than a degraded edit loop. That refusal covers the two-leading-separator forms only: a project hosted on a mapped network drive letter is indistinguishable from a local disk without a syscall and can still hold the goal read for the SMB timeout, the same residual the goal library states for its own transcript stat. Its silence, like the other fail-open hooks', is not evidence of health.

## The coordinator board

`coordinator/<machine>/board.md` in the memory store is the machine-coordinator seat's state, and it is the one such artifact a single seat maintains continuously about a machine's other sessions. It is not the only durable record one session keeps about another: `~/.claude/kit-events.jsonl` is machine-wide and durable too, though each of its entries is written by the session it describes, and the peer-sessions skill has each side of a handoff record its own half in its own Chapter, the receiver its held or deferred plan and the sender its unconverted handoff. It holds the roster with its role claims, active efforts per repo with plan paths and anchors, pending handoffs with their protocol state, machine-resource claims, and open operator escalations, each carrying the incident it is about, whether it has been briefed, and what it waits on. An efforts entry may note that a plan carries a `## Dispatch Authorization` section, as a pointer to the plan and nothing more: no dates, no scope, none of the operator's words.

**It is coordination state, never an authority surface**, and the reason is structural rather than a matter of wording. Nothing in the board warrants an action; a session needing an authorization goes to the artifact that carries it. The kit's one authority control is a receiver tracing a grant back to the operator, per Dispatch authority in `docs/architecture.md`, and a document the seat itself wrote cannot satisfy that trace however it is phrased. A board recording standing grants would defeat the control twice: once by replicating the operator's words irrecoverably to every machine the store reaches, and once by making them copy-pasteable into a plan any session writes, after which a receiver's trace finds real operator words in real git history and arms on them. The board is read as data like every other file the kit reads, with no exemption and the successor's own reading included: an entry the seat did not write is a claim, never a warrant.

**The board's readership is the store's, and that is an assumption about the installation rather than a property of the design.** The store replicates to whatever remote is configured for it, and nothing in the kit reads that remote's visibility or refuses a public one: there is no visibility probe in the doctor or the hooks, and the installer and the sync take the remote they find. So the reasonable-privacy premise the seat writes under is a precondition an operator satisfies, not a guarantee the kit makes. Where it is unestablished, which is the state a seat starts in and stays in until the operator answers, the seat writes the board as a public surface: sensitive commitment detail rides as a stub with its detail left on the channel the operator used, and the re-derivable lines are written short or left off. That default-closed posture, rather than the premise, is what replaced the publication clearance this design retired, and it is prose in the runbook with no test behind it. Even satisfied, the premise narrows readership to the store's principals rather than to a person: the store reaches every machine on that remote, which crosses the account, machine and person boundaries the Principals section above records. A repository host's own privacy flag does not answer the question either, and reaching for it is the natural mistake: the flag reports who can find the repository, not who can read it, and a private repository's collaborators read it exactly as they would a public one. The readership is the collaborator set, which is a second query and a different fact. Readership is therefore never the thing that makes a board line safe.

**Two bars do that work, the first with a strict case, and each holds whatever the readership.** No board line carries an absolute path, because a `goal-blocked` event names its project as one and a path typically embeds the OS username; a repo is named rather than pathed, a path inside a repo is spelled repo-relative, and a machine-scoped file's is spelled home-relative. The roster row is the strict case of the same bar, naming a session, its seat claim, and the roster's own ref where two sessions share a name, and never a working directory, whatever the seat learned one from. And the operator's words never appear on a board line, a bar that covers a paraphrase as much as a quotation. Two disclosures sit outside both bars, and the move to a per-machine directory is what makes the first of them worth stating here. The machine's hostname is the directory's own name, so it rides to every machine that pulls the store whatever any line says, and a roster row's session name carries it again in the machine-scoped form the seat is required to use, which is why no alias is on offer for either. Neither is a line a bar could refuse; they are properties of the layout, and an operator weighing whether to adopt the directory is weighing them rather than the bars. Blocker text is the payload the bars matter most for, because the worker composes it: the Stop hook records its first line, on a mid-queue advance, stripped to printable ASCII and cut at 120 characters, into the blocked project's goal state, and the funnel reads that line onto a brief and a board line. The cap the peer-sessions Worker seat states, that the line carries only what its sender would put on a public board, is what stands between a worker's own sentence and that replication, and it is deliberately independent of where the board lives: it is stated against a public board so that moving the board somewhere quieter never reads as relaxing it.

**The commitment categories fall back to a stub rather than vanishing.** The seat is the only record of what it has promised or brokered, so an entry whose detail will not take the pointer form rides as a stub while the detail stays on the channel the operator used, rather than being dropped. Two independent things stop an entry riding in full, matching the runbook's own split: fit, which stubs a commitment too bulky for the pointer form however harmless it is, and sensitivity, which is not fit's special case, so an escalation is not cleared by being compact enough to fit.

**One control here is input-side, and it is not one of the bars above.** The seat runs a command in a directory named by an absolute path it took from a machine-wide append-only file any local session can write, so before anything under that path is opened a network-shaped path (two leading separators, the UNC and `//server` forms) is refused outright whether or not the seat can place it, and every other path is normalized, refused where a parent-directory segment survives that normalization, and then matched by path-prefix containment against the normalized absolute path of a repo the operator named or the seat itself resolved from disk, with one it cannot place reported unread. The two surfaces that would most conveniently answer the placement question are refused as sources by name: a roster row's repo name is the self-chosen half of a session name, and the board is the same unauthenticated cross-machine artifact the screen exists to distrust, so a placement drawn from either is corroboration taken from the surface under test. That is distinct from the corroboration rule stated earlier: corroboration decides whether an event is believed, and this decides whether a path is opened at all.

**The seat's channels are recorded, never established.** A warranted channel is a closed list of three, stated in the coordinator skill: the operator's keyboard in the session, the account-allowlisted relay thread whose broker checks each author against a one-account allowlist, and an artifact-borne authorization per Dispatch authority, excluding one the seat itself wrote, which that skill bars whoever later traces it. Two properties of the list are worth stating rather than assuming. Whoever controls the allowlisted account holds what the relay leg confers, the check establishing an account rather than a person, and the broker performing it is an external system this repository neither implements nor tests, named among External integrations in `docs/architecture.md`, so that leg rests on a precondition the kit depends on and cannot verify. And the list lives in model-facing prose inside the user-writable plugin cache, which the build's hook manifest does not cover, so an in-place cache edit could widen it with no canary and no test: the list is a convention the seat follows, not a control anything enforces. An extension to it reads the same way, as an operator decision the operator tier records, confirmed over a channel already on the list before it is treated as one.

**What no control here reaches.** Any session on this machine can write the board by resolving the path itself, which is the Principals section applying to it unchanged. Writership is wider than that machine, and the widening comes with the move: the allowlist predicate that admits the directory matches `coordinator/` followed by anything, with no machine scoping, and the sync's inbound screen runs that same predicate, so an upstream tree carrying this machine's own board path clears the screen and is rebased into this store. One directory per machine is the seat's convention rather than something the sync enforces, and the read-as-data rule above is the only thing standing between an upstream board line and a successor reading it as its predecessor's own. The directory sits outside the `docs/` write guard because it is not inside any project's `docs/`, which is a fact about the path rather than about the allowlist, and outside the frontmatter guard's tier set because that guard covers the project, type and operator tiers alone. That second exemption is deliberate: the guard's rule is CLI-authored-only, while this directory exists for direct writes by seats today, and by a Stop hook and claim-writing subagents under the contract that adds them. What holds the contract is a writer rule stated per file plus reading after the fact, never prevention. The rule is not one blanket convention over the directory: the board and each session's registry entry are single-writer, while the heavy-process claim file and the Admin request inbox are multi-writer by design, each under its own protocol, the claim scoping a delete to the writer's own session so a completing writer cannot erase a live foreign claim, and the inbox admitting the two appending writers its own contract names, the coordinator routing an operator ask and the operator session itself, a narrowing that binds an honest writer and authenticates none, since nothing validates a write here and any session on this machine, or on any machine the sync reaches, can append a line the contract does not admit. Two destructive acts reach across that writer rule rather than sitting inside it, and both are the coordinator's: its reconciliation pass prunes a foreign `registry/<session-id>.md` where the entry's own heartbeat stamp reads exited, and it releases a foreign heavy-process claim on the claim protocol's own clock. Each destroys a record its writer never agreed to lose, and each is decided from that same record, which is an unauthenticated writer's assertion, so nothing independently attests that a session id is dead; the entry's `Started:` line and its `Heartbeat:` stamp are one writer's two fields, and one hand writing both reaches the exited reading by construction. What bounds them is visibility and recovery rather than prevention. The pass writes its own commitment line before it acts, naming the readings that established the verdict and the decider, so the act leaves a record instead of a gap; every reading that cannot be made cleanly keeps the entry rather than removing it, which is why an absent, unparseable, or future-dated stamp reads as unknown and never as stale; and a pruned entry is re-created by a living writer at its next push, the entry being that session's own account of itself rewritten each time. So the writer classes are seats, a Stop hook, claim-writing subagents, and inbox appenders, that last class being what the protocol admits rather than what the surface enforces, and the reading is weaker than attribution: the sync commits everything dirty under one fixed message and the store repository's single git identity, so the history attributes a machine and a sync window rather than a writer, and on a platform where that script does not run there is history only when the operator hand-runs the store's repair path. A contested seat, meaning two sessions claiming it, freezes the board by convention and routes to the operator; convention is the whole of that mechanism, since nothing refuses the write. One further bound belongs on everything above. The board write, the pointer form, and the board-as-record leg of reconciliation have run; what stays reviewed prose whose failure modes are argued rather than observed is narrower, the cold start against an absent board, the seat handoff, the stub forms and the contest freeze.

## Type-tier governance limits

The shared tier has no owner and no cross-project coordination beyond the lock:

- `memq add-type` refuses to overwrite an existing name, on the reasoning that another project may rely on it. Overwriting is reached only by asking for it: `--update` with a body flag and `--confirm-shared` replaces that record's description and body whole, and `delete-type` with `--confirm-shared` removes it outright. Both are refused under the engine store signals, for the reason the `memq-grant` paragraph above gives.
- Deletion removes the record from the store; it does not remove it from the store's history. The tiers are tracked in a git repository that replicates to a private remote, so a deleted record's blob stays reachable in that history and on every machine that already pulled, exactly as the storage properties above describe for any other tracked content. A record that carried a secret still needs the secret rotated after a delete.
- `memq decay-prune --archive-type` now names the projects declaring that type before it retires anything, and refuses the retirement unless `--confirm-shared` is passed whenever that scan finds more than one declaring project or cannot be run at all; `--archive-operator` requires the flag unconditionally, the operator tier belonging to every project reading the store. Only one of the two is a decision point: the operator-tier gate has no unshared case, so the kit's close-out supplies the flag on those calls and it stands as a typo guard; the type-tier gate is the one that stops a pass. Because the flag is invocation-wide rather than per target, the kit's ritual runs the two tiers as separate `decay-prune` calls, precisely so satisfying the first gate does not waive the second. That split is prose-enforced in the two skills with no mechanical check, and saying so is the point: one combined call satisfies both gates and nothing refuses it. The listing is printed either way, so a single-declarer retirement still shows what it acted on. Read the gate as bounding the ordinary case rather than guaranteeing the retirement's true reach: the scan is this machine's own, and it counts past a project whose index it cannot read, naming that project on stderr rather than failing, so two declaring projects with one unreadable index count as one and the gate waives. The same scan composes `delete-type`'s cost line, so that listing can name a count short of the real one as well, with the skip line printed immediately above it. `delete-type` prints the same listing before it removes anything, and so is the second emission point for those store segment names, which are flattened local filesystem paths reaching the model at column zero under the same 260-character sanitize. Where the scan that establishes the declarers fails, `delete-type` says the reach could not be established rather than naming the current project as the sole declarer, because a cost line an operator confirms against must not assert a reach nobody measured.
- One project's usage prune still collapses read and applied evidence that other projects of that type contributed, so a memory heavily used elsewhere can later scan as idle. This one is not closed: the prune has no equivalent declarer check.
- Under a store pin the type tier's shared-retirement gate does not operate, and the reason is structural rather than a bug. The operator tier's is unconditional and a pin does not reach it. The refusal fires when more than one `projects/` segment declares the type, or when the scan cannot be run at all, and the pin collapses an instance to exactly one segment by design, so on a readable projects root the count is always one and the gate never trips. The type tier it guards is not collapsed by the pin and stays genuinely shared across every worker of that instance, so the surface the gate protects is still there while the gate is not. The listing degrades the same way: it names the instance rather than the repositories a retirement actually costs. A root still carrying pre-pin cwd-derived segments is the exception, and it is not one to rely on.
- The pin also makes type-tier membership instance-wide. `Project-Type:` is read from the pinned index, so every worker of an instance inherits one declaration whatever repository it is running in, and reads and writes that shared tier accordingly. The content stays fenced; what widens is who is in the tier.
- A tier whose last declaring project drops its `Project-Type` line becomes unreachable to the decay scan and prune, and its sidecar grows without a reader.

## Not claimed

- The "data, not instructions" framing on emitted index lines is a mitigation, not a guarantee.
- `memq`'s argument validation protects the *store's shape*. It does not protect the user's secrets.
- `delete-type` and `delete-operator` remove a record from the store, not from its history, and they are not a redaction tool. They are for the record that was written by mistake; `decay-prune`'s archival remains the path for the record that aged out, and a successor's `supersedes:` pointer the path for the record that was right and is stale now. That last one removes nothing at all: it demotes the named record in `find`'s semantic ranking, labels it on the surfaces that serve a record by name (`find`'s two channels, `recall`, `get`, `decay-scan`), and nominates it at the next decay pass, while the record stays live, fetchable by name, and unmodified on disk. One read surface the label does not reach, deliberately: index-line changes are out of this remedy's scope, so the `MEMORY.md` index the SessionStart hook emits into a session's context carries the superseded record's description unlabeled, exactly as it did before. The pointer is model-written data on the successor rather than an adjudication of the target, which is why it is bounded to nominate rather than retire, why a pin outranks it, and why the unattended vector is refused it at both the grant hook and the CLI: no pin bounds which record a pointer may name, so the exemption that bounds the granted retirement flags does not bound this one. Both of those locks sit on the CLI path, and `memory-frontmatter-guard` is the third, sitting on the file-tool path the other two never covered: it refuses every `Write`, `Edit` and `MultiEdit` on the shared tiers and refuses a project-tier pointer naming no live same-tier record. What a worker holding file tools can still write by hand is a project-tier pointer at a real target, which is the instruction-rather-than-boundary residual the destination block above states, and every read surface honors such a pointer exactly as it honors a written one. What they guarantee is that no copy of the record's body the verb can name is left in the store's own tiers: the live record, the retired copy under `archive/`, and the repair backup beside either one all go in the same locked operation, and a name whose only copy is the retired one is a target rather than a refusal. The `.bak` of the two index files and of the usage sidecar go in that same operation, whoever wrote them, so the tier keeps no local copy of the removed record's index line that the verb can name. What they do not touch is the git history the storage properties above describe, nor the outcome journal, which no delete touches and which, unlike the backups and temps above, does replicate to the remote, nor the session transcripts and `history.jsonl` under the store root, which keep whatever a session printed or typed: a `get` of the record puts its body in a transcript and an `add-type --body` puts it on a recorded command line, so a record that carried a secret needs that secret rotated whatever this verb removed. Of a delete that completes, two things can leave a copy in the tier, both of them named in the storage properties above: a backup the sweep reported it could not remove, which deliberately does not fail the command, so a zero exit is not on its own evidence the residue is gone; and a `<file>.tmp.<pid>` stranded at one of those three paths by a rewrite killed between its write and its rename: `MEMORY.md.tmp.<pid>` at either index, holding that index as it then stood with the record's line in it, and `usage.jsonl.tmp.<pid>` at the sidecar, holding the read and applied stamps recorded against the record's name, because the sweep names the `.bak` at each path rather than the temp beside it. The second takes a hard kill to exist, and neither ever leaves the machine, `*.bak` and `*.tmp.*` both being never-sync patterns. Nor do
they touch the derived vector index at the store root
(`memory-index.jsonl`), which holds per record a name, a content hash of the
body, and the embedding built from it. That file is untracked by the store's
own `.gitignore` and never syncs, and the next semantic sweep that can read
the tier prunes the entry, so the residue is one local file until then. What
it holds is a content hash and an embedding rather than the prose, and the
bound this document rests on is the file's reach rather than the derivation's
strength: it never syncs, and the next sweep drops the entry. Embedding
inversion is an established technique against exactly this artifact class, so
treat the vector as recoverable content that happens to stay on one machine,
not as a safely irreversible derivative.
- The delete verbs are governed by the store-signal refusal and by nothing else on the agent axis. `readonly-agent-guard` is a denylist over shell verbs and tree paths and names no `memq` rule, because memq writes the external store rather than the reviewed tree, so a strict read-only agent holding Bash is refused these verbs inside a fleet worker (where the store signals are present) and is not refused them on an attended session. What stands there is the ordinary permission flow, which prompts unless a settings file grants the command. The kit ships no such grant, so the attended-session control is a prompt the operator answers rather than a guard, and a settings grant for `memq` added later would remove it without touching anything in this document.
- `decay-prune` is auditable, and reversible only in the weak sense that archiving is demotion rather than deletion: it prints everything it removed, leaves one generation of backup, durable in the project tier and not in a shared one, where the next `delete-type` or `delete-operator` sweeps it, and a retired memory keeps its description in the archive's own index and still answers `memq get` by name. The rollup is the irreversible half, discarding expired entries' prose for a tally and folding the usage sidecars' raw stamps into one rolled record per file. `--drop-malformed` rides it and is the third irreversible operation on this verb: it removes outright the unparseable usage lines every other read path and every other rewrite preserves, reaching the project tier and either shared tier the same call reaches rather than only the tier whose evidence line reported the skip, and leaving them in that one generation of backup. Its bound is that it refuses a tier where no parsed stamp would survive the drop, keeping every line and leaving that sidecar byte-unchanged, so the operation cannot empty a tier's usage evidence; a refusal on one tier does not stop the tiers where the drop is partial.
- Retention is bounded but not fixed. A memory's decay thresholds extend by 30 idle days for each distinct calendar day it was applied, capped at 365, so the most extended memory becomes an archive candidate at 425 idle days. That ceiling bounds the idle clock alone: a `supersedes: <name>` pointer on any live record of the tier makes the record it names an archive candidate whatever its clock reads, so the 425-day figure is the longest a record survives on idleness rather than the longest it survives. That pointer is authored data rather than a measurement, which is why it nominates and never retires. A `pinned:` frontmatter field exempts a memory from candidacy entirely, pointer included, and makes the prune refuse it by name. The pin binds the decay pass and not the delete verbs, deliberately: a pin is set and revoked only by editing the memory file, and no shared tier admits a hand edit, which `memory-frontmatter-guard` now enforces rather than leaving to convention, so a pin that also stopped `delete-type` and `delete-operator` would leave a pinned shared record removable by no path at all. That guard ships with no hatch of any kind for a pinned shared record, deliberately: `--update` carries a record's existing frontmatter across and so neither adds nor removes a `pinned:` line, and a content-scoped exemption would permit that delta in both directions, letting any writer silently remove a pin, which is a quieter form of what `memq-grant` withholds from an unattended worker. The delete verbs remain the path that retires a pinned shared record, and a hatch, whether a `pin`/`unpin` verb pair or an override signal the guard honors, is one verb's worth of work whenever a real case for one appears. The exemption is set only by editing the memory file and is revoked by deleting the line; a `decay-scan` that finds any pin counts the whole population and lists the first ten with a counted remainder, so the exempt population cannot grow unobserved. Because archived content is still served by name and by the recall digest, retiring a memory does not remove anything the storage properties above describe: a credential written into a memory persists after archiving exactly as it persisted before.
- Inside an engine worker, the store pin is effectively a single variable, because the gate it inherits is set by the engine rather than by anyone attacking it. The `KIT_MEMORY_ROOT` pair is already true on every spawn, so within that environment one repository-carried `KIT_MEMORY_PROJECT` is honored with no second signal an attacker has to supply, and a plan worker runs inside the repository it is working on. A valid-but-different value relocates that worker's whole project tier to a sibling segment under the engine's root, so its writes land where no adjudicator looks and its reads pull another segment's content into context; an unusable value denies that worker's memory subsystem outright, loudly. This is the `KIT_RUN_ID` residual below, widened from the pending tier to the project tier, and it is bounded the same way: everything stays inside the instance's own store root, which the engine allocates per instance, so the pin is never the separator between instances. The mitigation is the engine's rather than the kit's, and it is to set the variable explicitly on every spawn, which beats a value inherited from the parent environment. It does not beat configuration that runs inside the spawned session's own shells afterwards, so the mitigation is narrower than it first reads.
- Run scoping in the pending tier is not isolation. It keeps two runs from reading each other by ordinary operation, not by enforcement: the only thing selecting a run's directory is that process's own `KIT_RUN_ID`, which any session holding Bash can set to another run's value.
- The pending tier bounds what enters the *project* record without review only for a spawn that carries a run id. Under a pin, a spawn without one (the reviewer and the phone-driven shapes) is deliberately told to write memory files and their `MEMORY.md` index lines straight into the shared instance record, because a pinned project tier is that instance's ordinary adjudicated tier and those shapes are the attended half of the instance. It is a decided behavior, not an escape, and it means the quarantine covers plan-execution runs rather than every write. It does not bound the type tier: `memq add-type` inside a run still writes the shared type tier and its index directly, provenance-stamped rather than quarantined. Under the engine that store is per-instance, so the reach is that instance rather than the machine, but the write is unadjudicated. That bound is an external precondition, not something this repo enforces: it holds only while the engine points `KIT_MEMORY_ROOT` at a per-instance store, so a change to how the engine chooses that root re-opens this entry.
- Installing the optional embedding stack pulls transitive dependencies whose published advisories have no fix version at the pinned release. Accepted as a supply-chain risk of an optional, locally-installed stack rather than mitigated: the install is pinned to a reviewed version and runs with lifecycle scripts disabled, but a vulnerability with no patch available is not something a version pin closes.
- The output style's parity test bounds drift, not tampering. It holds `plugins/claude-kit/output-styles/kit.md` byte-identical with the doctrine's register core in the repository, which is a maintenance control against two copies diverging under editing. The file's security-relevant property, that it becomes system-prompt content in every main-thread session, is attested by nothing once the payload is installed, per the manifest coverage above. Its frontmatter pins are the same kind of control: `keep-coding-instructions: true` is pinned because absent or false it silently strips Claude Code's built-in coding instructions from every kit session, which is a correctness failure caught by review and by that test, not a boundary.
- Nothing here defends against an actor who already has write access to `~/.claude`. Such an actor can already execute code through hooks and settings.
