# Security model

What the kit's local state assumes, what it guards, and what it does not claim. Written as preconditions that can be checked, because a premise stated as a reassurance ("the store is trusted") cannot be re-tested when something changes underneath it, and one did: the memory store's trust premise was accepted when the store was per-project, then invalidated when a machine-wide shared tier was added, and nothing forced a re-check.

## Principals

**Within one machine account, there is exactly one principal**: that account's user. Every project session, every dispatched subagent, and every hook runs as that user with full read and write access to `~/.claude`. Anyone who can write there already has code execution through hooks and `settings.json`, so no control in this document defends against that.

**Across the deployment, there are several.** The kit is shared with other team members, the repositories sync across multiple machines, and the same person operates it under two work accounts and one personal account. That means kit code, and any repository-carried configuration, crosses account and person boundaries routinely. A control whose only justification is "one person, one machine" is not justified here.

Three consequences follow, and they are why several of the sections below are stricter than a single-user store would warrant:

- **The store is not a security boundary between projects.** Per-project separation is a convention the tooling follows, not a control the design enforces. Any session can read and write any project's memory directory by resolving the path itself.
- **The shared project-type tier is a cross-person surface, not merely a cross-project one.** Content one person writes is read into another person's session context, wherever a type tier is shared rather than machine-local.
- **A repository is a distribution channel for configuration.** Anything a synced or shared repository can set for the shell that opens a session (`terminal.integrated.env.windows` in a committed `.vscode/settings.json`, a `devcontainer.json` env block, an `.envrc`) reaches an account that merely cloned it. Environment-driven behavior is therefore attacker-reachable in a way it would not be on a single-operator machine.

**What is machine-local versus shared is worth checking rather than assuming.** The kit payload is shared by design. Whether a given store directory syncs depends on how that machine is configured, and the tooling neither knows nor enforces the answer. Treat a type tier as shared unless you have confirmed otherwise for that machine.

## The memory store, per tier

The store lives at `~/.claude/projects/<sanitized-cwd>/memory/` (project tier), `~/.claude/memory-types/<type>/` (type tier), and `~/.claude/memory-operator/` (operator tier). The `<sanitized-cwd>` of the project tier is the working directory's path with non-alphanumerics flattened; when the session runs in a git worktree, it is the MAIN checkout's path, because memq follows the worktree's `.git` pointer to the main checkout only when a two-way handshake holds (the pointed-at gitdir has the `.git/worktrees/<name>` shape, its `commondir` and back-pointer resolve, and `<main>/.git` is a real directory). That handshake is a trust boundary in itself: a `.git` pointer file is repo-adjacent data in a directory the session cd'd into, so a planted one must never redirect memory reads and writes, and only a link git itself maintains carries the back-pointer the handshake checks.

**Project tier.** Authored by that project's sessions and emitted into context by the kit's own SessionStart hook (the index emission below). Inside the trust boundary in the ordinary sense: the thing that wrote it is the thing that reads it. That condition, and not any harness behavior, is what leaves the tier unfenced where it is unfenced; Claude Code's auto-memory may also inject the same index when it is enabled, but nothing in the kit depends on whether it does.

Under a store pin that description does not hold, and the difference is the point of the pin rather than a side effect. One pinned tier serves every repository the instance works in, so the Principals section's "the store is not a security boundary between projects" stops being a caveat about what the tooling fails to enforce and becomes the operating condition: cross-repository sharing inside one instance is the intended behavior, because the instance is the entity meant to accumulate, not the repository. Two consequences follow. The tier's content is fenced on the way into context, per the fence discussion below. And the containment that remains is the store root: every memq-mediated write stays inside the root the engine chose for that instance, which is why that root, not the segment, is the boundary. For the memory files a session writes with its own file tools, the destination block is an instruction rather than a boundary, the same status this document gives the data-not-instructions framing.

**Type tier.** Authored by *any* project on the machine that declares `Project-Type: <type>`, and read into the context of *every* project declaring that type. This is a machine-wide shared read-and-write surface. A claim that no store-controlled content reaches a session's trusted context is false by design for this tier.

**Operator tier.** `~/.claude/memory-operator/`, authored by *any* project on the machine and read by *every* one of them. It is the type tier's sharing without the type tier's opt-in: no declaration gates it, so it is machine-wide by construction rather than by a project's choice, and the same sentence holds, that no-store-controlled-content-in-trusted-context is false by design here. Its content is fenced wherever it enters context, on the same reasoning the type tier's is. Two properties narrow the surface rather than widen it: authoring is CLI-only, so a memory arrives through `add-operator` under the tier's lock rather than through any session's file tools, and the tier is not emitted at session start, so it enters context only through a command a session chose to run. A `machine:` field scopes a fact to one box; it is a label rather than a boundary, and the reader re-validates it against the writer's own identifier gate before printing, so a hand-edited or synced value cannot put free prose on a search line.

**Pending tier.** `<project tier>/pending/<run-id>/`, present only inside a run the external engine spawned (the `KIT_RUN_ID` entry below). Authored by that one run, read back by that same run, and entered into the project tier only by an adjudication verdict the engine applies. It exists so a headless worker's memory writes do not enter a shared record unreviewed. A pending memory carries no `MEMORY.md` index line: the index is written at promotion. Pending content reaches a model's context only through the run's own memq reads (`find`, `get`, `recall`, `recent`), and none of them fences it. That is the resolution rule rather than a gap: each resolves the single directory the calling process's own `KIT_RUN_ID` names, so the run reading a pending record is the run that wrote it, and there is no provenance gap for a fence to frame. What `memory-session.js` emits for a run is the destination path, not the tier's content, and that path is fenced as the configuration it is (the destination block below).

The scoping is a resolution rule, not an enforced boundary. A process resolves the single pending directory its own `KIT_RUN_ID` names and enumerates no others, so runs do not see each other in ordinary operation. Nothing stops a session that holds Bash from setting a different id and resolving another run's directory, which is the same limit the Principals section already states for every tier.

Six paths carry store content into a model's context, and they are not equally guarded. All six carry shared-tier content, type and operator alike; the first also carries the project tier's index, the digests carry project records too, and the semantic block reaches further than any of them:

| Path | Guard |
|---|---|
| SessionStart index emission (`memory-session.js`), both the type tier's index and the project tier's | Read as a fixed-size prefix of the index file, so session start never pays for a grown index; each line reduced to bounded printable ASCII; line count and line length capped, with truncation announced as a counted remainder; two-space indented so a line cannot forge an unindented block; framed as data rather than instructions. Both indexes share one emitter, so the treatment cannot drift between them; the project index caps at 60 lines against the type tier's 30 |
| `memq get <name>` body | Length-capped, and for the type tier fenced the same way: provenance and a data-not-instructions line on stdout, every body line two-space indented so column zero stays the tool's own voice. Not charset-sanitized, because a body is a document where newlines and punctuation are legitimate content |
| `memq recall` digest | Every field reduced to bounded printable ASCII with the double quote barred, so no record can forge a line, a coverage claim, or a truncation remainder; total output capped by the line budget; the type-derived records framed as data rather than instructions |
| `memq recent` digest | The same guards as `recall`, over a time window instead of the whole store, and extended to the journal: this digest emits one line per journal entry rather than one per key, and the journal is the surface it cuts last, so under a pin those per-entry summary lines are what fills the budget, and they carry the fence with the rest of the pinned store's records |
| `memq unstamped` report | Every field reduced to bounded printable ASCII, the same treatment as the digests: the record name charset-closed by the store's filename gate, the description capped, the age numeric, the tier token and coverage wording the tool's own, and the type tier's coverage line naming the declared type, which is charset-closed by the same gate as any other identifier the store prints. Shared-tier lines two-space indented under one framing line named by contribution, so a tier that put no line in the run is not claimed by the fence. It carries no line budget, unlike the two digests: its output is bounded by the records this machine's own stamp hook opened inside a short window and never stamped, so no other worker's activity inflates it, and truncating an adjudication list would hide the record the judgment is owed on |
| `memq find`'s semantic block, emitted only where the local embedder is installed | One framing line in the shared fence wording, every hit line two-space indented. Its reach is machine-wide (every project store, all three tiers, every archive), which is why it is fenced where the lexical channel is not. Each line carries charset-closed identifiers and the tool's own words: the memory name and store segment, both closed to `[A-Za-z0-9_.-]` by the store's own gates; a fixed tier label; a similarity figure; an applied-day tally and the age of the last application, both computed here from the tier's own stamps rather than read from the record; and a `machine:` value re-validated at admission against the same gate its writer applies, dropped entirely when it fails, so a hand-edited or synced file cannot push free prose across the path. No description and no body crosses it. The withheld line that follows the block under archive suppression carries no store text at all: two counts and a similarity figure, all this tool's own arithmetic, which is why it sits at column zero |

The run-scoped destination block carries content into context and differs from the six above in its source: the block `memory-session.js` emits names the pending directory, and that path embeds `KIT_MEMORY_ROOT`, so its content is environment configuration rather than store content, and the environment is attacker-reachable per the Principals section. It is emitted faithfully or not at all (a value that would be truncated or reduced stands the session down instead), and it rides on its own indented line inside the block's data fence, so printable-ASCII prose set as a store root reads as a filesystem destination and not as an instruction.

The pin destination block is the same shape: under a store pin (the `KIT_MEMORY_PROJECT` entry below), a session with no run id is told where its memory files go, and that destination embeds the pin as well as the store root. Same treatment: emitted faithfully or not at all, on its own indented line inside the block's data fence.

The project destination block is the third of that family and the one with the widest trigger, since an ordinary session with no run and no pin still gets it. Its path embeds `KIT_MEMORY_ROOT` the same way, and it takes the same faithfully-or-not-at-all rule, but it answers an unemittable path with a third outcome the other two do not have: it withholds the directory, emits the index lines anyway, and points the session at `memq`, which resolves the directory itself. The write convention goes with the directory rather than staying behind, since a session that cannot be told where the directory is cannot follow an instruction to write a file in it, so what it is told instead is to report the condition rather than guess a path for one. It does not stand the session down. The reason is that a stand-down is a response to an environment that asked for something the kit cannot deliver, and an ordinary session has asked for nothing: standing it down would cost a developer their memory writes over a path this block happens not to be able to spell.

Its steering condition is the least gated of the three that decide where the model's own file tools write memory: the store pair alone reaches it, two variables and no `KIT_MEMORY_PROJECT`, where the pin destination block needs all three. Fewer preconditions means broader reach, which is why this block is the one to audit first. The consequence to keep in view is that a store root pointed inside a cloned repository puts a session's memory writes into that repository's working tree.

**The project index emission carries project-tier content into context with no command invoked at all, at every session start, and it fences unconditionally.** The `recall` and `recent` digests in the table above are automatic in the weaker sense of running at a fixed point in a workflow; this one needs nothing invoked. Under a pin, the justifying condition below (the project that wrote it is the project reading it) is false by design, so the writer is another of the instance's workers. The emitter does not key on that: it reduces, caps, indents, and frames the project index in every state, which is stricter than the rule below requires. That is deliberate and should not be "corrected" toward the looser rule, because the block's own trigger is the widest in the hook and a per-state fence would be one more branch to get wrong.

Those nine hops (the table's six rows, plus the run-scoped, pin, and project destination blocks) carry the fence, and the fence rather than the charset is the control on a body. Two further surfaces carry store content at column zero and deliberately do not fence it, both under the same reasoning and both over the project tier alone (find's withheld line and every coverage line also sit at column zero, but they carry counts and figures this tool computed, at most alongside a charset-closed identifier such as the declared type name, rather than store prose, so no fence question arises for them): `memq find`'s lexical channel, one bounded, charset-closed, quote-stripped line per hit, labelled by tier and never a body, over the caller's own tiers; and `memq unstamped`'s project-tier lines, the same shape over the records this project's own sessions opened. Both are guarded by construction rather than by framing, because a single sanitized line cannot forge a block, and that narrower guard is the claim to check rather than assuming the fence covers it. Both take the fence the moment the reach widens: each command indents its type-tier and operator-tier lines under the full framing line, and `unstamped` also fences its project lines under a store pin, since a pin makes that tier another worker's writing. The narrower guard is tied to the narrower reach, which is why `find`'s semantic channel, spanning every store on the machine, sits in the table above under the full fence rather than sharing this exception. The exposure it leaves is real and worth naming: under a pin, a description another of the instance's workers wrote arrives in the tool's own voice, as it already does for the type tier. The exposure that distinguishes them is frequency rather than guard: the index emission and both digests are automatic, `recall` at every effort start and `recent` at every close-out, while a `get` is a deliberate fetch of a named record.

The sync trigger (`memory-session.js`) is a further path into context and needs no fence, because it carries no store-derived text at all. The hook's own checks are read-only git subcommands and never a fetch, so a session start costs no in-hook network round trip and the "behind" figure it may report is what this machine last knew rather than what the remote holds now; the fetch, rebase, and push happen in a detached background runner (`doctor/sync-store.ps1`) the hook spawns off the session's critical path. Every value in an emitted line is an integer parsed out of a fixed count, a boolean read from whether `git status --porcelain` printed anything, or a fixed literal from the hook's own source (a state-file reason code is a lookup key mapped to a fixed literal with a fallback, never emitted text); no path, branch name, remote URL, or state-file string reaches the line, which is stricter than sanitizing and is what makes the fence unnecessary rather than merely absent. Only three states speak at all: a recorded standing-down gate, a failure streak past a week, and a broken sync chain (a spawn that recorded no outcome past a stale window); a healthy sync is silent.

Several conditions gate it, and they gate the spawn more tightly than the line. The store root must hold its own `.git`, checked by a stat before any git call runs, because git discovers repositories upward: without that check a store root merely sitting inside an unrelated checkout would be described as the memory store. Every `GIT_*` variable is stripped from the child environment (not only `GIT_DIR`/`GIT_WORK_TREE`), because a repo-carried `GIT_COMMON_DIR` would otherwise redirect even a `--local` config read at an attacker-supplied config. The background spawn, which commits, fetches, screens, rebases, and pushes, runs only when the store is the kit's OWN repository, established by the local git config key `claudekit.memorysync` rather than the marker-bearing `.gitignore` that also proves ownership elsewhere: a committed file rides into a clone and could be planted, but a `--local` config value is never cloned, so this gate is not forgeable by shipping a repo at the store root. The spawn also runs only at the default `<home>/.claude` root (an environment-overridden root is synced by the operator's own hand, since `os.homedir()` follows the attacker-reachable `USERPROFILE`, so ownership rather than the path is the security gate) and only on Windows, where the PowerShell runner exists. The runner screens the inbound direction as tightly as the doctor's probes screen the outbound: every entry of the incoming upstream tree is checked by its mode and its path against the allowlist before the rebase touches the working tree, so a rename, a duplicate-content push, or a symlink at an allowlisted path cannot materialize a disallowed file (`settings.json`, a credential) in the store root, where nothing un-writes it. The trigger is silent under a store pin the kit cannot honor and under a run-scoped session (a fleet of run-scoped workers each spawning a sync would be contention with no owner), whose own block already claims the whole of what this hook says about where the store stands; it rides beside every other state, a localized pin stand-down included, exactly as the decay nudge does.

The embedder-absence nudge is the same shape and needs no fence for the same reason: it reports whether the local embedding stack is installed, and every word of it is a literal in the hook's own source or the install remedy the doctor and `memq find` share, so nothing store-written or machine-derived rides it. It is gated identically, silent under a stand-down and inside a run.

**The sync repository's allowlist is the boundary the whole replication design rests on, and it is not self-enforcing.** The store root holds `.credentials.json`, `settings.json`, `history.jsonl`, and every session transcript, so a git repository there is one careless add away from publishing them. The gitignore excludes everything and re-includes only the memory tiers, admitting only the file forms those tiers write. But ignore rules alone do not close it: a `.gitignore` planted inside a directory git traverses outranks the root file and can re-include what the root excluded. So the guarantee is the rules plus four direct probes the doctor re-derives on every run, reading the four surfaces a path can reach by, the ignore rules, the worktree, the index, and the object history. Each answers a question the others cannot: a tracked file ignores the ignore rules entirely, and a blob in history survives being untracked. Any drift in the allowlist is a FAIL rather than a warning, and a probe that cannot answer is also a FAIL, because an unproven negative is not a clean one. The commit path refuses rather than repairs: it will not add or commit unless both managed files verify canonical, and it restores the index it found rather than leaving a disallowed path staged.

**Project-tier output is unfenced only while the project that wrote it is the project reading it.** That is the whole justification, so it holds exactly as far as the condition does. Under a store pin the condition is false by design: one tier serves every repository the instance works in, so a memory written while working one repo is read back by a session working another, and the writer is a spawned worker rather than the attended session reading it. That is the same sentence this document uses to justify fencing the pending tier, so pinned project-tier bodies and pinned digest records carry the fence too. The decision is keyed on whether a pin is in effect, never on the tier's name, because the name is precisely what stops being a reliable signal.

One record type is outside that rule today: `recall`'s journal lines print at column zero under a pin, each carrying the latest summary another of the instance's workers wrote for that key. `recent`'s journal lines are fenced, and the two differ because the surfaces differ in size, one line per key against one line per entry inside a window. The residual is real and narrower rather than absent, and it runs more often, since `recall` fires at every effort start. `docs/backlog.md` carries the item.

A second, narrower residual sits on `recent`'s framing line. The line is decided from the type-derived records the digest built, not from the ones that survive the budget cut, so a pinned digest whose every type line was cut still names the type tier in its provenance line. The direction is over-claiming provenance rather than under-fencing content: no line loses its indent, and every fenced line still rides under a fence.

## Storage properties

Plaintext. The three memory tiers are versioned: `~/.claude` is a git repository once the sync repo exists, and that repository replicates to a private remote once one is configured. The single-generation `.bak` `memq decay-prune` writes before a rewrite is the only local recovery for an overwritten memory, and the next pass overwrites it; that is unrelated to, and much weaker than, what git itself now retains.

A credential, connection string, or token written into a memory file or a journal entry is committed, and on a store with a remote pushed, with no further deliberate act: on Windows the background sync runner does both at the next session start, and the doctor's `-Fix` does both on demand. From there it persists like any other tracked content: a later edit or local delete leaves the earlier blob reachable in history, and once pushed it reaches the remote object history too, recoverable by anyone who can read that repository until the history is rewritten everywhere that cloned it and the credential rotated. The sync boundary is path-shaped rather than content-shaped: the allowlist probes prove a path sits inside a memory tier and takes a form `memq` writes, and nothing on the commit, push, or check path reads a byte of content looking for a secret. The only control preventing the write in the first place is the instruction in the `memory-system` skill telling the model not to record one. Sync does not weaken that instruction, but it changes what a lapse costs: what stayed on one machine now reaches every machine that pulls. There is no redaction, no scanning, and no mechanical guard, on write or on sync.

## Environment overrides, and why they differ

Variables that redirect where the tooling looks are gated, and deliberately gated differently:

- **`KIT_MEMORY_ROOT`** relocates the store root, and is honored only when `KIT_MEMORY_ROOT_ALLOW_DATA` is also set. It selects *which data reaches the model*, and, since the `memq-grant` hook below conditions on the same pair, it also selects whether one fixed Bash command shape bypasses the host's permission prompt. That second consequence is newer than the gate's original data-only rationale, and it is why the pair is now load-bearing for execution and not only for content. A third consequence is the background sync's: the auto-sync spawn is gated both to the default `<home>/.claude` root and to a store the config key marks owned, so relocating the root with this variable does not arm the automatic commit-and-push against the relocated directory. That is deliberate, and it is why the gate is ownership rather than the path: `os.homedir()` follows `USERPROFILE`, which is attacker-reachable, so a path check alone would move with the attacker while the un-clonable config key does not. Set without its signal, it is ignored, the real store is used, and a note goes to stderr.
- **`KIT_PLUGINS_ROOT`** relocates the plugin payload the `memq` shim executes, and is honored only when `KIT_PLUGINS_ROOT_ALLOW_CODE` is also set. It selects *which program runs*.
- **`KIT_RUN_ID`** routes a run's memory writes into the pending tier and scopes its reads to that tier plus the main one. It is honored only alongside the `KIT_MEMORY_ROOT` pair above, and carries no separate signal of its own because it selects a subdirectory *within* an already-gated store: the store's gate is the one that decides whether the redirection happens at all. Set without those signals, the memory routing is ignored, the session behaves as an ordinary attended session, and a note goes to stderr. One deliberate exception to that word: a goal-release event still carries the id in its `run` field, since the field is correlation metadata on an outbound record rather than a routing decision, and it is validated by the same grammar. The value becomes a directory name, so it is validated against a conservative token grammar that also refuses the Windows directory-name shapes that alias onto a different directory than they spell (dots-only names, trailing dots, reserved device stems) and is folded the way the platform's filesystem folds it. A value that fails the grammar is refused rather than fallen back on, because a silent fallback would place an unadjudicated write in the shared record.

- **`KIT_MEMORY_PROJECT`** replaces the `projects/<segment>` directory name, which is otherwise derived from the working directory, and is honored only alongside the `KIT_MEMORY_ROOT` pair. Like `KIT_RUN_ID` it carries no signal of its own, because it selects a directory *inside* an already-gated store. It exists because an engine instance spawns workers with three different working directories (a plan worker runs in the repository it is working on), so without it one instance's store fragments into a tier per cwd and a memory promoted out of a plan run lands where no later run and no reviewer reads. Set without the store pair it is ignored, the cwd derivation stands, and a note goes to stderr; set with the pair and unusable as a directory name it is refused loudly rather than falling back, since a silent fallback would scatter the instance's memories back across per-cwd directories invisibly. It answers the same grammar `KIT_RUN_ID` does, from one shared predicate.
- **`KIT_EMBEDDER_ROOT`** relocates where the optional embedding stack is loaded from, and is honored only when `KIT_EMBEDDER_ROOT_ALLOW_CODE` is also set. It selects *which program runs*, the same class as `KIT_PLUGINS_ROOT` and deliberately not the data class: the install location is spelled from the home directory rather than from the store root, so a store redirect gated as data can never move where code loads from. The stack is located by a direct file check rather than by module resolution, because resolution walks upward through parent `node_modules` and would make "installed" depend on where the process happened to start. Set without its signal, it is ignored, the real location is used, and a note goes to stderr.
- **`KIT_EVENTS_PATH`** redirects the goal-event sink `emitGoalEvent` appends to, and is honored only when `KIT_EVENTS_PATH_ALLOW` is also set. Unlike the others it selects *where data is written* rather than what reaches the model: the sink is an outbound notification feed an external watcher reads, not content injected into a session. Set without its signal, it is ignored, the real `~/.claude/kit-events.jsonl` is used, and a note goes to stderr. The intended users of both signals are the repo test suite and the hook canary's own goal probe, which point the stream at a throwaway file. What the signalled override grants is worth naming exactly, because "sink" understates it: the named path is appended to, and past 1 MB renamed to `<path>.old`, replacing any previous file of that name. Pointed at a regular file the user can write, a goal release therefore appends to it and can move it aside. A symlink or junction at the sink is refused (the regular-file check is an `lstat`), and the rest sits inside the accepted framing above, that the gates remove accidents rather than contain a deliberate actor.

**What the gates buy, stated plainly, because the uniform rule invites over-reading.** An actor who can set one variable from a committed file can set two in the same file, so against the repository-as-distribution-channel threat above, a second signal is not a mitigation. What it does buy is real but narrower: one auditable rule that holds across every override, so a reviewer checks a property rather than re-deriving a per-variable argument, and the elimination of the accidental case, where a variable set for an unrelated reason or inherited from a parent process silently steers a session. Read the gates as removing accidents and making deliberate redirection legible, not as containment.

**The ungated residual under all of them.** Every default path above ends in `os.homedir()`, which reads `USERPROFILE` on Windows and `HOME` on POSIX. One of those, set from the same committed file, relocates the store, the plugins root, and the event sink together, with no second signal anywhere. The Principals section places an actor with write access to `~/.claude` outside every control here; this is the adjacent case it does not state, an actor who redirects what the kit believes `~/.claude` is. It is a broader compromise than any single override (the harness's own settings and transcripts move with it), which is why no gate here addresses it, but a claim that every path-redirecting variable is gated is only true one level down from this one.

**`KIT_EXTERNAL_ENGINE`** redirects no path and carries no gate, and it is one of two deliberately ungated behavior-steering variables here (the other, `CLAUDE_CODE_SESSION_ID`, follows below), because an external engine must be able to declare itself on a spawn it already fully controls. Set to `1` it stands five hooks down: `session-start.js` drops its drive-to-completion push, `branch-reaper-nudge.js` and `kit-version-nudge.js` go silent, `hook-canary.js` returns before its first probe, and `kit-compact-gate.js` allows every auto-compaction (the compaction-gate section below carries why that is a scope decision rather than a lost control). `stop-docs-hygiene.js` also downgrades its block to advisory. Two consequences belong here rather than in the architecture doc, because they are the loss of controls this document credits elsewhere: the canary's integrity check (the SHA-256 manifest comparison) and its `memq-grant` both-direction probes do not run under the marker, so in a fleet worker neither the tamper detection nor the grant's health check is active, and the Stop-scan backstop for scratch reaching `docs/` becomes advisory. Setting the marker is therefore enough to turn off the detection this document describes, without any second signal. That is accepted rather than mitigated: the actor who can set it on a session is the actor who spawned that session, and the controls it disables all report to an attended operator who is not present in a spawn. What it means for the reader is narrower than it sounds and worth stating exactly: the manifest check protects an attended machine against a hook edited in place, and it has never protected a fleet worker, whose payload integrity is the deploy's concern.

**`CLAUDE_CODE_SESSION_ID`** is the second deliberately ungated behavior-steering variable, and the only one here the kit does not own: the harness sets it in every tool shell it spawns, naming the session the shell serves. The `/kit-goal` CLI's `arm` is its only reader, and what it steers is the leash binding: an arm run inside a session binds that session at arm time instead of arming unbound and waiting for a claim point. No second signal gates it, because the pairing rule above exists to remove accidents, and the accident case here is handled by corroboration instead: the id binds only when it is UUID-shaped and a transcript file with that basename exists under the harness's transcript store, checked before anything is written, so a stale export, an inherited value, or a repo-committed terminal env carrying a UUID that names no real session on this machine arms unbound and falls back to the claim points, exactly as an arm with no variable at all. What the corroboration cannot refuse is a value naming a real transcript on this machine that is nonetheless not the arming session; that binds a leash no session enforces, is visible in the arm output's binding report and in `/kit-goal status`, and re-arming recovers it, the same bounded, recoverable blast the claim predicate's accepted risk below states. Two smaller residuals ride with the mechanism: the transcript scan can store another project's transcript path in this repo's `.kit/goal-state.json` when the id's first match lies elsewhere (the path is never surfaced, per the goal-state section below), and the scan composes its candidate paths from `os.homedir()`, which the ungated-residual paragraph above already places outside these controls. The variable is undocumented upstream and can change or vanish without notice; either direction degrades to the unbound arm and the claim points, never to a wrong bind.

Two further variables, **`KIT_SPAWN_VECTOR`** and **`KIT_RUN_SECTION`**, redirect nothing. They are recorded as provenance in a pending memory's frontmatter, reduced to bounded printable ASCII at the write boundary so a value cannot forge an additional frontmatter field or break the document's structure.

No gate may be loosened to match another, and the reason the store root carries one at all is worth keeping: it was originally ungated on the reasoning that it redirects data rather than code. The project-type tier voided that. The SessionStart hook reads the store, so a redirected root supplies content a session sees before the user types, which makes it a behavior-shaping input and not merely a data path.

The precondition the old gate rested on was **the launching environment is trusted**. In a deployment where repositories sync across machines, accounts, and people, that precondition does not hold: a committed `.vscode/settings.json` (`terminal.integrated.env.windows`), a `devcontainer.json` env block, or an `.envrc` sets environment for whoever opens the repository. The gate exists because cloning a repository must not be enough to steer what a session reads.

## The `memq.cmd` residual

On Windows, `memq` resolves to a different wrapper per shell: PowerShell resolves `memq.ps1` (arguments splat directly onto node), Git Bash resolves the extensionless `memq` (`"$@"`), and only a caller inside `cmd.exe` reaches `memq.cmd`.

`memq.cmd` forwards arguments as `%*`, which `cmd.exe` substitutes into the command line before parsing it. An argument carrying an odd number of double quotes therefore ends the quoted region, and a following `&` starts a second command. This is confirmed by probe, not theoretical.

What covers it: the `memq.ps1` and sh wrappers keep the two common shells off that parser entirely, `memq` strips double quotes from free-text fields at the write boundary, and the skill instructs the model to compose summaries itself rather than pasting raw tool output into an argument.

The limit of that coverage: the write-boundary strip protects stored *summaries and descriptions*, not memory *bodies*, which are length-capped only.

This one is rated higher than a single-operator store would warrant. With a shared kit and a shared type tier, a body one person wrote can reach another person's command line, so the exposure is no longer bounded by one operator's own paste.

## Locks are availability, not integrity

The lockfile serializes rewrites of shared files. Two properties to know:

- A lock path can be wedged by a directory, or by a file whose contents are valid JSON but not a lock record, either of which the stale-break correctly refuses to remove. There is no in-tool recovery; the fix is deleting the file by hand.
- `decay-prune`'s rewrite copies any bytes appended after its read onto the replacement before renaming, but a window remains between that copy and the rename in which one concurrent append can be lost. That is one usage stamp, and it matches the tolerance the sidecar's readers already carry for torn appends.

## Hooks fail open, and what that costs

Every kit hook swallows errors and exits 0 silently, by design: a hook bug must never trap a session. The monitoring consequence follows directly and is easy to miss.

**Absence of a nudge, a stamp, or a warning is not evidence of health.** A hook that cannot run, cannot resolve its dependencies, or cannot write produces exactly the same observable output as one with nothing to say. The hook canary exists because of this, and it probes cache consistency rather than correctness.

## The guard hooks

Five PreToolUse hooks mechanically enforce the agent access model: four guards that deny, and one grant that allows a single fixed command shape. Each is the teeth under a skill's routing wording, and none is a security boundary: by the Principals section, every agent runs as the one machine principal, so the guards defend the work against well-intentioned-but-wrong agent behavior (a reviewer "fixing" the code under review, an implementer writing reports into the curated docs tree, a push stranding records off a merged branch), not against an attacker.

- **`readonly-agent-guard`** holds the state under review immutable, by agent class. Strict agents (adversarial-reviewer, blind-reviewer, security-reviewer, council-member, design-facilitator, consultant, blind-reader, prose-reviewer) get a read-only repo tree: writes, file mutations, git and GitHub state changes, package installs, and formatters are denied. The gate-runner (qa-verifier) builds and runs suites, so it may write and delete freely inside a fixed list of build-output directory names (bin, obj, TestResults, node_modules, .vs). Outside those directories it may still create a file that does not already exist, and chmod or copy to a fresh path (test scaffolding needs that), but may not modify, overwrite, delete, move, or rename anything existing; a stray created file leaves a tracked-tree delta the review bracket sees, or an untracked entry `git status` shows. Every other agent type and the main session are untouched, and `.kit/` (gitignored) is scratch both classes may write. Command text is judged against a quote-masked copy with nested executors descended recursively within a depth bound, and containment against the git root above the payload cwd. Coverage extends to a second dispatch route on one condition. On v2.1.205, established by probe rather than inferred, an agent dispatched through `Workflow`'s `agent()` with `agentType` naming a governed kit agent carries that identity into the PreToolUse payload, so its policy class resolves and the guard governs it exactly as under an Agent-tool dispatch; the named agent's frontmatter `tools:` list applies alongside its prompt, so the named agent holds no write tool on either route. Both halves are load-bearing, because the read-only property rests on two controls at once: `hooks.json` matches this guard on `Bash` and `PowerShell` only, so a strict agent's inability to write is held jointly by the guard denying write-shaped shell and by the `tools:` list withholding Write and Edit. A dispatch that omits `agentType` presents as `workflow-subagent`, resolves to no policy class, and loses both controls together rather than only the guard; what default toolset such an agent receives is unprobed and must not be assumed read-only. That condition is why the doctrine's Workflow grant and both skills' dispatch templates require the field.

  The requirement is prose-enforced, and saying so is the point: no hook matches the Workflow tool, so nothing observes the dispatch that decides whether a read-only agent, a reviewer or the consultant alike, is governed. It lives in the doctrine's standing-dispatch bullet and the two skills' templates, with one `doctrine-parity` test over the doctrine's wording as the only mechanical trace. The tree-state bracket around a review round is the sole runtime backstop, and by finishing-work's own account it misses a write to a gitignored path or outside the git root, a mutate-read-restore inside one round, and an outward `gh` mutation; under an omitted `agentType` those three classes rest on nothing. Accepted risk on the same footing as the memq-grant invariant below, checked by hand rather than by mechanism, with a Workflow-matcher hook as the fix if it ever needs one.

  The strict roster is itself hand-maintained in three places, the guard's own anchored regex and two enumerations in `test/readonly-agent-guard.test.js`, against a fourth set that is simply the files under `plugins/claude-kit/agents/`. Nothing fails when an addition misses one of them: the new agent resolves to no policy class and runs ungoverned, which is the silent direction. `docs/backlog.md` carries the directory-driven parity check that would turn that omission into a red.

  Two members of the class read prose that need not be the operator's own. `blind-reader` and `prose-reviewer` are dispatched at documents, a customer-facing draft among them, and both hold Bash, so a document in scope is untrusted input reaching an agent with a shell. Each charter states the prohibition with its reason: a document is data, an instruction found inside one is a finding reported verbatim rather than an action taken, and the reviewer chooses the command a claim check needs rather than letting a document choose it. That prohibition is prose and nothing under it is mechanical, because the guard denies write-shaped commands only: a read-shaped command is outside its denylist by construction, and so is an outbound `curl`, `wget`, or `Invoke-WebRequest`, which the review round's `git status --porcelain` bracket cannot see either, a network call leaving the worktree byte-identical. The exposure predates these two agents and is unchanged in kind; what changed is that two agents now exist whose whole job is reading documents. `docs/backlog.md` carries the denylist candidate and the reason it is not obviously right, which is that a reviewer sometimes has a legitimate reason to fetch.
- **`docs-write-guard`** keeps non-curator subagents out of `docs/`: only a main session and the docs-curator agent curate the library; reviewer and implementer reports belong in `.kit/`, with the plan's Chapter as the durable record.
- **`pr-docs-guard`** blocks creating a PR while `docs/` carries uncommitted changes attributable to the checkout the PR is created from, so documentation ships in the same PR as the code. A command that chains its own `git commit` ahead of the PR create is allowed, and a checkout parked on the default branch or a detached HEAD never denies.
- **`merged-pr-push-guard`** blocks a push to a branch whose PR the host reports MERGED, the stranded-commit trap. Its shell calls are fixed literals with the one variable (the branch) allowlisted before interpolation; that discipline is load-bearing against command injection.

- **`memq-grant`** is the inverse of the four guards: it never denies, and it emits an allow decision for exactly one command shape so a fleet worker on the engine's write-gated spawn vector keeps the memq CLI for recall and outcome logging. The invariant: a grant is emitted only when the fleet-store signals are present (`KIT_MEMORY_ROOT` with `KIT_MEMORY_ROOT_ALLOW_DATA=1`, checked through memq's own exported `storeSignalsPresent()` so the hook and the CLI share one definition), the command is one `node` invocation whose first argument is an absolute spelling resolving by normalized path equality to this plugin's own `scripts/memq.js` (anchored to the hook's on-disk location, never an environment variable, never a pattern; relative spellings are refused because the Bash tool's shell keeps a working directory nothing pins to the payload cwd, and on Windows a spelling without a drive-letter root is refused because this process and Git-Bash resolve it to different files), the interpreter is positively identified rather than accepted by name (the hook walks its own inherited PATH and grants only when the first `node` candidate realpath-equals its own `process.execPath`, so a PATH-planted node or wrapper refuses; that is the hook's PATH rather than provably the child's, since the shell the Bash tool runs can rewrite PATH, and the residual is a divergence between the two rather than an unchecked interpreter; the module-preload variables `NODE_OPTIONS`, `NODE_PATH`, and `NODE_REPL_EXTERNAL_MODULE` refuse the grant outright whenever set, since node honors them in the granted child), and the whole command line is free of shell metacharacters, quoted spans included, with word separators restricted to space and tab and the divergent spellings (a backslash outside quotes, a backslash before a quote, an unquoted comment tail) refused because the hook must never judge different words than the shell builds. That invariant has one known exception, bounded rather than closed: glob and brace characters are not banned, so a trailing argument carrying one does expand into different words than the hook saw. It reaches nothing, because the first two words must survive as literals (a bare `node` and an exact path match, neither of which a glob spelling produces), and everything past the script path is already the accepted memq-argv risk below. The refusals bite in the availability direction as well as the security one, and `docs/fleet-integration.md` carries that half: an engine setting any of the three preload variables ambiently on its spawns silently turns the grant off for every worker.

A further invariant this hook introduces, load-bearing for anything added later: a grant must stay disjoint from every deny guard's command shape. Today it is, and no mechanism checks it, so a new guard or a widened grant is checked against this rule by hand. On anything else it emits nothing and the call falls through to the engine's normal permission flow; its safe failure is silence, the opposite direction from the guards' fail-open-by-allowing. Accepted risks: arguments after the script path are granted along with it, because node hands everything past the script to the script, so they are memq's argv and memq's own argument validation is the control there; and the grant is agent-blind, so a strict read-only agent inside a fleet worker gets prompt-free memq writes (`readonly-agent-guard` does not deny memq, which writes the external store rather than the reviewed tree, and its agent classifier cannot be shared without restructuring that hook, while a second copy of the class list is exactly the drift the gated-override rule exists to prevent). The compensating controls, each with the bound it actually has: the grant surface ships in the build manifest like every hook (`hooks.json` rewiring included), so widening it is a stamped edit, and the canary probes the grant in both directions at session start (the allowed invocation must grant, a hostile one must stay silent), because a grant hook gone inert never announces itself in use. Both of those are attended-session controls only. The canary stands down under `KIT_EXTERNAL_ENGINE`, which the engine sets on every worker it spawns, so in the deployment this grant exists for, neither the manifest check nor the grant probe runs. State it plainly rather than counting it twice: the detection covers the machine where a person would act on it, and does not cover the fleet worker.

The quarantine is not a control here, and an earlier reading of it as one was wrong. The grant conditions on the store pair alone, while the run-scoped pending tier additionally requires a valid `KIT_RUN_ID`, so under the store pair without a run id a granted memq writes the project tier directly. Even inside a genuine run the tier bounds less than the word suggests: `log` appends to the project-tier journal and adds a `run` field rather than rerouting, `add-type` writes the shared type tier, and the grant covers every memq subcommand, `decay-prune` included, which archives memories and rewrites an index. The honest bound is the store: everything a granted invocation does lands inside the redirected store the engine owns, which is why the reach is that store rather than the machine, and it is the store boundary rather than the pending tier that does the containing. The gap it cannot see: it judges command text and its own environment, not what runs, so it cannot see what the granted memq process does with its arguments, nor an interpreter swap that happens after the decision, and an engine vector that already allows the command gains and loses nothing from it.

**Every guard fails open and denies only on positive confirmation. The grant fails the other way: silence.** A guard that cannot decide allows the call; a grant that cannot decide emits nothing, which leaves the call to the host's normal permission flow. The two directions are both the safe one for their own hook, and reading either as the general rule inverts the other. A parse error, an unidentifiable agent, an unresolvable path, a missing CLI, or a host timeout allows. The accepted risks that follow, per guard:

- The gate-runner's build-directory list is a policy assumption the guard does not check: a repo that tracks real content under one of those names gets no protection there.
- Agent identity comes from the hook payload's subagent-type field; a call the guard cannot positively attribute to a governed agent is allowed.
- `docs-write-guard` covers the Write/Edit tools exactly and shell writes heuristically; an exotic write (python, `sed -i`, `Copy-Item`, a variable-assembled path) is out of its reach and is caught, if at all, by the Stop-scan backstop. When the payload carries a cwd, its `docs/` match is contained against the git root above that cwd, so a path outside the session's project tree (a session scratchpad, a fixture repo) is out of scope; without a cwd, or for a target unresolvable before the shell runs (a variable, a home-relative path), the shape-only match stands and over-reaches in the false-deny direction.
- `pr-docs-guard` carries a residual false-deny: a payload cwd resolving to a different checkout that is both dirty and parked on a non-default branch still denies.

**Compensating controls, and the gap each cannot see:**

- Every strict agent's frontmatter grants no Write or Edit tools, the code reviewers, the two document lenses, the council and facilitator seats, and the consultant alike (each holds `Read, Grep, Glob, Bash` and nothing more), so the guard only has to police shell commands. Gap: nothing frontmatter can do about what Bash reaches.
- The executing-work skill brackets every review round with a `git status --porcelain` capture and comparison, so a write that slips past the guard surfaces as a tree delta and is treated as an incident. Gap: the comparison sees the worktree only; a `gh` or `az` host-state mutation leaves the tree byte-identical and is invisible to it.
- The Stop-scan backstop (`stop-docs-hygiene`) catches scratch that reached `docs/` by any route, including the exotic writes the write-guard cannot parse.
- The build stamps a SHA-256 manifest of every shipped hook file (`hooks.json` included, since rewiring is an equal disarm path to editing a guard) into `.claude-plugin/build-info.json`, and the canary verifies the executing plugin cache against it at session start, warning loudly on drift. This exists because the guards execute from the user-writable plugin cache: a governed agent holding Bash can overwrite a guard there, outside any git root where no tree comparison looks, disarming all four with no signal, and that write is confirmed reachable. The manifest converts a permanent silent disarm into a bounded loud one. Its limits: it is detection, not prevention, and it speaks at the next session start, not in the moment; the canary that performs the comparison stands down entirely under `KIT_EXTERNAL_ENGINE`, so the detection covers attended sessions and not the engine's spawned workers, whose payload integrity is the deploy's concern rather than this check's; and the manifest lives in the same writable cache as the payload it attests, so deleting the stamp file alone silences the check (the canary treats an absent manifest as an older build), and rewriting stamp and payload together defeats it outright. The actor who does either deliberately holds write access the Principals section already places outside every control in this document; the threat the detection is sized for is a model misstep or a rationalized edit, and one naive overwrite is exactly what it catches. Coverage is the shipped hook files; the cache's other executed payload (`scripts/`, `doctor/`) is outside the manifest today, and so is its model-facing prose, `skills/` and `output-styles/kit.md`, which steers behavior when read rather than when executed. The style is the one member of that prose needing no load to take effect: the harness reads it into the system prompt of every main-thread session the plugin is enabled for, so a cache edit to it reaches the model in every session rather than when something invokes it. `test/output-style-parity.test.js` is not that control, since it attests the repo copy against the repo's doctrine and never reads the installed cache.

## The goal state file

`.kit/goal-state.json` is the leash's whole state, and seven surfaces read it: the Stop hook that enforces, the compaction gate, the checkpoint CLI, the SessionStart notice, the `/kit-goal` CLI's own status report, the doctor, and the stop-failure watcher. The last is the one with reach beyond a session's context, since it composes an unattended resume prompt out of the plan paths it reads there; what bounds it is stated under the stop-failure pair below, and the bound is the paths being re-validated through this library's own rule and required to open rather than trusted as read. It is written only by `kit-goal-lib.js`, and its plan paths are normalized at write time to repo-relative paths that cannot traverse out of the project. Write-time normalization alone would leave a hand edit unchecked, so every read re-validates: the stored current plan and every queue entry must round-trip the same normalizer, and a value that does not round-trip is by definition not one this library wrote. A current plan that fails reads as no armed goal at all, which turns the leash off and leaves the doctor as the surface that flags the file; a queue entry that fails collapses the queue to the current plan rather than being dropped, because dropping one entry would silently renumber the positions `queueIndex` counts. The property that buys is that no reader can hand an unvalidated path to an `openSync`, which matters because a path naming a FIFO would block one, and the readers include a Stop hook where a block wedges the stop. The check is a round-trip rather than an acceptance test, which makes it stricter than the write path in one direction worth knowing: normalization is platform-dependent, so a state file carried from another operating system can read as malformed on arrival. It fails safe, and it is consistent with the file being machine-local in the first place. Staying machine-local is the other half of its posture, and it is a property of the consuming repository rather than one the kit can impose: the kit's own `.gitignore` covers `.kit/`, but nothing stops a project from tracking the file, and a tracked goal state puts one clone's plan paths into history where every collaborator's session start reads them back. So the doctor checks the property instead of assuming it, reporting the file tracked, neither tracked nor ignored, or ignored, each with the git command that fixes it, and reporting a git it cannot run rather than skipping silently, so an absent check never reads as a passing one. The check inspects the directory the doctor was launched from rather than the kit's own checkout, which is the whole point: the kit's checkout already ignores `.kit/`, so a check scoped to it would be a permanent pass over the one repository where the exposure cannot occur. Detection is all it is. Nothing prevents the exposure, and nothing runs unless somebody runs the doctor; the preventive fix, a nested ignore file written whenever `.kit/` is created, is backlogged. A queued arming adds `queue`, `queueIndex`, `history`, `boundTranscript`, `blockedAdvanceKey`, and `blockedAdvancePlan` to it; `queue`, `queueIndex`, and `history` carry the same provenance and the same guards as the fields beside them, being plan paths and an index the same writer produced, `blockedAdvanceKey` is a capped printable-ASCII token the hook derives from a transcript entry and compares only against itself, and `blockedAdvancePlan` is a plan path of the same provenance as the queue's, used only in equality compares against `plan` and the preceding queue entry and never opened.

- **`boundTranscript` is the one field naming a path outside the project, and it is never surfaced and never executed.** It has two provenances: an arm-time record from the `/kit-goal` CLI's existence-checked scan for `<sessionId>.jsonl` under the harness's transcript store (candidate paths composed from `os.homedir()`), and a claim-time record from the hook payload's `transcript_path`. Either way it is sanitized as a length-capped string with control characters refused and a network-shaped path (two leading separators, the UNC and `//server` forms) refused outright, and its only use is an `fs.stat` whose result reaches the model as a number and a unit ("last active about 20 minutes ago"), never as the path. So a hand-edited state file can point the stat at an arbitrary local path and learn nothing from it that reaches a session beyond an age in minutes. The FIFO-hang concern that governs transcript reads elsewhere does not arise, because the path is stated rather than opened, but the stat has a hang of its own and the network refusal is most of what answers it: the call is synchronous and runs at every session start, so a path naming an unreachable share would hold the hook for the SMB timeout. That refusal covers the UNC and `//server` forms only. A path on a mapped network drive letter is indistinguishable from a local disk without a syscall and passes it, so a state file naming one can still hold the stat for the SMB timeout. The harness itself never hands a hook such a transcript path, but the arm-time scan composes its candidates from `os.homedir()`, so a home resolved onto a mapped network drive makes the kit compose one with no hand edit; the residual is reachable from that configuration as well as from a hand edit, and it stays stated rather than closed because the only closure available is a syscall in the path the guard exists to keep cheap.
- **A hand edit is the threat model here, not a remote one.** Nothing outside the machine writes this file, and anything able to write it could equally have written `plan` or `boundSession`, which are the fields with real leverage. The readers are defensive anyway rather than trusting: `readGoal` normalizes every read to a consistent shape, so a queue disagreeing with `plan` or a non-array `history` is repaired rather than propagated, and the doctor discards a queue that disagrees with `plan` in favour of reading the file as a single-plan arming.
- **Advancing is the same write as arming, and it inherits the same atomicity.** The advance is one temp-file-plus-rename rewrite, so a state file is never observed half-advanced. What it does not have is a lock, and the session binding is deliberately not credited as one in its place: the binding serializes the Stop hook's own writes, while the `/kit-goal` CLI is a writer it does not exclude, so a re-arm or a clear can land between the snapshot a stop decided from and the advance's own re-read. A compare-and-swap is what closes that. The advance carries both the plan the stop decided from and the timestamp that state was armed at, and refuses when the re-read state no longer matches either. The timestamp is not redundant: a re-arm that puts the same plan back at the head is the ordinary crash-recovery spelling, and on the plan alone it would pass the compare and let a stop advance a queue that had just been freshly armed. A refused advance holds the stop rather than releasing it, so the failure direction is a retry at the next stop rather than a queue position spent against state the caller never saw. The compaction gate is a third write trigger, reaching the same library to claim a binding at an auto-compaction offer, and the binding cannot serialize it either, because it fires precisely in the unbound state where there is no binding yet. That write carries no compare-and-swap: it is last-writer-wins, so a clear or a re-arm landing between its read and its write can be resurrected by it, recoverable by clearing again.

## The compaction gate

`kit-compact-gate.js` is a PreCompact hook, and it is not a guard: it governs no agent and protects no state from anyone. It schedules. Native auto-compaction lands wherever context happens to fill, which on a leashed plan run is mid-section; the gate defers it until the run declares a boundary, a section's close or, during a drought between closes, an interim board entry. The only lever the harness offers is a veto, and a denied auto attempt is re-offered once per assistant turn indefinitely, which is what makes vetoing a schedule rather than a cancellation.

**The invariant:** the gate denies in exactly two states and allows every other, and both denials are bounded by the same ceiling. Two preconditions gate both: the trigger is `auto` and `KIT_EXTERNAL_ENGINE` is unset. Past those, it denies **boundary-gated** when a kit goal is armed for the project, the compacting session is the one bound to that goal's leash, no boundary checkpoint is open that matches the armed plan, matches the bound session, and is still fresh, and consumption read from the session transcript is legibly below a named ceiling. Those three checkpoint legs are one predicate in the shared library, which the gate's verdict and the CLI's status report both answer from, so what the report says gates nothing is what the gate treats as absent. It denies **interactive** when no goal is armed for the project, an armed one is bound to a different session, or an armed one is unbound and this session's transcript makes no claim on it, the transcript shows no native `/goal` or `/loop` driving it, and consumption is legibly below that same ceiling. An armed goal no session has claimed yet is resolved by the same claim proof the leash itself uses: where the compacting session's transcript shows the user typing the arming command, the gate claims the binding and takes the boundary-gated path, and where it does not, the session is a bystander and takes the interactive path. That second claim point exists because the leash's other one is a stop, and a run holding the completion contract does not stop while work remains, so a stop-only claim leaves a well-behaved run unbound and therefore ungated for its whole length. One armed state still allows outright: an armed goal beside a payload carrying no usable session id, which is an anomaly rather than evidence of a bystander, and from which no binding could be written in any case, so it is resolved toward allowing. Any other state, any read error, any ambiguity allows. Each denial writes its own fixed stderr string carrying no input-derived data, distinct per kind so a reader can tell which deferral fired. Manual `/compact` is never gated, checked in code as well as by the `hooks.json` matcher so a rewiring cannot silently widen it. Deny is exit code 2; the JSON deny form is inert for this event on the versions probed, so nothing is built on it.

**The scope of the interactive state, stated plainly because it is this section's widest claim.** The deny reaches every session the harness offers an auto-compaction to, not only the sessions that opted in by arming a kit goal, and the ceiling assumption below rides along with it onto that default population. What bounds the exposure is that the gate can only veto an offer the harness already made, never raise one, and that the same ceiling ends every deferral. The reach also makes the transcript reader a per-session code path rather than a per-plan-run one, which is why its input handling is treated as untrusted parsing rather than as a convenience read.

**Accepted risk: the automation detection reads attacker-influenceable transcript content.** The transcript holds file content, tool output, and agent reports, so the literal command markup the detector keys on can be planted by anything the session reads, including this repository's own documentation. Detection is therefore structural rather than substring-based: an entry must parse as JSON on a line of its own, carry the right entry type, and hold the markup in the user-typed position, and tool results, meta entries, compaction summaries, and sidechain rows are excluded. Content quoted into a transcript rides inside a JSON-escaped field and so cannot produce the standalone line the test requires, which is the property the whole defense rests on. The residual is bounded rather than absent, and it runs in both directions: the detector reads retirement evidence too (a completed goal, a `clear` argument, a loop's terminating stop), so a plant can push a session either way. What bounds it is that both destinations are treatments the gate already applies to real sessions, and both answer to the same ceiling: a plant can move a session between compacting at the native trigger and deferring to the ceiling, and can do nothing else. It cannot extend a deferral past the ceiling, and it cannot reach any file or process. The parsing itself is the sharper edge: the reader caps its read, parses line by line rather than with a whole-file pattern, and its span scanning is linear, because a backtracking pattern over untrusted transcript text is a denial-of-service reachable from every session's compaction path.

**Accepted risk: the claim predicate is an authorization decision taken from the same transcript.** The automation detection above only steers a deferral; the claim decides which session holds a leash and writes `boundSession` into the goal state, so an entry that satisfies it moves real state. It is not a second reader written for the gate. It is the predicate the Stop hook has always claimed a binding with, single-sourced in `kit-compact-lib.js` and called by both hooks, so the gate adds no evidence shape the leash did not already trust. The exclusions are the anti-steal set: the entry must be user-type and neither a sidechain, an `isMeta` harness injection, nor a compaction summary; local-command stdout is stripped before the tag scan; and the path match is directory-qualified, so a same-basename file elsewhere is not the plan. Two invocation shapes then count, and only those two. In the markup shape the plan path must sit in a `<command-args>` span belonging to a `<command-name>` that is exactly `/kit-goal` or ends `:kit-goal`, so another command taking a path argument cannot claim. The typed-lead shape covers the arming the harness does not parse into markup (a multi-line `/kit-goal` with one plan path per line): the message's first non-whitespace characters must be the `/kit-goal` token (optionally plugin-namespaced), and the plan path must sit inside the argument block, the text from the token to the first line that is empty or opens with a backtick or `<`, so quoted, fenced, or injected material after the argument list can never supply the path, and a message that leads with prose or merely mentions the path elsewhere never claims. Array content carrying any `tool_use` or `tool_result` block discards the whole entry rather than being filtered block by block, one step stricter than the sibling readers in the same file, because a claim is a decision and an entry mixing genuine user text with tool output is where planted markup would ride beside a real turn. What a claim would buy an actor who forged one is bounded and recoverable: the claiming session becomes the boundary-gated one and the real run becomes a bystander to its own plan, which re-arming undoes. The write carries no compare-and-swap, the residual recorded under the goal state file above.

**Accepted risk: the checkpoint file is user-writable and steers compaction timing.** `.kit/compact-checkpoint.json` is an ordinary file in a writable tree, so anyone who can write the tree can open or remove one. The worst case is bounded and small: a compaction landing earlier or later in a session than intended. It cannot deny a compaction that the gate would otherwise allow (the file only ever opens the gate), it cannot cause data loss (the harness's own summarizer runs unmodified either way, and the kit summarizes nothing), and it cannot reach outside the project (the filename is a fixed suffix joined onto the payload cwd, never caller-chosen, and the delete is an `unlink` that removes a planted symlink rather than writing through it). The plan and session fields are compared for equality and never joined to a path. An actor who can write this file already holds the tree write access the Principals section places outside every control in this document.

**Compensating controls, and the gap each cannot see:**

- **The safety valve is the control the rest rests on.** Sustained denial on a run that declares no boundary, neither a section close nor an interim board entry, would otherwise climb to the model's hard context limit, where a session dies outright on an over-length prompt, which is a strictly worse outcome than the mistimed compaction the gate exists to prevent. At or above the ceiling the gate allows regardless of any checkpoint, and the interactive denial answers to the same constant. Its gap: the ceiling is an absolute token count assuming the roughly 1,000,000-token window these sessions carry, because the PreCompact payload carries no `model` field to derive the real one. On a window falling between the trigger and the ceiling the valve would sit above the hard limit and never fire. That is the single direction of this design that is not fail-open, and it is an assumption pinned in the code rather than a property the hook can verify. One shared ceiling is a deliberate choice rather than an oversight, and through the interactive state it governs every session rather than only opted-in runs; what keeps the exposure bounded is that reaching the deny at all requires the harness to have offered a compaction, which a window too small to reach the trigger never does.
- **The doctor's auto-compaction-window check** reads the ceiling out of the hook file rather than restating it, warns when the configured `autoCompactWindow` would leave too small a band between the trigger and the ceiling, the state in which the valve allows everything and the gate defers nothing, and reports a configured value that merely differs from the recommendation, which is the only way a machine already carrying a value learns of a new one. Its one write that touches an operator's own choice, replacing a differing value, is withheld from the unattended `-Yes` consent and takes an interactive answer; supplying an absent value is not, because that case converges while replacement does not. Its gaps, stated plainly because this control is easy to credit with more than it does: it is an attended check that speaks only when someone runs it; it reads the configured window, which is not the running model's real context window, so **the not-fail-open direction above is not covered by this check or by anything else**, and a model whose window is smaller than the ceiling is caught by nothing; and if it cannot read the ceiling constant out of the hook source it reports the skip rather than the comparison.
- **The checkpoint expires.** A boundary is often reached below the trigger, where no compaction is pending, so a checkpoint with no staleness bound would sit open and admit the next offer, which arrives mid-section. The gate treats a checkpoint older than a short window as absent, and the executing-work ritual independently clears it when the next section starts. That second guard covers a section close alone: no section starts during a closure drought, so a checkpoint opened at an interim board entry rests on the expiry by itself. This is a correctness control rather than a security one, listed here because its absence makes every claim in this section describe a feature that is not doing anything. Its gap: the bound is wall-clock, so a chapter that crosses the trigger within that window of the previous boundary can still spend a stale checkpoint, costing one mistimed compaction.
- **Session binding retires an orphaned checkpoint.** The checkpoint records the goal's bound session alongside the plan, and the gate requires both to match, so a checkpoint left behind by a crashed run cannot open the gate for the session that resumes the plan. Its gap: it assumes a single writer, since the gate's read-then-delete is not atomic; a concurrent writer landing between the two would burn a boundary. The kit now has a second legitimate writer of that file, the queue advance, which rewrites an open checkpoint to the plan it moved to so a plan's own close-out boundary is not retired by the advance that follows it. It writes from the bound session's Stop event, the same session and a different event from the gate's read, so the assumption is unchanged rather than newly stretched. A checkpoint opened while the goal was still unbound records a null session and therefore matches nothing once the gate claims the binding, which costs one more chapter of deferral rather than opening the gate early.
- **The build's SHA-256 manifest covers these files like every other shipped hook**, so editing the gate or rewiring it out of `hooks.json` is a stamped edit the canary reports. Its gap is the manifest's own, stated in full under the guard hooks above: detection rather than prevention, at the next session start, and stood down entirely under `KIT_EXTERNAL_ENGINE`.

**Not a control:** the gate stands down under `KIT_EXTERNAL_ENGINE` because an engine's workers are fresh per section and have no mid-chapter context to protect. That is a scope decision, not a security property, and it removes nothing an attacker would otherwise face.

## The stop-failure logger and watcher

This pair is the kit's only component that executes a command unattended, on a schedule, using a value read from a file. That shape sets its whole posture, so the trust boundary is stated before the controls.

**The marker is user-writable.** `.kit/stop-failure-latest.json` is an ordinary file in the project tree, so anything that can write the tree can author one. What it can reach is the watcher's decision to launch `claude -p --resume <id>`, which is why the id is treated as hostile input rather than as the harness's own word.

- **The session id is validated against a strict grammar before it reaches any command line**, and a value failing it is refused outright rather than escaped or quoted around. Rejection, not sanitization, because a value that is not a session id has no correct interpretation.
- **The resume prompt is the `/kit-goal` invocation and nothing else.** No marker content reaches it. Its only interpolations are plan paths read from the goal state: the armed queue from the current position onward, so a run that dies mid-sequence is re-armed over the rest of the sequence rather than over its current plan alone. Three checks apply to each. It is validated through the same rule the goal state itself enforces (called out of `kit-goal-lib.js` rather than restated so the two cannot drift); it must match `^[A-Za-z0-9_./-]+$`; and it must name a file that opens, tested by the same read arming itself performs rather than by a weaker existence probe. The grammar is the check that narrows the free-text channel, and narrows is the honest verb: a filename is free text, and a name built from permitted characters can still read as prose, but the class excludes whitespace, quotes, and every metacharacter a `cmd.exe` re-parse could use, and forcing ASCII means the bytes that reach the command line are the bytes on disk whatever the console codepage is. It is deliberately stricter than the arming rule, which refuses only control characters and traversal; the cost is that an unusual filename truncates a queue the arming would have accepted, and what makes that acceptable is that the truncation is recorded rather than silent.

Two outcomes are possible per candidate, and they split on certainty rather than on position. A path failing any of the three checks truncates the queue there rather than being stepped over, since a prefix of an ordered queue is still a sequence that was armed while a gapped one is not. A plan whose `Status` reads `Complete` is skipped wherever it sits, because it is known-finished work rather than an uncertain entry: arming refuses a Complete plan all-or-nothing, so carrying it would lose the whole remainder, and truncating there would drop the unfinished plans behind it. The prompt therefore need not lead with the current plan, and when no candidate survives, none is composed and nothing is launched. Every truncation and every empty result writes one record naming the plan, the check that refused it, and how many candidates were dropped, so an unattended run that loses part of its queue leaves evidence. A queue that disagrees with `plan`, or is not an array, falls back to the current plan alone. The prompt is bounded at 1024 characters, below the `cmd.exe` argument limit a `.cmd` shim would impose, so an arbitrarily long queue cannot grow the command line without bound. Carrying no prose of its own is the other half of that closure, and it costs nothing, since a resumed session already holds its prior conversation and the session-start resume notice.
- **Nothing is spliced into a command line at all.** The validated session id and the fixed prompt reach a constant wrapper script through environment variables, and the child receives per-element argv, so the class of defect where a hostile value escapes its quoting has no surface to occur on rather than being escaped correctly.
- **The scope guard is a control, not only a policy.** A marker only acts when the project holds an armed goal whose bound session is the one the marker names, so authoring a marker is not by itself enough to make the watcher run anything; an unarmed project ignores every marker it is handed. The one accepted unbound case is narrow and does not widen the reachable set: a goal armed but not yet bound passes only when the sentinel names the marker's session as the one this watcher launched, which is the state a prior launch leaves behind. It widens nothing an attacker can reach, since the sentinel is a file in the same tree and anything able to author it could equally have written the bound session outright. An unbound goal beside no such sentinel is refused, because an unbound goal in a project where an interactive session died is exactly the fork this guard exists to prevent.
- **Every guard fails toward exit-without-acting.** No unparseable, ambiguous, or unexpected input reaches a launch. This is the opposite posture from the compaction gate above, and deliberately so: that gate's fail-open costs a mistimed compaction, while this one's would cost an unattended process launch.
- **The logger writes and reveals nothing.** It emits nothing on stdout or stderr, and a payload that is not a JSON object is recorded as a note naming only its length, so error text that could carry sensitive detail is never echoed into a channel a model reads. A non-object payload is treated the same as an unparseable one, since spreading an array into the record would reinstate its raw content under numeric keys.
- **The events log is capped**, so a session failing on every turn cannot fill a disk. The cap costs history only; the marker the watcher reads is written on every event regardless.
- **The build's SHA-256 manifest covers the logger** like every other shipped hook, with the same detection-not-prevention gap stated under the guard hooks above. The watcher and its installer are scripts rather than wired hooks and are not stamped by it.
- **Both atomic writers refuse a tmp path that is not a plain file**, so a pre-planted symlink or junction at a predictable tmp name cannot turn either write into an overwrite of a target outside the tree. This matches the guard `emitGoalEvent` applies for the same reason. A hardlink is a regular file and passes, in both places, deliberately.

**Accepted, and named rather than closed:**

- **The logger takes its output directory from the payload's own `cwd`.** A payload naming another directory would be written there. The trust boundary is the harness that writes the hook's stdin, and anything able to forge that already runs code on the machine; the sibling compaction gate resolves its project the same way. Stated because the "writes nothing outside `.kit/`" property is true of the project's own payloads, not of every conceivable one.
- **The scheduled task is the kit's only unattended executor, and the script it runs is unstamped.** The manifest gap above is documented for every script, but it was sized for code that runs only inside attended sessions, where the session-start canary reports drift to a human who is present. A registered watcher removes that precondition: it executes `scripts/stop-failure-watcher.ps1` from a user-writable path every fifteen minutes, as the user, with no session and therefore no detector that will ever see an in-place edit. Anything able to write the tree can reach unattended execution that way, and it is a shorter path than the marker the controls above are built around. Registering the task is opt-in for exactly this reason, and a machine that has not registered it carries none of this exposure. Closing it properly means extending the manifest to `scripts/` and having the watcher verify its own hash before acting.
- **The operator at a stale console modal.** The dangerous sequence is a watcher resuming headlessly while the dead session's console still shows its limit modal, and the operator later answering that modal, producing two continuations on one worktree. Four things narrow it: the scope guard, since re-arming rebinds the leash to the resumed session and leaves the console session unleashed; the marker staleness ceiling, which stops a marker that sat unacted-on for an hour from being resumed under an operator who has since come back to it; the in-flight sentinel, written before the child starts precisely so it exists during the window a fork is possible rather than only after it closes; and the operational rule that a stale modal is checked against `.kit/stop-failure-resumed.json` and the console session exited rather than continued. Deleting the marker is how an operator takes a run back by hand. The residual is a human choosing otherwise, and nothing mechanical stops that.
- **The sentinel is checked and then written, without a lock.** Two passes that both read an absent sentinel before either writes would both launch, which is the fork the sentinel exists to prevent. The scheduled path is covered, since the task is registered with `MultipleInstances = IgnoreNew`, so the exposure is a by-hand run overlapping a scheduled tick. The window is milliseconds and the remedy is not running the watcher by hand while its task is enabled. The sentinel's own pid-less form is bounded rather than trusted for the same reason in reverse: it blocks a rival pass only for one pass interval, 15 minutes, because a pass that died between its two sentinel writes would otherwise disarm the recovery permanently, and what covers the aged-out record is the launch spacing, 20 minutes, which the launch's own incident record enforces whatever the sentinel says.
- **The child runs with `CLAUDE_CODE_RETRY_WATCHDOG=1`**, which means a rate-limited child waits rather than failing. That is the intended behavior, and it also means a launched child can hold a process open for hours. It is bounded by an explicit child lifetime limit and by the incident budget, not by the retry logic itself.

## Type-tier governance limits

The shared tier has no owner and no cross-project coordination beyond the lock:

- `memq add-type` refuses to overwrite an existing name, on the reasoning that another project may rely on it.
- `memq decay-prune --archive-type` now names the projects declaring that type before it retires anything, and refuses a retirement affecting more than one declaring project unless `--confirm-shared` is passed. The listing is printed either way, so a single-declarer retirement still shows what it acted on.
- One project's usage prune still collapses read and applied evidence that other projects of that type contributed, so a memory heavily used elsewhere can later scan as idle. This one is not closed: the prune has no equivalent declarer check.
- Under a store pin the shared-retirement gate does not operate, and the reason is structural rather than a bug. The refusal fires when more than one `projects/` segment declares the type, and the pin collapses an instance to exactly one segment by design, so the count is always one and the gate never trips. The type tier it guards is not collapsed by the pin and stays genuinely shared across every worker of that instance, so the surface the gate protects is still there while the gate is not. The listing degrades the same way: it names the instance rather than the repositories a retirement actually costs. A root still carrying pre-pin cwd-derived segments is the exception, and it is not one to rely on.
- The pin also makes type-tier membership instance-wide. `Project-Type:` is read from the pinned index, so every worker of an instance inherits one declaration whatever repository it is running in, and reads and writes that shared tier accordingly. The content stays fenced; what widens is who is in the tier.
- A tier whose last declaring project drops its `Project-Type` line becomes unreachable to the decay scan and prune, and its sidecar grows without a reader.

## Not claimed

- The "data, not instructions" framing on emitted index lines is a mitigation, not a guarantee.
- `memq`'s argument validation protects the *store's shape*. It does not protect the user's secrets.
- `decay-prune` is auditable, and reversible only in the weak sense that archiving is demotion rather than deletion: it prints everything it removed, leaves one generation of backup, and a retired memory keeps its description in the archive's own index and still answers `memq get` by name. The rollup is the irreversible half, discarding expired entries' prose for a tally.
- Retention is bounded but not fixed. A memory's decay thresholds extend by 30 idle days for each distinct calendar day it was applied, capped at 365, so the most extended memory becomes an archive candidate at 425 idle days. A `pinned:` frontmatter field exempts a memory from candidacy entirely and makes the prune refuse it by name. The exemption is set only by editing the memory file and is revoked by deleting the line; a `decay-scan` that finds any pin counts the whole population and lists the first ten with a counted remainder, so the exempt population cannot grow unobserved. Because archived content is still served by name and by the recall digest, retiring a memory does not remove anything the storage properties above describe: a credential written into a memory persists after archiving exactly as it persisted before.
- Inside an engine worker, the store pin is effectively a single variable, because the gate it inherits is set by the engine rather than by anyone attacking it. The `KIT_MEMORY_ROOT` pair is already true on every spawn, so within that environment one repository-carried `KIT_MEMORY_PROJECT` is honored with no second signal an attacker has to supply, and a plan worker runs inside the repository it is working on. A valid-but-different value relocates that worker's whole project tier to a sibling segment under the engine's root, so its writes land where no adjudicator looks and its reads pull another segment's content into context; an unusable value denies that worker's memory subsystem outright, loudly. This is the `KIT_RUN_ID` residual below, widened from the pending tier to the project tier, and it is bounded the same way: everything stays inside the instance's own store root, which the engine allocates per instance, so the pin is never the separator between instances. The mitigation is the engine's rather than the kit's, and it is to set the variable explicitly on every spawn, which beats a value inherited from the parent environment. It does not beat configuration that runs inside the spawned session's own shells afterwards, so the mitigation is narrower than it first reads.
- Run scoping in the pending tier is not isolation. It keeps two runs from reading each other by ordinary operation, not by enforcement: the only thing selecting a run's directory is that process's own `KIT_RUN_ID`, which any session holding Bash can set to another run's value.
- The pending tier bounds what enters the *project* record without review only for a spawn that carries a run id. Under a pin, a spawn without one (the reviewer and the phone-driven shapes) is deliberately told to write memory files and their `MEMORY.md` index lines straight into the shared instance record, because a pinned project tier is that instance's ordinary adjudicated tier and those shapes are the attended half of the instance. It is a decided behavior, not an escape, and it means the quarantine covers plan-execution runs rather than every write. It does not bound the type tier: `memq add-type` inside a run still writes the shared type tier and its index directly, provenance-stamped rather than quarantined. Under the engine that store is per-instance, so the reach is that instance rather than the machine, but the write is unadjudicated. That bound is an external precondition, not something this repo enforces: it holds only while the engine points `KIT_MEMORY_ROOT` at a per-instance store, so a change to how the engine chooses that root re-opens this entry.
- Installing the optional embedding stack pulls transitive dependencies whose published advisories have no fix version at the pinned release. Accepted as a supply-chain risk of an optional, locally-installed stack rather than mitigated: the install is pinned to a reviewed version and runs with lifecycle scripts disabled, but a vulnerability with no patch available is not something a version pin closes.
- The output style's parity test bounds drift, not tampering. It holds `plugins/claude-kit/output-styles/kit.md` byte-identical with the doctrine's register core in the repository, which is a maintenance control against two copies diverging under editing. The file's security-relevant property, that it becomes system-prompt content in every main-thread session, is attested by nothing once the payload is installed, per the manifest coverage above. Its frontmatter pins are the same kind of control: `keep-coding-instructions: true` is pinned because absent or false it silently strips Claude Code's built-in coding instructions from every kit session, which is a correctness failure caught by review and by that test, not a boundary.
- Nothing here defends against an actor who already has write access to `~/.claude`. Such an actor can already execute code through hooks and settings.
