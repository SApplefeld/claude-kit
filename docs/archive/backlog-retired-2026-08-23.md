# Backlog items retired 2026-08-23

Retired by the dormant-feature removal effort (`claude-kit_dormant-feature-removal_spec_v1.md`): the stop-failure recovery feature this item was about no longer ships in the kit, so there is nothing left to live-fire.

- **Live-fire the stop-failure watcher, and decide the retry-watchdog question it raises (2026-08-16, operator-only, from the stop-failure-recovery close-out).** The feature auto-resumes a kit-goal-armed unattended run that died on a retryable API failure, and its end-to-end path is the one thing no session can force: a genuine session-limit hit. Two machine actions come first, both Scott's. Update the installed plugin, since the `StopFailure` hook runs from the plugin cache and does not exist for a live session until that lands. Then register the task on the unattended machine with `doctor -Fix -RegisterStopFailureWatcher`, run from the project directory to be watched (the registration takes that directory from where the doctor was invoked); registering is opt-in and a machine that skips it carries none of the feature, including the unattended-executor exposure the security model names. On the next real limit hit, what to look at: the events log holds the real payload, a resume lands after the reset, and the resumed session re-arms and continues the plan. Two outcomes reopen work rather than closing this. A resume whose session does not re-arm or does not continue the plan reopens the prompt and resume semantics; a genuine limit hit that writes no marker at all means the event or payload differs from what the probe captured, and reopens the logger. The open decision riding alongside: whether to set `CLAUDE_CODE_RETRY_WATCHDOG=1` machine-wide. Set, an interactive session at the limit stalls alive rather than dying, so no `StopFailure` fires and this watcher never engages; unset, interactive sessions keep today's behavior. The feature works either way, so this is a preference about interactive sessions rather than a dependency, and it is worth noting whether the modal behavior changes at all, which nothing currently knows.

Retired 2026-08-23 on the operator's own fleet check, reported through the session relay: no machine holds the task, and the watcher was never installed anywhere. The item existed to find a machine running a scheduled job against a script the payload no longer carries; there is none.

- **Confirm no fleet machine holds the stop-failure watcher scheduled task (2026-08-23, from the dormant-feature removal).** The kit no longer ships the watcher, its installer, or the doctor flag that unregistered it, so a machine that ever registered the task now runs a scheduled job every fifteen minutes against a script the payload no longer carries, with nothing in the kit reporting the failure. On each fleet machine, run `Get-ScheduledTask claude-kit-stop-failure-watcher` before taking the plugin update there. A red "No MSFT_ScheduledTask objects found" error is the clean answer. If a task does come back, `Unregister-ScheduledTask -TaskName claude-kit-stop-failure-watcher -Confirm:$false` removes it; that is a built-in Windows cmdlet and works whether or not the machine has updated. Best evidence is that no machine ever registered it, so this is expected to confirm rather than to find something. NEO-CLAUDE verified absent 2026-08-22 and again 2026-08-23.
