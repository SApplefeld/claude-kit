## Goal

The kit's auto-memory gains four capabilities layered on the existing file-per-fact store: outcome (success/failure) logging under namespaced action keys, a decay lifecycle (summarize at 30 idle days, archive at 60, application resets the clock) with dual used-tracking, a `memq` CLI giving deterministic two-tier retrieval (summary lines first, full record on demand) across keys, descriptions, and tags, and a project-type memory tier so conventions like "how Next.js projects are tested" carry into a new repo on day one. When this is done, a session can ask "what happened last time I tried X" and get a stop/go answer from summaries alone, stale memories retire instead of accumulating, and loosely related memories are findable by tag without an exact phrase.

## Approach

The design reverse-engineers a working system described publicly by its builder (Reddit user Glad_Contest_8014) and adapts it to the kit's architecture. The reconstruction, in one line: a slim rules-only bootstrap file, a namespaced key-value store with summary-then-full retrieval through short CLI queries with deterministic output, per-action success/failure logging, tags for cross-cutting retrieval, 30/60-day decay with use-resets, and locked shared writes for parallel agents. The kit already has the bootstrap (doctrine + skills), file-per-fact memories with an always-loaded index (which is two-tier retrieval), plan docs as the cross-session resume mechanism, and the close-out ritual. This effort adds only the missing pieces, on these decisions:

**Outcomes are a journal, not files (decided 2026-07-30).** Success/failure records are high-volume and individually low-value, the opposite profile of the file-per-fact store. They go to an append-only `outcomes.jsonl` sidecar in each project's memory directory, written only through `memq log` so format and append-atomicity live in one place. `MEMORY.md` carries a single pointer line; journal entries never touch the index. Append-only single-line writes make concurrent writers safe by construction (the same pattern as `kit-events.jsonl`), which is what keeps index contention from ever arriving.

**Action keys are dot-namespaced, tags are the cross-cutting escape hatch (decided 2026-07-30).** A key like `neo.sql.procs` gives precise prefix retrieval but forces a single hierarchy; "everything SQL-related across projects" cuts across it, and description substring search misses synonyms and non-mentions. So memory frontmatter gains an optional `tags:` list and outcome entries an optional `tags` array, and `memq find` matches on key prefix, description substring, or `--tag`. The tag set is a controlled vocabulary, not free-form: the memory-system skill owns a small registry (projects, domains, a few kinds), `memq` warns on an unregistered tag rather than silently minting it, and the decay pass folds in tag hygiene. Unmanaged tags decay into synonym sludge that makes `--tag` queries silently incomplete; the registry is the guard.

**Used-tracking is dual: hook floor plus self-report (decided 2026-07-30).** A new PostToolUse hook stamps Reads of memory files to a `usage.jsonl` sidecar (`kind: read`); the model stamps actual application via `memq touch <name> --applied` under a skill rule (`kind: applied`). Stamps go to the sidecar, never to frontmatter, because a hook editing frontmatter would race the model's own Edit calls. Decay keys on `applied`; `read` informs the summarize-versus-archive judgment. Known limit, accepted: memories recalled via system-reminder injection never pass through the Read tool, so the hook floor sees only explicit file reads; self-report carries the decay decision.

**Decay is deterministically scanned, human-judged, close-out-triggered (decided 2026-07-30).** `memq decay-scan` computes candidates from frontmatter dates, `usage.jsonl`, and journal entry ages: no `applied` stamp in 30 days marks a memory for summarization (condense the body, keep the description), 60 days moves it to `memory/archive/` and removes its index line; journal entries older than 30 days roll up into per-key summary entries. finishing-work step 7 runs the scan when the decay stamp file is older than 14 days, with summarize/archive decisions made in-session where a human is near; a SessionStart nudge fires when the stamp is badly overdue (30+ days). The scan is code so the candidate list is deterministic; the judgment is the model's with Scott's oversight, matching the kit's decay-by-curation posture rather than silent deletion.

**The project-type tier lives in `~/.claude/memory-types/<type>/` (decided 2026-07-30).** Same file-per-fact format with its own `MEMORY.md`. A project opts in with a `Project-Type: <type>` line in its memory `MEMORY.md`; the session hook reads it and emits the type index at session start. Type-tier writes go through `memq` under a lockfile, because this tier is the one surface genuinely shared by concurrent sessions of different projects. The memory-system skill owns the routing rule: a fact belongs in the type tier only when it holds for every project of that type, not just the one that taught it.

**`memq` ships in the plugin; the doctor installs a stable shim (decided 2026-07-30).** The plugin cache path changes per release (the cache-snapshot problem), so nothing durable may reference it. Doctor `-Fix` installs a `memq` shim into `~/.claude/bin` and verifies PATH, making the command stable across kit updates. `memq` resolves the project memory directory by the same cwd-sanitization Claude Code uses, verified against the real directory at build; an environment override exists for tests only, producer-side, same stance as `KIT_EVENTS_PATH`.

**All `memq` output is deterministic formatted lines, never raw JSON.** The scripts parse; the model reads summary lines. This is the reconstruction's "deterministically handled parsing" principle and it is what keeps query cost near-zero: a `find` returns one line per hit (key or name, age, outcome tally or description), and only a deliberate `get` pays for a full record.

**Repo constraints honored.** `session-start.js` is resume-critical and exempt from sweeps (backlog 2026-07-25); the new SessionStart behavior lands in its own hook file, `memory-session.js`. The doctrine's single source is the operating-instructions skill: the one new doctrine pointer bullet must land byte-identical in `plugins/claude-kit/skills/operating-instructions/SKILL.md` and `home/claude-kit-doctrine.md`. New hooks named in `hooks.json` are load-checked by the canary automatically; the stamp and session hooks are not guards, so load-check plus the repo test suite is their coverage. All hooks fail open and never block.

**Scope tension, recorded.** The kit's culture builds on observed failure, and `memq` plus the type tier ship ahead of demand. Scott's 2026-07-30 full-scope call is the authorization (goal: full parity with the reconstructed system); their edges are provisional the way the haiku implementer band's are, with the same posture: watch usage, tune on evidence, do not widen speculatively.

## Standing Brief Amendments

Folded into every dispatch brief from S1 onward.

- **No subagent writes anywhere under `~/.claude/`.** Three sections carry acceptance criteria that land on the real machine outside the repo: S1's round-trip against the live project memory dir, S4's `~/.claude/memory-types/`, and S5's `~/.claude/bin` shim. Implementers build and test exclusively against the test-only env override pointed at a temp directory; every live write to the real store is the main thread's, so it can be named in the close-out with its undo line. A subagent that writes the real store mutates the memory index this very session is running on.
- **Bound every value at the write boundary, not only at display.** A display cap is not a write cap. Any value that reaches a JSONL line gets its length and charset enforced before serialization, because the append-atomicity guarantee holds only for bounded lines and a downstream reader will later join that value onto a path. Added after two instances: S1 wrote uncapped `summary`/`detail` behind display-only constants, and S2 stamped an unbounded, uncharset-checked filename derived from a tool payload.
- **A comment claiming single-sourcing must be true, and a shared predicate lives in one place.** When two components decide the same question (what counts as a memory file, which directory is a tier root, what a valid name is), export one function and have both call it. Do not re-derive it and then assert in a comment that the two cannot drift. Added after S2 shipped three separate definitions of "is this a memory file" under a header claiming they were single-sourced.

## Sections of Work

### 1. memq core and the outcome journal
Model: fable
New `plugins/claude-kit/scripts/memq.js` (Node, no dependencies, same runtime posture as the hooks). Subcommands:
- `memq log <key> pass|fail "<summary>" [--tag t]... [--detail "..."]` appends `{ts, key, outcome, summary, tags?, detail?}` as one line to `outcomes.jsonl` in the project memory dir. Warns (does not block) on an unregistered tag.
- `memq find <term> [--tag t] [--outcomes|--memories|--all]` returns deterministic summary lines: for journal keys, `<key>  <pass>/<fail>  last <age>  <latest summary>`; for memory files, `<name>  [tags]  <description>`. Match is key-prefix or substring over keys/names/descriptions, intersected with `--tag` when given.
- `memq get <key|name>` returns the full journal entries for a key (newest first, capped with a count line) or the full body of a memory file.
Shared internals: project memory dir resolution via Claude Code's cwd sanitization (verified against this repo's real `~/.claude/projects/D--personal-sapplefeld-claude-kit/memory` at build); a test-only env override for the memory root; a lockfile helper (acquire with stale-break, for later sections' shared writes); the tag registry reader against `~/.claude/memory-types/tag-registry.md` (format defined here: one tag per line with an optional one-phrase gloss; content seeded by S5). UTF-8 throughout.
Registry-absent predicate: an absent registry file means the vocabulary is not yet established and no tag warns; a present file makes the vocabulary authoritative, so any tag outside it warns, an empty file included. Without this split, `memq log` would warn on every invocation for the whole window between S1 and S5, training the warning to be ignored before the registry it guards exists.
Acceptance: a log/find/get round-trip works against the real project memory dir; two concurrent `memq log` processes produce two intact lines (no interleaving, no loss); `find` output is byte-stable for identical store state, meaning the ordering and content of lines never depend on filesystem enumeration order (the `last <age>` field is a function of wall clock by construction, so stability holds within a coarse age bucket, not across one); an unregistered tag warns and still logs; malformed journal lines are skipped with a stderr note, never a crash.
Tests: lock both directions of the append guarantee (concurrent writers intact; a malformed line does not poison later reads) and the unregistered-tag warn; the Windows fs-failure preload pattern from the test suite applies where fault injection is needed.

### 2. Usage stamping
Model: opus
New `plugins/claude-kit/hooks/memory-usage-stamp.js`, registered in `hooks.json` under PostToolUse matcher `Read`. When the read path is inside a resolved memory directory (project tier or type tier), append `{ts, file, kind: "read"}` to that tier's `usage.jsonl`; otherwise exit silently. Fail-open on every error; never blocks; `process.exitCode` (not `exit()`) per the canary precedent. Add `memq touch <name> --applied` appending `{ts, file, kind: "applied"}`, the self-report path.
Acceptance: a Read of a memory file stamps; a Read elsewhere does not; a broken usage file or unwritable dir exits 0 silently; `touch --applied` stamps the applied kind; `hooks.json` parses with the new entry and the canary load-checks it.
Tests: both directions of the path predicate (memory file stamps, non-memory file does not), and fail-open under an injected write failure.

### 3. Decay lifecycle
Model: fable
`memq decay-scan` computes candidates deterministically: memories with no `applied` in 30 days (summarize) or 60 days (archive), journal entries older than 30 days (roll up per key), each with the evidence dates in the output line; writes nothing itself. The decay stamp is `memory/decay-stamp` (mtime is the record), touched when a pass completes. finishing-work step 7 gains the pass: when the stamp is older than 14 days, run the scan, act on candidates with judgment (summarize in place keeping the description, `git`-less move to `memory/archive/`, roll up journal entries, prune index lines, tag hygiene), and touch the stamp. New `plugins/claude-kit/hooks/memory-session.js` on SessionStart (`startup|resume`): when the stamp is 30+ days old, emit a one-line nudge naming the pass; otherwise silent. The skill (S5) owns the "applied means acted on, not read" definition.
Acceptance: decay-scan flags a memory idle past each threshold and not one with a recent `applied` stamp; the rolled-up journal preserves per-key tallies; finishing-work's step 7 text names the trigger, the pass, and the stamp; the nudge fires only past 30 days; `session-start.js` is untouched.
Carried from the S2 review: the `usage.jsonl` reader skips a malformed line the way `readJournal` does and never rewrites the file, which is what lets the type-tier sidecar stay lock-free under concurrent writers from different projects (a torn append then costs one stamp, not a failed pass). The decay pass prunes `usage.jsonl` alongside the journal rollup, since that sidecar grows automatically on every read while the journal grows only on a deliberate `log`. Stamps stop by design once a memory moves to `memory/archive/`, so the pass must not read that silence as idleness.
Tests: both threshold directions (idle decays, applied resets), and the nudge's silent path.

### 4. Project-type tier
Model: fable
`~/.claude/memory-types/<type>/` holding file-per-fact memories and a `MEMORY.md` index, same format as the project tier. A project opts in via a `Project-Type: <type>` line at the top of its memory `MEMORY.md`. `memory-session.js` gains the loader: parse the line, emit the type tier's index into session context (bounded; the index only, never file bodies). `memq find/get` span both tiers, labeling the tier in output; `memq` type-tier writes (a `memq add-type` or documented Write-then-index flow, decided at build) take the S1 lockfile. `memory-usage-stamp.js` covers type-tier reads (S2 already predicates on resolved memory dirs; confirm the type root is in its resolution set). The skill owns the routing rule and the starter set of types.
Acceptance: a project with the line gets its type index at session start and one without gets nothing; `find` returns hits from both tiers with tier labels; concurrent type-index writes from two projects serialize under the lock; decay-scan covers the type tier.
Carried from the S2 review, and owned here rather than in S2 because this is where the tier comes into existence: `memq touch` resolves the project tier only, while the usage-stamp hook already stamps `read` into both tiers. Left as-is, a type-tier memory would accumulate reads, never receive an `applied` stamp, and be flagged for archival at day 60 no matter how heavily used. S4 gives `touch` a type-tier target so both tiers can carry the signal decay keys on.
Tests: loader both directions (typed project emits, untyped is silent) and lock serialization on the shared index.

## Out of Scope

- Vector databases or embeddings. Prefix-keyed search over structured text is inspectable, diffable, and sufficient at personal scale; his own system runs JSON for the same reason.
- Compaction-time memory eviction and reload. The harness owns compaction; the kit's plan-doc plus re-readable store recovery is the practical approximation.
- Modifying Claude Code's built-in auto-memory prompt. The conventions layer on top; the built-in file-per-fact flow remains the path for durable facts.
- A non-Windows shim installer (rides the existing `doctor.sh` backlog item).
- Any external consumer of the journals (the AI OS reads `kit-events.jsonl`, not these).

## Open Questions

- The starter tag registry contents beyond the seed set: Scott's call, cheap to extend at any time.
- The outcome-logging noise bar: tune on the first weeks of real entries; the risk is journal noise, not index bloat, so it can settle empirically.
- Whether `memq add-type` (guided write) or documented direct Write is the type-tier authoring flow: **decided 2026-07-30, `memq add-type`.** The premise that both options sit "under the lock" does not hold on inspection: a documented direct-Write flow cannot take a lock, because the Write tool has no way to acquire one, so only the guided command can actually serialize the concurrent writers this tier exists to support. The lock is the whole reason the type tier is singled out as the genuinely shared surface, so the authoring flow has to be the one that can hold it.

### Chapter 3 - 2026-07-30
Completed: Section 3, decay lifecycle.
Implemented By: implementer-fable (fable override from an Opus session), one dispatch plus one review-fix round on the same agent.
Metrics: 1 review round (adversarial + blind at fable per Fable Spend, security at session model); 0 NEEDS_CONTEXT; 0 escalations; 1 API-error interruption recovered; advisor opus.
Decisions / Surprises:
- The section's central finding, and all three reviewers reached it independently: the spec made the scan deterministic code but left the mutation to the model hand-editing an unversioned store. The tell was that `memq.js` documents "neither sidecar is ever rewritten or truncated" while the skill text instructed exactly that rewrite by hand. Three things made it unacceptable rather than untidy: there is no version control under `~/.claude`, so a bad rollup is unrecoverable; the PostToolUse stamp hook appends to `usage.jsonl` on every memory read, including the reads the model performs while judging candidates, so the read-modify-write races itself inside a single session; and a sibling session widens that window. Resolution: a new `memq decay-prune` owns all mechanical mutation. It takes the lock the module already exported, validates every archive name and its source and destination before anything mutates, and routes every rewrite through backup, temp-write, concurrent-append tail-copy, and rename. The model keeps the judgment (which memories to summarize, which to archive) and the summarize edit, which is prose. That split is what the spec's "deterministically scanned, human-judged" was reaching for.
- The rollup acceptance criterion had no path to passing as specified. A journal entry carries one `outcome`, and `find` tallies by counting entries, so rolling 2/1 into one entry yielded 1/0 in every later `find`.
