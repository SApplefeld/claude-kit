## Goal

A leashed run in another repository compacted at the safety valve, mid-section, after three review-round adjudications with no section closing and no interim board entry. Asked to trace it, that session read the hook source and ranked five compounding causes: its own missed ritual (primary), a ten-minute checkpoint bound sized for 6 to 12 minute implementer runs against measured step durations of 22, 27, 67 and 73 minutes, the drought rule living only in a skill body that an earlier compaction had truncated, a Stop reminder that names the Chapter case and not the interim one, and a gate that logs nothing, so none of this is measurable. Every one of those readings is confirmed against the source below. When this plan is done:

- The gate records every decision it takes: a state file the CLI and a new hook read, and an append-only log an operator reads, both under the project's `.kit/`, both written after the verdict and never affecting it. "This keeps happening" becomes a count with timestamps.
- A checkpoint opened while an auto-compaction offer is already being held is honored until it is consumed or cleared, for as long as the gate keeps deferring: in practice for the life of the deferral episode behind it, whose four-hour idle bound is the honest ceiling and sits roughly three times outside the measured step durations, under an outer 24-hour sanity cap; a checkpoint opened below the trigger keeps the ten-minute bound, because the reason for that bound (a leftover honored mid-section on every later cycle) is real and unchanged.
- A PostToolUse hook, `compact-deferral-nudge.js`, tells the model, once per deferral episode at the return of a long tool call, that the gate is holding offers and names the interim-board ritual and the CLI call that closes it. The rule now lives where compaction cannot delete it.
- The Stop reminder names the interim-board case beside the Chapter case. finishing-work gains the interim boundary it had none of, keyed on the same signal, which closes the backlog item that said the finishing pass needed a trigger of its own. The CLI's `status` shows the gate's state.

## Approach

The design decisions, settled 2026-08-23 in the reviewing session, each with its reason:

- **Mechanism over discipline at every avenue that has a mechanism.** The diagnosing session fixed its own cause by writing the board it had missed, and named the bet that fix rests on: not missing the ritual a fourth time, which is the bet that lost three times. Each avenue below gets a hook, a record, or a rule leg, and the discipline stays as the floor.
- **The ten-minute bound is not raised.** `kit-compact-lib.js` states why it exists: a boundary reached below the compaction trigger has no offer to catch, and honoring its checkpoint later, when the next Chapter crosses the trigger mid-section, lands the compaction mid-chapter on every cycle after the first. Raising the bound to hours would re-open exactly that. What the bound is a proxy for is whether an offer was pending when the checkpoint opened, and the gate can now record that fact directly.
- **The gate's own state is the source of "an offer is pending."** Consumption is monotonic until a compaction lands, and past the trigger the harness re-offers every assistant turn, so once the gate has denied an auto offer, offers recur until one is allowed; a recorded deny with no later allow is a pending offer. The checkpoint CLI reads that state at `open` and writes `pendingOffer: true` when an episode is open. No trigger value has to be read from settings and no transcript has to be read at open. The recorded flag is necessary but not sufficient: a manual `/compact` never reaches this gate (its PreCompact matcher is auto-only) and so neither consumes the checkpoint nor ends the episode, so the flag can outlive the hold it describes. The long leg therefore also requires the gate state to still show an episode open, owned by this binding, and dated before the record it vouches for. That is one shared predicate at three call sites rather than a new instrument.
- **A pending checkpoint has no outer bound that matters, and gets one anyway.** By construction it is consumed at the first assistant turn after the long call, since the offer recurs every turn; nothing else has run in between, so honoring it lands the compaction at the boundary, late but correctly placed. A 24-hour sanity bound and the existing future-skew check stay, so a hand-made or clock-skewed record cannot become immortal. The operational bound is tighter and is the episode's own life: corroboration needs an open episode, and one goes idle four hours after its newest denial, so a call outrunning four hours drops its checkpoint back to the ten-minute leg.
- **The log stays project-local, in `.kit/`, and does not join `~/.claude/kit-events.jsonl`.** The events sink has two external consumers, Spine's `kit_event_cursor` and the channels broker's blocked-state fold, whose handling of an unknown event kind was not read in this session; a project-local log answers "how often, and why" without touching their contract. Promoting deferral events to the sink is a later change taken after those consumers are read. The log is bounded: when it passes 2 MB the writer keeps the newest 1 MB.
- **A nudge, never an auto-open,** on the reasoning `chapter-boundary-nudge.js` already carries: the checkpoint belongs after the board is written and the commit model honored, and an auto-open at a tool return would admit a compaction before either. The nudge is a detector plus a directive; a misfire costs a sentence.
- **The nudge rides PostToolUse on the long-return tools, once per episode.** The deny happens at a turn boundary where the model sees nothing (PreCompact stderr reaches the operator only). The first thing the model reads afterward is a tool result, so that is where the directive goes, on `Agent`, `TaskOutput`, `Bash`, and `PowerShell` (the tools whose results follow a wait; `Edit`, `Write`, and `MultiEdit` belong to the boundary nudge). It fires once per deferral episode and again after a 30-minute interval while the episode persists, so a deferral held across a hundred turns is two sentences rather than a hundred. The expected sequence, which the log will show on a real run: tool result plus nudge; the next offer denied once more (no checkpoint yet); the model writes the board, honors the commit model, opens the checkpoint under the pending episode; the next offer allowed and consumed; the compaction lands at the board.
- **The nudge's text carries two integers and nothing else from state:** the count of held offers and the minutes since the episode opened. No path, no session id, no log string, the same provenance bound `memory-session.js` holds for its nudges.
- **The finishing pass takes the same signal.** The backlog item parked the finishing boundary because the section loop's trigger (a count of adjudications without a close) has no analogue there. The gate's recorded deferral is the analogue: the nudge fires between finishing steps exactly as it does between section steps, and finishing-work's rule is the same interim board entry (`### Interim board N`) and the same `open`. No new count, no new heading shape.
- **Reminder texts name the interim case.** Both texts in `kit-goal-stop.js` are conditioned on "a Chapter has been closed"; each gains "or the compaction gate has been holding offers since the last boundary", and their test pins move with them.

## Sections of Work

### 1. The gate records every decision

Model: opus

In `kit-compact-lib.js`, add the gate-state helpers the gate, the CLI, and the Section 3 hook share: `gateStatePath(cwd)` (`.kit/compact-gate.json`), `gateLogPath(cwd)` (`.kit/compact-gate.jsonl`), `readGateState(cwd)` (null on any failure), `recordGateDecision(cwd, decision)` (writes the state atomically the way `writeCheckpoint` does and appends one JSON line to the log; never throws; returns nothing the caller can branch on). A decision carries `at` (ISO), `verdict` (`allow`, `deny-boundary`, `deny-interactive`), `reason` (the clause that decided: `not-auto`, `external-engine`, `no-session`, `no-goal`, `bystander`, `automation`, `checkpoint` (allowed and consumed), `valve`, `illegible`, and for a boundary deny the checkpoint's own mismatch reason from `checkpointMatches`), `consumed` (the token reading or null), `checkpoint` (`{ageSeconds, pendingOffer}` when a record was present, else null), and `session` (the payload's id, a harness-generated string). The state holds `lastDecision` (the newest record), `episode` (`{session, since, denials, lastDeniedAt, nudgedAt}` while a boundary deny stands with no later allow from its own session, else null), and `lastAllow`. The episode belongs to the leash rather than to a session. Only a `deny-boundary` opens or extends one, and only the bound session can produce that verdict, so a `deny-interactive` records its decision and leaves any standing episode untouched. A boundary deny whose session does not own the standing episode replaces it, because on that path a foreign incumbent can only be a dead binding rather than a rival. An allow clears the episode only when the allower owns it, since a bystander lands a compaction in its own context while the bound session's offers stay pending. The log is bounded: past 2 MB the writer rewrites it to its newest 1 MB.

In `kit-compact-gate.js`, call `recordGateDecision` after the verdict on every path, inside its own try so a write failure cannot change the verdict or the exit code; extend the boundary note with the episode's count and age in minutes when the state is readable ("held N offers over M minutes"), integers only. In `kit-compact-checkpoint.js`, `status` prints the gate state after the checkpoint lines: the last decision's verdict, reason and age, and the open episode's count and age, or "no deferral episode is open".

Tests, red first, in `test/kit-compact-gate.test.js`: each verdict path writes the expected record and state; a deny followed by an allow resets the episode; two denies count two; an unwritable `.kit/` (a file where the directory should be) leaves the verdict and exit code unchanged and writes nothing; the log cap rewrites to the tail; `status` renders the state; the note carries the integers.
