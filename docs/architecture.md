# Kit Architecture

The kit is a Claude Code plugin plus the repo material that maintains it. Almost all of it is prose: skills the model loads on demand, agent definitions, an output style the harness applies to every main-thread session, and a doctrine file that ships to the user's home directory. The exceptions are the pieces with real runtime behavior, and there are two: the Node hooks wired to session and tool events, and the `memq` CLI over the memory store.

That split is the thing to hold onto when changing anything here. Prose surfaces are behavior-shaping text whose general gate is the writing-skills RED/GREEN check; the hooks and the CLI are code with a real gate under `test/`. Two prose surfaces are the exception, for the same reason in both cases: the home doctrine and the output style each carry a copy of text whose source is elsewhere, so `test/doctrine-parity.test.js` and `test/output-style-parity.test.js` hold those copies byte-identical to it. Identity is not presence, and the doctrine gate covers both: its tests are one whole-body comparison plus a set of presence pins: assertions pinning individual rules present and the far ends they route to, a group holding one drift class where an amendment falsifies an unchanged sentence elsewhere, the pointer pairs naming the coordinator skill and the role skill, whose near ends are the repo README's payload map and the peer-sessions Roles section rather than any doctrine bullet, a group holding a deliberate duplication in step, where one rule is stated in full in the doctrine and again at the point of action and only a pin keeps the two statements saying the same thing, and a group over the seats' own contracts, the coordinator's function enumeration held against the count that enumeration states, the standing-delegation model's exclusions and the three refusal rules it composes with, and the reciprocal kaizen routing duty. That set is described here rather than counted, and deliberately so: it grows with every surface it comes to guard, and a count restated on a second surface is an invariant nothing checks, which is the defect class several of these pins exist to catch. What earns a rule its own pin is deferral. A bullet carrying its own content fails loudly when it is deleted, so a pin adds nothing, while a bullet that moves its operative content into a skill and keeps only a pointer can be deleted from both copies at once, pass the identity check, and leave the always-on layer silent with committed pointers aiming at nothing. Nine bullets meet that test today: the memory-extension pointer, the standing-dispatch grant, the chapter-close checkpoint sentence, the two liveness bullets, the peer-sessions pointer, the outline bullet, and the gate and test-authoring bullets that route the lanes, the cost shapes, and the red protocol to `testing-discipline`. Three of those pins reach the far end as well, which is the half a presence check otherwise leaves open: the outline bullet's asserts that the style skills it routes to still carry a recipe and that the four surfaces restating the rule still say so, and the peer-sessions bullet's asserts that the bullet still names its skill, that the skill is on disk carrying the three sections the bullet defers to (its contracts, sanctioned patterns, and etiquette) plus the Naming section the coordinator skill defers to from the other direction, which rides in this pin rather than one of its own because it is the same defect class against the same file, and that the skill's file is tracked in git's index, so deleting the skill, emptying it to a stub, or committing without the new directory cannot leave the pointer aiming at nothing with the suite green. The testing pair's far end is asserted the same way and across more surfaces, because its pointers reach past the doctrine: the skill on disk still carries the three sections the two bullets route to and the named leads inside them, the five surfaces that point at the skill rather than restating it still carry their pointer clause, and the adversarial reviewer's charter still judges test-worthiness by that litmus rather than by a list of its own.

## Repo layout

- **`plugins/claude-kit/`** is the installable payload, and the only zone an installed plugin loads. It holds `skills/` (24 skills, each a `SKILL.md` plus optional `references/`), `agents/` (three code reviewers and two document reviewers, implementers by model tier, the QA verifier, the docs curator, the design facilitator, the council member, the consultant; frontmatter pins a model where the role fixes one, and pins effort on eleven: `effort: medium` on implementer-sonnet, implementer-opus, the QA verifier and the docs curator, and `effort: high` on the three code reviewers, both document reviewers, implementer-fable, and the consultant, since judgment-heavy work is where deeper effort converts into signal and plan-following work is where it converts into tangents. Effort above a pinned default is chosen per dispatch, and the executing-work skill's reviewer-effort table owns that rule), `hooks/` (Node scripts plus `hooks.json`), `output-styles/` (one file, `kit.md`, the `Kit` style described under the always-on boundary below), `scripts/` (the `memq` CLI, its shim, `memory-index.js`, which owns the optional embedding stack and the semantic index, and the status line's two files, `kit-statusline.js` and `kit-goal-statusline.js`, described under Status line below), and `doctor/` (the Windows first-run and repair tool, whose installers sit beside it one per repair; it has no destructive action, so `-Fix` never deletes).
- **`home/`** holds the two files that land in the user's home directory rather than loading from the plugin: `CLAUDE.md`, an import stub that pulls the doctrine in and carries any machine-local pointers, and `claude-kit-doctrine.md`, the doctrine body itself. The doctrine's single source is the `operating-instructions` skill: `doctrine-refresh.js` strips that skill's frontmatter and writes the body to `~/.claude/claude-kit-doctrine.md` each session, so the copy here must stay byte-identical to the skill's body or a session loads doctrine the repo does not show. What earns a place in that body is a separate question, answered by the always-on boundary below.
- **`docs/`** is the working library: about-the-solution documents at the root, active plans in `plans/`, finished history in `archive/`. It is not part of the payload.
- **`kaizen/`** is the kit's self-improvement inbox, one note per piece of observed kit friction.
- **`settings/settings.recommended.json`** is the recommended user settings shape.
- **`test/`** is the gate over every code surface, and it is the only place a runner reaches. The suite is `node --test test/*.test.js`, spelled with the glob rather than the bare directory. One flat file per surface, named `<surface>.test.js`, with no subdirectories and no `describe` blocks, so a run reporting `suites 0` is the mechanical proof that nothing nested. A test file living anywhere else is invoked by nothing, and its coverage exists on paper only. `testing-discipline` defines a contention lane that would sit outside that glob and run serially at finishing and before a push; this repo has none, because no test here has machine-shared state as its genuine subject, so every test file under `test/` is in the main gate.
- **`tools/`** holds repo-side utilities that do not ship: `transcript-study/`, the session-corpus analysis scripts.
- **`build.ps1`, `build.sh`, `.claude-plugin/marketplace.json`** package and publish the plugin. Both builders stamp `plugins/claude-kit/.claude-plugin/build-info.json` before collecting files, so the stamp ships inside the zip: the git short hash and a dirty flag `kit-version-nudge.js` reads, plus a `hooks` map of `<filename>: <sha256>` over every file in the packaged `hooks/` directory, which the canary compares the executing cache against. The stamp carries no wall clock, so a clean rebuild of the same commit stays byte-identical, and it is gitignored, so the copy in a working tree is only as fresh as the last local build. `build.sh` fails the build rather than stamping when it cannot produce a 64-character hash for a hook, because a partial manifest would make every install read as tampered.

## Always-on boundary

The doctrine is the prose the model carries into every task, so what lives in it is an architectural decision rather than an editorial one. It holds the rules that are general (true in any repo, not just the one that taught them), earned (the harness's own system prompt and tool descriptions do not already guarantee them), and needed before any skill has been loaded. Everything else lives in the skill that owns the moment the rule applies, and the doctrine points at it. The communication register is the one part of that always-on text carried on a second surface as well, and the register surfaces below say why.

Orchestration mechanics are the largest thing that boundary keeps out. `brainstorming` owns the model tier bands, which session model executes an approved spec, and the scout sweep that derives a section's files in scope from the tree wherever the design changes a contract or a shared surface; `executing-work` owns dispatch briefs, the orchestrator's own re-read of a plan's `Standing Brief Amendments` block at every section open (a grep rather than a read, because step 4 writes to that block mid-run and any earlier full-doc read is stale by construction, and the only delivery an inline section gets, having no brief for the entries to fold into), scout banding and the scout return contract, the serialize-what-cannot-be-shared rule, the stagger rule that advances concurrent sections offset rather than in lockstep, the interim board entry a closure drought earns, the route that sends a surface found outside a section's declared files to a fold, an appended section, or out of the plan, the review round a qualifying fix delta owes and the re-open, in the closing section's own round, of a completed section's document whose described behavior that section changed, the moment a section's verified state commits under each commit model, the controller's gate, the review roster, which is two pairs rather than one (the code pair over a diff, and the document pair a section's `Audience:` line summons), the rule that runs every per-section reviewer one tier up from the section's writer tier without ever lifting a review past opus or pulling one below the writer's own tier, so a fable-tier section keeps fable pairs, with the security reviewer excepted from fable, and the reviewer-effort table that pairs an effort with whatever model that rule lands on. `finishing-work` owns the matching floor, and it is two states rather than one: fable at `high` by default, and a compensated re-dispatch at Opus and `max` where that gate could not be run at its fable tier. It also owns the wedge hallmark, the cross-class liveness predicate that decides when a dispatch of any class may be stopped for being quiet, along with the readings that fill it and the cadence it runs on. The hallmark's middle term takes one of three readings, and the dispatch's shape picks it. A dispatch that has taken a turn is read on byte growth, against its class's growth window and its class's probe window. One that has taken none is read on the count of `"type":"assistant"` lines whose `message.model` is not the harness's `<synthetic>` error placeholder, against a five-minute first-turn window and a five-minute probe, one pair shared by every class rather than derived per class the way the growth windows are: the asymmetry that sets the long windows, that a stop discards what a live agent built, carries no weight for an agent that has built nothing. One whose transcript cannot be read at all keeps its own class's growth and probe windows, since the shape that would earn the short pair is read from the very file that is unreadable. The same transcript is the resolved-model artifact: the distribution of `message.model` across its assistant lines is what the round ran at, while the dispatch record and the `.meta.json` sidecar beside the transcript carry only what was requested, so a harness that substitutes silently is read from the difference rather than from the absence of an error. That predicate fires during execution rather than at the finish, and every surface naming it points at it rather than restating it: `executing-work` at its dispatch sites, `consult`, `brainstorming`, `standing-watch`, which writes the check into its tick order because a watch re-blocks on nothing for the cadence to fire on, the doctrine's two liveness bullets, and the README. The doctrine keeps the habit and the route (the file by path under the plugin root, the rule found by its bold lead, since finishing-work carries no heading for it) and no number of its own, because its audience includes sessions that never load that skill and a bare pointer would leave them holding a duty they cannot discharge. The hallmark leans back on the doctrine once, and the dependency runs the other way there: a zero-growth transcript reading is an absence-proving check, so it takes the positive control the doctrine's "Make the test earn its green" bullet requires of any check that proves an absence through a hand-authored pattern, path, or scope, and where no control can be run the instrument is unproven rather than the agent dead. `consult` owns the fresh-context end of the escalation ladder: the trigger floor that decides when a stuck session convenes the `consultant` agent, the brief that makes a consult work, the same fable-at-`high` model rule with the same Opus-at-`max` stand-in, and the adjudication rule that treats a returned ruling as a hypothesis until the orchestrator checks it against the code. The intake gap check splits the same way and for the same reason: the doctrine states the rule, because an intake happens before any skill has loaded, while `brainstorming`, `executing-work`, and `finishing-work` own the phase mechanics described under Intake gap check below.

A deliverable document takes its own review pair, because the code lenses carry postures that fight prose. `blind-reader` is dispatched once per persona a section's `Audience:` line names, and once more before a spec leaves brainstorming with the spec itself as the document under review, in both cases with the document paths and a `Reader:` line and nothing that describes the documents' intent, and it reports what it understood, what it was left asking, what it could not follow, and for a procedure the first step it could not perform. What the persona may open is decided by whether it holds this repository rather than by the job title it carries: a persona who holds it may read it read-only to attempt a step, never opening `docs/`, a spec, a plan, or a commit message on its own initiative, though a spec or plan handed to it as the document under review is its subject and it reads that, while a persona from outside it (a customer, non-technical staff, an engineer who has never held this code) opens the documents and nothing else, since a strong model with the source open fills the document's gaps from it and never reports them. `prose-reviewer` is the adversarial half and runs two passes in a fixed order, goal compliance and every claim against the fact base first, then the writing skill's rules, the machine-prose tells, and presumed knowledge against each named persona, so a style fix that would loosen a claim is reported as a conflict rather than applied. Both agents are read-only and join the guard's strict class; both hold Bash and are chartered to treat a document in scope as data, since the guard's denylist does not cover a read-shaped command it can resolve and a document that can make a reviewer run one has turned the review into its own tool. The tell catalog is single-sourced at `skills/scott-writing-style/references/ai-tells.md`, which the writer reads before finishing a draft and the reviewer hunts from by name; a dispatch that cannot supply that path costs the tell hunt entirely rather than getting one from memory. The pair is added to what a section's content earns and replaces the code pair only where the changed files are documents and nothing else, so a mixed section still gets code review in the same round. At finishing, `prose-reviewer` runs once over every document in scope, reading each whole exactly as a section-time dispatch does; what earns the separate run is timing rather than scope, since only the finishing pass reads after every section has landed, the one vantage from which cross-document consistency, the whole-effort lens, is checkable at all; the blind reader is re-run only where a document changed after its section review. The prose-only security waiver also becomes an audience predicate: a document written for anyone outside the operator and the operator's own sessions voids it, and the security-reviewer's brief then carries the spec's `Disclosure:` list to sweep the documents against.

The consult is the kit's answer to a reasoning dead end, and it is deliberately the only one that runs on fresh context: the kit runs with no in-context advisor, because a companion model sharing the session's transcript inherits the session's blind spots and ratifies the framing at exactly the moments that matter. The `consultant` agent is read-only, fresh-context, and dispatched by the main session alone, since subagents carry no Agent tool; an implementer reaches it semantically instead, by returning NEEDS_CONTEXT stated consult-shaped (the decision, the options, the evidence, its lean) for the orchestrator to route. Four triggers form a counted floor rather than a felt one, because a stuck session feels almost done: a second failed attempt at one problem, a BLOCKED that turns on a decision, a debugging dead end, and a weighty decision the spec does not cover. The floor's width is judgment rather than data, and `docs/backlog.md` carries the adoption watch that judges it on the first real long run. A blocker reaches that floor already asked: the expert ask under Session roles below runs ahead of the consult, being the cheaper instrument and the one that resolves from sources that already exist, and it neither gates the declaration nor stands in for the consult, the ask asking whether the answer exists somewhere already and the consult asking whether the framing is wrong.

The doctrine's "Orchestrating fan-out work" section is three bullets. One points at those two skills, which buys always-on context back at the cost of a load: fanning out scouts, implementers, or reviewers outside a skill-driven run depends on that pointer actually triggering the skill load, an accepted risk rather than a guarantee. The other is the standing dispatch request, and it is the one place the always-on text carries a tool authorization rather than a rule. It covers the Agent tool for dispatch generally, and the Workflow tool for one narrow purpose, dispatching a read-only agent (a fresh-context reviewer, the consultant) at an effort the Agent tool cannot set. The covered class is a predicate the doctrine states itself (a read-only dispatch needing its effort set per call, naming an `agentType` the read-only guard governs) rather than a reference to what the skills say, because a skill that defined the class would be granting itself a permission the doctrine scopes; the skills say where and how and cannot widen it. The grant lapses on its own terms if the Agent tool ever gains a per-dispatch effort parameter. The third points at the `peer-sessions` skill, and it is the section's only outward-facing rule: the other two govern agents this session dispatches, while this one governs independent sessions it does not own, which is why it carves its own subagents back out and leaves them to executing-work and finishing-work.

One further Workflow authorization sits outside that class and outside the doctrine entirely, in `/kit-goal` arming. The arming invocation is user-typed, so it carries the operator's own request for that run: reduce wall-clock time by parallelizing whatever the sections and their gates allow, through subagent dispatch and through Workflows. Its authority is the arming act rather than any skill's text, its scope is executing the armed plan and nothing wider, and the canonical condition text `kit-goal-lib.js` composes carries the request, so it rides with the goal state across a session swap and the Stop hook restates it at the point of action.

Project-specific rules are kept out the same way. A product's honesty and privacy gates, its identity and framing constraints, and its test-suite naming live in that project's own `CLAUDE.md`, next to the gate tests that enforce them. The doctrine keeps only the general form: nothing untrue ships, and where a project defines honesty or privacy gates, a violation is a defect to sweep the whole tree for. The same rule sends .NET lessons to `csharp-style` and the capture bar to `kaizen` rather than into the always-on text.

Language-scoped knowledge splits on that seam too, and the outline-first reading rule is the sharpest instance of it. The doctrine states the principle, that a file past roughly 1,000 lines you are opening to find one thing is grepped for declarations and section labels before any range of it is read, along with the two guardrails that fail quietly (an outline never proves absence, so a symbol not found in one still earns a whole-file search, and an `<auto-generated>` header means grepping for the member by name instead). It carries no patterns. Those live in `csharp-style` and `sql-style`, each of which gained an Outlining section holding a recipe verified against a real file, because a language-agnostic surface cannot hold the house idioms a generic pattern misses: T-SQL's leading-semicolon `;ALTER PROCEDURE` deployment form and the banner comment whose label sits on the line after its border, C#'s `#region` organization and the interface whose members carry no access modifier for a member grep to anchor on. For a language no style skill covers, the bullet says to compose that language's own declaration and section markers on the spot, and no JS or TS anchors ship at all, the kit having no JS house style with the standing to own them. The trigger is the hunt rather than the size: a file whose whole content is the point is read whole, which is what keeps the rule from colliding with the two committed read-in-full mandates the kit already carries, `executing-work`'s post-compaction plan-doc read and the blind reviewer's charter.

Test discipline splits on the same seam, and what the doctrine keeps is set by what a session needs before any skill has loaded. It keeps which lane each gate moment takes (the targeted lane after every fix, the whole gate at section close, at finishing, and before a push, and the whole gate after a fix round only when that round's delta touches a shared module), the delta report against a baseline recorded on that same lane, the real exit code, green-necessary-not-sufficient, and the merge-reddens-a-suite warning. `testing-discipline` owns what the doctrine used to spell out: the litmus for what earns a test, the shared-setup blind spot, the cost shapes and their cheaper forms, the lane mechanics, the red protocol, the comparable-contention rule, and the engine-agnostic box check. Two doctrine bullets carry that pointer, and because each defers its operative mechanics rather than carrying them, each earns a presence pin among the nine above. Five surfaces point rather than restate: executing-work's step 2, its Dispatch Brief template's `Tests:` field, its step 3 (which points at the doctrine's gate bullet, that moment's own owner, rather than at the skill), brainstorming's `Tests:`-line paragraph, and the repo README's payload map. The adversarial reviewer's charter joins them from outside the doctrine, because that charter adjudicates every section review and a litmus restated there would outlive every deletion the fold performed. Two rules are deliberately stated in full on both surfaces rather than deferred, the targeted lane's definition and the contention lane's schedule, so a doctrine-only reader runs the right lane without loading anything, and a cross-surface pin holds the two statements identical. What the skill does not carry is any command: a repo's suite invocation and its lane commands are per-repo facts that live in that project's memory tier, which is what lets one skill ship kit-wide.

Mode-specific rules are kept out on the same test, and `standing-watch` is the case that names the mode. A session watching a live system it does not own, waking on a timer or an operator message, re-deriving the board, intervening, writing a ledger and sleeping again, carries failure modes no other work has, so the ledger's standing-versus-situational split, the tick order that arms the wake before it checks anything, the wake prompt that carries prohibitions and never a situation report, the ping's evidence line, and the one-way-door preflight all live in that skill and load only when a watch is running. The doctrine keeps from that same material only what is true of any session whether or not it is watching anything: probe a dispatched agent before killing it, read one heavy process at a time as a per-machine limit, take a background run's exit from a marker it wrote itself, answer "cannot measure" when the source that would answer is down, and ask, in the Before-you-send list, whether every figure or state names the source it came from and the subject it is about. That last one sits inside the register core, so it reaches the output style as well as both doctrine copies; the four bullets live in the doctrine copies alone.

### Intake gap check

Every input the kit takes in gets its gaps enumerated before anything is built on it, and the doctrine carries that rule because an intake precedes any skill load. At an intake (a prompt, a handoff, a spec, a dispatch brief) the session lists what the input does not state, then routes each gap three ways: (a) one an existing source answers (doctrine, memory, the plan doc, the code's own conventions, a house style) is resolved with the source cited; (b) a low-blast, reversible one with a conventional default is decided and declared; (c) a material one that is the operator's to make is asked, batched, with a recommendation. The first two routes produce declared assumptions and the third produces a question. Enumeration is a step rather than a habit because a model fills gaps silently and cannot see the ones it filled, which is the same reason brainstorming's self-review ends in a blind read rather than a second inline pass.

A declared assumption is never left only in a document, because the operator approves plans from the recap without reading the doc. Three surfaces carry it, one per phase. During brainstorming it rides the plan sketch and every later recap the operator approves, as its own `Assumptions` block, and a recap that omits the block has not shown the plan. During execution a material gap the spec does not cover is a `BLOCKED:` on an armed run or a decision ask on an attended one. At close-out the finishing status lists every execution-time entry verbatim, which is what reaches a run the operator walked away from, since under a leash that status is the closing message the `goal-complete` event points at.

The durable record is split in two by the external engine's approval-scoped fingerprint, which covers everything above `## Chapters`. The plan doc's `## Assumptions` section holds the design-time entries and freezes at approval, because a routine mid-run append there would mutate the fingerprinted region and read as approval drift; a deliberate spec amendment above that line is still made when the design changes and is recorded in a Chapter as the drift it is. Everything execution adds rides the Chapter's own `Assumptions:` line, which is append-only and below the boundary. One line format serves both, instanced normatively in brainstorming's spec template:

`- assumed YYYY-MM-DD (<route: a source name | default>): <the assumption>; reversal: <what changing it costs>`

with `, section N` added inside the parenthetical for an execution-time entry. The close-out block is computed from the Chapters rather than by dating entries against `## Assumptions`: no approval date is recorded anywhere, the entries carry day precision, and a plan approved and run the same day is the ordinary case, so a dated filter would report `none` on exactly the walked-away run the block exists to serve. An empty block says `none`, so silence is a stated fact rather than an omission.

Three skills instance the rule at the moments it applies. `brainstorming` carries it into the design conversation: its one-question-at-a-time rule is how route (c) is asked there, its sketch and recaps carry the `Assumptions` block, its spec template holds the `## Assumptions` section (inert to the plan-doc parser and required to stay outside `## Sections of Work`, whose block any foreign `##` heading ends early), and its self-review closes by dispatching `blind-reader` on the spec itself, adjudicating each returned question three ways (answer it in the spec, declare it as an assumption, or put it to the operator with a recommendation) and recording `blind read: <n> questions, <a> answered, <b> assumed, <c> asked` in the handoff recap. That costs one dispatch per spec, and a trivial spec of one or two sections may skip it, saying so. `executing-work` runs the check on the plan doc: it lists what each section leaves unstated during the plan-doc read and routes after `memq recall`, since memory is one of the sources a gap routes to, so a non-material gap is resolved before its section is dispatched and the brief carries the answer rather than the gap. Its implementer-status handling reads a `DONE_WITH_CONCERNS` "spec ambiguity you resolved" concern as a route (b) assumption bound for the Chapter line, while a concern that reads as material re-routes to `NEEDS_CONTEXT`. `finishing-work` step 5 delivers the close-out block and rides the same block on the finishing Chapter.

### Register surfaces

The communication register reaches the model on three copies of one text, and the copies exist because no single surface covers every session. `plugins/claude-kit/skills/operating-instructions/SKILL.md` is the source. `home/claude-kit-doctrine.md` is the mirror `doctrine-refresh.js` writes to the user's home directory, which the home `CLAUDE.md` imports and every subagent therefore inherits. `plugins/claude-kit/output-styles/kit.md` is the third: a Claude Code output style whose marked region carries a subset of the doctrine, the register core, byte-identical.

Coverage and lateness are the two properties no single surface has. CLAUDE.md prose reaches subagents and survives the triggers that deactivate a style (a plugin update lag, an older harness ignoring the force flag, a non-Code surface, safe mode disabling non-builtin styles, and a future deprecation of the feature itself), but it fades as a session grows. An output style rides the system prompt and is re-asserted after tool results, so it binds at turn 200 where the imported prose does not, and it reaches the session's own thread only: subagents never receive it. Holding one text on both surfaces is what buys both properties, and it is why the core is a copy rather than a pointer, since a subagent handed a pointer to style content cannot load it.

The core is seven bullets (`Skip the preamble`, `Disagree up front`, `No false certainty, no flattery`, `Teach the why; treat design as a dialog`, `Write every decision ask to the client-briefing register`, `Narrate the cadence, and close with the state`, `Close with the board when plans are pending`) plus the doctrine's whole `## Before you send` section. Bullets ride whole rather than split at the sentence, because a half-bullet on one surface and its other half on the other is paraphrase adjacency no test can pin. The style's own shell (the reader definition, the teaching posture, and the ★ Insight, ⚖ Decision, and ✎ Memory block mechanics) deliberately never enters the doctrine: subagents inherit the doctrine, and block mechanics in a worker's context would reshape the reports it returns.

Four frontmatter keys are the harness contract, and two of them are load-bearing beyond tidiness. `name: Kit` and a double-quoted `description` identify the style; `keep-coding-instructions: true` is what keeps Claude Code's built-in software-engineering instructions in a kit session, which the style otherwise silently removes; and `force-for-plugin: true` is what activates the style wherever the plugin is enabled, over a machine's own `outputStyle` setting. Rollback is removing that one flag, and safe mode is the always-available escape hatch.

`test/output-style-parity.test.js` is the gate over all of it, in 11 named tests. It pins the frontmatter as a closed set of exactly those four keys, each declared exactly once (YAML is last-key-wins, so a first-match read would accept a `true` followed by a `false`) with the two flags matched against the raw bare token `true`, since a quoted `"true"` is a string to a type-strict reader. It then locates each core bullet by its lead in both doctrine copies and in the style's region, requires exactly one hit in each, and compares bytes; compares the Before-you-send segment from its header to end of body across all three; and pins the region as a closed set, the seven bullets in spec order, then Before-you-send, then nothing but blank lines, so a paraphrased paragraph cannot sit alongside content that passes. The doctrine copies carry no markers of their own, which is why extraction is by lead, and the sync direction is skill to mirror to style core. One consequence lands on whoever edits the doctrine: a new section appended after `## Before you send` fails this test, and the fix is a deliberate call about where the core's boundary now sits rather than a widening of the compared segment.

## Hooks

`plugins/claude-kit/hooks/hooks.json` is the wiring, and every hook is a Node script invoked with the plugin root. The events in use:

- **SessionStart** runs `session-start.js` (eleven blocks: the compact-source re-load instruction, resume surfacing, the notice that in-progress plans sit here with no goal armed, the Ready-parked list, unarchived-plan flagging, the bounded-scan qualifier over every figure the docs/plans/ walk feeds, the kit-repo kaizen nudge, the plugin-view line, the armed-goal notice, the backlog block described below, and the shared-checkout advisory described under Dispatch authority), `branch-reaper-nudge.js`, `kit-version-nudge.js`, `doctrine-refresh.js`, `hook-canary.js`, and `memory-session.js` (the memory index emission described under the memory store below). Matchers differ per hook: the doctrine refresh also fires on `clear`, and `branch-reaper-nudge.js` and `hook-canary.js` skip the `compact` entry, the canary because a plugin cache cannot change mid-session. `session-start.js` firing on `compact` is what makes a compacted session re-read its plan doc, so it is the recovery path the kit relies on; on that source it also leads with a re-load block, emitted whether or not a plan is in progress, because a compaction keeps the doctrine and this hook's output but drops what tool calls had loaded (skill bodies, deferred tool schemas), and a session left to run a summarized skill executes the half the summary kept. Under `KIT_EXTERNAL_ENGINE=1`, the marker an external engine sets on every worker it spawns, four of these stand down: `session-start.js` omits its drive-to-completion push (it still lists each In Progress plan's path and commit model, followed by one line stating that the engine's own directive owns scope and continuation) and suppresses the unleashed notice entirely, since a worker starts in exactly the state that notice describes and a leash armed there would hold it past the section its engine assigned, `hook-canary.js` exits before spawning anything, and `branch-reaper-nudge.js` and `kit-version-nudge.js` emit nothing. The three nudges ask for an attended operator's action a headless worker cannot take, and the canary's sweep is serial child spawns whose report has no reader there, fleet payload integrity being the deploy's concern. `doctrine-refresh.js` and `memory-session.js` stay live: doctrine and memory wiring are wanted inside a worker.
- **PreToolUse** runs seven hooks: `docs-write-guard.js` on write-shaped tools, `memory-frontmatter-guard.js` on `Write|Edit|MultiEdit`, `pr-docs-guard.js`, `merged-pr-push-guard.js`, and `readonly-agent-guard.js` on shell tools, `memq-grant.js` on the Bash tool alone, and `memory-recognition-nudge.js` on every tool, which neither denies nor grants and is described with its PostToolUse half below. `memory-frontmatter-guard.js` is the memory store's write door and is described under the memory store below. `readonly-agent-guard.js` keys on the calling agent's type and governs two classes: the eight judgment agents (the three code reviewers, the two document reviewers, the council member, the design facilitator, and the consultant), for whom the repo tree is read-only, and `qa-verifier`, which may write and delete inside the build-output directories its suites need, and outside them may bring a fresh path into existence with `touch`, `New-Item`, or a copy, but not by any content-writing spelling. Both lose git and GitHub state changes, formatters, and the package-manager verbs that rewrite a lockfile or a tracked project file; reads, builds, and test runs stay untouched for both, and `.kit/` is writable scratch. The five guards fail open on their own malfunction and are denylists otherwise, blocking the shapes they name, with `readonly-agent-guard.js` running the other way on ambiguity it can attribute, denying command text it cannot resolve and a destructive cmdlet fed by an enumerating pipeline whose operands do not resolve, so the `git status --porcelain` comparison that executing-work and finishing-work run around each review round is the backstop for what the heuristics miss. That comparison is two porcelain readings rather than a byte comparison, so it misses an outward `gh` call as much as a merge or a `reset --hard` moving HEAD and the worktree together, and the denylist carries most of that class for exactly that reason. git's own ref, config and remote plumbing is the part it does not carry: the guard leaves `git fetch`, `git remote`, `git config`, `git notes`, `git replace` and `git reflog expire` allowed as review work, so a refspec fetch writing local refs, a remote repointed at another host, and an alias written into the global config each pass with neither control watching. An alias defined on the command line is the one member of that class the guard does take, since `git -c alias.<name>=<value>` puts the invocation's real verb in a config value and leaves the subcommand unresolvable, which is a deny under the same ambiguity rule.
- **PostToolUse** runs five hooks. `format-on-edit.js` runs CSharpier over edited `.cs` files. `memory-usage-stamp.js` records a `read` stamp when the Read tool opens a memory file of any of the three tiers. `memory-recognition-nudge.js` rides both tool boundaries and is the memory store's pull for the session that does not know to ask. It matches the project tier's `triggers:` entries and file anchors against the call: at PreToolUse the `cmd`, `skill`, `agent` and `tool` types, whose subject is knowable from the request and whose nudge is worthless once a command-shaped hazard has run; at PostToolUse the `err` and `glob` types and the records' anchor paths, none of which exists until the call has returned, with the `err` types reached only where the call itself failed, so a successful command that merely wrote progress to stderr raises nothing. A fragment type (`cmd`, `err`, `glob`) matches by containment or by a path-segment walk; an identifier type (`skill`, `agent`, `tool`) matches whole, since `tool:Bash` names Bash and not BashOutput. Every matcher is linear and constructs no regular expression, and a per-call operation budget is spent across the whole matrix, so neither one stored pattern nor a store full of them can cost a call more than a fixed amount of work. Anchors are matched on their paths with the sha ignored, drift being a different question asked by a different surface. The nudge is a pointer and never a body: the record's name, the trigger that fired, one clause of why, and the `memq get` spelling, so the session opens the record itself, and both the name and the trigger text are re-read from the store at the moment of emission rather than trusted from the index. Precision rides with the matcher: once per trigger per session, and at most two nudges per rolling two-minute window, both decided inside a lock over the marker, so a batch of parallel tool calls cannot each see room and each emit. Cache and marker state live in one kit-owned directory under the system temp directory, created 0700 and refused when anything other than a directory of the right ownership stands at the name, with every file written by exclusive create and rename so nothing is written through a planted path, read back as untrusted text against memq's own grammars, and swept by age. One further write goes elsewhere: a nudge log under the project's own gitignored `.kit/`, one line per nudge actually emitted carrying the record, the trigger and the moment, rotating past 1 MB to `.old`, which is what feeds the stamp-rate reading `memory-system/SKILL.md` describes. It stands down for a subagent's call on the same agent keys its siblings defend, since a subagent shares the parent's session id and would spend the parent's dedup budget; it stands down under `KIT_EXTERNAL_ENGINE=1`; and it stands down on a network-shaped working directory or store root, because it resolves the memory directory on every call and that resolution rides a synchronous stat that hangs for the SMB timeout. Every failure is silence at exit 0 on both channels, under a fence that drops any other write to either. `chapter-boundary-nudge.js` closes the checkpoint system's one-way loop: it fires when the session holding the leash on an armed kit goal adds a `### Chapter` heading to the armed plan's own doc, matched by path rather than to any doc under `docs/plans/`, because the reminder opens by asserting that a boundary was reached and that assertion is false on a sibling plan; and it puts a fixed reminder of the executing-work boundary steps (the memory sweep, then the checkpoint open, once the section's commit model has been honored) in front of the model. Added means a Chapter number present in an edit's `new_string` and absent from its `old_string`, not a heading present anywhere in the new text: a real append anchors its `old_string` on the document's tail, which past the first boundary already carries the previous Chapter's heading, so a presence test would go silent on the one shape the hook exists to catch. A whole-file `Write` has no pre-image to diff, so any heading in its content fires it. It reaches the model through the nested `hookSpecificOutput.additionalContext` JSON form, because the top-level `additionalContext` key the hooks documentation shows is inert on this harness. It is a detector plus a directive rather than an auto-open, since the checkpoint belongs after the section's commit and an auto-open at the Chapter append would admit a compaction between the Chapter write and its commit, the mid-boundary landing the gate exists to prevent. It stands down for a subagent's tool call on the payload's agent keys, `agent_id` plus the four `agent_type` spellings the kit's sibling detectors defend, rather than on the session id, because a subagent's payload carries the parent session's own id and the leash-holder check alone would pass one; it stands down under `KIT_EXTERNAL_ENGINE=1`; and every guard and every internal error exits 0 silently, so a missed nudge degrades to the pre-hook status quo rather than to a broken edit loop. `compact-deferral-nudge.js` closes the other half of that loop, the half no edit announces: the gate's deny lands at a turn boundary where PreCompact stderr reaches the operator and never the model, so a run can be held for hours without knowing it. This hook rides the return of the tools whose results follow a wait (`Agent`, `TaskOutput`, `Bash`, `PowerShell`), which is the first thing the model reads after a deferral, and tells it the gate is holding offers, how many and for how many minutes, and which boundary step ends the hold. It carries those two integers and nothing else out of the gate's state, the same provenance bound the memory nudges hold. Eight guards stand it down, each exiting 0 silently: the payload must parse and name a covered tool, the external-engine marker must be absent, no truthy agent-identity key may be present (truthiness rather than key presence, deliberately and unlike its sibling: a harness version emitting a null or empty `agent_id` on a main-session payload would otherwise stand this hook down on every call and kill the feature outright), the cwd must be a usable non-network path, a goal must be armed and its leash held by this session, the gate state must show a deferral episode open for that holder rather than for any bystander's hold, no matching checkpoint may already be open (an open one means the boundary is declared and the next turn lands it), and the episode's own nudge stamp must be absent or older than thirty minutes. The interval stamp is a compare-and-set against a re-read of the state, failing closed to no stamp, because a stamp landing across a valve or an illegible allow would restore an episode that allow had just cleared and hand a stale checkpoint the long freshness bound instead of the short one. Its honest rate is once per interval per tool batch rather than once per interval: parallel tool returns all read the stamp before any of them writes it.
- **PreCompact** runs `kit-compact-gate.js` on the `auto` matcher alone, the scheduler that lands native auto-compaction at the boundaries a plan run declares instead of wherever context happens to fill. A boundary is ordinarily a section's close, and where a run goes long enough with work in flight and no section closing, it is an interim board entry written to the plan doc and put through the run's commit model, so a drought between closes still leaves the gate somewhere safe to land. `executing-work` owns both moments and the drought's trigger, and opens the checkpoint the gate reads. Nothing can raise a compaction on demand, so the gate works the only lever there is: it vetoes one. A denied auto attempt is re-offered once per assistant turn, indefinitely, which is what turns a veto into a schedule. It reaches a three-state verdict, evaluated cheapest first. Two preconditions come first and allow outright when either fails: the trigger must be `auto`, and `KIT_EXTERNAL_ENGINE=1` must be absent (an engine's workers are fresh per section and have no mid-chapter context to protect). Past those, an armed kit goal whose leash this session holds takes the **boundary-gated** path, denying while no boundary checkpoint is open, consumption read from the transcript is legibly below a safety ceiling, and no live operator-consent marker names the bound session. An armed goal no session has yet claimed is decided by the same claim proofs the leash uses, two predicates that this gate and `kit-goal-stop.js` both call: a transcript showing the user typing the arming command (one predicate in `kit-compact-lib.js`) claims the binding, and so does a session whose own id equals the arming session id the state records (one predicate in `kit-goal-lib.js`, reading no transcript at all, which is the route by which a run that armed a plan for itself reaches its own leash). Either claim takes the boundary-gated path; a session meeting neither is a bystander on the interactive path. An in-session arm binds at arm time and reaches the gate already bound, so what this claim point serves is the narrower population the arm CLI could not bind: an arm whose session id was absent or matched no transcript on this machine, and an arm run outside any session. For that population, claiming here rather than only at a stop is what makes the gate reachable on a well-behaved run, since the completion contract forbids stopping while unblocked work remains, so a run that never stops would otherwise stay unbound and ungated for its whole length. The claim's write is best-effort and the verdict does not wait on it, matching the leash's own posture that enforcement never depends on the write: a `.kit/` that refuses the write leaves the run deferring to the safety ceiling, which is where a refused checkpoint write leaves it anyway. A checkpoint opened while the goal was still unbound records no bound session, and each claim point adopts such a record for the session it binds at the moment it binds it, carrying the original opening timestamp and pending flag over verbatim so an adoption grants no freshness and an expired record stays expired. A record already naming a session is never rewritten, so a checkpoint belonging to a genuinely different session still reads as absent. An armed goal beside a payload carrying no usable session id still allows outright rather than taking either denying path, since no binding could be written from it and no comparison made with it. Every other session, meaning no goal is armed for the project or an armed one belongs to a different session, takes the **interactive** path, which asks the transcript a different question: whether a native automation instrument is driving this session. When `/goal` or `/loop` is in effect the gate allows, because an automated run is better served compacting early at the native trigger than deferring; otherwise it denies to the same safety ceiling, so a hands-on session keeps its full context through the long middle of a working stretch instead of being compacted at the early trigger the armed path needs. That deny, and the boundary-gated one above, are what the two release markers lift, and each is read only after every allow already described has declined, so a session holding no marker takes exactly the path it always did. A live role-boundary marker naming the compacting session releases the interactive deny alone: it is a goalless seat's own declaration that its context holds nothing the disk does not, which is what a leashed worker's checkpoint already says on the other path. A live operator-consent marker naming the session releases either deny, being the operator's word rather than the session's judgment. Either one allows, retires itself, and journals its own reason, so a marker ordinarily lands exactly one compaction, the retirement being best-effort like the checkpoint's and a failed delete costing one extra release inside the marker's own age bound rather than a wedged run; both markers age out in 4 hours, each derived from the deferral episode's own idle bound rather than restated beside it, so the three quantities bounding a session's quiet gap retune together. Neither reaches a clause that denies for an integrity reason, so consent converts a not-yet into a now and never a never into a yes. Every other state, every read error, every ambiguity allows, so a forgotten checkpoint or a misread transcript degrades to compaction landing at the native trigger, the behavior before the gate existed, and never to a wedged run.

Automation detection reads the transcript for shapes the harness writes but does not document, which is why every misread is built to land on allow. Native `/goal` is read from two surfaces: the `goal_status` attachment the goal system writes at arming and at each stop evaluation, whose `met` field distinguishes a running goal from one that completed and auto-cleared, and the user-typed command markup, whose `clear` argument retires it. `/loop` is read from its own user-typed command markup, retired by the terminating `ScheduleWakeup` whose input carries `stop: true`. Both are ordered signals and the newest match decides, so a finished goal or a stopped loop returns the session to the interactive deferral rather than leaving it classified as automated forever. The reader takes a capped head-plus-tail slice of the transcript, because `/loop` evidence sits at the head where the command was typed while goal status lands in the tail, and it excludes tool results, meta entries, compaction summaries, and sidechain rows, since the literal command markup travels freely inside quoted file content and agent output. That exclusion is load-bearing rather than defensive: this repo's own plan docs and hook sources quote the markup, so reading them plants it in the reading session's transcript. Manual `/compact` is never gated, and it is excluded in code as well as by the `hooks.json` matcher, the in-code clause allowing a non-auto trigger outright rather than refusing it, though only the matcher is ever reached: the matcher is auto-only, so the gate process never starts for a manual compaction and the in-code clause is defence against a later wiring edit rather than a live path. That has one consequence for the release markers below. A manual compaction is not a landing the gate sees, so it spends no marker; a marker live at that moment survives the compaction and is retired by its own age bound or by the session's next gated landing. The boundary signal is `.kit/compact-checkpoint.json`, written by `kit-compact-checkpoint.js` at either executing-work boundary, a section's close or an interim board entry, and recording both the armed plan and the session bound to it, which is null where the goal is not yet bound; rewritten by `kit-goal-stop.js` when a queue advance moves the current plan out from under an open one; and given an owner by either claim point, in `kit-goal-stop.js` and `kit-compact-gate.js` alike, where the record it finds carries none; the gate consumes it when it allows, so one checkpoint lands exactly one compaction, and a checkpoint naming another plan or another session reads as absent so a crash-orphaned file cannot open the gate. The valve is the failure mode nothing else caps: sustained denial with a chapter that never closes would climb to the model's hard limit, where a session dies outright on an over-length prompt, so at or above the ceiling the gate allows regardless. One ceiling serves both denying paths, an absolute token count sized for the roughly 1,000,000-token window the models running these sessions carry, because the PreCompact payload provides no `model` field to derive the real one. That assumption is the one direction of this design that is not fail-open: on a model whose window fell between the trigger and the ceiling, the valve would never fire. It is bounded by what the gate can actually do, which is veto an offer the harness has already made, so a model whose window is too small to reach the trigger is never offered a compaction to defer. The consumption it compares against is read from the newest assistant `usage` block, taking the largest entry of that block's `iterations` array when one is present, because a multi-iteration turn's top-level cache figures are summed across iterations and describe no single request. Largest rather than last, because the two errors are not symmetric: understating consumption defers longer and walks a session toward the hard limit the valve exists to keep it away from, while overstating it only ends a deferral early. Nothing detects that state, and the doctor's auto-compaction-window check is not it. That check reads the configured window, which says nothing about the running model's real one; what it catches is the opposite and safer failure, a window configured so high that the trigger lands at or above the ceiling, where the valve allows everything and the gate defers nothing. `docs/security-model.md` carries the assumption and what does and does not cover it.

The boundary signal carries its own staleness bound, because a checkpoint that outlives its boundary is how this feature would quietly become a no-op. A boundary is often reached below the trigger, where there is no pending offer to catch, so without a bound that checkpoint would sit open and admit the next offer, which arrives mid-chapter. The gate therefore treats a stale checkpoint as absent, and it measures staleness two ways rather than one, because the two kinds of boundary are not alike. A checkpoint opened below the trigger has no offer waiting for it and takes a short window of ten minutes, which is what retires the leftover. A checkpoint opened while the gate is already holding offers takes a far longer one, because what delays its consumption is a tool call that has not returned yet, and a dispatched implementer or a whole-repo suite routinely runs past ten minutes. Which leg applies is not the caller's claim about itself: the CLI records a `pendingOffer` flag at the open, and the gate honors the long leg only when it can corroborate that flag against its own recorded state, requiring an episode still open, owned by this binding, and dated before the checkpoint it vouches for. A flag with no corroboration falls back to the short leg, which is the fail-safe direction. The predate condition is what stops the flag from minting its own licence, since without it the very denial that refuses a stale checkpoint would open the episode that corroborates the same checkpoint one turn later. The long leg's outer bound is 24 hours, a sanity cap on a hand-made or clock-skewed record rather than an operating figure; the operating bound is the episode's own life, which ends four hours after its newest denial, because a denial is recorded only at an assistant turn and a long call has none. The asymmetry that makes the short leg work is unchanged: past the trigger the harness re-offers every turn, so a checkpoint opened at a real boundary with the turn free is used within seconds, while one opened below the trigger simply ages out. The executing-work ritual also clears the checkpoint when the next section starts, so the two guards are independent. That clear runs only at a section start, so the expiry is the sole bound on a checkpoint opened at an interim board entry, where by definition no section is closing and none is about to start. The kit summarizes nothing itself: the native summarizer runs unmodified and re-grounding afterward is the existing `session-start.js` `compact` path.

The gate also records what it decides, which is what makes any of the above measurable rather than reconstructed from scrollback. Every verdict on every path writes two files under the project's `.kit/`: `compact-gate.json`, the current state, and `compact-gate.jsonl`, an append-only journal. One resolver in `kit-compact-lib.js` decides where that `.kit/` actually is, and it serves every writer of these files and the gate's own reader alike, which is what keeps a marker's writer and its reader agreeing on where it lives. Ordinarily it is the project directory's own `.kit/`. The exception is a project directory lying inside the memory store, which is the coordinator seat's normal state once its board lives there: dropping `.kit/` into that tree would replicate one machine's gate state to every other, so the resolver sends it to an unsynced per-machine location outside the store instead, `~/.kit/store/<store-relative-path>/`, keyed that way so two store-resident projects stay separate. The path is named here rather than left to the resolver's source because nothing else owns it: no doctor check knows about it and nothing prunes it, so a store-resident project's gate journal accretes there to its own 2 MB trim and an operator looking for it has only this line to go on. The alternative reading, a `.kit/` under the store root that the store's own exclusion would keep unsynced, was declined because it puts the file back inside the replicated tree and relies on ignore machinery to keep it out, which is the arrangement that has already failed once here. The journal carries two record classes, partitioned so a reader folding it never has to guess: a decision record carries `verdict`, and a nudge record carries `event`. A decision record holds the time, the verdict (`allow`, `deny-boundary`, `deny-interactive`), the clause that decided it, which on an allow a release marker lifted is `role-boundary` or `operator-consent` so a run's compaction history states which release landed it, the consumption figure read, the checkpoint's age and flags where one was present, and the payload's session id; a nudge record holds the time, the session, and which tool's return carried the reminder, that last field being how a run whose nudges were all consumed by dispatched agents is readable after the fact. The state additionally holds the open deferral episode, which is the aggregate the corroboration leg and the deferral nudge both read: how many offers have been denied, since when, and when the run was last nudged about it. Both writes happen after the verdict is emitted and the exit code set, under one try that covers the state write, the trim and the append together, so a recording failure cannot change what the gate decided but can cost the journal line whose state write already landed. That is the undercount direction, and it is the one chosen: the state is authoritative and the journal is allowed to lag it. A decision carrying no cwd is not recorded at all, and the recorder refuses rather than creating `.kit/`, so a project that has never armed a goal accumulates nothing. The log is bounded, rewritten to its newest 1 MB once it passes 2 MB. The episode also reaches the operator directly: the gate's stderr note at a boundary deny carries "held N offers over M minutes" from the same aggregate, both integers clamped by one shared rule so neither can print a figure the state could not hold, and its diagnosis clause names the case of a checkpoint whose pending-offer flag no episode vouches for.

The episode belongs to the leash rather than to a session, which is the non-obvious part. Only the bound session can produce a `deny-boundary`, so a boundary deny extends the episode it owns and otherwise takes the slot, a foreign incumbent on that path being a dead binding rather than a rival; an interactive deny records its decision and leaves any standing episode alone; and an allow clears the episode only when the allower owns it, since a bystander's compaction lands in its own context while the bound session's offers stay pending. The release markers are swept on a different rule, and it is the one allow-time action scoped by session rather than by ownership: every allow, whatever clause reached it, retires any marker naming the landing session, while a marker naming another session is not that landing's to spend and a deny retires nothing because nothing landed. The sweep needs the payload's cwd as well as a string session id, so an allow carrying no cwd reads the markers on the legs above and retires none, the same undercount direction the decision recorder beside it takes. That sweep closes a window the markers would otherwise open. A marker that missed its moment, left live through a valve, checkpoint or illegible landing, would stay honorable for the rest of its age bound, and if the same session crossed the trigger again mid-chapter inside that window the leftover would convert the deny into an allow at exactly the placement the gate exists to prevent. A manual `/compact` leaves that same leftover and the sweep cannot reach it, the gate never running for one, so an age bound is the only retirement there. Every failure direction under that model is an undercount, which degrades to the pre-recording status quo rather than to a checkpoint that outlives its hold. The read-modify-write is unlocked, so two gate processes in one project can both read a count and both write the successor: the state is authoritative and the log may disagree in either direction. It is a diagnostic surface, and nothing branches on it except the two consumers named above.

A denied auto attempt also leaves the operator a note on stderr, and that note is the operator's only diagnostic, since PreCompact stderr never reaches the model. It names both boundary kinds (a chapter close or an interim board entry), states the hold as running to that boundary or to the safety valve near the token limit, says that repeating for many turns inside one section is expected, and names the one state that is not expected: still firing after a Chapter has closed, which means the checkpoint was likely never opened. The remedy it prints is a runnable `node "<path>" status` and `node "<path>" open`, the path composed from the hook's own installed directory rather than written repo-relative, because the gate runs in every project on the machine and a repo-relative spelling resolves only inside the kit's own checkout. The `open` carries an at-a-true-boundary qualifier, since opening one mid-section is what executing-work forbids. A denied interactive attempt leaves a different note, and its remedy is the `boundary` verb rather than `open`, carrying the one precondition the verb itself cannot check: that the session banked its state at a natural boundary first. For a goalless seat that never loads the role skills, that note is the whole of what tells the operator the verb exists for that session, and the operator is the one who relays it, the note never reaching the seat itself.

Operating the gate is one CLI and one setting. `kit-compact-checkpoint.js` carries five subcommands, three for the leashed worker's own checkpoint and two for the release markers a goalless seat and the operator use: `open` writes a checkpoint for the armed plan and the session currently bound to it, and refuses when no goal is armed, since a checkpoint naming no plan could never match; `clear` removes one, which is what executing-work runs at the start of each section; and `status` reports whether a checkpoint is open and, where the gate would read it as absent, which clause failed, answering from the same match rule the gate itself decides by so the report cannot drift from the verdict, and it reports each release marker on the same terms, naming the session the marker is scoped to, the timestamp it was written at, and, where the marker is live or expired rather than consumed or malformed, the bound it ages out against. It reports the gate's own recorded state too: the last decision's verdict, the clause that reached it and its age, and either the open deferral episode's offer count and age or that no episode is open. That second half is what the Stop hook's boundary directive sends a session to read, so it is the operator-and-model-facing answer to "is the gate holding, and for how long". It is deliberately not scoped to a session, which is a reporting choice rather than a decision one: every code path that acts on an episode passes the owning session id, while `status` shows what is there, so a dead binding's episode can still stand in the report for up to the four-hour idle bound after a crash. `open` reports which freshness leg it opened, reading the gate's state to decide whether to record the `pendingOffer` flag, and refuses when no goal is armed. `boundary` opens a role-boundary marker for the calling session and takes no arguments at all, the marker being that session's own declaration and `boundary --session <id>` the natural misreading of the consent form, which a parser that ignored the tail would answer by denying the named session its release and handing the ambient session one it never asked for; `consent [--session <id>] [--project <path>]` records the operator's release for the caller's session or an explicitly named one, at the caller's own directory or at a named project. Both derive the caller's id from `CLAUDE_CODE_SESSION_ID` and refuse to write an unscoped marker where none is derivable, saying so rather than writing one. `boundary`, and `consent` without `--project`, write into the current directory's `.kit/` while the gate reads them at the compacting session's own project directory, so on those paths the working directory is load-bearing in a way no flag states: releasing a session that works another repo means running the command from that repo, and running it elsewhere writes a marker nobody reads and reports success. `consent --project` is what closes that silent miss for the operator's own case, resolving the marker against the named directory instead of the cwd, and it is corroborated rather than merely redirected: the command refuses loudly when the named session has no transcript under that project, so the failure that used to report success now reports the mismatch. That corroboration is also what bounds the widening, since the flag is the one place a caller's value reaches a marker's path. The setting is `autoCompactWindow` in the user's `settings.json`, and it is what gives the gate something to schedule, since the gate can only defer an offer and never raise one. The doctor reports the configured value, recommends one sized so the trigger leaves a band wide enough for a chapter to close before the valve fires, warns when a configured value leaves that band too thin, reports a configured value that differs from the recommendation so a machine already carrying one still learns of a new figure, and writes the value only behind an explicit `-Fix` consent prompt. Two write cases, and they take different consent. Supplying an absent value is what `-Fix -Yes` is for, since it converges: run it twice and the result is the same, and nothing the operator chose is lost. Replacing a value the operator did choose is withheld from `-Yes` and waits for an interactive answer, because an unattended run cannot tell a deliberate setting from a stale one, so it would revert the deliberate one, and would do so again after every retune of the recommendation it compares against. It reads the ceiling out of the hook source rather than restating it, and says so when it cannot, because a silent skip reads exactly like a healthy result.
- **Stop** runs `stop-docs-hygiene.js`, `kit-goal-stop.js`, and `seat-stop.js`, in that order. `seat-stop.js` serves the goalless seats: it resolves the stopping session's registry entry under the machine's coordinator directory and exits silently where there is none, so the whole cost for every unregistered session on the machine is one stat, and where there is one it stamps the entry's heartbeat under a ten-minute throttle and, when that entry's own status stamp shows the seat pushed status this turn and the working tree is clean, opens the role-boundary marker for it. That is what makes a seat's banked moment structural rather than a step its runbook asks it to remember, and the CLI's `boundary` verb survives as the manual path for a session no registry entry covers. `kit-goal-stop.js` is the deterministic leash that holds a `/kit-goal` run to completion. Its state is a file in the project (`.kit/goal-state.json`) that no session boundary deletes, resolved to the main checkout for a session working a linked worktree (see Worktree resolution below), and the hook enforces on session identity: native compaction preserves the session id, so an armed run keeps its leash across its own auto-compactions, while a session the hook cannot tie to the bound one is a bystander whose stop is allowed, and re-arming is the recovery. An arming may name several plans, in which case the state carries the ordered queue and a plan's terminal state advances the leash to the next plan rather than releasing the session; only the last plan releases. A `BLOCKED:` advance is keyed to the transcript entry that produced it, recorded in the state as `blockedAdvanceKey`, because the hook's read of the last assistant turn races the harness's append of it and a lead read twice would otherwise consume two queue positions off one blocker. The key rides with `blockedAdvancePlan`, the plan the advance moved to, and is retired by position rather than by deletion: it is honored while that plan is the current or the immediately previous queue position and ignored past that. Retiring rather than deleting is what stops an intervening advance, a plan behind the leash turning up Complete, from resurrecting a blocker the queue already consumed, while retiring at all keeps a stale key from widening the one collision surface the text-digest fallback has. A key with no recorded plan, which is what an older state file carries, is honored wherever it matches, since the failure direction there is holding rather than advancing. A lead whose key is already spent falls through to the ordinary hold: it never advances, never emits, and never releases. An advance also rewrites an open compaction checkpoint to the new plan, since the checkpoint is matched against the goal's current plan and a plan's own close-out opens one immediately before the stop that advances. The queue fields are strictly additive, with `plan` continuing to name the current plan and `boundSession` the leash holder, which is what lets the compaction gate read a queue-armed state with no knowledge of queues at all. One binding rides the whole sequence, and the SessionStart armed-goal notice reads that binding back rather than announcing the arming undifferentiated: the leash holder is told the leash is its own and where the queue stands, a bystander is told the leash belongs to another session and that the plan is not its business, with the re-arm path for a run that has died and a liveness hint taken from the bound session's recorded transcript mtime (a number and a unit reach the notice, never the path), and an arming no session has claimed keeps the claimable framing, naming both points a claim can land at, its first stop and its first auto-compaction offer, whichever lands first. A bound goal beside a payload carrying no session id is distinguishable from neither, so it degrades to the undifferentiated notice rather than risk telling the leash holder that its own plan belongs to somebody else. The doctor reads the same file for its armed-goal report, and reads it defensively rather than through the library's normalizer, because a hand edit is the case it exists to catch: it names the queue position and the remainder, discards a queue disagreeing with `plan` in favour of the single-plan reading, and splits the terminal-current-plan case into two warnings, since it means opposite things at the two queue positions. With plans remaining it is a stalled advance, normal mid-turn because the hook advances at the bound session's next stop, and otherwise a dead run to re-arm the remainder over; on the last plan it is the old stale goal, to clear. A separate exposure check runs alongside it, and deliberately outside the clone gate the report sits behind, because every armed session's start notice reads the state back and the gate's own journal records a session id and a work timeline beside it: it asks git whether the whole `.kit` directory under the directory the doctor was launched from is tracked, ignored, or neither, and warns on the first two of those with the command that fixes them. Both readings are taken over the directory rather than one standing in for the other, because a repository can ignore `.kit/` and still track a file inside it with `git add -f`, and the tracked reading runs first, since git stops reporting a path as ignored once it is tracked. A tracked result names every path it found, uncapped, and its remedy line names those paths rather than a hardcoded filename. Scoping it to the launch directory rather than to the kit's own checkout is what makes it reach a consuming project at all, since the kit's checkout already ignores `.kit/`. It detects the exposure without preventing it. Its three emit points also append to the goal event stream described below. Under `KIT_EXTERNAL_ENGINE=1`, `stop-docs-hygiene.js`'s blocking outcome becomes advisory text carrying no decision, so the stop is allowed: holding a headless worker at its turn end for a library-hygiene pass its directive does not cover trades a tidy `docs/` tree for a stuck run. `kit-goal-stop.js` does not read the marker, and does not need to: it binds to one session, bound at arm time when the arming CLI can corroborate its own session id against a transcript on disk, and otherwise claimed by one of two things: the user's own arming text (a plan path typed as a slash-command argument, or a message leading with the `/kit-goal` token whose argument block names the plan), or a session whose own id equals the arming session id the arm recorded, which is what reaches a run that armed a plan for itself and so typed nothing. A worker whose directive merely names the plan meets neither and is a bystander it never leashes. It has five block reasons, and only two of them carry the boundary ritual as well as the hold. The ordinary hold and the capacity-shaped refusal share one directive, spelled once in the file and interpolated twice, which names two conditions rather than one: a Chapter closed since the last boundary, or the compaction gate holding auto-compaction offers since then. The second condition exists because a run whose review rounds keep adjudicating without any section closing produces no Chapter for hours, so a Chapter-only test is silent for exactly the run the gate has been holding longest; the interim board entry is that run's boundary, and the directive names it. The second condition is additionally gated on the turn being at a clean point, since a deferral met mid-step is not a boundary and acting on one would land the compaction at the very place the gate exists to avoid. Both then tell the session to load executing-work if it is not loaded and complete that skill's boundary steps in its own order, running the memory sweep, appending the Chapter or the interim entry, honoring the section's commit model, and only then opening the checkpoint, naming the gate's two bounds (a matching checkpoint, or the safety valve near the context limit) rather than an unbounded hold. The other three reasons each decline the directive for their own reason, and the reasons are not interchangeable. The queue advance asks something narrower and specific to itself, whether the plan that just finished opened a checkpoint at its own close; note that it cannot assume a Chapter closed, because an advance on a leading `BLOCKED:` appends none, and such a run reaches its next boundary through the ordinary hold on the plan it moves to. The unusable-plan hold declines it because the plan doc cannot be read at all there, so instructing an append to it would name a step the session cannot perform. And the reason for a stop already spent carries none of it, because it fires only where the last assistant turn is an already-consumed transcript entry, so no Chapter can have closed since. This is the model-facing half of what the compaction gate's stderr note cannot say, that note reaching the operator alone.

`memq-grant.js` runs the other way and is the kit's only hook that allows rather than denies. Under the external engine's write-gated spawn vector the Bash tool refuses `node <script>` outright, which would cost a fleet worker the memq CLI, so `memq-grant.js` emits an allow decision for exactly one command shape: one `node` invocation whose first argument resolves by normalized path equality to this plugin's own `scripts/memq.js`, with the fleet-store signals present, a positively identified interpreter, no module-preload environment variable set, no shell metacharacter anywhere in the command line, a subcommand the hook's own list of granted verbs names, and none of the five withheld flag shapes among its words. On anything else it emits no decision and the call falls through to the host's normal permission flow, so its safe failure is silence rather than the guards' fail-open allow. `docs/security-model.md` carries the invariant in full, the accepted risks, and what the grant does and does not contain; `docs/fleet-integration.md` carries the engine-side preconditions it depends on.

### The canary

`hook-canary.js` is the one hook whose subject is the other hooks. Every kit hook fails open, so a stale or damaged plugin cache, a hook file that no longer parses, or a guard gone inert takes the enforcement away with no signal at all. The canary probes the cache a session actually executes (`CLAUDE_PLUGIN_ROOT`) and speaks only when something about it is positively broken.

Three probe classes run over that cache. **Load checks** cover every hook named in `hooks.json`: each named file is present and `node --check` parses it. **Known-answer behavior probes** run in both directions, so a guard that answers everything the same way cannot read as healthy: a governed subagent writing a `docs/` path must deny while a main session writing the same path must allow, a read-only subagent's `git commit` must deny while its `git diff` must allow, and a throwaway fixture holding an armed goal must draw a block from `kit-goal-stop.js` while a directory with no goal armed draws nothing. `memory-frontmatter-guard.js` takes both directions too, and the allow half is not optional there: the guard matches every `Write`, `Edit`, and `MultiEdit`, so one stuck at deny would block every file write in every session and only an allow probe catches that. Its two payloads name a project-tier path under a per-run random store root the probe environment points `KIT_MEMORY_ROOT` at, one carrying a dangling `supersedes:` that must deny and one carrying a sound block that must allow. `memq-grant.js` takes six probes on Windows and five elsewhere, one allowing and the rest withholding. The allowing one is the single invocation the grant covers, which must produce an allow decision. The withholding ones each aim at a screen the allow probe cannot see the loss of: a metacharacter-carrying near-miss, a `--body-file` value, a `--rollup`, `find` in the verb position, and, on Windows only, the Git-Bash `/d/` spelling of the script path, that rewrite being what the refusal there is about. Both directions run for the same reason as the guards and one more: a deny guard gone inert eventually shows up as something unexpectedly permitted, while a grant gone inert never announces itself, because a fleet worker simply loses memq. The withheld shapes divide by what stands behind them: `--body-file`, a body-carrying `--update`, `--supersedes`, and both delete verbs are refused by the CLI as well, so a hook that lost one of those screens is one lock short, and `--drop-malformed`'s second lock is the CLI's own coupling of that flag to the `--rollup` this hook also withholds, while `find`, `--rollup`, and the `anchor` and `triggers` verbs are withheld at the grant alone and a hook that lost any of the four is open with nothing else to say so. The probes cover that division incompletely: `find` and `--rollup` each carry one, the second-locked shapes ride `--body-file`'s, and `anchor` and `triggers` carry none, so the two unlocked shapes with no probe of their own are the ones a hook regression would take away silently. `test/memq-grant.test.js` pins the withholding in the deny direction instead, which is a repo-suite check rather than a session-start one. Its probe environment is constructed rather than inherited, with PATH pinned to the canary's own interpreter directory and every other variable dropped unless a short keep list names it, so ambient machine state cannot fail it. Building it from that list rather than subtracting known-bad names from the inherited environment is what lets the canary need no knowledge of what any hook refuses on. `merged-pr-push-guard.js` and `pr-docs-guard.js` get a load check plus a benign-payload plumbing probe only, because their deny paths need external state (a MERGED pull request, a dirty checkout off the default branch); the repo suite owns their behavior. The goal probe runs against a temp directory with the event sink and the re-read delays pinned away from real machine state. Those two classes are a few dozen serial spawns on the current wiring, one load check per hook `hooks.json` names plus one per behavior probe. The bound is per child at 5 seconds rather than per phase, so a healthy cache costs under a second in total while a cache where every grant probe hangs costs about 35 seconds of it; `docs/backlog.md` carries the whole-phase budget that would cap the failure case. **The integrity check** spawns nothing: it only reads and hashes files, so it is free against that budget.

Integrity is the class that sees a hook whose bytes changed after packaging, which parsing and behavior probes cannot: the plugin cache is writable by the principal a session runs as, and a guard edited in place enforces whatever it now says. The check re-hashes every file the build's `hooks` map names, from the executing cache, and reports a mismatch as bytes that are not the ones the build packaged, pointing at a reinstall or update. A manifest entry with no file on disk reports as missing from the build; any other read error (a lock, a scanner holding the file open) stays silent, because it says nothing about the file's contents. The check runs last and skips a file another probe already flagged, so a wholesale-different cache cannot fill the report's line cap ahead of a guard that is present, parses, and is positively answering wrong. An absent stamp, an unparseable one, or one with no `hooks` key is silent: an older build gives the check no basis, and a cache it cannot describe is never called tampered.

Its coverage is wider than the load check's in one direction and bounded in another. The build hashes the whole packaged `hooks/` directory while the load check enumerates `hooks.json`, so `kit-goal-lib.js` (required by `kit-goal-stop.js`, named by no command string) and `kit-goal.js` are covered here and nowhere else; `hooks.json` itself is in the map, because rewiring a guard out of the wiring disarms it exactly as editing the guard does; and `scripts/`, `doctor/`, and `output-styles/` ship in the same cache outside the manifest. The manifest also lives inside the cache it attests, so deleting the stamp silences the check and rewriting stamp and payload together defeats it. `docs/security-model.md` carries what that detection buys against the threat it is sized for.

A failure writes one warning into the session context naming each failed probe with its expected and actual answer, capped at 10 lines plus a count of the remainder, and points at `/kit-doctor` and a reinstall. Which repair to run is legible from the line: a load-check or wiring failure means a partial or damaged install, where reinstalling and restarting the session is the fix, while an integrity line means the installed file is not the one that was packaged, where updating or reinstalling the kit is what restores the packaged bytes and every guard verdict that session already took is suspect until it does. The canary always exits 0 and never blocks anything. The loud/silent boundary is deliberate: anything positively observed about the cache being broken is loud, including a missing hook file, a missing or unparseable `hooks.json`, a probed hook the wiring no longer names, and a plugin root that is not there, while an unexpected error inside the canary's own code stays silent through its fail-open catch, since a canary bug that warned at every session start would cost more than the blind spot it covers. What the canary measures is a cache's internal consistency, not its freshness against the repo: a stale but coherent cache reads healthy, and `kit-version-nudge.js` is what watches for drift. The doctor's "Hook canary" check confirms the file is present and wired into the `SessionStart` array.

One consequence lands on whoever edits a hook: `test/hook-canary.test.js` runs the canary against the repo's own `plugins/claude-kit/` directory, so a hook changed without a rebuild leaves the gitignored stamp beside it stale and the health assertions go red. That red is self-diagnosing, naming the stale stamp and telling you to run `.\build.ps1`, and the coupling is deliberate: it is also what catches a hook edited after the last build before a package ships.

### Backlog surfacing

`docs/backlog.md` is a pull surface in a push workflow, so the kit pushes it. `summarizeBacklog` in `session-start.js` reads the file under the payload cwd, scopes to its `## Active` section, and emits one block carrying three figures: the active item count, the oldest dated item's ISO date with its age in whole days, and a tally of items carrying no date. Where the read did not reach the whole `## Active` section the block states that bound instead of presenting the figures as totals. Two properties separate it from the kaizen counter beside it. It carries no kit-repo marker gate, so it fires in any project holding a `docs/backlog.md`, and `KIT_EXTERNAL_ENGINE` does not suppress it, because the block carries no engine gate of its own. Engine sensitivity is per block rather than a property of this hook: the plan block drops its drive-to-completion instruction under the marker, the unleashed notice is suppressed whole, the plugin-view line changes its remedy, and the post-compaction re-load block names the engine's own directive as the governing skill rather than executing-work, so that a worker is not handed the drive-to-completion loop by the side door after the plan block withheld it. This one is untouched.

Numbers and one regex-extracted ISO date are the only interpolations, and item text never reaches the block, so a hostile backlog line cannot inject instructions into session context. The parse is deliberately coarse. The read goes through `hooks/kit-read-lib.js`, the shared bounded reader, at a 1 MB ceiling, so a file past it comes back as whole lines with the summary marked bounded, and a UTF-8 BOM is tolerated; items are top-level `- ` bullets, with a bullet whose content is entirely parenthesized (the shape the `curating-docs` backlog template ships) and a bare empty bullet counted as structure rather than items; and the aging anchor is the first `\b\d{4}-\d{2}-\d{2}\b` token anywhere on the line, because the kit's convention puts the parked date in the title's parentheses beside other context. A cross-component pin in `test/session-start-backlog.test.js` seeds its fixture from the template's own backlog block, so the placeholder shape and the parser cannot drift apart silently.

Every failure is silent and additive. An absent file, one that is not a regular file, an unreadable one, and a file read whole that carries no `## Active` heading or no items emit no block at all, and the check runs inside its own try so it can never affect plan recovery. Silence is reserved for what the hook established: a bounded read that reached no heading or no item emits a sentence saying the file went partly unread, because nothing being there and the part that was read holding nothing are different answers and only the first is silence. One known degradation rides with the coarseness: an ISO-shaped impossible date such as `2026-02-30` either rolls to a neighboring real date or joins the undated tally, depending on the runtime's `Date.parse`, which is acceptable in a coarse age nudge. A bounded read is not one of them, because the block says so rather than reading as a total. Any read that did not reach the end of the file carries a clause stating that every figure in the summary is of what was read. The flag is set by the read alone and is not narrowed by a heading closing the `## Active` section, because the heading scan is a column-anchored `##` match that a fenced code block inside an item satisfies, which would certify a truncated read as a total. The cost of the conservative direction is that a backlog over the ceiling whose Active section genuinely ended early reads as bounded when it was complete, which understates confidence rather than overstating it.

The behavioral half lives in three skills and one template, and the hook is the primary enforcement because it fires whether or not any skill loads. The `curating-docs` backlog template states the dated item shape (`- **<item> (YYYY-MM-DD).** <body>`); that skill's prune pass doubles as the aging check, naming every item older than 90 days for a promote, retire, or keep call, where a keep writes the fresh adjudication date ahead of the original (`(2026-11-07, parked 2026-05-01)`) and an undated item is past the threshold by definition and gets a backfilled date in the same pass. That check also has a standalone trigger, offered in one line when the session-start block reports an oldest item past the threshold and no close-out is near. `finishing-work` step 5 carries each named aging item, by name and date, into the close-out status with its question, which is how an aging item reaches an operator reading close-outs on a phone. `brainstorming` step 1 reads the backlog straight after `memq recall`, so a new effort finds an already-parked solution before designing a fresh one. The two knobs are the 90-day threshold, stated in the hook's block text and in `curating-docs`, and `NUDGE_FILE_READ_CEILING_BYTES` in `session-start.js`, the 1 MB per-file ceiling `summarizeBacklog` and the kaizen note walk share.

## Memory store

`plugins/claude-kit/scripts/memq.js` is a zero-dependency CommonJS CLI over the file-backed memory store under `~/.claude`. It resolves a project's store from the cwd by reproducing the harness's own directory-name rule, so it lands on the same directory Claude Code writes. That derivation is the default and not the only one: under the engine's gated store a pin (`KIT_MEMORY_PROJECT`) replaces the derived segment with a fixed one, so one instance keeps one tier across workers whose working directories differ. Everything hanging off that directory follows, index and journal and sidecar and pending tier alike, which is the point; `docs/security-model.md` carries what the pin changes about who reads whose memories and why pinned content is fenced. It reads the file-per-fact memories of the project tier, a project-type tier shared by every project declaring that type, an operator tier at `~/.claude/memory-operator/` that every project on the machine reads and writes, each tier's `archive/` of retired memories, an outcomes journal (`outcomes.jsonl`) that exists per project only, and, inside a run the external engine spawned, that run's own `pending/<run-id>/` directory. The pending tier is present only under the three run signals and is scoped to the one run that owns it; `docs/security-model.md` carries what it is for and what its scoping does and does not guarantee. A used-tracking sidecar (`usage.jsonl`) sits beside each tier's memories carrying read and applied stamps; it is evidence about the records rather than a surface of its own. Retirement moves a memory into its tier's `archive/` rather than deleting it.

A fourth answer sits beside those resolutions, and it is a refusal rather than a store. An unpinned working directory whose spelling opens with two separators (`\\host\share` or `//server/share`) stands memq down at each of the twelve verbs that resolve the project memory directory from it: `log`, `find`, `get`, `recall`, `recent`, `unstamped`, `touch`, `anchor`, `triggers`, `decay-scan`, `decay-prune` and `decay-done`. The walk those verbs would otherwise take reaches `fs.statSync(<cwd>/.git)`, which under an unreachable host blocks for the SMB timeout rather than failing fast, so the refusal is what buys the verb the chance to say anything at all. The gate stands at each verb's own door rather than inside `projectSegment`, because the remaining four (`add-type`, `add-operator`, `delete-type`, `delete-operator`) reach the shared tiers alone and legitimately run from any working directory, and a gate in the shared resolver would refuse them for a reason that is not about them. Three properties of the gate are what a caller has to know. Every site reads `pinnedProjectSegment() === null && namesNetworkShare(cwd)`, so an honored pin answers ahead of the refusal and a pinned session never meets it. `touch` carries the one conditional site, `!toOperator`, because the operator tier resolves without a working directory at all. And `find` refuses whole rather than in part: its semantic channel resolves the project segment from the working directory itself, so standing the lexical block down alone would relocate the hang instead of avoiding it, and the refusal names both withheld channels so an unsearched one cannot read as an empty one. Every refusal is a sentence on stderr, and the status behind it splits: `log`, `touch`, `anchor`, `triggers`, `decay-prune` and `decay-done` exit 1, while the six reading verbs exit 0 with empty stdout, so a caller gating on status alone cannot tell a stood-down `recall` from a clean read of an empty store. What the predicate reads is the spelling and nothing else, so a drive letter mapped to an unreachable share is not a share to it and rides the same walk at the same cost; that residual belongs to the predicate rather than to any of the twelve doors, and a store pin is what avoids the walk where a mapped drive is the shape at hand.

Two frontmatter shapes sit in that store at once, and one field reader is what keeps them one store. On Claude Code a Write into a project's memory directory is rewritten in the same second into the harness's own shape: every key the author wrote at the top level is relocated into a column-0 `metadata:` map, keys of the harness's own join them there, and what stays at the top level is either an empty `name:` or the record's name with a `description:` beside it. Which of those variants a record gets, and which added keys ride along, varies by harness version and by which of the harness's memory features wrote it, so `frontmatterValue` promotes on the map's shape alone and tests no marker key, which is what makes the rule hold across the variants rather than across the one a probe happened to produce. It reads each of `tags:`, `created:`, `pinned:`, `machine:`, `supersedes:`, `anchors:` and `triggers:` at the top level first and inside that map second, the top-level value winning where both placements carry the field, since a top-level line on an already-rewritten file can only have been written after the rewrite and is the newer intent. A promoted value gives up one matching surrounding pair of quotes, the harness's serializer quoting the scalars that bare YAML would read as ambiguous, while a top-level value is taken verbatim because nothing rewrote it. Under any other key nothing relocates a field, so one found there is reported as misplaced rather than read, which is the answer `pinState` cannot afford to lose. Everything memq writes itself goes through Node's fs and is never rewritten, so both shared tiers and a decay pass's archive rename keep the top-level shape, and a fleet store pinned outside the harness's own directory keeps it entirely. The 40-line bound on the block is spent by both writers: the opening fence takes the first line, the harness spends four to seven of the remaining 39 with seven the common case, so a hand-written block budgets for 32 lines, and an overrun is total rather than partial, a closing fence past the bound leaving no field inside the block readable at all.

What the readers say about that overrun is a distinct answer rather than silence, and that is the store's rule for every could-not-read: no reader answers a defeated check with the value it gives a clean one. `frontmatterSite` and `frontmatterValue` carry an unclosed sentinel beside the unreadable and misplaced ones, so `pinState` answers `unclosed` and the prune exempts such a record exactly as it exempts an unreadable one, and the anchors reader answers not-checked. Two readers keep answering absent, and the ruling is stated rather than inherited: `readFrontmatterTags` and the `supersedes:` read cost a search match rather than a memory when they miss, which is the trade their own comments already make. The write door refuses the shape outright, per the frontmatter guard below. The record reaches those readers through two kinds of door, and the difference is worth knowing. `readFrontmatterAnchors` and `listMemories` take a capped head of 65536 bytes; `frontmatterField` reads the whole file, and `readFrontmatterTags`, `readFrontmatterCreated`, `pinState`, the `machine:` read, the `--supersedes` write-time screen, and the repair reader all go through it. A block that closes before the head's last line is the block every one of them sees, capped and uncapped alike, so an ordinary record is one record to the whole store. The two shapes the doors can disagree about are a block that does not close inside the head and a block whose closing fence is the head's own last line, which only a cut record can produce, and the write door declines to judge either rather than siding with one reader against the other. That is why the guard measures its own bound in bytes at the same 65536: a character bound would admit a record the store reads differently.

Inside a run the pending tier changes writes as well as reads. Every new memory file the run produces lands in `pending/<run-id>/` rather than the project tier, carrying provenance frontmatter memq stamps on anything it writes: `run:` from `KIT_RUN_ID`, `vector:` and `section:` from `KIT_SPAWN_VECTOR` and `KIT_RUN_SECTION` when those are present, and a `written:` date. Because a session's memory files are written by its Write tool rather than by memq, `memory-session.js` emits the same instruction into the session at start: the pending directory named verbatim on its own line, the frontmatter fields the file must carry, and the standing rule that `MEMORY.md` is not the run's to touch, since a pending memory carries no index line and the index entry is written at promotion by the engine. A session carrying the store signals with a run id the kit cannot honor is stood down from writing memory at all rather than left to write into the shared record. `memq log` keeps appending to the project-tier journal and gains a `run` field rather than rerouting, and `get` resolves the pending tier ahead of the project tier, following the file's own closest-tier-shadows rule. With `KIT_RUN_ID` unset there is no pending tier and every command behaves as it does outside a run.

`memory-session.js` is the store's session-start voice, and it runs eight blocks: the overdue-decay nudge, the type-tier index for a project declaring a `Project-Type`, the sync trigger, the embedder-absence nudge, the run-scoped pending destination, the pinned destination, the project-tier block that names what the project's memory index already holds and where a new memory file goes, and the anchor-drift line described under Anchors below. It is wired on `startup|resume|compact`, so a session resumed from a compaction runs the drift check rather than reading as a clean store.

One condition replaces every cwd-derived block with a single stand-down: no store pin is in effect and the working directory names a network share (the `\\host\share` and `//server/share` forms). Each of those blocks resolves the project memory directory from that working directory, whose first filesystem touch is a synchronous `statSync` on `<cwd>/.git`, and a synchronous call under an unreachable share hangs for the SMB timeout rather than failing fast. This hook carries no timeout entry in `hooks.json` and a hook that runs long loses its whole stdout, so the cost of the hang is every block, not one line. The sync trigger and the embedder nudge still run there, because neither touches the working directory. The predicate itself lives in `hooks/kit-network-lib.js`, a module holding `namesNetworkShare` and nothing else, and it reaches six consumers by two routes: `chapter-boundary-nudge.js` and `compact-deferral-nudge.js` require the module directly, while `memory-session.js`, `memory-frontmatter-guard.js` and `memory-recognition-nudge.js` reach it through memq's re-export because they already hold memq, and memq itself both requires the module and calls the predicate at twelve verb entry points. Counted at the module that is three importers, counted at the predicate it is six consumers, and the two counts are worth keeping apart: a reader taking the two hooks' direct requires for the whole would conclude the guard is ungated. The sync trigger both acts and speaks: on Windows, for the kit's own owned default store, it spawns the detached background runner that commits and syncs, and it emits a line only in the three states worth nagging about, a recorded standing-down gate, a week-old failure streak, or a broken sync chain (a spawn that recorded no outcome past a stale window), staying silent while a healthy sync does its work. The two blocks that speak to the machine's own state, sync and embedder, carry no store-derived text at all: integers the hook parsed and words that are literals in its source (a state-file reason code is a lookup key with a fixed fallback, never emitted text), which is stricter than sanitizing and is why neither needs a fence. Both stay silent under a stand-down and in a run-scoped session, whose own block already claims what the hook says about where the store stands. The decay nudge and the type index are independent of the rest; the three destination blocks are mutually exclusive, since a session must be handed one destination and never two, so a run suppresses the pin block and silences the project block, and a pin reduces the project block to its index lines alone, to a short notice when the index exists and cannot be read, or to nothing at all when the index is absent or empty. What the project block does not depend on is any harness setting: the kit states its own index and its own write destination rather than assuming Claude Code's auto-memory has supplied either, so the store behaves the same whatever that setting is. The cost is that a session with auto-memory on sees the same index twice, once verbatim from the harness and once reduced and capped by the hook; the alternative was mirroring a private harness resolver that changes without notice, which the kit deliberately does not do. A stand-down state replaces every one of them when the environment names a store the kit cannot resolve.

An ordinary session, with no run and no pin, gets the whole project block, and its two halves fail differently. The index half states one of three facts: the index lines themselves, reduced to bounded printable ASCII and capped at 60 lines against the type tier's 30 with the remainder counted; that the project has no index yet; or that the index could not be read and the tier is therefore to be treated as populated rather than empty, since "nothing is recorded" would invite a session to write a second copy of a fact already there. The destination half names the memory directory verbatim or not at all. A path that cannot be carried faithfully, longer than 260 characters or holding anything outside printable ASCII with the double quote barred, withholds the directory and the write convention with it, keeps the index lines, and points the session at `memq`, whose commands resolve the directory themselves. That is the one destination block that does not stand a session down over an unemittable path, because an ordinary session has asked for nothing the kit cannot do. Both index emissions run through one shared helper, so the read cap, the per-line reduction, the counted remainder, and the indent cannot drift between the two tiers.

Two properties shape the code more than anything else. The store is a **data-to-model boundary**: a SessionStart hook emits store content into a session's context before the user types, so a value entering a store file is bounded at the write rather than at display, in length always and in charset for the prose fields (summaries, descriptions), while a memory body is length-capped only; and the store root is settable only behind two signals rather than one, because that variable selects which data reaches the model. And its writers are **lock-free appenders around locked rewrite paths**: of memq's own writers, `log`, `touch`, `get`, and the read-stamp hook append without a lock, while `anchor`, which rewrites one project-tier record's `anchors:` line under that directory's decay and store locks in that order, `triggers`, which rewrites the same records' `triggers:` line under the same two locks in the same order, `decay-prune`, the shared-tier authoring commands (`add-type` and `add-operator`, their `--update` repair included, which rewrites the index description on every call and the record body as well when a body flag and `--confirm-shared` ride with it, the description positional being required on every form of the verb), and the shared-tier delete verbs (`delete-type` and `delete-operator`) rewrite under a per-tier lock, each leaving a backup beside every file it rewrites. A first-creation write and a memory-file move leave no backup, having no prior bytes to keep, and a delete is the one locked path that ends with less than it started: it removes the record's own copies first, that record's backup included, then both index lines, then the usage stamps, leaving a backup of each file it rewrites, and unlinks the record files last; then, once every removal step has landed, which includes the confirmed run that found no record and so removed nothing, it removes the backup beside each of those three files, whoever wrote it, so no copy of the deleted body the verb can name survives in the tier. That closing sweep is what makes the claim exact rather than approximate: an index line for a record authored without a body flag carries the whole stored body, so an index backup left beside the tier would keep the deleted memory readable in a file no reader lists and no hand may edit, the tier barring hand edits by design, and which nothing clears until some later rewrite of that same document happens to replace it. The exposure is local: `*.bak` sits in the sync's never-sync patterns, so the copy stays on the machine that made it. It runs only after the removals, because until then those backups are the single local recovery for a rewrite that stopped, and the bound is the path rather than the writer: those three are the documents this verb exists to edit, and a delete that stopped after its index rewrite leaves a backup there and no index line behind it, so a re-run bounded by what it had written itself would sweep nothing and leave the removed record's text in a file no reader lists and no hand may edit, cleared only if some later rewrite of that document happens to replace it. A backup it cannot remove is named on stderr and does not fail the delete, the deletion itself being complete by then and an error code only sending an operator to re-run a command with nothing left to do. What the sweep does not reach is a `<file>.tmp.<pid>` a hard-killed rewrite stranded at one of those three paths, `MEMORY.md.tmp.<pid>` at either index, holding that index as it then stood with the record's line in it, and `usage.jsonl.tmp.<pid>` at the sidecar, holding the stamps recorded against the record's name: the sweep names the `.bak` at each path and not the temp beside it. The copies it removes are found by listing each directory the tier writes under, its archive included, rather than by name alone, because an interrupted rewrite can leave a `.tmp` beside the `.bak` this module can name and both hold the record's text; the listing leads and nothing is unlinked before it returns, so an unreadable directory stops the verb before spending the record's only local copy on the way to the same stop. The verb runs two sweeps, the tier's own directory and its archive, and both directories are checked before either sweep unlinks anything, so a path that is not a directory at all stops the verb with every copy still whole. That check reaches the directories and not the backup paths inside them, so the other permanent case, a directory standing at `<name>.md.bak`, is not caught before the live sweep runs. What stays per sweep is the transient one: a directory that lists for the first sweep and fails for the second leaves the first sweep's unlinks done, which is a state the same command completes rather than one it cannot describe, and the report names the sweep it stopped in. The order is what makes the verb re-runnable: every state a stop can leave is one the same command completes. Whether a rewrite carries a tail copy of bytes that appeared past its read is decided at the call site rather than by a default, and on the index path saying so is mandatory: each helper there throws when its caller states nothing, so no index rewrite added later can inherit the wrong behavior by omission. The rewrite helper takes that answer directly. Every function above it on that path takes the tier instead and derives the answer from it, which is the same requirement asked in the words those callers actually know, since a caller holding an index path or a tier directory knows which tier it is holding and need not restate a consequence of it. The requirement is stated as a rule rather than as a tally of the functions carrying it, because the tally is what drifts. The journal and the usage sidecars are the other case, and the difference is worth stating rather than generalizing over: their helpers state the answer as a constant, because there it is a property of the file rather than of the caller, those files having lawful lock-free appenders in every tier and keeping the copy wherever they are rewritten. The refusal therefore guards the path where the answer varies, and a new sidecar-shaped writer modelled on one of those helpers inherits a constant that was chosen for the file it was written for, with nothing checking that it is right for a new one. The two index files are decided per tier rather than per name, because the same two filenames mean different things on either side: in the shared tiers nothing lawful appends to them, so a rewrite there takes itself as written, while the project tier's own `MEMORY.md` does have lock-free writers (the Write tool, and a reinstatement that restores an index line by hand) and so keeps the copy. The decay pass is the one writer reaching both tiers through a single code path, which is why the choice travels as an argument rather than living in the function. The replacement check is independent of that choice and runs on every rewrite rather than only the tail-carrying ones, because the whole store syncs and a pull replaces a file rather than appending to it, holding no lock this module takes: every rewrite reads the file back and proceeds only where the bytes the pass read are still its head, failing with nothing written when they are not, since the alternative is to republish a stale copy of every line the pass did not touch and drop whatever the pull added. What the call-site choice decides is the narrower question of whether bytes found past that head are spliced onto the new content or dropped. A caller that is removing a record also states what the carried tail may not bring back, so a usage stamp for the deleted name cannot ride back in past the rewrite that dropped it. That split is why the readers tolerate a torn line rather than failing on one.

A tolerated torn line is still a loss, and one contract carries that through every reader of a sidecar. `readUsage` returns a skip count beside its three-value status (`memq.js:1406-1425`), because a sidecar that reads whole while dropping one malformed line reports `ok` and is a partial loss the status alone cannot express. Every consumer whose claim rests on having read the evidence whole keys on both halves rather than on the status: `recall`'s per-tier unread flags, `recent`'s floor, `unstamped`'s two loss flags, and `decay-scan`'s evidence column and candidate suppression, so a torn applied append cannot nominate a memory for archive on a tally the scan itself half knows is false.

That leaves a persisted torn line, which every read path and every ordinary rewrite preserves, flooring its tier's coverage on every later run. `decay-prune --rollup --drop-malformed` is its one sanctioned exit, and preserving stays the default: the flag is explicit, it reaches the project tier and either shared tier the same invocation reaches, and it refuses outright any tier where no parsed stamp would survive the drop (`memq.js:7358`), keeping every line and leaving that sidecar byte-unchanged. The refusal stands down per tier, so a refusal on one does not stop a legitimate partial drop on another. `docs/security-model.md` carries it as the third irreversible operation riding that verb.

A shared-tier body reaches the store by one of two channels, and the second exists because a command line is not a reliable carrier for one. `--body` takes the text as an argument; `--body-file` takes a path and reads the body as UTF-8 from that file. Any body composed with newlines should take the file channel, because `cmd.exe` cuts a command line at its first newline and `memq.cmd` forwards its arguments through that parser, so a multi-line `--body` reaching memq through that one wrapper is cut there. The sh and `memq.ps1` wrappers pass a multi-line argument byte-exact, so the trap belongs to `memq.cmd` alone, and `docs/security-model.md` carries what the file channel removes of it and what it does not. Both channels answer the same gates, a refusal of a blank body and a 65536-character cap measured over the whole record rather than the body alone, since `get` reads and caps the whole file. The two flags on one call are a refusal rather than a merge, and `--body-file` is refused outright under the engine store signals, where a granted worker invokes the script directly, meets no wrapper, and so loses nothing to the refusal.

Truncation is only half detectable, which is what shapes the CLI's account of it. With the body flag last, the cut leaves a correct positional count and a silently shortened body at exit 0, which nothing can catch, so every successful `add-type` and `add-operator` reports the stored body's length on its success line instead. Where the cut takes a positional with it the count fails, and a hint fires on the residue truncation leaves: a free-text `--body` or `--detail` value last on the line with the positional count short. It is worded as a hypothesis rather than a verdict, because a forgotten argument leaves exactly that argv and no reading of argv separates the two, and it names the remedy the caller can actually reach, which is `--body-file` ordinarily, `--body` under the store signals, and one line for `log --detail`, the one free-text flag with no file channel behind it.

Retention runs on evidence rather than a fixed clock. A memory's idle clock is the freshest of its mtime, an author-asserted `created:` date, and its newest `applied` stamp, and each distinct calendar day of recorded application extends both decay thresholds by 30 idle days up to a 365-day cap, so a heavily used memory survives a long idle stretch in proportion to its record of use while nothing becomes permanent by accumulation. A `pinned:` frontmatter field is the judgment override for the rare must-never-age case; it is set by hand, counted in full on any scan that finds one so the exempt population cannot grow unobserved, and honored by the prune as well as the scan. Crossing a threshold nominates rather than retires, and the archive stays scoreable and fetchable, so the worst outcome is demotion rather than amnesia. A `supersedes: <name>` field on a newer record is the fourth retention state and the only one driven by evidence the store did not compute: it points back at the live same-tier record it replaces, and from the moment it lands that record is labeled by every surface that serves a record by name, demoted in `find`'s semantic ranking, and nominated at the next scan whatever its idle clock, while staying live and fetchable. The label does not reach the `MEMORY.md` index the SessionStart hook emits, index-line changes being out of the remedy's scope. The pointer is authored data rather than a measurement, which is why it nominates and never retires, why a pin outranks it, and why a mutual pair and a record naming itself are dropped rather than read as claims. A cycle labels nothing whatever its length, a self-pointer, a mutual pair and a longer loop alike, while a pointer reaching into a cycle from outside still labels the member it names. The map is an inverse scan of the tier's live records built once per invocation, so on the surfaces that already list a tier the cost sits in the same class as the pin walk beside it; `get` is the exception and it is deliberate, since answering for one name means opening the tier that held it, so it costs a tier walk rather than the single file read the lookup itself would need. Only a live successor labels anything.

Authoring the pointer splits by tier, and the two halves get different amounts of checking. The project tier writes it by hand, as it writes `tags:` and `pinned:`, so the frontmatter reader is the only thing standing between what a file says and what a line claims. The two shared tiers add a creation-only `--supersedes <name>` flag to `add-type` and `add-operator`, written as a top-level frontmatter line beside `tags:`, reported on the success line, carried across a later `--update` body repair verbatim, and refused alongside `--update` exactly as `--tag` and `--machine` are, so a record needing a different pointer is a delete and a fresh write. Six shapes refuse the command with nothing written: a name outside the record-name grammar, a name whose path is not a plain file or cannot be examined, a name whose own frontmatter cannot be read, a name no record of the tier holds, a name only the tier's archive holds, and a name whose own record already points back at the one being written, which is the pair every reader would drop whole. That gate is a typo guard and claims nothing more: its reads are lock-free, so a concurrent delete can still leave the dangling pointer the read surfaces treat as inert, and it closes the pair rather than the ring, a longer loop staying mintable through a delete and a recreate at no cost, since the readers drop every member of a cycle anyway. The flag is refused outright under the engine store signals and withheld by the grant hook, the two locks `--body-file` already carries, so an unattended worker writes the record without the pointer and the pointer waits for an attended session; `docs/security-model.md` carries why a demotion this light is withheld at all.

### Anchors

An anchor is a project memory's own record of which files it is about, at the bytes those files held when it was written. The field is `anchors: <path>@<sha>, <path>@<sha>` on one line at the top level of the frontmatter block, the same line discipline `tags:` takes, and the reader takes it under the harness's `metadata:` map as well. The `<sha>` is the git blob name, sha1 over `blob <length>` plus a NUL byte plus the file's own bytes, which `git hash-object --no-filters <path>` reproduces. The flag is load-bearing rather than decorative: this checkout runs `core.autocrlf=true` with no `.gitattributes`, so a bare `git hash-object` applies the clean filter and returns the LF-normalized hash, which for any CRLF file is not the hash an anchor records. Computing it from a file's own bytes is what makes an anchor verifiable by hand, valid on uncommitted content, and free of any git process at check time.

The tier is the project tier and only it, in this version. An anchor needs a project root to resolve against and a tree to hash, and the type and operator tiers have neither, so a shared-tier record declaring one is never checked and every read surface says so rather than answering clean.

The grammar is narrow on purpose, because a path lands on a report line a reader has to be able to check. A path is forward-slashed, relative to the project's main root, at most 256 characters, and refused for a leading slash, a `..` or dots-only or trailing-dot segment, a backslash, colon, `@`, comma, double quote, or any of `* ? < > |`, a win32 reserved device stem on every platform rather than only on Windows, a leading YAML indicator character, and every whitespace and invisible character. Visible non-ASCII is admitted, so a repository with non-English filenames keeps the feature. One line reads at most 32 entries and says so when it cut the rest. Three limits ride with that and are stated rather than softened: the hash is SHA-1, so an anchor gives change detection and not tamper evidence; nothing normalizes Unicode, so a name written where the filesystem stores NFD reads `missing` on a filesystem that stores NFC; and the whitespace bar costs real files, `docs/my notes.md` among them, because a stray space at either end of a quoted path is invisible on the refusal line that would report it.

`memq anchor <name> <path>...` is the writer, and it touches one line. A 40-hex value is the one field of a record a hand cannot check its own typing on, so the verb computes the hashes and writes nothing else: it merges per path into whatever line the record already carries (a fresh hash replaces the old one, the existing order is kept, a new path is appended), creates a block at the top when the record has none, and otherwise rewrites that one line, leaving the body byte for byte as it was. The write is temp-and-rename under both of the project directory's locks, decay first and then store, which is the order the file already establishes, so a concurrent decay pass cannot archive the record out from under the rewrite. Every path is judged and hashed before the lock is taken, so one refusal writes nothing at all. It refuses the two shared-tier flags with the v1 reason, refuses when no project root resolves, and refuses outright rather than answering not-checked when the working directory names a network share, because it authors a record rather than reporting on one. The success line names which entries this run hashed and which it carried across, since a line printed whole reads as though every entry on it was verified just now. Removing an entry is a hand edit in this version. The rewrite moves the record's mtime, which the idle clock counts as a sign of life, and that is correct: anchoring is a verification act.

Four read surfaces report drift, and drift nominates rather than retires. A changed file does not make a memory wrong, it makes it unverified, so the remedies are re-reading and re-anchoring, a successor carrying `supersedes:`, or a hand correction, and no drift line ever deletes anything. `memq decay-scan` prints a `DRIFT` block after its existing blocks, headed with the tier it covers because the block reads that tier alone, listing each record with its `changed:` and `missing:` paths, pinned records included, since a pin exempts a record from retirement and not from being unverified. `memq get <name>` prints one line per anchor after the body, each `fresh`, `changed (recorded <sha7>, now <sha7>)`, `missing`, or `unreadable`. `memq recall` appends a `[drift]` token to a drifted record's digest line, in the slot the `superseded by` label occupies, and `[drift?]` to one the pass could not verify. `memory-session.js` emits the count at session start, built from up to three sentences carrying integers and this hook's own words and nothing from the store.

Every one of those surfaces separates three answers rather than two, and that separation is the feature's load-bearing property: a surface whose whole job is to say "unverified" must never report "verified" because a check could not run. So a record the scan reached and could not settle is listed beside the drifted ones with its own cause, a whole tier that is there and cannot be examined answers `not checked (this tier could not be examined)`, a store pin answers with the pin as the cause, a record on a shared tier answers with the tier as the cause, and a record the session hook's own read budget stopped short of gets a sentence naming that budget rather than pointing at a scan that carries none. The hook's pass is bounded at 200 records, 500 anchors, and 8 MB hashed, because it runs at every session start and a hook that runs long loses its whole stdout. `blobSha` refuses a file over 4 MB rather than hashing it, and an anchor whose path runs through a symbolic link or junction inside the project reads `unreadable` rather than `fresh`, which is what closes the win32 hazard where a planted link to a UNC target turns a resolution into an outbound authenticating connection.

The fleet grant withholds the verb. Anchoring rewrites a record in the shared priors at a name the command line gives it, which is an authoring act on state a worker's writes are otherwise quarantined from, and a worker could re-anchor a memory onto whatever the tree holds now so that every drift surface then reports it verified when nobody read it. The CLI has no second refusal for the verb, so the grant's allowlist is the whole of what withholds it.

### Recognition triggers

A recognition trigger is a project memory's own declaration of what should bring it back, written as a pattern the session's tool stream can be matched against rather than as a file the record is about. The field is `triggers: <type>:<pattern>, <type>:<pattern>` on one line at the top level of the frontmatter block, the same line discipline `anchors:` takes, and the reader takes it under the harness's `metadata:` map as well. Six types decide how a pattern is read: `cmd:` against a Bash command, `err:` against a failed call's output, `glob:` against a path, and `skill:`, `agent:` and `tool:` against the identifier a call names. It is a sibling of `anchors:` rather than an extension of it, because an anchor carries a sha whose whole purpose is to go stale while a pattern has no bytes to hash.

The grammar is narrow for the reason the anchor grammar is: a pattern lands on a report line and inside a YAML plain scalar, and both readers have to be able to take it whole. A pattern runs to at most 256 characters, one line reads at most 32 entries, and whitespace is admitted only as an interior plain space, so that `cmd:node --test` is spellable at all. A comma, either quote, an opening bracket, a backslash, and the three sequences a plain scalar cannot carry (`: `, ` #`, and a trailing colon) are refused. Two specificity bars sit on top of that grammar and reach different types, because a bar written over a typed vocabulary holds only of the members it is true of. The four-character floor is asked of all six. The bare-token bar, a 22-word set of common command names compared without regard to case, is asked of `cmd:`, `err:` and `glob:` alone, those being the types whose pattern is a fragment of something longer; `tool:Bash` is a whole identifier with no longer spelling, so the same bar there would make the trigger unauthorable rather than ask for a better one. A `glob:` pattern takes the anchor path grammar with `*` and `?` admitted, and refuses the single quote anywhere rather than in the lead alone.

`memq triggers <name> <type>:<pattern>...` is the writer, in `memq anchor`'s idiom and reaching the project tier and a run's own pending tier alone. It merges per entry rather than replacing, so an entry the line already carries keeps its position and one it does not carry is appended, and entries are compared as text exactly, case included, because a command line carries its own casing where a filesystem folds it. A run that adds nothing writes nothing: it prints the line, says every entry was already there, and leaves the record's bytes, its one backup generation and its mtime as it found them, re-declaring a trigger verifying nothing where re-hashing an anchor does. A run that does add an entry rewrites that one line under the project directory's decay and store locks in that order, leaves `<name>.md.bak` beside the record, and moves the mtime the idle clock reads as a sign of life. Three surfaces read the field afterwards: the frontmatter guard holds a hand-written line to the same grammar at the write door, `memq get` prints one line per entry after the body, and `decay-scan` reports nothing at all, a pattern having no bytes that could have changed. `find` carries no trigger label on either channel, while the semantic index still embeds each record file whole with its frontmatter, so a pattern is a few words of search surface as well as a recognition rule. The fleet grant withholds the verb for the reason it withholds `anchor`: the line it writes decides when a memory is put in front of a session.

The nudge log is what makes the recognition layer measurable rather than merely felt. Every nudge `memory-recognition-nudge.js` claims for a session appends one JSON line to `.kit/memory-recognition-nudges.jsonl` under the project's resolved main checkout root, carrying the record, the trigger that fired and the moment, written inside the same lock that claims the emission so a rotation cannot land between one call's size check and another's append. The log is machine-local and never synced, it rotates to `<path>.old` past 1 MB, and its absence reads as no nudge has fired yet rather than as a fault. It is also the one writer that creates a project's `.kit/` from a hook running on every tool call, so it writes a `.gitignore` holding `*` into the directory at creation, which keeps the log out of a host repository that never excluded `.kit/` itself. The hook exports the reading as `nudgeStampRate(cwd, sinceMs)`, which splits the project tier's nudgeable records, those carrying at least one trigger or anchor, into a nudged arm and an unnudged one and reports each arm's applied-stamp rate over the stated window. Every bound that would shorten one arm without saying so refuses instead, the tier listing's cap, the index's byte bounds and the log's own read bound among them, because a number that flatters the feature it gates is worse than no number. That reading is the evidence the semantic tier's gate consumes, and it cannot separate the nudge causing an application from the record having been relevant to the work in the first place, which `memory-system/SKILL.md` states beside it.

### The frontmatter guard

`hooks/memory-frontmatter-guard.js` is the write door the store previously had none of. The project tier is authored with `Write`, `Edit`, and `MultiEdit`, so its frontmatter passed through none of the refusals memq's own verbs apply, and a hand-written `supersedes:` naming a record that does not exist, a `tags:` list in the YAML form memq reads as no tags, an indented `pinned:` that pins nothing, a malformed date, and an `anchors:` entry outside the grammar all landed with nothing said. The guard is wired PreToolUse on those three tools and is the only surface that sees a record before it exists.

Scope is memq's own store resolution rather than a second one. The target's directory must be a tier directory memq places, and the filename must satisfy `isMemoryFilename`, so `MEMORY.md`, `decay-stamp`, the sidecars, and anything under `archive/` are out of scope and allow. On the two shared tiers every `Write`, `Edit`, and `MultiEdit` is denied whoever is writing, the main session included, because the rule the memory-system skill already states is "never the Write tool" rather than "not by subagents"; the refusal names three commands, one per thing a blocked write could have been doing, since a create, an index-description change, and a body repair take different flag sets and naming one sends the other two authors to a command that refuses or, worse, to one that exits 0 having never opened the record. On the project tier the guard computes the resulting content, allows without validation when it has no frontmatter block or when the block matches the one on disk, and otherwise validates through memq's exported readers.

Every judgment about a record is memq's, loaded from the plugin's own `scripts/memq.js`, so the guard and the store cannot come to disagree about what a record declares. Three rules are the guard's own because memq decides none of them: the `YYYY-MM-DD` calendar form a `pinned:` or `created:` value takes, the `- ` item that follows a `tags:` key with no inline value, and the position of the opening fence. Fourteen paths deny: two on the block (one that opens on line 1 and never closes inside the reader's line bound, and a fence that is the record's first non-blank line without being line 1), one on placement (any of the seven fields memq reads indented under a key other than `metadata:`), one on list-form `tags:`, two on dates (a `created:` memq cannot parse, and either date field outside the house form), two on `anchors:` (an entry the grammar rejects, and a path escaping the project root), one on `triggers:` (an entry outside the recognition grammar), and five on `supersedes:` (a name outside the record-name grammar, the record's own name, a target held only under a variant casing or extension case, a target held only under `archive/`, and a name the tier holds no record of). Everything else allows.

The guard answers three ways, and each answer travels on a channel its reader is actually on. A deny exits 2 with one line on stderr, which is what the harness delivers to the model as its reason for blocking. A record that was checked and is clean exits 0 in silence. A target the guard placed inside the store and then could not check exits 0 like the clean one and says so on stdout as PreToolUse `hookSpecificOutput.additionalContext`, which is the one exit-0 channel the model receives, naming the tier and the cause and stating that the write is going ahead unchecked. Nineteen distinct causes reach that third answer, from a payload shape the guard does not read as a write through to a throw out of any reader it called. It is written only for a target already inside the store, because a hook that spoke on every `.md` write on the machine would be noise rather than signal.

Anchor validation is the one part of the guard that touches the filesystem beyond the record, and it is gated twice. The project root is derived only for a record that actually names an anchor, so a record declaring none pays none of the walk, and a working directory naming a network share answers not-checked before the walk runs. That second gate matters more here than at any other consumer of the shared predicate: the others cost a lost stdout block or an interruptible foreground wait, while this one sits in front of every write and would stall the operator's own tool call until the harness's hook timeout ended it.

Two bounds decide what the guard is judging rather than whether its judgment is right, and both are set from the consumer rather than from the guard. It reads the operation from `tool_name` and the subject from `tool_input`, both the harness's own fields, so a payload whose shape and name disagree is checked as the operation it actually is. And it bounds the record at 65536 bytes, measured as bytes because every memq reader bounds the same record in bytes; where the cut may have manufactured a closing fence, or the block does not close inside the head, the guard declines to judge rather than siding with one of memq's two readers against the other. Both streams are fenced for the life of the process, so the deny line is the only text on stderr and the not-checked object the only text on stdout.

Its residuals are stated in the guard's own header and are worth naming here. Store-root containment is lexical, with the real path tried as a second candidate only for a target already lexically under the store root, so a spelling the filesystem accepts and a lexical compare does not (a mapped drive letter, a UNC spelling by a fully qualified or aliased host name) places nothing and is allowed in silence; resolving either would mean an outbound connection made before the user's permission prompt. The run-scoped pending tier is not a tier directory to memq's `tierDirFor`, so a record written there is out of scope. A shell redirection never meets the guard at all, its matcher naming the three file-writing tools. And its own read cap duplicates memq's `FRONTMATTER_READ_CAP`, which memq does not export, so the two are held equal by hand.

`memq recall` is the read half. It takes no search term and emits the whole store as one bounded digest, a summary line per record across every surface, ordered by last sign of life, inside a fixed line budget whose every truncation is announced with a counted remainder. Ranking is deliberately left to the model reading the digest with its current task in context, because that is the only semantic scorer available and it is free; lexical scoring was rejected because a substring miss is silent, which is the expensive failure shape. The digest leans on nothing outside itself to have put a record in front of the reader: descriptions ride the journal, the archive surface across all three tiers, and the project tier. The type, operator, and pending tiers are the live surfaces that stay lean, the type tier because the session hook emits its index as a block of its own, the operator tier because it is reached by search rather than by emission, the pending tier because it holds the run's own writing that the run just produced. The trigger is procedural rather than ambient: `executing-work` and `brainstorming` each run it where an effort's context is assembled, and a boundary taking the hand walk runs it again, so no hook pays context and latency on every prompt. The store resolves from the cwd, and a git worktree resolves its main checkout's store (memq follows the worktree's `.git` pointer through a two-way handshake), so recall works from a worktree as well as the main checkout; a plain subdirectory, a bare-repo worktree, or a worktree whose `.git` handshake fails (memq notes that one on stderr, pointing at `git worktree repair`) still resolves a different, empty store, and the tell is a digest whose coverage lines all read zero on a project known to have memories.

`memq recent` is the second reader, and it answers what happened to the store rather than what the store holds. It digests one time window (`--since <n>d` or `<n>h`, default one day, any other spelling refused) and groups by write surface rather than by tier: journal entries logged, applied stamps written, and memory files added or updated. The grouping is what makes the digest answer whether the extension layer is being used at all, because provenance rides the surface: journal entries and stamps exist only through `memq`, while a project-tier memory file arrives through a session's own Write tool. Every group opens with a coverage line carrying its count even at zero, and evidence that exists but could not be read is said in that line, so a count is never quietly a floor. Read the file group's `added` label narrowly: it says the file's creation time falls inside the window, and the editing tools rewrite a memory file rather than patching it, which resets that time on every write. So the label separates how a file was written from how it was not, never a new record from an edited one, and `backlog.md` carries the choice of what to do about it.

Its span is every tier the store has, the project tier, a declared type tier, the operator tier, and a run's pending tier, each with its `archive/` directory, so a decay pass's demotion reads as the file change it is. Archive records key on the newer of mtime and ctime rather than the mtime alone, because archiving is a rename: the rename preserves the mtime a memory carried while it was live, which for an archive candidate is idle months by construction, and moves the ctime instead. The digest carries its own 200-line budget, matching `recall`'s and tunable apart from it, and the same rule that every truncation is announced with a counted remainder, and it cuts in the reverse of its print order, so the journal, which nothing else summarizes and no session-start block carries, is the last surface to lose lines. It is read-only and stamp-free: it reads sidecars, the journal, and file stats and never serves a body, so it appends no `read` stamp of its own, since a digest that stamped the reads it reports on would corrupt the decay evidence it exists to show.

The trigger is procedural, the same shape as `recall`'s: `finishing-work` step 7 runs it over the session's span at close-out, after the memory writes, the unstamped sweep, the after-query (the `memq find` pass over the vocabulary the effort learned), and any decay pass, so the close-out status reports counts instead of asserting that the effort banked something. The cwd caveat is the narrow one `recall` carries: a Commit-and-Push session sitting in a worktree resolves the main checkout's store (the worktree handshake), so `recent` reports the real activity there; a plain subdirectory, a bare-repo worktree, or a worktree whose `.git` handshake fails resolves a different, empty store and reports zero for a session that banked plenty.

`memq unstamped` is the third reader, and it answers which memories were opened and never reported applying. It diffs the used-tracking sidecars' `read` stamps against their `applied` evidence inside one window (`--since <n>d` or `<n>h`, a positive whole number of days or hours, default one day, on the same grammar and the same refusals `recent` carries: one `--since` per run, the value a separate argument, any other spelling a usage line) and reports the gap: one line per record carrying the tier token, the name, the age of the last read, and the tier index's description. An `applied-rollup` counts as applied evidence and is dated by the last application it folded rather than by the fold, the reading `recent` gives the same record. The window is a set-membership question rather than an ordering one, so a record applied anywhere inside it stays cleared however much later it was read again; comparing the two timestamps would re-ask an adjudicated record on every subsequent read, and the list works only while every line on it is a real question.

Its span is the live records of the project tier, a declared type tier, and the operator tier, each stating its count even at zero. Four surfaces are deliberately outside the domain, each for a reason that would otherwise teach an invocation that errors or a question with no answer: journal keys, which have no applied concept at all; `MEMORY.md`, which the stamp hook never records; the run-scoped pending tier, whose records `touch` cannot stamp; and any archived record, which `touch` refuses. The command writes nothing, not a read stamp, not a usage entry, and not a lock, since acquiring one creates the directory it sits in. It carries no line budget, unlike the two digests: its output is bounded by the swept tiers' live records carrying a read stamp inside a short window and no applied stamp, whoever wrote those stamps, and truncating an adjudication list would hide exactly the record the judgment is owed on. Where a tier's sidecar could not be read whole, or its record listing was anything but read whole, absent as readily as unreadable, that tier's coverage line says the count is a floor rather than reporting a clean zero, because the two errors cost differently: a false candidate costs one recognition question, a missed applied ages a load-bearing memory toward the archive. Output closes on one of two lines, selected by whether any tier raised a hit, or on nothing at all in the one state that reaches no tier: an absent project memory directory with no operator tier behind it, where a stderr note is the whole answer. Where a tier did, it is the same tier-aware stamp reminder `find` uses, naming the exact `touch` invocations this run's own hits need, which is why every hit is a live record of a tier this working directory resolves rather than merely a record that was read. Where none did, it is a verdict at column zero stating the read evidence behind the zeros: how many records carry a read stamp inside the window, or that none do, with a loss on either reading named where it can still be hiding a record awaiting a stamp. The two are exclusive by construction, and each is what the other's case cannot say: a reminder over an empty list would teach a `touch` with no argument to give it, and zeros with no verdict under them are byte-identical whether the window held no tracked read at all or held reads a boundary had already adjudicated.

The trigger is procedural on both ends. `executing-work` step 6 runs it at every Chapter boundary before the Chapter is appended, and the Chapter records the outcome in its `Stamps: <adjudicated N, stamped M>` field, a window that owed a hand walk saying so there, why it was owed and what the walk found, in place of a bare count; `finishing-work` step 7 runs a final sweep at close-out, ordered sweep, then after-query, then decay pass, then recap. The boundary trigger is what makes the mechanism work: read stamps survive a compaction and a session handoff, while the judgment of which read mattered does not, so a close-out-only sweep asks a long run to recall across boundaries it has already crossed. The close-out sweep precedes the decay pass because applied stamps are the evidence the decay thresholds extend on, so a sweep running after it could stamp a memory the same close-out had just archived for idleness.

The decay seeds (30 idle days per applied day, a 365-day cap) and both digest budgets (200 lines each, plus `recent`'s one-day default window) are invented constants with no live observations behind them, to be tuned on real tallies rather than widened speculatively.

The routing ladder is journal, project, type, operator, doctrine. The operator tier is the destination for a fact true of the operator or of a machine rather than of one project or one platform, and without it such a fact strands in whichever project store happened to learn it. It is shared by every project's concurrent sessions, so authoring goes through `memq add-operator` under the tier's lock rather than the Write tool, which cannot take one; a `machine: <name>` field on a memory scopes it to one box, which search labels rather than hides. Retrieval is most-specific-wins, project over type over operator and live over archived. The tier is deliberately absent from session start: it is reached through `recall`, `find`, and `get`, which keeps every use visible to the read and applied stamps that the decay clock runs on, where an injected index emission is use no stamp can see.

The store also syncs, and on Windows it syncs itself: the session-start hook spawns a detached background runner (`doctor/sync-store.ps1`) that commits pending memories and, where an upstream exists, fetches, screens the incoming content, rebases, and pushes, so a memory learned on one machine reaches the others with no hand-run step and no nag while it is healthy. `~/.claude` is a git repository whose gitignore excludes everything and re-includes only the memory tiers and the machine coordinator directory, pushed to whatever remote is configured for it; nothing in the kit reads that remote's visibility, so a private one is a precondition of an installation rather than a property of the design, which `docs/security-model.md` states in full. That allowlist is the whole boundary between replicating memories and publishing credentials, and it is not self-enforcing: a `.gitignore` inside a traversed directory outranks the root file and can re-include what the root excluded. So the guarantee is the rules plus the leak probes both committers re-derive on every run (the doctor's `-Fix` and the background runner, which dot-sources the same code), over the ignore rules, the worktree, the index, and the local committed history, refusing any commit carrying a path the allowlist does not admit. The allowlist guards both directions: outbound, those probes refuse a commit; inbound, the runner screens every entry of the incoming tree by its mode and its path before the rebase touches the working tree, so a rename, a duplicate-content push, or a symlink at an allowlisted path cannot drop a disallowed file into `~/.claude`, where nothing un-writes it. The journals merge as line unions, which fits their append-only shape. Project stores are keyed by the flattened project path, so a synced project tier resolves on another machine only where the project sits at the identical path; the type and operator tiers are path-independent and resolve everywhere; the coordinator directory holds one directory per machine by the seats' own convention rather than by anything the sync enforces, its allowlist predicate scoping to no machine, matching `coordinator/` followed by anything whose leaf is a `.md` and none of whose path components is transient-shaped, and every machine reads all of them.

The runner's own record of what it did is `kit-sync-state.json` at the store root, and it is the only channel a detached background process has. `Write-SyncState` composes five fields (`lastAttempt`, `lastResult`, `reason`, `lastOk`, `firstFailSince`), writes them to a per-PID temp file as UTF-8 without a BOM, and puts that file in place two ways: `File.Move` where no state file exists yet, and `[System.IO.File]::Replace` where one does, because a replace is atomic on NTFS while `Move-Item -Force` is a delete-then-move a concurrent reader can catch mid-gap. That `Replace` call passes `[NullString]::Value` as its backup path rather than `$null`, and the distinction is load-bearing: PowerShell marshals `$null` into a `string`-typed parameter as the empty string, `File.Replace` rejects an empty backup path, and the surrounding catch would swallow the exception, so the `$null` spelling lets only the first write in the file's lifetime land. The write is silent in both directions by construction, since the catch deletes the temp file and returns without an error, an exit code, or a record; `docs/backlog.md` carries that residual and the two triggers still reachable for it. `memory-session.js` reads three of the five fields, `lastResult` and `firstFailSince` for the seven-day failure-streak nudge and `lastAttempt` for the broken-chain check against the spawn marker's mtime. `lastOk` is the runner's own success stamp and is read nowhere outside `sync-store.ps1` and the tests.

Whether a push has anywhere to land is the doctor's question, and `Get-MemorySyncDestinationLines` in `doctor.ps1` answers it as a pure formatter over the status hashtable `Get-MemorySyncStatus` fills. Every read behind it is of a local ref or a `--local` config value, so the answer costs no network round trip and is as of the last fetch, a limit the report states rather than hides. Four states block: a detached HEAD, a branch tracking nothing, a branch tracking a remote other than origin, and a `push.default` that will not carry this branch's pair of names. The last is the one every other check reads clean over, because the runner's push leg is a bare `git push --quiet` and what a bare push does with a local branch whose upstream carries a different name is `push.default`'s to decide. The name comparison is ordinal over the raw `branch.<name>.merge` value against `refs/heads/<local branch>`, which is git's own comparison byte for byte, so a case-only difference and a short form (`merge = main`) are both refusals rather than matches; the setting itself is matched case-sensitively, because git parses it that way and rejects a value it does not recognize.

What a differing pair costs is a function of that value, so the finding is too. `simple` refuses the push fatally. `matching` updates only branches carrying the same name on both ends, so it publishes nothing and exits 0, which the runner records as a success: the quietest of the set. An unrecognized value makes git refuse every push as a malformed config value, and `nothing` errors out for want of a refspec whatever the names are. Those four are blocking, which reports the memory-sync check FAIL and exits the doctor 1. `current` publishes to a branch on origin named after the local branch, so the push succeeds and lands where no other machine pulls from, which is advisory: the check reports WARN and does not fail the run. `upstream` and `tracking` push to the upstream ref whatever the two names are, so a differing pair is not a finding at all. Each finding carries its own remedy, and two of those are gated. The rename is printed as a runnable `git branch -m` only where the merge ref sits under `refs/heads/`, both names match `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, and both survive `Get-SanitizedLine` unaltered, and is reported in prose with no pasteable command otherwise. The report's trailing "put HEAD on the sync branch and give it an upstream" line is emitted only for the three findings it repairs, since running `push -u origin <branch>` against a branch whose upstream on origin is already correct creates a second branch there and repoints the upstream at it, which is the silent cross-machine divergence the advisory check in the same function exists to report.

`memq find` answers by meaning as well as by substring. `plugins/claude-kit/scripts/memory-index.js` owns an embedding stack that installs per machine outside the plugin payload, so the kit core stays dependency-free, and a derived JSONL index beside the store covering all three tiers, live and archived, across every project store on the machine, and deliberately not the run-scoped pending tier, whose unadjudicated writes are one run's to read. The index is sync-excluded by design: a vector is valid only against the embedder that produced it, so each machine builds its own, and the sweep is lazy at query time, keyed on content hash so a synced checkout that moves every timestamp re-embeds nothing. Where the stack is absent, find says so in one line naming the remedy and serves lexical results; nothing degrades silently. The two channels fail differently, which is why both stay: lexical catches the exact identifiers embeddings fuzz, semantic catches the paraphrase substrings miss.

Archived records are ranked but withheld from the semantic block by default, and one line in memq's own voice at column zero is what keeps the suppression from being a silent miss. It headlines every archived record that cleared the admission floor, which is suppression's true extent, and it quotes a best raw similarity only over the archived records inside the pre-suppression display slice, which is exactly the set a `--archived` rerun puts on screen under the same 10-hit display cap. Two counts rather than one, because a similarity quoted from a record the rerun's own cap would cut sends a reader after a line that does not exist: the line names the subset's size whenever it is smaller than the headline, and where nothing archived reaches the cut it says so instead of recommending a rerun that hands back the same screen. Suppression runs after admission and ranking and before the display cap, so a live hit fills the slot an archived one would have taken. A search whose every admitted hit was archived still prints the block's framing line and the withheld line rather than falling into find's empty-result path, which exits to stderr with `no matches`: a suppressed hit is never allowed to read as an absent one. `--archived` turns the filter off, printing those records labeled `retired` and demoted by the archive-demotion constant, which under that flag is what keeps an equally similar live record ahead of its retired twin, and it prints no withheld line; it is refused with a usage line alongside `--outcomes`, which never opens the semantic channel, and on every other subcommand. The lexical channel lists live records only, so the flag changes the semantic block alone.

A superseded record is the same shape one notch lighter, and it is not suppressed: the lexical line carries `superseded by <name>` and the semantic hit carries a bare `superseded` token beside the `retired` one and a demotion by its own constant, seeded to match the archive demotion, so an equally similar record nothing replaces ranks ahead of it. The names ride the lexical label alone, and a fan-in enumerates them there name-ordered, capped with a counted remainder, while the demotion fires once whatever the count, the label being a flag rather than a sum. Suppression would be wrong here for the reason retirement would be: the record is still live and the pointer is authored data.

A semantic hit line states usage as two tokens, `applied x4, last 25h`. The count is the distinct calendar days the record was applied on and the age is the most recent of them, printed apart because one number that means a tally reads as an age. The count shown is the uncapped truth while the ranking's tiebreak keeps using the value capped at the boost's own ceiling, which is deliberate: the line is annotation, the blend stays dumb, and the reader judges freshness rather than inferring it from a rank. The semantic block spans stores the calling project never opened, so it takes the full provenance fence rather than find's narrower by-construction guard, and `docs/security-model.md` carries that distinction.

The `memory-system` skill owns the operating rules; this section owns the shape.

## Dispatch authority

A plan doc can carry its own arming grant. A `## Dispatch Authorization` section at the head of a plan records who authorized the work, when, and which sessions the grant covers, with "any session holding this plan" as the default scope. A session handed such a plan arms it without a confirmation round-trip once it has traced the grant to the operator, because the committed document is the grant and the message that delivered it is only a pointer to one. The trace is a step somebody performs before arming and no tool runs it: the section is prose a writer supplies, so a receiver that arms on its presence alone lets whoever wrote the plan widen its own leash. The peer-sessions skill owns that step and the states a receiver takes when the trace does not hold.

The mark is provenance, not credential. On a single-principal machine the section narrows an honest writer without authenticating one, and git history is its trail. Nothing here stops a malicious local writer, exactly as no kit guard does.

The section is inert to the machine contract. The plan-doc header and the shapes an external engine parses are a frozen v1 contract, and `## Dispatch Authorization` sits outside all of them, as `## Assumptions` does. The two take different positions, and `curating-docs` owns the rule: `## Dispatch Authorization` belongs above `## Sections of Work`, which is stricter than outside it, because no template reserves a place for the heading and both of the blocks bounded by the next `##` heading truncate silently when one lands in them, the sections block dropping every later `### N.` section and the Chapters block freezing every `Completed:` line below the intrusion. `## Assumptions` takes the weaker rule, outside the sections block and above `## Chapters`, because the spec template already places it after `## Out of Scope`.

`/kit-goal` records what it read. At arm time the CLI scans the head of each armed plan for the heading and stores that section's first sentence, screened to printable ASCII and capped at 320 characters, in an `authorizations` map in the goal state keyed by plan path; a plan carrying no such section records none. The scan reads a 16 KB head of the plan doc and refuses a heading it cannot read as a claim: one inside a fenced code block, one below `## Sections of Work`, and one whose section body ran to the window's edge with no following heading and no sentence terminator, where the end of the body is unseen rather than short. A sentence past the cap is stored with a visible truncation marker written inside the cap, so a cut claim cannot read as a whole one and re-screening a stored value cannot cut the marker off. The value is quoted file content taken at its word, re-screened on every read as well as at the write because the readers print it, and surfaced by the `/kit-goal` status report. It is an audit trail rather than a check: nothing consults it to decide whether an arm may proceed. The same arm records who ran the invocation, in an `armedBy` map keyed the same way: `self` where a run armed the plan for itself, `operator` where the operator typed the arm, with an absent or unrecognized entry reading as `operator` for compatibility with states written before the map existed. It is recorded per plan rather than per queue because an append can add a plan armed one way to a queue armed the other, and it decides text and two renders: the condition sentence the state carries, the arming clause that the ordinary hold, the queue advance and the spent-lead hold carry among the Stop hook's block reasons, the per-entry line the status report prints, and the arming line the doctor's leash report prints beside the plan it reports. The doctor's is the one render that parts an absent entry from a recorded operator arming, naming the plan and saying nothing is recorded rather than asserting a claim the state does not carry; it reads both the field name and the entry name ordinally, because PowerShell's member indexer is case-insensitive and its `-ceq` is culture-sensitive, where the JavaScript readers use `hasOwnProperty` and `===`. That one fact is deliberately all it carries, so nothing an arming asserts can stand in for the sentence beside it: what a plan grants stays in `authorizations`, where it comes from the document, and a self-armed arm over a plan recording none proceeds with a stderr warning rather than a refusal.

Queues grow rather than mutate. `--append` adds plans to an armed queue under the existing binding, deriving each appended plan's authorization from its own document exactly as an arm does, and refuses atomically when any named plan already sits in the queue, so a partial append cannot happen. The bare replace form replaces the queue outright and warns on stderr when it drops a non-empty queue, naming what it dropped, since a silently dropped armed plan is the expensive failure. The size bound is measured against the real serialized state rather than an estimate, so a queue too long to write is refused rather than truncated. An append is typed into whatever shell is at hand while the leashed session runs, so it re-reads the state immediately before writing and refuses unless the arming timestamp, the current plan, the queue position, the queue length and the history length all still match what it validated against. What it writes is that re-read with the append applied, never the snapshot, so a stop's bind or advance landing mid-validation survives instead of being reverted; `bindSession` follows the same rebase, setting only the two binding fields it owns. Neither closes the window between the re-read and the rename, which stays last-writer-wins.

Arming happens where the run happens, and where the run happens is a repository rather than a directory: one repository has one leash, which a linked worktree shares with its main checkout through the resolution described below. What stays tied to the calling tree is the plan doc, so a plan handed to a session in a worktree cut before that plan's commit is unreachable to the receiving CLI however real the plan is at origin, and the arm refuses and the handoff defers to the next safe tree advance. The sender holds the handoff open until any of the receiver's three replies arrives, and counts it converted only on the armed acknowledgment. Two sessions sharing one working tree is a different hazard, since a shared tree shares a checkout rather than only a leash, and session start says so where it can see one: `summarizeSiblingSessions` lists this project's transcript directory for another session's `.jsonl` whose modification time falls inside a ten-minute window, excluding this session's own id, and emits one advisory carrying the count and the age of the most recent. It opens no transcript, and no name or path leaves the function. The listing is incremental through `opendirSync` under a 4,096-entry ceiling, because the store keeps a per-session subdirectory beside each transcript and a ceiling applied after a whole-directory read would bound nothing. Recency is the whole signal, so the line is a hint rather than a verdict: a file mtime cannot tell a live session from one that ended minutes ago, and a different checkout whose path flattens to the same directory looks identical from here. Every failure path is silent, an unreadable directory and an unrecognized layout included.

### Worktree resolution

One repository has one leash and one plan doc has two copies, so the goal family resolves those two things in opposite directions over the same pair of trees. The leash resolves worktree-to-main, because a repository is what a leash belongs to. The live plan doc resolves main-to-worktree, because a doc belongs to the branch being executed. What keeps two opposed resolutions from contradicting each other is that only the first one decides anything.

`goalPath` in `hooks/kit-goal-lib.js` is the single resolution point, and every read and write helper in that file joins its path through it, so the whole family inherits the behavior with no per-caller edit: the Stop hook, the compaction gate, the checkpoint CLI, the two nudges, the SessionStart notice, the `/kit-goal` CLI, and the status-line widget. The resolution is a two-way handshake, and each leg is a refusal rather than a preference. Only `<cwd>/.git` is consulted and never a walk up the tree; it is read as a regular file; its `gitdir:` line is matched at the start of the file; and the path it names is judged on its text alone before any filesystem call, refusing a UNC or device-namespace spelling and anything past a 2,048-character cap, since opening `\\host\share` is an outbound authentication as the logged-in account. The claimed main checkout must then vouch back on all three legs or none: its own `.git` is a directory, `<gitdir>/commondir` is a file, and `<gitdir>/gitdir` names this `.git` in return. Any leg failing answers no worktree at all and the reading directory stands, so a bare-repo worktree and a broken handshake both keep today's behavior. It is the same rule `memq` applies to the memory store, reimplemented here rather than imported because a hook may not carry that ten-thousand-line script's weight, and pinned against it by a cross-implementation test over shared fixtures so the two cannot answer differently.

The reach is wider than a read, and that is the part worth stating plainly: resolution moves the writes too, so a bind, a queue advance, and the clear's unlink land outside the payload cwd's git root. What bounds it is the handshake, since the only directory reachable is one that named this `.git` back. Plan docs are untouched by all of it and stay resolved against the caller's own cwd. Three readers reach past that cwd and none replaces it: `planDisplayRoot`, which runs the other way for display alone, and `queueEntryState` and the Stop hook's `'gone'` cross-check, each of which asks both trees and acts only where they agree, which is a second opinion rather than a second resolution.

`executionTree` is the doc half. The checkpoint CLI's `open` is its sole writer and records `path.resolve(cwd)` when, and only when, the resolution above answers a main checkout other than that cwd, so a chapter boundary is what stamps which tree a run is executing in. The field is display trust only, stated at the writer and at the reader: nothing that decides a hold, a release, an advance, or a gate outcome reads it, and the worst a false value buys is a section count taken from the wrong copy of a document. Four guards run before anything under it is opened, in order: the lexical screen it shares with `boundTranscript`, a drive-qualified absoluteness requirement on Windows, the same two-way handshake closing from that tree onto the main checkout this session's own state resolves to, and the plan path standing there as a readable regular file inside the reader's own cap. Every failure answers the caller's cwd. Its lifetime is explicit at every path that could strand it: a clear unlinks the state, an arm builds from nothing, an advance deletes the field, a boundary opened from the resolved checkout drops any standing record, and the write takes a compare-and-swap on the plan path and the arming timestamp so an advance landing mid-write cannot re-attach the finished plan's tree.

### Queue position

The reported queue position is derived from the plan docs rather than read from `queueIndex`, because nothing in the system is level-triggered on the stored index. `advanceGoal` has exactly one call site in the whole plugin, inside the Stop hook, so the index moves only at a clean stop of the bound session, and `normalizeState` reconciles the stored queue against the stored plan and never against the world. A run that dies at its close-out therefore leaves an index naming a plan it finished and archived, with no later session repairing it.

`queuePosition` in `kit-goal-lib.js` answers instead from the evidence. It walks forward from the clamped stored index, never backward, since an entry behind the leash may be unfinished for a reason the leash already adjudicated; it is capped at sixteen entries; and it reports the first entry the plan docs do not show as finished. An entry counts finished only where every tree with a say agrees, the worktree and its main checkout both, because the two legitimately hold different copies of one doc; a disagreement reports the entry pending, which under-reports progress rather than moving the reported position past live work. Evidence is the doc's own `Status:` header read through the shared kind-and-size rule, and, where nothing stands at the plans path, the header of a same-named copy under `docs/archive/` held to that same bar: presence alone is not evidence, since nothing ties an archived file to a queue entry beyond its name. An entry no tree can resolve keeps its position and is labeled with the cause rather than skipped, because skipping renumbers every entry behind it. The walk writes nothing.

Three surfaces report from it and one deliberately does not. The SessionStart advisory names both plans where the two positions differ, the stored one and the plan actually current, and says that the leash still acts on the stored index and takes one stop per plan to catch up. `kit-goal.js status` reports the same position. The status-line widget's `Plans` segment does too, adding the corrected plan's base name and the stored index beside it (`Plans: 2/2 b_spec_v1 (stored 1)`), an `unresolvable: <cause>` clause where the entry cannot be read, and an `all complete` clause where the entry at the reported position itself reads finished, which is the state where the leash releases rather than advances. The doctor keeps printing the raw stored index, on purpose: it is the surface that exists to show a state file the hooks refuse, and one that silently corrected the number would stop being the reporting control. `docs/backlog.md` carries that as a parked decision rather than a gap.

## Session roles

Roles are the coordination vocabulary the concurrent sessions on one machine share, and they sit beside the authority rail above rather than on it. A role is a stewardship claim on a function-times-resource pair: it says which session tends a seam, never what a session may do. Any session can name itself anything, so a claim confers nothing beyond legibility, and the peer-sessions skill states that as a rule rather than a caution, because the failure it exists against is a self-chosen label read as a privilege.

The starter seats are the coordinator, the expert, the worker and the admin, and the set is open. The coordinator stewards the seam between repos and toward the operator, one per machine. The expert stewards a repo's knowledge and its plan authorship, one per repo. The worker stewards mutation of one checkout, exclusive per tree and usually leashed. The admin stewards machine state, one per machine. A claim is declared in layers and no layer authenticates: the session name advertises it under the `PROJECT: Role` convention the peer-sessions skill owns, with the harness's own `ListAgents` roster as the directory a peer looks it up in; the first-contact handshake confirms it; the session's own registry entry under `coordinator/<machine>/registry/` records it durably, written by the very session whose claim it states, which is why it advertises rather than attests; and the coordinator's board carries those claims as that seat last read them, a different file with a different writer in the same directory. A roster row carries what the harness knows about a session, and the peer-sessions skill owns that field list; nothing in a row corroborates a seat. A claim colliding with a standing claim on an exclusive seam is routed rather than assumed resolved by silence: it goes to the coordinator, or to the operator where that seat is empty or is itself party to the collision, and only an answer retires one of the two.

Every seat also declares its own compaction boundaries, which is how a goalless session earns the clean landings a leashed worker gets from its chapter checkpoint. The invariant is the gate's own, compact wherever context holds nothing the disk does not, and the peer-sessions skill owns the cross-seat routine: a seat ends a banked moment by pushing status to its own registry file, and the `seat-stop.js` Stop hook reads that push and opens the role-boundary marker for it, so the next deferred offer lands at the boundary instead of riding to the safety ceiling. The status push is the declaration and the hook is what makes it structural; `kit-compact-checkpoint.js boundary`, run from the project directory, survives as the manual path for a session no registry entry covers. The working directory is load-bearing on that manual path because the marker lands in that directory's `.kit/` while the gate reads it at the compacting session's own. The named moments are the expert's deliverable handoff (spec committed, blind read adjudicated, dispatch acked) or a consult answered and banked, the admin's completed-and-reported action, the coordinator's end of a reconciliation pass after the board write and the next wake's arming, and an unleashed worker's own banked moment on the tree it holds, that seat having no chapter checkpoint at all since the leashed verb refuses to open with no goal armed; a seat the list does not name derives its own the same way the seats themselves are derived. Two bounds ride with the routine, and both belong to the gate rather than to the skills. The marker releases the interactive deny alone, so a seat a native `/goal` or `/loop` drives is classified as automation and allows at the native trigger with no marker read at all, which bites a coordinator only where a `/loop` drives the watch, the self-armed timer this seat uses reading as hands-on instead; and the marker's age bound is the deferral episode's own four-hour idle bound, derived from that constant rather than restated beside it, so the three quantities bounding a seat's quiet gap retune together. The consent marker is not a seat's to write. `kit-compact-checkpoint.js consent` is run only on the operator's explicit instruction to release that session's deferred compaction, over one of the warranted channels the coordinator skill's closed list of three names, and never on the session's own judgment; `docs/security-model.md` carries what that prose bound does and does not buy.

The coordinator seat carries its own runbook, `plugins/claude-kit/skills/coordinator/SKILL.md`, on the standing-watch chassis, and its functions are closed at four: the operator interface, cross-repo dependency and portfolio sequencing, machine-resource arbitration, and kaizen capture, dispositioning and dispatch, that last one carrying the operator's standing authority for it while staying inside the seat's never-tasks-directly bound, so a disposition lands as an artifact in the repo that owns the work rather than as an instruction on the seat's say-so. Oversight within a repo is deliberately not among them, the expert seat owning that. The other seats carry the reciprocal duty rather than a share of the function: each routes captured kit friction to the coordinator and carries on, never actioning it inline and never shelving it, because a responsibility naming no owner is discharged by whichever party is least busy, which in a fleet is reliably the party least likely to have seen the friction. The seat's state is a board at `coordinator/<machine>/board.md` inside the memory store, one directory per machine because the store reaches every machine on whatever remote is configured for it, and the chassis override that makes it durable rather than gitignored is the design rather than an exception to it: a watch's state dies with the watch by intent, while a seat's state is how the seat survives the session holding it. The seat writes the file and runs no git in the store, the sync being the store's only committer and only on Windows running automatically, so the board reaches another machine on that machine's next sync rather than on a push the seat performs, and on a platform where that script does not run it acquires history only when the operator hand-runs the store's repair path. What the board holds is coordination state and never authority, and what may go on a board line is set by content bars that hold whatever the readership, since nothing in the kit reads a store's remote and so no seat can learn who will see the file: the private-remote premise is a precondition of an installation rather than a property of the design, and a seat writes the board as a public surface until the operator states otherwise. `docs/security-model.md` states the bars and that premise in full under The coordinator board. A declared blocker climbs a ladder these seats define between them: the worker asks its repo's live expert before declaring, an ask carrying the question rather than the work and never gating; on declaring it notifies the machine's live coordinator, whose brief to the operator races that worker's own relay ping rather than gating it; and the answer returns on a channel the brief names in advance, the worker's own, never through the seat, because an inbound peer message carries no authority and a document the seat itself wrote cannot satisfy the authority trace.

Operating the seat is a chassis loop whose runbook states only what it adds. A pass arms its wake before it reads anything, since a session-only timer dies with the crash that interrupted the read, and then reads the board, because everything the seat has promised or brokered lives there and nowhere else. The cadence is event-driven, the blocker funnel's messages and the operator's pings, with one paced wake: a reconciliation timer every 4 hours, which is exactly the boundary marker's own age bound, so a marker opened at the end of one pass is still live when the next paced wake fires. The margin is that pass's own tail and no more, since the wake is armed one step before the boundary is declared: consecutive declaring passes cover the interval between them end to end, and a pass that skips its declaration leaves the whole of the next interval uncovered. An event-driven wake arrives sooner than the paced one and is covered a fortiori. It re-derives the watched facts from durable state rather than from messages, and the runbook owns which sources those are and what reading each one takes. This document deliberately does not restate that list: a list restated on a second surface is an invariant nothing checks. It takes the board as the record only for the seat's own commitments, which no watched system can produce. The seat dispatches nothing: it writes the spec or the backlog entry in the repo that owns the work, asks the operator to arm over one of the three warranted channels, hands artifact-authorized plans on the dispatch-authority rail, and appends an operator ask of the Admin seat to that seat's request inbox in the machine coordinator directory, the one seat no send reaches. Handoff and contest run off the same registry. A successor reads the board and then takes the seat's name on the roster in the machine-scoped `HOSTNAME: Coordinator` form, while two live names claiming the seat freeze the board and route to the operator, the seat citing the anchor it observed rather than a commit, since running no git in the store it can cite none, a registry a contested claimant maintains settling nothing. The uses of the messaging surface that have won their way past its closed four patterns are recorded in the peer-sessions skill rather than counted there or here, and every one of them so far bears on this seat: the status round, one bounded line per live session at no more than the heartbeat cadence and answerable at the receiver's next boundary; the worker's blocker route, whose notice leg hands the seat an escalation to route while its pre-BLOCKED ask leg goes to the repo's expert and never reaches the seat at all; the claim probe, the one use whose subject is a machine resource rather than a session's own state, which this seat sends to the claimant of a claim past its bounded declared duration; and the kaizen routing message every other seat sends this one, whose subject is that the artifact it belongs in sits behind an authority only this seat holds.

The runbook is partly exercised procedure. The seat's machine-resource arbitration, its status round, and the board write itself have all run. Four branches have been read for defects and never performed: the cold start against an absent board, the seat handoff, the stub forms, and the freeze on a contested seat.

Each seat runs at the cheapest tier its judgment surface allows, and the peer-sessions Roles table is the single owner of those figures: the coordinator at Opus on the cadence its own skill states, the expert at Fable, the worker at whatever model the session itself runs (a plan's section tiers govern what that seat dispatches, never what it runs), and the admin at Sonnet with a 4-hour poll of its inbox. Every row states an observable step-down gate rather than a feel, and the admin's is the one built against a silent failure: a month of adjudicated routing decisions with a planted line among them, because inbox volume alone cannot tell a quiet month from one where a laundering-shaped line went past.

### The coordinator directory

The machine's coordination artifacts live in the memory store at `~/.claude/coordinator/<machine>/`, `<machine>` being what `os.hostname()` reports, and four file forms live there: `board.md`, the coordinator's ledger; `registry/<session-id>.md`, one per registered session; `claims/heavy-process.md`, the machine's one-heavy-process slot; and `admin-requests.md`, the Admin seat's artifact inbox. The list is the contract, and `plugins/claude-kit/skills/role/SKILL.md` owns it. Owning is precedence rather than sole spelling: the coordinator's runbook restates the parts of the contract a pass cannot be run without, and the dispatch-brief template in `executing-work` carries a second copy of the claim protocol because a dispatched subagent inherits no skills and that copy is the only one it ever receives. A curation pass finding either restatement is reading a designed copy.

The writer rule is stated per file rather than once over the four, and that split is what the rest rests on. The board and each registry entry are single-writer, the coordinator writing the board and a registering session writing its own entry, plus the one `Heartbeat:` line `seat-stop.js` stamps into it. The claim file and the inbox are multi-writer by design, each under its own protocol. Exactly two acts reach across that rule and both are the coordinator's: it prunes a registry entry whose own heartbeat reads exited, and it releases a heavy-process claim past its declared duration. Each is written to the board before the artifact is touched, and every reading that cannot be made cleanly keeps the artifact rather than removing it, so an absent, unparseable, or future-dated stamp reads as unknown. `docs/security-model.md` carries what those two acts are bounded by, which is visibility and recovery rather than prevention. All four forms are `.md`, which is the whole of what the store's sync allowlist admits under this root, so the two rules agree in form while the allowlist stays the wider of them: any `.md` at any depth here syncs, where the contract names four paths. The directory sits outside `memory-frontmatter-guard.js`'s tier set deliberately, that guard's rule being CLI-authored-only while every writer class here writes directly.

A registry entry is a session's own account of itself, carrying `Name:`, `Role:`, `Repo:`, `Workdir:`, `Session:`, `Started:`, `Status-updated:`, `Remaining:`, and `Heartbeat:`, then a few `Status:` lines holding what a public board could carry. The session rewrites the status fields at every banked boundary its runbook defines and at any event that changes what the coordinator's next board would say about it: a Chapter close, a BLOCKED declaration, a suite or gate baseline change, a claim write or release, a takeover or handoff. `Workdir:` is the gated field. The registry is the one place a working directory may live at all, readable across the elevation boundary the board is not, and an absolute path is written there only where the operator has answered who reads the store's remote. That answer's default state is unanswered, and until it arrives the field takes a repo name, a worktree-relative name, or nothing.

`claims/heavy-process.md` models the one-heavy-process-per-machine budget as one file. Before a suite, a build, or an embedding pass, the spawner reads the live claim and then writes `Name:`, `Repo:`, `Session:`, `Started:`, and `Expected-seconds:`, deleting the file at completion and only where its `Session:` line is the writer's own. The enforcement point is whoever spawns the process rather than the seat that dispatched it, since most of a box's heavy processes are subagents', which is why the brief carries the clause at the spawn step itself and a subagent's claim carries its dispatching session's id and name. A session finding a live claim waits or names the contention, and naming a contention never includes writing the claim, so a session that proceeds runs unclaimed and reports itself that way rather than replacing a live holder's record. The claim buys legibility and never a guarantee: an empty claims directory means nobody has claimed the box, not that the box is free. What backstops a claim is its holder rather than a process poll, an instrument that cannot see work shorter than its own sampling interval, misses in-process agent fan-out entirely, and reads a resident idle build server exactly as it reads a live one. Past the declared duration, bounded by a figure the coordinator's runbook states rather than one the contract sets, that seat probes the claimant and may release the claim on two legs together, a probe whose send returned no failure and went unanswered past the probe window, and a roster reading that agrees the claimant is not live. Either leg alone leaves the claim standing as an untracked hold reported to the operator, and the release itself is a recorded, notified, reversible decision rather than a measured fact.

### Seat takeover

`/role <Seat>` is the one command that takes a seat, replacing a ritual that was hand-assembled across three skills. Its steps run in order, and where a seat's own runbook states a tick order that order governs and these fold into it. The session's name is confirmed against the peer-sessions Naming convention first, since a relaunch rather than a rename is what a wrong name costs (the relay-channel flag bakes the name into its thread at process start); the exact launch invocation is a per-machine operator fact the public skill cannot carry, so it is resolved from the operator memory tier and described to the operator in prose for confirmation rather than presented as a runnable command. The seat's runbook loads next. The wake is armed before anything is read, which is the coordinator's cold-start order held for every seat, because a crash mid-read leaves no timer behind: a seat whose runbook states a cadence arms at it, a seat stating a loop but no cadence arms at the coordinator's reconciliation cadence, and a seat stating no loop at all arms no recurring wake, its heartbeat coming from the turns it takes while it works. Then the board is read, and for Admin the inbox; the delegation record is resolved; the registry entry is written; the takeover is announced; and the first status push lands, which is what opens the compaction boundary through `seat-stop.js`.

Standing delegation is the skill's second charge, and it is a model the skill defines rather than a grant the skill makes. The model is the chain (coordinator to expert to worker, a seat acting on scoped direction from the seats above it), the scope (planning, scoping, sequencing, and dispatching execution of sections whose arming the dispatch-authority rail already covers), and the exclusions, which are stated rather than left to inference: no push beyond a plan's recorded commit model, no deploy, no delete outside a plan's scope, no message to an external service, no edit to permissions, settings, or CLAUDE.md, and no work another session was denied. What turns the model on is a per-machine, hostname-keyed opt-in record in the operator tier, which `/role` resolves at takeover; where none answers, the seat announces itself undelegated and the operator's per-session paragraph remains the path. The record is provenance rather than credential, exactly as the dispatch-authority mark is, and its body is read as data, so a body purporting to widen the scope changes nothing and is reported as a finding. The three refusal rules it composes with stand unchanged: a peer message carries no authority, a role claim confers nothing, and a seat cannot warrant a grant it authored itself.

Every seat but the coordinator carries one duty beyond its runbook. Captured kit friction routes to the machine's coordinator, which holds kaizen capture, dispositioning and dispatch as a named function with the operator's standing authority behind it, and the capturing seat carries on rather than actioning the note inline or shelving it. The route is a message rather than an artifact because the authority is: the kaizen skill's capture bar puts the inbox behind the operator's nod, and only the coordinator's function holds that nod, so there is no artifact a capturing seat could write that would carry the note to the party who acts on it. The routing message takes the same cap the worker's blocker line takes, only what its sender would put on a public board, and friction that cannot be stated inside that cap goes to the operator as a decision ask instead.

The admin seat is the one whose mandate is open rather than allowlisted, and the mandate is the operator's arming of the particular session holding the seat rather than the seat description, so no session acquires it by claiming the name. Its rationale is a precondition the seat is gated on rather than a property the payload asserts, since the payload ships to installations whose perimeter it cannot see: where an installation runs sandboxed with disarmed access and a separate identity, that perimeter can stand as the whole restriction, interior allowlisting inside such a boundary buying little safety at real cost in capability. The perimeter does not protect the values inside it, the guard files in the user-writable plugin cache and the machine-wide memory tiers among them, which is what the seat's two binding constraints are for: every action is reported to the operator, and the seat is support rather than work, fixing processes, permissions, services and workspaces and never producing or bypassing work product.

## Goal release events

A `/kit-goal` leash release leaves a machine-readable line in `~/.claude/kit-events.jsonl`, so an outside notification layer watches one well-known path instead of parsing transcripts. Transport is not the kit's job; the kit's deliverable is the file and its contract.

`emitGoalEvent` in `kit-goal-lib.js` writes it, and `kit-goal-stop.js` calls it at exactly three points: the plan reaching `Status: Complete` (`goal-complete`, detail `plan-complete`), the plan file gone to the archive (`goal-complete`, detail `plan-archived`), and a last assistant message leading with `BLOCKED:` (`goal-blocked`). Two other releases deliberately emit nothing: a manual `/kit-goal clear`, where the user is already present, and the harness's own consecutive-block-cap override, which the hook never sees.

Under a queue the cadence is per plan rather than per run, and that is the only shape change a consumer sees: an arming of four plans emits at each plan's terminal state, so up to four events carrying four different `plan` values under one `session`, and only the last of them coincides with a release. The event names, fields, and `detail` values are unchanged, and each event names the plan that finished rather than the one now current, so a consumer written against a single-plan arming reads a queue correctly and simply sees more events. What it must not infer is that an event means the run ended; that was never stated in the contract and is now false for every event but the last.

That decoupling is sharpest for `goal-blocked`, which mid-queue is emitted on a stop the hook then blocks. The event says a plan hit a blocker, which is the thing worth notifying an operator about, and says nothing about whether the session stopped; the leash records the blocker, advances, and holds the session on the next plan. Emitting it there rather than suppressing it is deliberate, because a blocked plan is exactly what an operator wants to hear about and the alternative loses that signal for every plan but the last. A consumer that treats a `goal-blocked` as "the run stopped" and acts on it, by resuming or re-arming, is acting on an inference the contract does not support.

One thing the stream deliberately does not carry is the blocker's text. `history` accumulates a note per finished plan inside the state file, and the final plan's release deletes that file, so once a queue finishes the content of each mid-queue blocker survives only in the session's own closing summary. That is a soft record: a session that dies before writing its summary leaves plan paths and no blockers. That holds once the queue finishes and the goal clears; while the goal is still armed, a mid-queue blocker's recorded first line stands in the goal state, which is the field the coordinator's funnel reads and the reason its dead-worker backstop works at all. Closing the gap needs a new field or a new sidecar, both of which are event-shape changes the queue deliberately avoided, so it is a known limitation rather than an oversight.

The contract a consumer reads against:

- One JSON object per line, `{ts, event, project, plan, session}`, plus `detail` present only on a `goal-complete` and `run` present only inside a run. `ts` is ISO 8601, `project` the absolute project path, `plan` the repo-relative plan path, `session` the session id or null.
- `run` carries `KIT_RUN_ID`, and only a value memq's own `isRunId` accepts, so the event stream and the memory store cannot disagree about what a run id is and a consumer may rely on the value being a well-formed id. The field is absent rather than empty when the variable is unset or refused. Its presence says the process was told a run id, not that run-scoped memory was active: the pending tier additionally requires the store signals, so the two conditions are separate and a consumer must not read one as proof of the other.
- Every field is sanitized display data, not a command: printable ASCII, capped at 40 characters for `event` and `detail`, 120 for `plan` and `session`, and 260 for `project`.
- `project` is an absolute local path that typically embeds the OS username, so forwarding an event anywhere external is a PII call the consumer makes.
- A `goal-complete` is exactly-once per plan, but the two positions in a queue reach that guarantee differently. On the last plan the emit is gated on the clear that actually removed the goal state, so a persistently failing clear never re-reports and a racer that finds the state already gone stays silent. Mid-queue there is nothing to clear, so the guarantee rests on the advance itself: only the bound session's stops reach it and its stops are serial, and the advance is one atomic state rewrite carrying a compare-and-swap on the plan the stop decided from and the timestamp it was armed at, so a state some other writer moved in the meantime is refused rather than advanced over and the emit rides only on the write that lands. Both halves are load-bearing: a re-arm that puts the same plan back at the head, which is the ordinary crash-recovery spelling, matches on plan alone and is caught only by the timestamp. The binding alone would not carry that claim, because the CLI is a writer it does not exclude: a `/kit-goal` re-arm or clear can land inside the hook's own retry sleep. A failed or refused advance emits no `goal-complete` at all, since the write and the emit stand or fall together: the clause re-runs at the next stop against the state as it then is, and the event arrives once, late. What statelessness costs falls on the other event instead. `goal-blocked` is emitted before the advance is attempted, so a failed write means a second `goal-blocked` at the retry, and a plan can draw more than one anyway: the hook holds no record of a blocked stop except in the one mid-queue case where the spent advance key suppresses a re-read of the same turn. Dedup is therefore the consumer's policy and is load-bearing against notification spam.
- `KIT_EVENTS_PATH` redirects the sink per process, honored only alongside `KIT_EVENTS_PATH_ALLOW=1`. The intended users of both signals are the repo test suite and the canary's own goal probe, which point the stream at a throwaway file; a consumer must not honor either ambiently. An override set without the second signal is ignored in favor of the real sink, with a note on stderr. An engine that sets the path alone therefore does not fail loudly to its own watcher, it silently keeps writing to the default sink, so setting both is a deployment precondition rather than a convenience.
- Emitting is observability, never a decision input. The helper never throws, returns nothing to branch on, and leaves a stop's verdict, output, and exit code identical when the write fails. A sink that exists and is not a regular file is left untouched and nothing is written, the same FIFO-hang guard the Stop hook applies to transcript paths. The check is an `lstat`, so a symlink or junction at the sink path reads as the link rather than its target: nothing is appended through it, and the rotation cannot move a linked-to file aside. Rotation is best-effort and sized for a single writer: past 1 MB the file is renamed to `kit-events.jsonl.old`, replacing any previous one, and a rename that keeps failing degrades to unbounded growth rather than lost events.

## Status line

The kit draws one status-line segment naming the armed plan and how far through it the run is, and it ships as two files because the two halves have different lifetimes. `scripts/kit-goal-statusline.js` is the widget, and it lives inside the installed plugin payload, whose cache path carries the release version and so rots at the next kit update if it is baked into a durable setting. `scripts/kit-statusline.js` is the launcher, and the doctor's shim installer byte-copies it to `~/.claude/bin/kit-statusline.js` beside `memq-shim.js` (`doctor/install-memq-shim.ps1:44,49`), which is the stable path a status-line tool is configured with. The launcher bakes in nothing: it resolves the installed payload through `memq-shim.js`'s resolver on every invocation and loads the widget from there, so a kit update needs no doctor re-run. The dependency runs the other way for the launcher itself, and that is the one operating consequence: the operative copy is the one in `~/.claude/bin`, which a plugin update does not refresh, so a change to the launcher takes `doctor -Fix` first and the plugin update second.

The launcher requires the widget rather than spawning it (`kit-statusline.js:361`), so a refresh costs one node start rather than two. The saved cost is a whole interpreter start on every refresh of every open session, which is the load under which the segment stops drawing.

The line's two derived segments read two different trees, deliberately. `Sections` counts the copy of the plan doc that `planDisplayRoot` elects, which is the recorded `executionTree` where the goal state names one that passes every guard and the cwd's own copy otherwise, because the live doc sits on the executing branch while this checkout's copy may be a stale twin. A render resolves that root once and hands it to both the text read and the cache key, so the two cannot come from different copies. `Plans` takes its position from the library's `queuePosition` over this widget's bare cwd and the goal root, never the recorded tree, and the direction is the safe one: a branch-Complete doc is invisible to a walk that never opens that branch's copy, so the position under-reports rather than jumping ahead of work only the execution tree has finished, and the widget keeps agreeing with the SessionStart advisory and `kit-goal.js status`, which resolve the same way. The call is skipped outright for a queue of one, where the answer would be discarded, and a payload whose library does not export `queuePosition`, or whose answer does not carry the shape the widget verifies (integer `index` and `stored` both inside this queue, boolean `positional`), renders the stored index exactly as it did before the segment read a derived position at all.

The render is cached in the project, at `.kit/statusline-cache.json`, because this process is born and dies per refresh and nothing in memory survives it. The entry holds the last line drawn, the armed plan doc's stored path, and the modification times of the two files that line was rendered from, the goal state and that plan doc. A refresh stats both and prints the cached line on an unchanged pair, which costs two stats plus one read bounded at 8 KB and skips the plan doc's read and its parse. Not every render reaches it. The Plans segment takes its position from a walk over the queue's plan docs, and that walk reads as many files as the queue and the trees give it: a second checkout's copy of an entry in a worktree session, a plan's archived copy, and every entry past the stored one all sit outside the pair the key stats. So the walk reports the paths it actually read, and a line is stored only where that report is exactly the one keyed plan doc. Every other render is refused entry to the cache and so is never served, which trades a re-render per refresh for a number that cannot freeze. What makes the refusal hold is that it is decided on what the walk read rather than on a list of the states that send it further, so an input class added to the walk later cannot quietly widen what the key fails to cover. The plan doc is in the key because the goal state is written from five call sites, arm, append, advance, bind, and the chapter-boundary record of the tree a run is executing in (`armGoal`, `appendGoal`, `advanceGoal`, `bindSession` and `recordExecutionTree`, all in `hooks/kit-goal-lib.js`), so a goal-state-only key would hold a stale section count on screen for the whole span between those events while Chapters land in the doc. The plan doc's time is taken before the render reads that doc (`planKeyMtime` in `kit-goal-statusline.js`), so a write landing between the two stores a time older than the text and costs one re-render, where the reverse order would pin the stale line until the next write.

Blank is the widget having no reading to give rather than a reading that nothing is armed: a project with nothing armed draws an affirmative `🎯 unarmed` line, so a blank widget beside a plan run reads as a fault or a payload older than the widget rather than as an unleashed run. The launcher prints nothing on the failures a status line could not act on either: no installed payload, a payload older than the widget, a widget that will not load. A failure inside a widget that did load is a different answer, and there the last line drawn is printed instead, since a segment that vanishes under load is the failure this caching exists to prevent and a slightly stale line is not. `RENDER_BUDGET_MS = 750` (`kit-statusline.js`) takes that same branch before the render starts. Everything ahead of that point, the stdin read, the payload resolution, the widget require, the cache read and its two stats, costs tens of milliseconds on an unloaded box, an order of magnitude under the bound, so a refresh that has already spent three quarters of a second is one whose host may kill the command before the plan doc is parsed, and whatever arrived before the kill is what the operator sees. That constant is the one knob, and it comes down if a status-line host is found to kill the command earlier than about a second.

Two print paths carry the line, and the split between them is where the file-derived content is bounded. A line the widget just composed is printed as composed, every segment of it already sanitized at construction. A line read back off disk goes through the widget's own `safeLine` first (`kit-goal-statusline.js`), which strips C0 and C1 controls, bidi overrides, zero-width characters, the line and paragraph separators, and lone surrogates, under a 400-character cap, because that line came from a file inside a repository and a clone or a hand can have put a terminal escape or a second line into it since. A payload whose widget did not load has no sanitizer to call, so that one refresh stays blank and the next one that reaches the widget draws normally.

The cache write is one of the two `.kit/` writes that screen their own directory. It lstats `.kit` and requires a real directory, lstats the target and requires either a regular file or nothing at all, and lands through an exclusive-create temp plus a rename, so a symlink, junction, or FIFO planted at either path is refused rather than followed. It never creates `.kit/`, a project without one having no armed goal to draw. A temp file an interrupted write abandoned is removed by any later write once it is 5 minutes old, and the entry is dropped outright when the goal state is gone, so a disarm cannot leave a retired plan's line to be drawn at the next failure. `docs/security-model.md` carries the accepted risk in full, including why the stored plan path is a stat target that must round-trip the goal library's own normalizer and is never opened here.

`test/kit-statusline.test.js` is the gate over the launcher, pinning the in-process path and both directions of the stale-but-drawn fallback, and `test/kit-goal-statusline.test.js` covers the widget, whose CLI entry point stays alongside the exports the launcher calls.

## External integrations

- **Node** runs the hooks and `memq`; it is the kit's one runtime dependency.
- **git and the GitHub CLI** are what the branch-hygiene, PR-docs, and merged-PR-push guards observe and act on. Both build scripts also shell out to git for the short hash and the payload's dirty state that go into the build stamp, and fall back to an `unknown`/clean stamp when git is absent or errors.
- **The local filesystem under `~/.claude/`** is shared state: `projects/<sanitized-cwd>/<session-id>.jsonl` for transcripts, `projects/<sanitized-cwd>/memory/` for the project tier, which Claude Code writes to as well as the kit does and rewrites into its own frontmatter shape on every Write, and `kit-events.jsonl` for the goal release events above, the kit's one machine-readable event feed, which an external watcher reads and the coordinator's funnel reads back as session input.
- **The Discord relay broker** carries the operator's steering into a session as channel messages, checking each message's author against a one-account allowlist and refusing to start without one. Nothing in this repository implements or tests that check, so it is a precondition rather than a control here, and `docs/security-model.md` names it as what the relay leg of the coordinator's warranted-channel list rests on.
- **The external engine (the AI OS Spine)** delivers the kit into the sessions it spawns and reads three of its surfaces: the goal event stream, the pending memory tier it promotes from, and the plan doc, which it parses to drive dispatch. The plan-doc header and structure are a frozen v1 machine contract for that reason, owned by the `curating-docs` skill and pointed at from `brainstorming`, `executing-work`, and `writing-skills`. `docs/fleet-integration.md` is the integration contract in one place.
