# Kit Architecture

The kit is a Claude Code plugin plus the repo material that maintains it. Almost all of it is prose: skills the model loads on demand, agent definitions, an output style the harness applies to every main-thread session, and a doctrine file that ships to the user's home directory. The exceptions are the pieces with real runtime behavior, and there are two: the Node hooks wired to session and tool events, and the `memq` CLI over the memory store.

That split is the thing to hold onto when changing anything here. Prose surfaces are behavior-shaping text whose general gate is the writing-skills RED/GREEN check; the hooks and the CLI are code with a real gate under `test/`. Two prose surfaces are the exception, for the same reason in both cases: the home doctrine and the output style each carry a copy of text whose source is elsewhere, so `test/doctrine-parity.test.js` and `test/output-style-parity.test.js` hold those copies byte-identical to it. Identity is not presence, and the doctrine gate covers both: its eight tests are one whole-body comparison plus seven assertions pinning individual rules present. What earns a rule its own pin is deferral. A bullet carrying its own content fails loudly when it is deleted, so a pin adds nothing, while a bullet that moves its operative content into a skill and keeps only a pointer can be deleted from both copies at once, pass the identity check, and leave the always-on layer silent with committed pointers aiming at nothing. Six bullets meet that test today: the memory-extension pointer, the standing-dispatch grant, the chapter-close checkpoint sentence, the two liveness bullets, and the outline bullet, whose pin has a far end as well, asserting that the style skills it routes to still carry a recipe and that the four surfaces restating the rule still say so.

## Repo layout

- **`plugins/claude-kit/`** is the installable payload, and the only zone an installed plugin loads. It holds `skills/` (20 skills, each a `SKILL.md` plus optional `references/`), `agents/` (three code reviewers and two document reviewers, implementers by model tier, the QA verifier, the docs curator, the design facilitator, the council member, the consultant; frontmatter pins a model where the role fixes one, and pins effort on eleven: `effort: medium` on implementer-sonnet, implementer-opus, the QA verifier and the docs curator, and `effort: high` on the three code reviewers, both document reviewers, implementer-fable, and the consultant, since judgment-heavy work is where deeper effort converts into signal and plan-following work is where it converts into tangents. Effort above a pinned default is chosen per dispatch, and the executing-work skill's reviewer-effort table owns that rule), `hooks/` (Node scripts plus `hooks.json`), `output-styles/` (one file, `kit.md`, the `Kit` style described under the always-on boundary below), `scripts/` (the `memq` CLI, its shim, and `memory-index.js`, which owns the optional embedding stack and the semantic index), and `doctor/` (the Windows first-run and repair tool, whose installers sit beside it one per repair; it has no destructive action, so `-Fix` never deletes).
- **`home/`** holds the two files that land in the user's home directory rather than loading from the plugin: `CLAUDE.md`, an import stub that pulls the doctrine in and carries any machine-local pointers, and `claude-kit-doctrine.md`, the doctrine body itself. The doctrine's single source is the `operating-instructions` skill: `doctrine-refresh.js` strips that skill's frontmatter and writes the body to `~/.claude/claude-kit-doctrine.md` each session, so the copy here must stay byte-identical to the skill's body or a session loads doctrine the repo does not show. What earns a place in that body is a separate question, answered by the always-on boundary below.
- **`docs/`** is the working library: about-the-solution documents at the root, active plans in `plans/`, finished history in `archive/`. It is not part of the payload.
- **`kaizen/`** is the kit's self-improvement inbox, one note per piece of observed kit friction.
- **`settings/settings.recommended.json`** is the recommended user settings shape.
- **`test/`** is the gate over every code surface, and it is the only place a runner reaches. The suite is `node --test test/*.test.js`, spelled with the glob rather than the bare directory. One flat file per surface, named `<surface>.test.js`, with no subdirectories and no `describe` blocks, so a run reporting `suites 0` is the mechanical proof that nothing nested. A test file living anywhere else is invoked by nothing, and its coverage exists on paper only.
- **`tools/`** holds repo-side utilities that do not ship: `transcript-study/`, the session-corpus analysis scripts.
- **`build.ps1`, `build.sh`, `.claude-plugin/marketplace.json`** package and publish the plugin. Both builders stamp `plugins/claude-kit/.claude-plugin/build-info.json` before collecting files, so the stamp ships inside the zip: the git short hash and a dirty flag `kit-version-nudge.js` reads, plus a `hooks` map of `<filename>: <sha256>` over every file in the packaged `hooks/` directory, which the canary compares the executing cache against. The stamp carries no wall clock, so a clean rebuild of the same commit stays byte-identical, and it is gitignored, so the copy in a working tree is only as fresh as the last local build. `build.sh` fails the build rather than stamping when it cannot produce a 64-character hash for a hook, because a partial manifest would make every install read as tampered.

## Always-on boundary

The doctrine is the prose the model carries into every task, so what lives in it is an architectural decision rather than an editorial one. It holds the rules that are general (true in any repo, not just the one that taught them), earned (the harness's own system prompt and tool descriptions do not already guarantee them), and needed before any skill has been loaded. Everything else lives in the skill that owns the moment the rule applies, and the doctrine points at it. The communication register is the one part of that always-on text carried on a second surface as well, and the register surfaces below say why.

Orchestration mechanics are the largest thing that boundary keeps out. `brainstorming` owns the model tier bands, which session model executes an approved spec, and the scout sweep that derives a section's files in scope from the tree wherever the design changes a contract or a shared surface; `executing-work` owns dispatch briefs, the orchestrator's own re-read of a plan's `Standing Brief Amendments` block at every section open (a grep rather than a read, because step 4 writes to that block mid-run and any earlier full-doc read is stale by construction, and the only delivery an inline section gets, having no brief for the entries to fold into), scout banding and the scout return contract, the serialize-what-cannot-be-shared rule, the stagger rule that advances concurrent sections offset rather than in lockstep, the interim board entry a closure drought earns, the route that sends a surface found outside a section's declared files to a fold, an appended section, or out of the plan, the moment a section's verified state commits under each commit model, the controller's gate, the review roster, which is two pairs rather than one (the code pair over a diff, and the document pair a section's `Audience:` line summons), the rule that runs every per-section reviewer one tier up from the section's writer tier without ever lifting a review past opus or pulling one below the writer's own tier, so a fable-tier section keeps fable pairs, with the security reviewer excepted from fable, and the reviewer-effort table that pairs an effort with whatever model that rule lands on. `finishing-work` owns the matching floor, and it is two states rather than one: fable at `high` by default, and a compensated re-dispatch at Opus and `max` where fable is unreachable. It also owns the wedge hallmark, the cross-class liveness predicate that decides when a dispatch of any class may be stopped for being quiet, with the per-class windows and the cadence it runs on; that predicate fires during execution rather than at the finish, and every surface naming it points at it rather than restating it: `executing-work` at its dispatch sites, `consult`, `brainstorming`, `standing-watch`, which writes the check into its tick order because a watch re-blocks on nothing for the cadence to fire on, the doctrine's two liveness bullets, and the README. The doctrine keeps the habit and the route (the file by path under the plugin root, the rule found by its bold lead, since finishing-work carries no heading for it) and no number of its own, because its audience includes sessions that never load that skill and a bare pointer would leave them holding a duty they cannot discharge. The hallmark leans back on the doctrine once, and the dependency runs the other way there: a zero-growth transcript reading is an absence-proving check, so it takes the positive control the doctrine's "Make the test earn its green" bullet requires of any check that proves an absence through a hand-authored pattern, path, or scope, and where no control can be run the instrument is unproven rather than the agent dead. `consult` owns the fresh-context end of the escalation ladder: the trigger floor that decides when a stuck session convenes the `consultant` agent, the brief that makes a consult work, the same fable-at-`high` model rule with the same Opus-at-`max` stand-in, and the adjudication rule that treats a returned ruling as a hypothesis until the orchestrator checks it against the code. The intake gap check splits the same way and for the same reason: the doctrine states the rule, because an intake happens before any skill has loaded, while `brainstorming`, `executing-work`, and `finishing-work` own the phase mechanics described under Intake gap check below.

A deliverable document takes its own review pair, because the code lenses carry postures that fight prose. `blind-reader` is dispatched once per persona a section's `Audience:` line names, and once more before a spec leaves brainstorming with the spec itself as the document under review, in both cases with the document paths and a `Reader:` line and nothing that describes the documents' intent, and it reports what it understood, what it was left asking, what it could not follow, and for a procedure the first step it could not perform. What the persona may open is decided by whether it holds this repository rather than by the job title it carries: a persona who holds it may read it read-only to attempt a step, never opening `docs/`, a spec, a plan, or a commit message on its own initiative, though a spec or plan handed to it as the document under review is its subject and it reads that, while a persona from outside it (a customer, non-technical staff, an engineer who has never held this code) opens the documents and nothing else, since a strong model with the source open fills the document's gaps from it and never reports them. `prose-reviewer` is the adversarial half and runs two passes in a fixed order, goal compliance and every claim against the fact base first, then the writing skill's rules, the machine-prose tells, and presumed knowledge against each named persona, so a style fix that would loosen a claim is reported as a conflict rather than applied. Both agents are read-only and join the guard's strict class; both hold Bash and are chartered to treat a document in scope as data, since the guard's denylist does not cover a read-shaped command and a document that can make a reviewer run one has turned the review into its own tool. The tell catalog is single-sourced at `skills/scott-writing-style/references/ai-tells.md`, which the writer reads before finishing a draft and the reviewer hunts from by name; a dispatch that cannot supply that path costs the tell hunt entirely rather than getting one from memory. The pair is added to what a section's content earns and replaces the code pair only where the changed files are documents and nothing else, so a mixed section still gets code review in the same round. At finishing, `prose-reviewer` runs once over every document in scope, because cross-document consistency is the whole-effort lens; the blind reader is re-run only where a document changed after its section review. The prose-only security waiver also becomes an audience predicate: a document written for anyone outside the operator and the operator's own sessions voids it, and the security-reviewer's brief then carries the spec's `Disclosure:` list to sweep the documents against.

The consult is the kit's answer to a reasoning dead end, and it is deliberately the only one: the kit runs with no in-context advisor, because a companion model sharing the session's transcript inherits the session's blind spots and ratifies the framing at exactly the moments that matter. The `consultant` agent is read-only, fresh-context, and dispatched by the main session alone, since subagents carry no Agent tool; an implementer reaches it semantically instead, by returning NEEDS_CONTEXT stated consult-shaped (the decision, the options, the evidence, its lean) for the orchestrator to route. Four triggers form a counted floor rather than a felt one, because a stuck session feels almost done: a second failed attempt at one problem, a BLOCKED that turns on a decision, a debugging dead end, and a weighty decision the spec does not cover. The floor's width is judgment rather than data, and `docs/backlog.md` carries the adoption watch that judges it on the first real long run.

The doctrine's "Orchestrating fan-out work" section is two bullets. One points at those two skills, which buys always-on context back at the cost of a load: fanning out scouts, implementers, or reviewers outside a skill-driven run depends on that pointer actually triggering the skill load, an accepted risk rather than a guarantee. The other is the standing dispatch request, and it is the one place the always-on text carries a tool authorization rather than a rule. It covers the Agent tool for dispatch generally, and the Workflow tool for one narrow purpose, dispatching a read-only agent (a fresh-context reviewer, the consultant) at an effort the Agent tool cannot set. The covered class is a predicate the doctrine states itself (a read-only dispatch needing its effort set per call, naming an `agentType` the read-only guard governs) rather than a reference to what the skills say, because a skill that defined the class would be granting itself a permission the doctrine scopes; the skills say where and how and cannot widen it. The grant lapses on its own terms if the Agent tool ever gains a per-dispatch effort parameter.

One further Workflow authorization sits outside that class and outside the doctrine entirely, in `/kit-goal` arming. The arming invocation is user-typed, so it carries the operator's own request for that run: reduce wall-clock time by parallelizing whatever the sections and their gates allow, through subagent dispatch and through Workflows. Its authority is the arming act rather than any skill's text, its scope is executing the armed plan and nothing wider, and the canonical condition text `kit-goal-lib.js` composes carries the request, so it rides with the goal state across a session swap and the Stop hook restates it at the point of action.

Project-specific rules are kept out the same way. A product's honesty and privacy gates, its identity and framing constraints, and its test-suite naming live in that project's own `CLAUDE.md`, next to the gate tests that enforce them. The doctrine keeps only the general form: nothing untrue ships, and where a project defines honesty or privacy gates, a violation is a defect to sweep the whole tree for. The same rule sends .NET lessons to `csharp-style` and the capture bar to `kaizen` rather than into the always-on text.

Language-scoped knowledge splits on that seam too, and the outline-first reading rule is the sharpest instance of it. The doctrine states the principle, that a file past roughly 1,000 lines you are opening to find one thing is grepped for declarations and section labels before any range of it is read, along with the two guardrails that fail quietly (an outline never proves absence, so a symbol not found in one still earns a whole-file search, and an `<auto-generated>` header means grepping for the member by name instead). It carries no patterns. Those live in `csharp-style` and `sql-style`, each of which gained an Outlining section holding a recipe verified against a real file, because a language-agnostic surface cannot hold the house idioms a generic pattern misses: T-SQL's leading-semicolon `;ALTER PROCEDURE` deployment form and the banner comment whose label sits on the line after its border, C#'s `#region` organization and the interface whose members carry no access modifier for a member grep to anchor on. For a language no style skill covers, the bullet says to compose that language's own declaration and section markers on the spot, and no JS or TS anchors ship at all, the kit having no JS house style with the standing to own them. The trigger is the hunt rather than the size: a file whose whole content is the point is read whole, which is what keeps the rule from colliding with the two committed read-in-full mandates the kit already carries, `executing-work`'s post-compaction plan-doc read and the blind reviewer's charter.

Mode-specific rules are kept out on the same test, and `standing-watch` is the case that names the mode. A session watching a live system it does not own, waking on a timer or an operator message, re-deriving the board, intervening, writing a ledger and sleeping again, carries failure modes no other work has, so the ledger's standing-versus-situational split, the tick order that arms the wake before it checks anything, the wake prompt that carries prohibitions and never a situation report, the ping's evidence line, and the one-way-door preflight all live in that skill and load only when a watch is running. The doctrine keeps from that same material only what is true of any session whether or not it is watching anything: probe a dispatched agent before killing it, read one heavy process at a time as a per-machine limit, take a background run's exit from a marker it wrote itself, answer "cannot measure" when the source that would answer is down, and ask, in the Before-you-send list, whether every figure or state names the source it came from and the subject it is about. That last one sits inside the register core, so it reaches the output style as well as both doctrine copies; the four bullets live in the doctrine copies alone.

### Intake gap check

Every input the kit takes in gets its gaps enumerated before anything is built on it, and the doctrine carries that rule because an intake precedes any skill load. At an intake (a prompt, a handoff, a spec, a dispatch brief) the session lists what the input does not state, then routes each gap three ways: (a) one an existing source answers (doctrine, memory, the plan doc, the code's own conventions, a house style) is resolved with the source cited; (b) a low-blast, reversible one with a conventional default is decided and declared; (c) a material one that is the operator's to make is asked, batched, with a recommendation. The first two routes produce declared assumptions and the third produces a question. Enumeration is a step rather than a habit because a model fills gaps silently and cannot see the ones it filled, which is the same reason brainstorming's self-review ends in a blind read rather than a second inline pass.

A declared assumption is never left only in a document, because the operator approves plans from the recap without reading the doc. Three surfaces carry it, one per phase. During brainstorming it rides the plan sketch and every later recap the operator approves, as its own `Assumptions` block, and a recap that omits the block has not shown the plan. During execution a material gap the spec does not cover is a `BLOCKED:` on an armed run or a decision ask on an attended one. At close-out the finishing status lists every execution-time entry verbatim, which is what reaches a run the operator walked away from, since under a leash that status is the closing message the `goal-complete` event points at.

The durable record is split in two by the external engine's approval-scoped fingerprint, which covers everything above `## Chapters`. The plan doc's `## Assumptions` section holds the design-time entries and freezes at approval, because a routine mid-run append there would mutate the fingerprinted region and read as approval drift; a deliberate spec amendment above that line is still made when the design changes and is recorded in a Chapter as the drift it is. Everything execution adds rides the Chapter's own `Assumptions:` line, which is append-only and below the boundary. One line format serves both, instanced normatively in brainstorming's spec template:

`- assumed YYYY-MM-DD (<route: a source name | default>): <the assumption>; reversal: <what changing it costs>`

with `, section N` added inside the parenthetical for an execution-time entry. The close-out block is computed from the Chapters rather than by dating entries against `## Assumptions`: no approval date is recorded anywhere, the entries carry day precision, and a plan approved and run the same day is the ordinary case, so a dated filter would report `none` on exactly the walked-away run the block exists to serve. An empty block says `none`, so silence is a stated fact rather than an omission.

Three skills instance the rule at the moments it applies. `brainstorming` carries it into the design conversation: its one-question-at-a-time rule is how route (c) is asked there, its sketch and recaps carry the `Assumptions` block, its spec template holds the `## Assumptions` section (inert to the plan-doc parser and required to stay outside `## Sections of Work`, whose block any foreign `##` heading ends early), and its self-review closes by dispatching `blind-reader` on the spec itself, adjudicating each returned question three ways (answer it in the spec, declare it as an assumption, or put it to the operator with a recommendation) and recording `blind read: <n> questions, <a> answered, <b> assumed, <c> asked` in the handoff recap. That costs one dispatch per spec, and a trivial spec of one or two sections may skip it, saying so. `executing-work` runs the check on the plan doc: it lists what each section leaves unstated during the plan-doc read and routes after `memq recall`, since memory is one of the sources a gap routes to, so a non-material gap is resolved before its section is dispatched and the brief carries the answer rather than the gap. Its implementer-status handling reads a `DONE_WITH_CONCERNS` "spec ambiguity you resolved" concern as a route (b) assumption bound for the Chapter line, while a concern that reads as material re-routes to `NEEDS_CONTEXT`. `finishing-work` step 5 delivers the close-out block and rides the same block on the finishing Chapter.

### Register surfaces

The communication register reaches the model on three copies of one text, and the copies exist because no single surface covers every session. `plugins/claude-kit/skills/operating-instructions/SKILL.md` is the source. `home/claude-kit-doctrine.md` is the mirror `doctrine-refresh.js` writes to the user's home directory, which the home `CLAUDE.md` imports and every subagent therefore inherits. `plugins/claude-kit/output-styles/kit.md` is the third: a Claude Code output style whose marked region carries a subset of the doctrine, the register core, byte-identical.

Coverage and lateness are the two properties no single surface has. CLAUDE.md prose reaches subagents and survives the triggers that deactivate a style (a plugin update lag, an older harness ignoring the force flag, a non-Code surface, safe mode disabling non-builtin styles, and a future deprecation of the feature itself), but it fades as a session grows. An output style rides the system prompt and is re-asserted after tool results, so it binds at turn 200 where the imported prose does not, and it reaches the session's own thread only: subagents never receive it. Holding one text on both surfaces is what buys both properties, and it is why the core is a copy rather than a pointer, since a subagent handed a pointer to style content cannot load it.

The core is seven bullets (`Skip the preamble`, `Disagree up front`, `No false certainty, no flattery`, `Teach the why; treat design as a dialog`, `Write every decision ask to the client-briefing register`, `Narrate the cadence, and close with the state`, `Close with the board when plans are pending`) plus the doctrine's whole `## Before you send` section. Bullets ride whole rather than split at the sentence, because a half-bullet on one surface and its other half on the other is paraphrase adjacency no test can pin. The style's own shell (the reader definition, the teaching posture, and the ★ Insight, ⚖ Decision, and ✎ Memory block mechanics) deliberately never enters the doctrine: subagents inherit the doctrine, and block mechanics in a worker's context would reshape the reports it returns.

Four frontmatter keys are the harness contract, and two of them are load-bearing beyond tidiness. `name: Kit` and a double-quoted `description` identify the style; `keep-coding-instructions: true` is what keeps Claude Code's built-in software-engineering instructions in a kit session, which the style otherwise silently removes; and `force-for-plugin: true` is what activates the style wherever the plugin is enabled, over a machine's own `outputStyle` setting. Rollback is removing that one flag, and safe mode is the always-available escape hatch.

`test/output-style-parity.test.js` is the gate over all of it, in 11 named tests. It pins the frontmatter as a closed set of exactly those four keys, each declared exactly once (YAML is last-key-wins, so a first-match read would accept a `true` followed by a `false`) with the two flags matched against the raw bare token `true`, since a quoted `"true"` is a string to a type-strict reader. It then locates each core bullet by its lead in both doctrine copies and in the style's region, requires exactly one hit in each, and compares bytes; compares the Before-you-send segment from its header to end of body across all three; and pins the region as a closed set, the seven bullets in spec order, then Before-you-send, then nothing but blank lines, so a paraphrased paragraph cannot sit alongside content that passes. The doctrine copies carry no markers of their own, which is why extraction is by lead, and the sync direction is skill to mirror to style core. One consequence lands on whoever edits the doctrine: a new section appended after `## Before you send` fails this test, and the fix is a deliberate call about where the core's boundary now sits rather than a widening of the compared segment.

## Hooks

`plugins/claude-kit/hooks/hooks.json` is the wiring, and every hook is a Node script invoked with the plugin root. The events in use:

- **SessionStart** runs `session-start.js` (six blocks: the compact-source re-load instruction, resume surfacing, unarchived-plan flagging, the kit-repo kaizen nudge, the armed-goal notice, and the backlog block described below), `branch-reaper-nudge.js`, `kit-version-nudge.js`, `doctrine-refresh.js`, `hook-canary.js`, and `memory-session.js` (the memory index emission described under the memory store below). Matchers differ per hook: the doctrine refresh also fires on `clear`, and `branch-reaper-nudge.js` and `hook-canary.js` skip the `compact` entry, the canary because a plugin cache cannot change mid-session. `session-start.js` firing on `compact` is what makes a compacted session re-read its plan doc, so it is the recovery path the kit relies on; on that source it also leads with a re-load block, emitted whether or not a plan is in progress, because a compaction keeps the doctrine and this hook's output but drops what tool calls had loaded (skill bodies, deferred tool schemas), and a session left to run a summarized skill executes the half the summary kept. Under `KIT_EXTERNAL_ENGINE=1`, the marker an external engine sets on every worker it spawns, four of these stand down: `session-start.js` omits its drive-to-completion push (it still lists each In Progress plan's path and commit model, followed by one line stating that the engine's own directive owns scope and continuation), `hook-canary.js` exits before spawning anything, and `branch-reaper-nudge.js` and `kit-version-nudge.js` emit nothing. The three nudges ask for an attended operator's action a headless worker cannot take, and the canary's sweep is serial child spawns whose report has no reader there, fleet payload integrity being the deploy's concern. `doctrine-refresh.js` and `memory-session.js` stay live: doctrine and memory wiring are wanted inside a worker.
- **PreToolUse** runs five hooks: `docs-write-guard.js` on write-shaped tools, `pr-docs-guard.js`, `merged-pr-push-guard.js`, and `readonly-agent-guard.js` on shell tools, and `memq-grant.js` on the Bash tool alone. `readonly-agent-guard.js` keys on the calling agent's type and governs two classes: the eight judgment agents (the three code reviewers, the two document reviewers, the council member, the design facilitator, and the consultant), for whom the repo tree is read-only, and `qa-verifier`, which may write and delete inside the build-output directories its suites need but nowhere else. Both lose git and GitHub state changes, formatters, and the package-manager verbs that rewrite a lockfile or a tracked project file; reads, builds, and test runs stay untouched for both, and `.kit/` is writable scratch. The four guards are fail-open denylists, blocking only the shapes they name and allowing anything they cannot positively judge, so the `git status --porcelain` comparison that executing-work and finishing-work run around each review round is the backstop for what the heuristics miss; the mutations no tree comparison can see, an outward `gh` call or a ref creation that leaves the worktree byte-identical, are on the denylist for exactly that reason.
- **PostToolUse** runs three hooks. `format-on-edit.js` runs CSharpier over edited `.cs` files. `memory-usage-stamp.js` records a `read` stamp when the Read tool opens a memory file of any of the three tiers. `chapter-boundary-nudge.js` closes the checkpoint system's one-way loop: it fires when the session bound to an armed kit goal adds a `### Chapter` heading to the armed plan's own doc, matched by path rather than to any doc under `docs/plans/`, because the reminder opens by asserting that a boundary was reached and that assertion is false on a sibling plan; and it puts a fixed reminder of the executing-work boundary steps (the memory sweep, then the checkpoint open, once the section's commit model has been honored) in front of the model. Added means a Chapter number present in an edit's `new_string` and absent from its `old_string`, not a heading present anywhere in the new text: a real append anchors its `old_string` on the document's tail, which past the first boundary already carries the previous Chapter's heading, so a presence test would go silent on the one shape the hook exists to catch. A whole-file `Write` has no pre-image to diff, so any heading in its content fires it. It reaches the model through the nested `hookSpecificOutput.additionalContext` JSON form, because the top-level `additionalContext` key the hooks documentation shows is inert on this harness. It is a detector plus a directive rather than an auto-open, since the checkpoint belongs after the section's commit and an auto-open at the Chapter append would admit a compaction between the Chapter write and its commit, the mid-boundary landing the gate exists to prevent. It stands down for a subagent's tool call on the payload's agent keys, `agent_id` plus the four `agent_type` spellings the kit's sibling detectors defend, rather than on the session id, because a subagent's payload carries the parent session's own id and the bound-session check alone would pass one; it stands down under `KIT_EXTERNAL_ENGINE=1`; and every guard and every internal error exits 0 silently, so a missed nudge degrades to the pre-hook status quo rather than to a broken edit loop.
- **PreCompact** runs `kit-compact-gate.js` on the `auto` matcher alone, the scheduler that lands native auto-compaction at the boundaries a plan run declares instead of wherever context happens to fill. A boundary is ordinarily a section's close, and where a run goes long enough with work in flight and no section closing, it is an interim board entry written to the plan doc and put through the run's commit model, so a drought between closes still leaves the gate somewhere safe to land. `executing-work` owns both moments and the drought's trigger, and opens the checkpoint the gate reads. Nothing can raise a compaction on demand, so the gate works the only lever there is: it vetoes one. A denied auto attempt is re-offered once per assistant turn, indefinitely, which is what turns a veto into a schedule. It reaches a three-state verdict, evaluated cheapest first. Two preconditions come first and allow outright when either fails: the trigger must be `auto`, and `KIT_EXTERNAL_ENGINE=1` must be absent (an engine's workers are fresh per section and have no mid-chapter context to protect). Past those, an armed kit goal whose leash this session holds takes the **boundary-gated** path, denying while no boundary checkpoint is open and consumption read from the transcript is legibly below a safety ceiling. An armed goal no session has yet claimed is decided by the same claim proof the leash uses, one predicate in `kit-compact-lib.js` that this gate and `kit-goal-stop.js` both call: a transcript showing the user typing the arming command claims the binding and takes the boundary-gated path, and one that does not leaves the session a bystander on the interactive path. An in-session arm binds at arm time and reaches the gate already bound, so what this claim point serves is the narrower population the arm CLI could not bind: an arm whose session id was absent or matched no transcript on this machine, and an arm run outside any session. For that population, claiming here rather than only at a stop is what makes the gate reachable on a well-behaved run, since the completion contract forbids stopping while unblocked work remains, so a run that never stops would otherwise stay unbound and ungated for its whole length. The claim's write is best-effort and the verdict does not wait on it, matching the leash's own posture that enforcement never depends on the write: a `.kit/` that refuses the write leaves the run deferring to the safety ceiling, which is where a refused checkpoint write leaves it anyway. One visible consequence of claiming late: a checkpoint opened while the goal was still unbound records no bound session and so does not match the session that has just claimed the binding, so that offer defers one more chapter and the next checkpoint, written bound, opens the gate. An armed goal beside a payload carrying no usable session id still allows outright rather than taking either denying path, since no binding could be written from it and no comparison made with it. Every other session, meaning no goal is armed for the project or an armed one belongs to a different session, takes the **interactive** path, which asks the transcript a different question: whether a native automation instrument is driving this session. When `/goal` or `/loop` is in effect the gate allows, because an automated run is better served compacting early at the native trigger than deferring; otherwise it denies to the same safety ceiling, so a hands-on session keeps its full context through the long middle of a working stretch instead of being compacted at the early trigger the armed path needs. Every other state, every read error, every ambiguity allows, so a forgotten checkpoint or a misread transcript degrades to compaction landing at the native trigger, the behavior before the gate existed, and never to a wedged run.

Automation detection reads the transcript for shapes the harness writes but does not document, which is why every misread is built to land on allow. Native `/goal` is read from two surfaces: the `goal_status` attachment the goal system writes at arming and at each stop evaluation, whose `met` field distinguishes a running goal from one that completed and auto-cleared, and the user-typed command markup, whose `clear` argument retires it. `/loop` is read from its own user-typed command markup, retired by the terminating `ScheduleWakeup` whose input carries `stop: true`. Both are ordered signals and the newest match decides, so a finished goal or a stopped loop returns the session to the interactive deferral rather than leaving it classified as automated forever. The reader takes a capped head-plus-tail slice of the transcript, because `/loop` evidence sits at the head where the command was typed while goal status lands in the tail, and it excludes tool results, meta entries, compaction summaries, and sidechain rows, since the literal command markup travels freely inside quoted file content and agent output. That exclusion is load-bearing rather than defensive: this repo's own plan docs and hook sources quote the markup, so reading them plants it in the reading session's transcript. Manual `/compact` is never gated, checked in code as well as by the matcher so a later wiring edit cannot silently widen it. The boundary signal is `.kit/compact-checkpoint.json`, written by `kit-compact-checkpoint.js` at either executing-work boundary, a section's close or an interim board entry, and recording both the armed plan and the session bound to it, and rewritten by `kit-goal-stop.js` when a queue advance moves the current plan out from under an open one; the gate consumes it when it allows, so one checkpoint lands exactly one compaction, and a checkpoint naming another plan or another session reads as absent so a crash-orphaned file cannot open the gate. The valve is the failure mode nothing else caps: sustained denial with a chapter that never closes would climb to the model's hard limit, where a session dies outright on an over-length prompt, so at or above the ceiling the gate allows regardless. One ceiling serves both denying paths, an absolute token count sized for the roughly 1,000,000-token window the models running these sessions carry, because the PreCompact payload provides no `model` field to derive the real one. That assumption is the one direction of this design that is not fail-open: on a model whose window fell between the trigger and the ceiling, the valve would never fire. It is bounded by what the gate can actually do, which is veto an offer the harness has already made, so a model whose window is too small to reach the trigger is never offered a compaction to defer. The consumption it compares against is read from the newest assistant `usage` block, taking the largest entry of that block's `iterations` array when one is present, because a multi-iteration turn's top-level cache figures are summed across iterations and describe no single request. Largest rather than last, because the two errors are not symmetric: understating consumption defers longer and walks a session toward the hard limit the valve exists to keep it away from, while overstating it only ends a deferral early. Nothing detects that state, and the doctor's auto-compaction-window check is not it. That check reads the configured window, which says nothing about the running model's real one; what it catches is the opposite and safer failure, a window configured so high that the trigger lands at or above the ceiling, where the valve allows everything and the gate defers nothing. `docs/security-model.md` carries the assumption and what does and does not cover it.

The boundary signal carries its own staleness bound, because a checkpoint that outlives its boundary is how this feature would quietly become a no-op. A boundary is often reached below the trigger, where there is no pending offer to catch, so without a bound that checkpoint would sit open and admit the next offer, which arrives mid-chapter. The gate therefore treats a checkpoint older than a short window as absent. The asymmetry that makes a time bound work: past the trigger the harness re-offers every turn, so a checkpoint opened at a real boundary is used within seconds, while one opened below the trigger simply ages out. The executing-work ritual also clears the checkpoint when the next section starts, so the two guards are independent. That clear runs only at a section start, so the expiry is the sole bound on a checkpoint opened at an interim board entry, where by definition no section is closing and none is about to start. The kit summarizes nothing itself: the native summarizer runs unmodified and re-grounding afterward is the existing `session-start.js` `compact` path.

A denied auto attempt also leaves the operator a note on stderr, and that note is the operator's only diagnostic, since PreCompact stderr never reaches the model. It names both boundary kinds (a chapter close or an interim board entry), states the hold as running to that boundary or to the safety valve near the token limit, says that repeating for many turns inside one section is expected, and names the one state that is not expected: still firing after a Chapter has closed, which means the checkpoint was likely never opened. The remedy it prints is a runnable `node "<path>" status` and `node "<path>" open`, the path composed from the hook's own installed directory rather than written repo-relative, because the gate runs in every project on the machine and a repo-relative spelling resolves only inside the kit's own checkout. The `open` carries an at-a-true-boundary qualifier, since opening one mid-section is what executing-work forbids.

Operating the gate is one CLI and one setting. `kit-compact-checkpoint.js` carries three subcommands: `open` writes a checkpoint for the armed plan and the session currently bound to it, and refuses when no goal is armed, since a checkpoint naming no plan could never match; `clear` removes one, which is what executing-work runs at the start of each section; and `status` reports whether a checkpoint is open and, where the gate would read it as absent, which clause failed, answering from the same match rule the gate itself decides by so the report cannot drift from the verdict. The setting is `autoCompactWindow` in the user's `settings.json`, and it is what gives the gate something to schedule, since the gate can only defer an offer and never raise one. The doctor reports the configured value, recommends one sized so the trigger leaves a band wide enough for a chapter to close before the valve fires, warns when a configured value leaves that band too thin, reports a configured value that differs from the recommendation so a machine already carrying one still learns of a new figure, and writes the value only behind an explicit `-Fix` consent prompt. Two write cases, and they take different consent. Supplying an absent value is what `-Fix -Yes` is for, since it converges: run it twice and the result is the same, and nothing the operator chose is lost. Replacing a value the operator did choose is withheld from `-Yes` and waits for an interactive answer, because an unattended run cannot tell a deliberate setting from a stale one, so it would revert the deliberate one, and would do so again after every retune of the recommendation it compares against. It reads the ceiling out of the hook source rather than restating it, and says so when it cannot, because a silent skip reads exactly like a healthy result.
- **Stop** runs `stop-docs-hygiene.js` and `kit-goal-stop.js`, the deterministic leash that holds a `/kit-goal` run to completion. Its state is a file in the project (`.kit/goal-state.json`) that no session boundary deletes, and the hook enforces on session identity: native compaction preserves the session id, so an armed run keeps its leash across its own auto-compactions, while a session the hook cannot tie to the bound one is a bystander whose stop is allowed, and re-arming is the recovery. An arming may name several plans, in which case the state carries the ordered queue and a plan's terminal state advances the leash to the next plan rather than releasing the session; only the last plan releases. A `BLOCKED:` advance is keyed to the transcript entry that produced it, recorded in the state as `blockedAdvanceKey`, because the hook's read of the last assistant turn races the harness's append of it and a lead read twice would otherwise consume two queue positions off one blocker. The key rides with `blockedAdvancePlan`, the plan the advance moved to, and is retired by position rather than by deletion: it is honored while that plan is the current or the immediately previous queue position and ignored past that. Retiring rather than deleting is what stops an intervening advance, a plan behind the leash turning up Complete, from resurrecting a blocker the queue already consumed, while retiring at all keeps a stale key from widening the one collision surface the text-digest fallback has. A key with no recorded plan, which is what an older state file carries, is honored wherever it matches, since the failure direction there is holding rather than advancing. A lead whose key is already spent falls through to the ordinary hold: it never advances, never emits, and never releases. An advance also rewrites an open compaction checkpoint to the new plan, since the checkpoint is matched against the goal's current plan and a plan's own close-out opens one immediately before the stop that advances. The queue fields are strictly additive, with `plan` continuing to name the current plan and `boundSession` the leash holder, which is what lets the compaction gate read a queue-armed state with no knowledge of queues at all. One binding rides the whole sequence, and the SessionStart armed-goal notice reads that binding back rather than announcing the arming undifferentiated: the leash holder is told the leash is its own and where the queue stands, a bystander is told the leash belongs to another session and that the plan is not its business, with the re-arm path for a run that has died and a liveness hint taken from the bound session's recorded transcript mtime (a number and a unit reach the notice, never the path), and an arming no session has claimed keeps the claimable framing, naming both points the arming session claims at, its first stop and its first auto-compaction offer, whichever lands first. A bound goal beside a payload carrying no session id is distinguishable from neither, so it degrades to the undifferentiated notice rather than risk telling the leash holder that its own plan belongs to somebody else. The doctor reads the same file for its armed-goal report, and reads it defensively rather than through the library's normalizer, because a hand edit is the case it exists to catch: it names the queue position and the remainder, discards a queue disagreeing with `plan` in favour of the single-plan reading, and splits what used to be one warning in two, since a terminal current plan means opposite things at the two positions. With plans remaining it is a stalled advance, normal mid-turn because the hook advances at the bound session's next stop, and otherwise a dead run to re-arm the remainder over; on the last plan it is the old stale goal, to clear. A separate exposure check runs alongside it, and deliberately outside the clone gate the report sits behind, because a queue makes the file's payload several times the size a single plan gave it and every armed session's start notice reads it back: it asks git whether the state file under the directory the doctor was launched from is tracked, ignored, or neither, and warns on the first two of those with the command that fixes them. Scoping it to the launch directory rather than to the kit's own checkout is what makes it reach a consuming project at all, since the kit's checkout already ignores `.kit/`. It detects the exposure without preventing it. Its three emit points also append to the goal event stream described below. Under `KIT_EXTERNAL_ENGINE=1`, `stop-docs-hygiene.js`'s blocking outcome becomes advisory text carrying no decision, so the stop is allowed: holding a headless worker at its turn end for a library-hygiene pass its directive does not cover trades a tidy `docs/` tree for a stuck run. `kit-goal-stop.js` does not read the marker, and does not need to: it binds to one session, bound at arm time when the arming CLI can corroborate its own session id against a transcript on disk, and otherwise claimed only by the user's own arming text (a plan path typed as a slash-command argument, or a message leading with the `/kit-goal` token whose argument block names the plan), so a worker whose directive merely names the plan is a bystander it never leashes. Three of its four block reasons carry the boundary ritual as well as the hold: the ordinary hold, the capacity-shaped refusal, and the queue advance each tell a session that has closed a Chapter since the last boundary to load executing-work if it is not loaded and, once the section's commit model has been honored, run the memory sweep and open the checkpoint, naming the gate's two bounds (a matching checkpoint, or the safety valve near the context limit) rather than an unbounded hold. The reason for a stop already spent carries none of it, because it fires only where the last assistant turn is an already-consumed transcript entry, so no Chapter can have closed since. This is the model-facing half of what the compaction gate's stderr note cannot say, that note reaching the operator alone.

The fifth PreToolUse hook runs the other way and is the kit's only hook that allows rather than denies. Under the external engine's write-gated spawn vector the Bash tool refuses `node <script>` outright, which would cost a fleet worker the memq CLI, so `memq-grant.js` emits an allow decision for exactly one command shape: one `node` invocation whose first argument resolves by normalized path equality to this plugin's own `scripts/memq.js`, with the fleet-store signals present, a positively identified interpreter, no module-preload environment variable set, no shell metacharacter anywhere in the command line, a subcommand the hook's own list of granted verbs names, and none of the four withheld flag shapes among its words. On anything else it emits no decision and the call falls through to the host's normal permission flow, so its safe failure is silence rather than the guards' fail-open allow. `docs/security-model.md` carries the invariant in full, the accepted risks, and what the grant does and does not contain; `docs/fleet-integration.md` carries the engine-side preconditions it depends on.

### The canary

`hook-canary.js` is the one hook whose subject is the other hooks. Every kit hook fails open, so a stale or damaged plugin cache, a hook file that no longer parses, or a guard gone inert takes the enforcement away with no signal at all. The canary probes the cache a session actually executes (`CLAUDE_PLUGIN_ROOT`) and speaks only when something about it is positively broken.

Three probe classes run over that cache. **Load checks** cover every hook named in `hooks.json`: each named file is present and `node --check` parses it. **Known-answer behavior probes** run in both directions, so a guard that answers everything the same way cannot read as healthy: a governed subagent writing a `docs/` path must deny while a main session writing the same path must allow, a read-only subagent's `git commit` must deny while its `git diff` must allow, and a throwaway fixture holding an armed goal must draw a block from `kit-goal-stop.js` while a directory with no goal armed draws nothing. `memq-grant.js` takes six probes on Windows and five elsewhere, one allowing and the rest withholding. The allowing one is the single invocation the grant covers, which must produce an allow decision. The withholding ones each aim at a screen the allow probe cannot see the loss of: a metacharacter-carrying near-miss, a `--body-file` value, a `--rollup`, `find` in the verb position, and, on Windows only, the Git-Bash `/d/` spelling of the script path, that rewrite being what the refusal there is about. Both directions run for the same reason as the guards and one more: a deny guard gone inert eventually shows up as something unexpectedly permitted, while a grant gone inert never announces itself, because a fleet worker simply loses memq. The withheld shapes divide by what stands behind them, and the probes follow that division rather than the shape count: `--body-file` and a body-carrying `--update` are refused by the CLI as well, so a hook that lost one of those screens is one lock short and the second of them rides the first's probe, while `--rollup` and `find` are withheld at the hook alone and a hook that lost either is open with nothing else to say so. Its probe environment is constructed rather than inherited, with PATH pinned to the canary's own interpreter directory and every other variable dropped unless a short keep list names it, so ambient machine state cannot fail it. Building it from that list rather than subtracting known-bad names from the inherited environment is what lets the canary need no knowledge of what any hook refuses on. `merged-pr-push-guard.js` and `pr-docs-guard.js` get a load check plus a benign-payload plumbing probe only, because their deny paths need external state (a MERGED pull request, a dirty checkout off the default branch); the repo suite owns their behavior. The goal probe runs against a temp directory with the event sink and the re-read delays pinned away from real machine state. Those two classes are a few dozen serial spawns on the current wiring, one load check per hook `hooks.json` names plus one per behavior probe. The bound is per child at 5 seconds rather than per phase, so a healthy cache costs under a second in total while a cache where every grant probe hangs costs about 35 seconds of it; `docs/backlog.md` carries the whole-phase budget that would cap the failure case. **The integrity check** spawns nothing: it only reads and hashes files, so it is free against that budget.

Integrity is the class that sees a hook whose bytes changed after packaging, which parsing and behavior probes cannot: the plugin cache is writable by the principal a session runs as, and a guard edited in place enforces whatever it now says. The check re-hashes every file the build's `hooks` map names, from the executing cache, and reports a mismatch as bytes that are not the ones the build packaged, pointing at a reinstall or update. A manifest entry with no file on disk reports as missing from the build; any other read error (a lock, a scanner holding the file open) stays silent, because it says nothing about the file's contents. The check runs last and skips a file another probe already flagged, so a wholesale-different cache cannot fill the report's line cap ahead of a guard that is present, parses, and is positively answering wrong. An absent stamp, an unparseable one, or one with no `hooks` key is silent: an older build gives the check no basis, and a cache it cannot describe is never called tampered.

Its coverage is wider than the load check's in one direction and bounded in another. The build hashes the whole packaged `hooks/` directory while the load check enumerates `hooks.json`, so `kit-goal-lib.js` (required by `kit-goal-stop.js`, named by no command string) and `kit-goal.js` are covered here and nowhere else; `hooks.json` itself is in the map, because rewiring a guard out of the wiring disarms it exactly as editing the guard does; and `scripts/`, `doctor/`, and `output-styles/` ship in the same cache outside the manifest. The manifest also lives inside the cache it attests, so deleting the stamp silences the check and rewriting stamp and payload together defeats it. `docs/security-model.md` carries what that detection buys against the threat it is sized for.

A failure writes one warning into the session context naming each failed probe with its expected and actual answer, capped at 10 lines plus a count of the remainder, and points at `/kit-doctor` and a reinstall. Which repair to run is legible from the line: a load-check or wiring failure means a partial or damaged install, where reinstalling and restarting the session is the fix, while an integrity line means the installed file is not the one that was packaged, where updating or reinstalling the kit is what restores the packaged bytes and every guard verdict that session already took is suspect until it does. The canary always exits 0 and never blocks anything. The loud/silent boundary is deliberate: anything positively observed about the cache being broken is loud, including a missing hook file, a missing or unparseable `hooks.json`, a probed hook the wiring no longer names, and a plugin root that is not there, while an unexpected error inside the canary's own code stays silent through its fail-open catch, since a canary bug that warned at every session start would cost more than the blind spot it covers. What the canary measures is a cache's internal consistency, not its freshness against the repo: a stale but coherent cache reads healthy, and `kit-version-nudge.js` is what watches for drift. The doctor's "Hook canary" check confirms the file is present and wired into the `SessionStart` array.

One consequence lands on whoever edits a hook: `test/hook-canary.test.js` runs the canary against the repo's own `plugins/claude-kit/` directory, so a hook changed without a rebuild leaves the gitignored stamp beside it stale and the health assertions go red. That red is self-diagnosing, naming the stale stamp and telling you to run `.\build.ps1`, and the coupling is deliberate: it is also what catches a hook edited after the last build before a package ships.

### Backlog surfacing

`docs/backlog.md` is a pull surface in a push workflow, so the kit pushes it. `summarizeBacklog` in `session-start.js` reads the file under the payload cwd, scopes to its `## Active` section, and emits one block carrying three figures: the active item count, the oldest dated item's ISO date with its age in whole days, and a tally of items carrying no date. Two properties separate it from the kaizen counter beside it. It carries no kit-repo marker gate, so it fires in any project holding a `docs/backlog.md`, and `KIT_EXTERNAL_ENGINE` does not suppress it, because only the plan block's drive-to-completion instruction is engine-sensitive.

Numbers and one regex-extracted ISO date are the only interpolations, and item text never reaches the block, so a hostile backlog line cannot inject instructions into session context. The parse is deliberately coarse. The read is bounded at 64 KB and tolerates a UTF-8 BOM; items are top-level `- ` bullets, with a bullet whose content is entirely parenthesized (the shape the `curating-docs` backlog template ships) and a bare empty bullet counted as structure rather than items; and the aging anchor is the first `\b\d{4}-\d{2}-\d{2}\b` token anywhere on the line, because the kit's convention puts the parked date in the title's parentheses beside other context. A cross-component pin in `test/session-start-backlog.test.js` seeds its fixture from the template's own backlog block, so the placeholder shape and the parser cannot drift apart silently.

Every failure is silent and additive. An absent file, an unreadable one, no `## Active` heading, or zero items emits no block at all, and the check runs inside its own try so it can never affect plan recovery. Two known degradations ride with the coarseness: a backlog past 64 KB truncates mid-section and yields partial counts, and an ISO-shaped impossible date such as `2026-02-30` either rolls to a neighboring real date or joins the undated tally, depending on the runtime's `Date.parse`. Both are acceptable in a coarse age nudge.

The behavioral half lives in three skills and one template, and the hook is the primary enforcement because it fires whether or not any skill loads. The `curating-docs` backlog template states the dated item shape (`- **<item> (YYYY-MM-DD).** <body>`); that skill's prune pass doubles as the aging check, naming every item older than 90 days for a promote, retire, or keep call, where a keep writes the fresh adjudication date ahead of the original (`(2026-11-07, parked 2026-05-01)`) and an undated item is past the threshold by definition and gets a backfilled date in the same pass. That check also has a standalone trigger, offered in one line when the session-start block reports an oldest item past the threshold and no close-out is near. `finishing-work` step 5 carries each named aging item, by name and date, into the close-out status with its question, which is how an aging item reaches an operator reading close-outs on a phone. `brainstorming` step 1 reads the backlog straight after `memq recall`, so a new effort finds an already-parked solution before designing a fresh one. The two knobs are the 90-day threshold, stated in the hook's block text and in `curating-docs`, and the 64 KB read cap in `summarizeBacklog`.

## Memory store

`plugins/claude-kit/scripts/memq.js` is a zero-dependency CommonJS CLI over the file-backed memory store under `~/.claude`. It resolves a project's store from the cwd by reproducing the harness's own directory-name rule, so it lands on the same directory Claude Code writes. That derivation is the default and not the only one: under the engine's gated store a pin (`KIT_MEMORY_PROJECT`) replaces the derived segment with a fixed one, so one instance keeps one tier across workers whose working directories differ. Everything hanging off that directory follows, index and journal and sidecar and pending tier alike, which is the point; `docs/security-model.md` carries what the pin changes about who reads whose memories and why pinned content is fenced. It reads the file-per-fact memories of the project tier, a project-type tier shared by every project declaring that type, an operator tier at `~/.claude/memory-operator/` that every project on the machine reads and writes, each tier's `archive/` of retired memories, an outcomes journal (`outcomes.jsonl`) that exists per project only, and, inside a run the external engine spawned, that run's own `pending/<run-id>/` directory. The pending tier is present only under the three run signals and is scoped to the one run that owns it; `docs/security-model.md` carries what it is for and what its scoping does and does not guarantee. A used-tracking sidecar (`usage.jsonl`) sits beside each tier's memories carrying read and applied stamps; it is evidence about the records rather than a surface of its own. Retirement moves a memory into its tier's `archive/` rather than deleting it.

Inside a run the pending tier changes writes as well as reads. Every new memory file the run produces lands in `pending/<run-id>/` rather than the project tier, carrying provenance frontmatter memq stamps on anything it writes: `run:` from `KIT_RUN_ID`, `vector:` and `section:` from `KIT_SPAWN_VECTOR` and `KIT_RUN_SECTION` when those are present, and a `written:` date. Because a session's memory files are written by its Write tool rather than by memq, `memory-session.js` emits the same instruction into the session at start: the pending directory named verbatim on its own line, the frontmatter fields the file must carry, and the standing rule that `MEMORY.md` is not the run's to touch, since a pending memory carries no index line and the index entry is written at promotion by the engine. A session carrying the store signals with a run id the kit cannot honor is stood down from writing memory at all rather than left to write into the shared record. `memq log` keeps appending to the project-tier journal and gains a `run` field rather than rerouting, and `get` resolves the pending tier ahead of the project tier, following the file's own closest-tier-shadows rule. With `KIT_RUN_ID` unset there is no pending tier and every command behaves as it does outside a run.

`memory-session.js` is the store's session-start voice, and it runs seven blocks: the overdue-decay nudge, the type-tier index for a project declaring a `Project-Type`, the sync trigger, the embedder-absence nudge, the run-scoped pending destination, the pinned destination, and the project-tier block that names what the project's memory index already holds and where a new memory file goes. The sync trigger both acts and speaks: on Windows, for the kit's own owned default store, it spawns the detached background runner that commits and syncs, and it emits a line only in the three states worth nagging about, a recorded standing-down gate, a week-old failure streak, or a broken sync chain (a spawn that recorded no outcome past a stale window), staying silent while a healthy sync does its work. The two blocks that speak to the machine's own state, sync and embedder, carry no store-derived text at all: integers the hook parsed and words that are literals in its source (a state-file reason code is a lookup key with a fixed fallback, never emitted text), which is stricter than sanitizing and is why neither needs a fence. Both stay silent under a stand-down and in a run-scoped session, whose own block already claims what the hook says about where the store stands. The decay nudge and the type index are independent of the rest; the three destination blocks are mutually exclusive, since a session must be handed one destination and never two, so a run suppresses the pin block and silences the project block, and a pin reduces the project block to its index lines alone, to a short notice when the index exists and cannot be read, or to nothing at all when the index is absent or empty. What the project block does not depend on is any harness setting: the kit states its own index and its own write destination rather than assuming Claude Code's auto-memory has supplied either, so the store behaves the same whatever that setting is. The cost is that a session with auto-memory on sees the same index twice, once verbatim from the harness and once reduced and capped by the hook; the alternative was mirroring a private harness resolver that changes without notice, which the kit deliberately does not do. A stand-down state replaces every one of them when the environment names a store the kit cannot resolve.

An ordinary session, with no run and no pin, gets the whole project block, and its two halves fail differently. The index half states one of three facts: the index lines themselves, reduced to bounded printable ASCII and capped at 60 lines against the type tier's 30 with the remainder counted; that the project has no index yet; or that the index could not be read and the tier is therefore to be treated as populated rather than empty, since "nothing is recorded" would invite a session to write a second copy of a fact already there. The destination half names the memory directory verbatim or not at all. A path that cannot be carried faithfully, longer than 260 characters or holding anything outside printable ASCII with the double quote barred, withholds the directory and the write convention with it, keeps the index lines, and points the session at `memq`, whose commands resolve the directory themselves. That is the one destination block that does not stand a session down over an unemittable path, because an ordinary session has asked for nothing the kit cannot do. Both index emissions run through one shared helper, so the read cap, the per-line reduction, the counted remainder, and the indent cannot drift between the two tiers.

Two properties shape the code more than anything else. The store is a **data-to-model boundary**: a SessionStart hook emits store content into a session's context before the user types, so a value entering a store file is bounded at the write rather than at display, in length always and in charset for the prose fields (summaries, descriptions), while a memory body is length-capped only; and the store root is settable only behind two signals rather than one, because that variable selects which data reaches the model. And its writers are **lock-free appenders around locked rewrite paths**: of memq's own writers, `log`, `touch`, `get`, and the read-stamp hook append without a lock, while `decay-prune`, the shared-tier authoring commands (`add-type` and `add-operator`, their `--update` repair included, which rewrites the index description on every call and the record body as well when a body flag and `--confirm-shared` ride with it, the description positional being required on every form of the verb), and the shared-tier delete verbs (`delete-type` and `delete-operator`) rewrite under a per-tier lock, each leaving a backup beside every file it rewrites. A first-creation write and a memory-file move leave no backup, having no prior bytes to keep, and a delete is the one locked path that ends with less than it started: it removes the record's own copies first, that record's backup included, then both index lines, then the usage stamps, leaving a backup of each file it rewrites, and unlinks the record files last; then, once every removal step has landed, which includes the confirmed run that found no record and so removed nothing, it removes the backup beside each of those three files, whoever wrote it, so no copy of the deleted body the verb can name survives in the tier. That closing sweep is what makes the claim exact rather than approximate: an index line for a record authored without a body flag carries the whole stored body, so an index backup left beside the tier would keep the deleted memory readable in a file no reader lists and no hand may edit, the tier barring hand edits by design, and which nothing clears until some later rewrite of that same document happens to replace it. The exposure is local: `*.bak` sits in the sync's never-sync patterns, so the copy stays on the machine that made it. It runs only after the removals, because until then those backups are the single local recovery for a rewrite that stopped, and the bound is the path rather than the writer: those three are the documents this verb exists to edit, and a delete that stopped after its index rewrite leaves a backup there and no index line behind it, so a re-run bounded by what it had written itself would sweep nothing and leave the removed record's text in a file no reader lists and no hand may edit, cleared only if some later rewrite of that document happens to replace it. A backup it cannot remove is named on stderr and does not fail the delete, the deletion itself being complete by then and an error code only sending an operator to re-run a command with nothing left to do. What the sweep does not reach is a `<file>.tmp.<pid>` a hard-killed rewrite stranded at one of those three paths, `MEMORY.md.tmp.<pid>` at either index, holding that index as it then stood with the record's line in it, and `usage.jsonl.tmp.<pid>` at the sidecar, holding the stamps recorded against the record's name: the sweep names the `.bak` at each path and not the temp beside it. The copies it removes are found by listing each directory the tier writes under, its archive included, rather than by name alone, because an interrupted rewrite can leave a `.tmp` beside the `.bak` this module can name and both hold the record's text; the listing leads and nothing is unlinked before it returns, so an unreadable directory stops the verb before spending the record's only local copy on the way to the same stop. The verb runs two sweeps, the tier's own directory and its archive, and both directories are checked before either sweep unlinks anything, so a path that is not a directory at all stops the verb with every copy still whole. That check reaches the directories and not the backup paths inside them, so the other permanent case, a directory standing at `<name>.md.bak`, is not caught before the live sweep runs. What stays per sweep is the transient one: a directory that lists for the first sweep and fails for the second leaves the first sweep's unlinks done, which is a state the same command completes rather than one it cannot describe, and the report names the sweep it stopped in. The order is what makes the verb re-runnable: every state a stop can leave is one the same command completes. Whether a rewrite carries a tail copy of bytes that appeared past its read is decided at the call site rather than by a default, and on the index path saying so is mandatory: each helper there throws when its caller states nothing, so no index rewrite added later can inherit the wrong behavior by omission. The rewrite helper takes that answer directly. Every function above it on that path takes the tier instead and derives the answer from it, which is the same requirement asked in the words those callers actually know, since a caller holding an index path or a tier directory knows which tier it is holding and need not restate a consequence of it. The requirement is stated as a rule rather than as a tally of the functions carrying it, because the tally is what drifts. The journal and the usage sidecars are the other case, and the difference is worth stating rather than generalizing over: their helpers state the answer as a constant, because there it is a property of the file rather than of the caller, those files having lawful lock-free appenders in every tier and keeping the copy wherever they are rewritten. The refusal therefore guards the path where the answer varies, and a new sidecar-shaped writer modelled on one of those helpers inherits a constant that was chosen for the file it was written for, with nothing checking that it is right for a new one. The two index files are decided per tier rather than per name, because the same two filenames mean different things on either side: in the shared tiers nothing lawful appends to them, so a rewrite there takes itself as written, while the project tier's own `MEMORY.md` does have lock-free writers (the Write tool, and a reinstatement that restores an index line by hand) and so keeps the copy. The decay pass is the one writer reaching both tiers through a single code path, which is why the choice travels as an argument rather than living in the function. The replacement check is independent of that choice and runs on every rewrite rather than only the tail-carrying ones, because the whole store syncs and a pull replaces a file rather than appending to it, holding no lock this module takes: every rewrite reads the file back and proceeds only where the bytes the pass read are still its head, failing with nothing written when they are not, since the alternative is to republish a stale copy of every line the pass did not touch and drop whatever the pull added. What the call-site choice decides is the narrower question of whether bytes found past that head are spliced onto the new content or dropped. A caller that is removing a record also states what the carried tail may not bring back, so a usage stamp for the deleted name cannot ride back in past the rewrite that dropped it. That split is why the readers tolerate a torn line rather than failing on one.

A shared-tier body reaches the store by one of two channels, and the second exists because a command line is not a reliable carrier for one. `--body` takes the text as an argument; `--body-file` takes a path and reads the body as UTF-8 from that file. Any body composed with newlines should take the file channel, because `cmd.exe` cuts a command line at its first newline and `memq.cmd` forwards its arguments through that parser, so a multi-line `--body` reaching memq through that one wrapper is cut there. The sh and `memq.ps1` wrappers pass a multi-line argument byte-exact, so the trap belongs to `memq.cmd` alone, and `docs/security-model.md` carries what the file channel removes of it and what it does not. Both channels answer the same gates, a refusal of a blank body and a 65536-character cap measured over the whole record rather than the body alone, since `get` reads and caps the whole file. The two flags on one call are a refusal rather than a merge, and `--body-file` is refused outright under the engine store signals, where a granted worker invokes the script directly, meets no wrapper, and so loses nothing to the refusal.

Truncation is only half detectable, which is what shapes the CLI's account of it. With the body flag last, the cut leaves a correct positional count and a silently shortened body at exit 0, which nothing can catch, so every successful `add-type` and `add-operator` reports the stored body's length on its success line instead. Where the cut takes a positional with it the count fails, and a hint fires on the residue truncation leaves: a free-text `--body` or `--detail` value last on the line with the positional count short. It is worded as a hypothesis rather than a verdict, because a forgotten argument leaves exactly that argv and no reading of argv separates the two, and it names the remedy the caller can actually reach, which is `--body-file` ordinarily, `--body` under the store signals, and one line for `log --detail`, the one free-text flag with no file channel behind it.

Retention runs on evidence rather than a fixed clock. A memory's idle clock is the freshest of its mtime, an author-asserted `created:` date, and its newest `applied` stamp, and each distinct calendar day of recorded application extends both decay thresholds by 30 idle days up to a 365-day cap, so a heavily used memory survives a long idle stretch in proportion to its record of use while nothing becomes permanent by accumulation. A `pinned:` frontmatter field is the judgment override for the rare must-never-age case; it is set by hand, counted in full on any scan that finds one so the exempt population cannot grow unobserved, and honored by the prune as well as the scan. Crossing a threshold nominates rather than retires, and the archive stays scoreable and fetchable, so the worst outcome is demotion rather than amnesia. A `supersedes: <name>` field on a newer record is the fourth retention state and the only one driven by evidence the store did not compute: it points back at the live same-tier record it replaces, and from the moment it lands that record is labeled by every surface that serves a record by name, demoted in `find`'s semantic ranking, and nominated at the next scan whatever its idle clock, while staying live and fetchable. The label does not reach the `MEMORY.md` index the SessionStart hook emits, index-line changes being out of the remedy's scope. The pointer is authored data rather than a measurement, which is why it nominates and never retires, why a pin outranks it, and why a mutual pair and a record naming itself are dropped rather than read as claims. A cycle labels nothing whatever its length, a self-pointer, a mutual pair and a longer loop alike, while a pointer reaching into a cycle from outside still labels the member it names. The map is an inverse scan of the tier's live records built once per invocation, so on the surfaces that already list a tier the cost sits in the same class as the pin walk beside it; `get` is the exception and it is deliberate, since answering for one name means opening the tier that held it, which is a tier walk where it used to be one file read. Only a live successor labels anything.

Authoring the pointer splits by tier, and the two halves get different amounts of checking. The project tier writes it by hand, as it writes `tags:` and `pinned:`, so the frontmatter reader is the only thing standing between what a file says and what a line claims. The two shared tiers add a creation-only `--supersedes <name>` flag to `add-type` and `add-operator`, written as a top-level frontmatter line beside `tags:`, reported on the success line, carried across a later `--update` body repair verbatim, and refused alongside `--update` exactly as `--tag` and `--machine` are, so a record needing a different pointer is a delete and a fresh write. Six shapes refuse the command with nothing written: a name outside the record-name grammar, a name whose path is not a plain file or cannot be examined, a name whose own frontmatter cannot be read, a name no record of the tier holds, a name only the tier's archive holds, and a name whose own record already points back at the one being written, which is the pair every reader would drop whole. That gate is a typo guard and claims nothing more: its reads are lock-free, so a concurrent delete can still leave the dangling pointer the read surfaces treat as inert, and it closes the pair rather than the ring, a longer loop staying mintable through a delete and a recreate at no cost, since the readers drop every member of a cycle anyway. The flag is refused outright under the engine store signals and withheld by the grant hook, the two locks `--body-file` already carries, so an unattended worker writes the record without the pointer and the pointer waits for an attended session; `docs/security-model.md` carries why a demotion this light is withheld at all.

`memq recall` is the read half. It takes no search term and emits the whole store as one bounded digest, a summary line per record across every surface, ordered by last sign of life, inside a fixed line budget whose every truncation is announced with a counted remainder. Ranking is deliberately left to the model reading the digest with its current task in context, because that is the only semantic scorer available and it is free; lexical scoring was rejected because a substring miss is silent, which is the expensive failure shape. The digest leans on nothing outside itself to have put a record in front of the reader: descriptions ride the journal, the archive surface across all three tiers, and the project tier. The type, operator, and pending tiers are the live surfaces that stay lean, the type tier because the session hook emits its index as a block of its own, the operator tier because it is reached by search rather than by emission, the pending tier because it holds the run's own writing that the run just produced. The trigger is procedural rather than ambient: `executing-work` and `brainstorming` each run it once where an effort's context is assembled, so no hook pays context and latency on every prompt. The store resolves from the cwd, and a git worktree resolves its main checkout's store (memq follows the worktree's `.git` pointer through a two-way handshake), so recall works from a worktree as well as the main checkout; a plain subdirectory, a bare-repo worktree, or a worktree whose `.git` handshake fails (memq notes that one on stderr, pointing at `git worktree repair`) still resolves a different, empty store, and the tell is a digest whose coverage lines all read zero on a project known to have memories.

`memq recent` is the second reader, and it answers what happened to the store rather than what the store holds. It digests one time window (`--since <n>d` or `<n>h`, default one day, any other spelling refused) and groups by write surface rather than by tier: journal entries logged, applied stamps written, and memory files added or updated. The grouping is what makes the digest answer whether the extension layer is being used at all, because provenance rides the surface: journal entries and stamps exist only through `memq`, while a project-tier memory file arrives through a session's own Write tool. Every group opens with a coverage line carrying its count even at zero, and evidence that exists but could not be read is said in that line, so a count is never quietly a floor. Read the file group's `added` label narrowly: it says the file's creation time falls inside the window, and the editing tools rewrite a memory file rather than patching it, which resets that time on every write. So the label separates how a file was written from how it was not, never a new record from an edited one, and `backlog.md` carries the choice of what to do about it.

Its span is every tier the store has, the project tier, a declared type tier, the operator tier, and a run's pending tier, each with its `archive/` directory, so a decay pass's demotion reads as the file change it is. Archive records key on the newer of mtime and ctime rather than the mtime alone, because archiving is a rename: the rename preserves the mtime a memory carried while it was live, which for an archive candidate is idle months by construction, and moves the ctime instead. The digest carries its own 200-line budget, matching `recall`'s and tunable apart from it, and the same rule that every truncation is announced with a counted remainder, and it cuts in the reverse of its print order, so the journal, which nothing else summarizes and no session-start block carries, is the last surface to lose lines. It is read-only and stamp-free: it reads sidecars, the journal, and file stats and never serves a body, so it appends no `read` stamp of its own, since a digest that stamped the reads it reports on would corrupt the decay evidence it exists to show.

The trigger is procedural, the same shape as `recall`'s: `finishing-work` step 7 runs it over the session's span at close-out, after the memory writes and any decay pass, so the close-out status reports counts instead of asserting that the effort banked something. The cwd caveat is the narrow one `recall` carries: a Commit-and-Push session sitting in a worktree resolves the main checkout's store (the worktree handshake), so `recent` reports the real activity there; a plain subdirectory, a bare-repo worktree, or a worktree whose `.git` handshake fails resolves a different, empty store and reports zero for a session that banked plenty.

`memq unstamped` is the third reader, and it answers which memories a session opened and never reported applying. It diffs the used-tracking sidecars' `read` stamps against their `applied` evidence inside one window (`--since <n>d` or `<n>h`, a positive whole number of days or hours, default one day, on the same grammar and the same refusals `recent` carries: one `--since` per run, the value a separate argument, any other spelling a usage line) and reports the gap: one line per record carrying the tier token, the name, the age of the last read, and the tier index's description. An `applied-rollup` counts as applied evidence and is dated by the last application it folded rather than by the fold, the reading `recent` gives the same record. The window is a set-membership question rather than an ordering one, so a record applied anywhere inside it stays cleared however much later it was read again; comparing the two timestamps would re-ask an adjudicated record on every subsequent read, and the list works only while every line on it is a real question.

Its span is the live records of the project tier, a declared type tier, and the operator tier, each stating its count even at zero. Four surfaces are deliberately outside the domain, each for a reason that would otherwise teach an invocation that errors or a question with no answer: journal keys, which have no applied concept at all; `MEMORY.md`, which the stamp hook never records; the run-scoped pending tier, whose records `touch` cannot stamp; and any archived record, which `touch` refuses. The command writes nothing, not a read stamp, not a usage entry, and not a lock, since acquiring one creates the directory it sits in. It carries no line budget, unlike the two digests: its output is bounded by what this machine's own stamp hook opened inside a short window, and truncating an adjudication list would hide exactly the record the judgment is owed on. Where a tier's sidecar or its record listing could not be read whole, that tier's coverage line says the count is a floor rather than reporting a clean zero, because the two errors cost differently: a false candidate costs one recognition question, a missed applied ages a load-bearing memory toward the archive. Output closes with the same tier-aware stamp reminder `find` uses, naming the exact `touch` invocations this run's own hits need, which is why every hit is a live record of a tier this working directory resolves rather than merely a record that was read.

The trigger is procedural on both ends. `executing-work` step 6 runs it at every Chapter boundary before the Chapter is appended, and the Chapter records the outcome in its `Stamps: <adjudicated N, stamped M>` field; `finishing-work` step 7 runs a final sweep at close-out, ordered sweep, then decay pass, then recap. The boundary trigger is what makes the mechanism work: read stamps survive a compaction and a session handoff, while the judgment of which read mattered does not, so a close-out-only sweep asks a long run to recall across boundaries it has already crossed. The close-out sweep precedes the decay pass because applied stamps are the evidence the decay thresholds extend on, so a sweep running after it could stamp a memory the same close-out had just archived for idleness.

The decay seeds (30 idle days per applied day, a 365-day cap) and both digest budgets (200 lines each, plus `recent`'s one-day default window) are invented constants with no live observations behind them, to be tuned on real tallies rather than widened speculatively.

The routing ladder is journal, project, type, operator, doctrine. The operator tier is the destination for a fact true of the operator or of a machine rather than of one project or one platform, and without it such a fact strands in whichever project store happened to learn it. It is shared by every project's concurrent sessions, so authoring goes through `memq add-operator` under the tier's lock rather than the Write tool, which cannot take one; a `machine: <name>` field on a memory scopes it to one box, which search labels rather than hides. Retrieval is most-specific-wins, project over type over operator and live over archived. The tier is deliberately absent from session start: it is reached through `recall`, `find`, and `get`, which keeps every use visible to the read and applied stamps that the decay clock runs on, where an injected index emission is use no stamp can see.

The store also syncs, and on Windows it syncs itself: the session-start hook spawns a detached background runner (`doctor/sync-store.ps1`) that commits pending memories and, where an upstream exists, fetches, screens the incoming content, rebases, and pushes, so a memory learned on one machine reaches the others with no hand-run step and no nag while it is healthy. `~/.claude` is a git repository whose gitignore excludes everything and re-includes only the memory tiers, pushed to a private remote. That allowlist is the whole boundary between replicating memories and publishing credentials, and it is not self-enforcing: a `.gitignore` inside a traversed directory outranks the root file and can re-include what the root excluded. So the guarantee is the rules plus the leak probes both committers re-derive on every run (the doctor's `-Fix` and the background runner, which dot-sources the same code), over the ignore rules, the worktree, the index, and the local committed history, refusing any commit carrying a path the allowlist does not admit. The allowlist guards both directions: outbound, those probes refuse a commit; inbound, the runner screens every entry of the incoming tree by its mode and its path before the rebase touches the working tree, so a rename, a duplicate-content push, or a symlink at an allowlisted path cannot drop a disallowed file into `~/.claude`, where nothing un-writes it. The journals merge as line unions, which fits their append-only shape. Project stores are keyed by the flattened project path, so a synced project tier resolves on another machine only where the project sits at the identical path; the type and operator tiers are path-independent and resolve everywhere.

The runner's own record of what it did is `kit-sync-state.json` at the store root, and it is the only channel a detached background process has. `Write-SyncState` composes five fields (`lastAttempt`, `lastResult`, `reason`, `lastOk`, `firstFailSince`), writes them to a per-PID temp file as UTF-8 without a BOM, and puts that file in place two ways: `File.Move` where no state file exists yet, and `[System.IO.File]::Replace` where one does, because a replace is atomic on NTFS while `Move-Item -Force` is a delete-then-move a concurrent reader can catch mid-gap. That `Replace` call passes `[NullString]::Value` as its backup path rather than `$null`, and the distinction is load-bearing: PowerShell marshals `$null` into a `string`-typed parameter as the empty string, `File.Replace` rejects an empty backup path, and the surrounding catch would swallow the exception, so the `$null` spelling lets only the first write in the file's lifetime land. The write is silent in both directions by construction, since the catch deletes the temp file and returns without an error, an exit code, or a record; `docs/backlog.md` carries that residual and the two triggers still reachable for it. `memory-session.js` reads three of the five fields, `lastResult` and `firstFailSince` for the seven-day failure-streak nudge and `lastAttempt` for the broken-chain check against the spawn marker's mtime. `lastOk` is the runner's own success stamp and is read nowhere outside `sync-store.ps1` and the tests.

Whether a push has anywhere to land is the doctor's question, and `Get-MemorySyncDestinationLines` in `doctor.ps1` answers it as a pure formatter over the status hashtable `Get-MemorySyncStatus` fills. Every read behind it is of a local ref or a `--local` config value, so the answer costs no network round trip and is as of the last fetch, a limit the report states rather than hides. Four states block: a detached HEAD, a branch tracking nothing, a branch tracking a remote other than origin, and a `push.default` that will not carry this branch's pair of names. The last is the one every other check reads clean over, because the runner's push leg is a bare `git push --quiet` and what a bare push does with a local branch whose upstream carries a different name is `push.default`'s to decide. The name comparison is ordinal over the raw `branch.<name>.merge` value against `refs/heads/<local branch>`, which is git's own comparison byte for byte, so a case-only difference and a short form (`merge = main`) are both refusals rather than matches; the setting itself is matched case-sensitively, because git parses it that way and rejects a value it does not recognize.

What a differing pair costs is a function of that value, so the finding is too. `simple` refuses the push fatally. `matching` updates only branches carrying the same name on both ends, so it publishes nothing and exits 0, which the runner records as a success: the quietest of the set. An unrecognized value makes git refuse every push as a malformed config value, and `nothing` errors out for want of a refspec whatever the names are. Those four are blocking, which reports the memory-sync check FAIL and exits the doctor 1. `current` publishes to a branch on origin named after the local branch, so the push succeeds and lands where no other machine pulls from, which is advisory: the check reports WARN and does not fail the run. `upstream` and `tracking` push to the upstream ref whatever the two names are, so a differing pair is not a finding at all. Each finding carries its own remedy, and two of those are gated. The rename is printed as a runnable `git branch -m` only where the merge ref sits under `refs/heads/`, both names match `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, and both survive `Get-SanitizedLine` unaltered, and is reported in prose with no pasteable command otherwise. The report's trailing "put HEAD on the sync branch and give it an upstream" line is emitted only for the three findings it repairs, since running `push -u origin <branch>` against a branch whose upstream on origin is already correct creates a second branch there and repoints the upstream at it, which is the silent cross-machine divergence the advisory check in the same function exists to report.

`memq find` answers by meaning as well as by substring. `plugins/claude-kit/scripts/memory-index.js` owns an embedding stack that installs per machine outside the plugin payload, so the kit core stays dependency-free, and a derived JSONL index beside the store covering all three tiers, live and archived, across every project store on the machine, and deliberately not the run-scoped pending tier, whose unadjudicated writes are one run's to read. The index is sync-excluded by design: a vector is valid only against the embedder that produced it, so each machine builds its own, and the sweep is lazy at query time, keyed on content hash so a synced checkout that moves every timestamp re-embeds nothing. Where the stack is absent, find says so in one line naming the remedy and serves lexical results; nothing degrades silently. The two channels fail differently, which is why both stay: lexical catches the exact identifiers embeddings fuzz, semantic catches the paraphrase substrings miss.

Archived records are ranked but withheld from the semantic block by default, and one line in memq's own voice at column zero is what keeps the suppression from being a silent miss. It headlines every archived record that cleared the admission floor, which is suppression's true extent, and it quotes a best raw similarity only over the archived records inside the pre-suppression display slice, which is exactly the set a `--archived` rerun puts on screen under the same 10-hit display cap. Two counts rather than one, because a similarity quoted from a record the rerun's own cap would cut sends a reader after a line that does not exist: the line names the subset's size whenever it is smaller than the headline, and where nothing archived reaches the cut it says so instead of recommending a rerun that hands back the same screen. Suppression runs after admission and ranking and before the display cap, so a live hit fills the slot an archived one would have taken. A search whose every admitted hit was archived still prints the block's framing line and the withheld line rather than falling into find's empty-result path, which exits to stderr with `no matches`: a suppressed hit is never allowed to read as an absent one. `--archived` turns the filter off, printing those records labeled `retired` and demoted by the archive-demotion constant, which under that flag is what keeps an equally similar live record ahead of its retired twin, and it prints no withheld line; it is refused with a usage line alongside `--outcomes`, which never opens the semantic channel, and on every other subcommand. The lexical channel lists live records only, so the flag changes the semantic block alone.

A superseded record is the same shape one notch lighter, and it is not suppressed: the lexical line carries `superseded by <name>` and the semantic hit carries a bare `superseded` token beside the `retired` one and a demotion by its own constant, seeded to match the archive demotion, so an equally similar record nothing replaces ranks ahead of it. The names ride the lexical label alone, and a fan-in enumerates them there name-ordered, capped with a counted remainder, while the demotion fires once whatever the count, the label being a flag rather than a sum. Suppression would be wrong here for the reason retirement would be: the record is still live and the pointer is authored data.

A semantic hit line states usage as two tokens, `applied x4, last 25h`. The count is the distinct calendar days the record was applied on and the age is the most recent of them, printed apart because one number that means a tally reads as an age. The count shown is the uncapped truth while the ranking's tiebreak keeps using the value capped at the boost's own ceiling, which is deliberate: the line is annotation, the blend stays dumb, and the reader judges freshness rather than inferring it from a rank. The semantic block spans stores the calling project never opened, so it takes the full provenance fence rather than find's narrower by-construction guard, and `docs/security-model.md` carries that distinction.

The `memory-system` skill owns the operating rules; this section owns the shape.

## Goal release events

A `/kit-goal` leash release leaves a machine-readable line in `~/.claude/kit-events.jsonl`, so an outside notification layer watches one well-known path instead of parsing transcripts. Transport is not the kit's job; the kit's deliverable is the file and its contract.

`emitGoalEvent` in `kit-goal-lib.js` writes it, and `kit-goal-stop.js` calls it at exactly three points: the plan reaching `Status: Complete` (`goal-complete`, detail `plan-complete`), the plan file gone to the archive (`goal-complete`, detail `plan-archived`), and a last assistant message leading with `BLOCKED:` (`goal-blocked`). Two other releases deliberately emit nothing: a manual `/kit-goal clear`, where the user is already present, and the harness's own consecutive-block-cap override, which the hook never sees.

Under a queue the cadence is per plan rather than per run, and that is the only shape change a consumer sees: an arming of four plans emits at each plan's terminal state, so up to four events carrying four different `plan` values under one `session`, and only the last of them coincides with a release. The event names, fields, and `detail` values are unchanged, and each event names the plan that finished rather than the one now current, so a consumer written against a single-plan arming reads a queue correctly and simply sees more events. What it must not infer is that an event means the run ended; that was never stated in the contract and is now false for every event but the last.

That decoupling is sharpest for `goal-blocked`, which mid-queue is emitted on a stop the hook then blocks. The event says a plan hit a blocker, which is the thing worth notifying an operator about, and says nothing about whether the session stopped; the leash records the blocker, advances, and holds the session on the next plan. Emitting it there rather than suppressing it is deliberate, because a blocked plan is exactly what an operator wants to hear about and the alternative loses that signal for every plan but the last. A consumer that treats a `goal-blocked` as "the run stopped" and acts on it, by resuming or re-arming, is acting on an inference the contract does not support.

One thing the stream deliberately does not carry is the blocker's text. `history` accumulates a note per finished plan inside the state file, and the final plan's release deletes that file, so once a queue finishes the content of each mid-queue blocker survives only in the session's own closing summary. That is a soft record: a session that dies before writing its summary leaves plan paths and no blockers. Closing the gap needs a new field or a new sidecar, both of which are event-shape changes the queue deliberately avoided, so it is a known limitation rather than an oversight.

The contract a consumer reads against:

- One JSON object per line, `{ts, event, project, plan, session}`, plus `detail` present only on a `goal-complete` and `run` present only inside a run. `ts` is ISO 8601, `project` the absolute project path, `plan` the repo-relative plan path, `session` the session id or null.
- `run` carries `KIT_RUN_ID`, and only a value memq's own `isRunId` accepts, so the event stream and the memory store cannot disagree about what a run id is and a consumer may rely on the value being a well-formed id. The field is absent rather than empty when the variable is unset or refused. Its presence says the process was told a run id, not that run-scoped memory was active: the pending tier additionally requires the store signals, so the two conditions are separate and a consumer must not read one as proof of the other.
- Every field is sanitized display data, not a command: printable ASCII, capped at 40 characters for `event` and `detail`, 120 for `plan` and `session`, and 260 for `project`.
- `project` is an absolute local path that typically embeds the OS username, so forwarding an event anywhere external is a PII call the consumer makes.
- A `goal-complete` is exactly-once per plan, but the two positions in a queue reach that guarantee differently. On the last plan the emit is gated on the clear that actually removed the goal state, so a persistently failing clear never re-reports and a racer that finds the state already gone stays silent. Mid-queue there is nothing to clear, so the guarantee rests on the advance itself: only the bound session's stops reach it and its stops are serial, and the advance is one atomic state rewrite carrying a compare-and-swap on the plan the stop decided from and the timestamp it was armed at, so a state some other writer moved in the meantime is refused rather than advanced over and the emit rides only on the write that lands. Both halves are load-bearing: a re-arm that puts the same plan back at the head, which is the ordinary crash-recovery spelling, matches on plan alone and is caught only by the timestamp. The binding alone would not carry that claim, because the CLI is a writer it does not exclude: a `/kit-goal` re-arm or clear can land inside the hook's own retry sleep. A failed or refused advance emits no `goal-complete` at all, since the write and the emit stand or fall together: the clause re-runs at the next stop against the state as it then is, and the event arrives once, late. What statelessness costs falls on the other event instead. `goal-blocked` is emitted before the advance is attempted, so a failed write means a second `goal-blocked` at the retry, and a plan can draw more than one anyway: the hook holds no record of a blocked stop except in the one mid-queue case where the spent advance key suppresses a re-read of the same turn. Dedup is therefore the consumer's policy and is load-bearing against notification spam.
- `KIT_EVENTS_PATH` redirects the sink per process, honored only alongside `KIT_EVENTS_PATH_ALLOW=1`. The intended users of both signals are the repo test suite and the canary's own goal probe, which point the stream at a throwaway file; a consumer must not honor either ambiently. An override set without the second signal is ignored in favor of the real sink, with a note on stderr. An engine that sets the path alone therefore does not fail loudly to its own watcher, it silently keeps writing to the default sink, so setting both is a deployment precondition rather than a convenience.
- Emitting is observability, never a decision input. The helper never throws, returns nothing to branch on, and leaves a stop's verdict, output, and exit code identical when the write fails. A sink that exists and is not a regular file is left untouched and nothing is written, the same FIFO-hang guard the Stop hook applies to transcript paths. The check is an `lstat`, so a symlink or junction at the sink path reads as the link rather than its target: nothing is appended through it, and the rotation cannot move a linked-to file aside. Rotation is best-effort and sized for a single writer: past 1 MB the file is renamed to `kit-events.jsonl.old`, replacing any previous one, and a rename that keeps failing degrades to unbounded growth rather than lost events.

## External integrations

- **Node** runs the hooks and `memq`; it is the kit's one runtime dependency.
- **git and the GitHub CLI** are what the branch-hygiene, PR-docs, and merged-PR-push guards observe and act on. Both build scripts also shell out to git for the short hash and the payload's dirty state that go into the build stamp, and fall back to an `unknown`/clean stamp when git is absent or errors.
- **The local filesystem under `~/.claude/`** is shared state: `projects/<sanitized-cwd>/<session-id>.jsonl` for transcripts, and `kit-events.jsonl` for the goal release events above, the kit's one outbound machine-readable feed.
- **The external engine (the AI OS Spine)** delivers the kit into the sessions it spawns and reads three of its surfaces: the goal event stream, the pending memory tier it promotes from, and the plan doc, which it parses to drive dispatch. The plan-doc header and structure are a frozen v1 machine contract for that reason, owned by the `curating-docs` skill and pointed at from `brainstorming`, `executing-work`, and `writing-skills`. `docs/fleet-integration.md` is the integration contract in one place.
