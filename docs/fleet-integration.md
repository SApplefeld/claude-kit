# Fleet Integration

The kit runs inside sessions an external engine spawns, and this document is the contract between the two. The engine in question is the AI OS Spine, which delivers the kit per spawn with `--plugin-dir <payload>` rather than a per-account plugin install, sets a marker on every worker, and reads three of the kit's surfaces back. Everything here is the kit's half: what the engine must set, what the kit does with it, and where a mismatch shows up. `architecture.md` describes each mechanism in its own section, and `security-model.md` states what the gates buy; this document is the assembly.

Delivery through `--plugin-dir` is the reason the seams exist at all. A plugin loaded that way still fires its SessionStart, PreToolUse, PostToolUse, PreCompact, Stop, and StopFailure hooks, and `CLAUDE_PLUGIN_ROOT` still resolves to the payload directory, so every ambient hook the kit ships runs inside a worker exactly as it runs in an attended session. The marker is the only signal that separates the two.

## Environment contract

Nine variables carry the whole contract, two of them gate signals that must never arrive without the variable they gate. The kit's rule is that every environment override redirecting a path takes a second signal, so an override arriving alone is ignored with a note on stderr rather than honored.

- **`KIT_EXTERNAL_ENGINE=1`** declares the session a spawned worker. It redirects nothing and takes no second signal, because the engine setting it already controls the spawn outright.
- **`KIT_MEMORY_ROOT`** with **`KIT_MEMORY_ROOT_ALLOW_DATA=1`** points the memory store at the engine's per-instance store. The pair is load-bearing twice over: it selects which memory content reaches the model, and it is the condition the memq grant hook checks before allowing anything.
- **`KIT_MEMORY_PROJECT`** pins the store's `projects/<segment>` directory, which is otherwise derived from the worker's working directory. Set it on every spawn. The engine's three spawn shapes carry three working directories (the reviewer and the phone-driven worker run in the instance directory; a plan worker runs inside the repository it is working on, or a per-branch copy of it), so without the pin one instance's store fragments into a tier per working directory and a memory promoted out of a plan run lands where no later run and no reviewer ever reads. Omitting it does not fail: it fragments, and for the two spawn shapes that carry no run id (the reviewer and the phone-driven worker) the project-memory block then names the cwd-derived directory as the destination in the kit's own voice, so the fragmentation arrives stated rather than merely guessed at while nothing reports it as a misconfiguration. That is the failure worth designing against. Honored only alongside the store pair above, carrying no separate signal of its own for the same reason `KIT_RUN_ID` carries none, and answering the same directory-name grammar. Set it explicitly rather than relying on inheritance, which beats a value inherited from the parent environment; it does not beat configuration that runs inside the spawned session's own shells afterwards. Two behaviors to model: under a pin the project tier's content is fenced on the way into a session's context, because the worker that wrote it is not the session reading it back; and a session with no run id is told the pinned directory as its memory destination, with `MEMORY.md` beside it as the ordinary index, unlike a run's pending tier, alongside that pinned tier's own index lines under the same reduction and caps the type index gets.
- **`KIT_RUN_ID`** scopes the run's memory writes and reads. It is honored only alongside the store pair above, carries no separate signal of its own because it selects a subdirectory inside an already-gated store, and its value becomes a directory name, so it must satisfy a conservative token grammar of at most 40 characters that also refuses the Windows spellings aliasing onto a different directory than they name (dots-only, trailing dots, reserved device stems). A value failing the grammar is refused loudly rather than fallen back on.
- **`KIT_SPAWN_VECTOR`** and **`KIT_RUN_SECTION`** are optional provenance. They redirect nothing and are recorded in a pending memory's frontmatter.
- **`KIT_EVENTS_PATH`** with **`KIT_EVENTS_PATH_ALLOW=1`** redirects the goal event sink. Both or neither: an engine setting the path alone does not fail loudly to its own watcher, it keeps writing to the default `~/.claude/kit-events.jsonl` that nobody is watching, so shipping both together is a deployment precondition rather than a convenience.

## Hook stand-down

Under the marker, seven hooks change behavior and the rest run unchanged. `session-start.js` drops its drive-to-completion push and emits the In Progress plan inventory as plain information followed by one line stating that the engine's directive owns scope and continuation. Its compact-source re-load block still fires but names no skill of its own, saying "the skill the engine's directive names" where an attended session is told to re-invoke executing-work, so a compacted worker is not handed the loop the plan block withholds. Its other four blocks are unaffected, the backlog block included: a worker in a repository holding a `docs/backlog.md` still receives the item count and oldest-item age. `branch-reaper-nudge.js` and `kit-version-nudge.js` emit nothing, and `hook-canary.js` returns before its first child spawn. All four ask for something an attended operator would do and a headless worker cannot. `stop-docs-hygiene.js` keeps running but downgrades its blocking outcome to advisory text carrying no decision, so a worker is never held at its turn end for a library-hygiene pass its directive does not cover. `kit-compact-gate.js`, the PreCompact gate, allows every auto-compaction rather than deferring one, and the marker is checked ahead of both of its deny paths, so neither the boundary schedule nor the interactive deferral applies in a worker. A worker is fresh per section, so there is no mid-chapter context for a schedule to protect, and it is unattended, so there is no discussion for the interactive deferral to keep intact; a worker therefore compacts at whatever trigger the machine's `autoCompactWindow` sets. `chapter-boundary-nudge.js`, the PostToolUse hook that reminds a leashed session of its chapter-close checkpoint, emits nothing for the same reason read from the other end: with no compaction schedule to protect there is no checkpoint to owe, and a worker that is fresh per section has no boundary ritual to be reminded of. Those two are the stand-downs taken for a scope reason rather than an attendance one.

Everything else stays live deliberately: the doctrine refresh, the memory wiring, all four PreToolUse deny guards, the grant hook, the two PostToolUse hooks the marker does not touch (`format-on-edit.js` and `memory-usage-stamp.js`), the goal leash, and the StopFailure logger. The logger is worth one line for the engine, because it writes where a worker's own state lives: a turn that dies of an API error appends to `.kit/stop-failure-events.jsonl` and rewrites `.kit/stop-failure-latest.json` under the payload's cwd. Those two files are a record on disk rather than a contract surface: nothing in the engine protocol reads them, and they are named here so a worker's `.kit/` directory holds no file whose writer is unaccounted for. Nothing resumes from it in a worker, since the watcher that acts on a marker is a machine-side scheduled task that requires an armed kit goal bound to the dead session, and an engine directive arms none. Guards and memory are wanted inside a worker, and the leash needs no marker of its own, because nothing an engine directive does can bind one. A session holds the leash in one of two ways: it ran the `/kit-goal` arm CLI, which binds the session its own shell names once it corroborates that id against a transcript on disk, or its transcript carries the user's own arming text, a plan path inside a `/kit-goal` command-argument span or a message leading with the `/kit-goal` token whose argument block names the plan. A directive is prose that runs no arm, so a worker whose directive merely names a plan is a bystander.

Two controls go with the canary and are worth naming rather than discovering. Its SHA-256 integrity check over the shipped hook files does not run in a worker, so payload tampering is undetected there and payload integrity is the deploy's concern. Nor do its both-direction probes of the memq grant, which means a grant gone inert in a fleet worker produces no signal at all beyond the worker quietly losing memq.

## Run-scoped memory

A run's memory writes are quarantined by scope rather than withheld. Every new memory file lands in `<store>/projects/<segment>/memory/pending/<run-id>/`, where `<segment>` is the pin when one is set and the sanitized working directory otherwise. Under the pin this contract mandates it is always the pin, and that is the path an adjudicator promotes from. The file is stamped with `run:`, `written:`, and the optional `vector:` and `section:` provenance. The run reads its own pending memories back through `find`, `get`, `recall`, and `recent` exactly as it reads the project tier, with `get` resolving pending ahead of project and `recent` counting the tier's stamps and files alongside the others'. What the tier withholds is entry into the shared record, and that is the engine's half of the contract: promotion of a pending memory into the project tier and the `MEMORY.md` index line that goes with it are an adjudication verdict the engine applies. The kit writes neither.

Two limits belong in the engine's model of this. The scoping is a resolution rule, not an enforced boundary: a process resolves the one directory its own `KIT_RUN_ID` names and enumerates no others, so cooperating runs do not see each other, but nothing stops a session holding Bash from naming a different id. And the tier bounds the project record only. `memq log` appends to the project-tier journal with a `run` field rather than rerouting, and `memq add-type` writes the shared type tier and its index directly, provenance-stamped rather than quarantined. Under a per-instance store the reach of both is that instance, which is why the store root the engine chooses is what actually does the containing.

## The memq grant

The engine's write-gated spawn vector refuses `node <script>` through the Bash tool, which would cost a worker memory recall and outcome logging, so `memq-grant.js` allows exactly that one command and nothing else. It grants only when the store pair is present, the command is one `node` invocation whose first argument resolves by normalized path equality to the payload's own `scripts/memq.js` in an absolute drive-rooted spelling, the interpreter on PATH is positively identified as the hook's own, and the whole command line carries no shell metacharacter. On anything else it stays silent and the call falls through to the vector's normal permission flow.

One coupling runs the other way and the engine owns it. The hook refuses the grant outright whenever `NODE_OPTIONS`, `NODE_PATH`, or `NODE_REPL_EXTERNAL_MODULE` is set at all, because node honors all three in the granted child. An engine that sets any of them ambiently on its spawns, and a benign `--max-old-space-size` would do it, turns this grant dark: workers keep running and quietly fall back to the vector's deny, losing memq with no error anywhere. Over-refusing is the correct direction for a grant surface, so the behavior is deliberate, but the engine's spawn environment therefore decides whether fleet workers keep the memory CLI.

Two further facts bound what the grant means. It conditions on the store pair alone, so under the pair without a valid run id a granted memq writes the project tier directly rather than pending. And it is agent-blind: a read-only judgment agent running inside a worker gets prompt-free memq writes, which `security-model.md` records with its compensating controls and their limits.

## What the engine reads

Three surfaces flow back out. The goal event stream at `~/.claude/kit-events.jsonl`, or wherever both events variables point it, carries one JSON object per line; inside a run each line gains a `run` field carrying `KIT_RUN_ID`, and only a value the kit's own run-id grammar accepts, so the event stream and the memory store cannot disagree about what a run id is. The field's presence says the process was told a run id, not that run-scoped memory was active, because the pending tier additionally requires the store pair. The full consumer contract, field caps, PII call, and dedup rules are in `architecture.md` under Goal release events. One cadence property matters to an engine reading the stream as run telemetry: an arming may name a sequence of plans, and the stream then carries one event per plan rather than one per run, each naming the plan that finished under a single unchanging `session`. Only the last of them coincides with the leash releasing, so a `goal-complete` says a plan is done and never that the worker is.

The pending tier is the second, read by the adjudicator that promotes from it. The plan doc is the third, and its header and structure are a frozen v1 machine contract: nine parsed shapes, each case-sensitive and anchored to the start of a line, four of them carrying a value rule the engine enforces silently rather than loudly. A plan may also carry an `## Assumptions` section between `## Out of Scope` and `## Chapters`, holding the assumptions the plan was approved on; it adds no row and is inert to the parser, and the kit freezes it at approval and routes every execution-time assumption to the Chapters instead, so the region the approval-scoped fingerprint covers is not rewritten by ordinary progress. The `## Chapters` block carries a second entry kind alongside the Chapters themselves: a run that goes long with work in flight and no section closing appends an `### Interim board N - YYYY-MM-DD` entry recording each in-flight section's stage, the live dispatches and what each was asked, the current gate baseline, the rulings adopted since the last boundary, and the next action per section. That heading cannot match the parsed `### Chapter N` row, which reads only the literal word and the number, and the entry carries no `Completed:` line, so a Chapter's own completion and next lines are still the first ones the engine finds. The `curating-docs` skill owns the table and is the normative reference, with pointers from `brainstorming`, `executing-work`, and `writing-skills` so the rule sits in the skill a session has loaded at the moment it writes a header or a Chapter. The `Model:` value rule is one of the silent ones: the engine accepts only the bare tokens `haiku`, `sonnet`, `opus`, and `fable`, downgrading anything else to a sonnet default with no error, and the kit's skills emit only those bare tokens, with a section's execution locus carried on its separate `Locus:` line that no consumer parses. Changing the shape or value rule of any row is a coordinated versioned change across both repositories, never a drive-by edit to plan-doc prose.
